[#what]
== What OmniFaces Is, and What It Is Not

Every Faces project grows the same helper classes. One fetches a request parameter without navigating
`+FacesContext.getCurrentInstance().getExternalContext().getRequestParameterMap()+`; one adds a `+FacesMessage+` in one line; one turns a
`+byte[]+` into an image; one registers a filter to compress the response. OmniFaces is that collection, maintained as a library: a
_utility library_ for standard Faces. Its own description is that it focuses on utilities that ease everyday tasks with the standard Faces API, and
that it does not and will not contain visual components such as rich tables or look and feels. It works with any component library;
the OmniFaces showcase application is itself built with PrimeFaces.

That scope separates it from PrimeFaces (see xref:web/jsf/primefaces-getting-started-and-themes.adoc[the PrimeFaces pages] of this section, which start with the setup and continue with xref:web/jsf/primefaces-ajax-forms-and-validation.adoc[Ajax and forms], xref:web/jsf/primefaces-data-components.adoc[data components] and xref:web/jsf/primefaces-extensions.adoc[PrimeFaces Extensions]), which is a UI library: PrimeFaces gives you a data table and a
dialog, OmniFaces gives you the missing `+@Param+` annotation, the validator that compares two fields, a handler that makes an Ajax failure show
your error page, and a few output components (`+o:cache+`, `+o:tree+`, `+o:highlight+`) that render no widget markup of their own.

OmniFaces is organised by the kind of artefact it adds. The table lists the packages under `+org.omnifaces+` and the sections of this page that
cover them; the showcase groups its examples the same way.

Three design choices explain how the library behaves. First, it is a WAR library: it is a web fragment with CDI extensions and Faces configuration
that it registers by itself, and the jar belongs in `+WEB-INF/lib+` of each web application (<<install>>). Second, it keeps its own dependencies to a minimum:
Bean Validation is optional, and the library bundles its own JSON encoder, XML helpers and cache. Third, it prefers the standard to the proprietary where the standard has caught up. Several ideas that OmniFaces offered first reached Faces itself:
`+f:importConstants+` and `+f:websocket+` (both in Faces 2.3; `+o:socket+` of OmniFaces 2.3 came first), CDI injection into converters and validators (Faces 2.3, and
`+managed=true+` in 4.0), and a CDI replacement for `+@ManagedProperty+` (`+jakarta.faces.annotation.ManagedProperty+`, covered on
xref:web/jsf/backing-beans-and-cdi.adoc#managed-property[the backing beans page]), which injects a value by EL expression and coerces it by the EL rules but, unlike `+@Param+` (<<param>>), has no Faces converter, validator or
message. The OmniFaces documentation says so on the page of the feature concerned, and this page does the same: for every
feature it states whether the standard now covers the case and when to reach for OmniFaces anyway.

  <artifactId>omnifaces</artifactId>
  <version>5.5.5</version>

The 4.x and 3.x lines receive the bugfixes of 5.x but no new features. The 5.5.5 and 4.7.15 releases are dated the same day and carry the same fixes. A Faces
4.0 server (Jakarta EE 10) therefore stays on 4.7.15 until it moves to Jakarta EE 11, and a Faces 4.1 server uses 5.5.5. The one
optional dependency worth knowing is Bean Validation (version 3.1 for 5.x), needed only for `+o:validateBean+` and `+FacesLabelMessageInterpolator+`.

Three rules about where the jar goes, from the project documentation:

* *Only in `+WEB-INF/lib+` of the WAR.* Placed in an EAR `+lib+` directory or in the server's own library directory, the webapp cannot find
  the Faces and CDI annotated classes inside the jar, and fails at deployment or at run time.
* *Never twice.* A second copy of the jar makes CDI report ambiguous dependencies at deployment.
* *Servlet container.* On Tomcat (xref:web/jsf/tomcat-and-weld.adoc[Tomcat and Weld]) the jar works with Weld and either Faces implementation (all examples of this page ran that way); a server such as
  WildFly or GlassFish needs nothing else (xref:web/jsf/jakarta-ee-servers.adoc[Jakarta EE servers]). On Spring Boot the JoinFaces starter `+omnifaces-spring-boot-starter+` pulls in the Faces and Weld starters and maps
  `+joinfaces.omnifaces.*+` properties to the `+org.omnifaces.*+` context parameters. On Quarkus the Quarkiverse extension `+quarkus-omnifaces+` exists. The
  xref:web/jsf/spring-boot-with-joinfaces.adoc#starters[Spring Boot with JoinFaces] and xref:web/jsf/quarkus.adoc#omnifaces[Quarkus] pages of this section cover those setups.

On start-up the library logs one line that confirms it was found (`+INFO: Using OmniFaces version 5.5.5+` in the scratch runs, from `+ApplicationInitializer+`).

=== The XML namespace

OmniFaces 5 declares every tag and every EL function under one URN namespace:

.The namespace declarations
[source,xml]
----
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core"
      xmlns:o="omnifaces"
      xmlns:sec="omnifaces.security">
----

Source: https://omnifaces.org/[OmniFaces: XML namespaces]

The history matters when you read older code. OmniFaces 1.x to 4.x declared the tags with `+xmlns:o="http://omnifaces.org/ui"+` and the
EL functions with a second prefix, `+xmlns:of="http://omnifaces.org/functions"+`, so that the books and blog posts you find call the functions as
`+#{of:abbreviate(...)}+`. In 5.0 both were merged into `+xmlns:o="omnifaces"+`, and the functions are called as `+#{o:abbreviate(...)}+`. The security
tags (`+sec:+`) are new in 5.0 and use `+xmlns:sec="omnifaces.security"+`. The migration is three steps: change the `+o+` namespace, rename `+of:+` calls to `+o:+`, remove the
`+of+` declaration. The old URL namespaces still work in 5.5.5 (a page declaring `+xmlns:o="http://omnifaces.org/ui"+` and `+xmlns:of="http://omnifaces.org/functions"+`
rendered `+#{of:abbreviate('The quick brown fox', 10)}+` as `+The quick...+` on both implementations, with no warning in the log), but the taglibs that provide them
state that they are deprecated and will be removed in 6.x. New code uses the URN namespace.

=== What registers itself

OmniFaces needs no entry in `+web.xml+` or `+faces-config.xml+` for most of its features: the jar ships a `+faces-config.xml+` that is ordered after all other
configuration files, a `+web-fragment.xml+` marked `+<distributable/>+`, a `+beans.xml+`, four CDI extensions and one `+ServletContainerInitializer+`. The following
list was read from the jar of 5.5.5, and it explains behaviour that otherwise looks magical: the extra `+omnifaces.js+` script in the head, the hidden form
that OmniFaces adds to a page without a form when a component needs one (`+omnifaces_form+` in the scratch run of `+o:deferredScript+`), or the way a view scoped bean is destroyed.

Two consequences follow. A feature that appears inactive (the combined resource, the CDN) is inactive because it is opt-in, not because OmniFaces failed to load.
And because the jar replaces the render kit, the partial view context and the view handler by wrapping them, it composes with PrimeFaces and other libraries that do the same;
the scratch run of this page (<<primefaces>>) used both libraries together on both implementations.

[#lifecycle]
== Where OmniFaces Sits in the Request Processing Lifecycle

The utilities that need a lifecycle position hook into the six phases (see xref:web/jsf/request-processing-lifecycle.adoc#phases[the lifecycle page]) as the diagram
shows. The positions come from the Javadoc and from the source of the 5.5.5 sources jar; the sections below repeat them where they change behaviour.

[mermaid]
----
flowchart LR
    A[Restore View] --> B[Apply Request Values] --> C[Process Validations] --> D[Update Model Values] --> E[Invoke Application] --> F[Render Response]
    A1["@Eager(viewId) beans created after the phase; o:enableRestorableView rebuilds an expired view"] -.-> A
    B1["o:inputHidden converts and updates here; o:viewParam, o:hashParam, o:scriptParam"] -.-> B
    C1["o:validateEqual and the other multi-field validators when the tree walk reaches them; o:validateBean class level, before and after the phase; o:skipValidators"] -.-> C
    D1["o:validateBean with method validateActual runs after the phase"] -.-> D
    E1["o:viewAction evaluates its if attribute here; @RateLimit runs on the action method; Ajax.update and Ajax.oncomplete"] -.-> E
    F1["o:cache, o:highlight, o:messages, o:graphicImage URLs; CombinedResourceHandler; the handle of FullAjaxExceptionHandler after every phase"] -.-> F
----

Anything that reads a request parameter, `+@Param+` among them, runs when the bean that holds it is created, which is a different moment from
all of the above: the first time a view or a class refers to the bean. <<param>> shows what that costs.

[#faces-util]
== The Utility Classes: Faces, FacesLocal and Friends

`+org.omnifaces.util.Faces+` is the class most people meet first. It is a set of static shortcuts that "flatten" the hierarchy of objects that you reach from
`+FacesContext+`, plus a number of helpers that remove multi-line boilerplate: `+Faces.getRequestParameter(name)+` instead of the chain through the external context,
`+Faces.redirect(...)+` that prepends the context path and URL-encodes its parameters, `+Faces.sendFile(...)+` that streams a download, `+Faces.getLocale()+` that never returns null.
`+FacesLocal+` has the same methods with the `+FacesContext+` as first argument; use it in code that calls many of them, to look up the thread-local context once.
The classes beside it follow the same pattern for a different part of the API:

.The static utility classes of `+org.omnifaces.util+`
[cols="2,5",options="header"]

|Class |What it is for

|`+Faces+`, `+FacesLocal+`
|Request, session, cookie, locale, view, project stage, resource bundle, redirect, `+sendFile+`, `+getBookmarkableURL+`, metadata attributes, `+evaluateExpressionGet+`

|`+Messages+`, `+MessagesLocal+`

=== A bean that uses them

The bean reads parameters and settings, adds messages, redirects with encoded parameters and sends a file. It is the `+UtilsBean+` of the scratch application:

.UtilsBean.java
[source,java]
----
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Named;
import java.nio.charset.StandardCharsets;
import java.util.List;
import org.omnifaces.util.Faces;
import org.omnifaces.util.Messages;

@Named
@RequestScoped
public class UtilsBean {

    public String getQuery() {
        // null when absent, no Map lookup and no null checks on the chain
        return Faces.getRequestParameter("q");
    }

    public Integer getPage() {
        // typed access: converts with the Faces converter for Integer, null when absent or invalid
        return Faces.getRequestParameter("page", Integer.class);
    }

    public String getBaseUrl() {
        return Faces.getRequestBaseURL();
    }

    public String getViewId() {
        return Faces.getViewId();
    }

    public String getStage() {
        return Faces.getProjectStage().toString();
    }

    public String getMapping() {
        return Faces.getMapping();
    }

    public List<String> getLocales() {
        return Faces.getSupportedLocales().stream().map(Object::toString).toList();
    }

    public java.time.LocalDate getStart() { return java.time.LocalDate.of(2020, 1, 15); }
    public java.time.LocalDate getEnd() { return java.time.LocalDate.of(2026, 10, 8); }

    public void greet() {
        Messages.addGlobalInfo("Welcome back, {0}!", "reader");
    }

    public void problem() {
        Messages.addError("form:title", "The title {0} is already on the shelf", "Dune");
        Messages.addGlobalWarn("Your changes were not saved");
    }

    public void builder() {
        Messages.create("Review saved").detail("Thank you, {0}", "reader").add();
    }

    public String flashAndRedirect() {
        Messages.addFlashGlobalInfo("Book {0} added", 42);
        return "utils?faces-redirect=true";
    }

    public void redirectWithParams() {
        // parameters are URL-encoded by Faces.redirect
        Faces.redirect("utils.xhtml?q=%s&page=%d", "war & peace", 2);
    }

    public void download() {
        Faces.sendFile("hello.txt".getBytes(StandardCharsets.UTF_8), "hello.txt", true);
    }

    public void downloadNamed() {
        String name = Faces.getRequestParameter("name");
        Faces.sendFile("x".getBytes(StandardCharsets.UTF_8), name, true);
    }
}
----

What the runs showed, on Mojarra and on MyFaces alike:

* `+utils.xhtml?q=dune+` rendered `+q=dune+`; `+page+` was empty because `+Faces.getRequestParameter("page", Integer.class)+` returns `+null+` for an absent parameter,
  and `+?page=3+` gave `+3+`. The base URL was `+http://localhost:8570/bookshelf/+`, the view id `+/utils.xhtml+`, the stage `+Production+` and the mapping `+.xhtml+`.
* `+Faces.getSupportedLocales()+` returned `+[en, es]+` only after the application declared `+<locale-config>+` with a default locale `+en+` and a supported locale `+es+`;
  without it the list was empty on both implementations, so do not rely on the Javadoc's remark that the default locale comes first before you configure the locales (see
  xref:web/jsf/messages-and-i18n.adoc#locale-selection[the messages page]).
* `+Faces.redirect("utils.xhtml?q=%s&page=%d", "war & peace", 2)+` sent the browser to `pass:c[utils.xhtml?q=war+%26+peace&page=2]`: the format arguments are URL-encoded, the
  format string is not, and the context path was added for a relative path. Encode the arguments of a redirect with this method; do not concatenate user input into the path.
* `+Faces.sendFile(bytes, name, true)+` answered `+Content-Disposition: attachment;filename="hello.txt"; filename*=UTF-8''hello.txt+` with the content type derived from the
  file name. The file name goes through percent-encoding: a name with a quote, a backslash or a CR-LF pair
  (`+a"b.txt+`, `+..\..\x.txt+`, `+a<CR><LF>X-Evil: 1.txt+`) came out as `+a%22b.txt+`, `+..%5C..%5Cx.txt+` and `+a%0D%0AX-Evil%3A%201.txt+` in both parameters, so header injection is
  prevented. The encoding is not a path sanitiser, though: the name still contains the separators, which a browser removes when it saves the file. Build the name from your own data,
  never from the request, and apply the checks of xref:web/jsf/file-upload-and-download.adoc#content-disposition[the download section] (including
  xref:web/jsf/file-upload-and-download.adoc#csv-injection[the CSV formula escaping]) before you send anything the user typed.

=== The faces EL object

The `+FacesELResolver+` (since 2.6) exposes the parameterless `+get...+` and `+is...+` methods of `+Faces+` that return a `+String+` or a `+boolean+` as properties of an
implicit object `+#{faces}+`. The Faces 4.1 specification has no such object, so this is an OmniFaces feature and works only with OmniFaces in the application. Observed on both
implementations: `+#{faces.development}+` (`+false+` in `+Production+`), `+#{faces.requestBaseURL}+`, `+#{faces.requestContextPath}+` (`+/bookshelf+`), `+#{faces.ajaxRequest}+` and
`+#{faces.serverInfo}+` (`+Apache Tomcat/11.0.26+`) resolved, while `+#{faces.contextPath}+` and `+#{faces.projectStage}+` failed on both (Mojarra's message: `+#{faces.contextPath} does not exist+`), because there is no
getter of that name that returns a string or a boolean. The Javadoc of `+importFunctions+` itself prefers `+#{faces.development}+` or `+#{request.contextPath}+` to calling the function form.

Source: https://omnifaces.org/docs/javadoc/current/org.omnifaces/org/omnifaces/el/FacesELResolver.html[OmniFaces 5.5.5 API: FacesELResolver]

=== The @messages search keyword

[#messages]
== The Messages Utility and o:messages

Adding a message by hand takes a client id, a severity, a summary and a detail, and a `+MessageFormat+` call if there are arguments. `+Messages+` reduces each case to one line.
The summary is formatted with `+MessageFormat+` and the given arguments by default, so `+{0}+` is a placeholder (a literal quote or brace in the text has the usual `+MessageFormat+` rules).

.The ways to add a message
[source,java]
----
// A global message (no client id)
Messages.addGlobalInfo("Welcome back, {0}!", "reader");
Messages.addGlobalWarn("Your changes were not saved");

// A message for one component, by its full client id
Messages.addError("form:title", "The title {0} is already on the shelf", "Dune");

// With a detail, through the builder
Messages.create("Review saved").detail("Thank you, {0}", "reader").add();

// Survives a redirect (flash scope), for Post/Redirect/Get
Messages.addFlashGlobalInfo("Book {0} added", 42);
return "utils?faces-redirect=true";

// In a validator or a converter
Messages.throwValidatorException("Invalid input.");
throw Messages.asConverterException("Unknown input.");
----

Source: https://omnifaces.org/docs/javadoc/current/org.omnifaces/org/omnifaces/util/Messages.html[OmniFaces 5.5.5 API: Messages] and https://showcase.omnifaces.org/utils/Messages[OmniFaces showcase: Messages]

Observed with the `+UtilsBean+` above: the three actions rendered `+Welcome back, reader!+` in `+h:messages+`, the pair `+The title Dune is already on the shelf+` (also on the `+h:message for="title"+`
of the form) and `+Your changes were not saved+`, and `+Review saved+` for the builder (the detail `+Thank you, reader+` is added too, but `+h:messages+` shows the summary unless `+showDetail="true"+`).
The flash message appeared on the redirected page, `+Book 42 added+`, which is what the flash is for (see
xref:web/jsf/flash-and-post-redirect-get.adoc#flash[the flash page]). The methods exist per severity (`+Info+`, `+Warn+`, `+Error+`, `+Fatal+`) in the global, per-client-id and flash variants,
with `+clear...+` methods and `+isEmpty()+` checks beside them.

*Resource bundle keys.* The shortcuts take the message text, not a bundle key, so an internationalised application sets a _resolver_ once: `+Messages.setResolver(...)+` with an
implementation of `+Messages.Resolver+` that looks the text up in the bundle for `+Faces.getLocale()+` (the Javadoc has the example). The resolver can be set only once, early
(in a `+@Startup+` bean for instance, <<eager>>). That example was not run; the standard way of putting localised messages on the page is on
xref:web/jsf/messages-and-i18n.adoc#faces-message[the messages page].

=== o:messages

`+o:messages+` extends `+h:messages+` with four things. `+for+` accepts several client ids separated by spaces, and ids of non-input containers that hold inputs, so one
list of errors can serve a group of fields. `+message+` shows one fixed text whenever any of the listed components has a message ("There are validation errors. Please fix them."). `+var+` hands each
`+FacesMessage+` to the body, so the markup is yours (the iteration is stateless and meant for output). `+escape="false"+` switches the escaping off; the Javadoc itself warns of cross-site scripting
when user-controlled text is redisplayed, and the rule of this section applies: leave it `+true+`. The scratch run used `+<o:messages for="form:title form:author"/>+` and showed
`+Book title: Validation Error: Value is required.+` for the first field, where the label `+Book title+` comes from `+o:outputLabel+` (<<tags>>).

Source: https://showcase.omnifaces.org/components/messages[OmniFaces showcase: messages] and https://omnifaces.org/docs/vdldoc/current/o/messages.html[OmniFaces VDL: o:messages]

[#ajax-util]
== The Ajax Utility

Standard Ajax decides what is re-rendered in the view: the `+render+` attribute of `+f:ajax+` lists the ids (see xref:web/jsf/ajax.adoc#execute-render[the Ajax page]). When the bean knows better,
`+org.omnifaces.util.Ajax+` adds to the list from Java, runs a script when the response has been processed, and passes data to that script. It works through the
`+OmniPartialViewContext+` that the jar installs, so it needs nothing in the page:

.AjaxUtilBean.java
[source,java]
----
package org.example.bookshelf.web;

import jakarta.faces.view.ViewScoped;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.Map;
import org.omnifaces.util.Ajax;

@Named
@ViewScoped
public class AjaxUtilBean implements Serializable {
    private static final long serialVersionUID = 1L;
    private int clicks;
    private int other;

    public void click() {
        clicks++;
        other++;
        // adds the component to the render list although the f:ajax tag did not name it
        Ajax.update("other");
        // arguments for the on-complete script, available as OmniFaces.Ajax.data in JavaScript
        Ajax.data(Map.of("clicks", clicks, "title", "Dune"));
        Ajax.oncomplete("window.result = OmniFaces.Ajax.data.title + ':' + OmniFaces.Ajax.data.clicks + ':' + OmniFaces.Ajax.validationFailed");
    }

    public int getClicks() { return clicks; }
    public int getOther() { return other; }
}
----

.ajaxutil.xhtml
[source,xml]
----
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core"
      xmlns:o="omnifaces">
<h:head><title>Ajax util</title></h:head>
<h:body>
  <h:form id="form">
    <h:commandButton id="b" value="click" action="#{ajaxUtilBean.click}"><f:ajax render="mine"/></h:commandButton>
    <h:outputText id="mine" value="#{ajaxUtilBean.clicks}"/>
  </h:form>
  <h:outputText id="other" value="#{ajaxUtilBean.other}"/>
  <o:onloadScript>window.loads = (window.loads || 0) + 1;</o:onloadScript>
</h:body>
</html>
----

Source: https://omnifaces.org/docs/javadoc/current/org.omnifaces/org/omnifaces/util/Ajax.html[OmniFaces 5.5.5 API: Ajax] and https://showcase.omnifaces.org/utils/Ajax[OmniFaces showcase: Ajax]

In headless Chrome, two clicks on the button on Mojarra and on MyFaces updated `+form:mine+` (named in `+f:ajax render+`) _and_ the `+other+` output outside the form (named only in the bean), both to `+2+`; the script
set `+window.result+` to `+Dune:2:false+`, that is the data from `+Ajax.data+` and `+OmniFaces.Ajax.validationFailed+` (new in 5.4: the value of `+FacesContext.isValidationFailed()+` for that response, so a
script can react to a failed validation without reading the DOM). `+o:onloadScript+` ran its body on the initial load and after each of the two Ajax responses (three times), which is how to re-apply
a jQuery plugin to markup that an Ajax response replaced. Other methods of the class are `+updateRow(UIData, int)+` and `+updateColumn(UIData, int)+` (the cell content must be wrapped in a container with a fixed id),
`+load(library, resource)+` to add a script resource on completion, `+updateAll()+` and `+isExecuted(clientId)+`.

Two limits to remember. The `+data+` values are encoded as JSON by the library's own encoder, which supports numbers, strings, booleans, dates, arrays, collections, maps and (as a last resort) JavaBeans, so send plain values,
and never put secrets in them: everything lands in the browser. And `+Ajax.update+` takes client ids, so an id inside a naming container needs its full path (`+form:mine+`), as everywhere else in Faces.

`+o:form+` (<<tags>>) complements this on the request side: it posts only the parts of the form that the Ajax execute list needs.

[#param]
== @Param, @Cookie and @ContextParam: Injecting Request Data

A bookmarkable page (xref:web/jsf/view-parameters-and-view-actions.adoc#overview[see the view parameters page]) usually declares `+f:viewParam+` in `+f:metadata+`, adds a `+f:viewAction+` or a `+preRenderView+` listener to load the
data, and puts the loaded value into the bean in a method the framework calls at a particular phase. `+@Param+` collapses this: the request parameter is injected into the
bean's field, converted and validated, and is available in `+@PostConstruct+`.

.DetailParams.java
[source,java]
----
package org.example.bookshelf.web;

import jakarta.annotation.PostConstruct;
import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;
import org.omnifaces.cdi.Cookie;
import org.omnifaces.cdi.Eager;
import org.omnifaces.cdi.ContextParam;
import org.omnifaces.cdi.Param;
import org.omnifaces.cdi.param.ParamValue;
import jakarta.faces.validator.LengthValidator;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import org.omnifaces.cdi.param.Attribute;

@Eager(viewId = "/param-first.xhtml")
@Named
@RequestScoped
public class DetailParams {

    @Inject
    @Param(name = "id", label = "Book id")
    private Long id;

    @Inject
    @Param(name = "tag")
    private List<String> tags;

    @Inject
    @Param(name = "isbn", validatorClasses = LengthValidator.class,
           validatorAttributes = { @Attribute(name = "minimum", value = "10"),
                                   @Attribute(name = "maximum", value = "13") },
           validatorMessage = "{1}: the ISBN must have 10 to 13 characters", label = "ISBN")
    private String isbn;

    @Inject
    @Param(name = "n", label = "Page size")
    @Min(1) @Max(100)
    private Integer pageSize;

    @Inject
    @Param(name = "year", converter = "jakarta.faces.Integer")
    private ParamValue<Integer> year;

    @Inject
    @Cookie(name = "theme")
    private String theme;

    @Inject
    @ContextParam(name = "jakarta.faces.PROJECT_STAGE")
    private String stage;

    @Inject
    private BookService books;

    private Book book;

    @PostConstruct
    void init() {
        // the injected values are already available here, no f:viewAction or preRenderView needed
        if (id != null) {
            book = books.find(id);
        }
    }

    public Long getId() { return id; }
    public List<String> getTags() { return tags; }
    public String getIsbn() { return isbn; }
    public Integer getPageSize() { return pageSize; }
    public Integer getYear() { return year.getValue(); }
    public String getTheme() { return theme; }
    public String getStage() { return stage; }
    public Book getBook() { return book; }
}

The elements of `+@Param+` (all `+@Nonbinding+`, so they do not change which bean CDI injects):

.The elements of @Param (5.5.5)
[cols="2,5",options="header"]
|===
|Element |Meaning

|`+name+`
|The request parameter name; defaults to the name of the field (or of the constructor parameter, if the class is compiled with `+-parameters+`)

|`+pathIndex+`, `+pathName+`
|The zero-based index of a path parameter (needs the `+FacesServlet+` mapped by prefix, or FacesViews with MultiViews, <<facesviews>>); the name of a dynamic route segment (5.5). Setting both is an `+IllegalArgumentException+`

|`+label+`
|The label in messages; observed: `+Book id: 'abc' must be a number consisting of one or more digits.+`

|`+converter+`, `+converterClass+`, `+converterAttributes+`, `+converterMessage+`
|A converter id, an EL expression for an id or an instance, or a class; attributes as `+@Attribute(name, value)+`

|`+validators+`, `+validatorClasses+`, `+validatorAttributes+`, `+validatorMessage+`, `+required+`, `+requiredMessage+`
|The same for validators; `+{1}+` in a message is the label

|`+globalMessage+`
|Attach the message to no component (since 4.5); the default attaches it to the view root, shown by `+<h:messages for="#{view.id}"/>+`

|`+disableBeanValidation+`, `+overrideGlobalBeanValidationDisabled+`
|Switch Bean Validation for this field off, or on despite the global switch
|===

Supported field types are `+String+`, every type with a Faces converter, `+List<T>+` and arrays (for repeated parameters, `+?tag=a&tag=b+` gave `+[a, b]+`), and
`+ParamValue<T>+` for a converted value that is not serializable: the bean is serializable, the `+ParamValue+` is converted again from the original parameter after deserialisation.
A `+ParamValue+` always holds the submitted string beside the converted value (`+getSubmittedValue()+`), which is useful in a message.

What the scratch run showed (identical on Mojarra and MyFaces):

* `+?id=2&tag=a&tag=b&isbn=1234567890&n=20&year=1990+` injected `+2+`, `+[a, b]+`, `+1234567890+`, `+20+` and `+1990+`, and `+@PostConstruct+` loaded the book (`+Cosmos+`).
* `+?id=abc+` left `+id+` null and added `+Book id: 'abc' must be a number consisting of one or more digits.+`. A failed field is `+null+` and the bean still exists (the Javadoc adds that
  `+FacesContext.isValidationFailed()+` is `+true+` afterwards): code in `+@PostConstruct+` must cope with `+null+`.
* `+?isbn=123&n=0+` produced `+ISBN: the ISBN must have 10 to 13 characters+` (the `+validatorClasses+` element, with `+{1}+` in the message replaced by the label) and `+must be greater than or equal to 1+` (the Bean Validation constraint `+@Min(1)+` on the
  field; Bean Validation messages carry no label); `+?n=500+` gave `+must be less than or equal to 100+`. Bean Validation annotations on the injected field are honoured, and `+@Param+` is a way to get server-side validation of query parameters
  without writing any Java validator.
* `+@Cookie(name = "theme")+` injected `+dark+` for a request that carried `+Cookie: theme=dark+`, and `+@ContextParam(name = "jakarta.faces.PROJECT_STAGE")+` injected `+Production+`. `+@Cookie+` has no validation "by design" according to the Javadoc; that is no reason to trust it, because the user
  controls their cookies as completely as the query string. Validate a cookie value yourself before it reaches a query, a file name or a redirect.

=== When the messages appear

A `+@Param+` field is injected when the bean is created, and in a request scoped bean that is the first time the page refers to it. Messages added at that moment land in the queue only if
the component that displays them has not rendered yet. In `+param.xhtml+` the `+h:messages+` is _after_ the expressions that touch the bean, so the messages showed. Move it to the top
and they do not: the scratch page `+param-first.xhtml+`, identical but with the messages first, rendered an empty `+ul id="msgs"+` for `+?id=abc+` on Mojarra. Two ways to fix it, and a third that does not work:

* Put the messages component after the first use of the bean. Cheap, and a trap for the next person who tidies the page.
* Make the bean eager for the view with `+@Eager(viewId = "/param-first.xhtml")+` (<<eager>>): it is created after the Restore View phase, before rendering, and the message appeared above the list on both implementations.
* `+@Eager(requestURI = ...)+` does _not_ work here: the bean is then created before the `+FacesServlet+` runs, there is no `+FacesContext+`, and the injection fails with
  `+NullPointerException: Cannot invoke "FacesContext.getApplication()" because "context" is null+` in `+ParamProducer+`; the Javadoc of `+@Eager+` states that the `+FacesContext+` is not available in that case, and OmniFaces logs
  `+Could not instantiate eager request scoped beans for request ...+`.

A related difference to `+f:viewParam+`: `+@Param+` runs at bean creation, which can be in any phase, including Render Response. A conversion error in a `+f:viewParam+`, by contrast, stops the lifecycle at Process Validations
for the view, and invokes `+f:viewAction+` only if everything passed. When you need the "validate everything first, then act" semantics, use `+o:viewParam+` with `+o:viewAction+` (<<viewparam>>).

=== Path parameters

`+@Param(pathIndex = 0)+` reads the first segment after the page name (`+/book/978-0441013593+` mapped to `+book.xhtml+`), which needs a prefix-mapped `+FacesServlet+` or FacesViews with MultiViews. The scratch run of that is in <<facesviews>>.
Path parameters are as untrusted as query parameters; in the run, `+/books/abc/reviews+` injected the string `+abc+` into a `+pathName+` field without complaint, so add a converter or a validator wherever the value is not free text.

=== What changed

`+@Param+` has existed since OmniFaces 1.6; multi-valued parameters came in 2.4, path parameters in 2.5, `+globalMessage+` in 4.5 and `+pathName+` in 5.5. Between 3.6 and 5.3 a `+@Param+` field also worked without `+@Inject+`; since 5.4 that is deprecated, a warning is logged at
deployment for each such field, and it will be removed, so put `+@Inject+` next to every `+@Param+`. The standard alternative for a single string is `+@Inject @ManagedProperty("#{param.id}")+` (xref:web/jsf/backing-beans-and-cdi.adoc#managed-property[the backing beans page]), which has none of the conversion, validation and message features above.

[#eager]
== @Eager and @Startup

CDI creates beans lazily, at the first use. That is wrong for a bean that must do something at a defined moment: warm a cache when the application starts, register a listener, or prepare data when
a particular URL is requested. The old Faces `+@ManagedBean(eager = true)+` did the first; CDI has no equivalent, and `+@Eager+` fills the gap for five scopes.

.Where @Eager creates the bean
[cols="2,4",options="header"]
|===
|Declaration |The bean is created

|`+@Eager @ApplicationScoped+` (or `+@Startup+`)
|At application start

|`+@Eager @SessionScoped+`
|Whenever a session is created

|`+@Eager(requestURI = "/eager.xhtml") @RequestScoped+`
|When that context-relative URI is requested, before the `+FacesServlet+` runs, so no `+FacesContext+` yet

|`+@Eager(viewId = "/param-first.xhtml") @RequestScoped+`
|After the Restore View phase of that view, with a `+FacesContext+`

|`+@Eager(viewId = "...") @ViewScoped+` (Faces or OmniFaces)
|When that view is created; like the request scoped bean, a view scoped bean needs `+requestURI+` or `+viewId+`
|===

----

On Tomcat with Weld and Mojarra the log showed `+BookshelfStartup created at application start+` right after the line `+Using OmniFaces version 5.5.5+` and before Mojarra reported initialising the context: the startup
bean is created before Faces itself is started. The Javadoc says that `+FacesContext+` is not available in the `+@PostConstruct+` of `+@Eager+` beans declared without a `+viewId+`; inject the `+HttpServletRequest+`, `+HttpSession+`, `+ServletContext+` or other beans instead. `+EagerPage created for /eager.xhtml+`
appeared on the first request for `+/eager.xhtml+`. The `+@Startup+` that OmniFaces defines is a stereotype for `+@Eager @ApplicationScoped+`; the identically named `+jakarta.ejb.Startup+` needs an EJB container and turns the
class into a session bean, so watch the import. The scopes page has the same bean in a different role (xref:web/jsf/scopes.adoc#application[the application scope section]).

[#cdi-scopes]
== OmniFaces @ViewScoped and @RateLimit

=== The OmniFaces view scope

`+org.omnifaces.cdi.ViewScoped+` is an alternative to `+jakarta.faces.view.ViewScoped+` with a stricter lifecycle: the bean is destroyed (and its `+@PreDestroy+` called) when the browser unloads
the page, by a `+navigator.sendBeacon+` or keepalive fetch call, and not only when the session expires or the view map is evicted. The unload can be cancelled by a leave confirmation. It also physically removes the view state of the view from the
implementation's store, which reduces the risk of `+ViewExpiredException+` on the other views of the user. Its extra element, `+saveInViewState+`, stores the whole bean in the
view state (client state saving only, and the Javadoc cautions against it). The standard scope, its limits and the comparison are in xref:web/jsf/scopes.adoc#view-omnifaces[the scopes page]; what this page adds is a measurement.

The scratch run navigated headless Chrome from a page that used one bean of each kind to another page:

.OmniViewBean.java (the two beans differ in the import and the log text)
[source,java]
----
package org.example.bookshelf.web;

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.logging.Logger;
import org.omnifaces.cdi.ViewScoped;

@Named
@ViewScoped
public class OmniViewBean implements Serializable {
    private static final long serialVersionUID = 1L;
    private static final Logger LOG = Logger.getLogger("bookshelf");

    @PostConstruct
    void init() { LOG.info("OmniViewBean created"); }

    @PreDestroy
    void destroy() { LOG.info("OmniViewBean destroyed"); }

    public String getHello() { return "omni"; }
}
----

Source: https://omnifaces.org/docs/javadoc/current/org.omnifaces/org/omnifaces/cdi/ViewScoped.html[OmniFaces 5.5.5 API: ViewScoped] and https://showcase.omnifaces.org/cdi/ViewScoped[OmniFaces showcase: ViewScoped]

* On *Mojarra* both beans were destroyed within two seconds of leaving the page: `+StdViewBean destroyed+` and `+OmniViewBean destroyed+`. This is the side effect the Javadoc describes, that the standard view scoped beans referenced in the same view are destroyed too.
* On *MyFaces* only `+OmniViewBean destroyed+` appeared; the standard bean stayed until the view map was evicted or the session ended.

So the unload behaviour is a feature of the OmniFaces bean on both, and of the standard bean only on Mojarra, as a side effect. Do not depend on the side effect. Two other facts from the Javadoc: the bean must be `+Serializable+` (see xref:web/jsf/deployment-and-clustering.adoc#serialisable[serialisability in a cluster])
(the scope is passivating), and `+@PreDestroy+` must not use `+FacesContext+`. The number of live view scopes is limited per session by the context parameter `+org.omnifaces.VIEW_SCOPE_MANAGER_MAX_ACTIVE_VIEW_SCOPES+`,
or by the Mojarra or MyFaces parameter for the number of views if that one is present, with a default of 20.

=== @RateLimit

`+@RateLimit+` (since 5.0) limits how often a method of a CDI bean may run per client, using a sliding window. It is an interceptor binding; the default client identifier is the client's IP address.

.ReviewApi.java
[source,java]
----
package org.example.bookshelf.web;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Named;
import org.omnifaces.cdi.RateLimit;

@Named
@ApplicationScoped
public class ReviewApi {
    private int saved;

    /** At most 2 calls per client address and 60 seconds. */
    @RateLimit(maxRequestsPerTimeWindow = 2, timeWindowInSeconds = 60, maxRetries = 0)
    public String submit() {
        saved++;
        return null;
    }

    public int getSaved() { return saved; }
}
----

Source: https://omnifaces.org/docs/javadoc/current/org.omnifaces/org/omnifaces/cdi/RateLimit.html[OmniFaces 5.5.5 API: RateLimit] and https://showcase.omnifaces.org/cdi/RateLimit[OmniFaces showcase: RateLimit]

Four posts of the form through a button bound to `+reviewApi.submit+`: the first two ran (`+saved=1+`, `+saved=2+`), the third and fourth answered HTTP 500 and the log recorded
`+RateLimitExceededException: Rate limit exceeded for client ID '0:0:0:0:0:0:0:1'+` (the IPv6 loopback address of the test client). That is the default: the interceptor throws, and the exception handling
of your application decides what the user sees (a mapping for the exception in `+error-page+` or a handler, see xref:web/jsf/exception-handling.adoc#error-pages[the error pages section]). The element
`+maxRetries+` waits and retries instead of failing at once.

*The default client id can be forged.* `+Faces.getRemoteAddr()+`, which `+@RateLimit+` uses, takes the first address of the `+Forwarded+`, `+X-Forwarded-For+` or `+X-Real-IP+` request header when one is present, and the
request address only when none is. With the limit above exhausted, five more posts from the same machine, each with a different `+X-Forwarded-For: 10.0.0.n+` header, all succeeded (`+saved=3+` to `+saved=7+`). A rate limit keyed on the
default can therefore be bypassed by any client that can send a header. Either run the application behind a proxy that overwrites those headers (and reaches the application only through it), or set
`+clientId+` explicitly to something the client cannot choose: the authenticated user name or the session id.

Behind the limit, the same caution applies to `+Servlets.getRemoteAddr+` wherever else you use it for logging or access decisions.

[#viewparam]
== View Parameters Done Right: o:viewParam, o:viewAction and Friends

The view parameters page of this section (xref:web/jsf/view-parameters-and-view-actions.adoc#overview[view parameters and view actions]) explains `+f:viewParam+` and `+f:viewAction+` and the traps in them. OmniFaces offers variants that avoid several
of those traps, `+o:viewParam+` and `+o:viewAction+`, and a tag for what to do on a failure. The two components are drop-in: change the prefix from `+f:+` to `+o:+`.

.The _Bookshelf_ detail view with the OmniFaces tags
[source,xml]
----
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core"
      xmlns:ui="jakarta.faces.facelets"
      xmlns:o="omnifaces">
<f:metadata>
  <o:viewParam name="id" value="#{viewParamBean.id}" required="true"/>
  <o:viewParamValidationFailed sendError="400" message="A book id is required"/>
  <o:viewAction action="#{viewParamBean.load}" if="#{viewParamBean.id ne null}"/>
</f:metadata>
<h:head><title>View</title></h:head>
<h:body>
  <h:messages id="msgs"/>
  <p>id=<span id="id">#{viewParamBean.id}</span> title=<span id="title">#{viewParamBean.book.title}</span> loads=<span id="loads">#{viewParamBean.loads}</span></p>
  <h:form id="form">
    <h:commandButton id="again" value="again" action="#{viewParamBean.load}"/>
  </h:form>
</h:body>
</html>
----

.ViewParamBean.java
[source,java]
----
package org.example.bookshelf.web;

import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import jakarta.validation.constraints.NotNull;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;

@Named
@ViewScoped
public class ViewParamBean implements java.io.Serializable {
    private static final long serialVersionUID = 1L;
    @Inject
    private transient BookService books;

    @NotNull
    private Long id;
    private Book book;
    private int loads;

    public void load() {
        loads++;
        book = books.find(id);
    }

    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public Book getBook() { return book; }
    public int getLoads() { return loads; }
}
----

Source: https://showcase.omnifaces.org/components/viewParam[OmniFaces showcase: viewParam], https://showcase.omnifaces.org/components/viewAction[viewAction] and https://showcase.omnifaces.org/taghandlers/viewParamValidationFailed[viewParamValidationFailed]

The same page written with the standard tags (`+f:viewParam+` and `+f:viewAction+` with the same attributes) is the control. Both pages were requested with different query strings and then posted back, on Mojarra and on MyFaces:

.Standard tags against the OmniFaces tags
[cols="3,3,4",options="header"]
|===
|Request |Standard `+f:viewParam+`, `+f:viewAction+` |`+o:viewParam+`, `+o:viewAction+`, `+o:viewParamValidationFailed+`

|no `+id+`
|HTTP 200, the page with `+j_idt1: Validation Error: Value is required.+` (the label is the generated id: `+j_id__md_1+` on MyFaces)
|HTTP 400 with the text `+A book id is required+`

|`+?id=abc+`
|HTTP 200 and `+'abc' must be a number consisting of one or more digits.+`
|HTTP 400

|`+?id=2+`
|HTTP 200, but the action did _not_ load the book: `+title+` empty, `+loads=0+`
|HTTP 200, `+title=Cosmos+`, `+loads=1+`

|postback of the page
|the bean is updated again from the query string; `+loads+` goes to 1
|`+loads+` goes to 2; the id is kept by the view scoped bean; the parameter is not converted or validated again

|postback to the bare URL (no query)
|Mojarra: works (`+loads=2+`). MyFaces: `+Validation Error: Value is required.+` and `+loads+` stays 1
|works on both (`+loads=3+`)
|===

What the table shows is what the `+o:+` tags are for:

* *`+o:viewParam+` has a stateless mode.* The standard parameter converts, validates and updates the model on every postback, so a required parameter that the form does not carry makes the postback fail (the MyFaces
  cell above) and a view scoped bean is overwritten. `+o:viewParam+` keeps the submitted value in the component and skips conversion, validation and the model update after the first request. Choose a view scoped bean
  to hold the value, as above: with a request scoped bean the postback finds nothing in the model (the same button bound to `+load()+` found `+id+` null and failed with a `+NullPointerException+`).
* *An absent parameter.* In Faces 2.0 to 2.2 the standard tag took a shortcut for a missing value that bypassed Bean Validation and the `+PreValidateEvent+` and `+PostValidateEvent+` listeners that `+o:viewParamValidationFailed+` relies on, and `+o:viewParam+`
  was the fix. The Javadoc says that Faces 2.3 repaired the standard tag, and that the OmniFaces fix now matters only when `+jakarta.faces.INTERPRET_EMPTY_STRING_SUBMITTED_VALUES_AS_NULL+` is `+true+`. On 4.1 the standard page in the run reported its required error normally; the stateless mode is the remaining reason.
* *`+o:viewParam+` also gives a default label* (its `+name+`), accepts a `+default+` value for an absent parameter, and does not turn a `+null+` model value into an empty parameter in generated links (`+includeViewParams+`).
* *`+o:viewAction+` evaluates `+if+` late.* The standard action evaluates `+if+` in Apply Request Values, before the view parameter has reached the model, so `+if="#{viewParamBean.id ne null}"+` saw `+null+` on the GET and the book was never loaded (`+loads=0+` above).
  `+o:viewAction+` evaluates it in Invoke Application, after conversion, validation and the model update. With `+immediate="true"+` it behaves like the standard one. Its `+message+` attribute adds a flash warning if the action
  redirects.
* *`+o:viewParamValidationFailed+` decides what a failure means.* In `+f:metadata+` it applies when any view parameter failed; nested in one view parameter it applies to that one only and takes precedence. With `+sendError="400"+` it
  sends an HTTP status (and a page from `+<error-page>+` if you declared one); with `+sendRedirect="login.xhtml"+` it redirects with the message as a global flash error. `+message+` overrides the text. It works with any conversion or validation, Bean Validation included.
  A redirect always has the status of the redirect; to answer another status, use `+sendError+` and an `+error-page+`.

Behind the tags, a page that is reached by path instead of query parameters (`+/book/123+`) uses `+o:pathParam+` and `+@Param(pathIndex)+` with FacesViews (<<facesviews>>). Three more input components belong to the same family and were
only read, not run: `+o:hashParam+` (the fragment after `+#+`, kept in sync with a model value by `+window.onhashchange+` and every Ajax response), `+o:scriptParam+` (the result of a JavaScript expression that the client evaluates and sends,
for the time zone offset or the screen width) and `+o:componentIdParam+` (renders only the components named by a GET parameter, for mashups). All three put client-controlled data in the model; validate it like any request parameter.

*Choosing.* A single lookup of a record by id is a good fit for `+@Param+` (<<param>>). A page that must reject a bad or absent parameter before anything runs, and that posts back, is a good fit for the OmniFaces tags above.

[#validators]
== Validators: o:validateBean and the Multi-Field Family

Bean Validation (see xref:web/jsf/bean-validation.adoc[the Bean Validation page]) validates one property at a time during Process Validations, because that is how Faces works: a model is updated only after all inputs are valid. Two needs fall outside:
switching validation off for one button, and validating a constraint that spans several properties of one object. `+o:validateBean+` serves both, and the `+o:validateXxx+` components do the same for plain inputs without a bean.

=== o:validateBean: per component and per class

Per component, it is `+disabled+` and `+validationGroups+` on a command or an input, where the standard `+f:validateBean+` offers one setting for a whole form or request:

.Skip Bean Validation for a "save draft" button
[source,xml]
----
<h:commandButton id="nobv" value="save without checks" action="#{borrowDraftBean.submit}">
  <o:validateBean disabled="true"/>
</h:commandButton>
----

Source: https://showcase.omnifaces.org/validators/validateBean[OmniFaces showcase: validateBean]

On the scratch page a `+@Size(min = 3)+` note field with the value `+ab+` failed with the message `+note too short+` when the ordinary button was pressed, and the button that carried `+<o:validateBean disabled="true"/>+` went through and
ran its action (`+Saved ...+`). Use it for drafts. Do not use it to bypass validation of data that you will persist: the model still receives the unvalidated value, so the service layer must validate again (the rule of
xref:web/jsf/bean-validation.adoc#service-layer[the service layer section]).

Per class, `+<o:validateBean value="#{bean.object}"/>+` validates the whole object with its class-level constraints after all its properties were set. The problem it solves is that the standard flow validates the properties one at a time and never sees the object. Faces 4.1 has its own answer, `+f:validateWholeBean+`,
and the model class and the constraint here are the ones of the Bean Validation page (xref:web/jsf/bean-validation.adoc#whole-bean[class-level validation]): a `+BorrowRequest+` with `+@NotNull+` pick-up and return dates and a class-level `+@ValidPeriod(groups = PeriodChecks.class)+`, "the return date is after the pick-up date". The tag names the group:

.validate.xhtml, the whole form of the examples of this section
[source,xml]
----

      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core"
      xmlns:ui="jakarta.faces.facelets"
      xmlns:o="omnifaces">
<h:head><title>Validate</title></h:head>
<h:body>
  <h:messages id="msgs"/>
  <h:form id="form">
    <h:inputText id="from" value="#{borrowDraftBean.request.from}"><f:convertDateTime type="localDate" pattern="yyyy-MM-dd"/></h:inputText>
    <h:inputText id="to" value="#{borrowDraftBean.request.to}"><f:convertDateTime type="localDate" pattern="yyyy-MM-dd"/></h:inputText>

One change to that page's code is needed. Its `+ValidPeriodValidator+` calls `+request.getFrom().isBefore(request.getTo())+` without a null test, because for `+f:validateWholeBean+` the specification guarantees that the properties have already passed. `+o:validateBean+` makes no such guarantee: it validates a copy, in the same pass, with
every constraint of the group. The scratch run submitted the form with the return date empty:

* with the validator of the xref:web/jsf/bean-validation.adoc#whole-bean[Bean Validation page], both implementations answered *HTTP 500*: `+ValidationException: HV000028: Unexpected exception during isValid call+`, caused by a `+NullPointerException+` in the validator;
* with the guard below, both answered the form again with `+must not be null+`, from the `+@NotNull+` of the group.

.ValidPeriodValidator.java, tolerant of missing dates (the constraint reports them)
[source,java]
----
package org.example.bookshelf.validation;

import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;
import org.example.bookshelf.model.BorrowRequest;

public class ValidPeriodValidator implements ConstraintValidator<ValidPeriod, BorrowRequest> {

    @Override
    public boolean isValid(BorrowRequest request, ConstraintValidatorContext context) {
        if (request.getFrom() == null || request.getTo() == null) {
            return true; // the @NotNull constraints of the same group report missing dates
        }
        return request.getFrom().isBefore(request.getTo());
    }
}
----

Source: https://omnifaces.org/docs/javadoc/current/org.omnifaces/org/omnifaces/taghandler/ValidateBean.html[OmniFaces 5.5.5 API: ValidateBean] and https://omnifaces.org/docs/vdldoc/current/o/validateBean.html[OmniFaces VDL: o:validateBean]

Observed (both implementations): with a start date after the end date the form was redisplayed with `+The return date must be after the pick-up date+` as a global message (`+showMessageFor="@global"+`) and the action did not run; with valid dates the action ran
(`+Saved 2026-01-01 to 2026-02-01+`). The mechanism matters because it has consequences. Faces updates the model only when all inputs are valid, so to validate the object OmniFaces first makes a _copy_ of the bean, sets the submitted values on the copy and validates
there; if the validation passes, the original is updated. The copy is made with the first strategy that works: `+Cloneable+`, `+Serializable+` (as `+BorrowRequest+` is), a copy constructor, or a new instance; the `+copier+` attribute names another one. Where copying is impossible, `+method="validateActual"+` updates the model and validates after Update Model Values,
with the disadvantages the Javadoc lists: the invalid values stay in the model and the action runs anyway, so it must check `+FacesContext.isValidationFailed()+`. The tag collects the values before Process Validations and checks the constraints after it.

Where the message goes is controlled by `+showMessageFor+`: `+@form+` (the default, on the form's client id), `+@all+`, `+@global+`, a list of client ids, or `+@violating+`, which puts each violation on the input whose property it concerns and falls back to the form. `+messageFormat+` (3.12)
overrides the site-wide `+jakarta.faces.validator.BeanValidator.MESSAGE+` format for this tag; its `+{0}+` is the message and `+{1}+` the labels. Give the inputs labels (`+o:outputLabel+`, <<tags>>) so that the messages of the individual properties name the field.

=== The multi-field validators

For constraints between plain inputs there is a family of components with one shared contract. They are placed in the same form as the inputs and take the inputs as a space-separated list of client ids (or, since 3.13, one common parent) in `+components+`:

.The multi-field validators
[cols="2,5,5",options="header"]
|===
|Tag |Passes when |Default message

|`+o:validateEqual+`
|all values are equal
|`+{0}: Please fill out the same value for all of those fields+`

|`+o:validateOrder+`
|the values are in the order `+type+` says: `+lt+` (default, strictly ascending), `+lte+`, `+gt+`, `+gte+`
|`+{0}: Please fill out the values of all those fields in order+`

|`+o:validateUnique+`
|no value occurs twice
|`+{0}: Please fill out an unique value for all of those fields+`

|`+o:validateAll+`
|all are filled
|`+{0}: Please fill out all of those fields+`

|`+o:validateAllOrNone+`
|all or none are filled
|`+{0}: Please fill out all or none of those fields+`

|`+o:validateOne+`, `+o:validateOneOrMore+`, `+o:validateOneOrNone+`
|exactly one, at least one, at most one is filled
|`+...only one of those fields+`, `+...at least one...+`, `+...only one or none...+`

|`+o:validateMultiple+`
|your `+validateMethod+` (signature `+boolean m(FacesContext, List<UIInput>, List<Object>)+`) or a `+MultiFieldValidator+` object returns `+true+`

|`+o:validateUniqueColumn+`
|(a tag handler inside a column) the input's value is unique in all rows of the `+UIData+`, also the rows not on the current page; does not work when the model is lazy
|`+{0}: Please fill out an unique value for the entire column. Duplicate found in row {1}+`
|===

The attributes shared by the component family are `+components+` (required), `+message+` (a `+{0}+` is replaced by the labels), `+invalidateAll+` (mark all inputs invalid, default, or only the offending ones), `+showMessageFor+` (`+@this+`, the default, `+@all+`, `+@invalid+`, `+@global+` or ids), `+disabled+`
and `+binding+` for the read-only `+validationFailed+` property. Examples from the scratch form, with the two new tags in `+validate.xhtml+` above:

[source,xml]
----
<h:inputSecret id="pw" value="#{borrowDraftBean.password}" redisplay="true"/>
<h:inputSecret id="pw2" value="#{borrowDraftBean.confirm}" redisplay="true"/>
<o:validateEqual id="eq" components="pw pw2" message="Passwords differ"/>
<h:message for="eq"/>
----

Source: https://showcase.omnifaces.org/validators/validateEqual[OmniFaces showcase: validateEqual], https://showcase.omnifaces.org/validators/validateOrder[validateOrder] and https://omnifaces.org/docs/javadoc/current/org.omnifaces/org/omnifaces/component/validator/ValidateMultipleFields.html[ValidateMultipleFields API]

Observed on both implementations: different passwords gave `+Passwords differ+`, inputs `+2+` and `+1+` under `+o:validateOrder type="lt"+` gave `+Second must come after first+`, and equal passwords and ascending values passed.

Four rules from the Javadoc decide whether they behave:

* *Placement is the priority.* The validators validate when the tree walk reaches them. A validator placed _after_ all its inputs runs after their own converters and validators, and is skipped if one of them failed. A validator placed _before_ them runs first and, if it fails,
  their own converters and validators do not run. Placing it between the inputs is discouraged because only the preceding inputs are converted. Put it at one end.
* *It always runs in Process Validations*, cannot be made `+immediate+`, and is skipped entirely when an `+immediate="true"+` command calls `+renderResponse()+`.
* *A disabled, read-only or non-rendered input contributes its model value*, so the validator can compare against existing data.
* *`+disabled+` takes an EL expression that is evaluated per request.* The Javadoc example is `+disabled="#{param.validationDisabled}"+`. Do not copy that: a condition the client controls is a switch for the client to turn your validation off. Use a server-side condition.

`+o:requiredCheckboxValidator+` fixes a different bug: a `+required="true"+` on `+h:selectBooleanCheckbox+` never fails, because an unticked box is coerced to `+false+`, not to `+null+`. Nested in the checkbox, with a `+requiredMessage+`, it fails when the box is not ticked. The run showed `+Tick to accept+` for the unticked box. The standard tags and the
standard approach to cross-field validation (a `+postValidate+` listener, `+f:validateWholeBean+`) are in xref:web/jsf/validators.adoc#cross-field[the validators page]; the OmniFaces family is the no-Java version of the first.

Behind both: `+org.omnifaces.util.Validators+` runs Bean Validation programmatically (`+validateBean(bean, groups)+`, `+resolveViolatedProperty+`) when a service has to validate by hand.

[#converters]
== Converters

A converter turns a submitted string into an object and back (see xref:web/jsf/converters.adoc[the converters page]). Most of the OmniFaces converters exist to remove the need to write one. Each has a converter id (`+omnifaces.SelectItemsConverter+`) for the `+converter+` attribute and, since 4.5, a tag
(`+o:selectItemsConverter+`) for nesting in the component.

.The OmniFaces converters
[cols="2,4,3",options="header"]
|===

Observed on both implementations, with `+Book+` as a record with `+title+`, `+author+`, `+year+` and `+genre+`:

* The menu `+plain+`, without a converter, rendered each option's value as the record's `+toString()+` and failed on the postback: `+Conversion Error setting value 'Book[id=2, title=Cosmos, author=Carl Sagan, year=1980, genre=SCIENCE]' for 'null Converter'.+` The error also stops every other component in the form from being updated.
* The same menu with `+omnifaces.SelectItemsConverter+` converted the submitted `+toString()+` back to the _same instance_ from the list, so `+pickBean.selected+` was the record for `+Cosmos+`. No database was touched.
* The menu with `+o:selectItemsIndexConverter+` rendered the values `+0+`, `+1+`, `+2+`, `+3+` and converted `+2+` to the third book.
* A `+List<Genre>+` bound to `+h:selectManyCheckbox+` held `+[SCIENCE, HISTORY]+` with no converter at all; the `+GenericEnumConverter+` is obsolete for that case in Faces 4.1, as its Javadoc says.
* `+o:toCollectionConverter+` turned `+ a , b,c ,a+` into `+[a, b, c, a]+` (the default is an `+ArrayList+`; a `+Set+` property gets a `+LinkedHashSet+`); `+o:trimConverter+` turned `+  Ada  +` into `+Ada+`; `+o:toLowerCaseConverter+` turned `+  ADA@Example.ORG +` into `+ada@example.org+`; `+o:toUpperCaseConverter+` turned `+ zx-1 +` into `+ZX-1+`; `+o:implicitNumberConverter type="percent"+` turned `+25+` and `+25%+` into `+0.25+`.

What this teaches about `+SelectItemsConverter+` and `+toString()+`:

* *The `+toString()+` is the wire format.* Every option's value in the HTML source is the string form of the entity, here all five fields of the record, visible to anyone who views the page source. A `+toString()+` that contains sensitive data (a price paid, a note, a personal field) leaks it into the page. Either write a `+toString()+` that holds only the id (`+Book[id=2]+`, the pattern the Javadoc recommends)
  or subclass the converter and override `+getAsString+` (the Javadoc shows it), or use the index converter, which exposes nothing.
* *It must be unique and stable.* Two different entities with the same string would be confused, and an entity whose string changes between the render and the postback (a field edited in between) no longer matches.
* *It needs the same list on the postback.* The converter looks the string up in the items of the component, which are evaluated again on the postback. A list that is not the same on both requests (a request scoped bean with a changing query) breaks the match; the index variant is the more fragile to a list that changes.
* *`+equals()+` and `+hashCode()+`* of the entity must still be right for Faces to select the right option on render.

*An `+ImplicitNumberConverter+` limit on user input.* The scratch run showed that the converter fails on input that the other converters accept. When the submitted text lacks the symbol, the converter builds the string with `+Matcher.replaceAll+` using the submitted value as the replacement; a submitted `+$1+` (for a field with `+currencySymbol="€"+`
or for a percent field) ended in HTTP 500 on both implementations, with `+IndexOutOfBoundsException: No group 1+` in the log. On MyFaces, a currency field also failed for ordinary input: `+12.50+` gave `+'¤12.50' could not be understood as a currency value+`, the generic currency sign in place of the symbol, and `+$12.50+` gave HTTP 500 for the same `+replaceAll+` reason, while Mojarra accepted both.
The percent case worked on both. Treat the currency mode as unverified on MyFaces, and write your own converter, or validate the text first, when a currency field is public. This is an observation on 5.5.5, not documented behaviour; test it again on the version you use.

With PrimeFaces, the converter works as in the Javadoc: `+p:selectOneMenu+` with `+omnifaces.SelectItemsConverter+`, and `+p:pickList+` with `+<o:converter converterId="omnifaces.ListConverter" list="#{pickBean.picks.source}"/>+`, converted `+Cosmos+` back to the right instance and the picked list to a one-element target list on Mojarra and on MyFaces (<<primefaces>>).

=== o:form, o:link and o:url: keeping the request's query string

The standard `+h:form+` posts to the view id and drops the query string; a request scoped bean that needs the same query parameters on the postback does not get them. `+o:form+` posts to the exact request URI with its query string. This is the default
since 3.0 (`+useRequestURI+`); `+includeRequestParams="true"+` keeps just the parameters, and `+<f:param>+` or `+<o:param>+` inside the form adds parameters to the action URL. Also since 3.0 the form
posts, during an Ajax request, only the parts of the form that the `+execute+` list needs (`+partialSubmit+`, comparable to the PrimeFaces attribute of the same name), which shrinks the payload of a large editable table.

.components.xhtml (the relevant parts)
[source,xml]
----
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core"
      xmlns:ui="jakarta.faces.facelets"
      xmlns:o="omnifaces">
<h:head><title>Components</title></h:head>
<h:body>
  <o:messages id="msgs" for="form:title form:author"/>
  <o:form id="form">
    <o:outputLabel for="title" value="Book title"/>
    <h:inputText id="title" value="#{compBean.title}" required="true"/>
    <o:outputLabel for="author" value="Author name"/>
    <h:inputText id="author" value="#{compBean.author}" required="true"/>
    <h:commandButton id="save" value="save" action="#{compBean.save}"/>
    <h:commandButton id="skip" value="skip" action="#{compBean.skip}"><o:skipValidators/></h:commandButton>
    <h:commandButton id="ignore" value="ignore" action="#{compBean.ignore}"><o:ignoreValidationFailed/></h:commandButton>
  </o:form>
  <o:highlight/>
  <p>log=<span id="log">#{compBean.log}</span></p>
  <p>link=<o:link id="l1" outcome="components" value="same query" includeRequestParams="true"/>
     <h:link id="l2" outcome="components" value="std link"/>
     url=<span id="url"><o:url includeRequestParams="true"/></span></p>
  <o:cache id="c1" time="60">
    <p>cached hit=<span id="hit">#{compBean.hits}</span></p>
  </o:cache>
</h:body>
</html>
----

Source: https://omnifaces.org/docs/vdldoc/current/o/form.html[OmniFaces VDL: o:form] and https://showcase.omnifaces.org/components/form[OmniFaces showcase: form]

Requested as `+components.xhtml?x=1+` the form's `+action+` was `+/bookshelf/components.xhtml?x=1+` on both implementations. `+<o:link includeRequestParams="true"/>+` rendered `+href=".../components.xhtml?x=1&y=2"+` and the plain `+h:link+` the bare view; `+<o:url includeRequestParams="true"/>+` rendered the full URL
`+http://localhost:8570/bookshelf/components.xhtml?x=1&y=2+` (with a `+;jsessionid=...+` path parameter on the first request of a client without a cookie, as every URL rewritten by the container has). `+o:url+` exists for the places where JSTL's `+c:url+` was used: a `+link+`
element, a JavaScript variable, a canonical URL, with `+viewId+` or `+value+`, `+domain+`, `+includeViewParams+`, nested `+o:param+` and a `+var+` that holds the URL instead of printing it.

A nested form is a mistake that browsers silently repair. According to the Javadoc of `+OmniViewHandler+`, OmniFaces turns it into an `+IllegalStateException+` in the `+Development+` project stage, which helps when a template already has a form (not run).

=== o:outputLabel, o:highlight and o:messages: feedback that names the field

`+o:outputLabel+` is an `+h:outputLabel+` that sets its own value as the `+label+` of the input in `+for+`, so the validation message names the field the user saw. In the run, with an empty `+title+` the message read `+Book title: Validation Error: Value is required.+`, taken from the label text,
and not from a generated id. `+o:highlight+` adds an error style class to every invalid input and its label and focuses the first invalid one; one per page, ideally in the master template. The markup it produced for the failed `+title+` was a script,
`+OmniFaces.Highlight.apply(["form:title"], 'error', true);+`, and you write the CSS (`+input.error {...}+`); `+styleClass+` and `+focus+` configure it. The class is removed again when the user starts to use the field. `+o:messages+` is in <<messages>>.

=== o:skipValidators and o:ignoreValidationFailed: buttons that do not need a valid form

Both are tag handlers that go inside a command (or an Ajax-capable component) and change how a failure is treated. `+o:skipValidators+` skips validation entirely for that action: converters still run and the model is still updated. `+o:ignoreValidationFailed+` lets the action run even though
validation failed (inside an `+o:form+`; with Ajax, the form must be in the `+execute+` list), updating only the inputs that passed. In the run, with the required `+title+` empty and `+author+` set:

* the ordinary button redisplayed the form with `+Book title: Validation Error: Value is required.+` and did not run the action;
* the button with `+o:skipValidators+` ran its action (`+log=skip+`) and showed no message;
* the button with `+o:ignoreValidationFailed+` ran its action (`+log=ignore(null/Ada)+`: `+title+` still `+null+`, `+author+` updated) and still showed the message.

Use them for "add a row", "save as draft" and "cancel" buttons. Compare the standard answer, `+immediate="true"+`, and its consequences in xref:web/jsf/request-processing-lifecycle.adoc#immediate[the lifecycle page]; these tags do not skip the Update Model Values phase the way `+immediate+` does.
The validators of a skipped action are skipped: an action that processes the model must validate it by itself.

=== o:enableRestorableView: an expired view that can be rebuilt

An expired view makes a postback fail with `+ViewExpiredException+` (see xref:web/jsf/state-saving-and-stateless-views.adoc#expired[the state saving page] and xref:web/jsf/exception-handling.adoc#view-expired[the exception handling page]). `+<o:enableRestorableView/>+` in `+f:metadata+` makes OmniFaces rebuild the
view from scratch when the state is missing and the request is a postback. The view comes back exactly as it was on the first GET, so changes made since then (conditionally rendered parts, a view scoped value) are lost: the page must work with a request scoped bean. Two pages differed in the run only by this tag, and posted the form with a view state that the server had never issued:

* the page with the tag answered HTTP 200 and ran the action, on Mojarra and on MyFaces;
* the page without it answered HTTP 500 (the unhandled `+ViewExpiredException+`) on both.

The Javadoc suggests `+<f:view transient="true">+` instead where it fits, because it keeps no state at all (xref:web/jsf/state-saving-and-stateless-views.adoc#stateless[stateless views]). Rebuilding an expired view also means that a request that carries a forged or stale state is accepted as a fresh view;
that is the whole point, and it limits the use to pages where a replayed form is harmless. Do not put it on a page that performs a state-changing action protected only by the view state (xref:web/jsf/security.adoc#csrf[the CSRF section]).

=== o:cache: caching a rendered fragment

`+o:cache+` stores the rendered markup of its children and serves it without evaluating the beans behind it, for `+time+` seconds. The default scope is `+session+` (one copy per user); `+scope="application"+` shares one copy among all users. The key defaults to the view id plus the client id of the component
(the Javadoc warns that a client id can change when the view changes dynamically, so set `+key+` yourself in that case); `+reset+` drops the entry and `+disabled+` switches the component off; `+o:cacheValue+` caches a single value like `+c:set+`. Capacity and lifetime defaults come from the context parameters
`+org.omnifaces.CACHE_SETTING_SESSION_MAX_CAPACITY+`, `+org.omnifaces.CACHE_SETTING_SESSION_TTL+`, `+org.omnifaces.CACHE_SETTING_APPLICATION_MAX_CAPACITY+` and `+org.omnifaces.CACHE_SETTING_APPLICATION_TTL+`, and the implementation from `+org.omnifaces.CACHE_PROVIDER+`.

The scratch page `+cached.xhtml+` has three caches around request-driven content: one with `+scope="application"+`, one with the default scope, one around a form. A bean printed the request parameter `+u+`:

* Alice requested `+?u=alice+` and the application cache stored `+user=alice+`. Bob, a different client with a different session, requested `+?u=bob+` and was served `+user=alice+` by the application cache and `+user=bob+` by the session cache. This is the leak: whatever the first visitor caused to be rendered, every later visitor gets.
* The counter result: the first fragment evaluation printed a number from a bean counter and the second request of the same session served the same number (the bean was not asked again), on Mojarra and on MyFaces.
* The cached form broke. On the second request Mojarra served the form with the literal text `+~com.sun.faces.saveStateFieldMarker~+` where the view state field belongs, and MyFaces served the `+jakarta.faces.ViewState+` field of the _first_ request, again on every hit. Neither form can be posted back successfully.

The rules that follow: a fragment that depends on the user (a name, a price list, a menu by role, a token) must never be cached in application scope; keep the default session scope for per-user fragments, and for application scope cache only content that is identical for all users and does not change between requests. Never put a form, or anything that contains view state or a CSRF token, inside `+o:cache+`.

Source: https://omnifaces.org/docs/javadoc/current/org.omnifaces/org/omnifaces/component/output/Cache.html[OmniFaces 5.5.5 API: Cache] and https://showcase.omnifaces.org/components/cache[OmniFaces showcase: cache]

* *`+o:conditionalComment+`* renders the markup inside a conditional comment: `+<!--[if lte IE 9]><link rel="stylesheet" href="old.css" /><![endif]-->+`, even with `+jakarta.faces.FACELETS_SKIP_COMMENTS+` set to `+true+`, which is the setting that removes ordinary comments. Only for a legacy browser you still have to support, which in 2026 should be none.
* *`+o:criticalStylesheet+`* rendered `+<link rel="preload" href="..." as="style" onload="this.onload=null;this.rel='stylesheet'" />+` followed by a `+noscript+` fallback with the plain `+link+`, and moved it to the top of the head, ahead of the OmniFaces and Faces scripts.
* *`+o:deferredScript+`* rendered `+<script>OmniFaces.DeferredScript.add('/bookshelf/jakarta.faces.resource/js/late.js.xhtml','','',null,function() {window.late=1});</script>+` at the end of the body; the `+onsuccess+` code ran after the window load event (`+window.late+` was `+1+`).
* *`+o:lazyPanel+`* with `+loaded="true"+` rendered its children; without it, an empty `+div+` and `+OmniFaces.LazyPanel.init('lp2', {})+`, and the content arrived by an Ajax request when the panel scrolled into view (it did, in the headless Chrome run). The `+listener+` receives a `+LazyPanelEvent+` once.
* *`+o:massAttribute+`* put `+class="wide"+` on the input without a `+styleClass+` and left `+class="own"+` on the one that had one.
* *`+o:resolveComponent+`* made the component `+a+` available by name (`+#{aComp.clientId}+` printed `+a+`); `+o:moveComponent+` moves components, facets and behaviors to another place in the tree (`+BEFORE+`, `+AFTER+`, `+ADD_FIRST+`, `+ADD_LAST+`, `+FACET+`, `+BEHAVIOR+`); `+o:outputFormat var="_greeting"+` captured `+Hello reader+` into a variable instead of printing it.
* *`+o:tree+`* (with `+o:treeNode+`, `+o:treeNodeItem+` and `+o:treeInsertChildren+`) renders any `+TreeModel+` with markup that you write, recursively; it draws nothing itself. *Not run.*
* *`+o:inputHidden+`* converts, validates and updates the model immediately in Apply Request Values, regardless of errors on other inputs. *`+o:inputFile+`* adds `+maxsize+`, `+directory+` and server-side checks of `+accept+` to `+h:inputFile+` (<<tags-upload>>).
* *`+o:scriptErrorHandler+`* reports uncaught JavaScript errors and rejected promises by `+navigator.sendBeacon()+` to the server, where they arrive as a CDI `+ScriptError+` event for an observer to log; *`+o:resourceInclude+`* renders the output of a JSP or servlet and exists only to ease a migration away from JSP. Neither was run.

Two cautions that the markup above makes concrete. Several of these components write inline script (`+OmniFaces.Highlight.apply(...)+`, `+DeferredScript.add(...)+`, `+LazyPanel.init(...)+`) and an inline `+onload+` attribute (`+o:criticalStylesheet+`); a Content-Security-Policy without
`+'unsafe-inline'+` or a nonce blocks them, which you find out only in a browser. The CSP section of xref:web/jsf/security.adoc#csp[the security page] explains the nonce support of Mojarra and what PrimeFaces 16 does; apply the same test to every OmniFaces component you use.
And `+o:resourceInclude+`, `+o:scriptParam+`, `+o:hashParam+` and `+o:componentIdParam+` are all doors for client data or server resources into the page: do not pass a user-chosen value to `+path+`.

[#tags-upload]
=== o:inputFile

`+o:inputFile+` is `+h:inputFile+` with `+accept+` and `+maxsize+` checked on the server (`+acceptMessage+` and `+maxsizeMessage+` customise the text), `+multiple+` and `+directory+` (select a folder). It does not replace the controls of
xref:web/jsf/file-upload-and-download.adoc#limits[the upload page]: the `+accept+` check compares the declared content type, which the client chooses, so inspect the content too, and keep the container's multipart limits. It was not run here.

Observed on both implementations: `+#{Limits.MAX_TITLE_LENGTH}+` printed `+120+`, `+#{Limits.SORT_BY_YEAR}+` printed `+year+`, `+#{G.SCIENCE}+` printed `+SCIENCE+` for the enum imported as `+G+`, `+#{G.values()}+` and `+#{G.members()}+` both listed `+[FICTION, SCIENCE, HISTORY]+`,
and `+#{m:abs(-10)}+` printed `+10+`. Details from the Javadoc: an unknown constant name throws `+IllegalArgumentException+` at run time (EL cannot check it earlier); for an enum, `+members()+` (since 4.6) lists only the enum constants where `+values()+` of an enum that implements an interface lists the interface constants too; `+loader+` (4.3)
names an object whose class loader finds the type, for a classpath with duplicates.

Faces has had its own `+f:importConstants+` since 2.3. It must be a child of `+f:metadata+`, which is why it does not suit an include, a tag file or a composite component, where `+o:importConstants+` can be placed anywhere (the Javadoc's argument). In a plain view `+f:importConstants+` is enough (see
xref:web/jsf/core-tags.adoc[the core tags page]). `+o:importFunctions+` has no standard counterpart; EL functions otherwise need a tag library XML file (xref:web/jsf/tag-files-and-tag-libraries.adoc#el-functions[the tag libraries page]). EL does not support overloading, so with several methods of the same name the one with the fewest parameters wins.

=== The other tag handlers

* *`+o:converter+` and `+o:validator+`* extend `+f:converter+` and `+f:validator+` with deferred value expressions in all attributes, evaluated at each access instead of once when the view is built, so they can differ per row of an iterating component and refer to bean properties. They are how a parameterised converter is configured
  (`+<o:converter converterId="omnifaces.ImplicitNumberConverter" type="currency" currencySymbol="$"/>+`), and what `+o:listConverter+` and `+o:validateBean+` build on.
* *`+o:massAttribute+`, `+o:tagAttribute+`, `+o:methodParam+`* help tag files and templates: set an attribute on every nested component (with `+target+` to select a class), declare a tag attribute explicitly so a parent's value is cleared, pass a method expression through a tag attribute.
* *`+o:loadBundle+`* extends `+f:loadBundle+` with a `+loader+` and better default locale handling. The bundle approach of xref:web/jsf/messages-and-i18n.adoc[the messages page] does the same without a handler.
* *`+o:skipValidators+`, `+o:ignoreValidationFailed+`, `+o:enableRestorableView+`, `+o:viewParamValidationFailed+`, `+o:validateBean+`, `+o:validateUniqueColumn+`* are covered above.

Three of the functions are for security-sensitive places, and one is a trap:

* `+o:escapeJS+` escapes a value for a JavaScript string. In the run, a request parameter `+'; alert(1);//</script><b>+` came out of `+var plain = '#{param.t}';+` unchanged, which breaks out of the string and out of the script element, and out of `+var safe = '#{o:escapeJS(param.t)}';+` as
  `+\'; alert(1);\/\/<\/script><b>+`, which is inert. The standard EL escaping is for HTML, not for JavaScript (see xref:web/jsf/security.adoc#xss[the XSS section]); `+o:escapeJS+` closes the gap for string literals. Better still is no data in script at all: use a `+data-+` attribute.
* `+o:encodeURL+` percent-encodes a value for a query string: `+q=#{o:encodeURL(param.t)}+` gave `pass:c[%27%3B+alert%281%29...]`.
* `+o:stripTags+` removes HTML tags from text; it is a way to produce a plain-text summary, not a sanitiser to make markup safe.
* `+o:printStackTrace+` prints a `+Throwable+`, which belongs on a developer error page and nowhere a user can see it (exception messages and class names are internal information, and the stack trace may carry values of the failed request).

Prefer the implicit objects and the plain EL where they do the job; the OmniFaces Javadoc itself says that the `+o:+` form of the `+Faces+` functions is poor practice next to `+#{request.contextPath}+` or `+#{faces.development}+`.

[#graphic]
== o:graphicImage and @GraphicImageBean

The standard `+h:graphicImage+` shows a file served as a Faces resource. An image from a database (a book cover) needs a servlet. `+o:graphicImage+` accepts a `+byte[]+` or an `+InputStream+` in its `+value+`, and the library serves it through a resource URL, without a servlet. A bean whose methods return the image bytes is marked
`+@GraphicImageBean+`, a stereotype that makes it a named application scoped bean (the annotation implies `+@Named+` and `+@ApplicationScoped+`).

.CoverBean.java
[source,java]
----
package org.example.bookshelf.web;

import java.awt.Color;
import java.awt.Graphics2D;
import java.awt.image.BufferedImage;
import java.io.ByteArrayOutputStream;
import java.io.IOException;
import java.io.UncheckedIOException;
import javax.imageio.ImageIO;
import org.omnifaces.cdi.GraphicImageBean;

/** A GraphicImageBean exposes its methods to o:graphicImage as images, with no servlet. */
@GraphicImageBean
public class CoverBean {
    public byte[] cover(long id) {
        System.setProperty("java.awt.headless", "true");
        BufferedImage image = new BufferedImage(60, 90, BufferedImage.TYPE_INT_RGB);
        Graphics2D g = image.createGraphics();
        g.setColor(new Color((int) (id * 60) % 255, 90, 160));
        g.fillRect(0, 0, 60, 90);
        g.dispose();
        ByteArrayOutputStream out = new ByteArrayOutputStream();
        try {
            ImageIO.write(image, "png", out);
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
        return out.toByteArray();
    }
}
----

.graphic.xhtml
[source,xml]
----
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core"
      xmlns:ui="jakarta.faces.facelets"
      xmlns:o="omnifaces">
<h:head><title>Graphic</title></h:head>
<h:body>
  <ui:repeat value="#{bookService.all()}" var="b">
    <o:graphicImage id="img" value="#{coverBean.cover(b.id)}" type="png" alt="cover"/>
  </ui:repeat>
  <o:graphicImage id="uri" value="#{coverBean.cover(1)}" dataURI="true" type="png"/>
  <p id="url">#{o:graphicImageURL('coverBean.cover(2)')}</p>
</h:body>
</html>
----

Source: https://omnifaces.org/docs/javadoc/current/org.omnifaces/org/omnifaces/cdi/GraphicImageBean.html[OmniFaces 5.5.5 API: GraphicImageBean] and https://showcase.omnifaces.org/components/graphicImage[OmniFaces showcase: graphicImage]

The rendering on Mojarra and on MyFaces: each `+img+` had a `+src+` of the form `+/bookshelf/jakarta.faces.resource/CoverBean_cover.png.xhtml?ln=omnifaces.graphic&v=0&p=1+` (the method name and the argument become the resource name and the `+p+` parameter), `+dataURI="true"+` produced `+src="data:image/png;base64,..."+`, and `+#{o:graphicImageURL('coverBean.cover(2)')}+`
printed the URL form. Fetching a URL answered `+200+` with `+Content-Type: image/png+`, a one-week `+Expires+` and `+Last-Modified+` in 1970 (no `+lastModified+` attribute given); `+lazy="true"+` defers evaluating the method until the image request, and `+type+`, `+lastModified+`, `+width+`
and `+height+` are available. An unknown bean or method in the URL (`+OtherBean_secret.png.xhtml+`) answered `+404+`, and so did a non-numeric argument for a `+long+` parameter.

*The security consequence.* The Javadoc states that `+@GraphicImageBean+` "basically enables endusers to invoke any public method returning a byte[] or InputStream on the bean by just a HTTP GET request." The scratch run fetched `+...CoverBean_cover.png.xhtml?ln=omnifaces.graphic&v=0&p=3+` with no session cookie and received the image, and any `+p+` that
the method accepts can be requested. That makes every public image method of the bean a public, guessable URL. Rules that follow:

* Put only methods on the bean that are meant to be public, and give a private image its own check: authenticate and authorise inside the method (the caller, from an injected `+SecurityContext+` or the request), or serve it through a protected servlet instead. This part was not run; the point is that nothing in the URL carries a session.
* Never return a file path, a name or any other user-supplied string from such a method as a way to choose a file; a method that opens a file from its argument turns the URL into a file reader.
* Choose identifiers that cannot be guessed where the images are confidential, and set the `+lastModified+` or a version so that a changed cover is not cached for a week.

Before `+@GraphicImageBean+` (OmniFaces 2.5) the bean could be any `+@Named @ApplicationScoped+` bean; the Javadoc explains that after a server restart the images stop working until a Faces page has referenced the method once, because of exactly the security restriction above.

no `+integrity+` because the CDN handler does not know the remote content. Order matters, as the Javadoc says: a handler registered after `+CombinedResourceHandler+` wraps it, and `+UnmappedResourceHandler+` must come after the others or the combined resources keep their mapped URLs.

Three security notes:

* *The CDN handler does not validate the URL* (Javadoc). It is a context parameter, so only the deployer controls it; but a URL taken from user-editable configuration turns your pages into a script injection point. Pin versions in the URL, and prefer self-hosting or a CDN with Subresource Integrity (the resources have no `+integrity+` here) for scripts.
* *The `+crossorigin="anonymous"+` attribute* makes the request cookie-less, which is what you want for a CDN; the Javadoc shows overriding it per resource with a passthrough attribute (`+a:crossorigin="use-credentials"+`) only when the CDN needs the cookies.
* *The versioned handler* is a cache buster, not a security control: it makes a changed resource visible at once. Its version can be an EL expression such as `+#{environmentInfo.version}+`, so deployments change it without editing the pages.

[#push]
== Push: o:socket, o:sse and o:notification

xref:web/jsf/websocket-push.adoc#omnifaces[The push page] compares `+f:websocket+` and `+o:socket+` in a table and shows the sender API; this section adds the other two components and the results of running them. Three transports share one sender API, `+@Inject @Push PushContext+`, selected by the `+type+` of the annotation:

.The push components
[cols="2,3,3",options="header"]
|===
|Component |Transport |Sender

|`+o:socket+` (2.3)
|WebSocket, one-way (server to client), channel scopes `+application+`, `+session+`, `+view+`, optional `+user+`; `+connected+` switches it on and off from the server
|`+@Inject @Push(channel = "reviews") PushContext+`

|`+o:sse+` (5.2)
|Server-Sent Events over plain HTTP (servlet async); the browser reconnects by itself; best with HTTP/2
|`+@Inject @Push(channel = "alerts", type = Push.Type.SSE) PushContext+`

|`+o:notification+` (5.2)
|The browser's Web Notifications API on top of SSE; needs the PWA manifest and the user's permission
|`+@Push(type = NOTIFICATION)+`, `+Notification.createNotificationMessage(title, body, url)+`
|===

.FeedBean.java
[source,java]
----
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import org.omnifaces.cdi.Push;
import org.omnifaces.cdi.PushContext;

@Named
@RequestScoped
public class FeedBean {
    @Inject
    @Push(channel = "reviews")
    private PushContext reviews;

    @Inject
    @Push(channel = "alerts", type = Push.Type.SSE)
    private PushContext alerts;

    public void sendSocket() {
        reviews.send("{\"book\": \"Dune\", \"stars\": 5}");
    }

    public void sendSse() {
        alerts.send("new-review");
    }
}
----

.feed-socket.xhtml and feed-sse.xhtml (each page has one component)
[source,xml]
----

<!-- or, in the other page -->
<o:sse channel="alerts" onmessage="onAlert"/>
----

Source: https://showcase.omnifaces.org/push/socket[OmniFaces showcase: o:socket], https://showcase.omnifaces.org/push/sse[o:sse] and https://showcase.omnifaces.org/push/notification[o:notification]

Observed in headless Chrome, on Mojarra and on MyFaces: a click on a button with an Ajax action that called `+reviews.send(...)+` made the `+onmessage+` function receive the message, and likewise for `+alerts.send("new-review")+` on the SSE page. A message sent as a String arrives as a JSON string, `+"{\"book\": ..."+`, so
send an object (a map or a bean, encoded by the library's JSON encoder) when the page should receive structured data. The rendered page registers each channel as `+reviews?<uuid>+`, a channel name plus a random token, and the client's `+OmniFaces.Push.init+` call.

* *Mojarra and a view with both components.* The page that held `+o:socket+` _and_ `+o:sse+` worked on MyFaces, but on Mojarra 4.1.17 the second Ajax click failed on the server: `+ClassCastException: SseChannelManager$ViewScope cannot be cast to SocketChannelManager$ViewScope+` in `+SocketPushContext+`, on every attempt. Give a view one push component until that is fixed in the version you use.
* *Endpoint and idle timeout.* Since 5.2 the WebSocket endpoint is registered automatically when an `+@Inject @Push+` exists, and the URL pattern changed from `+/omnifaces.push/*+` to `+/omnifaces.socket/*+`, so security constraints and proxy rules written for the old pattern no longer match; the SSE endpoint is `+/omnifaces.sse/<channel>+`. The idle timeout and the maximum number of sessions per channel have context parameters (`+org.omnifaces.SOCKET_ENDPOINT_IDLE_TIMEOUT+`, `+org.omnifaces.SOCKET_MAX_SESSIONS_PER_CHANNEL+`, `+org.omnifaces.SSE_ENDPOINT_IDLE_TIMEOUT+`, `+org.omnifaces.SSE_MAX_SESSIONS_PER_CHANNEL+`); the defaults have no limit, so set the session cap on public channels.
* *Security.* Release 5.4.3 restricted the session and view scoped SSE and notification channels to their owning HTTP session (advisory GHSA-w3w6-9m25-g88p, per the release notes), so keep the library current. The rules of the `+f:websocket+` page apply unchanged: take the `+user+` from the authenticated principal, never from a request parameter; put a security constraint on the endpoint path; write received data with `+textContent+`, not `+innerHTML+`.
* *SSE prerequisites.* Every filter mapped on `+/*+` must support async (`+asyncSupported=true+`), or SSE fails; without HTTP/2, a browser keeps at most six connections per origin and further tabs can block ordinary requests. SSE cannot be connected and disconnected from the server like `+connected+` on `+o:socket+`.
* *Frameworks.* 5.4.4 made `+o:socket+` session and view channels work on Quarkus (which does not expose the HTTP session in the handshake) and made `+o:sse+` and `+o:notification+` work there at all; 5.4.5 fixed both on Open Liberty. The `+SocketPushContextProducer+`, deprecated in 5.2, was removed in 5.5.1.

== FacesViews: Extensionless URLs, MultiViews and Dynamic Routes

FacesViews serves Facelets at URLs without an extension, selected by directory scanning, with no `+FacesServlet+` mapping required. Faces 4.0 has an extensionless mapping of its own (see xref:web/jsf/project-setup.adoc#servlet-mapping[the project setup page] and
xref:web/jsf/configuration-and-project-stages.adoc#extensionless[the configuration page]), which maps `+/index+` to `+/index.xhtml+` and nothing more. FacesViews adds the redirects, the path parameters of MultiViews and, since 5.5, dynamic route segments.

Zero configuration: views below `+/WEB-INF/faces-views/+` become public as `+/name+`. For the other places, `+org.omnifaces.FACES_VIEWS_SCAN_PATHS+`; its value `+/*.xhtml/*+` scans every `+.xhtml+` file below the web root (not `+WEB-INF+`, `+META-INF+` or `+resources+`) and turns MultiViews on. The relevant context parameters are `+FACES_VIEWS_EXTENSION_ACTION+` (`+REDIRECT_TO_EXTENSIONLESS+`, `+SEND_404+`, `+PROCEED+`), `+FACES_VIEWS_PATH_ACTION+` (default `+SEND_404+` for views requested by their path below a scanned directory), `+FACES_VIEWS_SCANNED_VIEWS_ALWAYS_EXTENSIONLESS+`
(links always without extension), `+FACES_VIEWS_ENABLED+` and `+FACES_VIEWS_LOWERCASED_REQUEST_URI+`. A link to a dynamic route needs `+<o:pathParam name=... value=.../>+` for every segment, because the rendered URL cannot contain the square brackets. A dynamic-route directory name must be unambiguous: two different segment names under one parent, the same name twice in one path, or an unbalanced bracket fail the deployment.
A literal sibling directory always wins over the dynamic one (an organisation whose id is `+settings+` is unreachable).

*Filters and security.* FacesViews reaches a view in two ways: by wrapping the request and continuing the chain (the MultiViews `+/search/dune/2+` case) or by forwarding (dynamic routes and the redirects). A forward bypasses the filters that are mapped for the default `+REQUEST+` dispatcher. The scratch run mapped a `+@WebFilter("/*")+` that set a header:

* by default the header was present for `+/search/dune/2+` and _absent_ for `+/books/1/reviews+` (a dynamic route), `+/books/1+`, and the redirects;
* with `+org.omnifaces.FACES_VIEWS_FILTER_AFTER_DECLARED_FILTERS+` set to `+true+`, the header was present on all of them.

This is the documented behaviour (the Javadoc says the FacesViews filter is first in the chain by default), and the consequence is the point: an authentication or authorisation filter, a CSRF filter or a security-headers filter that is mapped as usual can be skipped on part of the application. Either set the parameter, or protect by `+security-constraint+` (which the container applies before any of this, 403 above), or declare the filter for `+FORWARD+` too. Check every protection you rely on with a request to a dynamic route.
Also keep in mind that the constraint pattern must match the URL as FacesViews serves it: `+/admin/panel.xhtml+` does not constrain `+/admin/panel+` (the pitfall of xref:web/jsf/security.adoc#web-xml[the security page]); use `+/admin/*+`.

[#fileservlet]
== FileServlet: Serving Files From Outside the WAR

Uploads and media belong outside the web application, and the default servlet cannot serve them. `+org.omnifaces.servlet.FileServlet+` is an abstract servlet that does the work properly: ETag, `+If-None-Match+`, `+If-Modified-Since+`, `+Range+` and `+If-Range+` (needed by media players to seek and by downloads to resume). You override `+getFile(request)+`:

.MediaFileServlet.java
[source,java]
----
package org.example.bookshelf.web;

import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServletRequest;
import java.io.File;
import java.io.IOException;
import java.nio.file.Path;
import org.omnifaces.servlet.FileServlet;

/** Serves files below one folder, with Range and ETag support, and refuses anything outside it. */
@WebServlet("/media/*")
public class MediaFileServlet extends FileServlet {
    private static final long serialVersionUID = 1L;

    private Path folder;

    @Override
    public void init() {
        // A real application reads this from configuration, not from code.
        folder = Path.of(System.getProperty("bookshelf.media", "media-data")).toAbsolutePath().normalize();
    }

    @Override
    protected File getFile(HttpServletRequest request) {
        String pathInfo = request.getPathInfo();

        if (pathInfo == null || pathInfo.isEmpty() || "/".equals(pathInfo)) {
            throw new IllegalArgumentException(); // answered with HTTP 400
        }

        Path file = folder.resolve(pathInfo.substring(1)).normalize();

        if (!file.startsWith(folder)) {
            throw new IllegalArgumentException(); // outside the folder: HTTP 400
        }

        return file.toFile();
    }
}
----

Source: https://omnifaces.org/docs/javadoc/current/org.omnifaces/org/omnifaces/servlet/FileServlet.html[OmniFaces 5.5.5 API: FileServlet] and https://showcase.omnifaces.org/servlets/FileServlet[OmniFaces showcase: FileServlet]

The run, on Mojarra: `+/media/readme.txt+` answered 200 `+text/plain+`; a missing file 404; `+/media/+` 400 (the `+IllegalArgumentException+`); `+/media/..%2f..%2fetc/passwd+` 400 from Tomcat before the servlet; a request with `+Range: bytes=0-99+` for a 20,000-byte file answered `+206+` with `+Accept-Ranges: bytes+`.
The default response also carried `+Cache-Control: public,max-age=2592000,must-revalidate+` (30 days, `+public+`) and `+Content-Disposition: inline+`.

Two changes follow for anything that is not a public cover image. The servlet serves exactly the file you return and does no confinement of its own, and the Javadoc example builds `+new File(folder, pathInfo)+`; the class above resolves, normalises and checks the prefix, which is the minimum (also resolve symbolic links with `+toRealPath()+` if the folder may contain any; not run).
And a response that is `+public+` for 30 days may be stored by shared caches, so override `+getExpireTime+` and the headers for files that only some users may see, and authorise inside `+getFile+` (return `+null+` for 404, throw `+IllegalArgumentException+` for 400). Also override `+isAttachment+` and `+getContentType+` for user-supplied files, so that an uploaded HTML or SVG file is delivered as a download or with a safe content type and not as active content of your origin (xref:web/jsf/file-upload-and-download.adoc#validating[the upload validation section]).

[#sec]
== The sec: Tags (Jakarta Security)

OmniFaces 5.0 added three tags under `+xmlns:sec="omnifaces.security"+` that render their content by the state of the Jakarta Security `+SecurityContext+`: `+<sec:authorize role="ADMIN">+` (or `+anyRole="ADMIN, EDITOR"+`, or `+allRoles="ADMIN, AUDITOR"+`; exactly one of the three),
`+<sec:isAuthenticated>+` and `+<sec:isAnonymous>+`. `+var="isAdmin"+` on `+authorize+` exposes the result as a variable for several uses. If no `+SecurityContext+` is available a warning is logged and nothing is rendered (it fails closed).

[source,xml]
----
<sec:authorize anyRole="LIBRARIAN, ADMIN">
  <h:link value="Manage catalogue" outcome="/admin/catalogue"/>
</sec:authorize>
<sec:isAnonymous>
  <h:link value="Sign in" outcome="/login"/>
</sec:isAnonymous>
----

Source: https://showcase.omnifaces.org/security/AuthorizeTagHandler[OmniFaces showcase: AuthorizeTagHandler] and https://omnifaces.org/docs/vdldoc/current/sec/authorize.html[OmniFaces VDL: sec:authorize]

These were read in the documentation and not run. They are tag handlers, evaluated when the view is built like JSTL tags (xref:web/jsf/jstl-and-build-time-vs-render-time.adoc[the JSTL page]), so the decision is made once per view build and not on each render. They hide user interface elements; they authorise nothing. Protect the targets
with a `+security-constraint+`, `+@RolesAllowed+` or the checks of the service layer (xref:web/jsf/security.adoc#roles[the roles section]), and treat the tags as a convenience that keeps the menu honest.

`+o:ignoreValidationFailed+`, `+o:enableRestorableView+`, `+o:graphicImage+`, the EL functions, `+Ajax+`, `+@RateLimit+`, `+o:socket+` and `+o:sse+` separately, FacesViews and the resource handlers.

[#books]
== Where the Books Are Outdated

None of the eight books that this section consulted covers OmniFaces 4 or 5: the newest of them, the second edition of the PrimeFaces cookbook, dates from May 2015, and the others from 2004 to 2014. They solve by hand, or by other libraries, problems that OmniFaces now solves, and some of what they teach is
no longer possible or no longer safe. Taking the topics that the books treat and that this page covers:

* *Helper code around `+FacesContext+`.* The books that work with `+FacesContext+` and `+ExternalContext+` directly (Mann on the context objects, the JSF 2.0 reference of Burns and Schalk, Leonard's recipes) leave the reader to write the shortcuts for parameters, messages, redirects and file downloads in every project. `+Faces+`, `+Messages+`, `+Servlets+` and `+Ajax+` are those shortcuts, maintained, with Ajax-aware redirects (<<faces-util>>).
* *Selecting objects and converters.* The converter chapters (Leonard on standard and custom converters, Burns and Schalk) write one converter per entity, which usually queries the database on every postback. `+SelectItemsConverter+` needs none (<<converters>>).
* *Request parameters.* Books written for JSF 2.x inject a parameter with `+@ManagedProperty+` from `+javax.faces.bean+`, which was removed in Faces 4.0. `+@Param+` (<<param>>) is the replacement, with conversion, validation and messages the old annotation never had.
* *Custom handlers.* The extension chapters (Burns and Schalk on `+PhaseListener+`, `+ExceptionHandler+`, `+ViewHandler+` and factories; Leonard on custom resource handlers and the JSF 2.0 `+ExceptionHandler+`; Jonna on Ajax error handling and resource optimisation) end in code you write yourself. The finished versions are `+FullAjaxExceptionHandler+`, `+CombinedResourceHandler+`, `+VersionedResourceHandler+` and `+CDNResourceHandler+` (<<exceptions>>, <<resource-handlers>>).
* *Pretty and bookmarkable URLs.* Leonard's view parameter and pretty URL recipes, and the PrettyFaces library, belong to JSF 2.0; FacesViews and the extensionless mapping of Faces 4.0 serve the need today (<<facesviews>>, <<viewparam>>).
* *Push.* PrimeFaces Push on Atmosphere (Çalışkan and Varaksin) was removed in PrimeFaces 7.0; the answers are `+o:socket+` and `+f:websocket+` (<<push>>).
* *Cross-field validation.* The validation chapters (Leonard on cross-field validation, Burns and Schalk, Dudney and others) write a custom validator for "password equals confirmation"; `+o:validateEqual+`, the rest of the family and class-level `+o:validateBean+` replace them (<<validators>>).
* *Libraries that ended.* RichFaces, Tomahawk, Trinidad, Seam 2 and PrettyFaces appear in Leonard's recipes and in Burns and Schalk; they ended, and PrimeFaces with OmniFaces and the standard features is the maintained route.
* *Everything before Faces 2.3 and Jakarta.* `+javax.faces.*+` imports, `+http://java.sun.com/jsf/*+` namespaces and JSP views in all of them; OmniFaces 4 and 5 use `+jakarta.*+` and, from 5.0, one URN namespace (<<install>>).

[#pitfalls]
== Common Mistakes

Security first, then correctness.

* *Trusting `+Faces.getRemoteAddr()+` or the default of `+@RateLimit+`.* Both take the client address from the `+Forwarded+`, `+X-Forwarded-For+` or `+X-Real-IP+` header when present; a client that sends a different one each time defeats the limit (<<cdi-scopes>>). Behind a proxy that overwrites the header, fine; otherwise give `+clientId+`.
* *Public image methods in a `+@GraphicImageBean+`.* Every public method that returns `+byte[]+` or `+InputStream+` is a public GET URL with a guessable parameter (<<graphic>>).
* *`+o:cache+` with `+scope="application"+`* for anything user-specific, or around a form (<<tags>>).
* *`+o:enableRestorableView+` on a page whose action changes data* with only the view state as protection (<<tags>>).
* *Filters that FacesViews skips.* Security filters mapped only for `+REQUEST+` do not run for dynamic routes and redirects unless `+FACES_VIEWS_FILTER_AFTER_DECLARED_FILTERS+` is set (<<facesviews>>).
* *`+FileServlet+` without confinement*, and with the default public 30-day cache (<<fileservlet>>); `+Faces.sendFile+` with a user-chosen name (<<faces-util>>).
* *Conditions the client controls.* `+disabled="#{param.x}"+` on a validator, a CDN URL in user-editable configuration, a path or channel name from a request (<<validators>>, <<resource-handlers>>, <<push>>).
* *`+escape="false"+` on `+o:messages+`* and `+o:printStackTrace+` on a page a user can see (<<messages>>, <<functions>>).
* *A `+toString()+` that holds more than an id* under `+SelectItemsConverter+`: all of it goes into the page source (<<converters>>).
* *Parameters that arrive unchecked.* `+@Param+` path segments, `+@Cookie+` values, `+o:scriptParam+` and `+o:hashParam+` are client data; validate them (<<param>>).
* *A `+@Param+` message that never shows* because the bean was created after the messages component rendered; use `+@Eager(viewId = ...)+`, not `+requestURI+`, which fails without a `+FacesContext+` (<<param>>).
* *Mixing up the two `+@ViewScoped+` annotations and the two `+@Startup+` annotations:* `+jakarta.faces.view.ViewScoped+` against `+org.omnifaces.cdi.ViewScoped+`, `+jakarta.ejb.Startup+` against `+org.omnifaces.cdi.Startup+` (<<eager>>).
* *The jar in the wrong place or twice* (<<install>>); *old namespaces* that disappear in 6.x (<<install>>); *`+@Param+` without `+@Inject+`* that is deprecated since 5.4 (<<param>>).
* *`+o:socket+` and `+o:sse+` in one view on Mojarra* (<<push>>); *`+o:implicitNumberConverter+` for public currency input* (<<converters>>).
* *Placing a multi-field validator between its inputs* (<<validators>>).
* *Treating `+sec:authorize+` as access control.* It hides links; the constraint must exist on the server (<<sec>>).
