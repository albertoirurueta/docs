[#what]
== What PrimeFaces Extensions Is

PrimeFaces Extensions is a community-driven open source project (MIT licensed) that adds Faces components and utilities to
PrimeFaces: components missing from PrimeFaces, and variants of existing ones. It is a separate project from PrimeFaces: it lives in
its own GitHub organisation (`+primefaces-extensions+`) and has its own issue tracker and release notes. The project site says its releases are intended to follow the PrimeFaces releases, and the repository README maps each
Extensions major line to one PrimeFaces line:

.Version pairing from the README (16.x and the three previous lines)
[cols="1,2",options="header"]
|===
|PrimeFaces Extensions
|Built for

|16.x (16.0.0)
|PrimeFaces 16.0.0

|15.x
|PrimeFaces 15.0.0

|14.x
|PrimeFaces 14.0.0

|13.x
|PrimeFaces 13.0.0
|===

Source: https://github.com/primefaces-extensions/primefaces-extensions[PrimeFaces Extensions README: Versioning] and https://primefaces-extensions.github.io/[PrimeFaces Extensions project site]

Three consequences follow from the pairing, and they decide most upgrade problems:

* *Upgrade both together.* An Extensions release is compiled against one PrimeFaces version (the parent POM of 16.0.0 sets
  `+primefaces.core.version+` to 16.0.0). Mixing Extensions 16 with PrimeFaces 15 is not something the project promises.
* *The components are PrimeFaces components.* Most of them extend PrimeFaces base classes, use PrimeFaces widgets (`+PF('name')+`),
  its Ajax engine and its search expressions, so what the xref:web/jsf/primefaces-ajax-forms-and-validation.adoc#model[other PrimeFaces pages] say about `+process+`, `+update+` and the
  lifecycle applies unchanged.
* *Some components exist in both libraries.* `+pe:blockUI+`, `+pe:tooltip+` and `+pe:remoteCommand+` have PrimeFaces core
  counterparts (`+p:blockUI+`, `+p:tooltip+`, `+p:remoteCommand+`); see <<catalogue>>.

[#setup]
== Setup

=== Maven coordinates

The Extensions JAR does *not* bring PrimeFaces with it. In the published POM of 16.0.0 the `+primefaces+` dependency has scope
`+provided+`, so a project that lists only the Extensions JAR gets no transitive PrimeFaces (checked with `+mvn dependency:tree+`,
which listed the Extensions JAR alone). Declare both, with the same version:

.pom.xml (dependencies)
[source,xml]
----
<properties>
    <primefaces.version>16.0.0</primefaces.version>
</properties>

<dependencies>
    <dependency>
        <groupId>org.primefaces</groupId>
        <artifactId>primefaces</artifactId>
        <version>${primefaces.version}</version>
    </dependency>
    <dependency>
        <groupId>org.primefaces.extensions</groupId>
        <artifactId>primefaces-extensions</artifactId>
        <version>${primefaces.version}</version>
    </dependency>
</dependencies>
----

Source: https://repo1.maven.org/maven2/org/primefaces/extensions/primefaces-extensions/16.0.0/primefaces-extensions-16.0.0.pom[primefaces-extensions 16.0.0 POM on Maven Central] and https://github.com/primefaces-extensions/primefaces-extensions[PrimeFaces Extensions README: Maven]

The README still shows a `+<classifier>jakarta</classifier>+` dependency under "Release (jakarta)". For 16.0.0 the Maven Central
directory holds one binary JAR (plus sources, Javadoc and SBOM files) and no `+jakarta+` classifier JAR, and its `+faces-config.xml+`
declares Faces 4.0, so use the plain coordinates above.

=== The namespace

Faces 4.0 and later identify tag libraries by URN. The Extensions JAR ships two tag library descriptors (checked in the JAR): the
URN `+primefaces.extensions+` and the old URI `+http://primefaces.org/ui/extensions+`. PrimeFaces core has the same pair
(`+primefaces+` and `+http://primefaces.org/ui+`). The old namespaces still work in 4.1, but support for them is planned to be removed in Faces 5.0, so use the URNs; the prefix is only an alias, and `+pe+` is the convention:

.basics.xhtml: namespaces, a tooltip and a QR code
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core"
      xmlns:ui="jakarta.faces.facelets"
      xmlns:p="primefaces"
      xmlns:pe="primefaces.extensions">
<h:head>
  <title>Bookshelf extensions</title>
</h:head>
<h:body>
  <h:form id="f">
    <p:growl id="msg"/>
    <p:commandButton id="share" value="Share" icon="pi pi-share-alt" type="button"/>
    <pe:tooltip for="share" value="Copy the link to this book"/>
    <pe:qrCode id="qr" text="https://bookshelf.example.org/book.xhtml?isbn=9780441172719" size="160" label="Dune" radius="0"/>
  </h:form>
</h:body>
</html>
----

Source: https://primefaces-extensions.github.io/vdldoc/[PrimeFaces Extensions VDL documentation] and https://github.com/primefaces-extensions/primefaces-extensions[PrimeFaces Extensions README: Namespaces]

Two observations from running this page. First, `+radius="0"+` on `+pe:qrCode+` is deliberate: in 16.0.0 the component's `+radius+`
property is declared `+Double+` but its default is the `+Integer+` `+0+`, so a `+pe:qrCode+` without an explicit `+radius+` fails
while rendering with `+ClassCastException: class java.lang.Integer cannot be cast to class java.lang.Double+`, on Mojarra (HTTP
500) and on MyFaces alike (reproduced on both; the cast is in `+QRCodeBaseImpl.getRadius+`). Setting the attribute makes the
component store a `+Double+` and the page renders. Second, the rendered page contained the Extensions script
(`+primefaces-extensions.js+`, `+?ln=primefaces-extensions+`) and a widget call `+PrimeFaces.cw("ExtTooltip",...)+`: the library
registers a resource handler and a system event listener from its own `+META-INF/faces-config.xml+` (it is ordered *after*
PrimeFaces), so nothing is needed in `+web.xml+` or in your `+faces-config.xml+`.

=== Resources and the build

Extensions' own CSS and JavaScript are served by the Faces resource handler like any library resource (see
xref:web/jsf/resource-handling.adoc[resource handling]) and are minified inside the JAR. The wiki page that explains a
`+org.primefaces.extensions.DELIVER_UNCOMPRESSED_RESOURCES+` context parameter describes releases before 3.2.0 only and says that
later releases ship no uncompressed copies (they use source maps for debugging); do not set it. For your own pages, the project
also publishes a Maven plugin, `+org.primefaces.extensions:resources-optimizer-maven-plugin+`, which compresses and merges
JavaScript and CSS at build time; Maven Central lists 2.7.9 as the latest version (checked 2026-10-08; the 16.0.0 build itself
uses 2.6.6), and it was not run for this page. The performance page
(xref:web/jsf/performance.adoc#combining[combining resources]) discusses the OmniFaces alternative; whether
`+CombinedResourceHandler+` and the Extensions resource handler cooperate was not tested.

[#sanitizer]
== Safe HTML: Sanitizing Converters, Editors and the Output Listener

Extensions is the one library of this section that ships a dedicated defence for user-supplied HTML, and it deserves the first
example because it is easy to use wrongly. It is built on the OWASP Java HTML Sanitizer, which parses markup and rebuilds it from
an allow-list (a `+PolicyFactory+`).

=== pe:sanitizer: a converter

`+pe:sanitizer+` is a converter tag (class `+org.primefaces.extensions.converter.SanitizingConverter+`, registered as
`+primefaces.SanitizingConverter+`). Its attributes are `+policy+` (a `+PolicyFactory+`; the default is a *strict* policy that
allows no tags) and `+decodeHtml+` (default `+true+`). As a converter it runs when the submitted value is converted, in _Process
Validations_ (xref:web/jsf/converters.adoc[converters], xref:web/jsf/request-processing-lifecycle.adoc#phases[lifecycle phases]),
so the bean setter only ever sees the sanitized text; `+getAsString+` sanitizes again on the way out.

.sanitize.xhtml: the default (strict) converter, shown escaped and unescaped
[source,xml]

<?xml version="1.0" encoding="UTF-8"?>

      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core"
      xmlns:ui="jakarta.faces.facelets"
      xmlns:p="primefaces"
      xmlns:pe="primefaces.extensions">
<h:head>
  <title>Review comment</title>
</h:head>
<h:body>

|===

The last two rows are the trap. With the default `+decodeHtml="true"+` the converter sanitizes and then decodes HTML entities
(`+SanitizingConverter.sanitize+` calls the OWASP decoder after the policy). Entity-encoded markup survives the policy as harmless
text and is then turned back into *live markup*: the stored value is plain text that contains `+<script>+` or an `+<img onerror>+`.
That is safe only if every place that prints it escapes it. Printed with `+escape="false"+`, as in the last column, the response
contains the payload as markup, which is cross-site scripting (the test inspected the response, no browser ran it). The rule,
which the xref:web/jsf/security.adoc#xss[security page] gives for `+escape+` in general:

* *With the default converter, store plain text and print it escaped.* The converter then merely removes markup the user should
  not be sending.
* *If you must print HTML, sanitize with `+decodeHtml="false"+` and an explicit policy,* so the stored value is HTML that is
  already safe to print unescaped:

.ReviewPolicies.java
[source,java]

package org.example.bookshelf.web;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Named;
import org.owasp.html.PolicyFactory;
import org.owasp.html.Sanitizers;

/** The HTML a review may contain: inline formatting and links, nothing else. */
@Named
@ApplicationScoped
public class ReviewPolicies {

    private final PolicyFactory review = Sanitizers.FORMATTING.and(Sanitizers.LINKS);

    public PolicyFactory getReview() {
        return review;
    }
}
----

=== pe:sunEditor and pe:markdownEditor: editors that sanitize

`+pe:sunEditor+` (a WYSIWYG editor; it replaced the removed CKEditor, see <<moved>>) and `+pe:markdownEditor+` carry the `+secure+`
attribute (default `+true+`) and the `+allowBlocks+`, `+allowFormatting+`, `+allowLinks+`, `+allowStyles+`, `+allowImages+`,
`+allowTables+` and `+allowMedia+` switches. With `+secure="true"+` their renderers sanitize the submitted value in decode (and
`+pe:sunEditor+` also sanitizes the value it renders into the editor).

package org.example.bookshelf.web;

import jakarta.annotation.PostConstruct;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.ArrayList;
import java.util.List;
import org.primefaces.extensions.model.dynaform.DynaFormControl;
import org.primefaces.extensions.model.dynaform.DynaFormLabel;
import org.primefaces.extensions.model.dynaform.DynaFormModel;
import org.primefaces.extensions.model.dynaform.DynaFormRow;

/** A form whose fields come from a model instead of from the page. */
@Named
@ViewScoped
public class BorrowDynaFormBean implements Serializable {

    /** The value holder of one field; the page binds the control to {@code data.value}. */
    public static class Field implements Serializable {
        private final String name;
        private final boolean required;
        private Object value;

        public Field(String name, boolean required) {
            this.name = name;
            this.required = required;
        }

        public String getName() {
            return name;
        }

        public boolean isRequired() {
            return required;
        }

        public Object getValue() {
            return value;
        }

        public void setValue(Object value) {
            this.value = value;
        }
    }

    private DynaFormModel model;
    private final List<String> submitted = new ArrayList<>();

    @PostConstruct
    void init() {
        model = new DynaFormModel();
        row(model.createRegularRow(), "Reader name", new Field("name", true), "text");
        row(model.createRegularRow(), "Email", new Field("email", true), "text");
        row(model.createRegularRow(), "Loan weeks", new Field("weeks", false), "select");
        row(model.createRegularRow(), "Note", new Field("note", false), "area");
    }

    private void row(DynaFormRow row, String label, Field field, String type) {
        DynaFormLabel l = row.addLabel(label);
        DynaFormControl c = row.addControl(field, type);
        l.setForControl(c);
    }

    public void submit() {
        submitted.clear();
        for (DynaFormControl control : model.getControls()) {
            Field f = (Field) control.getData();
            submitted.add(f.getName() + "=" + f.getValue());
        }
    }

    public DynaFormModel getModel() {
        return model;
    }

    public List<String> getSubmitted() {
        return submitted;
    }

    public List<Integer> getWeeks() {
        return List.of(1, 2, 3, 4);
    }
}

* The sheet loaded in headless Chrome and showed the 12 books.
* Editing a numeric cell (the copies of the row at index 1, set to 7) fired the `+change+` Ajax behaviour at once, and the row object held 7 afterwards.
* Editing a text cell fires `+change+` later: after the selection moves on. The event then describes the *newly selected* row and

  and use the event only to learn that something changed.
* Firing a change with no cell selected (a script that sets a value without selecting a cell) threw a
  `+NullPointerException+` in `+Sheet.queueEvent+` because `+getSelectedRow()+` was `+null+`. A person always selects a cell
  first; this matters for UI tests that edit through the widget API: select the cell first.

and a real one would add a `+@Min(0)+` constraint, which Bean Validation applies to the row property as it does for any
input (xref:web/jsf/bean-validation.adoc[Bean Validation]; not run for the sheet).

[#waypoint]
== pe:waypoint: React to Scrolling

`+pe:waypoint+` registers a trigger on the position of an element in the viewport (the jQuery Waypoints library). The behaviour
event is `+reached+`, and the event object carries the scroll direction. Attributes: `+for+` (the target component; the parent
if omitted), `+offset+`, `+continuous+`, `+triggerOnce+`, `+enabled+`, `+horizontal+` and `+forContext+` (a scrollable container
instead of the window). The _Bookshelf_ feed loads four more books when the sentinel at the end of the list is reached.

.FeedScrollBean.java
[source,java]
----
package org.example.bookshelf.web;

import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.ArrayList;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;
import org.primefaces.extensions.event.WaypointEvent;

/** Loads the next chunk of books when the sentinel at the end of the list scrolls into view. */
@Named
@ViewScoped
public class FeedScrollBean implements Serializable {

    private static final int CHUNK = 4;

    @Inject
    private transient BookService books;

    private final List<Book> shown = new ArrayList<>();
    private int events;

    public List<Book> getShown() {
        if (shown.isEmpty()) {
            appendChunk();
        }
        return shown;
    }

    /** Fires for both directions; only scrolling down loads more. */
    public void onReached(WaypointEvent event) {
        events++;
        if (event.getDirection() == WaypointEvent.Direction.DOWN) {
            appendChunk();
        }
    }

    private void appendChunk() {
        List<Book> all = books.all();
        int from = Math.min(shown.size(), all.size());
        shown.addAll(all.subList(from, Math.min(from + CHUNK, all.size())));
    }

    public int getEvents() {
        return events;
    }
}
----

Source: https://primefaces-extensions.github.io/vdldoc/[PrimeFaces Extensions VDL: waypoint]

Three things learned by running it. First, `+offset+` is written into the widget configuration as raw JavaScript: `+offset="bottom-in-view"+`
(the string form some waypoint libraries use) rendered `+offset:bottom-in-view+` and the page threw `+SyntaxError: Unexpected token 'in'+`,
so the widget never existed. A JavaScript string literal such as `+offset="'100%'"+` and a function expression (the form the showcase uses) worked; a bare number is
documented in the VDL but was not run.
Second, `+reached+` fires for both directions: scrolling back up fires it too (7 events in the test below), so the listener loads
only for `+WaypointEvent.Direction.DOWN+`. Third, in headless Chrome the list grew from 4 to 8 when the test scrolled to the bottom,
and to 12 only after it scrolled back to the top and down again (the sequence 8, 12, 12, 12 on both implementations); repeatedly
scrolling to the bottom without leaving it did not load a third chunk. Waypoints compare positions at scroll time and the Ajax update
moves the sentinel, so test the feel in a real browser, and keep the sentinel outside the region that you update (it is a sibling of
`+feed+` above). Scrolling was driven with `+window.scrollTo+`, not with a mouse wheel.

[#remote]
== Calling the Server from JavaScript: pe:remoteCommand

`+pe:remoteCommand+` creates a JavaScript function, named by `+name+`, that runs a server method over Ajax. It has the usual Ajax
attributes (`+process+`, `+update+`, `+oncomplete+`, `+partialSubmit+`, `+resetValues+`, `+autoRun+`, `+delay+`, `+timeout+`) and adds what
the core component lacks: *typed parameters*. `+pe:methodSignature+` declares the Java types, in order; each `+pe:methodParam+`
names a JavaScript argument and may carry a converter; `+pe:assignableParam+` writes a parameter straight into a bean property
through an EL value expression.

import jakarta.faces.view.ViewScoped;
import jakarta.inject.Named;
import java.io.Serializable;
import java.time.LocalDate;
import java.util.Date;

/** Receives typed parameters from a JavaScript call through pe:remoteCommand. */
@Named
@ViewScoped
public class ShelfRemoteBean implements Serializable {

    /** A scanned shelf label, sent from JavaScript as JSON. */
    public static class Scan implements Serializable {
        private String shelf;
        private int slot;

        public String getShelf() {
            return shelf;
        }

        public void setShelf(String shelf) {
            this.shelf = shelf;
        }

        public int getSlot() {
            return slot;
        }

        public void setSlot(int slot) {
            this.slot = slot;
        }
    }

    private String last = "nothing yet";
    private String assigned = "";

    /** The signature declared with pe:methodSignature: String, Date, Scan. */
    public void received(String reader, Date when, Scan scan) {
        last = reader + " | " + (when == null ? "no date" : LocalDate.ofInstant(when.toInstant(), java.time.ZoneOffset.UTC)) + " | " + scan.getShelf() + "/" + scan.getSlot();
    }

    public String getLast() {
        return last;
    }

    public String getAssigned() {
        return assigned;
    }

    public void setAssigned(String assigned) {
        this.assigned = assigned;
    }
}

Source: https://primefaces-extensions.github.io/vdldoc/[PrimeFaces Extensions VDL: remoteCommand, methodSignature, methodParam and assignableParam]

Clicking the button in headless Chrome called `+shelfScanned('mira', '2026-10-08', JSON.stringify({shelf: 'B2', slot: 7}))+`; the
bean received a `+String+`, a `+Date+` (converted by `+f:convertDateTime+`) and a `+Scan+` object (built by `+pe:convertJson+`, which

Both implementations agreed. The parameters come from the client, so treat them like any request parameter: the `+Scan+` object
is built from client JSON, so validate its fields and never trust it for authorisation. The Java class named in
`+pe:methodSignature+` is written with its binary name (`+ShelfRemoteBean$Scan+` for the nested class).

`+pe:javascript+` is a client behaviour that runs a JavaScript expression on an event instead of sending a request (its VDL
description says it intercepts the event to prevent the Ajax call); it receives the widget's event data as `+ext+`.
See xref:web/jsf/client-behaviors.adoc[client behaviours] for the mechanism it plugs into; it was not run here.

The migration guide also records two renames that the 16.x line inherits: `+pe:qrCode+` attributes `+mSize+`, `+mPosX+` and
`+mPosY+` became `+labelSize+`, `+labelPosX+` and `+labelPosY+` in 14.0.4, and `+ThemeAccentColorResourceHandler+` became

`+mSize+`, `+mPosX+` and `+mPosY+` keys (observed in the page output), which is internal.

[#timeline]
== Timeline: Now p:timeline

The book's `+pe:timeline+` is not in the Extensions tag library any more; PrimeFaces core has `+p:timeline+`, documented as an
interactive graph to visualize events in time. Its value is a `+TimelineModel+` of `+TimelineEvent+` objects built with
`+TimelineEvent.<String>builder()+`. The PrimeFaces timeline page also shows a custom menu facet, loading screens and tooltips.

.timeline.xhtml
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:p="primefaces">
<h:head>
  <title>Acquisitions</title>
</h:head>
<h:body>
  <p:timeline id="acquisitions" value="#{acquisitionTimelineBean.model}" height="250px"/>
</h:body>
</html>
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/components/timeline[PrimeFaces 16 documentation: Timeline]

.AcquisitionTimelineBean.java
[source,java]
----
package org.example.bookshelf.web;

import jakarta.annotation.PostConstruct;
import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Named;
import java.time.LocalDate;
import org.primefaces.model.timeline.TimelineEvent;
import org.primefaces.model.timeline.TimelineModel;
import org.primefaces.util.EscapeUtils;

/** Acquisition dates of the catalogue, drawn by the PrimeFaces core p:timeline. */
@Named
@RequestScoped
public class AcquisitionTimelineBean {

    private TimelineModel<String, String> model;

    @PostConstruct
    void init() {
        model = new TimelineModel<>();
        add("Dune acquired", LocalDate.of(2024, 3, 12));
        add("Hyperion acquired", LocalDate.of(2025, 9, 2));
    }

    /** The event text is written into the page as markup: encode whatever did not come from you. */
    private void add(String text, LocalDate day) {
        model.add(TimelineEvent.<String>builder().data(EscapeUtils.forHtml(text)).startDate(day).build());
    }

    public TimelineModel<String, String> getModel() {
        return model;
    }
}
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/components/timeline[PrimeFaces 16 documentation: Timeline]

The bean compiled against PrimeFaces 16.0.0 as written (`+TimelineModel<String, String>+`; the documentation example uses the raw
type) and both implementations drew the two events in headless Chrome. The browser console logged
`+You disabled XSS protection for vis-Timeline+`, a warning from the bundled library, and it is accurate. The event `+data+` goes into
the page as the `+content+` of an inline script object and is shown as HTML. With the text `+<b>Dune</b> "q" </script><i>x</i>+`
passed unencoded (Mojarra), the page contained `+content:"<b>Dune</b> "q" </script><i>x</i>"+`: the double quote ended the
JavaScript string (`+SyntaxError: Unexpected identifier 'q'+`) and `+</script>+` ended the script element. That is script
injection if the text comes from users. Encoding the text first with `+org.primefaces.util.EscapeUtils.forHtml+` (the helper class the
PrimeFaces documentation uses in its exporter example), as the bean above does, produced
`+content:"&lt;b&gt;Dune&lt;/b&gt; &#34;q&#34; &lt;/script&gt;&lt;i&gt;x&lt;/i&gt;"+` and the timeline showed the text literally. This is
behaviour of PrimeFaces core, not of Extensions; it is recorded here because moving from `+pe:timeline+` to `+p:timeline+` is the
migration this section is about, and the fix is on your side.

[#lifecycle]
== Where the Components Sit in the Lifecycle

Extensions components follow the same request processing lifecycle as every Faces component
(xref:web/jsf/request-processing-lifecycle.adoc#phases[the six phases]), and the earlier pages on xref:web/jsf/ajax.adoc[Ajax] and xref:web/jsf/primefaces-ajax-forms-and-validation.adoc[PrimeFaces] apply:
`+process+` chooses what is decoded, converted, validated and updated, `+update+` what is re-rendered
(xref:web/jsf/ajax.adoc#execute-render[execute and render]).

.Where each group of components takes part
[cols="2,3",options="header"]
|===
|Group
|Phases that matter

|Input components: `+pe:codeMirror+`, `+pe:sunEditor+`, `+pe:markdownEditor+`, `+pe:timePicker+`, `+pe:sheet+`, `+pe:dynaForm+` controls
|_Apply Request Values_ reads the submitted string (the editors sanitize here), _Process Validations_ converts and validates (so the `+pe:sanitizer+` converter runs here), _Update Model Values_ calls the setter. Validation failure skips _Invoke Application_
|Output only: `+pe:fluidGrid+`, `+pe:qrCode+`, `+pe:tooltip+`, `+pe:session+`
|_Render Response_ only
|Behaviour sources: `+pe:waypoint+`, `+pe:sheet+` events, `+pe:remoteCommand+`
|An Ajax request enters at _Apply Request Values_ with the `+process+` ids; listeners run in _Invoke Application_ (or earlier when `+immediate+` is set); `+pe:remoteCommand+` parameters are converted by the nested converters before the method is called
|Navigation: `+pe:masterDetail+`
|The level is an input of the component (`+level+` binding); `+pe:selectDetailLevel+` changes it in the same request, then _Render Response_ draws the new level
|===

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a401[Jakarta Faces 4.1 specification, 2.2 Standard Request Processing Lifecycle Phases] and https://primefaces-extensions.github.io/vdldoc/[PrimeFaces Extensions VDL]

The table is derived from how the components are built (input components, behaviours, renderers), and from the observed results
above; the exact phase of every event of every component was not traced with a `+PhaseListener+`.

[#mojarra-myfaces]
== Mojarra and MyFaces

Every example above ran on both implementations with the same results, except for these points:

* *Conversion messages:* Mojarra printed `+{0}: Conversion error occurred.+` for a bad `+pe:timePicker+` value, MyFaces
  `+Pickup time: Conversion error occurred.+` (the label placeholder).
* *Scripted Ajax posts:* MyFaces only treated a post as coming from the form when the request carried the hidden field
  `+f_SUBMIT=1+` that its rendered form contains (a hand-built request without it did not apply the posted values). Browsers send the field, so the difference
  matters only for tests that build requests by hand, and for tools that post forms without rendering the page first.
* *Rendering details:* partial-response and view-state ids differ between the two (`+j_id1:...+` versus `+j_id__v_0:...+`) in the raw Ajax
  responses; Extensions does not hide that.
* *The `+pe:qrCode+` `+radius+` defect:* both implementations fail the same way (<<setup>>).

Everything else, including the sanitizer results, the editors, the sheet events, `+pe:remoteCommand+` conversion and the exports, was
identical in the runs. Not compared: application servers other than Tomcat with Weld, and Faces 4.0.

[#versions]
== What Changed

* *Extensions 8.0 to 11.0:* Badge, Exporter, Gravatar, LetterAvatar and Social deprecated in 10.0.0 and removed in 10.0.1; FAB and
  Scaffolding deprecated in 11.0.0 and PrinterBehavior removed in 11.0.0; `+ThemeAccentColorResourceHandler+` moved to
  `+org.primefaces.extensions.application+` in 11.0.0 (migration guide).
* *12.0.5 and 12.0.6:* CKEditor removed (legal reasons); SunEditor added as the replacement.
* *13 to 14:* `+pe:inputPhone+` decodes values as E.164 numbers; use `+formatOnDisplay="true"+` or a converter to display another
  form. In 14.0.1 its `+countrySearch+` attribute was removed (always on). In 14.0.4 the `+pe:qrCode+` label attributes were renamed.
* *15.0.2:* `+ThemeAccentColorResourceHandler+` renamed `+ThemeModificationResourceHandler+`.
* *16.0.0-RC1 to 16.0.0 (2026):* the project moved to PrimeFaces' component development kit (the release notes list "CDK" migrations
  for many components, which is why attributes now come with generated descriptions), gave `+pe:markText+` a backend Ajax round trip,
  updated Orgchart, SunEditor 3.x and jQuery UI Layout 2.0.0 and added touch drag and drop to Kanban. 16.0.0 adds the `+complete+` event to `+pe:inputOtp+` and an
  `+outsideClickDeselects+` option on `+pe:sheet+`.
* *PrimeFaces core, for contrast:* the PrimeFaces 16 "What is new" page lists its own changes (button `+size+`, dialog
  `+dismissableMask+`, GMap asynchronous loading, and others); they are not Extensions changes.

Source: https://github.com/primefaces-extensions/primefaces-extensions.github.com/wiki/Migration-Guide[PrimeFaces Extensions wiki: Migration Guide], https://github.com/primefaces-extensions/primefaces-extensions/releases[PrimeFaces Extensions release notes] and https://primefaces.github.io/primefaces/16_0_0/#/gettingstarted/whatsnew[PrimeFaces 16 documentation: What is new]

[#books]
== Where the Books Are Outdated

Sudheer Jonna's _Learning PrimeFaces Extensions Development_ (Packt, 2014) targets Extensions 1.2.1 and PrimeFaces 4.0, and its
sample code is on GitHub. For the Extensions-specific chapters it is a useful tour of ideas, but little of the setup and many of
the components have changed:

* *Packaging and namespace.* Its `+javax.faces+` pages with `+xmlns:pe="http://primefaces.org/ui/extensions"+` become `+jakarta.faces.*+` with the URN `+primefaces.extensions+` (<<setup>>). The project wiki's "Getting Started"
  page uses the old URI (still accepted) and says PrimeFaces is a transitive dependency, which is not true for 16.0.0 (the
  dependency is `+provided+`).
* *Components that are gone or renamed:* CKEditor, exporter, timeline, spotlight and Ajax error handling (<<moved>>); their
  replacements are in PrimeFaces core, SunEditor and the core exception handler.
* *Components that stayed but were reworked:* tooltips, `+pe:remoteCommand+` (typed parameters through `+pe:methodSignature+` and
  `+pe:methodParam+`), `+pe:dynaForm+`, `+pe:fluidGrid+`, `+pe:layout+`, `+pe:masterDetail+`, `+pe:codeMirror+`, `+pe:waypoint+`,
  `+pe:timePicker+`, QR codes and the image components: check each attribute against the VDL instead of trusting the book.
* *Utility functions and resource optimisation.* The 16.0.0 tag library declares no EL functions, and resource handling is
  the optimizer plugin plus ordinary Faces resource handling (<<setup>>, and the section's performance page).
* *Security.* Check any book sample that prints rich text or user input against <<sanitizer>> before copying it, in particular any
  `+escape="false"+` output. The CKEditor XSS fix in 8.0.4 and its removal in 12.0.5 show that rich-text input needs care.
* *Release practice.* The book describes one downloadable release; Extensions now releases in step with
  PrimeFaces and still releases older lines (the release list shows 15.0.18 and 13.0.21), so choose the line that matches your PrimeFaces line.

Source: https://www.packtpub.com/product/learning-primefaces-extensions-development/9781783983247[Learning PrimeFaces Extensions Development (Packt publisher page; blocks automated requests, open it in a browser)] and https://github.com/sudheerj/Learning-Primefaces-Extension-Development[companion code on GitHub]

[#pitfalls]
== Pitfalls

* *Mixed versions.* Extensions 16.0.0 with PrimeFaces 15 (or the reverse) is not supported by the pairing table. Use one property for both.
* *Expecting a transitive PrimeFaces.* The Extensions dependency is `+provided+`; leave out `+primefaces+` and the application has no PrimeFaces classes (not run: expect a
  class-loading failure).
* *Missing optional libraries.* Editors with `+secure="true"+` want the OWASP sanitizer on the classpath, `+pe:convertJson+` wants Gson,
  `+pe:inputPhone+` wants libphonenumber. Add the dependency, or set `+secure="false"+` only if you accept the consequences.
* *Printing sanitized text with `+escape="false"+` after `+decodeHtml="true"+`.* Entity-encoded markup comes back as markup (<<sanitizer>>).
* *Trusting `+secure+` on `+pe:codeMirror+`.* The renderer in 16.0.0 does not apply it; escape and validate the value yourself.
* *`+pe:qrCode+` without `+radius+`.* A `+ClassCastException+` in 16.0.0 on both implementations; set `+radius="0"+`.
* *Raw JavaScript attributes.* `+pe:waypoint+` `+offset+` is emitted as JavaScript source, so a string needs quotes inside the attribute value.
* *Sheet events describe the selection, not the edit.* Read changed values from the model; select a cell before scripting a change.
* *Mixing `+p:+` and `+pe:+` versions of blockUI, tooltip and remoteCommand.* They are different components with different attributes.
* *User text in `+p:timeline+` events.* Encode it with `+EscapeUtils.forHtml+` (or sanitize) before adding it to the model.
* *Assuming CSP support.* The xref:web/jsf/security.adoc#csp[security page] documents PrimeFaces' content security policy mode; whether the Extensions
  widgets (Handsontable, CodeMirror, SunEditor and others) work under a strict policy was not tested, so test them with
  `+primefaces.CSP+` set to `+reportOnly+` first (xref:web/jsf/security.adoc#csp[CSP]).
* *Components not run.* Monaco, Kanban, OrgChart, ECharts, GChart, OSMap, DocumentViewer, Keynote, CodeScanner, InputPhone and the
  rest of the catalogue were not run; learn each from the showcase before depending on it.
