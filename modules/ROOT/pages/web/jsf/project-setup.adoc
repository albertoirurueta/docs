[#what-a-project-consists-of]
== What a Faces Project Consists Of

A Faces application is an ordinary Jakarta EE web application: a WAR file with Facelets views (`+.xhtml+`), Java classes
for the backing beans and services, and a few descriptors. The Jakarta EE Tutorial lists the minimum as a web deployment
descriptor, a set of application classes and Faces pages, and optionally an application configuration resource file, tag
library descriptors and a set of JAR files. The tutorial still lists `+web.xml+` as required, but later sections of this
page show that a Servlet 6.1 container can map the `+FacesServlet+` without it; the table shows what each file is for and
whether the _Bookshelf_ ships it.

[cols="2,3,3,1",options="header"]
|===
| File or directory | Purpose | Spec or tutorial reference | Bookshelf

| `+pom.xml+`
| Declares the WAR packaging, the compile-time API and, outside a Jakarta EE server, the Faces and CDI implementations.
| Maven, see the next section
| yes

| `+WEB-INF/web.xml+`
| Declares the `+FacesServlet+`, its mapping, the welcome files and the `+jakarta.faces.*+` context parameters.
| Faces 4.1 spec, chapter 11.1
| yes

| `+WEB-INF/beans.xml+`
| Tells the CDI container which classes of the archive are beans.
| CDI 4.1 spec, bean archives
| yes

| `+WEB-INF/faces-config.xml+`
| The application configuration resource: locales, resource bundles, navigation rules, factories, listeners, flows.
| Faces 4.1 spec, chapter 11.3
| yes

| `+WEB-INF/templates/+`
| Facelets templates that must not be requested directly by a browser.
| Facelets, see the xref:web/jsf/templating.adoc[templating] page of this section
| yes

| `+resources/+`
| Web resources (styles, scripts, images, composite components) served through the resource handler.
| Faces 4.1 spec, chapter 2.6
| yes

| `+contracts/+`
| Resource library contracts (themes and template sets).
| Faces 4.1 spec, chapter 2.7
| yes

| `+META-INF/faces-config.xml+` in a JAR
| Lets a library contribute components, converters or listeners without touching the application.
| Faces 4.1 spec, chapter 11.3
| no
|===

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_basic_requirements_of_a_jakarta_faces_application[Jakarta EE Tutorial: Basic Requirements of a Jakarta Faces Application]

The ASP.NET Web Forms counterpart of this set of descriptors is `+Web.config+` together with the page directives; the
xref:web/aspnet/web-forms/http-pipeline-handlers-and-configuration.adoc[Web Forms configuration page] shows how a Web
Forms site registers handlers and settings. In Faces the equivalent of a registered handler is the one servlet declared in
`+web.xml+`.

[#maven-war]
== The Maven WAR

A Faces WAR needs two kinds of dependencies, and the difference between them decides almost every packaging problem.

* *The API*, needed at compile time because the beans and components import `+jakarta.faces.*+`, `+jakarta.inject.*+` and
  `+jakarta.enterprise.*+`. It is declared with `+provided+` scope so that Maven compiles against it but does not put it
  into the WAR.
* *The implementation*, needed at run time. A Jakarta EE server (GlassFish, WildFly, Payara, Open Liberty, TomEE) ships
  its own, so the WAR must not contain one. A plain servlet container such as Tomcat ships none, so the WAR must carry
  Mojarra or MyFaces and a CDI implementation.

The specification states the packaging rule directly: the Servlet, Tags and Faces API classes, and the Faces
implementation classes, are normally made available to all web applications through the container's shared facilities and
therefore should not be included inside the web application archive.

=== Choosing the API dependency

[cols="3,3,4",options="header"]
|===
| Coordinates | Contains | Use it when

| `+jakarta.platform:jakarta.jakartaee-web-api:11.0.0+`
| The whole Jakarta EE 11 Web Profile API; its pom pulls in `+jakarta.faces:jakarta.faces-api:4.1.2+`, Servlet 6.1, CDI,
Expression Language 6.0, Bean Validation, Persistence and the other web-profile specifications.
| The target is a Jakarta EE 11 server. One dependency covers the beans, services, entities and views of the application.

| `+jakarta.platform:jakarta.jakartaee-api:11.0.0+`
| The Platform API, a superset of the Web Profile.
| The application also uses specifications outside the Web Profile.

| `+jakarta.faces:jakarta.faces-api:4.1.2+`
| Only the Faces API.
| The application is a thin layer over a few Faces classes, or the other specifications arrive separately (for example
Servlet and CDI from Tomcat and Weld).
|===

Source: https://jakarta.ee/specifications/faces/4.1/[Jakarta Faces 4.1 -- Maven coordinates] and https://jakarta.ee/specifications/webprofile/11/[Jakarta EE Web Profile 11]

The Faces 4.1 API artifact lives under the group id `+jakarta.faces+` (not `+jakarta.platform+`), and the `+latest+`
entry of the artifact's metadata on Maven Central points at the `+5.0.0-M9+` milestone, so always pin `+4.1.2+` rather than
asking for the latest version.

=== A complete pom.xml

The pom below builds a WAR that runs unchanged on a Jakarta EE 11 server and, with a Maven profile, on Tomcat 11 with either
implementation. Selecting a profile with `+-Ptomcat-mojarra+` or `+-Ptomcat-myfaces+` adds the run-time JARs to the WAR.
The xref:web/jsf/tomcat-and-weld.adoc#descriptors[Tomcat and Weld] page of this section explains the Tomcat side in depth.

[#servlet-definition]
== Declaring the FacesServlet in web.xml

Every Faces request goes through `+jakarta.faces.webapp.FacesServlet+`. The specification calls it the standard servlet
that provides the request processing lifecycle: on each request it obtains a `+FacesContext+` from the factory, runs the
lifecycle's execute and render steps and releases the context. The servlet name is free, but the mapping must use the same
value.

A `+web.xml+` for Servlet 6.1 starts with this root element; the version attribute and the schema file are what a Jakarta EE
11 server expects:

.The skeleton of a Servlet 6.1 web.xml with the FacesServlet
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<web-app xmlns="https://jakarta.ee/xml/ns/jakartaee"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-app_6_1.xsd"
         version="6.1">

  <display-name>Bookshelf</display-name>

  <servlet>
    <servlet-name>facesServlet</servlet-name>
    <servlet-class>jakarta.faces.webapp.FacesServlet</servlet-class>
    <load-on-startup>1</load-on-startup>
  </servlet>
  <servlet-mapping>
    <servlet-name>facesServlet</servlet-name>
    <url-pattern>*.xhtml</url-pattern>
  </servlet-mapping>

</web-app>
----

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6066[Jakarta Faces 4.1 specification, 11.1.1 Servlet Definition] and https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_basic_requirements_of_a_jakarta_faces_application[Jakarta EE Tutorial: Identifying the Servlet for Lifecycle Processing]

`+load-on-startup+` makes the container initialise the servlet when the application is deployed instead of on the first
request. The `+web.xml+`, `+faces-config.xml+` and `+beans.xml+` files on this page validate against the schemas named in their
root elements (`+web-app_6_1.xsd+`, `+web-facesconfig_4_1.xsd+`, `+beans_4_1.xsd+`).

=== When the servlet is mapped for you

Since Servlet 3.0 the `+web.xml+` entry above is optional. The `+FacesServlet+` API documentation states that the servlet
is mapped automatically if it is not explicitly mapped in `+web.xml+` or `+web-fragment.xml+` and at least one of these
conditions holds:

* a `+faces-config.xml+` file is found in `+WEB-INF+`;
* a `+faces-config.xml+` file, or a file whose name ends in `+.faces-config.xml+`, is found in the `+META-INF+` directory
  of a JAR on the classpath;
* the `+jakarta.faces.CONFIG_FILES+` context parameter is declared;
* the set of classes handed to the runtime's servlet container initializer is not empty. Those are the classes annotated
  with, or extending, the Faces types the API lists, among them `+FacesConfig+`, `+ResourceDependency+`,
  `+FacesComponent+`, `+UIComponent+`, `+Converter+`, `+FacesConverter+`, `+ListenerFor+`, `+FacesBehaviorRenderer+`,
  `+Renderer+`, `+FacesValidator+` and `+Validator+`.

When the servlet is mapped automatically, it receives four patterns: `+/faces/*+`, `+*.jsf+`, `+*.faces+` and `+*.xhtml+`. The
automatic `+*.xhtml+` mapping can be switched off with the context parameter `+jakarta.faces.DISABLE_FACESSERVLET_TO_XHTML+`.
The flowchart summarises the decision.

.How Faces decides whether and how to map the FacesServlet
[mermaid]
----
flowchart TD
    A["Container deploys the WAR"] --> B{"FacesServlet declared in web.xml or web-fragment.xml?"}
    B -- yes --> C["Only the declared url-pattern entries apply"]
    B -- no --> D{"faces-config.xml, CONFIG_FILES or a Faces type found?"}
    D -- no --> E["Faces is not activated"]
    D -- yes --> F["Map /faces/*, *.jsf, *.faces and *.xhtml"]
    F --> G{"DISABLE_FACESSERVLET_TO_XHTML is true?"}
    G -- yes --> H["Leave out *.xhtml"]
    G -- no --> I["Keep all four patterns"]
----

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/webapp/FacesServlet.html[Jakarta Faces 4.1 API: FacesServlet]

The same behaviour was observed on both implementations. A WAR whose `+web.xml+` has no servlet entry but ships
`+WEB-INF/faces-config.xml+` answered `+/index.xhtml+`, `+/faces/index.xhtml+`, `+/index.jsf+` and `+/index.faces+`, and
disabling the `+*.xhtml+` mapping made `+/index.xhtml+` return the unprocessed source while the other three kept working.
An explicit declaration is still recommended because it documents the URL space of the application, and because the
automatic mapping exposes four URL variants of every view instead of one.

[#servlet-mapping]
== The FacesServlet Mapping

The mapping decides which request paths are Faces requests and how `+FacesServlet+` derives the view id (the path of the
XHTML file) from the request path. The specification requires an implementation to support any valid `+url-pattern+`,
prefix or extension, and recommends `+/faces/*+` for prefix mapping and `+*.faces+` for extension mapping. The Jakarta EE
Tutorial uses `+*.xhtml+` and mentions extensionless URLs.

image::jsf-servlet-mapping.svg["Three request paths, with an extension mapping, a prefix mapping and an extensionless mapping, reaching the same Bookshelf view through the FacesServlet",width=900]

Table of the four mappings and what they do. The "observed" column describes the scratch run, which produced the same
results with Mojarra 4.1.17 and MyFaces 4.1.4.

[cols="2,3,3,3",options="header"]
|===
| Mapping | Declaration | Request URL for `+/books/list.xhtml+` | Observed behaviour

| Extension, `+*.xhtml+`
| `+<url-pattern>*.xhtml</url-pattern>+`
| `+/books/list.xhtml+`
| Views are served at their file names. A request to a file that does not exist, or to `+/WEB-INF/web.xml+`, returned 404.
No other extension answered (`+/index.faces+` returned 404).

| Extension, `+*.faces+` or `+*.jsf+`
| `+<url-pattern>*.faces</url-pattern>+`
| `+/books/list.faces+`
| The view id is the path with the Facelets suffix put back. With only this mapping declared, `+/index.faces+` rendered and
`+/index.xhtml+` returned the unprocessed source from the container's default servlet.

| Prefix, `+/faces/*+`
| `+<url-pattern>/faces/*</url-pattern>+`
| `+/faces/books/list.xhtml+`
| The prefix is removed to find the file. With only this mapping declared, `+/books/list.xhtml+` itself returned the
unprocessed XHTML source instead of a rendered page.

| Extensionless, exact
| `+<url-pattern>/books/list</url-pattern>+` in addition to a normal mapping
| `+/books/list+`
| One mapping per view. The Jakarta EE Tutorial describes this as manually exact-mapping the `+FacesServlet+`; in the
scratch run `+/index+` answered when `+/index+` was listed, and nothing else gained a URL.
|===

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6076[Jakarta Faces 4.1 specification, 11.1.2 Servlet Mapping] and https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_basic_requirements_of_a_jakarta_faces_application[Jakarta EE Tutorial: Identifying the Servlet for Lifecycle Processing]

=== Extension mapping, the recommended default

Mapping `+*.xhtml+` is the simplest and safest choice. The URL names the file, the container's default servlet never sees a
view, and nothing outside `+WEB-INF+` can be requested as source. All the Jakarta EE Tutorial examples use it, with
`+index.xhtml+` as the welcome file.

=== Prefix mapping and the exposed source

Prefix mapping keeps the URL space of Faces apart from other servlets, which helps when one WAR mixes Faces with REST
endpoints or static content. Its drawback is the one in the figure: the XHTML files still exist at their physical paths, and
a request that does not carry the prefix is served by the container's default servlet as plain text. The `+FacesServlet+` API
documentation names the remedy, applying a `+<security-constraint>+` to all Facelets files and flow definition files, and
the safest practical alternative is to combine the prefix mapping with views stored under `+WEB-INF+`, which the container
never serves. A prefix mapping also puts `+/faces+` into every bookmarkable URL, so it is rarely used for new applications.

.Prefix mapping with the matching welcome file
[source,xml]
----
<servlet-mapping>
  <servlet-name>facesServlet</servlet-name>
  <url-pattern>/faces/*</url-pattern>
</servlet-mapping>

<welcome-file-list>
  <welcome-file>faces/index.xhtml</welcome-file>
</welcome-file-list>
----

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_basic_requirements_of_a_jakarta_faces_application[Jakarta EE Tutorial: Identifying the Servlet for Lifecycle Processing] and https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/webapp/FacesServlet.html[Jakarta Faces 4.1 API: FacesServlet]

=== Extensionless URLs

Faces 4.0 introduced the context parameter `+jakarta.faces.AUTOMATIC_EXTENSIONLESS_MAPPING+`. The API documentation says the
implementation enables the extra mapping if and only if the value equals `+true+` (ignoring case); it is off by default.
Mojarra's context parameter reference adds that enabling it walks the whole web application root at startup and registers a
servlet mapping for every view found, so the startup cost grows with the number of views.

.Automatic extensionless mapping in web.xml
[source,xml]
----
<context-param>
  <param-name>jakarta.faces.AUTOMATIC_EXTENSIONLESS_MAPPING</param-name>
  <param-value>true</param-value>
</context-param>
----

With this parameter set and the servlet declared with only `+*.xhtml+`, `+/index+` answered in the scratch run on both
implementations, and `+/faces/index.xhtml+` did not, because the declared mapping replaced the automatic four. With no
servlet declared at all, every variant answered (`+/index+`, `+/index.xhtml+`, `+/faces/index.xhtml+`, `+/index.jsf+` and
`+/index.faces+`).

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/webapp/FacesServlet.html[Jakarta Faces 4.1 API: FacesServlet] and https://github.com/eclipse-ee4j/mojarra/blob/4.1/CONTEXT-PARAMS.md[Mojarra 4.1 context parameters]

The alternative is to list the exact paths yourself:

.Manual extensionless mapping for two views
[source,xml]
----
<servlet-mapping>
  <servlet-name>facesServlet</servlet-name>
  <url-pattern>*.xhtml</url-pattern>
  <url-pattern>/books/list</url-pattern>
  <url-pattern>/books/detail</url-pattern>
</servlet-mapping>
----

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_basic_requirements_of_a_jakarta_faces_application[Jakarta EE Tutorial: Identifying the Servlet for Lifecycle Processing]

=== Where the view id comes from

For an exact mapping the specification's `+ViewHandler+` algorithm obtains the facelets suffix from the context parameter
`+jakarta.faces.FACELETS_SUFFIX+` (or its default `+.xhtml+`), so `+/books/list+` becomes the view id `+/books/list.xhtml+`.
Because the mapping only changes the URL, backing beans, navigation outcomes and `+h:link+` targets are written with view
ids in every case; the xref:web/jsf/request-processing-lifecycle.adoc#restore-view[lifecycle] page of this section shows how the view id is used in the Restore View phase.

[#context-parameters]
== Context Parameters

The specification requires every implementation to support a fixed list of `+jakarta.faces.*+` application configuration
parameters, set with `+<context-param>+` elements in `+web.xml+` (or `+web-fragment.xml+`). The names always start with
`+jakarta.faces.+` since Faces 3.0; the old `+javax.faces.*+` names of the books have no effect in Faces 4.x. The table groups
the ones that matter when a project is set up, with the defaults documented by the specification and by the
Mojarra reference. A parameter that an implementation adds on top (`+com.sun.faces.*+` for Mojarra, `+org.apache.myfaces.*+`
for MyFaces) is in the comparison section further down.

[cols="3,2,5",options="header"]
|===
| Parameter | Default | Effect

| `+jakarta.faces.PROJECT_STAGE+`
| `+Production+`
| Where the application is in its development lifecycle: `+Development+`, `+UnitTest+`, `+SystemTest+` or `+Production+`,
the constants of `+jakarta.faces.application.ProjectStage+`. Other settings default from it; it can also be set through JNDI.

| `+jakarta.faces.FACELETS_REFRESH_PERIOD+`
| `+0+`, or `+-1+` in `+Production+`
| Seconds between checks for a changed view file. `+-1+` never checks again after compilation, `+0+` checks on every request.

| `+jakarta.faces.FACELETS_SKIP_COMMENTS+`
| `+false+`
| When `+true+`, XML comments in the Facelets source are not delivered to the browser.

| `+jakarta.faces.FACELETS_BUFFER_SIZE+`
| `+1024+`
| Response buffer size in bytes while a view renders; `+-1+` leaves the container's size. The specification suggests
raising it in development so that an error cannot arrive after the response is partly flushed.

| `+jakarta.faces.FACELETS_SUFFIX+`
| `+.xhtml+`
| Suffix of the files that contain Facelets views.

| `+jakarta.faces.FACELETS_VIEW_MAPPINGS+`
| none
| Semicolon-separated list of extensions or prefixes that must be treated as Facelets regardless of their extension.

| `+jakarta.faces.FACELETS_LIBRARIES+`
| none
| Semicolon-separated, web-root-relative paths of tag library files to load.

| `+jakarta.faces.FACELETS_DECORATORS+`
| none
| Semicolon-separated names of `+TagDecorator+` classes applied when a view is compiled.

| `+jakarta.faces.STATE_SAVING_METHOD+`
| `+server+`
| Where the view state is kept: `+server+` (the session) or `+client+` (a hidden field of the page). The value is
compared ignoring case.

| `+jakarta.faces.PARTIAL_STATE_SAVING+` and `+jakarta.faces.FULL_STATE_SAVING_VIEW_IDS+`
| `+true+`, none
| Disable partial state saving, or list views that must use the full mechanism. Both are deprecated since Faces 4.1, because
full state saving will be removed.

| `+jakarta.faces.SERIALIZE_SERVER_STATE+`
| `+false+`
| With server state saving, guarantees that the stored state is serializable.

| `+jakarta.faces.CONFIG_FILES+`
| none
| Comma-separated, context-relative paths of additional configuration resources. They are added to the files found in
`+META-INF+`, they do not replace that scan (see <<faces-config>>). `+/WEB-INF/faces-config.xml+` must not be listed.

| `+jakarta.faces.DISABLE_FACESSERVLET_TO_XHTML+`
| `+false+`
| Switches off the automatic `+*.xhtml+` mapping.

| `+jakarta.faces.AUTOMATIC_EXTENSIONLESS_MAPPING+`
| `+false+`
| Adds an extensionless mapping for every view (Faces 4.0).

| `+jakarta.faces.WEBAPP_RESOURCES_DIRECTORY+`
| `+resources+`
| Path relative to the web root of the resource directory; must not start with `+/+`.

| `+jakarta.faces.WEBAPP_CONTRACTS_DIRECTORY+`
| `+contracts+`
| Path relative to the web root of the resource library contracts.

| `+jakarta.faces.RESOURCE_EXCLUDES+`
| `+.class .jsp .jspx .properties .xhtml .groovy+`
| Extensions the resource handler never serves; a configured value replaces the default entirely.

| `+jakarta.faces.CLIENT_WINDOW_MODE+`
| `+none+`
| Enables the `+ClientWindow+` feature behind `+@ClientWindowScoped+`.

| `+jakarta.faces.ENABLE_WEBSOCKET_ENDPOINT+`
| `+false+`
| Registers the WebSocket endpoint behind `+f:websocket+`.

| `+jakarta.faces.INTERPRET_EMPTY_STRING_SUBMITTED_VALUES_AS_NULL+`
| `+false+`
| Treats an empty submitted string as `+null+` before conversion and validation.

| `+jakarta.faces.VALIDATE_EMPTY_FIELDS+`
| `+auto+`
| Runs validators on empty values; `+auto+` means yes when Jakarta Validation is on the classpath.

| `+jakarta.faces.validator.ENABLE_VALIDATE_WHOLE_BEAN+`
| `+false+`
| Without it `+f:validateWholeBean+` is a no-op.

| `+jakarta.faces.LIFECYCLE_ID+`
| `+DEFAULT+`
| Identifier of the lifecycle the `+FacesServlet+` uses; also readable as a servlet `+init-param+`.
|===

An application can read its own stage, which is how the _Bookshelf_ catalogue page printed it in the scratch run:

.Reading the project stage from a backing bean
[source,java]
----
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.faces.context.FacesContext;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;

@Named
@RequestScoped
public class CatalogueBean {

    @Inject
    private BookService bookService;

    @Inject
    private FacesContext facesContext;

    public List<Book> getBooks() {
        return bookService.findAll();
    }

    public String getProjectStage() {
        return facesContext.getApplication().getProjectStage().name();
    }
}
----

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/application/ProjectStage.html[Jakarta Faces 4.1 API: ProjectStage] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a3054[Jakarta Faces 4.1 specification, 5.6.1 Jakarta Faces Objects Valid for @Inject Injection]

Injecting `+FacesContext+` into a request-scoped bean is one of the objects the specification says must be injectable
with `+@Inject+`. `+getBooks()+` here only returns an existing list; any real work (queries, calculations) stays out of
getters because they run several times per request.

[#faces-config]
== faces-config.xml

`+faces-config.xml+` is the *application configuration resource*: an XML document in the Jakarta EE namespace that
configures what annotations cannot or what an application prefers to keep out of code: locales and resource bundles,
navigation rules, factories, listeners, lifecycle phase listeners, flow definitions and the ordering of libraries. A
Faces 4.1 document must use the schema declaration shown in the specification, with `+version="4.1"+`.

.A minimal Faces 4.1 faces-config.xml with locales and a resource bundle
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<faces-config xmlns="https://jakarta.ee/xml/ns/jakartaee"
              xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
              xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-facesconfig_4_1.xsd"
              version="4.1">

  <application>
    <locale-config>
      <default-locale>en</default-locale>
      <supported-locale>es</supported-locale>
    </locale-config>
    <resource-bundle>
      <base-name>org.example.bookshelf.messages</base-name>
      <var>msg</var>
    </resource-bundle>
  </application>

</faces-config>
----

The bundle named by `+base-name+` is `+src/main/resources/org/example/bookshelf/messages.properties+` and its Spanish
sibling `+messages_es.properties+`; a view then reads a message as `+#{msg['catalogue.title']}+`. The document validated
against `+web-facesconfig_4_1.xsd+` and rendered on both implementations in the scratch run.

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6254[Jakarta Faces 4.1 specification, 11.3.5 Application Configuration Resource Format] and https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_registering_application_messages[Jakarta EE Tutorial: Registering Application Messages]

The schema declaration changed with every Faces version, and a document that names an older schema keeps running only
because the implementation reads it as written:

[cols="1,3,1",options="header"]
|===
| Faces | Namespace of the root element | `+version+`

| 4.1
| `+https://jakarta.ee/xml/ns/jakartaee+`, schema `+web-facesconfig_4_1.xsd+`
| `+4.1+`

| 4.0 and 3.0
| `+https://jakarta.ee/xml/ns/jakartaee+`, schemas `+web-facesconfig_4_0.xsd+` and `+web-facesconfig_3_0.xsd+`
| `+4.0+`, `+3.0+`

| 2.3 and 2.2
| `+http://xmlns.jcp.org/xml/ns/javaee+`
| `+2.3+`, `+2.2+`

| 2.1 and 2.0
| `+http://java.sun.com/xml/ns/javaee+`
| `+2.1+`, `+2.0+`

| 1.2
| `+http://java.sun.com/xml/ns/javaee+`
| `+1.2+`

| 1.1 and 1.0
| DOCTYPE with `+http://java.sun.com/dtd/web-facesconfig_1_1.dtd+` and `+..._1_0.dtd+`
| none
|===

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6254[Jakarta Faces 4.1 specification, 11.3.5 Application Configuration Resource Format]

=== Which configuration files are read

At startup the implementation builds a list of application configuration resources and then reads
`+/WEB-INF/faces-config.xml+` last, so that the application's own file takes precedence over the libraries it uses. The
specification's algorithm is:

* every `+META-INF/faces-config.xml+` and every file ending in `+.faces-config.xml+` in a `+META-INF+` directory on the
  classpath is added;
* if the `+jakarta.faces.CONFIG_FILES+` context parameter is present, its comma-separated, context-relative paths are
  added as well. The specification text (11.3.2) says the `+META-INF+` search is then skipped, but neither Mojarra 4.1.17
  nor MyFaces 4.1.4 skips it in an observed run, so treat `+CONFIG_FILES+` as an addition, not as a replacement;
* implementations of the `+jakarta.faces.application.ApplicationConfigurationPopulator+` service found with the
  `+ServiceLoader+` contribute a document each (the 4.1 API class; the specification text uses an older name);
* `+/WEB-INF/faces-config.xml+`, when it exists, is processed last and is never listed in `+CONFIG_FILES+`.

A library JAR that contributes components or listeners therefore ships its own `+META-INF/faces-config.xml+`. To control
the order among several such files, the library names itself and states a position:

.A library's META-INF/faces-config.xml with a name and an ordering
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<faces-config xmlns="https://jakarta.ee/xml/ns/jakartaee"
              xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
              xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-facesconfig_4_1.xsd"
              version="4.1">
  <name>bookshelfWidgets</name>
  <ordering>
    <after>
      <others/>
    </after>
  </ordering>
</faces-config>
----

The application's own `+faces-config.xml+` can in turn use `+<absolute-ordering>+` to fix the order of all libraries at once.

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6201[Jakarta Faces 4.1 specification, 11.3.2 Application Startup Behavior]

=== Is faces-config.xml still required?

No. Faces 2.0 introduced annotations for components, converters, validators and renderers, and since 4.0 CDI replaces the
managed bean facility, so a project with no navigation rules, bundles or factories can ship without the file. Keep it when
configuration is the clearer tool: resource bundles and supported locales, global navigation rules, resource library
contract mappings, lifecycle phase listeners, and the ordering of libraries.

[#beans-xml]
== beans.xml and CDI

Faces 4.1 runs on a container that supports CDI and uses it for every backing bean, for the scopes and for injecting Faces
objects. Whether a class of the WAR is a CDI bean is decided by the *bean discovery mode* of its archive, which `+beans.xml+`
configures. CDI 4.1 defines three modes:

[cols="1,4",options="header"]
|===
| `+bean-discovery-mode+` | Meaning

| `+annotated+`
| Only classes with a bean defining annotation (a scope such as `+@RequestScoped+`, `+@ApplicationScoped+`, the Faces
`+@ViewScoped+`, or `+@Dependent+`) are beans. This is the default for a non-empty `+beans.xml+` that gives no mode, and the
CDI 4.0 schema made it the default; an empty `+beans.xml+` is an implicit bean archive.

| `+all+`
| Every class is a bean. Faces backing beans and services work, but so do types that were never meant to be beans.

| `+none+`
| The archive is not a bean archive: nothing in it is discovered, so no backing bean in it resolves.
|===

Source: https://jakarta.ee/specifications/cdi/4.1/jakarta-cdi-spec-4.1.html#bean_archive_full[CDI 4.1 specification, Bean archives]

The recommended file for a Faces application is the explicit `+annotated+` mode, which keeps the discovery cost small and
makes it obvious which classes are beans:

.WEB-INF/beans.xml for CDI 4.1
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<beans xmlns="https://jakarta.ee/xml/ns/jakartaee"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/beans_4_1.xsd"
       version="4.1" bean-discovery-mode="annotated"/>
----

Source: https://jakarta.ee/specifications/cdi/4.1/jakarta-cdi-spec-4.1.html#bean_archive_full[CDI 4.1 specification, Bean archives] and https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_basic_requirements_of_a_jakarta_faces_application[Jakarta EE Tutorial: Basic Requirements]

What the scratch run showed on Tomcat with Weld, with the same `+@Named @RequestScoped+` bean in `+WEB-INF/classes+`:

* `+bean-discovery-mode="annotated"+`, `+all+`, and a bare `+<beans ... version="4.1"/>+` element: the page rendered, on both
  implementations.
* `+bean-discovery-mode="none"+`: the bean was not found.
* no `+beans.xml+` at all: the bean was not found either. A servlet container with Weld does not behave like a Jakarta EE
  server, where an annotated bean in an implicit archive is discovered without the file. Always ship the file when the target
  includes Tomcat.

The scopes that make a class a bean in a Faces application, the `+jakarta.faces.view.ViewScoped+` annotation among them, are
the subject of the xref:web/jsf/backing-beans-and-cdi.adoc[backing beans and CDI] and xref:web/jsf/scopes.adoc[scopes] pages of this section.

[#faces-config-annotation]
== @FacesConfig

`+jakarta.faces.annotation.FacesConfig+` was added in Faces 2.3 as the switch that turned on the CDI-specific features of
Faces for an application. In Faces 2.3 an application opted in by putting it on a CDI bean; from Faces 4.0, with the
managed bean facility removed and CDI mandatory, Faces always uses CDI, so the annotation is no longer needed to activate
those features.

The annotation still exists in 4.1, with a narrower role. Its API documentation says that the presence of the annotation on
a class deployed within an application guarantees activation of Faces and its CDI-specific features even when
`+/WEB-INF/faces-config.xml+` is absent and the `+FacesServlet+` is not explicitly registered. It is also a CDI qualifier.
Its `+version+` element no longer has any effect since 4.0 (the implementation's own version is leading) and is deprecated
for removal.

.A marker class that guarantees Faces activation
[source,java]
----
package org.example.bookshelf.web;

import jakarta.faces.annotation.FacesConfig;

@FacesConfig
public class FacesActivation {
}
----

The marker is only worth adding to a project that ships neither a `+faces-config.xml+` nor a `+FacesServlet+` entry and
whose classes include no other Faces type for the container initializer to notice. In the scratch run on Tomcat the marker
was never decisive: with the implementation JARs in `+WEB-INF/lib+`, a WAR with only an `+index.xhtml+` and no descriptor at
all was activated on both Mojarra and MyFaces, with or without the annotation. Do not infer from that a rule for Jakarta EE
servers, where the implementation is not in the WAR.

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/annotation/FacesConfig.html[Jakarta Faces 4.1 API: FacesConfig]

[#welcome-files]
== Welcome Files

A *welcome file* is the resource a Servlet container serves when the request is a directory such as the context root. It is
declared in `+web.xml+` and has nothing Faces-specific except what it must point to: a path that the `+FacesServlet+`
mapping matches.

.Welcome file for an extension mapping
[source,xml]
----
<welcome-file-list>
  <welcome-file>index.xhtml</welcome-file>
</welcome-file-list>
----

With the `+*.xhtml+` mapping the request `+/bookshelf/+` was answered with the rendered `+index.xhtml+` in the scratch run, on
both implementations. The right entry depends on the mapping:

[cols="2,2,3",options="header"]
|===
| Mapping | Welcome file | Reason

| `+*.xhtml+`
| `+index.xhtml+`
| The file exists and its name matches the mapping.

| `+/faces/*+`
| `+faces/index.xhtml+`
| The path has to contain the prefix. In the scratch run the entry `+index.xhtml+` made `+/+` return unprocessed source.

| `+*.xhtml+` plus `+/index+`
| `+index+`
| A name the exact mapping matches. In the scratch run `+/+` and `+/index+` both rendered. The welcome-file algorithm belongs
to the Servlet specification, so check the result on the target container.
|===

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_basic_requirements_of_a_jakarta_faces_application[Jakarta EE Tutorial: Identifying the Servlet for Lifecycle Processing] and https://jakarta.ee/specifications/servlet/6.1/[Jakarta Servlet 6.1]

The _Bookshelf_ grows page by page into the layout below. The scratch app used for this page contained the model, service

.The Bookshelf project layout
[source,text]
----
bookshelf/
├── pom.xml
└── src/
    └── main/
        ├── java/org/example/bookshelf/
        │   ├── model/                 Book, Author, Review (records and entities)
        │   ├── service/               BookService and the other application services
        │   └── web/                   CatalogueBean and the other backing beans
        ├── resources/org/example/bookshelf/
        │   ├── messages.properties
        │   └── messages_es.properties
        └── webapp/
            ├── index.xhtml            the catalogue (welcome file)
            ├── books/                 list.xhtml, detail.xhtml and the other views
            ├── resources/             served by the Faces resource handler
            │   ├── css/bookshelf.css
            │   ├── js/
            │   └── img/
            ├── contracts/             resource library contracts
            │   └── default/template.xhtml

                ├── web.xml
                ├── beans.xml
                ├── faces-config.xml

[cols="2,4",options="header"]
|===
| Location | What lives there and why

| `+java/.../model+`
| Domain types. `+Book+` is a Java record; reading its components from Expression Language needs Jakarta Expression Language 6.0
(Jakarta EE 11), which added support for `+java.lang.Record+`. On EE 10 use classes with getters.

| `+java/.../service+`
| Application-scoped or stateless services that backing beans inject. No Faces types here, which keeps them testable.

| `+java/.../web+`
| Backing beans (`+@Named+` with a scope) and the other Faces-aware classes: converters, validators, listeners.

| `+resources/org/.../messages*.properties+`
| Resource bundles registered in `+faces-config.xml+`; they are on the class path, so they are not web resources.

| `+webapp/index.xhtml+` and `+webapp/books/+`
| Views requested by URL. With the `+*.xhtml+` mapping their paths are the application's URL space.

| `+webapp/resources/+`
| Web resources. A reference such as `+<h:outputStylesheet library="css" name="bookshelf.css"/>+` was rendered by Mojarra
as a link to `+/bookshelf/jakarta.faces.resource/bookshelf.css.xhtml?ln=css+`, and the file was also directly reachable at
`+/bookshelf/resources/css/bookshelf.css+`. The directory name is configurable with `+jakarta.faces.WEBAPP_RESOURCES_DIRECTORY+`.

| `+webapp/contracts/+`
| One subdirectory per resource library contract. The name is configurable with `+jakarta.faces.WEBAPP_CONTRACTS_DIRECTORY+`.

| `+webapp/WEB-INF/templates/+`
| Templates referenced from views as `+/WEB-INF/templates/layout.xhtml+`. The container never serves `+WEB-INF+`, so the
raw template cannot be requested; a request for it returned 404 in the scratch run.

| `+webapp/WEB-INF/*.xml+`
| The three descriptors described above.
|===

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6088[Jakarta Faces 4.1 specification, 11.1.3 Application Configuration Parameters] and https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_basic_requirements_of_a_jakarta_faces_application[Jakarta EE Tutorial: Including the Classes, Pages, and Other Resources]

.model/Book.java and service/BookService.java

public record Book(long id, String title, String author, int year) {
}

[source,java]
----
package org.example.bookshelf.service;

import jakarta.enterprise.context.ApplicationScoped;
import java.util.List;
import org.example.bookshelf.model.Book;

@ApplicationScoped
public class BookService {

    private final List<Book> books = List.of(
            new Book(1, "Dune", "Frank Herbert", 1965),
            new Book(2, "Neuromancer", "William Gibson", 1984),
            new Book(3, "The Left Hand of Darkness", "Ursula K. Le Guin", 1969));

    public List<Book> findAll() {
        return books;
    }
}
----

Source: https://jakarta.ee/specifications/cdi/4.1/jakarta-cdi-spec-4.1.html#bean_archive_full[CDI 4.1 specification] and https://jakarta.ee/specifications/expression-language/6.0/[Jakarta Expression Language 6.0]

[#development]
== Development with Hot Reload

Two things speed up the edit-and-refresh loop of a Faces application: the *Development* project stage, which turns on
diagnostics and caches that re-check, and the Facelets refresh period, which lets the browser show an edited view without
a redeploy. The Jakarta EE Tutorial states that error messages can be displayed during the Development stage but are
suppressed in the Production stage, and that without a configured stage the application runs as Production.

=== The stage and the refresh period together

The refresh period is the interval, in seconds, at which the Facelets compiler checks a view file for changes. When the
parameter is not specified, the default depends on the project stage: in `+Production+` the runtime acts as if it were
`+-1+`, in every other stage as if it were `+0+`.

.How the effective refresh period is chosen
[mermaid]
----
flowchart TD
    A{"FACELETS_REFRESH_PERIOD set in web.xml?"} -- yes --> B{"Value"}
    B -- "-1" --> C["Never check again after the view is compiled"]
    B -- "0" --> D["Check on every request"]
    B -- "a positive n" --> E["Check at most every n seconds"]
    A -- no --> F{"PROJECT_STAGE"}
    F -- Production --> C
    F -- "Development, UnitTest, SystemTest" --> D
----

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6088[Jakarta Faces 4.1 specification, FACELETS_REFRESH_PERIOD in 11.1.3]

Observed behaviour in the scratch run, editing `+index.xhtml+` while the application was running and requesting it again:

[cols="3,2,3",options="header"]
|===
| web.xml parameters | Edit visible? | Notes

| `+PROJECT_STAGE=Development+`, `+FACELETS_REFRESH_PERIOD=1+`
| yes, Mojarra and MyFaces
| MyFaces only if the edit was saved more than the refresh period after the view was compiled (see below).

| `+PROJECT_STAGE=Development+`, no refresh parameter
| yes, both
| The default of `+0+` re-checks on every request.

| `+PROJECT_STAGE=Development+`, `+FACELETS_REFRESH_PERIOD=-1+`
| no, both
| An explicit `+-1+` overrides the stage default.

| no stage parameter (so `+Production+`), no refresh parameter
| no, both
| Production compiles once. The comment was also delivered because `+FACELETS_SKIP_COMMENTS+` was not set.

| `+PROJECT_STAGE+` absent, `+FACELETS_REFRESH_PERIOD=1+`
| yes, both
| The explicit period wins over the Production default.
|===

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6088[Jakarta Faces 4.1 specification, 11.1.3 Application Configuration Parameters] and https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_basic_requirements_of_a_jakarta_faces_application[Jakarta EE Tutorial: Configuring Project Stage]

Several practical details sit behind that table.

* *The container caches too.* Tomcat's `+Resources+` element caches file metadata and its `+cacheTtl+` defaults to 5000
  milliseconds, so an edit can take up to five seconds longer than the Faces setting suggests. The scratch run waited 6.5
  seconds after each edit for that reason.
* *MyFaces compares timestamps.* In MyFaces a view is reloaded when the file's last-modified time is later than the time the
  view was created plus the refresh period (the method `+needsToBeRefreshed+` of `+DefaultFaceletFactory+`). An edit saved within
  the period right after the first request is therefore not noticed, and a later request does not change that. The effect
  is invisible with the default of `+0+`, which re-compiles on every request without comparing timestamps; with a positive
  value, save the file again if the first save was too early.
* *Only views reload.* The refresh covers Facelets sources: pages, templates, composite components and tag files. Java
  classes, `+web.xml+`, `+faces-config.xml+` and `+beans.xml+` are read at startup and need a redeploy or restart.
* *Use a small value, not zero everywhere.* `+0+` re-checks on every request, so reserve it for development. A production
  server should run with `+PROJECT_STAGE+` set to `+Production+` (or unset) and `+FACELETS_REFRESH_PERIOD+` of `+-1+`.

=== An edit-and-refresh loop with Maven

The pom above produces an exploded directory as well as the WAR. Pointing the server at `+target/bookshelf+` and refreshing
that directory after each source edit avoids packaging and redeploying:

.Updating the exploded WAR after editing a view
[source,bash]
----
mvn -Ptomcat-mojarra package        # first build: target/bookshelf/ and target/bookshelf.war
# ...start the server with target/bookshelf as its web application directory...
# edit src/main/webapp/index.xhtml, then:
mvn -Ptomcat-mojarra war:exploded   # copies the changed webapp files into target/bookshelf/
----

In the scratch run `+mvn war:exploded+` copied a changed `+index.xhtml+` into `+target/bookshelf+`, and with the Development
stage the next request showed it. The `+war:exploded+` goal is documented as a way to speed up testing during development by
creating an exploded webapp in a specified directory. Java class changes still need `+mvn package+` and a redeploy; IDE
hot-swap tools reload method bodies, but not new classes, new annotations or changes to descriptors.

Source: https://maven.apache.org/plugins/maven-war-plugin/[Apache Maven WAR Plugin] and https://tomcat.apache.org/tomcat-11.0-doc/config/resources.html[Apache Tomcat 11 Resources]

[#mojarra-vs-myfaces]
== Mojarra and MyFaces: Configuration Differences

Both implementations pass the same specification and, in the scratch run, answered every mapping and welcome-file case of
this page identically. They differ in packaging, in the parameters they add and in a few defaults.

[cols="2,3,3",options="header"]
|===
| Topic | Mojarra 4.1.17 | MyFaces 4.1.4

| Maven artifacts
| One JAR, `+org.glassfish:jakarta.faces+`, with API and implementation.
| Two JARs, `+myfaces-api+` and `+myfaces-impl+`, in `+org.apache.myfaces.core+`.

| Own parameter namespace
| `+com.sun.faces.*+`, documented in `+CONTEXT-PARAMS.md+` of the 4.1 branch.
| `+org.apache.myfaces.*+`, documented in the Configuration section of the MyFaces Core 4.1 page, where `+o.a.m+` is
the shortcut used in the table.

| Servlet container initializer
| `+com.sun.faces.config.FacesInitializer+` (and `+FacesInitializer2+`).
| `+org.apache.myfaces.webapp.MyFacesContainerInitializer+`.

| Starting without a `FacesServlet`
| `+com.sun.faces.forceLoadConfiguration+` loads the configuration even when no `+FacesServlet+` is found, for applications
that register everything programmatically.
| `+org.apache.myfaces.INITIALIZE_ALWAYS_STANDALONE+` skips the servlet-mapping check, and
`+org.apache.myfaces.INITIALIZE_SKIP_JAR_FACES_CONFIG_SCAN+` skips the scan of JARs for `+faces-config.xml+`.

| Limiting the annotation scan
| `+com.sun.faces.annotationScanPackages+`, described as the largest startup win on a big classpath.
| `+org.apache.myfaces.annotation.SCAN_PACKAGES+`, and `+org.apache.myfaces.annotation.USE_CDI_FOR_ANNOTATION_SCANNING+`.

| Logging the configuration
| `+com.sun.faces.displayConfiguration+` logs all parameters at INFO instead of FINE.
| `+org.apache.myfaces.LOG_WEB_CONTEXT_PARAMS+`; the default is `+dev-only+`, which logs in the Development stage only.

| Validating configuration files
| `+com.sun.faces.validateXml+` and `+com.sun.faces.verifyObjects+`, both `+false+` by default.
| `+org.apache.myfaces.VALIDATE_XML+` and `+org.apache.myfaces.VALIDATE+`.

| Server-side state limits
| `+com.sun.faces.numberOfLogicalViews+` and `+com.sun.faces.numberOfViewsInSession+`, both 15.
| `+org.apache.myfaces.NUMBER_OF_VIEWS_IN_SESSION+` (20) and `+org.apache.myfaces.NUMBER_OF_SEQUENTIAL_VIEWS_IN_SESSION+` (4).

| Client state protection
| Encrypted by default (through a `+ByteArrayGuard+`, which also makes the state tamper evident);
`+com.sun.faces.disableClientStateEncryption+` exists for debugging and is never to be set in production.
| `+org.apache.myfaces.USE_ENCRYPTION+` is `+true+` by default, with `+ALGORITHM+`, `+SECRET+` and `+MAC_ALGORITHM+`
(`+HmacSHA256+`) as companions.

| Error handling by the implementation
| Covered by the xref:web/jsf/exception-handling.adoc[exception handling] page of this section.
| `+org.apache.myfaces.ERROR_HANDLING+`: `+false+`, but `+true+` in the Development stage.

| `+Optional` in Expression Language
| `+com.sun.faces.disableOptionalELResolver+` (4.1.4) removes the `+OptionalELResolver+` from the chain.
| `+org.apache.myfaces.enableOptionalELResolver+` (4.1.2), `+false+` by default, adds it.

| Facelets refresh with a positive period
| An edit saved at any time after the first request was picked up in the scratch run.
| Reloads only if the file's last-modified time is later than the compile time plus the period.
|===

Source: https://github.com/eclipse-ee4j/mojarra/blob/4.1/CONTEXT-PARAMS.md[Mojarra 4.1 context parameters] and https://myfaces.apache.org/#/core41[Apache MyFaces Core 4.1 -- Configuration]

Two consequences for a project that keeps both options open. First, keep implementation-specific parameters in a profile or
in the container-specific descriptor, not in the shared `+web.xml+`, because the other implementation ignores them silently.
Second, test the configuration-dependent behaviour (hot reload, state limits, error pages) on the implementation that
production uses; a Jakarta EE server fixes that choice, and the xref:web/jsf/jakarta-ee-servers.adoc#matrix[Jakarta EE servers] page of this section lists which implementation
each server bundles.

[#books]
== Where the Books Are Outdated

The eight books consulted for this section date from 2004 to 2015 and describe Faces 1.0 to 2.2. For project setup they
differ from current practice in these ways, and the official documentation of Faces 4.1 wins wherever they disagree:

* *JSP views.* The older books wire a JSP page to the `+FacesServlet+` and use `+.jsp+` extensions or the `+*.jsf+` suffix
  mapping to reach it. JSP support was removed in Faces 4.0, and the views are Facelets files.
* *The old package names.* Class names, context parameters (`+javax.faces.STATE_SAVING_METHOD+`) and the
  `+javax.faces.webapp.FacesServlet+` class in the `+web.xml+` all became `+jakarta.*+` in Faces 3.0; descriptors with the
  old names are not recognised by a Faces 4 runtime.
* *Mandatory `+faces-config.xml+` with `+<managed-bean>+` entries.* Managed beans, their scopes and the
  `+@ManagedBean+` and `+@ManagedProperty+` annotations were replaced by CDI. The Jakarta EE Tutorial's configuration chapter
  still contains pages about the managed bean facility because it documents Jakarta EE 10; do not follow them for a Faces 4.1
  project.
* *DTD-based descriptors.* The Faces 1.0 and 1.1 configuration files used a DOCTYPE with `+web-facesconfig_1_x.dtd+`; the schema
  has since moved through five namespaces, summarised in the table above.
* *Standalone Facelets 1.x.* The Facelets book describes adding a `+com.sun.facelets+` view handler to `+faces-config.xml+` and a
  `+facelets.*+` set of context parameters. Facelets has been part of Faces since 2.0 and needs neither the JAR nor the
  view handler; the `+FACELETS_*+` parameters of this page replace the old names.
* *Libraries bundled by hand.* The books tell the reader to copy `+jsf-api.jar+` and `+jsf-impl.jar+` into `+WEB-INF/lib+`. Modern
  builds declare coordinates in the pom, and on a Jakarta EE server the implementation is provided and must not be bundled.
* *Application server and tool setups of the era* (Tomcat 5 or 6 with the Sun reference implementation, early IDE wizards,
  Ant build scripts) are historical. Maven, `+provided+` scope and the descriptors on this page replace them.

[#pitfalls]
== Common Pitfalls

* *Bundling the implementation on a Jakarta EE server.* The server already loads its own implementation. A second one in
  `+WEB-INF/lib+` leads to class loading conflicts, so `+jakartaee-web-api+` stays `+provided+` and the implementation JARs go
  into a Tomcat-only profile.
* *Prefix mapping without protecting the views.* A view that does not carry the prefix is served as plain source; use
  `+*.xhtml+`, or keep views under `+WEB-INF+`, or add a `+security-constraint+`.
* *Wrong welcome file for the mapping.* `+index.xhtml+` under prefix mapping returned source in the scratch run; the entry
  has to match the mapping.
* *Production as the default stage.* A project that never sets `+PROJECT_STAGE+` runs as `+Production+`, hides development
  diagnostics and compiles each view once. Set `+Development+` in the development descriptor only; never ship it.
* *`+FACELETS_REFRESH_PERIOD+` of `+0+` or a small value in production.* It re-checks the file system on requests. Leave the
  parameter unset in `+Production+`, which uses `+-1+`.
* *Missing `+beans.xml+` on Tomcat.* Backing beans do not resolve and EL expressions silently render empty. Always ship the
  file when Tomcat is a target.
* *Expecting a Java edit to appear on refresh.* Only view files reload; classes and descriptors are read at startup.
* *Forgetting that implementation parameters are ignored by the other implementation.* `+com.sun.faces.*+` and
  `+org.apache.myfaces.*+` settings in a shared `+web.xml+` do nothing on the other runtime.
* *Enabling extensionless mapping on a big application without measuring.* The automatic variant registers one mapping per
  view found at startup.
* *Debug settings in production.* Settings such as `+com.sun.faces.disableClientStateEncryption+` exist for debugging; the
  xref:web/jsf/state-saving-and-stateless-views.adoc#client-keys[state saving] and xref:web/jsf/security.adoc[security] pages of this section explain the safe configuration.
