Much of the Faces code in production was written for JSF 2.x on Java EE 7 or 8, and some of it for JSF 1.x with JSP views.
None of it compiles or even starts on a Jakarta EE 10 or 11 runtime without changes, and some of the changes do not fail at all:
they are silently ignored and the application misbehaves. This page is the field guide for that move. It follows one small
application, the _Bookshelf_ catalogue written the way a JSF 2.3 project of 2018 would write it, through every change needed to
run it on Jakarta Faces 4.1, and it records what each tool does and what it leaves for you.

The page is written against Jakarta Faces 4.1 (API `+jakarta.faces-api+` 4.1.2, Jakarta EE 11, Java 17 or later), Eclipse Mojarra
4.1.17 and Apache MyFaces Core 4.1.4, with PrimeFaces 16.0.0 and OmniFaces 5.5.5 where libraries are involved. Faces 4.0 (Jakarta
EE 10, Java 11 or later) is named where it differs. Faces 5.0 (Jakarta EE 12) is still a milestone (`+5.0.0-M9+` is the latest on
2026-10-08), so everything said about it is "upcoming". Every experiment was run on 2026-10-08: the application was built with
Maven 3.9.16 for Java 21 (`+maven.compiler.release+` 21), deployed to an embedded Apache Tomcat 11.0.26 with Weld 6.0.4.Final on JDK 26,
and queried with `+curl+` and a small script that posts Ajax requests. Every runtime test was repeated on Mojarra and on MyFaces. A
claim that was not run is labelled "documented" or "not run".

Two other pages hold the pieces this page does not repeat. The xref:web/jsf/versions-and-implementations.adoc[Versions and
Implementations] page has the version matrix, the Java baselines and the per-release feature lists, and the
xref:web/jsf/backing-beans-and-cdi.adoc[Backing Beans and CDI] page explains the CDI model that replaces managed beans in detail.
This page is about the _move_: the order of the steps, the tools, the symptoms of each missed step, and the replacements.

[#route]
== The Route: Which Releases to Cross

A Faces application does not jump between "JSF" and "Jakarta Faces". It crosses up to four releases, each of which broke something
different. The list below is the order in which the breaks happened, and it is also the order in which a careful migration
removes them.

.What each release broke, and the minimum Java it needs
[cols="2,2,1,5",options="header"]
|===
|Faces release |Platform |Java SE |What breaks when you cross it

|2.3
|Java EE 8
|8
|Nothing. It is the best place to start: Facelets, CDI and `+javax+` still work together, and `+@ManagedBean+` is deprecated but present.

|3.0
|Jakarta EE 9 (9.1 for Java 11)
|8
|Everything named `+javax.faces+`, `+javax.servlet+`, `+javax.el+`, `+javax.enterprise+`, `+javax.inject+` becomes `+jakarta.*+`. No other change: the
specification says only that the namespace changed and that this is a breaking change.

|4.0
|Jakarta EE 10
|11
|JSP support, `+@ManagedBean+` and the `+javax.faces.bean+` scopes, `+MethodBinding+`, `+ValueBinding+` and the `+jakarta.faces.el+` package,
the `+CURRENT_COMPONENT+` constants, the deprecated `+StateManager+` methods and `+ResourceResolver+` are removed. The XML
namespaces move to the `+jakarta.faces.*+` URNs, and `+jsf.js+` becomes `+faces.js+`.

|4.1
|Jakarta EE 11
|17
|Nothing is removed that Faces 4.0 still had. More API is deprecated for removal (full state saving, `+ActionSource2+`, the custom-scope
events, `+cc:extension+`) and the `+UIComponent.bindings+` field is gone. Java 17 is required.

|5.0 (upcoming)
|Jakarta EE 12 (planned)
|21
|Planned: removal of everything deprecated for removal since 4.0, of the old namespaces, and API modernisation. Not released.
|===

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#changes-between-3-0-and-2-3[Faces 4.1 specification, B.3: Changes between 3.0 and 2.3], https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#changes-between-4-0-and-3-0[B.2: Changes between 4.0 and 3.0] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#changes-between-4-1-and-4-0[B.1: Changes between 4.1 and 4.0]

The practical consequence is a staged route. Stage 1 is done while everything is still `+javax+`, because it needs no rename and
can be tested on the platform you already run. Stages 2 to 4 are mechanical or nearly so, and the fewer problems you carry into
each stage, the easier it is to tell a rename error from a design problem.

The stages are advice, not a rule of the platform. The code can jump from 2.3 straight to 4.1 in one commit, and the Bookshelf below
does exactly that in its later sections. The staging is about _where you get feedback_: stage 1 can be verified on the old server,
and each later stage fails in a recognisable way (see <<symptoms>>).

== The Legacy Bookshelf

The application to migrate is the _Bookshelf_ catalogue as a JSF 2.3 project would have built it: a WAR for Java EE 8, `+javax+` everywhere,
two library dependencies, a managed bean with an injected service, an old-style variable resolver, a phase listener, an Ajax
button written with the old script name, a JSP page next to the Facelets pages, and the old namespaces. It compiles against
`+javax:javaee-web-api:8.0.1+` and builds a WAR; no Java EE 8 server was used in these experiments, because the subject is the move, not the old runtime. It is deliberately dense in legacy idioms, one of each kind
this page treats, so that every step has something to change. The packages follow the conventions of the section
(`+org.example.bookshelf.model+`, `+.service+` and `+.web+`, bundle variable `+msg+`).

The bean filters inside its getter, so the filter runs every time the table asks for its value. That is one of the habits of the
period that the section's best practices reject, and the migration removes it in <<beans>>. The old expression API and the old resolver
live in two small classes:

.QueryReader.java and LegacyVariableResolver.java (legacy)
[source,java]
----
package org.example.bookshelf.web;

import javax.faces.context.FacesContext;
import javax.faces.el.MethodBinding;
import javax.faces.el.ValueBinding;

/** Uses the Faces 1.x expression API that Faces 4.0 removed. */
public class QueryReader {

    public static String currentQuery() {
        FacesContext ctx = FacesContext.getCurrentInstance();
        ValueBinding vb = ctx.getApplication().createValueBinding("#{catalogue.query}");
        return (String) vb.getValue(ctx);
    }

    public static void runSearch() {
        FacesContext ctx = FacesContext.getCurrentInstance();
        MethodBinding mb = ctx.getApplication().createMethodBinding("#{catalogue.search}", new Class<?>[0]);
        mb.invoke(ctx, new Object[0]);
    }
}
----

package org.example.bookshelf.web;

import javax.faces.context.FacesContext;
import javax.faces.el.EvaluationException;
import javax.faces.el.VariableResolver;

/** A Faces 1.1 style resolver; Faces 1.2 deprecated it and Faces 4.0 removed it. */
public class LegacyVariableResolver extends VariableResolver {

    private final VariableResolver parent;

    public LegacyVariableResolver(VariableResolver parent) {
        this.parent = parent;
    }

    @Override
    public Object resolveVariable(FacesContext context, String name) throws EvaluationException {
        if ("appName".equals(name)) {
            return "Bookshelf";
        }
        return parent.resolveVariable(context, name);
    }
}

[#symptoms]
== What Happens If You Only Upgrade the Runtime

The honest way to learn what a migration step does is to leave it out. The legacy application was put on the Faces 4.1 runtime in four
increasingly well-prepared states, each on Mojarra 4.1.17 and on MyFaces 4.1.4 (Tomcat 11.0.26, Weld 6.0.4.Final). The first
column says what was in the WAR.

.Four attempts to run the Bookshelf on a Faces 4.1 runtime
[cols="3,6",options="header"]
|===
|State of the WAR |What happened (identical on both implementations unless stated)

|The legacy WAR as built (PrimeFaces 11.0.0, OmniFaces 3.14.4, `+javax+` classes and descriptors)
|Startup fails before Faces is reached. `+SEVERE: Error configuring application listener of class [org.primefaces.webapp.UploadedFileCleanerListener]+`,
`+NoClassDefFoundError: javax/servlet/ServletRequestListener+`, then `+Context [/bookshelf] startup failed due to previous errors+`. Every request answers 404.
MyFaces adds `+Class javax.faces.webapp.FacesServlet not found+`.

|Library jars replaced by PrimeFaces 16.0.0 and OmniFaces 5.5.5, application classes and descriptors still `+javax+`
|Mojarra: `+Caused by: java.lang.NoClassDefFoundError: javax/faces/event/PhaseListener+` while loading `+AuditPhaseListener+`, then
`+Servlet [facesServlet] ... threw load() exception+`; every request 404. MyFaces: `+Class javax.faces.webapp.FacesServlet not found+`,
`+Exception sending context initialized event to listener ... StartupServletContextListener+`, the same `+ClassNotFoundException: javax.faces.event.PhaseListener+`, startup failed.

|The WAR after Eclipse Transformer 1.0.0 (names rewritten to the Jakarta EE 9 form, libraries included)
|Startup fails in the OmniFaces 3.14.4 listener: `+NoClassDefFoundError: jakarta/faces/bean/ApplicationScoped+`. The transformer produced the EE 9 names, and
`+jakarta.faces.bean+` does not exist in Faces 4.x. Every request answers 404.

|The sources after the OpenRewrite recipe (see <<tools>>), with the new libraries
|Does not compile: `+javax:javaee-web-api+` is still the compile dependency and the rewritten code calls methods that no longer exist (<<tools>>).
|===

None of these failures is subtle, and that is the good news: a missing rename stops the application at startup. The dangerous states are
the ones in which the application starts. After the compile errors were fixed by hand but five legacy leftovers were kept
(`+@ManagedProperty+` without `+@Inject+`, `+javax.faces.PROJECT_STAGE+` in `+web.xml+`, a `+<managed-bean>+` entry, a `+<variable-resolver>+` entry and
`+jsf.js+`), the application deployed on both implementations and answered like this:

.A deployed application that is not migrated (Mojarra 4.1.17 and MyFaces 4.1.4)
[cols="3,3,4",options="header"]
|===
|Leftover |Observed result |Message in the log

|`+javax.faces.PROJECT_STAGE+` context parameter
|`+#{facesContext.application.projectStage}+` printed `+Production+`
|None.

|`+<managed-bean>+` entry `+settings+` in `+faces-config.xml+`
|`+#{settings.query}+` printed an empty string
|None.

|`+<variable-resolver>+` entry for `+appName+`
|`+#{appName}+` printed an empty string
|None.

|`+@ManagedProperty+` (now `+jakarta.faces.annotation+`) on a field of a CDI bean, without `+@Inject+`
|The first request for `+index.xhtml+` answered 500: `+Cannot invoke "org.example.bookshelf.service.BookService.findAll()" because "this.service" is null+`
|`+NullPointerException+` at first use. MyFaces logs it as `+occurred while processing RENDER_RESPONSE+`.

|`+<h:outputScript library="jakarta.faces" name="jsf.js"/>+`
|Mojarra renders `+<script src="RES_NOT_FOUND">+`; MyFaces renders nothing. A request for the resource answers 404 on both.
|MyFaces: `+WARNING: Resource referenced by resourceName jsf.js and libraryName jakarta.faces not found ... It will be silenty ignored.+` (spelling as logged). Mojarra: none.
|===

The first three rows are the reason the inventory of <<inventory>> searches the descriptors as well as the Java: Faces never complains about
an unknown parameter name, an unknown element it no longer reads, or a resolver it no longer calls. The `+@ManagedProperty+` row is the
costliest of the five, because the annotation still exists in the new API with a different meaning (<<beans>>).

[#when]
== Where in the Lifecycle Each Failure Shows Up

A migration problem is cheapest when it shows up early. The failures of the previous section appear at four different moments, and the later the moment, the easier it is to ship the problem. The
phases named below are those of the xref:web/jsf/request-processing-lifecycle.adoc#phases[request processing lifecycle]; the first moments happen before any request.

.When each kind of failure appears
[cols="3,3,4",options="header"]
|===
|Kind of failure |Moment |What it looks like

|A removed API called from Java (`+createValueBinding+`, `+VariableResolver+`)
|Build time
|A compile error, once the dependency is the Jakarta EE 11 API

|A `+javax+` library, or a `+javax+` or `+jakarta.faces.bean+` class that a listener or the servlet loads
|Container start-up, before Faces is reached
|`+SEVERE+` in the log, `+Context [/bookshelf] startup failed+`, every request 404

|A descriptor entry or a parameter that 4.x no longer reads (`+<managed-bean>+`, `+<variable-resolver>+`, `+javax.faces.PROJECT_STAGE+`)
|Faces start-up
|Nothing: no error and no warning on either implementation

|An old tag library URI
|View build, on the first request for a view (Restore View builds the tree from the page)
|Nothing in 4.1: the tag works. Removal is planned for 5.0.

|A script resource that no longer exists (`+jsf.js+`)
|Render Response, when the head renderer asks for the resource
|Mojarra: `+RES_NOT_FOUND+` in the markup. MyFaces: a log warning. The browser then has no `+faces+` object to call.

|An expression that no longer resolves (`+#{appName}+`, `+#{settings.query}+`)
|Wherever the expression is read, usually Render Response
|An empty string

|A field that is no longer injected (`+@ManagedProperty+` without `+@Inject+`)
|At the first use of the field: Render Response here, because the table reads `+getBooks()+`; Invoke Application for an action method
|HTTP 500 and a `+NullPointerException+`; MyFaces names `+RENDER_RESPONSE+` in the log
|===

[#javax]
== javax to jakarta (Faces 3.0, Jakarta EE 9)

The first and widest change is the one the specification states in a single sentence: the namespace changed from `+javax.faces+` to
`+jakarta.faces+`, and that is a breaking change. Jakarta EE 9 applied the same rename to every Jakarta EE API, so the change
reaches far beyond Faces: Servlet, Expression Language, CDI, Bean Validation, Persistence and the rest of the platform moved with
it. Jakarta EE 9 was only the rename, with no new behaviour (the BalusC article on Faces 4.0 describes Faces 3.0 as the same
specification and implementation as 2.3 with `+javax+` replaced by `+jakarta+`), which is why a Faces 3.0 application is the
safest intermediate stop.

The string `+javax.faces+` appears in more places than the imports. A migration that renames only the Java sources leaves the rest
working until a request touches it. Search the whole tree for each of these:

.Where the rename has to reach
[cols="3,4,4",options="header"]
|===
|Place |Old |New

|Java packages
|`+javax.faces.*+`, `+javax.servlet.*+`, `+javax.el.*+`, `+javax.enterprise.*+`, `+javax.inject.*+`, `+javax.validation.*+`, `+javax.persistence.*+`, `+javax.ejb.*+`, `+javax.websocket.*+`
|The same names under `+jakarta.+`

|Annotations in `+javax.annotation+`
|`+javax.annotation.PostConstruct+`, `+PreDestroy+`, `+Resource+`, `+Priority+`, `+javax.annotation.security.*+`
|`+jakarta.annotation.*+`. But `+javax.annotation.processing+` is part of Java SE (module `+java.compiler+`) and stays.

|Context parameters in `+web.xml+`
|`+javax.faces.PROJECT_STAGE+`, `+javax.faces.STATE_SAVING_METHOD+`, `+javax.faces.FACELETS_*+`
|`+jakarta.faces.*+`. An unrenamed name is ignored without a message (<<symptoms>>).

|Component, converter, validator and renderer identifiers
|`+javax.faces.Integer+`, `+javax.faces.Input+`, `+javax.faces.Text+`
|`+jakarta.faces.*+`, in `+faces-config.xml+`, in `+f:converter converterId+` and in `+@FacesConverter+` values

|Messages
|The bundle `+javax.faces.Messages+` and keys such as `+javax.faces.component.UIInput.REQUIRED+`
|`+jakarta.faces.Messages+` and `+jakarta.faces.component.UIInput.REQUIRED+`. A bundle with the old keys is ignored, as the xref:web/jsf/messages-and-i18n.adoc#message-bundle[messages page] shows.

|Resources
|Library `+javax.faces+` with `+jsf.js+`; URL prefix `+/javax.faces.resource/+`
|Library `+jakarta.faces+` with `+faces.js+`; URL prefix `+/jakarta.faces.resource/+` (<<faces-js>>)

|Request parameters
|`+javax.faces.ViewState+`, `+javax.faces.partial.ajax+`, `+javax.faces.source+`
|`+jakarta.faces.ViewState+` and the same under `+jakarta.faces.partial.*+`. Hand-written Ajax posts and Selenium or `+curl+` scripts break here.

|Service files
|`+META-INF/services/javax.faces.context.FacesContextFactory+` and every other factory file
|`+META-INF/services/jakarta.faces.context.FacesContextFactory+`; the specification names this form for a factory resource

|JNDI names read by Mojarra (4.0)
|`+java:comp/env/jsf/ClientSideSecretKey+`
|`+java:comp/env/faces/ClientSideSecretKey+`. This rename came with 4.0, not 3.0; the xref:web/jsf/state-saving-and-stateless-views.adoc#client-keys[state saving page] explains the silent fallback to a random key.
|===

Two Java rules decide whether a global search-and-replace is safe. The first is that not every `+javax+` package moved: the
packages that Java SE itself provides (`+javax.naming+`, `+javax.sql+`, `+javax.crypto+`, `+javax.net+`, `+javax.security.auth+`, `+javax.xml.parsers+`,
`+javax.annotation.processing+`) keep their names. A blanket `+s/javax/jakarta/+` breaks the build in exactly those places. The
second is that the rename does not tell you whether the target exists: `+javax.faces.bean+` and `+javax.faces.el+` become
`+jakarta.faces.bean+` and `+jakarta.faces.el+`, names that Faces 4.0 removed (<<removed>>).

The script below renames only the packages and names that moved. It was run on a copy of the legacy sources to which a class
with `+javax.naming+`, `+javax.sql+`, `+javax.annotation.PostConstruct+` and `+javax.annotation.processing+` imports had been added.

.javax2jakarta.sh: rename what moved, keep what Java SE owns
[source,bash]
----
#!/bin/sh
# javax2jakarta.sh [project-directory]
cd "${1:-.}" || exit 1
find src -type f \( -name '*.java' -o -name '*.xhtml' -o -name '*.xml' -o -name '*.properties' -o -name '*.js' \) -print0 |
  xargs -0 sed -i.bak -E \
    -e 's/javax\.(faces|servlet|el|enterprise|inject|validation|persistence|ejb|websocket|interceptor|transaction|xml\.bind)([."])/jakarta.\1\2/g' \
    -e 's/javax\.security\.enterprise/jakarta.security.enterprise/g' \
    -e 's/javax\.annotation\.(PostConstruct|PreDestroy|Resource|Resources|Priority|Generated|security)/jakarta.annotation.\1/g'
find src -name '*.bak' -delete
----

After it ran, 19 lines contained `+jakarta.+` and three `+javax+` lines were left: the `+javax.annotation.processing+`, `+javax.naming+` and
`+javax.sql+` imports, which is correct. The inventory of <<inventory>> then read `+0, 2, 2, 0, 1, 1, 2, 1, 1, 1, 3+`: the packages and the
parameters were done, and the work that a rename cannot do (managed beans, the old expression API, the resolver, the namespaces, the
JSP view, `+jsf.js+`, the descriptor namespaces) was still listed.

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#changes-between-3-0-and-2-3[Faces 4.1 specification, B.3: Changes between 3.0 and 2.3], https://balusc.omnifaces.org/2021/11/whats-new-in-faces-40.html[BalusC: What's new in Faces 4.0 (the Jakarta EE 9 rename)] and https://jakarta.ee/specifications/platform/9/[Jakarta EE Platform 9]

== Tools: Eclipse Transformer and OpenRewrite

Two tools do part of this work, and they do different parts. Both were run on the legacy Bookshelf. The results matter more than the
descriptions, because each tool stops at a different boundary.

[#transformer]
=== Eclipse Transformer: Names in Binaries, up to Jakarta EE 9

The Eclipse Transformer rewrites `+javax+` names to `+jakarta+` names in already built archives (WAR, JAR, EAR), in bytecode and in
text resources, using the rule sets of the Jakarta project. It needs no source and no build. Version 1.0.0 was run
from the command line on the legacy WAR:

.Transforming a WAR with the Eclipse Transformer command line
[source,bash]
----
java -jar org.eclipse.transformer.cli-1.0.0.jar bookshelf-1.0.0.war bookshelf-jakarta.war
----

It finished with `+Transformer Return Code [ 0 ] [ Success ]+`, accepted 2648 resources, changed 1245 and renamed two. Its output differed from the
original in these ways, all read from the transformed WAR:

* `+web.xml+` became `+web-app_5_0.xsd+`, `+version="5.0"+`, the `+jakarta.faces+` parameter names and the `+jakarta.faces.webapp.FacesServlet+` class.
* `+faces-config.xml+` became `+web-facesconfig_3_0.xsd+`, `+version="3.0"+`, and still named `+LegacyVariableResolver+` and the `+<managed-bean>+` entry.
* `+beans.xml+` became `+beans_3_0.xsd+`.
* The bytecode of the application and of the two libraries now refers to `+jakarta.faces.bean.ManagedBean+` and `+jakarta.faces.bean.ViewScoped+`.
* The XHTML files were not changed: the `+xmlns.jcp.org+` namespaces and `+library="javax.faces"+` with `+jsf.js+` were still there.
* The two library jars were transformed too (`+primefaces-11.0.0.jar+` now refers to `+jakarta/faces/component/UIComponent+`).

That is exactly the Faces 3.0 and Jakarta EE 9 boundary. It is the right tool to run a binary that you cannot rebuild, or a library that
has no `+jakarta+` release, on an EE 9 server. It is the wrong tool to reach Faces 4: the transformed WAR failed at startup on Faces 4.1
on both implementations, because `+jakarta.faces.bean+` does not exist there (<<symptoms>>). The transformer migrates names, not APIs.

Source: https://github.com/eclipse-transformer/transformer/blob/main/README.md[Eclipse Transformer: README] and https://projects.eclipse.org/projects/technology.transformer[Eclipse Transformer project]

OpenRewrite rewrites the _source_ of a project with recipes. The recipe set `+rewrite-migrate-java+` contains Faces recipes for every

That last recipe runs the 2.x to 3.x and 3.x to 4.x recipes, then updates the Faces API dependency to 4.1.x, replaces the OmniFaces

[#namespaces]
== XML Namespaces: java.sun.com and xmlns.jcp.org to the URNs (Faces 4.0)

Faces 4.0 replaced the HTTP URLs of its tag libraries with URNs (`+jakarta.faces.html+`, `+jakarta.faces.core+`, `+jakarta.faces.facelets+`,
`+jakarta.faces.composite+`, `+jakarta.faces.passthrough+`, `+jakarta.faces+` for pass-through elements, and `+jakarta.tags.core+` and
`+jakarta.tags.functions+` for the Tags library). The full table with the prefixes is in
xref:web/jsf/facelets-and-xhtml-views.adoc#namespaces[Facelets and XHTML Views]; the xref:web/jsf/facelets-and-xhtml-views.adoc#old-namespaces[old-namespaces
section] shows the sed script that rewrites them. This section adds what the migration experiments showed.

The descriptors have a second, separate family of namespaces, and a migration touches both. The recipe wrote `+https://jakarta.ee/xml/ns/jakartaee+` into
`+web.xml+` and `+faces-config.xml+`, and left `+beans.xml+` on `+http://xmlns.jcp.org/xml/ns/javaee+`.

.Three generations of namespaces, and the three places that use them
[cols="2,3,3,3",options="header"]
|===
|Where |JSF 1.x to 2.1 (Java EE 5, 6) |JSF 2.2, 2.3 and Faces 3.0 as written (Java EE 7, 8) |Faces 4.0 and later (Jakarta EE 9 onwards)

|Tag libraries in XHTML
|`+http://java.sun.com/jsf/html+`
|`+http://xmlns.jcp.org/jsf/html+`
|`+jakarta.faces.html+`
|Pass-through elements
|not available (the Facelets 1.x `+jsfc+` attribute)
|`+http://xmlns.jcp.org/jsf+` (prefix `+jsf:+`)
|`+jakarta.faces+` (prefix `+faces:+` by convention)
|JSTL in XHTML
|`+http://java.sun.com/jsp/jstl/core+`
|`+http://xmlns.jcp.org/jsp/jstl/core+`
|`+jakarta.tags.core+`
|Descriptors
|`+http://java.sun.com/xml/ns/javaee+`
|`+http://xmlns.jcp.org/xml/ns/javaee+`
|`+https://jakarta.ee/xml/ns/jakartaee+`
|===

Two facts were observed on Mojarra 4.1.17 and on MyFaces 4.1.4 (Tomcat 11.0.26):

* *The old tag library URIs still work.* A page with `+http://xmlns.jcp.org/jsf/html+`, `+/core+`, `+/facelets+`, `+/passthrough+`, the pass-through element
namespace `+http://xmlns.jcp.org/jsf+` and the JSTL URI rendered correctly with `+h:form+`, `+f:ajax+`, `+p:commandButton+`, `+jsf:id+` on a plain `+<form>+`, `+pt:placeholder+`
and `+c:if+`; so did the same page with the `+java.sun.com+` URIs. The specification plans to remove the old namespaces in 5.0, so treat this as a grace period.
* *The old descriptors still load.* A `+web.xml+` with the `+xmlns.jcp.org+` namespace and `+version="4.0"+` and a `+faces-config.xml+` with `+version="2.3"+`
(without the removed elements) deployed on Tomcat 11.0.26 with both implementations, and the application answered. This was run only on Tomcat; application servers
may validate descriptors more strictly. Update them anyway: editors validate against the schema named in the document, and the schema decides which elements you see.

A new page that declares the pass-through element namespace as `+xmlns:jsf="jakarta.faces"+` worked with the old prefix `+jsf:+`; the prefix is only a local alias.
The convention of the 4.x documentation is `+faces:+` (see xref:web/jsf/html5-friendly-markup.adoc#passthrough-elements[pass-through elements]).

.index.xhtml header before and after the namespaces step
[source,xml]
----
<!-- before -->
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="http://xmlns.jcp.org/jsf/html"
      xmlns:f="http://xmlns.jcp.org/jsf/core"
      xmlns:ui="http://xmlns.jcp.org/jsf/facelets"
      xmlns:c="http://xmlns.jcp.org/jsp/jstl/core"
      xmlns:p="http://primefaces.org/ui">

<!-- after -->
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"

xref:web/jsf/primefaces-getting-started-and-themes.adoc#namespace[the PrimeFaces namespace section]). The OmniFaces URI `+http://omnifaces.org/ui+` is

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#backward-compatibility-with-previous-versions[Faces 4.1 specification, B.2.1] and https://balusc.omnifaces.org/2021/11/whats-new-in-faces-40.html[BalusC: What's new in Faces 4.0 (the namespace URNs)]

[#jsp]
== JSP to Facelets

JSP was deprecated in Faces 2.0, when Facelets became the standard view declaration language, and removed in Faces 4.0, together with the
JSP tag classes of the `+jakarta.faces.webapp+` package. The BalusC article states the reason: JSP writes template text to the response as soon as
it meets it, while Faces needs it postponed to Render Response, which forced the `+f:verbatim+` workaround and an "everything must be a
component" habit. The tools of <<tools>> do not convert a JSP view; the OpenRewrite run left `+legacy.jsp+` byte for byte as it was.

The conversion is a short list of mechanical rules plus one design decision per page:

.JSP constructs and their Facelets equivalents
[cols="3,4",options="header"]
|===
|In a JSP view |In a Facelets view

|`+<%@ taglib uri="http://java.sun.com/jsf/html" prefix="h" %>+`
|`+xmlns:h="jakarta.faces.html"+` on the root element

|`+<f:view>+` around the page
|Not needed. Use `+<f:view locale="...">+` only when you need its attributes.

|`+<f:verbatim>+` around template text
|Delete it. Template text is part of the tree in the right order. The tag is gone.

|`+<jsp:include>+`, `+<%@ include %>+`
|`+ui:include+`, or better a template with `+ui:composition+` and `+ui:define+` (xref:web/jsf/templating.adoc[Templating])

|JSP comments `+<%-- --%>+`
|`+<!-- -->+` (sent to the browser) or `+ui:remove+` (not sent)

|Scriptlets, JSP declarations, `+${...}+` read as JSP EL
|Delete them. Use `+#{...}+` expressions (xref:web/jsf/expression-language.adoc[Expression Language]).

|`+c:forEach+` and `+c:if+` mixed with component tags
|Usually `+ui:repeat+` and `+rendered+`; the two sets of tags run at different times (xref:web/jsf/jstl-and-build-time-vs-render-time.adoc[JSTL and build time versus render time])

|A custom component as a JSP tag handler (`+UIComponentELTag+`) plus a `+.tld+`
|A composite component, a tag file, or `+@FacesComponent(createTag = true)+` (xref:web/jsf/composite-components.adoc[Composite Components], xref:web/jsf/custom-components-and-renderers.adoc[Custom Components and Renderers])

|The `+FacesServlet+` mapped to `+*.jsp+`, `+*.jsf+` or `+/faces/*+`
|The mapping `+*.xhtml+`, or none at all with the automatic extensionless mapping (xref:web/jsf/project-setup.adoc#servlet-mapping[Project Setup])
|===

The legacy search page converts to this Facelets page, which is the `+search.xhtml+` of the migrated Bookshelf:

.search.xhtml: legacy.jsp as a Facelets view
[source,xml]
----
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html">
<h:head>
  <title>Search</title>
</h:head>
<h:body>
  <h:form>
    <h:inputText id="query" value="#{catalogue.query}"/>
    <h:commandButton id="go" value="Search" action="#{catalogue.search}"/>
  </h:form>
</h:body>
</html>
----

It rendered on both implementations (a form with the `+jakarta.faces.ViewState+` field). The head of the page also shows that the HTML moved from "a JSP
that happens to contain Faces tags" to "a view that is a component tree": there is a `+h:head+` and a `+h:body+` instead of `+head+`
and `+body+` inside `+f:view+`, so Faces can add resources to the page (<<faces-js>>).

Old URLs are the other half of the move. Users and search engines still hold `+/search.jsp+` or `+/faces/search.jsp+`. Two observations from the run, with the
`+FacesServlet+` mapped to `+*.jsp+` as well as `+*.xhtml+`:

* A request for `+/legacy.jsp+` when a view `+/legacy.xhtml+` existed rendered that view on Mojarra and on MyFaces (`+PrimeFaces.settings+` in the page showed
`+viewId:'/legacy.xhtml'+`). The JSP file itself, with its `+<%@ taglib %>+` lines, was never read.
* The same request without a `+legacy.xhtml+` answered 404 on Mojarra and 500 on MyFaces (`+InvalidFileException: Invalid path provided: /legacy.jsp+`).

So a temporary extra mapping lets old bookmarks keep working while the pages are converted one by one, but delete the `+.jsp+` files at the same time as you
convert them: leaving the old file next to the new view only hides which of the two a user got. For a clean break, answer the old URLs with a 301
redirect from a servlet filter or from the web server in front, and remove the mapping.

Source: https://balusc.omnifaces.org/2021/11/whats-new-in-faces-40.html[BalusC: What's new in Faces 4.0 (Remove all JSP support)], https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-facelets/faces-facelets.html[Jakarta EE Tutorial: Facelets] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#backward-compatibility-with-previous-versions[Faces 4.1 specification, B.2.1 (Remove all JSP support)]

[#beans]
== Managed Beans to CDI

Faces 4.0 removed the native managed bean facility: `+@ManagedBean+`, the scopes in `+javax.faces.bean+`, `+@ManagedProperty+` in that package and the
`+<managed-bean>+` element. The mapping of every piece, with the CDI form of each, is in the
xref:web/jsf/backing-beans-and-cdi.adoc#managedbean-removed[Backing Beans and CDI page] and its
xref:web/jsf/backing-beans-and-cdi.adoc#migration-example[worked migration]. What follows is what the Bookshelf run adds: what the recipe gets wrong, and what
a managed bean silently did that a CDI bean does not.

.The result for BookService: @Named, an application scope, and an explicit start-up observer
[source,java]
----
package org.example.bookshelf.service;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.enterprise.context.Initialized;
import jakarta.enterprise.event.Observes;
import jakarta.inject.Named;
import java.util.List;
import java.util.logging.Logger;
import org.example.bookshelf.model.Book;

@Named
@ApplicationScoped
public class BookService {

    private static final Logger LOG = Logger.getLogger(BookService.class.getName());

    private final List<Book> books = List.of(
            new Book("Dune", "Frank Herbert"),
            new Book("Neuromancer", "William Gibson"),
            new Book("Snow Crash", "Neal Stephenson"));

    /** Replaces eager = true of the old managed bean: runs when the application scope starts. */
    void start(@Observes @Initialized(ApplicationScoped.class) Object event) {
        LOG.info("catalogue holds " + books.size() + " books");
    }

    public List<Book> findAll() {
        return books;
    }
}
----

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-develop/faces-develop.html#_managed_beans_in_jakarta_faces_technology[Jakarta EE Tutorial: Managed Beans in Jakarta Faces Technology] and https://docs.openrewrite.org/recipes/java/migrate/jakarta/facesmanagedbeansremoved[OpenRewrite: Substitute removed Faces Managed Beans]

Three details of this class are migration decisions, not typing:

* *`+@Named+` without a name* is `+bookService+`, the same rule `+@ManagedBean+` used, so the expressions of the views need no change. The recipe wrote the name out
(`+@Named("bookService")+`); both forms resolve.
* *`+eager = true+` has no automatic equivalent.* The recipe dropped the attribute without a trace. A CDI application-scoped bean is created on its first use. The
observer above runs when the application scope is initialised: on Mojarra 4.1.17 with Weld 6.0.4.Final on Tomcat 11 the log line appeared at start-up, before the first request.
Do this only for a bean whose start-up has a side effect you need (loading a cache, validating configuration); most services do not need it.
* *The class is not `+Serializable+` and does not need to be.* An application-scoped bean is never passivated. The view-scoped bean below is a different matter.

.CatalogueBean: @Inject instead of @ManagedProperty, and the filter out of the getter
[source,java]
----
package org.example.bookshelf.web;

import jakarta.annotation.PostConstruct;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.List;
import java.util.Locale;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;

@Named("catalogue")
@ViewScoped
public class CatalogueBean implements Serializable {

    @Inject
    private BookService service;

    private String query = "";
    private List<Book> books = List.of();

    @PostConstruct
    void init() {
        books = service.findAll();
    }

    public String getQuery() {
        return query;
    }

    public void setQuery(String query) {
        this.query = query;
    }

    public List<Book> getBooks() {
        return books;
    }

    public void search() {
        String needle = query.toLowerCase(Locale.ROOT);
        books = service.findAll().stream()
                .filter(b -> b.getTitle().toLowerCase(Locale.ROOT).contains(needle))
                .toList();
    }
}
----

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/annotation/ManagedProperty.html[Jakarta Faces 4.1 API: ManagedProperty] and https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/view/ViewScoped.html[ViewScoped]

The bean differs from the recipe's output in three ways that matter:

* *`+@Inject+` replaces the field annotation and the setter.* The recipe kept `+@ManagedProperty(value = "#{bookService}")+` with only its import changed. The annotation
still exists in 4.1, in `+jakarta.faces.annotation+`, with a different meaning: it is a CDI qualifier that evaluates an EL expression, and it injects nothing unless it is combined with
`+@Inject+`. A bean that kept it compiled, started, and answered the first request with a `+NullPointerException+` (<<symptoms>>). Grep for `+ManagedProperty+` after every automated run; the only
legitimate uses are `+@Inject @ManagedProperty("#{param.id}")+` for an EL value, as shown on the xref:web/jsf/backing-beans-and-cdi.adoc#managed-property[backing beans page].
* *The filter runs once per action, not once per render.* The legacy `+getBooks()+` filtered the service's list inside the getter, so the work ran every time the table asked for its
value, and in a real application that call would have been a database query. The migration is a good moment to remove the habit: the filter moved into `+search()+`, and the getter returns a field.
The view-scoped bean keeps the result between the postbacks of the same view. The change is behaviour-preserving for the page: Mojarra and MyFaces returned the same rows for
`+DUNE+` (case-insensitive), `+snow+` and `+neuro+`, for the `+f:ajax+` button and for the PrimeFaces button.
* *`+toLowerCase(Locale.ROOT)+`.* Case-insensitive comparison with the default locale gives wrong answers in a few locales (the Turkish dotted and dotless i). It is not a Faces
change; it is the kind of defect an old code base carries and a review during a migration finds.

Two descriptor facts complete the bean story:

* *`+beans.xml+` from the Java EE 8 era was accepted.* The unchanged file (`+xmlns.jcp.org+` namespace, `+version="2.0"+`, `+bean-discovery-mode="all"+`) deployed and worked with Weld 6.0.4.Final on
Tomcat 11. It is still worth replacing: in discovery mode `+all+` every class of the archive is a bean candidate, which is how a converter or a helper ends up injectable by accident. The Jakarta EE 11 form is shown in <<config>>.
* *Without any `+beans.xml+`, Weld on Tomcat discovered nothing.* The page rendered, and the table had no books (`+#{catalogue.books}+` resolved to nothing) and the log had no error, which is
the same silent failure as the unresolved `+settings+` managed bean. CDI's implicit bean archive rule lets a full application server discover annotated beans in an archive without `+beans.xml+` (not run on a server here); on Tomcat with Weld the
descriptor is required (see xref:web/jsf/project-setup.adoc#beans-xml[Project Setup]).

The `+<managed-bean>+` entry named `+settings+` in `+faces-config.xml+` has no replacement worth writing: it declared a session-scoped copy of `+CatalogueBean+`, nothing in the views used it, and it was removed.
If yours is used, the replacement is a class with the right scope annotation and a `+@Named+` name. Session scope for page state is the first habit to leave behind, with `+@ViewScoped+` as
the usual successor (xref:web/jsf/scopes.adoc[Scopes]).

=== The Expression API and the Resolver, Rewritten

Two classes of the legacy Bookshelf used the removed expression API. The recipe changed their imports and left the calls. The migrated `+QueryReader+` evaluates a value expression through the
`+Application+` and builds a method expression through the `+ExpressionFactory+`:

.QueryReader.java after the migration
[source,java]
----
package org.example.bookshelf.web;

import jakarta.el.ExpressionFactory;
import jakarta.el.MethodExpression;
import jakarta.faces.context.FacesContext;

/** Reads a value and calls a method through the Expression Language API of Jakarta Faces 4. */
public class QueryReader {

    public static String currentQuery() {
        FacesContext ctx = FacesContext.getCurrentInstance();
        return ctx.getApplication().evaluateExpressionGet(ctx, "#{catalogue.query}", String.class);
    }

    public static void runSearch() {
        FacesContext ctx = FacesContext.getCurrentInstance();
        ExpressionFactory factory = ctx.getApplication().getExpressionFactory();
        MethodExpression search = factory.createMethodExpression(
                ctx.getELContext(), "#{catalogue.search}", void.class, new Class<?>[0]);
        search.invoke(ctx.getELContext(), new Object[0]);
    }
}
----

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/application/Application.html[Jakarta Faces 4.1 API: Application (evaluateExpressionGet, getExpressionFactory)]

The Faces 1.1 `+VariableResolver+` becomes an `+ELResolver+`, which is a different contract: three methods that read, type and write a property of a _base_ object, and one that
tells whether a name is read-only. A resolver for a top-level name such as `+appName+` answers only when `+base+` is `+null+` and marks the property resolved.

.AppNameResolver.java replaces LegacyVariableResolver
[source,java]
----
package org.example.bookshelf.web;

import jakarta.el.ELContext;
import jakarta.el.ELResolver;

/** The EL resolver that replaces the Faces 1.1 variable resolver: it supplies the name appName. */
public class AppNameResolver extends ELResolver {

    private static final String NAME = "appName";

    @Override
    public Object getValue(ELContext context, Object base, Object property) {
        if (base == null && NAME.equals(property)) {
            context.setPropertyResolved(true);
            return "Bookshelf";
        }
        return null;
    }

    @Override
    public Class<?> getType(ELContext context, Object base, Object property) {
        if (base == null && NAME.equals(property)) {
            context.setPropertyResolved(true);
            return String.class;
        }
        return null;
    }

    @Override
    public void setValue(ELContext context, Object base, Object property, Object value) {
        // read-only: isReadOnly() answers true, so Faces never calls this for appName
    }

    @Override
    public boolean isReadOnly(ELContext context, Object base, Object property) {
        if (base == null && NAME.equals(property)) {
            context.setPropertyResolved(true);
            return true;
        }
        return false;
    }

    @Override
    public Class<?> getCommonPropertyType(ELContext context, Object base) {
        return base == null ? String.class : null;
    }
}
----

In `+faces-config.xml+` the `+<variable-resolver>+` entry becomes `+<el-resolver>+`. The old entry did not fail, and `+#{appName}+` printed an empty string (<<symptoms>>); with the new one
`+legacy.xhtml+` printed `+Bookshelf+` on both implementations.

[source,xml]
----
<application>
  <resource-bundle>
    <base-name>org.example.bookshelf.messages</base-name>
    <var>msg</var>
  </resource-bundle>
  <el-resolver>org.example.bookshelf.web.AppNameResolver</el-resolver>
</application>
----

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#backward-compatibility-with-previous-versions[Faces 4.1 specification, B.2.1] and the xref:web/jsf/extending-faces.adoc#el-resolver[ELResolver section of Extending Faces]

A resolver registered with `+<el-resolver>+` is one for the whole application. If the only need is "a value reachable by name", a CDI bean with `+@Named+` and a `+@Produces+` method does the
same without a resolver (xref:web/jsf/backing-beans-and-cdi.adoc#producers[Producers]); the resolver is the right tool when the answer depends on the `+base+` object or on the name itself.

== jsf.js to faces.js

The JavaScript API of Faces was renamed with the package: the resource `+jsf.js+` of the library `+javax.faces+` became `+faces.js+` of the library `+jakarta.faces+`, the global `+jsf+` became `+faces+`, and
the Java constants followed. Faces 4.0 introduced the new names and deprecated the old Java constants for removal.

.The Ajax JavaScript names, old and new
[cols="3,3",options="header"]
|===
|Faces 2.x (javax) |Faces 4.x

|`+<h:outputScript library="javax.faces" name="jsf.js"/>+`
|`+<h:outputScript library="jakarta.faces" name="faces.js"/>+`

|`+jsf.ajax.request(...)+`, `+jsf.ajax.addOnEvent(...)+`, `+jsf.getViewState(...)+`
|`+faces.ajax.request(...)+`, `+faces.ajax.addOnEvent(...)+`, `+faces.getViewState(...)+`

|`+window.jsf+`
|`+window.faces+`

|`+ResourceHandler.JSF_SCRIPT_LIBRARY_NAME+`, `+JSF_SCRIPT_RESOURCE_NAME+`
|`+ResourceHandler.FACES_SCRIPT_LIBRARY_NAME+`, `+FACES_SCRIPT_RESOURCE_NAME+`

|Request parameters `+javax.faces.partial.ajax+`, `+javax.faces.source+`
|`+jakarta.faces.partial.ajax+`, `+jakarta.faces.source+`
|===

The failure is in the table of <<symptoms>>: a view that asks for `+jsf.js+` gets no script, the log says so (MyFaces) or not (Mojarra), and the first
`+jsf.ajax.request+` call has no script to call (the global `+jsf+` does not exist any more; not run in a browser here). The recipe rewrote the library name in the XHTML (`+javax.faces+` to `+jakarta.faces+`) but not
`+jsf.js+`, and it rewrote `+jsf.ajax+` only in `+.js+` and `+.ts+` files, not in an `+onclick+` attribute of a page. Search the XHTML too.

.index.xhtml after the change: faces.js, the standard Ajax button, the raw API call and the PrimeFaces button
[source,xml]
----
<h:head>
  <title>#{msg['catalogue.title']}</title>
  <h:outputScript library="jakarta.faces" name="faces.js"/>
</h:head>
<h:body>
  <h:form id="searchForm">
    <h:inputText id="query" value="#{catalogue.query}"/>
    <h:commandButton id="search" value="#{msg['catalogue.search']}" action="#{catalogue.search}">
      <f:ajax execute="@form" render=":results"/>
    </h:commandButton>
    <h:commandButton id="raw" type="button" value="Raw Ajax"
                     onclick="faces.ajax.request(this, event, {execute: 'searchForm', render: 'results'}); return false;"/>
    <p:commandButton id="pf" value="PrimeFaces" action="#{catalogue.search}" update=":results"/>
  </h:form>
  <h:panelGroup id="results" layout="block">
    <h:dataTable value="#{catalogue.books}" var="book">
      <h:column><f:facet name="header">Title</f:facet>#{book.title}</h:column>
      <h:column><f:facet name="header">Author</f:facet>#{book.author}</h:column>
    </h:dataTable>
  </h:panelGroup>
</h:body>
----

The explicit `+h:outputScript+` is only needed because the page calls `+faces.ajax.request+` itself; `+f:ajax+` adds the script by itself. The `+faces.js+` resource was served
(`+/jakarta.faces.resource/faces.js.xhtml?ln=jakarta.faces+` answered 200) and `+jsf.js+` in either library was not (404 for `+ln=jakarta.faces+` and for `+ln=javax.faces+`). The Ajax page explains
the details, including why the script has to come first in the head when your own scripts use `+faces+` while loading (xref:web/jsf/ajax.adoc#faces-js[Getting faces.js onto the Page]).

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/application/ResourceHandler.html[Jakarta Faces 4.1 API: ResourceHandler (FACES_SCRIPT_LIBRARY_NAME, FACES_SCRIPT_RESOURCE_NAME)] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#changes-between-4-0-and-3-0[Faces 4.1 specification, B.2]

[#libraries]
== Libraries Across Majors

A Faces application is rarely only Faces. The component library, the utility library and the server each have their own line of releases, and each has a release at which
it crossed the `+javax+` boundary. Crossing it is part of the same migration, and the library often needs more than one step.

[#primefaces]
=== PrimeFaces

PrimeFaces did not cross the boundary at once. Its plain artifact stayed on `+javax+` for years, and a second artifact with the Maven classifier `+jakarta+` carried the same version for
the new namespace, until 16.0.0. This was checked by reading the class `+CommandButton+` in each jar on Maven Central:

Three consequences for the plan:

* *The classifier is a transition tool, not a design.* A project on Java EE 8 uses the plain artifact up to 15.x; a project on Jakarta EE uses the same version with `+<classifier>jakarta</classifier>+`;
at 16.0.0 the classifier disappears, and a build that still asks for it cannot resolve the artifact. The OpenRewrite recipe added the classifier and pinned 14.0.x, which is a correct step on the way and a wrong end.
* *Go one major at a time.* Each guide lists what was deleted and what was deprecated "for the next release". Deleting is where code breaks, so read the guide of every major you cross, grep your XHTML and Java for
the names it lists, and build and test between steps. A jump from 11 to 16 skips the deprecation notices that tell you what to change first. The xref:web/jsf/primefaces-getting-started-and-themes.adoc[PrimeFaces pages] cover the current
components; the migration guides cover the old names.
* *Not every major breaks your pages.* The legacy `+p:commandButton+` of the Bookshelf, written for PrimeFaces 11, worked unchanged on 16.0.0 (an Ajax click filtered the table on both implementations). What broke it was the namespace, not the library API.

The PrimeFaces 16 documentation page on dependencies still lists the Faces runtimes "2.3, 3.0, 4.0" while the 16.0.0 migration guide says Faces 2.x and `+javax.*+` support were removed
and the baseline is Faces 4.0; the jar agrees with the guide (all its classes use `+jakarta.faces+`). Trust the jar and the guide. The xref:web/jsf/versions-and-implementations.adoc#version-matrix[version matrix] already carries a warning about the dependencies page.

removed; the table is in xref:web/jsf/primefaces-extensions.adoc#moved[What Moved into PrimeFaces Core or Was Removed].

[#omnifaces]
=== OmniFaces

OmniFaces follows the platform with three lines, and the first of them is `+javax+`:

* *3.x* targets Faces 2.3 on Java 8. `+omnifaces-3.14.4.jar+`, the version of the legacy Bookshelf, refers to `+javax/faces/context/PartialViewContext+`. It is the line that failed in the first row of the table
in <<symptoms>>.
* *4.x* targets Faces 3.0 and 4.0 on Java 11 (last release 4.7.15).
* *5.x* targets Faces 4.1 on Java 17 (5.5.5 is the current release; 5.0 is its upper Faces version).

The OpenRewrite recipe set contains `+OmniFacesNamespaceMigration+`, which rewrites `+http://omnifaces.org/ui+` and `+http://omnifaces.org/functions+` to the single URN `+omnifaces+` of OmniFaces 5. It was
not exercised on the Bookshelf, which has no OmniFaces tags; the namespace and the `+o:+` functions are described in xref:web/jsf/omnifaces.adoc#install[the OmniFaces page]. On a Jakarta EE 10 server such as TomEE 10.2.0
(Faces 4.0) use the 4.x line, because 5.x needs Faces 4.1.

[#struts]
== Struts 1 to Faces

The older books treat Struts 1 integration and conversion to Faces as a main subject: Mann's book integrates the two frameworks, and the book of Dudney and colleagues has a chapter on converting a Struts
application. That material is historical. The Apache Struts project has declared Struts 1 end of life (its announcement counts the Struts 2 releases as of April 2013); the last Struts 1 release was 1.3.10 in December 2008,
and the announcement says that there is no drop-in replacement for it. (Struts and JSP in general are the subject of the planned issue #241; this section mentions it by number only.)

One technical fact makes the old integration advice unusable on a current platform: `+struts-core+` 1.3.10, the newest release on Maven Central, refers to `+javax/servlet/http/HttpServlet+` in its `+ActionServlet+`, so it
does not run on a Servlet 5 or newer container such as Tomcat 10 or later. Struts 1 and Faces 4 cannot share a WAR on a Jakarta EE 9 or newer server unless the Struts jars are transformed (the Eclipse Transformer of
<<transformer>> could do it; not run). The practical plan for a Struts 1 application is therefore to convert it screen by screen while it still runs on its old platform, as stage 1 of the route, or to run old and new
applications as two deployments behind a reverse proxy that routes by URL.

The concepts map one to one in most places, and this is the table to use when converting. It is the author's mapping from the two frameworks' concepts; no Struts 1 application was converted for this page.

.Struts 1 concepts and their Faces counterparts
[cols="3,5",options="header"]
|===
|Struts 1 |Jakarta Faces 4.1

|`+ActionServlet+` and `+struts-config.xml+`
|`+FacesServlet+`, `+faces-config.xml+` and annotations

|An `+Action+` class per URL (`+execute+` returns an `+ActionForward+`)
|An action method of a backing bean, returning an outcome (xref:web/jsf/navigation.adoc[Navigation])

|`+ActionForward+` and `+<forward>+` entries
|Outcomes, implicit navigation, `+faces-redirect=true+` and navigation rules

|`+ActionForm+` with `+reset()+` and `+validate()+`
|Properties of a `+@ViewScoped+` or `+@RequestScoped+` bean, with validators and Bean Validation (xref:web/jsf/validators.adoc[Validators], xref:web/jsf/bean-validation.adoc[Bean Validation])

|`+ActionErrors+` and `+ActionMessages+`
|`+FacesMessage+` and `+h:messages+` (xref:web/jsf/messages-and-i18n.adoc[Messages])

|The Commons Validator rules in `+validation.xml+`
|Bean Validation constraints and the standard validators

|Tiles definitions
|Templates with `+ui:composition+`, `+ui:define+`, `+ui:insert+` (xref:web/jsf/templating.adoc[Templating])

|The Struts tag libraries (`+html:text+`, `+bean:write+`, `+logic:iterate+`)
|`+h:inputText+`, expressions in template text, `+ui:repeat+` and `+h:dataTable+`

|Message resources (`+ApplicationResources.properties+`)
|Resource bundles declared with `+<resource-bundle>+`, read as `+#{msg['key']}+`

|One request, one action, no component state
|A component tree restored on every postback, with view state (xref:web/jsf/architecture-and-component-model.adoc[Architecture and Component Model])
|===

The last row is the one that costs time. Struts is action-based: a URL names an action, and the page is a template. Faces is component-based: a URL names a view, a form posts back to the same view, and the
server keeps state for it. A Struts screen with several buttons becomes one view with several action methods, not several URLs. Plan the conversion by screens, not by files.

Source: https://struts.apache.org/struts1eol-announcement.html[Apache Struts 1 End-Of-Life Announcement], https://repo1.maven.org/maven2/org/apache/struts/struts-core/[Maven Central: struts-core] and https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-intro/faces-intro.html[Jakarta EE Tutorial: Introduction to Jakarta Faces Technology]

[#verify]
== Proving the Migration: A Smoke Test

The most dangerous failures of this page are the silent ones, so the end of the migration needs a test that fails on them. The script below makes one check for each: books listed (the bean was
injected), the project stage (the parameter was read), no missing script resource, no `+jsf.+` left in the page, `+faces.js+` served, the EL resolver working, and an Ajax search that filters the table. It needs
only `+curl+` and a running application, and it works on any server and on both implementations.

.smoke.sh: one check per silent failure
[source,bash]
----
#!/bin/sh
# smoke.sh http://localhost:8080/bookshelf
BASE=${1:?base url}
JAR=$(mktemp)
fail=0
check() { if [ "$2" = "ok" ]; then echo "ok    $1"; else echo "FAIL  $1"; fail=1; fi; }

page=$(curl -s -c "$JAR" -b "$JAR" "$BASE/index.xhtml")
echo "$page" | grep -q 'Dune' && check "bean injected, books listed" ok || check "bean injected, books listed" no
echo "$page" | grep -q 'stage=Development' && check "jakarta.faces.PROJECT_STAGE read" ok || check "jakarta.faces.PROJECT_STAGE read" no
echo "$page" | grep -q 'RES_NOT_FOUND' && check "no missing script resource" no || check "no missing script resource" ok
echo "$page" | grep -q 'jsf\.' && check "no jsf.* left in the page" no || check "no jsf.* left in the page" ok
[ "$(curl -s -o /dev/null -w '%{http_code}' "$BASE/jakarta.faces.resource/faces.js.xhtml?ln=jakarta.faces")" = 200 ] \
  && check "faces.js served" ok || check "faces.js served" no
curl -s "$BASE/legacy.xhtml" | grep -q 'Bookshelf' && check "EL resolver supplies appName" ok || check "EL resolver supplies appName" no

state=$(echo "$page" | sed -n 's/.*name="jakarta.faces.ViewState"[^>]*value="\([^"]*\)".*/\1/p' | head -1)
answer=$(curl -s -c "$JAR" -b "$JAR" -H 'Faces-Request: partial/ajax' \
  --data-urlencode 'searchForm=searchForm' --data-urlencode 'searchForm_SUBMIT=1' \
  --data-urlencode 'searchForm:query=snow' --data-urlencode "jakarta.faces.ViewState=$state" \
  --data-urlencode 'jakarta.faces.source=searchForm:search' --data-urlencode 'jakarta.faces.partial.ajax=true' \
  --data-urlencode 'jakarta.faces.partial.execute=searchForm' --data-urlencode 'jakarta.faces.partial.render=results' \
  --data-urlencode 'jakarta.faces.behavior.event=action' --data-urlencode 'searchForm:search=' \
  "$BASE/index.xhtml")
echo "$answer" | grep -q 'Snow Crash' && ! echo "$answer" | grep -q 'Dune' \
  && check "Ajax search filters the table" ok || check "Ajax search filters the table" no
rm -f "$JAR"
exit $fail
----

Against the migrated Bookshelf the script printed `+ok+` seven times and exited with 0 on Mojarra 4.1.17 and on MyFaces 4.1.4. Against the state with the five leftovers of <<symptoms>>
it exited with 1: four of the seven checks failed (the page itself answered 500, so the first two checks failed together). The line `+searchForm_SUBMIT=1+` is needed by MyFaces only; Mojarra ignores it. Add the script to the
build pipeline; it is the cheapest regression test the migration can leave behind. The xref:web/jsf/security.adoc[Security] and xref:web/jsf/testing.adoc#browser[testing] pages hold the browser-level tests.

The finished application is the Bookshelf as listed in this page: `+BookService+`, `+CatalogueBean+`, `+QueryReader+`, `+AppNameResolver+`, `+AuditPhaseListener+` (unchanged but for the import), the three
views, the three descriptors and the pom. It builds with `+mvn package+` (`+maven.compiler.release+` 21), deploys to Tomcat 11.0.26 with Weld 6.0.4.Final, runs on Mojarra 4.1.17 and MyFaces 4.1.4, and compiles without warnings against the

[#faces5]
== Preparing for Faces 5.0

Faces 5.0 is not released. The specification page marks it as under development with Java SE 21 as the minimum, and the latest milestone of the API is `+5.0.0-M9+` (2026-09-18). What the
final release contains can still change, so this section describes a method and the milestone's data, not a promise.

The direction is stated on the versions page: the removal of everything deprecated for removal since 4.0, of the old XML namespaces, of `+composite:extension+` and of the custom scope events, plus a
modernisation of the API with generics and enums. That makes the preparation concrete, because the things to avoid are already marked:

. *Compile with `+-Xlint:removal+` against 4.1.* Every `+[removal]+` warning is something 5.0 plans to delete. A class using `+@FacesConfig(version = ...)+`, the `+JSF_SCRIPT_*+` constants and
`+ViewHandler.DEFAULT_SUFFIX+` gave five warnings against 4.1.2.
. *Compile against the milestone in a separate step.* The same class gave five errors against `+5.0.0-M9+` (cannot find symbol `+version()+`, `+Version+`, `+JSF_SCRIPT_LIBRARY_NAME+`, `+JSF_SCRIPT_RESOURCE_NAME+`, `+DEFAULT_SUFFIX+`). The migrated Bookshelf compiled against it with no warning and no error.
. *Replace the old namespaces now.* They still work in 4.1 (<<namespaces>>) and are planned to go in 5.0.
. *Check the libraries.* Whether PrimeFaces 16, OmniFaces 5 and your own extensions run on a 5.0 milestone was not run here.

.Compiling the application against the 5.0 milestone, apart from the normal build
[source,bash]
----
# once: get the milestone API and the compile classpath of the project
mkdir -p target/faces5
curl -s -o target/faces5/jakarta.faces-api-5.0.0-M9.jar \
  https://repo1.maven.org/maven2/jakarta/faces/jakarta.faces-api/5.0.0-M9/jakarta.faces-api-5.0.0-M9.jar
mvn -q dependency:build-classpath -DincludeScope=compile -Dmdep.outputFile=target/cp.txt

# the milestone first on the class path, so it wins over the 4.1 classes inside jakartaee-web-api
mkdir -p target/faces5-classes
javac -Xlint:removal -d target/faces5-classes \
  -cp "target/faces5/jakarta.faces-api-5.0.0-M9.jar:$(cat target/cp.txt)" \
  $(find src/main/java -name '*.java')
----

Source: https://jakarta.ee/specifications/faces/5.0/[Jakarta Faces 5.0 (under development)] and https://repo1.maven.org/maven2/jakarta/faces/jakarta.faces-api/[Maven Central: jakarta.faces-api]

Reading the milestone API jar against the 4.1.2 jar shows the direction in detail. In `+5.0.0-M9+` these public API elements are _absent_ (present and deprecated for removal in 4.1.2):

* `+FacesConfig.version()+` and `+FacesConfig.Version+`;
* `+ResourceHandler.JSF_SCRIPT_LIBRARY_NAME+` and `+JSF_SCRIPT_RESOURCE_NAME+`;
* `+ViewHandler.DEFAULT_SUFFIX+` and `+DEFAULT_SUFFIX_PARAM_NAME+`;
* `+StateManager.PARTIAL_STATE_SAVING_PARAM_NAME+` and `+FULL_STATE_SAVING_VIEW_IDS_PARAM_NAME+`;
* the `+alt+`, `+autocomplete+`, `+maxlength+`, `+readonly+` and `+size+` accessors of `+HtmlInputFile+`, and `+alt+` of `+HtmlInputSecret+`;
* `+ActionSource2+`, `+ActionSource2AttachedObjectHandler+`, `+ActionSource2AttachedObjectTarget+`, `+PostConstructCustomScopeEvent+` and `+PreDestroyCustomScopeEvent+`.

And the milestone newly marks as deprecated for removal (`+since = "5.0"+`): `+ConfigurableNavigationHandler+` and its wrapper, `+ScopeContext+`, two constructors of `+NavigationCase+`, the `+FacesMessage.SEVERITY_*+` constants, `+StateManager.STATE_SAVING_METHOD_CLIENT+`
and `+STATE_SAVING_METHOD_SERVER+`, `+ViewHandler.getBookmarkableURL+` and `+getRedirectURL+` (and their wrapper methods), the `+processSaveState+` and `+processRestoreState+` family of `+UIComponent+`, `+UIForm.prependId+`, and the `+managed+` element of
`+@FacesConverter+`, `+@FacesValidator+` and `+@FacesBehavior+`. These come from scanning the milestone jar and may change before the release; `+prependId+` and the navigation handler matter to many applications, so read them as a reason to look at
your own use, not as a rule. Note also that the class files of `+5.0.0-M9+` are Java 17 class files (version 61) although the specification page asks for Java SE 21.

[#mojarra-myfaces]
== Mojarra vs MyFaces During a Migration

The two implementations agreed on almost everything above, and the differences are mostly in what they say, not in what they do:

* *Both* ignored the old context parameters, the `+<managed-bean>+` and `+<variable-resolver>+` entries and an unannotated `+@ManagedProperty+`; both accepted the old namespaces and the old descriptor versions; both
failed the same way when a library or a class still used `+javax+` (Mojarra with `+NoClassDefFoundError+` for the class it was loading, MyFaces with `+Class javax.faces.webapp.FacesServlet not found+` and a failed `+StartupServletContextListener+`).
* *Missing script resource:* Mojarra renders `+<script src="RES_NOT_FOUND">+` and logs nothing; MyFaces renders nothing and logs a warning with the resource and library names.
* *A request mapped to a missing view* (`+*.jsp+` with no `+.xhtml+` sibling): Mojarra answered 404, MyFaces 500 with `+InvalidFileException+`.
* *Startup noise:* on an embedded Tomcat without Jasper, MyFaces 4.1.4 logs `+SEVERE: Class org.apache.jasper.servlet.JspServlet not found+` while starting, after looking up the JSP servlet class. It is harmless
here (JSP support is gone) and is not the reason the application fails when it fails; the actual cause is further down the log.
* *Hand-built Ajax posts:* MyFaces needs the hidden `+form_SUBMIT=1+` field in a request that you assemble by hand, as the smoke test does; Mojarra ignores it.
* *Generated markup:* the Ajax button's `+onclick+` is `+mojarra.ab(...)+` on Mojarra and `+myfaces.ab(...)+` inside `+faces.util.chain+` on MyFaces. Tests must not depend on either.

The general comparison is in xref:web/jsf/versions-and-implementations.adoc#mojarra-vs-myfaces[Versions and Implementations].

== Where the Books Are Outdated: Every Statement in One Place

The eight books of the section's bibliography date from 2004 to 2015 and describe JSF 1.0 to 2.2 and PrimeFaces 2 to 5. Their ideas are mostly sound, which is why

[#books-errata]
=== Bad Practices the Era Normalised

Separately from outdated APIs, the sources of the period show habits that this section does not reproduce. They are listed because a migrated code base usually still has them, and the migration is the
moment to remove them; the right-hand column names the page that shows the correct form.

.Habits to remove while migrating
[cols="4,5",options="header"]
|===
|Habit common in the era's code |Correct form, and the page

|Page state in session-scoped beans (memory growth, cross-tab bugs)
|`+@ViewScoped+`, `+@FlowScoped+` or `+@ClientWindowScoped+` (xref:web/jsf/scopes.adoc[Scopes], xref:web/jsf/multi-window-support.adoc[Multi-Window Support])

|Business logic or queries in getters that run several times per request
|Load in `+@PostConstruct+`, a view action or the action method (<<beans>>, xref:web/jsf/backing-beans-and-cdi.adoc[Backing Beans and CDI])

|`+binding+` to session-scoped beans
|`+binding+` only to a request-scoped bean or none (xref:web/jsf/architecture-and-component-model.adoc[Architecture and Component Model])

|JSTL `+c:if+` and `+c:forEach+` used as if they ran at render time
|`+rendered+` and `+ui:repeat+` (xref:web/jsf/jstl-and-build-time-vs-render-time.adoc[JSTL and Build Time versus Render Time])

|`+immediate="true"+` used to "skip validation" without knowing the lifecycle consequences
|Understand the phases first (xref:web/jsf/request-processing-lifecycle.adoc#immediate[Request Processing Lifecycle])

|Secrets, passwords or database URLs written in `+faces-config.xml+`, `+web.xml+` or beans
|The environment or a secret store (xref:web/jsf/security.adoc#secrets[Security])

|`+escape="false"+` on user-supplied text
|Escaped output; sanitise if markup must be kept (xref:web/jsf/security.adoc#xss[Security])

|State-changing `+h:link+` or GET requests, or switching off view state or CSRF protection
|POST with view state; protected views (xref:web/jsf/security.adoc#csrf[Security])

|Client state saving without encryption and a MAC
|Keep the defaults, fix the keys (xref:web/jsf/state-saving-and-stateless-views.adoc#client[State Saving])
|===

[#pitfalls]
== Common Mistakes

* *Renaming only the imports.* The `+javax.faces+` string also lives in parameters, XML, messages, ids, request parameters and resources, and a missed one fails without an error (<<javax>>, <<symptoms>>).
* *Blind `+s/javax/jakarta/+`.* It breaks `+javax.naming+`, `+javax.sql+`, `+javax.crypto+` and `+javax.annotation.processing+`, which Java SE still owns, and it produces `+jakarta.faces.bean+` and
`+jakarta.faces.el+`, which do not exist in 4.x.
* *Trusting a green build from an automated tool.* OpenRewrite reported success on a project that did not compile, and on JDK 26 skipped the most important class with a warning. Count the changed files
and compile.
* *Keeping `+@ManagedProperty+` without `+@Inject+`.* It compiles, it deploys and it fails on the first request with a null service.
* *Leaving the old descriptor entries.* `+<managed-bean>+`, `+<variable-resolver>+` and the `+javax.faces.*+` parameters are ignored without a message; the stage falls back to Production.
* *Changing `+jsf.js+` in Java and XHTML but not in the JavaScript files, or the other way round.* Search all three.
* *Jumping several PrimeFaces majors at once.* The deprecations that told you what to change were in the releases you skipped (<<primefaces>>).
* *Using the `+jakarta+` classifier on PrimeFaces 16.* The artifact has none.
* *Assuming the artifact name tells the namespace.* `+org.glassfish:jakarta.faces:2.3.21+` is `+javax+` (<<implementations>>).
* *Mixing `+javax+` and `+jakarta+` jars in one WAR.* A library that was not migrated fails at startup, in its own listener, before Faces is reached (<<symptoms>>).
* *Shipping with the `+Development+` stage because the migrated `+web.xml+` came from a development copy.* Set `+Production+` for deployments (xref:web/jsf/configuration-and-project-stages.adoc#project-stage[Project Stages]).
* *Letting the temporary `+*.jsp+` mapping stay.* Old URLs keep working and hide which page is served (<<jsp>>).
* *Migrating without a test that fails on the silent errors.* The smoke test of <<verify>> is a start.
* *Copying a book's example and "fixing" it by trial.* Start from the current page of this section, not the book.
