[#how]
== How to Use the Checklist

Each item has a bold name, the rule, and a link to the page and section that explains the reason and the observed behaviour.
The items are grouped by the question a reviewer asks, and the order of the groups follows the life of a request:
design of the beans, rendering, views, input, navigation, Ajax, security, state, configuration, libraries, persistence,
servers, testing and deployment. The groups after them collect what not to do:

* <<avoid>> turns the habits listed as errata in the books of the JSF 1.x and 2.0 era into things to avoid, each with the
  right form and its page. The habit table of the migration page (xref:web/jsf/migrating-to-jakarta-faces.adoc#books-errata[Bad Practices the Era Normalised])
  is the same list seen from a migration; this page is the same list seen from new code.
* <<silent>> lists the mistakes that produce no error at all, with the cheap test that finds each.
* <<portable>> lists what differs between Mojarra and MyFaces, so that the application does not depend on either.

A checklist is a prompt, not a proof. The last section (<<pitfalls>>) names the ways a checklist is misused.

[#design]
== Design: Scopes and Beans

* *Page state lives in `+@ViewScoped+`.* A view-scoped bean (`+jakarta.faces.view.ViewScoped+`) lives as long as the user stays on the
  view and is created again for the next one, which is what a form, a table with a filter or a wizard step needs. The
  session holds identity and preferences, not the state of pages (xref:web/jsf/scopes.adoc#view[View scope],
  xref:web/jsf/scopes.adoc#choosing[Choosing a scope]).
* *Know when the view scope ends.* Any navigation outcome that builds a new view root ends it, even for the same view
  id; returning `+null+` keeps it. A redirect or a new GET does not destroy the old bean at that moment; it waits for the
  eviction of the view or the end of the session (xref:web/jsf/scopes.adoc#view-ends[When the view scope ends]).
* *Make every bean in a passivating scope `+Serializable+`.* View, session, client-window and conversation beans must be, and so must
  every `+@Dependent+` object injected into them: Weld refuses a non-serialisable one at deployment
  (`+WELD-000072+`, `+WELD-001413+`), and in a cluster or with client state saving it fails at run time otherwise
  (xref:web/jsf/scopes.adoc#serialisation[Serialisation and passivation]).
* *Use CDI `+@Named+` beans only.* The native managed beans (`+@ManagedBean+` and the `+javax.faces.bean+` scopes) were removed
  in Faces 4.0, and a `+<managed-bean>+` element in `+faces-config.xml+` is silently ignored on both implementations
  (xref:web/jsf/backing-beans-and-cdi.adoc#managedbean-removed[Managed beans were removed]).
* *Let CDI find the bean.* A class with only `+@Named+` is not a bean in the default `+annotated+` discovery mode, and on
  Tomcat with Weld Servlet nothing is found without a `+WEB-INF/beans.xml+` (xref:web/jsf/backing-beans-and-cdi.adoc#discovery[Bean discovery],
  xref:web/jsf/tomcat-and-weld.adoc#beans-xml[beans.xml on Tomcat]).
* *Keep the bean thin; put rules and queries in a service.* The bean translates between the view and the service, the
  service is a plain CDI bean that can be tested without Faces (xref:web/jsf/backing-beans-and-cdi.adoc#layering[Layering],
  xref:web/jsf/persistence-and-services.adoc#layers[Layers of a Faces application]).
* *Use constructor injection correctly.* A normal-scoped bean with constructor injection needs a protected no-argument
  constructor, or deployment fails with `+WELD-001435+` (xref:web/jsf/backing-beans-and-cdi.adoc#constructor-injection[Constructor injection]).
* *Inject the Faces objects.* `+@Inject FacesContext+`, `+Flash+`, `+ExternalContext+` and the request-map qualifiers work in
  Faces 4.x; do not inject them into something created at application start-up, where no request is active
  (xref:web/jsf/backing-beans-and-cdi.adoc#inject-faces[Injecting Faces artefacts]).
* *Use the scope that matches the interaction.* A multi-step process is a flow (`+@FlowScoped+`), a form that must survive several
  browser tabs independently is `+@ClientWindowScoped+`, which needs a client window mode or it fails with `+WELD-001303+`
  (xref:web/jsf/faces-flows.adoc[Faces Flows], xref:web/jsf/multi-window-support.adoc[Multi-Window Support]).

[#example]
.A view-scoped search bean that loads once and filters in the action (compiled and run on both implementations)
[source,java]
----
package org.example.bookshelf.web;

import jakarta.annotation.PostConstruct;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;

@Named
@ViewScoped
public class ViewSearchBean implements Serializable {

    @Inject
    private BookService books;

    private String text = "";
    private List<Book> results = List.of();

    @PostConstruct
    void init() {
        results = books.search(text);
    }

    /** Runs once per click, in Invoke Application. */
    public void search() {
        results = books.search(text);
    }

    public List<Book> getResults() {
        return results;
    }

    public String getText() {
        return text;
    }

    public void setText(String text) {
        this.text = text;
    }
}
----

[#rendering]
== Rendering: Getters, EL, JSTL and `binding`

* *A getter returns a field.* Faces calls a getter many times in a request: in the performance runs a table of five rows with
  `+rendered+` expressions called getters 4 times on a GET and 13 times on a postback on Mojarra (3 and 10 on MyFaces). A query
  in a getter runs that many times (xref:web/jsf/performance.adoc#getters[Getters and EL cost],
  xref:web/jsf/performance.adoc#cost-model[The cost model]).
* *Load in `+@PostConstruct+`, in a view action or in the action method.* A new model built on every evaluation is evaluated
  three times before the action and once more to render (xref:web/jsf/data-tables-and-iteration.adoc[Data Tables and Iteration],
  xref:web/jsf/view-parameters-and-view-actions.adoc#viewaction[View actions]).
* *Do not use JSTL tags as if they ran at render time.* `+c:if+` and `+c:forEach+` run when the view is built; inside `+ui:repeat+`
  they rendered nothing in the runs. Use `+rendered+` and `+ui:repeat+` for anything that depends on a request-time value
  (xref:web/jsf/jstl-and-build-time-vs-render-time.adoc#decision[Choosing between JSTL and Facelets tags]).
* *Bind a component only to a request-scoped bean, or do not bind.* A `+binding+` to a session or application bean shares component
  instances between requests and users; most uses need no binding at all
  (xref:web/jsf/architecture-and-component-model.adoc#binding[The binding attribute]).
* *Do not name a property `+empty+`.* `+empty+` is an EL reserved word, so `+#{bean.empty}+` does not parse
  (xref:web/jsf/performance.adoc#pitfalls[Performance pitfalls]).
* *Treat an empty output as a symptom.* An EL name that resolves to nothing renders as empty text with no error, which is the usual symptom of a
  bean that CDI did not find (xref:web/jsf/backing-beans-and-cdi.adoc#probe[A probe for scopes and discovery],
  xref:web/jsf/expression-language.adoc#pitfalls[Expression language pitfalls]).
* *Pick the iteration component on purpose.* `+h:dataTable+` and `+ui:repeat+` differ in their attributes and in
  `+varStatus+`; `+h:dataTable+` has none (xref:web/jsf/data-tables-and-iteration.adoc#repeat-vs[ui:repeat versus h:dataTable],
  xref:web/jsf/data-tables-and-iteration.adoc#differences[Mojarra versus MyFaces differences]).

[#views]
== Views, Templates and Resources

* *Write one template and fill its slots.* Common layout belongs in one template with `+ui:insert+` slots and clients that use
  `+ui:define+`; a misspelt slot name is ignored without a message
  (xref:web/jsf/templating.adoc[Templating], xref:web/jsf/templating.adoc#pitfalls[its pitfalls]).
* *Put `+f:metadata+` in a slot that the client defines.* Inside a template it is silently ignored
  (xref:web/jsf/core-tags.adoc#metadata[f:metadata]).
* *Use the Jakarta URNs and an HTML5 doctype.* The `+jakarta.faces.html+`, `+jakarta.faces.core+`, `+jakarta.faces.facelets+`,
  `+jakarta.faces.composite+` and `+jakarta.faces.passthrough+` namespaces (4.0). The old `+java.sun.com+` and `+xmlns.jcp.org+` URIs
  still rendered on 4.1, but their removal is planned for Faces 5.0
  (xref:web/jsf/facelets-and-xhtml-views.adoc#old-namespaces[Old namespaces], xref:web/jsf/migrating-to-jakarta-faces.adoc#namespaces[Namespaces in a migration]).
* *Repeat markup as a composite component or a tag file, not as copied XHTML.* Both take attributes and have their own
  naming container (xref:web/jsf/composite-components.adoc[Composite Components],
  xref:web/jsf/tag-files-and-tag-libraries.adoc[Tag Files and Tag Libraries]).
* *Reference CSS, scripts and images as resources.* `+h:outputStylesheet+`, `+h:outputScript+` and the resource EL give versioning,
  caching and relocation; a hand-written path gives none of them (xref:web/jsf/resource-handling.adoc#tags[Resource tags],
  xref:web/jsf/resource-handling.adoc#versioning[Versioning]).
* *Give an `+id+` to a form and to everything that Ajax or a test refers to.* Generated ids change when the view changes
  (xref:web/jsf/html-components.adoc#client-ids[Client ids]).
* *Label inputs.* Use `+h:outputLabel for+` and the `+label+` attribute of the input, so that messages name the field instead of showing the client id
  (xref:web/jsf/html5-friendly-markup.adoc#accessibility[Accessibility], xref:web/jsf/validators.adoc#messages-display[Messages and labels]).
* *Do not write JSP or Facelets 1.x.* JSP support was removed in Faces 4.0 and the standalone `+com.sun.facelets+` library has been
  built in since 2.0 (xref:web/jsf/facelets-and-xhtml-views.adoc#facelets-vs-jsp[Facelets versus JSP]).

[#input]
== Input: Conversion, Validation and Messages

* *Validate at three levels.* Faces converters and validators (and the `+required+` attribute) reject malformed input on the form,
  Bean Validation constraints on the model state the rule once, and the service re-checks what it depends on, because a bean
  is not the only caller of a service (xref:web/jsf/validators.adoc[Validators],
  xref:web/jsf/bean-validation.adoc#service-layer[Bean Validation in the service layer]).
* *Put the Bean Validation provider on the class path.* On Tomcat the constraints do nothing until Hibernate Validator and
  an EL implementation are in place, and nothing says so (xref:web/jsf/tomcat-and-weld.adoc#validation[Bean Validation on Tomcat],
  xref:web/jsf/bean-validation.adoc#activation[Activation]).
* *Know the empty-value rules.* With a provider on the class path an empty optional text field fails `+f:validateRegex+` or a minimum
  `+f:validateLength+` unless `+jakarta.faces.INTERPRET_EMPTY_STRING_SUBMITTED_VALUES_AS_NULL+` is `+true+` or the validators tolerate empty
  input; a required input missing from the POST is not validated unless
  `+jakarta.faces.ALWAYS_PERFORM_VALIDATION_WHEN_REQUIRED_IS_TRUE+` is on
  (xref:web/jsf/validators.adoc#empty-values[Empty values], xref:web/jsf/bean-validation.adoc#empty-values[Empty values and Bean Validation]).
* *Turn on `+f:validateWholeBean+` deliberately.* It does nothing unless `+jakarta.faces.validator.ENABLE_VALIDATE_WHOLE_BEAN+` is `+true+`
  (xref:web/jsf/bean-validation.adoc#whole-bean[Whole-bean validation]).
* *Keep messages in a bundle.* Texts, validator messages and labels come from resource bundles so that they can be translated, and
  a `+validatorMessage+` replaces every message of the validators it covers (xref:web/jsf/messages-and-i18n.adoc[Messages and Internationalisation],
  xref:web/jsf/validators.adoc#messages[Validator messages]).
* *Give an entity converter an `+equals+` method.* Without it a select list answers `+Validation Error: Value is not valid+`
  (xref:web/jsf/persistence-and-services.adoc#converter[An entity converter],
  xref:web/jsf/converters.adoc#entity[Entity converters]).
* *Use `+immediate+` only when you know the phases.* An immediate command runs in Apply Request Values and skips validation of the
  other inputs, which suits a Cancel button and nothing else (xref:web/jsf/request-processing-lifecycle.adoc#immediate[Immediate components],
  xref:web/jsf/events-and-listeners.adoc#immediate-actions[Immediate actions]).
* *Never trust a rendered form.* A forged value for a `+h:selectOneMenu+` is rejected by the component, and a button with `+rendered="false"+` is not
  invoked by a forged post; everything else the browser sends is input to validate (xref:web/jsf/validators.adoc#skipping[Skipping validation],
  xref:web/jsf/security.adoc#layers[Layers of defence]).

.A form bean whose rules are constraints on the model, read by Faces when the view is validated (compiled and run on both implementations)

package org.example.bookshelf.web;

import jakarta.faces.view.ViewScoped;
import jakarta.inject.Named;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;
import java.io.Serializable;

@Named
@ViewScoped
public class BookForm implements Serializable {

    @NotBlank
    @Size(max = 200)
    private String title;

    @Min(1450)
    @Max(2100)
    private int year = 2000;

    public String getTitle() {
        return title;
    }

    public void setTitle(String title) {
        this.title = title;
    }

    public int getYear() {
        return year;
    }

    public void setYear(int year) {
        this.year = year;
    }
}
----

A post with an empty title and the year `+3000+` came back on both implementations with the messages `+must not be blank+` and

[#navigation]
== Navigation, Post/Redirect/Get and Links

* *Redirect after every POST that changes something.* Return an outcome with `+?faces-redirect=true+` so that reload and Back
  do not send the form again; carry the message across with `+Flash+` (xref:web/jsf/flash-and-post-redirect-get.adoc#problem[The problem],
  xref:web/jsf/flash-and-post-redirect-get.adoc#prg-example[PRG example]).
* *Keep messages across the redirect on purpose.* A `+FacesMessage+` is lost on a redirect unless `+Flash.setKeepMessages(true)+`;
  the first following request of the session consumes the flash, whichever page and tab it is
  (xref:web/jsf/flash-and-post-redirect-get.adoc#messages[Messages across a redirect],
  xref:web/jsf/flash-and-post-redirect-get.adoc#lifetime[Lifetime of a flash entry]).
* *Use GET for reading, POST for changing.* `+h:link+`, `+h:button+`, `+f:viewParam+` and `+f:viewAction+` make bookmarkable pages;
  anything that changes state is a command component with a view state (xref:web/jsf/view-parameters-and-view-actions.adoc#bookmarkable[Bookmarkable pages],
  xref:web/jsf/navigation.adoc#get[Navigation by GET]).
* *Validate view parameters and answer for bad ones.* A missing book is a 404, a malformed id a 400; use
  `+responseSendError+` together with `+responseComplete+` (xref:web/jsf/view-parameters-and-view-actions.adoc#not-found[Not found],
  xref:web/jsf/view-parameters-and-view-actions.adoc#bad-request[Bad request]).
* *Know that a view action does not run on a postback by default.* Set `+onPostback+` only when a guard must run on one
  (xref:web/jsf/view-parameters-and-view-actions.adoc#onpostback[onPostback]).
* *Let the framework build redirect URLs.* Use outcomes, `+includeViewParams+` and `+f:param+`; raw or pre-encoded query strings in an outcome were broken
  on MyFaces (xref:web/jsf/navigation.adoc#redirect[Redirects], xref:web/jsf/flash-and-post-redirect-get.adoc#parameters[Parameters]).

[#prg]
.An action that registers a loan, queues a message that survives the redirect and answers with a redirect (compiled and run on both implementations)
[source,java]
----
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;
import jakarta.faces.context.Flash;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import org.example.bookshelf.service.BookService;

@Named
@RequestScoped
public class BorrowDesk {

    @Inject
    private FacesContext facesContext;
    @Inject
    private Flash flash;
    @Inject
    private BookService books;

    private long bookId;
    private String member;

    /** A POST that changes state answers with a redirect, so reload and Back never repeat it. */
    public String borrow() {
        int loan = books.borrow(bookId, member);
        flash.setKeepMessages(true);
        facesContext.addMessage(null,
                new FacesMessage(FacesMessage.SEVERITY_INFO, "Loan " + loan + " registered", null));
        return "confirmation?faces-redirect=true";
    }

    public long getBookId() {
        return bookId;
    }

    public void setBookId(long bookId) {
        this.bookId = bookId;
    }

    public String getMember() {
        return member;
    }

    public void setMember(String member) {
        this.member = member;
    }
}
----

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/context/Flash.html[Jakarta Faces 4.1 API: Flash] and https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-intro/faces-intro.html#_navigation_model[Jakarta EE Tutorial: Navigation Model]

The POST answered `+302+` with `+Location: /bookshelf/confirmation.xhtml+`, and the confirmation view showed `+Loan 1 registered+`
once, on both implementations. MyFaces answered `+500+` in the earlier runs when the redirecting request had no session yet and a
message was queued; `+externalContext.getSession(true)+` before the outcome avoids it
(xref:web/jsf/flash-and-post-redirect-get.adoc#implementations[Mojarra and MyFaces]).

[#ajax]
== Ajax Scoping

* *Execute as little as the request needs and render only what changes.* The default `+execute+` of `+f:ajax+` is `+@this+`; list the inputs
  that belong together, render the results and the messages that live next to them, and avoid `+@all+` and `+@form+` without a reason
  (xref:web/jsf/ajax.adoc#execute-render[Execute and render], xref:web/jsf/performance.adoc#ajax-scope[Ajax scope and cost]).
* *Render ids that exist.* An `+id+` that is not in the view fails the request; with PrimeFaces an unknown `+update+` or `+process+` id is an HTTP 500 for the whole
  page, and rendering a component with `+rendered="false"+` aborts the remaining updates on Mojarra
  (xref:web/jsf/ajax.adoc#render-targets[Render targets], xref:web/jsf/primefaces-ajax-forms-and-validation.adoc#unknown-id[Unknown ids]).
* *Know the PrimeFaces defaults.* `+p:commandButton+` processes `+@all+` by default and `+p:ajax+` processes `+@this+`; they do not match `+f:ajax+`
  (xref:web/jsf/primefaces-ajax-forms-and-validation.adoc#process-update[Process and update]).
* *Reset input that failed validation when a Cancel or navigation button re-renders it.* Use `+f:resetValues+` or `+resetValues+`
  (xref:web/jsf/ajax.adoc#reset-values[Resetting values], xref:web/jsf/core-tags.adoc#reset-values[f:resetValues]).
* *List `+faces.js+` first when your script uses it at load time,* and use the `+faces.ajax+` API, not hand-written `+XMLHttpRequest+`
  (xref:web/jsf/ajax.adoc#faces-js[faces.js], xref:web/jsf/ajax.adoc#js-api[The JavaScript API]).
* *Show errors and a busy state.* A `+ViewExpiredException+` reaches the page as a `+200+` partial response with an error element; register an error handler
  and decide what the user sees (xref:web/jsf/ajax.adoc#errors[Errors], xref:web/jsf/exception-handling.adoc#ajax[Ajax exceptions]).
* *Re-render the messages component.* Without it a failed validation is invisible (xref:web/jsf/validators.adoc#ajax[Validation in Ajax requests]).

[#security]
== Security

* *Constrain directories and deny the uncovered methods.* `+/admin/*+` covered the `+.xhtml+` name, the extensionless name and every path
  variation tried; a constraint on one file name left the extensionless URL open, and a GET-only constraint left POST open
  without `+<deny-uncovered-http-methods/>+` (xref:web/jsf/security.adoc#web-xml[Securing URLs in web.xml]).
* *Secure every mapping of the `+FacesServlet+`.* A second mapping such as `+/faces/*+` was a second door around a constraint on `+/admin/*+`;
  JoinFaces adds such an alias by default, and a Spring Security rule on `+/admin/**+` was bypassed through `+/faces/admin/...+`
  (xref:web/jsf/security.adoc#web-xml[Securing URLs in web.xml],
  xref:web/jsf/spring-boot-with-joinfaces.adoc#security[Spring Security with JoinFaces]).
* *Leave output escaping on.* `+h:outputText+` and the message components escape by default. `+escape="false"+` with user text is XSS; the same applies to
  `+p:messages+` and `+p:menuitem+` with `+escape="false"+`, to the data of `+p:chart+` and `+p:timeline+`, which are written into an inline script, and to
  `+b:growl+` of BootsFaces, which does not escape by default (xref:web/jsf/security.adoc#xss[Cross-site scripting],
  xref:web/jsf/primefaces-files-media-charts-and-drag-drop.adoc#charts-xss[Chart data and XSS],
  xref:web/jsf/other-component-libraries.adoc#bootsfaces-security[BootsFaces and security]).
* *Do not put EL output into JavaScript.* EL in a `+<script>+` string or an `+onclick+` attribute is HTML-escaped only, which is not
  JavaScript escaping; pass data in `+data-*+` attributes (xref:web/jsf/security.adoc#xss[Cross-site scripting]).
* *Keep the view state on and server-side for views that change something.* Server state is a per-session reference; forged posts with client state or a stateless view
  were accepted in the runs and ran the action as the victim, so those views need a second defence: protected views, an `+Origin+`
  check or tokens (xref:web/jsf/security.adoc#csrf[CSRF], xref:web/jsf/security.adoc#protected-views[Protected views],
  xref:web/jsf/security.adoc#csrf-other[CSRF beyond the view state]).
* *Never change state with a GET.* `+h:link+`, `+h:outputLink+`, a view action that deletes something and an image URL are all GETs that a third-party page can
  trigger (xref:web/jsf/security.adoc#csrf-other[CSRF beyond the view state],
  xref:web/jsf/view-parameters-and-view-actions.adoc#viewaction[View actions]).
* *Set the cookie attributes.* `+HttpOnly+`, `+Secure+` and `+SameSite+` on the session cookie, and cookie tracking only, so that the session id
  does not appear in URLs (xref:web/jsf/security.adoc#cookies[Cookie attributes and SameSite],
  xref:web/jsf/security.adoc#session[Session handling]).
* *Authenticate with Jakarta Security and hash passwords with a configured cost.* The session id rotated on login in the runs; the default
  `+Pbkdf2PasswordHash+` used 2048 iterations, so set the iteration count explicitly
  (xref:web/jsf/security.adoc#mechanisms[Authentication mechanisms],
  xref:web/jsf/security.adoc#identity-stores[Identity stores]).
* *Authorise in the service, not only in the view.* `+rendered+` hides a control; roles checked in an interceptor or the service protect the operation
  (xref:web/jsf/security.adoc#roles[Roles and authorisation]).
* *Send security headers and a content security policy.* Mojarra has its own CSP nonce parameter; PrimeFaces has `+primefaces.CSP+`;
  a container-level redirect or `403` carries none of the headers of an application filter (xref:web/jsf/security.adoc#headers[Security headers],
  xref:web/jsf/security.adoc#csp[Content security policy]).
* *Treat uploads and downloads as hostile.* Limit size, validate name and content type, store under a generated name, escape formula characters in
  exported CSV and encode the download file name (xref:web/jsf/file-upload-and-download.adoc#validating[Validating uploads],
  xref:web/jsf/file-upload-and-download.adoc#csv-injection[CSV formula injection],
  xref:web/jsf/primefaces-files-media-charts-and-drag-drop.adoc#validate-file[PrimeFaces file validation]).
* *Do not trust forwarding headers for security decisions.* `+Faces.getRemoteAddr()+`, which `+@RateLimit+` of OmniFaces uses, believes `+X-Forwarded-For+`;
  the rate limit was bypassed by changing the header (xref:web/jsf/omnifaces.adoc#cdi-scopes[OmniFaces CDI annotations]).
* *Secure the WebSocket channel.* A channel and its scope decide who receives a push (xref:web/jsf/websocket-push.adoc#security[Security of push]).
* *Do not show internals.* Tomcat's default 500 page shows a stack trace and the server version; map error codes and the exceptions you expect
  to pages without detail (xref:web/jsf/exception-handling.adoc#error-pages[Error pages],
  xref:web/jsf/exception-handling.adoc#security[Exception handling and security]).

[#state]
== State Saving, Keys and Secrets

* *Keep server state saving unless you can show why not.* It is the default, it is the CSRF defence of <<security>> and it keeps state out of the page; client state
  suits stateless nodes and costs a larger page (xref:web/jsf/state-saving-and-stateless-views.adoc#choosing[Choosing],
  xref:web/jsf/state-saving-and-stateless-views.adoc#client[Client state saving]).
* *Configure the client-state keys from the environment, the same on every node.* Mojarra reads the JNDI entry `+java:comp/env/faces/ClientSideSecretKey+`
  (it was `+jsf/ClientSideSecretKey+` before 4.0); MyFaces reads `+org.apache.myfaces.SECRET+` and `+org.apache.myfaces.MAC_SECRET+`.
  With no key the application starts with a random key, and every restart or second node expires the open pages
  (xref:web/jsf/state-saving-and-stateless-views.adoc#client-keys[Keys]).
* *Do not switch client state encryption off.* The unencrypted state is a Java serialisation stream that the server deserialises, and the
  authentication code goes with the encryption (xref:web/jsf/state-saving-and-stateless-views.adoc#client-audit[Auditing client state]).
* *Set the PrimeFaces secret too.* With JoinFaces `+primefaces.SECRET+` is the public word `+primefaces+` unless `+joinfaces.primefaces.secret+` is set from the environment
  (xref:web/jsf/spring-boot-with-joinfaces.adoc#properties[JoinFaces properties]).
* *Use stateless views for pages that only read.* `+<f:view transient="true"/>+` creates no session and no state on the server, but view-scoped beans become request beans and
  programmatic changes are lost (xref:web/jsf/state-saving-and-stateless-views.adoc#stateless[Stateless views],
  xref:web/jsf/scopes.adoc#view-stateless[View scope and stateless views]).
* *Make the view state serialisable.* An object without a no-argument constructor in component attributes breaks the next postback, and a non-serialisable field breaks
  replication (xref:web/jsf/state-saving-and-stateless-views.adoc#serialisable[Serialisable state]).
* *Handle `+ViewExpiredException+` as a normal event.* Pages expire (timeout, restart, eviction): an error page or a handler that
  returns to the view, and a message that says what happened (xref:web/jsf/state-saving-and-stateless-views.adoc#expired[Expired views],
  xref:web/jsf/exception-handling.adoc#view-expired[ViewExpiredException]).
* *Know the view limits.* The number of views kept per session differs between the implementations (Mojarra 15, MyFaces 4 sequential views and 20 in total by default), and
  more tabs than that expire older pages (xref:web/jsf/scopes.adoc#view-limits[View limits],
  xref:web/jsf/state-saving-and-stateless-views.adoc#server-limits[Server state limits]).
* *Do not use full state saving.* It is deprecated for removal in Faces 4.1 and logs a warning; partial state saving is the default
  (xref:web/jsf/state-saving-and-stateless-views.adoc#partial[Partial state saving]).
* *Keep every secret outside the WAR.* Keys, passwords, database URLs and client secrets come from the environment or a secret store; examples and tests use
  placeholders and a scanner such as `+detect-secrets+` runs in the pipeline (xref:web/jsf/security.adoc#secrets[Secrets and configuration]).

The Tomcat form of the first rule, with the secrets read from the environment when Tomcat parses the file (the file holds placeholders only):

.META-INF/context.xml -- the keys come from the process environment
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<Context>
    <!-- Mojarra -->
    <Environment name="faces/ClientSideSecretKey" type="java.lang.String"
                 value="${FACES_CLIENT_SECRET}" override="false"/>
    <!-- MyFaces -->
    <Parameter name="org.apache.myfaces.SECRET" value="${MYFACES_SECRET}" override="false"/>
    <Parameter name="org.apache.myfaces.MAC_SECRET" value="${MYFACES_MAC_SECRET}" override="false"/>
</Context>
----

Source: https://tomcat.apache.org/tomcat-11.0-doc/config/context.html[Apache Tomcat 11: The Context Container] and https://tomcat.apache.org/tomcat-11.0-doc/config/systemprops.html[Apache Tomcat 11: System properties]

Tomcat substitutes the variables only when started with
`+-Dorg.apache.tomcat.util.digester.PROPERTY_SOURCE=org.apache.tomcat.util.digester.EnvironmentPropertySource+`; without it the literal `+${...}+` text becomes the key
and the application fails closed (xref:web/jsf/state-saving-and-stateless-views.adoc#client-keys[Keys]). The snippet shows both implementations at once; deploy the entry of the
implementation you use.

[#configuration]
== Configuration and Production

* *Deploy with the `+Production+` stage.* The development stage prints stack traces, component trees and submitted values in error pages; the
  stage is set with `+jakarta.faces.PROJECT_STAGE+` in `+web.xml+`, except on Quarkus, where `+web.xml+` is ignored and the stage comes from the build profile, and with JoinFaces, where the
  default is `+Production+` (xref:web/jsf/configuration-and-project-stages.adoc#project-stage[Project stages],
  xref:web/jsf/exception-handling.adoc#development-pages[Development pages],
  xref:web/jsf/quarkus.adoc#dev[Quarkus development mode]).
* *Do not rely on a stage for security.* The stage changes messages, caching and diagnostics; it does not decide who may do what
  (xref:web/jsf/configuration-and-project-stages.adoc#stage-effects[What the stage changes]).
* *Know where the settings live and in which order they win.* `+web.xml+`, `+faces-config.xml+`, annotations, and the implementation-specific
  parameters (`+com.sun.faces.*+`, `+org.apache.myfaces.*+`) are different families; look up the parameter on the page and in the implementation's reference
  (xref:web/jsf/configuration-and-project-stages.adoc#context-params[Context parameters],
  xref:web/jsf/configuration-and-project-stages.adoc#mojarra-params[Mojarra parameters],
  xref:web/jsf/configuration-and-project-stages.adoc#myfaces-params[MyFaces parameters]).
* *Map error codes and exceptions to pages.* A catch-all `+java.lang.Throwable+` error page shadows the specific exception pages; use an error code for the catch-all, and
  keep the error page itself free of the failing component (xref:web/jsf/exception-handling.adoc#error-page-pitfalls[Error page pitfalls],
  xref:web/jsf/exception-handling.adoc#throwable-shadow[The Throwable shadow]).
* *Cache resources and compress responses.* The Production stage sends `+max-age+` headers for resources; versioned libraries and a build id in the URL make long
  caching safe (xref:web/jsf/resource-handling.adoc#caching[Caching], xref:web/jsf/performance.adoc#production[Production settings],
  xref:web/jsf/performance.adoc#resources[Resources]).
* *Measure before tuning.* Load test with the same state saving and stage as production (xref:web/jsf/performance.adoc#load-testing[Load testing],
  xref:web/jsf/testing.adoc#load-testing[Load testing the application]).

.web.xml (excerpt) -- the production settings that the rules above name; every value is a setting, none is a secret
[source,xml]
----
<context-param>
    <param-name>jakarta.faces.PROJECT_STAGE</param-name>
    <param-value>Production</param-value>
</context-param>
<session-config>
    <cookie-config>
        <http-only>true</http-only>
        <attribute>
            <attribute-name>SameSite</attribute-name>
            <attribute-value>Lax</attribute-value>
        </attribute>
    </cookie-config>
    <tracking-mode>COOKIE</tracking-mode>
</session-config>
<deny-uncovered-http-methods/>
----

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a3455[Jakarta Faces 4.1 specification, 7.1.9 ProjectStage Property] and https://jakarta.ee/specifications/servlet/6.1/[Jakarta Servlet 6.1 specification]

Add `+<secure>true</secure>+` to `+cookie-config+` and a `+CONFIDENTIAL+` transport guarantee to the security constraints when the application is served over HTTPS,
which in production it is (xref:web/jsf/security.adoc#cookies[Cookie attributes and SameSite]).

[#libraries]
== Component Libraries: PrimeFaces, OmniFaces and Others

* *Pin versions that belong together.* PrimeFaces 16.0.0 and PrimeFaces Extensions 16.0.0 need Faces 4.0 or later and publish one jar without a classifier; OmniFaces 5 uses the
  `+omnifaces+` namespace; match them to the Faces implementation you run
  (xref:web/jsf/primefaces-getting-started-and-themes.adoc#dependencies[PrimeFaces dependencies],
  xref:web/jsf/omnifaces.adoc#install[OmniFaces installation],
  xref:web/jsf/primefaces-extensions.adoc#setup[PrimeFaces Extensions setup]).
* *Ask the six questions before adopting a library.* Which Jakarta release does its newest jar target and does it work on 4.1, when was the last release, what does it add to the page,
  what does it do to security, how much of the server-side API does it override, and how do you leave it
  (xref:web/jsf/other-component-libraries.adoc#plugging-in[How a library plugs into Faces]).
* *Run the three cheap tests on any library.* One page with a command component using `+action+`, one Ajax update of a component that renders a `+<script>+`, and one message or output
  component fed with `+<img src=x onerror=...>+`; a BootsFaces button silently ignored `+action+` on Faces 4.1 and its growl ran the handler
  (xref:web/jsf/other-component-libraries.adoc#choosing[Choosing],
  xref:web/jsf/other-component-libraries.adoc#action-trap[The ActionSource2 trap]).
* *Replace libraries that ended.* RichFaces, ICEfaces 1.x, Tomahawk, Trinidad, Seam and the Shale project have no release for Jakarta Faces
  (xref:web/jsf/other-component-libraries.adoc#discontinued[Discontinued libraries],
  xref:web/jsf/other-component-libraries.adoc#replacements[Replacements]).
* *Prefer a component library's lazy and server-side features for large data.* Lazy data models, server-side sorting and paging keep the page small
  (xref:web/jsf/primefaces-data-components.adoc#lazy[Lazy data tables]).
* *Sanitise instead of switching escaping off.* PrimeFaces Extensions has a sanitising converter, but its default decoding of HTML entities turns encoded input into markup;
  read its page before relying on it (xref:web/jsf/primefaces-extensions.adoc#sanitizer[Sanitiser]).
* *Do not add a library for what the standard components do.* Each library is a dependency to update and a surface to attack
  (xref:web/jsf/other-component-libraries.adoc#choosing[Choosing]).
* *Reach for OmniFaces for the gaps.* Messages, view parameters, validators across fields, exception handling, resource combining and `+o:socket+` are covered and tested
  (xref:web/jsf/omnifaces.adoc[OmniFaces]).

[#data]
== Persistence and Services

* *Open the transaction in the service.* A Faces bean is not a transactional boundary, and a runtime exception rolls the transaction back while a checked exception commits unless
  `+rollbackOn+` says otherwise (xref:web/jsf/persistence-and-services.adoc#transactions[Transactions],
  xref:web/jsf/persistence-and-services.adoc#rollback[Rollback rules]).
* *Do not hold entities in a view-scoped bean.* They fail on the next postback, and a lazy association that is read in Render Response raises `+LazyInitializationException+`
  there (xref:web/jsf/persistence-and-services.adoc#lazy[Lazy loading], xref:web/jsf/persistence-and-services.adoc#view-scope[Entities in view scope]).
* *Choose what each page reads.* In the runs a table of 24 books issued 43 statements with plain entities and open-session-in-view, 25 with a join fetch, and 1 with an entity graph or a DTO
  (xref:web/jsf/persistence-and-services.adoc#fetching[Fetching],
  xref:web/jsf/persistence-and-services.adoc#dto[DTO projections],
  xref:web/jsf/persistence-and-services.adoc#graphs[Entity graphs]).
* *Do not make open-session-in-view the design.* It turns a mapping mistake in a view into queries that nobody planned
  (xref:web/jsf/persistence-and-services.adoc#osiv[Open session in view]).
* *Page in the database.* Never load every row and slice in memory; use a lazy model or a paging query
  (xref:web/jsf/persistence-and-services.adoc#paging[Paging], xref:web/jsf/data-tables-and-iteration.adoc#paging[Paging in the page]).
* *Protect concurrent edits.* A version column and the exception it raises are a message to the user, not a stack trace
  (xref:web/jsf/persistence-and-services.adoc#edit[Editing]).

[#runtime]
== Servers and Runtimes

* *Use the Faces implementation of the server, or replace it deliberately.* GlassFish 8.0.5 and Payara 7 bundle Mojarra, WildFly 41 bundles Mojarra, Open Liberty bundles MyFaces and TomEE 10.2.0 bundles MyFaces;
  putting the other implementation in the WAR failed with `+WELD-001414+` (ambiguous bean names) on GlassFish and Payara, with an ambiguous resolution on TomEE and with a `+NoClassDefFoundError+` on Open Liberty's `+faces-4.1+` feature (the `+facesContainer-4.1+` feature takes Mojarra)
  (xref:web/jsf/jakarta-ee-servers.adoc#matrix[Server matrix],
  xref:web/jsf/jakarta-ee-servers.adoc#replacing[Replacing the implementation]).
* *Never ship two implementations.* A leftover directory with both Mojarra and MyFaces gives `+WELD-001414+` for `+requestScope+`, and the same happens when a test run packages both
  (xref:web/jsf/testing.adoc#pitfalls[Testing pitfalls]).
* *On Tomcat, match Weld to Faces and add the descriptors.* Mojarra 4.1 needs CDI 4.1 (Weld 6.0.x); with Weld 5 it fails with a `+ClassNotFoundException+`, and MyFaces 4.1.4 failed with Weld 7;
  `+WEB-INF/beans.xml+` is required; the Tomcat servlet, EL and WebSocket classes must not be in the WAR
  (xref:web/jsf/tomcat-and-weld.adoc#versions[Versions that fit],
  xref:web/jsf/tomcat-and-weld.adoc#weld-startup[Weld start-up],
  xref:web/jsf/tomcat-and-weld.adoc#pitfalls[Tomcat and Weld pitfalls]).
* *With JoinFaces use the `+joinfaces.faces.*+` properties.* The old `+joinfaces.jsf.*+` names are ignored without a message; the application needs `+server.servlet.register-default-servlet=true+` for a `+POST /login+`
  to reach Spring Security, a welcome file for `+GET /+`, cookie-only session tracking, and `+joinfaces.faces-servlet.url-mappings=*.xhtml+` to close the `+/faces/*+` alias
  (xref:web/jsf/spring-boot-with-joinfaces.adoc#properties[Properties],
  xref:web/jsf/spring-boot-with-joinfaces.adoc#security[Security],
  xref:web/jsf/spring-boot-with-joinfaces.adoc#session[Session]).
* *With Quarkus put views under `+META-INF/resources+`.* `+src/main/webapp+` is ignored, the context path and the stage are build-time settings, client state needs the secrets from the environment, and `+o:socket+` replaces `+f:websocket+`
  (xref:web/jsf/quarkus.adoc#layout[Layout], xref:web/jsf/quarkus.adoc#state[State], xref:web/jsf/quarkus.adoc#websocket[WebSocket]).
* *Do not assume another servlet container behaves like Tomcat.* Jetty needs its CDI and WebSocket modules and refuses the Tomcat `+resource-env-ref+`
  (xref:web/jsf/tomcat-and-weld.adoc#jetty[Jetty]).
* *Keep the Faces and CDI jars `+provided+` on a server that has them.* The default WAR of the deployment runs was 22,519 bytes, the Tomcat profile with Faces and Weld 6.1 MB
  (xref:web/jsf/deployment-and-clustering.adoc#packaging[Packaging]).

[#testing]
== Testing

* *Test the beans without Faces.* Beans and services are plain Java; constructor injection makes them testable
  (xref:web/jsf/testing.adoc#beans[Testing beans], xref:web/jsf/backing-beans-and-cdi.adoc#testing[Testing backing beans]).
* *Test converters, validators and constraints directly.* Faces artefacts have small interfaces, and constraints can be validated with the provider
  (xref:web/jsf/testing.adoc#converters-validators[Converters and validators], xref:web/jsf/testing.adoc#constraints[Constraints]).
* *Test in a container for CDI, injection and the lifecycle.* Arquillian deployments or an embedded server give the real wiring; keep the number of such tests small
  (xref:web/jsf/testing.adoc#arquillian[Arquillian], xref:web/jsf/testing.adoc#arquillian-modes[Container modes]).
* *Test the pages with a real browser.* Selenium or Playwright, with page objects and waits for Ajax instead of sleeps; HtmlUnit 5.5.0 could not parse the MyFaces `+faces.js+`
  (xref:web/jsf/testing.adoc#ajax-waiting[Waiting for Ajax], xref:web/jsf/testing.adoc#selenium[Selenium],
  xref:web/jsf/testing.adoc#playwright[Playwright], xref:web/jsf/testing.adoc#htmlunit[HtmlUnit]).
* *Test hostile input and forged requests.* A script in a text field, a forged ViewState, a tampered state, a POST of a button that was not rendered
  (xref:web/jsf/testing.adoc#hostile[Hostile input], xref:web/jsf/testing.adoc#client-state[Client state in tests]).
* *Run the suite on the stage and the state saving production uses,* and on every implementation you support (xref:web/jsf/testing.adoc#project-stages[Project stages in tests],
  xref:web/jsf/testing.adoc#implementations[Mojarra and MyFaces]).
* *Do not test with JSFUnit.* It ended (xref:web/jsf/testing.adoc#books[Where the books are outdated]).
* *Use the shared browser-testing page for the parts that are not Faces.* Page objects, waits and CI belong to the general guide
  (xref:web/e2e-testing-real-browsers.adoc[End-to-End Testing with Real Browsers]).

[#deployment]
== Deployment and Clustering

* *Build a reproducible WAR and keep the configuration outside it.* The Production stage in `+web.xml+`, everything environment-specific in the environment
  (xref:web/jsf/deployment-and-clustering.adoc#packaging[Packaging],
  xref:web/jsf/deployment-and-clustering.adoc#production-stage[The Production stage]).
* *Do not run the container as root, and keep credentials out of the image.* The official Tomcat image runs Tomcat as root unless told otherwise, which the Dockerfile of the page changes; pass
  credentials as runtime secrets, never as literals in a Dockerfile (xref:web/jsf/deployment-and-clustering.adoc#containers[Containers],
  xref:web/jsf/deployment-and-clustering.adoc#orchestrators[Orchestrators]).
* *Choose sticky sessions or replication on purpose.* Sticky sessions are simple and lose state when a node dies; replication needs a distributable application and serialisable state;
  Quarkus has no session replication, so its instances need sticky sessions with server state or client state with shared keys
  (xref:web/jsf/deployment-and-clustering.adoc#sticky[Sticky sessions], xref:web/jsf/deployment-and-clustering.adoc#replication[Session replication], xref:web/jsf/quarkus.adoc#state[Quarkus state],
  xref:web/jsf/deployment-and-clustering.adoc#failover[Failover]).
* *Set `+com.sun.faces.enableDistributable+` to `+true+` for Mojarra in a replicated cluster.* Without it the server state did not move with the replicated session and the other node
  answered `+ViewExpiredException+`, even with `+<distributable/>+` (xref:web/jsf/deployment-and-clustering.adoc#replication[Session replication]).
* *Know that Tomcat replicates a session attribute only when it is set.* A session object changed in place after it was stored was not replicated on either implementation
  (three list additions were lost), and a MyFaces view-scoped bean showed a counter of 1 instead of 4 on the other node (Mojarra with `+enableDistributable+` showed 4); store an immutable value and call `+setAttribute+` again, or re-set the attributes in a filter
  (xref:web/jsf/deployment-and-clustering.adoc#in-place[Changing a session object in place],
  xref:web/jsf/deployment-and-clustering.adoc#view-scoped[View scope in a cluster]).
* *Use the same client-state keys on every node, or stay with server state.* Different keys without a shared session expired the page on both implementations
  (xref:web/jsf/deployment-and-clustering.adoc#client-state[Client state in a cluster]).
* *Do not keep per-user data in a node.* The flash was lost on another node on Mojarra even with a replicated session, and application-scoped caches, timers and uploads are per node
  (xref:web/jsf/deployment-and-clustering.adoc#node-local[Node-local state], xref:web/jsf/websocket-push.adoc#cluster[Push in a cluster]).
* *Encrypt the replication channel and secure the proxy.* A Tomcat `+EncryptInterceptor+` with the key from the environment; `+RemoteIpValve+` so that the session cookie is `+Secure+` behind TLS termination;
  `+ErrorReportValve+` with `+showReport=false+` and `+showServerInfo=false+` (xref:web/jsf/deployment-and-clustering.adoc#proxy[Proxy and TLS]).
* *Monitor sessions, state and errors.* JMX attributes of the session manager, the access log with the request time, and the Faces loggers at the level you need
  (xref:web/jsf/deployment-and-clustering.adoc#monitoring[Monitoring], xref:web/jsf/deployment-and-clustering.adoc#logging[Logging]).

[#avoid]
== Things to Avoid

The books of the JSF 1.x and 2.0 era, and the forums that grew from them, spread habits that were never good and that migrations carry into new code. They are listed here as things to avoid,
each with what happens (from the runs of the linked page) and the form that replaces it. The migration page lists the same habits as a table of old code to remove
(xref:web/jsf/migrating-to-jakarta-faces.adoc#books-errata[Bad Practices the Era Normalised]).

.The errata of the older books as things to avoid
[cols="3,4,4",options="header"]
|===
|Avoid |What happens |Do instead

|Session-scoped beans for page state
|Memory grows with every user and view, and two tabs of one user overwrite each other's form; the bean is serialised with the session.
|`+@ViewScoped+`, `+@FlowScoped+` or `+@ClientWindowScoped+` (xref:web/jsf/scopes.adoc#choosing[Scopes], xref:web/jsf/multi-window-support.adoc#problem[Multi-Window Support])

|Business logic or database queries in getters
|The query ran 4 to 13 times for one table in the performance runs.
|Load in `+@PostConstruct+`, a view action or the action (xref:web/jsf/performance.adoc#getters[Getters], xref:web/jsf/backing-beans-and-cdi.adoc#lifecycle-position[Lifecycle position of a bean])

|`+binding+` to a session-scoped bean
|Component instances are shared between requests and users.
|No `+binding+`, or a request-scoped bean (xref:web/jsf/architecture-and-component-model.adoc#binding[The binding attribute])

|JSTL `+c:if+` and `+c:forEach+` used as if they ran at render time
|They run when the view is built; inside `+ui:repeat+` they rendered nothing.
|`+rendered+` and `+ui:repeat+` (xref:web/jsf/jstl-and-build-time-vs-render-time.adoc#decision[JSTL or Facelets])

|`+immediate="true"+` as a way to skip validation
|The command runs in Apply Request Values; the other inputs are neither validated nor updated, and a listener that calls `+renderResponse()+` skips the model update.
|Understand the phases first; use it for Cancel only (xref:web/jsf/request-processing-lifecycle.adoc#immediate[Immediate components])

|Secrets, passwords or database URLs in `+faces-config.xml+`, `+web.xml+` or beans
|Everyone with the repository has them for ever.
|The environment or a secret store (xref:web/jsf/security.adoc#secrets[Secrets and configuration], xref:web/jsf/state-saving-and-stateless-views.adoc#client-keys[Keys])

|`+escape="false"+` on user-supplied content
|Stored or reflected XSS; also `+p:messages+`, `+p:menuitem+`, `+b:growl+` and chart data.
|Escaped output; sanitise when markup must be kept (xref:web/jsf/security.adoc#xss[Cross-site scripting], xref:web/jsf/primefaces-extensions.adoc#sanitizer[Sanitiser])

|State-changing `+h:link+` or GET, or turning off the view state or CSRF protection
|A third-party page can trigger the change; client state and stateless views were accepted from a forged post.
|POST with view state, protected views, an `+Origin+` check (xref:web/jsf/security.adoc#csrf[CSRF], xref:web/jsf/security.adoc#protected-views[Protected views])

|Client-side state saving without encryption and a MAC
|Unencrypted state is a serialisation stream that the server deserialises; the MAC goes with the encryption switch.
|Keep the defaults and set the keys from the environment (xref:web/jsf/state-saving-and-stateless-views.adoc#client[Client state saving], xref:web/jsf/state-saving-and-stateless-views.adoc#client-audit[Auditing client state])
|===

Further habits belong to the same family, and the runs of this section show the effect of each:

.More things to avoid
[cols="3,4,4",options="header"]
|===
|Avoid |What happens |Do instead

|`+@ManagedBean+`, `+@ManagedProperty+` from `+javax.faces.bean+`, `+<managed-bean>+`
|Removed in Faces 4.0; the descriptor entry is ignored and `+@ManagedProperty+` without `+@Inject+` leaves a null field.
|CDI `+@Named+` and `+@Inject+` (xref:web/jsf/backing-beans-and-cdi.adoc#managedbean-removed[Managed beans were removed], xref:web/jsf/backing-beans-and-cdi.adoc#managed-property[ManagedProperty])

|Entities in view-scoped beans, and open-session-in-view as the design
|Failures on the postback, 43 statements for a table of 24 books.
|DTOs, join fetch or entity graphs (xref:web/jsf/persistence-and-services.adoc#dto[DTO projections], xref:web/jsf/persistence-and-services.adoc#osiv[Open session in view])

|A second `+FacesServlet+` mapping that nobody secured
|`+/faces/admin/panel.xhtml+` bypassed the constraint on `+/admin/*+`.
|Constrain `+/*+`, or each prefix, or map nothing else (xref:web/jsf/security.adoc#web-xml[Securing URLs in web.xml])

|Changing a session or view-scoped object in place in a cluster
|Not replicated; the session moved back to a stale copy after failover.
|Immutable values and `+setAttribute+` (xref:web/jsf/deployment-and-clustering.adoc#in-place[In-place changes])

|A catch-all `+java.lang.Throwable+` error page
|It shadowed the pages for specific exceptions.
|An error-code page for the catch-all (xref:web/jsf/exception-handling.adoc#throwable-shadow[The Throwable shadow])

|Development stage in production
|Stack traces, component trees and request parameters in error pages; no resource caching.
|`+Production+` (xref:web/jsf/configuration-and-project-stages.adoc#project-stage[Project stages])

|Hand-written Ajax, Weblets, ajax4jsf or `+jsf.js+`
|`+jsf.js+` is a missing resource in Faces 4.x; the others ended.
|`+f:ajax+` and `+faces.js+` (xref:web/jsf/ajax.adoc#faces-js[faces.js], xref:web/jsf/migrating-to-jakarta-faces.adoc#faces-js[jsf.js to faces.js])

|JSP views and `+UIComponentELTag+` custom components
|Removed in Faces 4.0.
|Facelets and Facelets tag libraries (xref:web/jsf/migrating-to-jakarta-faces.adoc#jsp[JSP to Facelets], xref:web/jsf/custom-components-and-renderers.adoc[Custom components])

|Adopting RichFaces, Tomahawk or Seam in a new project
|No release for Jakarta Faces.
|PrimeFaces, OmniFaces and the standard components (xref:web/jsf/other-component-libraries.adoc#replacements[Replacements])

|Turning off client-state encryption to read the state
|The server deserialises bytes chosen by the client.
|The development stage and server logs (xref:web/jsf/state-saving-and-stateless-views.adoc#client-keys[Keys])

[#portable]
== Writing Code That Does Not Depend on One Implementation

* *Do not depend on view parameters being re-applied on a postback.* Mojarra did, MyFaces did not; use a view-scoped bean and
  `+required="#{not facesContext.postback}"+` (xref:web/jsf/view-parameters-and-view-actions.adoc#postback[Postback]).
* *Use `+<redirect-param>+` and `+includeViewParams+` in outcomes.* `+<redirect include-view-params="true"/>+` worked on Mojarra only
  (xref:web/jsf/navigation.adoc#include-view-params-config[Include view params]).
* *Do not inject into classes named in `+faces-config.xml+`.* Mojarra left the field null and MyFaces injected it; use `+CDI.current()+`
  (xref:web/jsf/events-and-listeners.adoc#implementations[Implementations], xref:web/jsf/extending-faces.adoc#implementations[Extension points]).
* *Send plain Java beans, not records, enums or `+java.time+` values, through `+f:websocket+`.* The two implementations failed or serialised them differently
  (xref:web/jsf/websocket-push.adoc#implementations[WebSocket differences]).
* *Do not depend on the order of `+ui:repeat+` attributes `+size+` and `+end+`.* Mojarra treats `+size+` as an end index, MyFaces as a count
  (xref:web/jsf/data-tables-and-iteration.adoc#repeat-attributes[ui:repeat attributes]).
* *Do not depend on the defaults of the view limits, the flash storage or the scope destruction order.* They differ
  (xref:web/jsf/scopes.adoc#mojarra-myfaces[Scopes], xref:web/jsf/flash-and-post-redirect-get.adoc#implementations[Flash]).
* *Test with both when the application is meant to run on both.* The pages of this section note differences in a closing "Mojarra and MyFaces" section; the list in
  xref:web/jsf/versions-and-implementations.adoc#mojarra-vs-myfaces[Mojarra versus MyFaces] is the overview.

[#books]
== Where the Books Are Outdated

The eight books consulted for this section teach much that holds: separate view from model, keep beans small, validate on the server, redirect after a post. The parts of their practice that no longer hold:

* Their examples use JSP, JSP tag handlers, Facelets 1.x, `+javax.faces+` and `+@ManagedBean+`, and some keep page state in session beans; Faces 4.1 has none of the first four and a view scope for the last.
* They show hand-written Ajax, Ajax frameworks, RichFaces, Tomahawk, Trinidad, Seam, Shale and JSFUnit; the evidence that these projects ended or have no Jakarta Faces release is in xref:web/jsf/other-component-libraries.adoc#discontinued[the discontinued libraries section] and, for JSFUnit, xref:web/jsf/testing.adoc#books[the testing page].
* They show client state saving and the state-saving API of Faces 1.x and 2.0, and none of them mentions the key configuration that client state needs today.
* Their security material relies on the container and on projects that ended (the JSF Security project, Acegi; this statement follows the survey of the books in xref:web/jsf/security.adoc#books[the security page]); Jakarta Security, protected views and client windows came after them, and <<security>> covers the forged-request and escaping cases.
* None of them covers flows, the CDI view scope, stateless views, CDI injection of Faces objects, WebSocket push, programmatic Facelets, JoinFaces or Quarkus.

The migration page keeps the complete list, area by area, book by book and page by page
(xref:web/jsf/migrating-to-jakarta-faces.adoc#books-by-area[by area], xref:web/jsf/migrating-to-jakarta-faces.adoc#books-by-book[by book],
xref:web/jsf/migrating-to-jakarta-faces.adoc#books-by-page[by page]).

[#pitfalls]
== Common Mistakes in Using a Checklist

* *Ticking an item you did not test.* Every item on this page was observed with a test on a page of the section; copy the test, not only the rule.
* *Testing only the development stage and the default state saving.* Several rules (client state keys, the stage, replication) change what is observed.
* *Applying one implementation's behaviour to the other.* The runs differ in the places listed in <<portable>>.
* *Treating a version number as a rule.* The versions here are those verified on 2026-10-08; re-check them before copying (xref:web/jsf/versions-and-implementations.adoc#version-matrix[Version matrix]).
* *Reading the checklist instead of the page.* An item gives the rule; the reason, the lifecycle position and the exceptions are on the page it links.
* *Fixing the symptom.* A flash message, a larger buffer or a longer timeout hides the cause that the item names.
