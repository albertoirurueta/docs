Testing a Faces application is different from testing a REST API because the thing under test is a state machine that lives on the server and is driven by a browser: a request
restores a component tree, applies the submitted values, converts and validates them, updates the model, calls the action and renders. A test can enter that machine at
five heights, and the skill is to test each rule at the cheapest height at which it can fail. This page walks up the heights in order of cost: plain objects, mocked Faces
objects, a real container without a browser, a browser without a real display, and a real browser. The page on the xref:web/e2e-testing-real-browsers.adoc[real-browser end-to-end tests] of the web
section compares Selenium, Playwright and Cypress in general; this page adds only what is specific to Faces and its component libraries.

[#what-to-test]
== What to Test, and at Which Height

The request processing lifecycle (see the xref:web/jsf/request-processing-lifecycle.adoc#phases[lifecycle page]) has six phases, and the code you write is called from four of
them: converters and validators from Process Validations, setters from Update Model Values, action methods and listeners from Invoke Application, and getters and
`+rendered+` expressions from Render Response. A rule belongs at the lowest height that executes the code, and the table shows what each height executes.

.What each height runs
[cols="2,3,3,3",options="header"]
|===
|Height |Lifecycle code that runs |What it proves |What it cannot prove

|Plain JUnit and Mockito
|None. The test calls the method the lifecycle would call (`+getAsObject+`, `+validate+`, `+search+`).
|The rule itself: conversion, validation, branching, messages.
|That the page wires the rule to the right component, in the right phase.

|MyFaces Test mock objects
|One component's `+validate+` and `+updateModel+`, called by hand on real component objects.
|Interplay of converter, validators, messages and the model for one input.
|Anything rendered: the mock render kit has no renderers.

|Arquillian in-container
|None by itself; CDI injects into the test class, the bean runs in the container.
|Wiring: CDI scopes, events, interceptors, producers, the container's own bean validation.
|The page.

|Arquillian client mode, HTTP, HtmlUnit
|All six phases, on the real FacesServlet.
|A page renders, a form posts, the view state round-trips, the Ajax protocol.
|What a real browser's JavaScript engine does.

|Real browser (Selenium, Playwright, PrimeFaces Selenium, Graphene)
|All six phases, `+faces.js+`, and the component library's JavaScript.
|Whole features as a user sees them: widgets, dialogs, focus, timing.
|Nothing the others could; it is the slowest and the flakiest.
|===

== The Bookshelf Test Project

One parent POM and four modules keep the heights apart, because they need different dependencies and run at different times. `+shelf+` is the _Bookshelf_ WAR with its unit tests;
`+myfaces-test+` tests components with mock objects; `+e2e+` unpacks the WAR, starts it in an embedded Tomcat and drives it; `+arquillian+` deploys test archives to an embedded TomEE.

[source]
----
bookshelf-parent/
  pom.xml                       JUnit BOM, surefire 3.6.0, failsafe 3.6.0, war plugin 3.5.1
  shelf/                        WAR + unit tests (surefire, *Test)
    src/main/java/org/example/bookshelf/{model,service,web}
    src/main/webapp/            index.xhtml, review.xhtml, shelf.xhtml, fixture.xhtml, WEB-INF/templates/layout.xhtml
    src/test/java/             CatalogueBeanTest, IsbnConverterTest, ...
  myfaces-test/                 mock Faces objects (surefire)
  e2e/                          browser, HTTP and server tests (failsafe, *IT)
  arquillian/                   Arquillian with TomEE embedded (failsafe, *IT)
----

Two conventions matter more than any tool. Unit tests are named `+*Test+` and run in Maven's `+test+` phase with the Surefire plugin; tests that start a server or a browser are named `+*IT+` and run in
the `+integration-test+` phase with the Failsafe plugin, so that `+mvn test+` stays fast and a failing server start does not hide a unit-test result. The second convention is that
tests never depend on a fixed port or on a browser that another build is using: every port in the listings below is a system property with a default, set in the POM.

The unit-test module needs only the APIs at compile time. The Faces implementation and Weld are bundled into the WAR through a profile, so the same sources run on either
implementation (`+mvn verify+` for Mojarra, `+mvn verify -Pmyfaces+` for MyFaces).

Source: https://maven.apache.org/surefire/maven-surefire-plugin/[Apache Maven Surefire Plugin], https://maven.apache.org/surefire/maven-failsafe-plugin/[Apache Maven Failsafe Plugin] https://javadoc.io/doc/org.mockito/mockito-core/latest/org.mockito/org/mockito/Mockito.html#0.3[Mockito: Mockito as a Java agent] and https://openjdk.org/jeps/451[JEP 451: Prepare to Disallow the Dynamic Loading of Agents]

Three details of that excerpt come from failures, not from taste.

* *The agent.* Mockito 5 uses the inline mock maker, which can mock final classes and static methods (both are used below). Without `+-javaagent+`, Mockito attaches itself at run time, and on JDK 26 the
  run printed "Mockito is currently self-attaching", followed by the JVM warnings "A Java agent has been loaded dynamically" and "Dynamic loading of agents will be disallowed by default in a future release" (JEP 451).
  The `+maven-dependency-plugin+` `+properties+` goal supplies the jar's path as `+${org.mockito:mockito-core:jar}+`.
* *An Expression Language implementation.* Hibernate Validator interpolates constraint messages with Jakarta Expression Language, so a plain JVM test of a constraint needs an EL implementation on the class path
  (here Expressly). Without it the test class fails to start with `+HV000183: Unable to initialize 'jakarta.el.ExpressionFactory'+` (observed). Inside a servlet container or a Jakarta EE server one is already present.
* *The locale.* Message texts such as "not between the expected values of 1 and 5" depend on the JVM default locale. The `+-Duser.language=en -Duser.country=US+` arguments make every run produce the same text on every machine.

[#beans]
== Unit-Testing Backing Beans

A backing bean is a plain class whose collaborators are injected, which is exactly what makes it easy to test, and what the xref:web/jsf/backing-beans-and-cdi.adoc#testing[backing beans page] meant
by testing the layers without Faces. Two Faces-specific obstacles remain: the bean reaches the `+FacesContext+` to add messages, and the container, not the test, calls its `+@PostConstruct+` method.

Since Faces 2.3 the specification requires that the `+FacesContext+` can be injected into a CDI bean with `+@Inject+` (section 5.6.1, changes listed in B.4). A bean written that way receives the context
through a field or a constructor, so a test replaces it with a mock. Mockito can mock `+FacesContext+`, an abstract class, directly.

.CatalogueBean.java -- the bean under test (view scoped, injected collaborators)
[source,java]
----
package org.example.bookshelf.web;

import jakarta.annotation.PostConstruct;
import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;

@Named
@ViewScoped
public class CatalogueBean implements Serializable {

    private static final long serialVersionUID = 1L;

    @Inject
    private BookService service;

    @Inject
    private FacesContext facesContext;

    private String query;
    private List<Book> books;

    @PostConstruct
    void load() {
        books = service.catalogue();
    }

    public void search() {
        books = service.search(query);
        if (books.isEmpty()) {
            facesContext.addMessage("catalogue:query", new FacesMessage(FacesMessage.SEVERITY_WARN,
                    "Nothing found", "No book matches '" + query + "'."));
        }
    }

    public void borrow(long id) {
        service.borrow(id, "reader");
        facesContext.addMessage(null, new FacesMessage("Borrowed book " + id));
    }

    public String getQuery() {
        return query;
    }

    public void setQuery(String query) {
        this.query = query;
    }

    public List<Book> getBooks() {
        return books;
    }
}
----

.CatalogueBeanTest.java -- JUnit 5 and Mockito; no container, no Faces runtime
[source,java]
----
package org.example.bookshelf.web;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertNotSame;
import static org.junit.jupiter.api.Assertions.assertTrue;
import static org.mockito.ArgumentMatchers.eq;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.verifyNoInteractions;
import static org.mockito.Mockito.when;

import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;
import java.io.ByteArrayInputStream;
import java.io.ByteArrayOutputStream;
import java.io.ObjectInputStream;
import java.io.ObjectOutputStream;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.ArgumentCaptor;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

@ExtendWith(MockitoExtension.class)
class CatalogueBeanTest {

    private static final Book EMMA = new Book(2, "Emma", "Jane Austen", 1815);

    @Mock
    BookService service;

    @Mock
    FacesContext facesContext;

    @InjectMocks
    CatalogueBean bean;

    @Test
    void loadsTheCatalogueWhenCreated() {
        when(service.catalogue()).thenReturn(List.of(EMMA));

        bean.load();                       // the container would call the @PostConstruct method

        assertEquals(List.of(EMMA), bean.getBooks());
    }

    @Test
    void anEmptySearchAddsAWarningToTheQueryField() {
        when(service.search("zzz")).thenReturn(List.of());
        bean.setQuery("zzz");

        bean.search();

        ArgumentCaptor<FacesMessage> message = ArgumentCaptor.forClass(FacesMessage.class);
        verify(facesContext).addMessage(eq("catalogue:query"), message.capture());
        assertEquals(FacesMessage.SEVERITY_WARN, message.getValue().getSeverity());
        assertEquals("No book matches 'zzz'.", message.getValue().getDetail());
    }

    @Test
    void aSuccessfulSearchAddsNoMessage() {
        when(service.search("emma")).thenReturn(List.of(EMMA));
        bean.setQuery("emma");

        bean.search();

        assertEquals(List.of(EMMA), bean.getBooks());
        verifyNoInteractions(facesContext);
    }

    @Test
    void borrowingReportsToTheUser() {
        bean.borrow(2);

        verify(service).borrow(2, "reader");
        ArgumentCaptor<FacesMessage> message = ArgumentCaptor.forClass(FacesMessage.class);
        verify(facesContext).addMessage(eq(null), message.capture());
        assertEquals("Borrowed book 2", message.getValue().getSummary());
    }

    @Test
    void theViewStateSurvivesSerialisation() throws Exception {
        // A view-scoped bean is serialised when the session is passivated or replicated.
        // The injected collaborators are proxies, so only the state of the bean itself matters here.
        CatalogueBean plain = new CatalogueBean();
        plain.setQuery("emma");

        ByteArrayOutputStream bytes = new ByteArrayOutputStream();
        try (ObjectOutputStream out = new ObjectOutputStream(bytes)) {
            out.writeObject(plain);
        }
        try (ObjectInputStream in = new ObjectInputStream(new ByteArrayInputStream(bytes.toByteArray()))) {
            CatalogueBean copy = (CatalogueBean) in.readObject();
            assertNotSame(plain, copy);
            assertEquals("emma", copy.getQuery());
            assertTrue(copy instanceof java.io.Serializable);
        }
    }
}
----

All five tests passed on 2026-10-08. What the test relies on, and what it deliberately leaves out:

* `+@InjectMocks+` writes the two mocks into the private `+@Inject+` fields; the container is not involved, so the bean's scope annotation (`+@ViewScoped+`) is inert in the test. Whether the
  scope is the right one is a question for the page and for the xref:web/jsf/scopes.adoc[scopes page], not for the unit test.
* The test calls `+load()+` itself because the container would call a `+@PostConstruct+` method. The method is package-private on purpose; the test sits in the same package.
* `+ArgumentCaptor+` reads the `+FacesMessage+` that the bean added. A message is the bean's visible output, so the test asserts on its severity, summary or detail and on the client id it was
  attached to (`+catalogue:query+`, the id of the input inside the form `+catalogue+`).
* `+verifyNoInteractions(facesContext)+` proves the happy path adds no message, which is a requirement stated in a test and not only in the code.
* The serialisation test checks that the view-scoped bean's own state survives `+ObjectOutputStream+`; a `+@ViewScoped+` bean must be `+Serializable+` because Faces keeps it with the view and an
  application server may passivate or replicate it (see the xref:web/jsf/scopes.adoc#view-limits[scopes page]). The comment in the listing explains why the injected fields are not part of that test.

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a3054[Jakarta Faces 4.1 specification, 5.6.1 Jakarta Faces Objects Valid for @Inject Injection], https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#changes-between-2-2-and-2-3[B.4 Changes between 2.2 and 2.3] and https://javadoc.io/doc/org.mockito/mockito-core/latest/org.mockito/org/mockito/Mockito.html[Mockito]

[#static-context]
=== Code That Reaches for FacesContext.getCurrentInstance()

Older code, and helper classes in every code base, call the static `+FacesContext.getCurrentInstance()+`, which reads a thread-local that exists only while a Faces request is being processed. A unit test
that calls such code sees `+null+`. There are two remedies, in order of preference. The first is to inject the `+FacesContext+` into the class and pass it down, as `+CatalogueBean+` does. The second, for code that
cannot change, is `+Mockito.mockStatic+`.

.Messages.java -- a static helper of the kind older code bases have
[source,java]
----
package org.example.bookshelf.web;

import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;

/** Static helper of the kind older code bases have: it reaches the context through the thread. */
public final class Messages {

    private Messages() {
    }

    public static void info(String summary) {
        FacesContext.getCurrentInstance()
                .addMessage(null, new FacesMessage(FacesMessage.SEVERITY_INFO, summary, null));
    }
}
----

.MessagesTest.java -- mockStatic replaces the static method for the duration of the try block, on this thread only
[source,java]
----
package org.example.bookshelf.web;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.mockito.ArgumentMatchers.isNull;
import static org.mockito.Mockito.mock;
import static org.mockito.Mockito.mockStatic;
import static org.mockito.Mockito.verify;

import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;
import org.junit.jupiter.api.Test;
import org.mockito.ArgumentCaptor;
import org.mockito.MockedStatic;

class MessagesTest {

    @Test
    void infoAddsAGlobalMessage() {
        FacesContext context = mock(FacesContext.class);
        // FacesContext.getCurrentInstance() is a static method that reads a thread-local:
        // mockStatic replaces it for the duration of the try block, on this thread only.
        try (MockedStatic<FacesContext> faces = mockStatic(FacesContext.class)) {
            faces.when(FacesContext::getCurrentInstance).thenReturn(context);

            Messages.info("Saved");

            ArgumentCaptor<FacesMessage> message = ArgumentCaptor.forClass(FacesMessage.class);
            verify(context).addMessage(isNull(), message.capture());
            assertEquals("Saved", message.getValue().getSummary());
            assertEquals(FacesMessage.SEVERITY_INFO, message.getValue().getSeverity());
        }
    }
}
----

The static mock is thread-local, so it does not leak into other tests, and it is closed by the `+try+`-with-resources. If the code under test starts its own thread, it sees the real static method again.

Source: https://javadoc.io/doc/org.mockito/mockito-core/latest/org.mockito/org/mockito/Mockito.html#static_mocks[Mockito: Mocking static methods] and https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/context/FacesContext.html[FacesContext API documentation]

[#services]
=== The Layer Below: Services and Events

The service that the bean calls is an `+@ApplicationScoped+` class with constructor injection and a `+jakarta.enterprise.event.Event+` it fires, as the backing beans page shows. The version in the test project adds a
`+search+` method and rejects a blank reader. Constructor injection is what makes it testable: the test builds it with mocks, with no CDI container at all.

.BookServiceTest.java -- constructor injection, a mocked Event, no container
[source,java]
----
package org.example.bookshelf.service;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertThrows;
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.verifyNoInteractions;
import static org.mockito.Mockito.when;

import jakarta.enterprise.event.Event;
import java.util.List;
import java.util.Optional;
import org.example.bookshelf.model.Book;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

@ExtendWith(MockitoExtension.class)
class BookServiceTest {

    @Mock
    BookRepository repository;

    @Mock
    Event<BookBorrowed> borrowed;

    @Test
    void searchMatchesTitleOrAuthorIgnoringCase() {
        when(repository.findAll()).thenReturn(List.of(
                new Book(1, "Emma", "Jane Austen", 1815),
                new Book(2, "Dracula", "Bram Stoker", 1897)));
        BookService service = new BookService(repository, borrowed);

        assertEquals(List.of("Emma"), service.search("AUSTEN").stream().map(Book::title).toList());
        assertEquals(2, service.search("  ").size());
    }

    @Test
    void borrowingFiresAnEvent() {
        when(repository.findById(2)).thenReturn(Optional.of(new Book(2, "Emma", "Jane Austen", 1815)));
        BookService service = new BookService(repository, borrowed);

        service.borrow(2, "ana");

        verify(borrowed).fire(new BookBorrowed(2, "ana"));
    }

    @Test
    void borrowingNeedsAReader() {
        BookService service = new BookService(repository, borrowed);

        assertThrows(IllegalArgumentException.class, () -> service.borrow(2, " "));

        verifyNoInteractions(repository);
        verify(borrowed, never()).fire(org.mockito.ArgumentMatchers.any());
    }
}
----

`+verifyNoInteractions(repository)+` and the `+never()+` verification state the other half of a rule: when the reader is missing, nothing is looked up and no event is fired. The observer side of the
event is tested differently: it needs CDI, and the Arquillian test of <<arquillian>> does it.

[#converters-validators]
== Unit-Testing Converters and Validators

Converters and validators run in Process Validations (the lifecycle page has the order: conversion first, then the validators, with `+required+` checked before them). Both are small classes with one
method, which makes them the best value for a unit test: every rule, every message and every edge case (null, blank, separators, lengths) runs in milliseconds.

The converter of the xref:web/jsf/converters.adoc[converters page] ignores its `+FacesContext+` and `+UIComponent+` arguments, so the test passes `+null+` for both. When a converter reads component attributes, pass a mock
`+UIComponent+` and stub `+getAttributes()+`.

.IsbnConverter.java
[source,java]
----
package org.example.bookshelf.web;

import jakarta.faces.application.FacesMessage;
import jakarta.faces.component.UIComponent;
import jakarta.faces.context.FacesContext;
import jakarta.faces.convert.Converter;
import jakarta.faces.convert.ConverterException;
import jakarta.faces.convert.FacesConverter;
import org.example.bookshelf.model.Isbn;

@FacesConverter(forClass = Isbn.class)
public class IsbnConverter implements Converter<Isbn> {

    @Override
    public Isbn getAsObject(FacesContext context, UIComponent component, String value) {
        if (value == null || value.isBlank()) {
            return null;
        }
        String digits = value.replaceAll("[-\\s]", "");
        if (!digits.matches("\\d{13}")) {
            FacesMessage message = new FacesMessage(FacesMessage.SEVERITY_ERROR,
                    "Not an ISBN-13", "'" + value + "' must contain exactly 13 digits (hyphens are allowed).");
            throw new ConverterException(message);
        }
        return new Isbn(digits);
    }

    @Override

package org.example.bookshelf.web;

import jakarta.faces.application.FacesMessage;
import jakarta.faces.component.UIComponent;
import jakarta.faces.context.FacesContext;
import jakarta.faces.validator.FacesValidator;
import jakarta.faces.validator.Validator;
import jakarta.faces.validator.ValidatorException;
import java.text.MessageFormat;
import java.util.ResourceBundle;

@FacesValidator("bookshelf.isbnLength")
public class IsbnLengthValidator implements Validator<String> {

    private static final int LENGTH = 13;

    @Override
    public void validate(FacesContext context, UIComponent component, String value) {
        if (value == null || value.length() == LENGTH) {
            return;
        }
        ResourceBundle bundle = context.getApplication().getResourceBundle(context, "msg");
        String text = MessageFormat.format(bundle.getString("isbn.length"),
                LENGTH, value, value.length());
        throw new ValidatorException(new FacesMessage(FacesMessage.SEVERITY_ERROR, text, null));
    }
}

import static org.junit.jupiter.api.Assertions.assertNull;
import static org.junit.jupiter.api.Assertions.assertTrue;

import jakarta.faces.component.UIInput;
import java.util.List;
import org.apache.myfaces.test.base.junit.AbstractJsfTestCase;
import org.example.bookshelf.model.Isbn;
import org.junit.jupiter.api.Test;

/**
 * Real UIInput components running the real validation step, with mock servlet and Faces objects around them.
 * The mock render kit has no renderers, so the component falls back to its own converter (and logs a warning).
 */
class IsbnInputTest extends AbstractJsfTestCase {

    private UIInput input(String id) {
        UIInput input = new UIInput();
        input.setId(id);
        facesContext.getViewRoot().getChildren().add(input);
        return input;
    }

    @Test
    void aValidIsbnIsConverted() {
        UIInput input = input("isbn");
        input.setConverter(new IsbnConverter());
        input.setSubmittedValue("978-0-306-40615-7");

        input.validate(facesContext);

        assertTrue(input.isValid());
        assertEquals(new Isbn("9780306406157"), input.getLocalValue());
        assertTrue(facesContext.getMessageList().isEmpty());
    }

    @Test
    void aBadIsbnProducesAConverterMessageForTheComponent() {
        UIInput input = input("isbn");
        input.setConverter(new IsbnConverter());
        input.setSubmittedValue("12345");

        input.validate(facesContext);

        assertFalse(input.isValid());
        List<FacesMessage> messages = facesContext.getMessageList("isbn");
        assertEquals(1, messages.size());
        assertEquals("Not an ISBN-13", messages.get(0).getSummary());
    }

    @Test
    void validatorsRunOnTheConvertedValue() {
        // A String validator on an input whose converter produces an Isbn fails with a ClassCastException:
        // converters run first and the validator receives their result.
        UIInput input = input("isbn");
        input.setConverter(new IsbnConverter());
        input.addValidator(new IsbnLengthValidator());
        input.setSubmittedValue("978-0-306-40615-7");

        org.junit.jupiter.api.Assertions.assertThrows(ClassCastException.class, () -> input.validate(facesContext));
    }

    @Test
    void updateModelValuesWritesTheBean() {
        // The mock application evaluates value expressions; request attributes play the role of the request scope.
        ReviewBean bean = new ReviewBean();
        request.setAttribute("reviewBean", bean);
        UIInput comment = input("comment");
        comment.setValueExpression("value", application.getExpressionFactory()
                .createValueExpression(facesContext.getELContext(), "#{reviewBean.comment}", String.class));
        comment.setSubmittedValue("Lovely.");

        comment.validate(facesContext);
        assertNull(bean.getComment());              // not yet: the model is updated in a later phase

        comment.updateModel(facesContext);
        assertEquals("Lovely.", bean.getComment());
    }

All four tests passed with `+myfaces-api+` and `+myfaces-impl+` 4.1.4 on the class path. Three observations from the runs:

* The mock render kit has no renderers, so every `+UIInput+` logs a warning "No Renderer found for component" and the component falls back to its own converter. The tests do not read rendered output, only `+isValid()+`, the local value and the messages.
* `+validatorsRunOnTheConvertedValue+` records the order the lifecycle uses: a converter runs first and the validators receive the converter's result. A validator written for `+String+` that is attached to
  an input with the `+Isbn+` converter fails with a `+ClassCastException+`. The same mistake in a page appears as an HTTP 500 after the first postback, so a component-level test is where it is found cheaply.
* `+updateModelValuesWritesTheBean+` shows the phases split: after `+validate+` the bean is still untouched, and only `+updateModel+` writes it. The mock application evaluates value expressions, and request attributes play the role of the request scope.

I ran the framework with MyFaces on the class path only. The mock classes are MyFaces' own, and I did not find a counterpart published by the Mojarra project; an application on Mojarra can still use this height with
the MyFaces jars as test dependencies, or use Mockito mocks as in <<beans>>. Nothing in the framework replaces a deployed page: it has no Facelets compilation, no `+FacesServlet+` and no state saving.

[#arquillian]
== Integration Tests with Arquillian

A unit test cannot tell whether CDI finds the bean, whether the event reaches its observer, or whether the page renders. Arquillian closes that gap: it packs a test archive with ShrinkWrap, starts a container (or connects to
one) through an adapter, deploys the archive and runs the tests, in the container or against it. Each test class builds its own small deployment, so a test depends only on what it lists.

[#arquillian-modes]
=== In-Container and Client Mode

The default mode is _in-container_: the test class is added to the archive, and the methods execute in the server's JVM, where `+@Inject+` works on the test class itself. The second mode, _client_ mode
(`+@Deployment(testable = false)+` or `+@RunAsClient+`), deploys the archive as it is and runs the test in the test JVM as a client of the container, which is the mode for web pages. One class can mix both.

Four problems appeared while getting the TomEE run to work, and each is a mistake that other containers produce in a different form.

* *The API jar shadows the container's.* Adding `+jakarta.jakartaee-api:10.0.0+` with `+provided+` scope put `+jakarta.faces-api+` 4.0.1 in front of MyFaces' own API jar, and the deployment failed with
  `+NoClassDefFoundError: com/sun/faces/util/Util+` raised from `+jakarta.faces.CurrentThreadToServletContext+`. An embedded container supplies its own APIs; do not add a second set.
* *The second error hides the first.* After one failed deployment, the next test class failed with `+Child name [/bookshelf] is not unique+`. Read the first `+SEVERE+` line of the log, not the last stack trace.
* *Records in Expression Language.* `+#{book.title}+` on the `+Book+` record threw `+PropertyNotFoundException: Property [title] not found on type [org.example.bookshelf.model.Book]+` on this Jakarta EE 10 server.
  Expression Language 6.0 (Jakarta EE 11) adds `+RecordELResolver+`, enabled by default; on EE 10 the page calls the accessor as a method, `+#{book.title()}+`, as the pages written for the test do.
* *Noise.* TomEE embedded logs `+SEVERE: Unable to initialize agent: null+` and an unused-property warning for ports it does not use; the tests passed with both messages present.

[#browser]
== Browser Tests

A browser test starts the application, opens a page in a real browser, acts like a user and reads what is on the screen. It exercises what nothing below it can: `+faces.js+`, the component library's JavaScript, the DOM that the renderers produce,
focus, dialogs and timing. It is also the slowest height, so the Bookshelf suite keeps it for flows (search, review, borrow, dialog) and not for single rules.

[#fixture]
=== A Server for the Tests

The `+e2e+` module starts the exploded WAR in an embedded Tomcat 11.0.26 once per JVM and hands out its URL. The WAR is unpacked into `+target/webapp+` by the dependency plugin, so the tests run the same bytes that the
build packaged, with Weld bundled in the WAR as in the xref:web/jsf/getting-started.adoc[getting started page] and the Faces implementation chosen by the Maven profile. `+-Dbookshelf.url=...+` points the same tests at an
application that runs somewhere else (a staging server), and the project stage is `+Production+` unless `+-Dbookshelf.stage+` says otherwise, so the tests run with the settings the users get.

.BookshelfServer.java -- the embedded Tomcat, started once per JVM
[source,java]
----
package org.example.bookshelf.e2e;

import java.io.File;
import java.nio.file.Files;
import java.nio.file.Path;
import java.util.Map;
import org.apache.catalina.Context;
import org.apache.catalina.LifecycleException;
import org.apache.catalina.startup.Tomcat;

/** Starts the unpacked WAR on an embedded Tomcat once per JVM and hands out its base URL. */
public final class BookshelfServer {

    private static Tomcat tomcat;
    private static String baseUrl;

    /** A second, separately configured application: its own port, context parameters and lifetime. */
    public record Running(Tomcat tomcat, String url) implements AutoCloseable {
        @Override
        public void close() {
            try {
                tomcat.stop();
                tomcat.destroy();
            } catch (LifecycleException ignored) {
                // shutting down
            }
        }
    }

    public static Running start(int port, Map<String, String> contextParameters) {
        try {
            Path base = Files.createTempDirectory("bookshelf-tomcat");
            Tomcat server = new Tomcat();
            server.setBaseDir(base.toString());
            server.setPort(port);
            server.getServer().setPort(-1);
            server.getConnector();
            Context context = server.addWebapp("/bookshelf", new File("target/webapp").getAbsolutePath());
            contextParameters.forEach(context::addParameter);
            server.start();
            return new Running(server, "http://localhost:" + port + "/bookshelf");
        } catch (Exception e) {
            throw new IllegalStateException("Cannot start the application", e);
        }
    }

    private BookshelfServer() {
    }

    public static synchronized String url() {
        if (baseUrl == null) {
            // -Dbookshelf.url=... tests an application that is already running somewhere else
            baseUrl = System.getProperty("bookshelf.url");
            if (baseUrl == null) {
                baseUrl = startEmbedded();
            }
        }
        return baseUrl;
    }

    private static String startEmbedded() {
        int port = Integer.getInteger("bookshelf.port", 8750);
        try {
            Path base = Files.createTempDirectory("bookshelf-tomcat");
            tomcat = new Tomcat();
            tomcat.setBaseDir(base.toString());
            tomcat.setPort(port);
            tomcat.getServer().setPort(-1);          // no shutdown port
            tomcat.getConnector();
            Context context = tomcat.addWebapp("/bookshelf", new File("target/webapp").getAbsolutePath());
            context.addParameter("jakarta.faces.PROJECT_STAGE", System.getProperty("bookshelf.stage", "Production"));
            tomcat.start();
            Runtime.getRuntime().addShutdownHook(new Thread(BookshelfServer::stop));
            return "http://localhost:" + port + "/bookshelf";
        } catch (Exception e) {
            throw new IllegalStateException("Cannot start the application", e);
        }
    }

    private static synchronized void stop() {
        try {
            if (tomcat != null) {
                tomcat.stop();
                tomcat.destroy();
            }
        } catch (LifecycleException ignored) {
            // shutting down
        }
    }
}

[#locators]
=== Finding Elements on a Faces Page

Three properties of Faces markup decide how a test finds an element.

* *Client ids carry the naming containers.* The `+h:inputText id="query"+` inside `+h:form id="catalogue"+` is rendered with the id `+catalogue:query+`; a data table row adds the row index
  (`+catalogue:books:0:borrow+`). `+By.id("catalogue:query")+` takes the id as it is. In a CSS selector the colon must be escaped, so the tests use an attribute selector, `+[id='catalogue:books']+`.
* *Labels are real.* `+h:outputLabel for="isbn"+` renders `+<label for="review:isbn">+`, so Playwright's `+getByLabel("ISBN")+` works and doubles as an accessibility check.
* *Passthrough attributes make stable hooks.* `+pt:data-testid="save-review"+` (namespace `+jakarta.faces.passthrough+`) adds a `+data-testid+` attribute to the HTML element without a renderer or an id, and it survives a refactoring that
  moves the component into another form or a composite component. Locating by test id is the documented default in Playwright (`+getByTestId+`).

[#ajax-waiting]
=== Waiting for Ajax

The most common reason for a flaky Faces browser test is reading the page before the Ajax response has been applied. A fixed sleep is slow when the server is fast and wrong when it is slow, and Selenium's implicit wait only waits for
elements to exist, not for an element's content to change. The reliable signal is Faces' own: `+faces.ajax.addOnEvent+` reports `+begin+` and `+success+` of every request, and `+faces.ajax.addOnError+` reports failures (the xref:web/jsf/ajax.adoc#events[Ajax page]
documents both). The helper counts them and the test waits until none is in flight.

.FacesAjax.java -- counts the Ajax events that faces.js reports
[source,java]
----
package org.example.bookshelf.e2e;

import java.time.Duration;
import org.openqa.selenium.JavascriptExecutor;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.support.ui.WebDriverWait;

/** Knows when a Jakarta Faces Ajax request has finished: counts the events faces.ajax reports. */
public final class FacesAjax {

    private static final String INSTALL = """
            if (!window.__ajax) {
              window.__ajax = { pending: 0, finished: 0, errors: [] };
              faces.ajax.addOnEvent(function (event) {
                if (event.status === 'begin') { window.__ajax.pending++; }
                if (event.status === 'success') { window.__ajax.pending--; window.__ajax.finished++; }
              });
              faces.ajax.addOnError(function (error) {
                window.__ajax.pending--;
                window.__ajax.errors.push(error.status + ': ' + error.description);
              });
            }
            """;

    private FacesAjax() {
    }

    /** Call once after each full page load (a full page load discards the script's state). */
    public static void install(WebDriver driver) {
        ((JavascriptExecutor) driver).executeScript(INSTALL);
    }

    /** Waits until no Faces Ajax request is in flight. Call it right after the action that starts one. */
    public static void waitIdle(WebDriver driver) {
        new WebDriverWait(driver, Duration.ofSeconds(10)).until(d -> {
            Object pending = ((JavascriptExecutor) d).executeScript("return window.__ajax ? window.__ajax.pending : -1");
            return Long.valueOf(0).equals(pending);
        });
    }

    public static long finished(WebDriver driver) {
        return (Long) ((JavascriptExecutor) driver).executeScript("return window.__ajax.finished");
    }
}
----

The script state lives in the page, so `+install+` must run after every full page load (the base class does it in `+open+`). `+finished(driver)+` also proves that a test stayed on one page: after a search the counter was 1, which
a full reload would have reset to 0.

Source: https://jakarta.ee/specifications/faces/4.1/jsdoc/faces.ajax.html[Jakarta Faces 4.1 JavaScript API: faces.ajax] and https://www.selenium.dev/documentation/webdriver/waits/[Selenium: Waiting strategies]

The helper listens to the standard `+faces.ajax+` events, which `+f:ajax+` uses on both implementations. PrimeFaces components send their requests through the library's own jQuery-based client, and a page that
contains only PrimeFaces components may not define a global `+faces+` at all, so the helper is for plain Faces pages and the PrimeFaces guards of <<primefaces-selenium>> are for PrimeFaces ones.

=== PrimeFaces Selenium

PrimeFaces publishes its own test library, built on JUnit 5 and Selenium and "heavily inspired by Arquillian Graphene" in the words of its README: page objects, typed wrappers for PrimeFaces components, and Ajax guards that know the PrimeFaces client.
Its Maven artifacts are `+org.primefaces:primefaces-selenium-core+` and `+org.primefaces:primefaces-selenium-components+`, both 16.0.0 on Maven Central (the README's snippet still shows 15.0.0). The components artifact has 55 component classes in its 16.0.0
sources, among them `+DataTable+`, `+Dialog+`, `+CommandButton+`, `+InputText+`, `+SelectOneMenu+`, `+AutoComplete+`, `+DatePicker+`, `+FileUpload+`, `+TabView+` and `+Tree+`.

The library needs two things from the project: a configuration file, `+src/test/resources/primefaces-selenium/config.properties+`, and a `+DeploymentAdapter+` that starts the application and returns its URL.

.config.properties -- an adapter that starts the server, an adapter that creates the browser
[source,properties]

.The configuration keys (from the README and ConfigProvider in the 16.0.0 sources)
[cols="3,2,5",options="header"]
|===
|Key |Default |Meaning

|`+deployment.baseUrl+`
|none
|The URL of a running application (remote testing). Either this or `+deployment.adapter+` is required.

|`+deployment.adapter+`
|none
|A class implementing `+DeploymentAdapter+` that starts and stops the application.

|`+webdriver.adapter+`
|built-in
|A class implementing `+WebDriverAdapter+`. The built-in adapter uses WebDriverManager to download a driver for `+chrome+`, `+firefox+` or `+safari+`.

|`+webdriver.browser+`, `+webdriver.headless+`, `+webdriver.version+`, `+webdriver.logLevel+`
|none, `+false+`, newest, `+WARNING+`
|The browser, headless mode, the driver version and the level of browser console messages that are collected.

|`+timeout.gui+`, `+timeout.ajax+`, `+timeout.http+`, `+timeout.documentLoad+`, `+timeout.fileUpload+`
|2, 10, 10, 15, 20 (seconds)
|Waits of the GUI, Ajax and HTTP guards, document load and file upload.

|`+disableAnimations+`
|`+true+`
|Turns the component library's animations off during the test, a large source of flakiness.

|`+screenshotDirectory+`
|none
|Where a screenshot and a text file with the stack trace are saved when a test fails.
|===

A value of the form `+${NAME}+` is resolved from a system property, then from an environment variable, and a system property named like the key overrides the file, so CI can change the browser without editing it.

=== A Regression Test for Escaping

Security is correctness, and a browser test is the only place where "the input stays text" can be proved end to end. The test submits a value that would execute if a component wrote it unescaped, into the standard message of an
`+h:messages+` and into the message of a PrimeFaces growl, and asserts three things: the text appears literally, no element was created from it, and the page title (which the payload would change) is intact.

.HostileInputIT.java -- the validator message repeats what the user typed, which is where unescaped output would show
[source,java]

[#ajax-view-state]
== Testing Ajax and the View State Without a Browser

A browser is the wrong tool for some questions: "does the server answer a validation failure with HTTP 200 and the message?", "what happens when the view has expired?", "does a view survive the loss of the session when the state is on the client?".
Those are questions about the protocol, and the protocol is plain HTTP: a `+GET+` that returns the page with a `+jakarta.faces.ViewState+` hidden field, and a `+POST+` with that field, the form's values and a few `+jakarta.faces.*+` parameters that
`+faces.js+` adds. A test can send them with the JDK's `+HttpClient+` in milliseconds and parse the XML that comes back (the xref:web/jsf/ajax.adoc#partial-response[partial response], as the Ajax page describes it).

.FacesHttp.java -- the requests and the parsing of the response, written once
[source,java]
----
package org.example.bookshelf.e2e;

import static org.junit.jupiter.api.Assertions.assertTrue;

import java.io.ByteArrayInputStream;
import java.net.URI;
import java.net.URLEncoder;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.nio.charset.StandardCharsets;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.regex.Matcher;
import java.util.regex.Pattern;
import java.util.stream.Collectors;
import javax.xml.XMLConstants;
import javax.xml.parsers.DocumentBuilderFactory;
import javax.xml.xpath.XPathConstants;
import javax.xml.xpath.XPathFactory;
import org.w3c.dom.Document;

/** Speaks the Faces Ajax protocol over plain HTTP, the way faces.js does, without a browser. */
final class FacesHttp {

    private static final Pattern VIEW_STATE =
            Pattern.compile("<input[^>]*name=\"jakarta.faces.ViewState\"[^>]*value=\"([^\"]*)\"");

    private FacesHttp() {
    }

    static String get(HttpClient client, String page) throws Exception {
        return client.send(HttpRequest.newBuilder(URI.create(page)).build(),
                HttpResponse.BodyHandlers.ofString()).body();
    }

    static String viewStateOf(String html) {
        Matcher matcher = VIEW_STATE.matcher(html);
        assertTrue(matcher.find(), "no jakarta.faces.ViewState field in the page");
        return matcher.group(1);
    }

    /** The parameters that f:ajax sends for the Save button of review.xhtml, as Mojarra and MyFaces send them. */
    static HttpResponse<String> save(HttpClient client, String page, String viewState, String isbn, String rating)
            throws Exception {
        Map<String, String> form = new LinkedHashMap<>();
        form.put("review", "review");
        form.put("review_SUBMIT", "1");                 // MyFaces looks for this marker, Mojarra ignores it
        form.put("review:isbn", isbn);
        form.put("review:rating", rating);
        form.put("review:comment", "");
        form.put("jakarta.faces.ViewState", viewState);
        form.put("jakarta.faces.source", "review:submit");
        form.put("jakarta.faces.partial.event", "click");
        form.put("jakarta.faces.partial.execute", "review:submit review");
        form.put("jakarta.faces.partial.render", "review");
        form.put("jakarta.faces.behavior.event", "action");
        form.put("jakarta.faces.partial.ajax", "true");
        String body = form.entrySet().stream()
                .map(e -> URLEncoder.encode(e.getKey(), StandardCharsets.UTF_8) + "="
                        + URLEncoder.encode(e.getValue(), StandardCharsets.UTF_8))
                .collect(Collectors.joining("&"));
        HttpRequest request = HttpRequest.newBuilder(URI.create(page))
                .header("Content-Type", "application/x-www-form-urlencoded;charset=UTF-8")
                .header("Faces-Request", "partial/ajax")
                .header("X-Requested-With", "XMLHttpRequest")
                .POST(HttpRequest.BodyPublishers.ofString(body))
                .build();
        return client.send(request, HttpResponse.BodyHandlers.ofString());
    }

    static Document xml(String text) throws Exception {
        DocumentBuilderFactory factory = DocumentBuilderFactory.newInstance();
        factory.setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true);
        factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
        return factory.newDocumentBuilder().parse(new ByteArrayInputStream(text.getBytes(StandardCharsets.UTF_8)));
    }

    static String text(Document document, String xpath) throws Exception {
        return (String) XPathFactory.newInstance().newXPath().evaluate(xpath, document, XPathConstants.STRING);
    }
}
----

.AjaxProtocolIT.java -- four questions about the Ajax protocol
[source,java]
----
package org.example.bookshelf.e2e;

import static org.example.bookshelf.e2e.FacesHttp.get;
import static org.example.bookshelf.e2e.FacesHttp.save;
import static org.example.bookshelf.e2e.FacesHttp.text;
import static org.example.bookshelf.e2e.FacesHttp.viewStateOf;
import static org.example.bookshelf.e2e.FacesHttp.xml;
import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertFalse;
import static org.junit.jupiter.api.Assertions.assertTrue;

import java.net.CookieManager;
import java.net.http.HttpClient;
import java.net.http.HttpResponse;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.w3c.dom.Document;

/** Tests the Ajax protocol itself: no browser, no JavaScript, one HTTP client that keeps the session cookie. */
class AjaxProtocolIT {

    private final String page = BookshelfServer.url() + "/review.xhtml";
    private HttpClient client;

    @BeforeEach
    void newBrowser() {
        client = HttpClient.newBuilder().cookieHandler(new CookieManager()).build();
    }

    @Test
    void aValidSubmissionReturnsAPartialResponseThatUpdatesTheForm() throws Exception {
        HttpResponse<String> response = save(client, page, viewStateOf(get(client, page)), "9780306406157", "5");

        assertEquals(200, response.statusCode());
        assertTrue(response.headers().firstValue("Content-Type").orElse("").startsWith("text/xml"));
        Document document = xml(response.body());
        assertEquals("partial-response", document.getDocumentElement().getTagName());
        assertTrue(text(document, "/partial-response/changes/update[@id='review']")
                .contains("Saved review 5/5 for 9780306406157"));
    }

    @Test
    void anInvalidSubmissionStillReturnsHttp200WithTheMessage() throws Exception {
        HttpResponse<String> response = save(client, page, viewStateOf(get(client, page)), "12345", "5");

        assertEquals(200, response.statusCode());
        // The update is HTML in a CDATA section; MyFaces writes the quotes as &quot;, Mojarra writes them as they are
        String html = text(xml(response.body()), "/partial-response/changes/update[@id='review']")
                .replace("&quot;", "\"");
        assertTrue(html.contains("ISBN must have 13 digits, but \"12345\" has 5."));
    }

    @Test
    void theResponseCarriesTheViewStateForTheNextRequest() throws Exception {
        String body = save(client, page, viewStateOf(get(client, page)), "9780306406157", "5").body();

        String viewState = text(xml(body), "/partial-response/changes/update[contains(@id,'ViewState')]");
        assertFalse(viewState.isBlank());
    }

    @Test
    void anExpiredViewIsReportedInsideTheXml() throws Exception {
        String viewState = viewStateOf(get(client, page));
        newBrowser();                                    // a new client: the session cookie is gone

        HttpResponse<String> response = save(client, page, viewState, "9780306406157", "5");

        assertEquals(200, response.statusCode());                   // the error is inside the XML, not in the status
        assertTrue(text(xml(response.body()), "/partial-response/error/error-name").contains("ViewExpiredException"));
    }
}
----

All four tests passed on Mojarra 4.1.17 and on MyFaces 4.1.4. What they establish, and what they showed:

* *A validation failure is an HTTP 200.* The response is a `+text/xml+` document whose root is `+partial-response+`, with the failed message already rendered inside the `+<update id="review">+` element. A test or a monitor that looks for a 4xx
  to detect a failed form will never see one.
* *The new state travels in the response.* An `+<update>+` element whose id contains `+jakarta.faces.ViewState+` carries the value for the next request. Its id differs: `+j_id1:jakarta.faces.ViewState:0+` on Mojarra and
  `+j_id__v_0:jakarta.faces.ViewState:1+` on MyFaces, which is why the test matches on `+contains(@id,'ViewState')+`.
* *An expired view is an error inside the XML, not a status.* A second client with no session cookie sends the state of the first; the response is still HTTP 200, with
  `+<error><error-name>+` naming the `+ViewExpiredException+`. The browser-side handling of that element is on the Ajax page, and the xref:web/jsf/state-saving-and-stateless-views.adoc#expired[state saving page] explains why the state is bound to the session.
* *Raw tests are tied to the implementation.* The hand-built request has a marker field named after the form, `+review_SUBMIT=1+`, which MyFaces looks for in a postback (Mojarra ignores it). MyFaces writes the quotes of the message as `+&quot;+` inside the HTML in the
  response, Mojarra writes them as they are, and the two markups differ in other details (the Mojarra form holds a hidden field named after the form, `+onclick="mojarra.ab(...)"+` against `+myfaces.ab+`). The listing is written to accept both, and for this reason a handful
  of protocol tests is plenty: they are for questions the browser cannot answer, not a replacement for it.

Source: https://jakarta.ee/specifications/faces/4.1/jsdoc/faces.ajax.html[Jakarta Faces 4.1 JavaScript API: faces.ajax] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a401[Jakarta Faces 4.1 specification, 2.2 Standard Request Processing Lifecycle Phases]

[#project-stages]
== The UnitTest and SystemTest Project Stages

`+jakarta.faces.application.ProjectStage+` has four constants: `+Development+`, `+UnitTest+`, `+SystemTest+` and `+Production+`. The specification defines the property (section 7.1.9): the value comes from the context parameter `+jakarta.faces.PROJECT_STAGE+` or from JNDI,
and `+Application.getProjectStage()+` returns it. It does not say what the two test stages change, and the implementations barely do. The xref:web/jsf/configuration-and-project-stages.adoc#stage-effects[configuration page] measured the effects: on MyFaces `+UnitTest+` and `+SystemTest+` behave like `+Production+` in
everything checked, and on Mojarra they differ from `+Production+` only in the text of an unresolved `+h:link+`. The stages are therefore a convention for the application's own code, and testing is where that convention is useful:

* `+UnitTest+` marks code that runs under a test harness, so that it can skip what needs a real container (a connection to a mail server, a timer).
* `+SystemTest+` marks a deployed application that is driven from outside, so that it can offer what only a test needs: a way to put the data back to a known state, a clock that can be set, a fake payment gateway.

Anything a stage unlocks is a back door, and the rest of this section is about keeping it closed in production. The Bookshelf version is a button that resets the catalogue, available in `+SystemTest+` only.

import jakarta.enterprise.context.RequestScoped;
import jakarta.faces.application.ProjectStage;
import jakarta.faces.context.FacesContext;

import jakarta.inject.Named;

/** Test support that exists only while the application runs in the SystemTest project stage. */

@RequestScoped
public class FixtureBean {

    @Inject
    private FacesContext facesContext;

    @Inject
    private BookRepository repository;

    public boolean isAvailable() {

            throw new IllegalStateException("Fixtures are available in the SystemTest stage only");
        }
        repository.reset();
    }
}

[#load-testing]
== Load Testing

A load test replays what `+FacesHttp+` does, at volume, and everything that makes a Faces page different from a REST endpoint is in those few lines: a session cookie per virtual user, a `+GET+` first to obtain the `+jakarta.faces.ViewState+` value (and, on MyFaces, the form marker),
and a `+POST+` that sends it back with the form's client ids as parameter names. Use one cookie jar and one extracted state per virtual user; replaying a recorded state shared by all users fails with a `+ViewExpiredException+`, as the protocol test showed. In Apache JMeter that is an HTTP Cookie Manager and a Regular Expression
Extractor on the `+GET+` response, whose output variable is used in the `+POST+`. The xref:backend/springboot/performance-testing-jmeter.adoc[JMeter page] of the backend section covers the tool, and the xref:web/jsf/performance.adoc[performance page] says what to measure (state size, session memory, render time). The JMeter elements were not run for this page; the
protocol that they must reproduce was.

Source: https://jmeter.apache.org/usermanual/get-started.html[Apache JMeter: Getting started] and https://jmeter.apache.org/usermanual/regular_expressions.html[Apache JMeter: Regular expressions]

[#ci]
== Running the Tests in CI

* *Two phases.* Surefire runs `+*Test+` in `+mvn test+`; Failsafe runs `+*IT+` in `+mvn verify+` and only fails the build after the server has been stopped. Browser and server tests are in the second.
* *Both implementations.* The production runtime decides which Faces implementation matters, and an application that is expected to run on more than one should run the browser suite with both (`+mvn verify+` and `+mvn verify -Pmyfaces+` here); `+mvn clean+` between them.
* *Fixed, configurable ports.* The ports in the listings are system properties with defaults, so parallel builds on a shared agent do not collide.
* *A headless browser and a driver cache.* Headless Chrome plus Selenium Manager's cache (`+SE_CACHE_PATH+`) keeps builds fast and offline-capable once the driver is downloaded. Playwright is told not to download its own browser.
* *Artifacts of a failure.* Keep Playwright's `+target/traces+` and PrimeFaces Selenium's `+screenshotDirectory+` as CI artifacts.
* *No real secrets.* A test application that needs a login uses a test identity store and placeholder credentials supplied by the environment, not values in the repository.

[#books]
== Where the Books Are Outdated

* *JSFUnit.* Leonard's JSF 2.0 cookbook devotes a chapter to JSFUnit, a JBoss framework that runs tests inside the container with access to the managed beans, the `+FacesContext+` and the component tree, based on JUnit and HtmlUnit. The book works with JSFUnit 1.1.0 GA, JSF 1.1, 1.2 and
  the JSF 2.0 beta, HtmlUnit 2.5, an Ant task and a deployer for JBoss AS 5. The project page still online (jsfunit.jboss.org) shows as its newest announcement the 2.0.0.Beta2 of 15 September 2011, and I found no `+org.jboss.jsfunit+` artifact on Maven Central. It targets the `+javax.faces+` packages, so it
  cannot run on a Jakarta Faces 3.0 or later application at all. The need it answered has three current answers: Arquillian for tests inside the container (<<arquillian>>), the HTTP-level tests of <<ajax-view-state>> for the protocol, and a browser tool for the page (<<browser>>).
* *The container as the only place a bean can be tested.* The older books test through the container because their beans reached for `+FacesContext.getCurrentInstance()+`. With injection (2.3) and constructor injection of services the same classes are tested in a plain JVM (<<beans>>); the rest of the books' advice about the
  container is still right for the wiring, and Arquillian is where it is done now.
* *Faces Console.* The same chapter introduces Faces Console 1.7, a stand-alone tool for browsing and checking the Faces 1.1 configuration and TLD files. The 4.1 `+faces-config.xml+` is validated against its schema by any current IDE or build, and the tag documentation is the VDL.
* *JMeter and the view state.* The cookbook's load-testing recipe extracts the view state from each response with a regular expression and sends it back. The idea has not changed (<<load-testing>>), but the field is `+jakarta.faces.ViewState+` (not `+javax.faces.ViewState+`), a stateless view sends the literal `+stateless+`, and the Ajax requests need the `+Faces-Request: partial/ajax+` header
  and the `+jakarta.faces.partial.*+` parameters.
* *Still valid.* Mann's _JSF in Action_ advises putting the core logic of a converter or validator in a method that uses no runtime Faces classes, so that its JUnit tests need no web container or mock objects, and its business objects are unit tested the same way. The advice
  stands; the only change is that a converter that ignores its context arguments can be called with `+null+` (<<converters-validators>>) and that an injected `+FacesContext+` can be mocked.
* *Silent.* In the extracted text of the eight books, Selenium, Arquillian, Mockito and HtmlUnit appear only in Leonard's cookbook (JSFUnit and HtmlUnit). None of them covers testing the Ajax protocol over HTTP, one suite against both implementations, mocking the injected `+FacesContext+`, test ids through passthrough attributes, browser tests of PrimeFaces components, or the `+SystemTest+` stage as a switch for fixtures.

Source: https://jsfunit.jboss.org/[JSFUnit project page, JBoss Community] and https://repo1.maven.org/maven2/org/jboss/[Maven Central: org.jboss]

[#pitfalls]
== Common Mistakes

* *Sleeping instead of waiting.* `+Thread.sleep+` after a click is the most frequent cause of slow and flaky suites. Wait for the Faces event, for the retrying assertion or for the library's guard (<<ajax-waiting>>).
* *Selecting by generated id.* `+j_id_xy+` ids change when a component is added before it. Give the component an `+id+`, and use `+pt:data-testid+` or a label as the hook.
* *Testing everything in the browser.* A converter rule tested through a page costs a hundred times more than the same rule in `+IsbnConverterTest+`. Put the rule in the unit, and one end-to-end test per feature in the browser.
* *Mocking what you do not own, too deeply.* A chain such as `+facesContext.getExternalContext().getRequestMap()+` needs three mocks; inject the narrow object (the `+ExternalContext+`, a `+@RequestMap Map+`) instead, and the test stays short.
* *Static state between tests.* A `+@ApplicationScoped+` in-memory repository keeps changes from one test to the next. The test project resets it through the `+SystemTest+` fixture; a unit test constructs a fresh object.
* *A shared Tomcat directory after a profile change.* A leftover `+target/webapp+` mixed Mojarra and MyFaces and Weld refused to start (see <<fixture>>).
* *Forgetting the second implementation.* A test suite green on Mojarra does not prove the page on MyFaces (HtmlUnit above is one example, the markup differences another).
* *A back door left open.* A fixture, a debug page or a reset endpoint guarded by a stage or a flag needs a test in the `+Production+` configuration that proves it is not there (`+ProjectStageIT+`).
* *Asserting on exact markup.* Quotes, ids and attribute order differ between implementations and versions; assert on text, on the message, or on the element's presence.
