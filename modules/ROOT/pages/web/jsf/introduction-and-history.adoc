[#what-faces-is]
== What Jakarta Faces Is

The Jakarta Faces specification describes itself as a model-view-controller framework for building user interfaces for web
applications. It defines a set of user interface components, a way to manage their state, an event and listener model, input
validation, page navigation, and support for internationalisation and accessibility. The specification is implemented by independent
products, mainly Eclipse Mojarra and Apache MyFaces Core, and it is part of the Jakarta EE platform that application servers implement.

Three words in that description decide how a Faces application feels.

* *Server-side.* The application's logic and the component tree live on the server. The browser receives HTML, CSS and a small
  JavaScript library (`+faces.js+`) that sends Ajax requests.
* *Component-based.* A page is not a template that pulls model values into markup. It is a tree of stateful UI components
  (`+UIViewRoot+`, `+UIForm+`, `+UIInput+`, ...) that the framework builds, restores, updates and renders on every request.
* *Standard.* The component model, the lifecycle, the extension points and the XML and annotation configuration are a Jakarta EE
  specification with a technology compatibility kit, so a view written for one implementation runs on another.

Source: https://jakarta.ee/specifications/faces/[Jakarta Faces specification page]

The following view is the whole presentation layer of a Bookshelf search page. It declares components and binds them to a
CDI bean; nothing in it says how the request is decoded, validated or rendered.

.A Faces view: components bound to a bean (books.xhtml)
[source,xml]
----
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core">
<h:head>
    <title>Bookshelf</title>
</h:head>
<h:body>
    <h:form id="search">
        <h:inputText id="query" value="#{bookListBean.query}">
            <f:valueChangeListener type="org.example.bookshelf.web.SearchChangeListener"/>
        </h:inputText>
        <h:commandButton value="Search" action="#{bookListBean.search}"/>
    </h:form>
    <h:dataTable value="#{bookListBean.books}" var="book">
        <h:column>#{book.title}</h:column>
        <h:column>#{book.author}</h:column>
    </h:dataTable>
</h:body>
</html>
----

The bean is a plain CDI bean. `+@ViewScoped+` (package `+jakarta.faces.view+`) keeps it alive for as long as the user stays on the same view.

.The backing bean (BookListBean.java)
[source,java]
----
package org.example.bookshelf.web;

import java.io.Serializable;
import java.util.List;

import jakarta.faces.view.ViewScoped;
import jakarta.inject.Named;
import org.example.bookshelf.model.Book;

@Named
@ViewScoped
public class BookListBean implements Serializable {

    private String query = "";
    private List<Book> books = List.of(
            new Book("978-0-441-17271-9", "Dune", "Frank Herbert"),
            new Book("978-0-441-56956-5", "Neuromancer", "William Gibson"));

    public void search() {
        books = books.stream()
                .filter(b -> b.title().toLowerCase().contains(query.toLowerCase()))
                .toList();
    }

    public String getQuery() {
        return query;
    }

    public void setQuery(String query) {
        this.query = query;
    }

    public List<Book> getBooks() {
        return books;
    }
}
----

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-intro/faces-intro.html[Jakarta EE Tutorial: Introduction to Jakarta Faces Technology]

The Jakarta EE Tutorial published as `+current/+` is the Jakarta EE 10 tutorial, which covers Faces 4.0. There is no Jakarta EE 11

[#component-vs-action-vs-spa]
== Component-Based MVC, Action-Based MVC and Single-Page Applications

Web user interfaces are built with three broad models. They answer the same question -- who owns the user interface state, and where does
a user's gesture become a method call -- in different ways.

[cols="2,3,3,3",options="header"]
|===
| | Component-based (Faces) | Action-based (Spring MVC, Struts) | Single-page application (React)

| Unit of work
| A component tree, built and kept per view
| A request mapped to a controller method
| A component tree in the browser

| Where UI state lives
| On the server (or serialised to the client), restored on every postback
| Nowhere by default: each request is independent, state is held in the model, a session or hidden fields
| In the browser, in memory

| Who produces HTML
| Renderers attached to the components, driven by a view declaration
| A view template filled with a model by the controller
| JavaScript running in the browser

| Typical interaction
| An event on a component calls a listener or action method
| A URL and an HTTP method call a handler; the result chooses a view or a body
| An event handler updates state and calls a JSON API

| Server contract
| Faces requests to the same view, partial responses for Ajax
| URLs and HTML, or URLs and JSON
| JSON (or similar) APIs
|===

A component-based framework models the page the way a desktop toolkit models a window. The developer declares components, binds each
to a property or a method of a bean, and the framework runs a fixed lifecycle: it restores the tree, copies the submitted values into
the components, converts and validates them, updates the model, invokes the action and renders. The same page address receives the
request and the postback, which is why Faces pages are naturally stateful and why bookmarkable URLs need extra tools (xref:web/jsf/view-parameters-and-view-actions.adoc[view parameters],
covered in their own page of this section).

An action-based framework models the page as the response to a request. The controller method receives parameters, calls services and
returns a view name and a model; the template engine renders it. Spring MVC is the original web framework built on the Servlet
API, and Thymeleaf is one of the view technologies the Spring documentation lists. The same Bookshelf search looks as follows.

.The same search as an action: controller and template
[source,java]
----
@Controller
class BookController {

    private final BookService books;

    BookController(BookService books) {
        this.books = books;
    }

    @GetMapping("/books")
    String list(@RequestParam(defaultValue = "") String query, Model model) {
        model.addAttribute("books", books.search(query));
        return "books";
    }
}
----

[source,html]
----
<tr th:each="book : ${books}">
    <td th:text="${book.title}">Dune</td>
    <td th:text="${book.author}">Frank Herbert</td>
</tr>
----

Source: https://docs.spring.io/spring-framework/reference/web/webmvc.html[Spring Framework reference: Spring Web MVC] and https://www.thymeleaf.org/doc/tutorials/3.1/usingthymeleaf.html[Using Thymeleaf]

A single-page application moves the component tree into the browser. The server exposes data, and the browser renders and updates it.
The same Bookshelf row as a React component:

[source,javascript]
----
function BookRow({ book }) {
  return (
    <tr>
      <td>{book.title}</td>
      <td>{book.author}</td>
    </tr>

----

Source: https://react.dev/learn[React: Quick Start]

Server-side component frameworks and single-page applications are not opposites. Faces applications use Ajax (`+f:ajax+`) to update only part of a
page, and a Faces page can embed JavaScript components. What differs is where the authoritative component tree lives and what a
developer is expected to write. The site pages on xref:web/thymeleaf/index.adoc[Thymeleaf], xref:web/vaadin/index.adoc[Vaadin],
xref:web/react/index.adoc[React] and xref:web/django/index.adoc[Django] show the other models with the same kind of Bookshelf pages.

Several steps deserve a closer look.

* *From JSP to Facelets (1.x to 2.0).* Early versions used JSP as the page technology, with its tag handlers and TLDs. Version 2.0
  introduced Facelets as the view declaration language, and version 4.0 removed JSP support altogether.
* *Platform integration (2.2 and 2.3).* Version 2.2 added Faces Flows, the CDI-based `+@ViewScoped+`, passthrough markup and stateless
  views. Version 2.3 let CDI inject Faces artefacts.
* *The move to the Eclipse Foundation.* The Java EE 8 specifications, reference implementations and TCKs were transferred to the
  Eclipse Foundation, and in February 2018 the community voted on the new name, Jakarta EE. Jakarta Server Faces 2.3 is the first release
  for Jakarta EE 8 and is JSR 372 under a new licence.
* *`jakarta.*` (3.0).* Jakarta EE 9 replaced the `+javax.*+` namespace with `+jakarta.*+`. This is the change that breaks every
  existing import, and it is why a Faces 2.3 application does not run unchanged on a Faces 3.0 or later server.
* *Faces 4.0.* Besides the renaming, 4.0 added programmatic Facelets, extensionless mapping, `+@ClientWindowScoped+` and the `+jakarta.faces.*+`
  URN namespaces, and removed `+@ManagedBean+`, `+MethodBinding+`, `+ValueBinding+` and `+ResourceResolver+`.
* *Faces 4.1.* The release adds generics to several APIs such as `+FacesMessage+`, a `+UUIDConverter+`, `+rowStatePreserved+` on `+UIRepeat+`,
  injection of the current flow, and deprecates full state saving.
* *Faces 5.0 (upcoming).* The plan lists Content Security Policy support, `+oninput+` events for `+UIInput+`, generics across converters and
  validators, enums for `+FacesMessage.Severity+` and `+PhaseId+`, removal of code deprecated for removal in 4.0, dropping the old XML
  namespaces and a Java SE 21 baseline. The release review ballot has not happened, so none of this is current behaviour.

Source: https://jakarta.ee/specifications/faces/4.0/[Jakarta Faces 4.0], https://jakarta.ee/specifications/faces/4.1/[Jakarta Faces 4.1], https://jakarta.ee/specifications/faces/5.0/[Jakarta Faces 5.0] and https://jakarta.ee/about/faq/[Jakarta EE FAQ]

The two "What's new in Faces" articles by BalusC listed in the references complement the specification pages for 4.0 and 4.1.

[#design-patterns]
== Design Patterns Behind Faces

Faces was designed from well-known patterns, and recognising them explains the shape of the API. The patterns below are the ones that
matter when reading the specification, writing extensions and debugging. The classes named are the actual types of the 4.1 API.

=== Model-View-Controller

The model is the application data and services (`+Book+`, a service bean). The view is the Facelets page and the components it creates.
The controller role is split: `+FacesServlet+` is the front controller that receives every Faces request and runs the lifecycle, and the
backing bean's action and listener methods are the application-specific handlers it calls.

.The model: a Bookshelf entity as a record (Book.java)
[source,java]
----
package org.example.bookshelf.model;

public record Book(String isbn, String title, String author) {
}
----

Together with `+BookListBean+` and `+books.xhtml+` above, this is the whole triangle: `+Book+` is the model, `+books.xhtml+` the view and the
`+FacesServlet+` plus `+BookListBean+` the controller.

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html[Jakarta Faces 4.1 specification]

=== Composite

A page is a tree whose nodes and leaves share one interface: `+UIComponent+`. A container such as `+UIForm+` holds children exactly as a
leaf such as `+UIInput+` does, and operations such as rendering, state saving or finding a component by identifier work recursively. The
snippet walks the tree of the current view.

.Walking the component tree (TreeDump.java)
[source,java]
----
package org.example.bookshelf.web;

import jakarta.faces.component.UIComponent;
import jakarta.faces.context.FacesContext;

public final class TreeDump {

    private TreeDump() {
    }

    public static void print(UIComponent component, int depth, StringBuilder out) {
        out.append("  ".repeat(depth)).append(component.getClass().getSimpleName())
                .append(" id=").append(component.getId()).append('\n');
        for (UIComponent child : component.getChildren()) {
            print(child, depth + 1, out);
        }
    }

    public static String ofCurrentView() {
        StringBuilder out = new StringBuilder();
        print(FacesContext.getCurrentInstance().getViewRoot(), 0, out);
        return out.toString();
    }
}
----

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/component/UIComponent.html[API: UIComponent]

=== Strategy

Behaviour that varies is delegated to a replaceable object instead of subclassing the component. A `+Validator+` decides what is valid, a
`+Converter+` decides how a string becomes an object, and a `+Renderer+` decides how a component is written as markup. The same
`+UIInput+` can be combined with any of them. The validator below is a strategy that a page attaches by identifier.

.A validator strategy (IsbnLengthValidator.java)
[source,java]
----
package org.example.bookshelf.web;

import jakarta.faces.application.FacesMessage;
import jakarta.faces.component.UIComponent;
import jakarta.faces.context.FacesContext;
import jakarta.faces.validator.FacesValidator;
import jakarta.faces.validator.Validator;
import jakarta.faces.validator.ValidatorException;

@FacesValidator("bookshelf.isbnLength")
public class IsbnLengthValidator implements Validator<String> {

    @Override
    public void validate(FacesContext context, UIComponent component, String value) {
        if (value != null && value.replace("-", "").length() != 13) {
            throw new ValidatorException(
                    new FacesMessage(FacesMessage.SEVERITY_ERROR, "An ISBN has 13 digits", null));
        }
    }
}
----

[source,xml]
----
<h:inputText id="isbn" value="#{bookForm.isbn}">
    <f:validator validatorId="bookshelf.isbnLength"/>
</h:inputText>
----

=== Observer

Components publish events and listeners subscribe to them. An input component fires a `+ValueChangeEvent+` when its submitted value differs
from the previous one, and every registered `+ValueChangeListener+` is told. Action events, phase events and system events follow the same
model. The page at the start of this section registers the listener below with `+f:valueChangeListener+`.

.A value-change observer (SearchChangeListener.java)
[source,java]
----
package org.example.bookshelf.web;

import java.util.logging.Logger;

import jakarta.faces.event.AbortProcessingException;
import jakarta.faces.event.ValueChangeEvent;
import jakarta.faces.event.ValueChangeListener;

public class SearchChangeListener implements ValueChangeListener {

    private static final Logger LOG = Logger.getLogger(SearchChangeListener.class.getName());

    @Override
    public void processValueChange(ValueChangeEvent event) throws AbortProcessingException {
        LOG.info(() -> "Query changed from '" + event.getOldValue() + "' to '" + event.getNewValue() + "'");
    }
}
----

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/event/ValueChangeListener.html[API: ValueChangeListener]

=== Decorator

Most pluggable Faces services -- the `+ViewHandler+`, `+ExceptionHandler+`, `+NavigationHandler+`, `+ExternalContext+` and others -- have a
`+*Wrapper+` base class that implements the interface by delegating to the wrapped instance (the `+FacesWrapper+` interface). A subclass overrides
only the methods it cares about, and the implementation's own object stays underneath. The wrapper is registered in `+faces-config.xml+`.

.A view-handler decorator (AuditViewHandler.java)
[source,java]
----
package org.example.bookshelf.web;

import java.util.logging.Logger;

import jakarta.faces.application.ViewHandler;
import jakarta.faces.application.ViewHandlerWrapper;
import jakarta.faces.context.FacesContext;

public class AuditViewHandler extends ViewHandlerWrapper {

    private static final Logger LOG = Logger.getLogger(AuditViewHandler.class.getName());

    public AuditViewHandler(ViewHandler wrapped) {
        super(wrapped);
    }

    @Override
    public String getActionURL(FacesContext context, String viewId) {
        LOG.fine(() -> "Action URL requested for " + viewId);
        return super.getActionURL(context, viewId);
    }
}
----

[source,xml]
----
<faces-config xmlns="https://jakarta.ee/xml/ns/jakartaee"
              xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
              xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-facesconfig_4_1.xsd"
              version="4.1">
    <application>
        <view-handler>org.example.bookshelf.web.AuditViewHandler</view-handler>
    </application>
</faces-config>
----

[#when-to-choose]
== When to Choose Faces, and When Not To

The benefits that the Jakarta EE tutorial lists for the technology explain why teams keep choosing it. Faces separates the presentation
of a page from the application logic behind it, so a designer can work on the Facelets markup while a developer works on beans. The user
interface is built from reusable components with their own state, events, conversion and validation, so a date picker or a data table is
configured once and used everywhere. Everything is a standard API rather than a vendor product, which means several independent
implementations, tool support in IDEs and component libraries that work across them, and a programming model that the application server
already ships. The costs of the same design (per-view server state, less control of the markup) are the subject of the lists below.

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-intro/faces-intro.html#_jakarta_faces_technology_benefits[Jakarta EE Tutorial: Jakarta Faces Technology Benefits]

Faces is a good fit when most of the following hold.

* The organisation already runs Jakarta EE servers (GlassFish, WildFly, Payara, Open Liberty, TomEE) or Tomcat with Weld, and Faces comes
  with the platform.
* The application is an internal, form-heavy or data-heavy business application where server-side validation, conversion and a rich
  component set (PrimeFaces, OmniFaces) matter more than a custom visual identity.
* The team is Java-centric and prefers one language and one deployment unit to a Java back end plus a JavaScript front end.
* An existing JSF 2.x application has to be maintained or moved to `+jakarta.*+`. The migration is mostly mechanical and is covered by the xref:web/jsf/migrating-to-jakarta-faces.adoc[migrating to Jakarta Faces] page of this section.

Look at another model when:

* The user interface is public, content-heavy and needs fine control of the markup and the URLs. An action-based framework with a template
  engine such as Thymeleaf, or a single-page application, gives that control with less machinery.
* The interface is highly interactive on the client (offline use, drag-and-drop canvases, real-time collaboration), which favours a
  browser-side framework.
* The team has no Java ecosystem or a Jakarta EE deployment, and a Python, .NET or Node.js stack is already in place.
* The server cannot hold per-view state, or the application must scale to very large numbers of anonymous visitors. Faces can use stateless
  views and client-side state saving, but its default design is stateful.

The choice is rarely binary. Faces pages can call JSON services, host JavaScript components, and be served by Spring Boot through
JoinFaces or by Quarkus; the xref:web/jsf/spring-boot-with-joinfaces.adoc[Spring Boot with JoinFaces] and xref:web/jsf/quarkus.adoc[Quarkus] pages of this section show those combinations. The decision guide
xref:backend/architecture/decisions-and-migrations/starting-a-new-project.adoc[Starting a New Project] and the page
xref:backend/springboot/web-ui-frameworks.adoc[Web UI Frameworks for Spring Boot] compare these options at a broader level, and
xref:programming-languages/java/index.adoc[the Java reference] covers the language itself.

Struts and GWT are not documented on this site, so they are described here in prose with their official links. Fuller sections on Thymeleaf with Spring MVC (issue #238), GWT (issue #240) and Struts and JSP (issue #241) are tracked as separate issues of the same documentation effort, and a dedicated framework comparison (issue #263) is planned; until those exist, this table is the short version.

*Apache Struts.* The Struts project describes itself as a free, open-source MVC framework for building Java web applications. Its home
page lists Struts 7.4.0 and Struts 6.12.0 as the current releases (both published on 2026-10-02). The older Struts 1.x line has
https://struts.apache.org/struts1eol-announcement.html[reached its end of life] and is no longer officially supported, with Struts 2 recommended
as its successor. A Struts action maps a request to a method and then to a result, which makes it action-based like Spring MVC and unlike Faces,
whose unit is a component tree. Struts 1 integration with early JSF versions is a historical topic and is not covered here.

*GWT.* The Google Web Toolkit is described on its official page as a development toolkit for building and optimising complex
browser-based applications. The developer writes client code in Java, and the GWT compiler turns it into JavaScript, optimising the whole
program. The latest release shown on the overview page is 2.13.1. GWT therefore sits at the opposite end from Faces: the user interface
is a program that runs in the browser and talks to the server through remote calls, and the Java code never runs on the server as a UI.
See https://www.gwtproject.org/[the GWT project site].

Source: https://struts.apache.org/[Apache Struts] and https://www.gwtproject.org/overview.html[GWT overview]

ASP.NET Web Forms is documented by Microsoft in the .NET Framework part of its ASP.NET documentation, while the current ASP.NET Core
overview describes a different, cross-platform framework. The site's own Web Forms pages explain the model in detail, and the Faces
xref:web/jsf/request-processing-lifecycle.adoc#web-forms[lifecycle] page of this section compares its six phases with the Web Forms page lifecycle.

Source: https://learn.microsoft.com/en-us/aspnet/core/overview[ASP.NET Core overview]

[#books-outdated]
== Where the Older Books Are Outdated

The Faces books published between 2004 and 2015 are useful for the concepts in this page (the architecture, the patterns, the
lifecycle), and they are listed in the section bibliography. Their code and a few statements are out of date.

* They use JSP views, JSP tag handlers and TLDs. Facelets has been the standard view technology since 2.0, and JSP support was removed in 4.0.
* They use the `+javax.faces+` package and the `+http://java.sun.com/jsf/*+` and `+http://xmlns.jcp.org/jsf/*+` namespaces. The current names are
  `+jakarta.faces+` and the `+jakarta.faces.html+`, `+jakarta.faces.core+` URNs; support for the old namespaces is planned to be removed in 5.0.
* They use `+@ManagedBean+`, which was removed in 4.0. Use CDI `+@Named+` beans.
* They treat Struts 1 integration and Struts-to-Faces conversion as a main topic. Struts 1 has reached end of life.
* They describe an ecosystem of libraries (RichFaces, Tomahawk, Trinidad, Seam 2) that has ended; use PrimeFaces, OmniFaces and Jakarta Security instead.
* They describe JSR 127 to JSR 314 as the state of the art. The history above runs to Faces 4.1, and the specification, not the books, is
  authoritative wherever the two differ.
