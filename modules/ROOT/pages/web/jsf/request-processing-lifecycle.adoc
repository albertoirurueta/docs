include::partial$jsf-disclaimer.adoc[]

The lifecycle is the single most useful idea to understand in Jakarta Faces. Almost every question of the form "why is my
action method not called", "why does my bean still hold the old value", "why does the cancel button complain about
required fields" or "why does this listener run twice" is answered by knowing in which of six phases a piece of code
runs and which events can skip the phases after it. This page is written against Jakarta Faces 4.1 (API
`jakarta.faces-api` 4.1.2, Jakarta EE 11, Java 17 or later), Eclipse Mojarra 4.1.17 and Apache MyFaces Core 4.1.4. Faces
4.0 (Jakarta EE 10, Java 11 or later) has the same six phases and the same rules, and the differences that matter for
this page are listed in <<versions>>. Faces 5.0 (Jakarta EE 12, Java 21 or later) is still an upcoming release (the
latest milestone is `5.0.0-M9`), so nothing here describes it as current behaviour. The examples were compiled and run
in a scratch Maven WAR on Mojarra 4.1.17, Weld 6.0.4 and Tomcat 11.0.26 with Java 21 as the compiler release, and the
phase traces shown below are the real output of that run. The running scenario is the original _Bookshelf_ -- a
catalogue of books, authors and reviews -- and this page uses its review form.

[#overview]
== The Lifecycle at a Glance

Every request that reaches the `FacesServlet` runs through a `jakarta.faces.lifecycle.Lifecycle`. The specification
describes the lifecycle as two calls: `execute()` runs every phase up to, but not including, Render Response, and
`render()` runs Render Response. The six standard phases, in order, are:

[cols="1,2,3,3"]
|===
| # | Phase | What the implementation does | Typical code that runs there

| 1 | Restore View | Builds the component tree for the request: a new view for an initial request, the saved view for a postback. | System events such as `PostAddToViewEvent` and `PostRestoreStateEvent`; no user input is available yet
| 2 | Apply Request Values | Every component decodes the submitted request parameters into a _submitted value_ (and, for components with `immediate="true"`, converts and validates it). | `Renderer.decode()`, immediate converters, validators and value-change listeners, immediate action listeners
| 3 | Process Validations | Every non-immediate input converts its submitted value into a _local value_, runs its validators and queues messages. | Converters, validators, Bean Validation, `ValueChangeListener`
| 4 | Update Model Values | Valid local values are written to the bean properties named by the `value` attributes. | Bean setters
| 5 | Invoke Application | Action events are delivered: action listeners and the action method run and navigation is decided. | `action`, `actionListener`, `f:ajax listener`, `f:viewAction`
| 6 | Render Response | The view is built or completed, rendered to the response and its state is saved. | Getters, `PreRenderViewEvent`, `encodeBegin()` and the other encode methods, state saving
|===

image::jsf-lifecycle.svg["The six lifecycle phases of a postback, the dashed initial-request shortcut, the red failure and renderResponse shortcut to Render Response and the orange responseComplete exit",width=1000]

Two things in the figure are worth fixing in the mind early. The straight arrows are the only path that a successful,
non-immediate postback takes. And every other path is a *shortcut forward*: the lifecycle never goes back to an
earlier phase. A shortcut either jumps to Render Response (a request that failed validation, a request that asked for
`renderResponse()`, an initial request) or ends the lifecycle without rendering (`responseComplete()`).

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-intro/faces-intro.html#_the_lifecycle_of_a_jakarta_faces_application[Jakarta EE Tutorial: The Lifecycle of a Jakarta Faces Application] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a401[Jakarta Faces 4.1: 2.2 Standard Request Processing Lifecycle Phases]

[#access]
=== Reaching the Lifecycle from Code

Application code seldom needs the `Lifecycle` object, but two paths lead to it. Inside a request, `FacesContext.getLifecycle()`
(since Faces 4.0) returns the instance that is processing it, and throws an `IllegalStateException` once the context has been
released. Outside a request, for example in a `ServletContextListener` that registers a listener at startup, the instance
comes from the factory: `FactoryFinder.getFactory(FactoryFinder.LIFECYCLE_FACTORY)` returns the `LifecycleFactory`, whose
`getLifecycle(LifecycleFactory.DEFAULT_LIFECYCLE)` returns the default instance (`getLifecycleIds()` lists the ids, and the
`jakarta.faces.LIFECYCLE_ID` init parameter of the `FacesServlet`, or the context parameter of the same name, selects another
one). The same instance serves every request of the web application, which is why a `PhaseListener` added to it must be
thread safe.

.LifecycleAccess.java -- the two paths to the Lifecycle
[source,java]
----
package org.example.bookshelf;

import jakarta.faces.FactoryFinder;
import jakarta.faces.context.FacesContext;
import jakarta.faces.event.PhaseListener;
import jakarta.faces.lifecycle.Lifecycle;
import jakarta.faces.lifecycle.LifecycleFactory;

public final class LifecycleAccess {

    private LifecycleAccess() {
    }

    /** Inside a request: the lifecycle that is running now (Faces 4.0 and later). */
    public static PhaseListener[] listenersOfCurrentRequest() {
        Lifecycle lifecycle = FacesContext.getCurrentInstance().getLifecycle();
        return lifecycle.getPhaseListeners();
    }

    /** Outside a request, for example from a ServletContextListener at startup. */
    public static void register(PhaseListener listener) {
        LifecycleFactory factory =
                (LifecycleFactory) FactoryFinder.getFactory(FactoryFinder.LIFECYCLE_FACTORY);
        Lifecycle lifecycle = factory.getLifecycle(LifecycleFactory.DEFAULT_LIFECYCLE);
        lifecycle.addPhaseListener(listener);
    }
}
----

The class was compiled against the 4.1.2 API but, unlike the traces of this page, was not run.

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/context/FacesContext.html[API: FacesContext.getLifecycle()], https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/lifecycle/LifecycleFactory.html[API: LifecycleFactory] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6088[specification 11.1.3: jakarta.faces.LIFECYCLE_ID]

[#initial-vs-postback]
== Initial Requests and Postbacks

The Jakarta EE Tutorial distinguishes two kinds of requests that the lifecycle handles. An *initial request* is a
user's first request for a page, for example following a link or typing the address. A *postback* is the submission of
a form on a page that an earlier response had delivered to the browser. The tutorial's summary is that an initial
request executes only Restore View and Render Response, because there is no user input to process, while a postback
executes all the phases.

The specification gives the precise test. During Restore View the implementation finds the render kit for the request,
asks that render kit's `ResponseStateManager.isPostback()` whether the request is a postback, and, if the servlet
container is displaying an error page, never treats the request as a postback. For the default HTML render kit a
request is a postback when it carries the hidden `jakarta.faces.ViewState` field (it is rendered into every
`h:form`). Application code asks the same question with `FacesContext.isPostback()`, which the phase listener below
logs.

For an initial request the specification adds a detail that matters for bookmarkable pages. After the empty view is
created, the implementation looks for view metadata. If the view has none, `renderResponse()` is called and the
lifecycle jumps to Render Response, which is the "only phases 1 and 6" case. If the view declares `f:metadata`, the
lifecycle continues through all six phases, so that `f:viewParam` can convert, validate and set its parameters and
`f:viewAction` can run, and that happens although `FacesContext.isPostback()` is `false`. The _Bookshelf_ detail page
is such a page.

.A bookmarkable Bookshelf detail page: an initial request that runs all six phases
[source,xml]
----
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core">
<f:metadata>
  <f:viewParam name="isbn" value="#{bookBean.isbn}" required="true"/>
  <f:viewAction action="#{bookBean.load}"/>
</f:metadata>
<h:head><title>Book</title></h:head>
<h:body>
  <h1>#{bookBean.title}</h1>
</h:body>
</html>
----

.The request-scoped bean behind it

package org.example.bookshelf.web;

import java.util.logging.Logger;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Named;

@Named
@RequestScoped
public class BookBean {
    private static final Logger LOG = Logger.getLogger(BookBean.class.getName());

    private String title;

    public String getIsbn() { return isbn; }
    public void setIsbn(String isbn) { this.isbn = isbn; }
    public String getTitle() { return title; }

    public void load() {

[#phases]
== The Six Phases in Detail

The specification fixes what each phase must do. The sections below list the entry points that matter to application
code, the events that are delivered at the end of the phase, and the ways the phase can send the request to Render
Response early. At the end of phases 2, 3, 4 and 5 the `UIViewRoot` broadcasts the events that components and
validators queued during the phase to their listeners; the specification calls this common event processing.

[#restore-view]
=== Phase 1: Restore View

* The implementation calls `ViewHandler.initView()` first, which sets the character encoding for the request.
* It derives the view id from the request path, and decides whether the request is a postback (see above).
* For a postback it calls `ViewHandler.restoreView()`, with `FacesContext.setProcessingEvents(false)` around it so that
  system events are not published while the tree is rebuilt. If no view comes back the implementation throws a
  `ViewExpiredException`. That is the exception a user sees after a session expired or after the server dropped the
  saved state; the xref:web/jsf/exception-handling.adoc#view-expired[exception handling] page shows how to turn it into a friendly redirect.
* For an initial request it creates a new view (`ViewHandler.createView()`), and uses the view metadata rule from the
  previous section to decide whether to call `renderResponse()`.
* If the view is declared as a protected view, a view-protection check runs, which requires a token on
  non-postback requests and compares `Referer` and `Origin` headers. This is part of why a protected view cannot be
  reached from just any link.
* The implementation publishes `PostAddToViewEvent` for a newly created view and `PostRestoreStateEvent` for every
  node of a restored tree.

What this means in practice: when your code runs in Restore View, the tree exists but no submitted value has been
applied to it, so do not read user input here. A `@ViewScoped` bean is created the first time an expression refers to
it, which for a new view is while it is rendered in phase 6; later postbacks of the same view find the same instance.

[#apply-request-values]
=== Phase 2: Apply Request Values

`UIViewRoot.processDecodes()` walks the tree and calls `processDecodes()` on each component. For an `UIInput` the
renderer's `decode()` reads the request parameter and stores it as the component's _submitted value_. The submitted
value is a raw `String`: it has not been converted, validated or copied to the bean.

Components that are activated record it here. A `UICommand` whose button or link was the cause of the request queues
an `ActionEvent`. Whether the event is delivered at the end of this phase or at the end of Invoke Application depends
on the component's `immediate` property, which is the subject of <<immediate>>.

This phase is also where a component can bring conversion and validation forward. An input component with
`immediate="true"` converts and validates in `processDecodes()`, queues its `ValueChangeEvent` here and, if it is
invalid afterwards, calls `FacesContext.renderResponse()`.

If a `decode()` method or an event listener calls `responseComplete()`, the lifecycle ends after the phase. If it
calls `renderResponse()`, the lifecycle jumps to Render Response. Otherwise it continues to Process Validations.

[#process-validations]
=== Phase 3: Process Validations

`UIViewRoot.processValidators()` calls `processValidators()` on each component. `UIInput.processValidators()` calls
`validate()` unless the component is immediate, and `validate()` implements the algorithm below, which is worth
knowing by heart because it explains most messages that appear on a page:

. Take the submitted value. If it is `null` (no parameter was submitted for the component) validation is skipped,
  except that a `required` input is still validated when the context parameter named by
  `UIInput.ALWAYS_PERFORM_VALIDATION_WHEN_REQUIRED_IS_TRUE` is true. If the context parameter
  `jakarta.faces.INTERPRET_EMPTY_STRING_SUBMITTED_VALUES_AS_NULL` is true, an empty submitted string is treated as
  `null` from here on.
. Convert the submitted value to the type the component needs. The implementation uses the converter attached to the
  component, or, failing that, a converter registered for the type of the `value` expression. A `ConverterException`
  queues a message with `FacesContext.addMessage()` and marks the component invalid.
. Run the validation: first the `required` check (an empty value fails it), then every attached validator, which
  includes the default validator that applies the Bean Validation constraints of the bound property when Bean Validation
  is available. A validator that throws `ValidatorException` queues its
  messages and marks the component invalid.
. If the component is still valid, store the converted value as the component's _local value_, clear the submitted
  value, and, if the local value differs from the previous value, queue a `ValueChangeEvent`.

Messages queued in this phase are displayed by `h:messages` and `h:message` during Render Response. An input
that is invalid after `validate()` calls `FacesContext.renderResponse()`. That call is the mechanism behind the most
important short-circuit of the lifecycle and has its own section (<<short-circuits>>). The implementation also sets the
flag that `FacesContext.validationFailed()` records and `FacesContext.isValidationFailed()` reads, which is why the phase
listener below prints `validationFailed=true` after a failed phase 3.

[#update-model-values]
=== Phase 4: Update Model Values

If this phase is reached, the specification says that the request is assumed to be syntactically and semantically
valid. `UIViewRoot.processUpdates()` calls `processUpdates()` on each component and `UIInput.updateModel()` writes the
local value to the target of the `value` expression, and then clears the local value. `updateModel()` does nothing for
a component that is invalid, that has no local value, or that has no `value` expression. Only bean properties named by
`value` attributes are written; nothing else on the bean changes.

If the setter throws an exception the implementation queues an error message, hands an `UpdateModelException` to the
`ExceptionHandler`, marks the component invalid, and does not rethrow, so that the other components are still
processed. An invalid component after `processUpdates()` again calls `renderResponse()`. This is how a setter that
rejects a value (a business rule in a setter, or a type problem that a converter did not catch) ends up showing a
message and skipping Invoke Application.

[#invoke-application]
=== Phase 5: Invoke Application

`UIViewRoot.processApplication()` broadcasts the events queued for this phase. That is where `ActionEvent`s of
non-immediate commands are delivered to the registered listeners and to the default `ActionListener`, which calls the
action method, passes its outcome to the `NavigationHandler` (see xref:web/jsf/navigation.adoc#lifecycle-position[navigation]), and so decides which view is rendered next. It is also
where the listener of an `f:ajax` behaviour runs (when the behaviour is not immediate) and where an `f:viewAction`
runs by default.

The specification requires the default `ActionListener` to call `FacesContext.renderResponse()` as its first step, so
that the lifecycle moves on to Render Response once the action has returned, whichever outcome it returned. That is the
reason a `PhaseListener` trace of a successful postback shows `renderResponse=true` after Invoke Application.

[#render-response]
=== Phase 6: Render Response

Render Response is called as `Lifecycle.render()`. For a Facelets view the implementation calls the
`ViewDeclarationLanguage.buildView()` method, so that the component tree is populated from the XHTML, and publishes
`PreRenderViewEvent`. It then renders the tree depth first: each component's `encodeBegin()`, `encodeChildren()` and
`encodeEnd()` (or the renderer's equivalents) are called, and a component whose `rendered` property is `false`
produces no markup and none of its children are rendered. Rendering resolves the value expressions of output
components, which is when getters run. After the markup is written the implementation publishes `PostRenderViewEvent`
and saves the view's state so that the next postback can restore it.

If this phase renders the page again after a failed postback, the inputs show the _submitted values_ of the failed
request, not the (unchanged) bean properties: the user sees what they typed, next to the queued messages. That detail
is what lets a form re-display invalid input. The tutorial's summary of the phase says the same thing: if errors were
found in phases 2, 3 or 4 on a postback, the original page is rendered again, with `h:message` and `h:messages`
showing the queued messages.

== A Complete Example: The Bookshelf Review Form

The example below is used for the rest of the page. It is a review form with a required reviewer name, a rating
validated by `f:validateLongRange`, and three buttons: Save, a Cancel button that uses `immediate` correctly, and a
Clear button that does not need `immediate` at all.

.review.xhtml: the Bookshelf review form
[source,xml]
----
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:f="jakarta.faces.core">
<h:head><title>Review a book</title></h:head>
<h:body>
  <h1>Review a book</h1>
  <h:form id="review">
    <h:messages id="msgs"/>

    <h:outputLabel for="reviewer" value="Your name"/>
    <h:inputText id="reviewer" value="#{reviewBean.reviewer}" required="true"/>

    <h:outputLabel for="rating" value="Rating (1-5)"/>
    <h:inputText id="rating" value="#{reviewBean.rating}">
      <f:validateLongRange minimum="1" maximum="5"/>
    </h:inputText>

    <h:outputLabel for="comment" value="Comment"/>
    <h:inputTextarea id="comment" value="#{reviewBean.comment}">
      <f:validateLength maximum="500"/>
    </h:inputTextarea>

    <h:commandButton id="save" value="Save review" action="#{reviewBean.submit}"/>

    <!-- Runs in Apply Request Values; skips validation and the model update -->
    <h:commandButton id="cancel" value="Cancel" action="#{reviewBean.cancel}" immediate="true"/>

    <!-- Execute only the button, then re-render the form with reset inputs -->
    <h:commandButton id="clear" value="Clear">
      <f:ajax execute="@this" listener="#{reviewBean.clear}" render="@form" resetValues="true"/>
    </h:commandButton>
  </h:form>
</h:body>
</html>
----

.ReviewBean: a view-scoped backing bean
[source,java]
----
package org.example.bookshelf.web;

import java.io.Serializable;
import java.util.logging.Logger;

import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Named;

@Named
@ViewScoped
public class ReviewBean implements Serializable {

    private static final long serialVersionUID = 1L;
    private static final Logger LOG = Logger.getLogger(ReviewBean.class.getName());

    private String reviewer;
    private Integer rating;
    private String comment;

    public String getReviewer() { return reviewer; }
    public void setReviewer(String reviewer) { LOG.info("  model: setReviewer(" + reviewer + ")"); this.reviewer = reviewer; }

    public Integer getRating() { return rating; }
    public void setRating(Integer rating) { LOG.info("  model: setRating(" + rating + ")"); this.rating = rating; }

    public String getComment() { return comment; }
    public void setComment(String comment) { LOG.info("  model: setComment(" + comment + ")"); this.comment = comment; }

    /** Application logic: Invoke Application, only if every earlier phase succeeded. */
    public String submit() {
        LOG.info("  action: submit() by " + reviewer + " rating " + rating);
        FacesContext.getCurrentInstance().addMessage(null,
                new FacesMessage(FacesMessage.SEVERITY_INFO, "Thanks, " + reviewer + "!", null));
        return null; // stay on the same view
    }

    /** The Cancel button: the model has NOT been updated when this runs. */
    public String cancel() {
        LOG.info("  action: cancel() reviewer=" + reviewer);
        return "catalogue?faces-redirect=true";
    }

    /** The Ajax Clear button: only the button is executed, so no input is decoded or validated. */
    public void clear() {
        LOG.info("  listener: clear()");
        reviewer = null;
        rating = null;
        comment = null;
    }
}
----

    C -- "no" --> R["Restore View, then Render Response"]
    C -- "yes" --> F["All six phases, view parameters and view actions"]
    B -- "yes" --> D["Restore View, Apply Request Values"]
    D --> E{"Immediate command activated?"}
    E -- "yes" --> R2["Its action runs, then Render Response"]
    E -- "no" --> V["Process Validations"]
    V --> W{"Any conversion or validation error?"}
    W -- "yes" --> R3["Render Response with messages"]
    W -- "no" --> U["Update Model Values, Invoke Application"]
    U --> X{"responseComplete called?"}
    X -- "yes" --> Z["Lifecycle ends, no rendering"]
    X -- "no" --> R4["Render Response"]
....

[#short-circuits]
== Short-Circuiting the Lifecycle

The lifecycle changes its route through two methods on `FacesContext`, and every shortcut in the figure is one of
them being called.

[cols="2,3,3"]
|===
| Method | Effect | Who calls it

| `renderResponse()` | As soon as the current phase has completed, control passes to Render Response and the phases in between are skipped. | A component after a conversion, validation or update error; the default `ActionListener`; the implementation for an initial request without view metadata; your code in a listener
| `responseComplete()` | The HTTP response has already been generated (for example a redirect or a file) and the lifecycle ends as soon as the current phase has completed: nothing is rendered. | Your code, after writing the response itself
| `validationFailed()` | Sets the flag read by `isValidationFailed()`. It does not change the route by itself; it records that a conversion or validation error occurred while processing the inputs (form inputs or view parameters). | The implementation, when a conversion or validation error is found
|===

=== Conversion and validation failures

When any input in the form is invalid, the lifecycle never reaches Update Model Values and never reaches Invoke
Application. Each `UIInput` calls `renderResponse()` when it is invalid after validation, so the next phase is Render
Response. The page is rendered again, from the same component tree, showing the submitted values and the queued
messages. The bean has not been touched, so no property holds a half-validated value, and the action method has not
run, so it never has to check that its inputs are valid. That is the contract that makes Faces action methods short:
if the method is running, the inputs were valid.

A reviewer who submits an empty name and a rating of 9 (both invalid) produces:

[source,text]
----
BEFORE RESTORE_VIEW         postback=true partial=false
AFTER  RESTORE_VIEW         validationFailed=false renderResponse=false responseComplete=false
BEFORE APPLY_REQUEST_VALUES postback=true partial=false
AFTER  APPLY_REQUEST_VALUES validationFailed=false renderResponse=false responseComplete=false
BEFORE PROCESS_VALIDATIONS  postback=true partial=false
AFTER  PROCESS_VALIDATIONS  validationFailed=true renderResponse=true responseComplete=false
BEFORE RENDER_RESPONSE      postback=true partial=false
AFTER  RENDER_RESPONSE      validationFailed=true renderResponse=true responseComplete=false
----

No `setReviewer()` and no `submit()` lines appear. Submitting `abc` as the rating, a *conversion* failure, gives an
identical trace: the `Integer` converter fails during phase 3 (`validate()` converts before it validates), the message
is queued, the component is marked invalid, and the lifecycle jumps to phase 6. The text of the messages depends on the
locale and on the implementation's bundle, so it is not reproduced here; the xref:web/jsf/messages-and-i18n.adoc#message-bundle[messages and i18n] page shows how to
replace it.

Three consequences are worth remembering:

* When an action method "is not called", look at the page for a message first. A validation error on a field the user
  cannot see (a hidden field, a field inside a collapsed panel that is still in the tree, a `required` input that was
  not filled) skips the action silently if there is no `h:messages` on the page.
* A conversion failure and a validation failure are the same path. Both stop before phase 4.
* On the re-rendered page an input that holds a submitted value shows what the user typed, not the bean's value, so
  the user never loses input to a failed validation.

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-intro/faces-intro.html#_process_validations_phase[Jakarta EE Tutorial: Process Validations Phase] and https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/context/FacesContext.html[API: FacesContext]

=== renderResponse()

Call `FacesContext.renderResponse()` when a listener has decided that the rest of the form must not be processed but
the same page (or the target of a navigation) must be rendered. The lifecycle then skips straight to Render Response.
The typical use is a value-change or system-event listener that rebuilds part of the view. The method is a request, not
an immediate jump: the current phase finishes first, which is why an event listener can call it and still let the other
listeners of the same event run. `FacesContext.getRenderResponse()` reports whether it has been called.

=== responseComplete()

Call `FacesContext.responseComplete()` after writing the response yourself. The specification lists three cases: a
redirect, a response generated by another technology, and a response that is just the bytes of a resource. The
_Bookshelf_ catalogue offers the most common one, a download. The bean below writes a CSV file and tells Faces that
there is nothing to render.

.catalogue.xhtml: a page with an export button
[source,xml]

      xmlns:h="jakarta.faces.html"
      xmlns:ui="jakarta.faces.facelets">
<h:head><title>Catalogue</title></h:head>
<h:body>
  <h1>Catalogue</h1>
  <ul>
    <ui:repeat value="#{catalogueBean.books}" var="b">
      <li>#{b[0]} by #{b[1]}</li>
    </ui:repeat>
  </ul>
  <h:form id="export">
    <h:commandButton id="csv" value="Export CSV" action="#{catalogueBean.exportCsv}"/>
  </h:form>

</h:body>
</html>
----

.CatalogueBean: writes the response and calls responseComplete()
[source,java]
----
package org.example.bookshelf.web;

import java.io.IOException;
import java.io.Writer;
import java.nio.charset.StandardCharsets;
import java.util.List;

import jakarta.enterprise.context.RequestScoped;
import jakarta.faces.context.ExternalContext;
import jakarta.faces.context.FacesContext;
import jakarta.inject.Inject;
import jakarta.inject.Named;

@Named
@RequestScoped
public class CatalogueBean {

    private static final List<String[]> BOOKS = List.of(
            new String[] {"Dune", "Frank Herbert"},
            new String[] {"Neuromancer", "William Gibson"});

    @Inject
    private FacesContext facesContext;

    public List<String[]> getBooks() { return BOOKS; }

    /** Writes the response itself, so the lifecycle must not render a view afterwards. */
    public void exportCsv() throws IOException {
        ExternalContext ec = facesContext.getExternalContext();
        ec.responseReset();
        ec.setResponseContentType("text/csv");
        ec.setResponseCharacterEncoding(StandardCharsets.UTF_8.name());
        ec.setResponseHeader("Content-Disposition", "attachment; filename=\"catalogue.csv\"");
        Writer out = ec.getResponseOutputWriter();
        out.write("title,author\n");
        for (String[] book : BOOKS) {
            out.write(book[0] + "," + book[1] + "\n");
        }
        out.flush();
        facesContext.responseComplete(); // skip Render Response
    }
}
----

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a401[Jakarta Faces 4.1: 2 Request Processing Lifecycle] (section 2.1.3, Faces Request Generates Non-Faces Response) and https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/context/ExternalContext.html[API: ExternalContext]

Clicking the button returns `text/csv;charset=UTF-8` with the two catalogue rows, and the trace ends after Invoke
Application, with no Render Response phase at all (the export data here is the fixed catalogue; an export of
user-supplied text would need the escaping rules for spreadsheet formulas that the xref:web/jsf/file-upload-and-download.adoc#csv-injection[file download] page of this section
discusses):

[source,text]
----
BEFORE INVOKE_APPLICATION   postback=true partial=false
AFTER  INVOKE_APPLICATION   validationFailed=false renderResponse=true responseComplete=true
----

Forgetting `responseComplete()` after writing a response is the classic mistake here. When the call was removed in the
scratch run, the response was still `text/csv`, the two CSV rows were followed by the HTML of the catalogue page in the
same body, and Mojarra logged a warning that it was skipping an attempt to set the buffer size on a committed response:
Faces carried on to Render Response and wrote the view after the bytes you had already sent. A redirect produced
with a navigation outcome such as `catalogue?faces-redirect=true` (used by the Cancel button above) makes the
implementation call `responseComplete()` for you, which is why the Cancel trace in the next section ends after phase 2.

[#immediate]
== The immediate Attribute

`immediate` exists on input components (`h:inputText` and the other `UIInput` components, through
`EditableValueHolder`), on command components (`h:commandButton`, `h:commandLink`, through `ActionSource`), on the
`f:ajax` behaviour and on `f:viewAction`. It has one meaning: _do the processing that normally comes later in the
lifecycle now, at the end of Apply Request Values._ It does not skip validation. The MyFaces documentation puts it
plainly: many developers think that `immediate` skips the Process Validations phase, but it only makes the component
be processed in Apply Request Values.

[cols="2,4"]
|===
| Where | What changes

| Input (`UIInput`) | Conversion, validation and the `ValueChangeEvent` happen in phase 2, before any non-immediate input is validated. If it is invalid, `renderResponse()` is called, so the messages of the non-immediate inputs never appear. The model is still updated in phase 4, like any other input.
| Command (`UICommand`) | The `ActionEvent` is delivered at the end of phase 2, so the action listeners and the action method run before phases 3 and 4. The default `ActionListener` then calls `renderResponse()`, so phases 3, 4 and 5 are skipped for the whole form.
| `f:ajax` | `immediate="true"` broadcasts the behaviour's events in Apply Request Values instead of Invoke Application.
| `f:viewAction` | `immediate="true"` delivers the action in Apply Request Values rather than waiting; its `phase` attribute can name `APPLY_REQUEST_VALUES`, `PROCESS_VALIDATIONS`, `UPDATE_MODEL_VALUES` or `INVOKE_APPLICATION` (the default).
|===

The consequence people miss is the one in the second row. While an immediate command's action runs, the non-immediate
inputs of the form have a submitted value but no local value, and the bean has not been updated. Whatever the action
does, it cannot read the user's other input from the model. The tutorial spells out the combinations: if the button
and an input are both immediate, the input's new value is converted, validated and available to the button's
processing, because both are handled while the request parameters are applied; if only the button is immediate, the
event is processed without the input's value reaching the model.

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-page/faces-page.html#_the_immediate_attribute[Jakarta EE Tutorial: The immediate Attribute], https://jakarta.ee/specifications/faces/4.1/vdldoc/f/ajax.html[Faces 4.1 VDL: f:ajax] and https://jakarta.ee/specifications/faces/4.1/vdldoc/f/viewAction.html[Faces 4.1 VDL: f:viewAction]

=== A Cancel button done correctly

A Cancel button is the use for which `immediate` was designed: the user wants to leave the page, any validation
errors in the half-filled form are irrelevant, and the typed data is to be thrown away. The correct form combines
`immediate="true"` with an action that *navigates away*, and does not read the form's data:

[source,xml]
----
<h:commandButton id="cancel" value="Cancel" action="#{reviewBean.cancel}" immediate="true"/>
----

[source,java]
----
/** The Cancel button: the model has NOT been updated when this runs. */
public String cancel() {
    LOG.info("  action: cancel() reviewer=" + reviewer);
    return "catalogue?faces-redirect=true";
}
----

Source: https://myfaces.apache.org/#/coreConceptsImmediateAttribute[Apache MyFaces: Immediate Attribute]

Clicking Cancel with an empty required name and a rating of 9 produced a `302` redirect to the catalogue and this trace.
The action ran at the end of phase 2 and saw `reviewer=null`, because Update Model Values never ran, and the
redirect completed the response, so there is no Render Response either:

[source,text]
----
BEFORE RESTORE_VIEW         postback=true partial=false
AFTER  RESTORE_VIEW         validationFailed=false renderResponse=false responseComplete=false
BEFORE APPLY_REQUEST_VALUES postback=true partial=false
  action: cancel() reviewer=null
AFTER  APPLY_REQUEST_VALUES validationFailed=false renderResponse=true responseComplete=true
----

When the action returns a view id without `faces-redirect=true`, or returns `null`, the lifecycle also jumps to Render
Response and the target view (or the same view with the _submitted_ values of its non-immediate inputs) is rendered
in the same response. The MyFaces concept page, which describes the behaviour in older terms, says that a `null` outcome lets processing
continue as normal; the 4.1 specification describes a default `ActionListener` that always calls `renderResponse()`, and
Mojarra 4.1.17 behaves that way in the scratch run, so do not rely on a `null` outcome of an immediate command
continuing to Process Validations. If the only purpose of the control is to navigate, `h:button` or `h:link` with an
`outcome` does it with a plain GET and no lifecycle for the form at all.

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a401[Jakarta Faces 4.1: 2.2 Standard Request Processing Lifecycle Phases] and https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-page/faces-page.html#_the_immediate_attribute[Jakarta EE Tutorial: The immediate Attribute]

=== Better than immediate: execute only what you need

Most uses of `immediate` that go beyond the two above are attempts to say "process only this part of the form". Since
Faces 2.0 there is a direct way to say that with Ajax: the `execute` attribute of `f:ajax` names the components that
take part in the execute phases, and `@this` (the default) names only the component that fired the request. The Clear
button of the review form uses it. The request carries the whole form, but only the button is decoded, validated and
updated, so there is no validation to skip and no `immediate` to reason about; `resetValues="true"` then resets the
inputs listed in `render` (the `UIViewRoot.resetValues()` method) so that the form shows empty fields instead of the
previously submitted values.

[source,xml]
----
<h:commandButton id="clear" value="Clear">
  <f:ajax execute="@this" listener="#{reviewBean.clear}" render="@form" resetValues="true"/>
</h:commandButton>
----

Source: https://jakarta.ee/specifications/faces/4.1/vdldoc/f/ajax.html[Faces 4.1 VDL: f:ajax] and https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/component/UIViewRoot.html[API: UIViewRoot]

The scratch run returned a partial response with the form re-rendered and both inputs empty, and the trace shows all six
phases with `partial=true`: the five execute phases ran for the button only, and `clear()` ran in Invoke Application.

[#phase-listener]
== PhaseListener

A `jakarta.faces.event.PhaseListener` is told before and after each phase. It is the supported way to observe or
influence the lifecycle from outside the components: logging, timing, a security gate, request-wide setup and tear-down.
The interface has three methods. `getPhaseId()` returns the `PhaseId` the listener wants (`RESTORE_VIEW`,
`APPLY_REQUEST_VALUES`, `PROCESS_VALIDATIONS`, `UPDATE_MODEL_VALUES`, `INVOKE_APPLICATION`, `RENDER_RESPONSE`, or
`ANY_PHASE` for all of them). `beforePhase(PhaseEvent)` and `afterPhase(PhaseEvent)` are called around the phase; in
the 4.1 API both are `default` methods, so a listener overrides only the one it needs. The `PhaseEvent` carries the
`FacesContext` and the `PhaseId`.

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/event/PhaseListener.html[API: PhaseListener]

The rules that the specification sets for listeners are precise and worth knowing:

* For each phase, the implementation selects the listeners whose `getPhaseId()` is that phase or `ANY_PHASE`. It calls
  every `beforePhase()` in the order the listeners were registered, then runs the phase, then calls every
  `afterPhase()` in the _reverse_ order.
* If a `beforePhase()` listener called `renderResponse()` or `responseComplete()`, the phase itself is not executed
  (but `afterPhase()` still is). The scratch run confirmed it on Mojarra: a throwaway listener that called
  `renderResponse()` before Process Validations made an invalid rating of 9 pass unchecked, and the trace shows
  `validationFailed=false`. Treat it as a power tool: it skips the work of the phase.
* If `beforePhase()` was called on a listener, its `afterPhase()` is guaranteed to be called, even if the phase threw.
  An exception thrown by a listener is published to the `ExceptionHandler` and the `afterPhase()` of the listeners
  whose `beforePhase()` had not run is skipped.
* Listeners must be thread-safe. One instance serves every request, so per-request data belongs in the
  `FacesContext` (its attribute map), not in fields.
* A listener may call `renderResponse()` or `responseComplete()` itself, the same two methods as any other code.

.LoggingPhaseListener: logs every phase, keeps no state in fields
[source,java]
----
package org.example.bookshelf.web;

import java.util.logging.Logger;

import jakarta.faces.context.FacesContext;
import jakarta.faces.event.PhaseEvent;
import jakarta.faces.event.PhaseId;
import jakarta.faces.event.PhaseListener;

public class LoggingPhaseListener implements PhaseListener {

    private static final long serialVersionUID = 1L;
    private static final Logger LOG = Logger.getLogger(LoggingPhaseListener.class.getName());

    @Override
    public PhaseId getPhaseId() {
        return PhaseId.ANY_PHASE;
    }

    @Override
    public void beforePhase(PhaseEvent event) {
        FacesContext context = event.getFacesContext();
        LOG.info(() -> "BEFORE %-20s postback=%b partial=%b".formatted(
                event.getPhaseId().getName(),
                context.isPostback(),
                context.getPartialViewContext().isPartialRequest()));
    }

    @Override
    public void afterPhase(PhaseEvent event) {
        FacesContext context = event.getFacesContext();
        LOG.info(() -> "AFTER  %-20s validationFailed=%b renderResponse=%b responseComplete=%b".formatted(
                event.getPhaseId().getName(),
                context.isValidationFailed(),
                context.getRenderResponse(),
                context.getResponseComplete()));
    }
}
----

              xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-facesconfig_4_1.xsd"

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6635[Jakarta Faces 4.1: 12.3 PhaseListener] and https://jakarta.ee/xml/ns/jakartaee/web-facesconfig_4_1.xsd[web-facesconfig_4_1.xsd]

Every trace on this page was produced by this listener. There are three ways to attach a `PhaseListener`:

* In `faces-config.xml`, as above: application-wide, every request. The specification names this the `phase-listener`
  element of the application configuration resources.
* Per view, with `f:phaseListener`, which registers a `PhaseListener` on the `UIViewRoot` it is nested in. It takes a
  `type` attribute (a class name) or a `binding` attribute (an expression evaluating to a listener).
* Programmatically with `Lifecycle.addPhaseListener()` on the lifecycle obtained from the `LifecycleFactory` (see <<access>>; the
  specification shows `FactoryFinder.getFactory(FactoryFinder.LIFECYCLE_FACTORY)`). Duplicate registrations should be
  prevented and logged by the implementation.

Two classes of the 4.1 API itself are phase listeners (`ELResolverInitPhaseListener` and
`HttpMethodRestrictionsPhaseListener`), which suggests the intended use: infrastructure that has to
act at a precise point of every request. For application work, prefer the narrower tools when they fit: a system
event listener for "when this component is added", a `f:viewAction` for "before this view renders", an
`ExceptionHandler` for errors. A `PhaseListener` is the right tool when the thing you want to observe is the phase
boundary itself.

Source: https://jakarta.ee/specifications/faces/4.1/vdldoc/f/phaseListener.html[Faces 4.1 VDL: f:phaseListener] and https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/lifecycle/Lifecycle.html[API: Lifecycle]

[#partial]
== The Partial (Ajax) Lifecycle

An Ajax request goes through the same six phases. What changes is how much of the tree each phase visits. The tutorial's
section "Partial Processing and Partial Rendering" and the "Ajax Request Lifecycle" section of the Ajax chapter describe
it this way: the state of an Ajax request is captured by the `PartialViewContext`, which says which components are
targeted for processing and for rendering, and `PartialViewContext.processPartial(PhaseId)` does the partial tree
traversal for each phase.

* *Detection.* The JavaScript API sends the request with the header `Faces-Request: partial/ajax` and the parameters
  `jakarta.faces.partial.ajax=true`, `jakarta.faces.source` (the id of the element that triggered the request) and
  `jakarta.faces.ViewState`. `PartialViewContext.isPartialRequest()` is true for such a request, and each phase checks
  it before deciding between full and partial processing.
* *Execute.* In phases 2, 3 and 4 the implementation calls `processPartial()` for the ids in the `execute` list instead
  of walking the whole tree, so only those components (and their descendants) decode, convert, validate and update.
  `f:ajax` defaults `execute` to `@this`; the JavaScript API's default is also `@this`. Among the keywords are `@all`, `@none`,
  `@this` and `@form`.
* *Invoke Application.* The `f:ajax` `listener` runs here, once, unless `immediate` is set.
* *Render.* Render Response renders only the ids in the `render` list (default `@none`), writes a `text/xml` partial
  response and sets `Cache-control: no-cache`. The response is a list of `update` operations that `faces.ajax.response`
  applies to the DOM, followed by an update of the view state.

Because validation still happens, the short-circuit still happens. The `review-ajax.xhtml` page is the review
form with a Save button that submits through `f:ajax`:

----

The practical rules follow from this. The `render` list must contain the component that displays the messages, or an
Ajax failure will be invisible to the user. The `execute` list must contain every input whose value the action needs,
otherwise the bean property keeps its old value while the action runs. Validation errors on components that are not in
`execute` do not occur, because those components are not processed. The xref:web/jsf/ajax.adoc[Ajax] page of this section covers the full
`f:ajax` attribute set, the JavaScript API and the response format.

[#web-forms]
== Comparison with the ASP.NET Web Forms Page Life Cycle

Faces and ASP.NET Web Forms are the two classic server-side component frameworks, and their lifecycles map onto each
other closely enough that the comparison is useful in both directions. The Web Forms side is described in
xref:web/aspnet/web-forms/page-lifecycle-and-postback.adoc[Page Life Cycle and Postback]; the state that rides on
the round trip in xref:web/aspnet/web-forms/view-state-and-control-state.adoc[ViewState and Control State]; and the
validation controls in xref:web/aspnet/web-forms/validation-controls.adoc[Validation Controls].

[cols="2,3,3"]
|===
| Idea | Jakarta Faces | ASP.NET Web Forms

| Component tree restored from state | Phase 1 Restore View, state from the `jakarta.faces.ViewState` hidden field or the server | ViewState is loaded between `PreLoad` and `Load`; the hidden field is `+__VIEWSTATE+`
| Is this a postback? | `FacesContext.isPostback()`, decided by the `ResponseStateManager` | `Page.IsPostBack`
| Reading request data into controls | Phase 2: decode to a submitted value | Postback data is loaded onto controls before `Load`
| Converting and validating | Phase 3, automatic, for every non-immediate input, before the bean is touched | Validators run when a control with `CausesValidation` posts back; code must check `Page.IsValid` before acting
| Writing to the data model | Phase 4, a distinct step, only when everything is valid | Your own code, in an event handler
| Event handlers | Phase 5, only on valid input | After `Load`, whether or not the page is valid; guard with `Page.IsValid`
| Per-request code | No `Page_Load`: use bean construction, `f:viewAction`, `PreRenderViewEvent` | `Page_Load` runs on every request, guarded by `if (!IsPostBack)`
| Last chance to change the tree | `PreRenderViewEvent`, or the encode methods | `PreRender`
| Opting out of validation | `immediate="true"` on the command, or `execute` with Ajax | `CausesValidation="false"`
| Partial rendering | `f:ajax` with `execute` and `render`, a true partial lifecycle | `UpdatePanel`, which still runs the full page life cycle and trims only the response
| Event order is visible with | A `PhaseListener` | Overriding the `OnXxx` methods of `Page`
|===

Three differences matter when moving between them. First, Faces is stricter: an invalid form never reaches an event
handler, so there is no `IsValid` check to forget, and `immediate` is the explicit escape hatch where Web Forms uses a
flag on the control. Second, Faces separates the model update (phase 4) from the action (phase 5), so a bean property
has its new value by the time the action runs without the action copying it. Third, Faces has a real partial
lifecycle for Ajax, where the Web Forms ajax-and-client-side page describes `UpdatePanel` as running the entire page
life cycle and trimming the response. Both frameworks share the lesson that the order of events is the thing to learn
first.

[#versions]
== What Changed Between Versions

The six phases have existed since JSF 1.0 and the rules above are the same in Faces 4.0 and 4.1. These are the
changes that touch the lifecycle:

[cols="1,4"]
|===
| Version | Change relevant to the lifecycle

| JSF 2.0 | Ajax and partial processing and rendering (`f:ajax`, `PartialViewContext`), system events (`PostAddToViewEvent`, `PreRenderViewEvent` and others), view metadata (`f:metadata`, `f:viewParam`) so that an initial request can run the full lifecycle
| JSF 2.2 | `f:viewAction`, with the `immediate`, `onPostback` and `phase` attributes, so that an action can run on an initial request; protected views, which add a check in Restore View
| Faces 3.0 | The package rename from `javax.faces` to `jakarta.faces`; `PhaseListener` is now `jakarta.faces.event.PhaseListener`
| Faces 4.0 | The JavaScript resource is `faces.js` and the API is `faces.ajax.request` (it was `jsf.js` and `jsf.ajax.request`); `FacesContext.getLifecycle()` is new
| Faces 4.1 | The additions listed in the section's version baseline (`UUIDConverter`, `rowStatePreserved`, the injectable `Flow`, deprecated full state saving) do not change the phases; `beforePhase()` and `afterPhase()` are `default` methods in the 4.1 API
| Faces 5.0 (upcoming, milestone `5.0.0-M9`) | Not described here as current behaviour
|===

[#implementations]
== Mojarra and MyFaces

Both implementations implement the same specification text for the lifecycle, so the phase order, the events and the
`renderResponse()` and `responseComplete()` rules on this page are the contract on both. Neither the specification
nor the documentation pages checked for this page lists a difference in the route a request takes through the six
phases; what differs is the surrounding detail, such as the text of the validation messages and the format of the
log lines. The traces and the skip behaviour of a `renderResponse()` called before a phase were verified on Mojarra
4.1.17 only. MyFaces 4.1.4 was not run for this page, and its concept page for `immediate` (linked below) is the
documentation to read for that implementation.

Source: https://myfaces.apache.org/#/coreConcepts[Apache MyFaces: Core Concepts] and https://myfaces.apache.org/#/core41[Apache MyFaces Core 4.1]

[#books]
== Where the Books Are Outdated

The lifecycle is the part of the older Faces books that has aged best, because the six phases did not change. The
classic descriptions (Burns and Schalk, Dudney et al., Mann) are still a good account of the order of phases, of
`immediate` and of `renderResponse()` / `responseComplete()`. Read them with these corrections:

* Everything in them uses `+javax.faces.*+`. The current packages are `+jakarta.faces.*+`, and the `PhaseListener` of
  Faces 4.1 has default `beforePhase()` and `afterPhase()` methods, so you no longer write empty bodies.
* Their view examples are JSP pages, where the JSP tag handlers add the components while the page renders. With
  Facelets, which is the only view declaration language of Faces 4.0 and later, the tree is built by the
  `ViewDeclarationLanguage`, and view metadata and view actions (JSF 2.0 and 2.2) make an initial request run the full
  lifecycle, which the JSP-era books never mention.
* The Ajax chapters (Jacobi and Fallows, and the early Ajax chapters of the others) describe hand-written
  `XMLHttpRequest` code, Weblets, ajax4jsf and Dynamic Faces; since JSF 2.0 the lifecycle itself knows partial
  requests (`PartialViewContext`, `f:ajax`), and since Faces 4.0 the script is `faces.js`.
* Some books describe `immediate` as a way to skip validation or to run business logic "early". It does neither; it
  moves conversion, validation or action delivery to Apply Request Values, with the consequences in <<immediate>>.
* The pre-2.0 books know no system events. `PostAddToViewEvent`, `PreRenderViewEvent` and the other component
  system events publish around the phases in the sequence described above.
* `@ManagedBean`, the `javax.faces.bean` scopes, `ValueBinding` and `MethodBinding` appear in their lifecycle
  examples; the current examples use CDI `@Named` beans, `@ViewScoped` (`jakarta.faces.view.ViewScoped`) and the
  `MethodExpression` that the `action` attribute resolves to.

[#pitfalls]
== Common Pitfalls

* *The action method is not called.* Look for a queued message. A validation or conversion error anywhere in the
  executed part of the form skips phases 4 and 5. Put an `h:messages` in the form while developing, and log the phases
  with the listener above.
* *A getter runs several times.* It runs once for every expression that refers to it, in every phase in which the
  expression is evaluated, and Render Response evaluates it while encoding. Keep getters free of logic and of queries;
  load data in a view action or a listener instead.
* *The bean still has the old value after a cancel.* That is `immediate` working. The model was never updated.
* *A button whose `rendered` expression is false on the postback is never activated.* Phase 2 skips a component whose
  `rendered` property is false, so it is not decoded and its action is not called. The expression is evaluated again
  on the postback, so it must give the same answer then as when the page was rendered.
* *`ViewExpiredException` on the first click after a long idle time.* Phase 1 could not restore the view. The xref:web/jsf/exception-handling.adoc#view-expired[exception handling]
  page shows a redirect to the same page.
* *Redirecting from an action without completing the response.* Use a navigation outcome with
  `faces-redirect=true`, or call `responseComplete()` after `ExternalContext.redirect()`.
* *A `PhaseListener` that keeps request data in fields.* There is one instance for all requests. Use the
  `FacesContext` attribute map.
