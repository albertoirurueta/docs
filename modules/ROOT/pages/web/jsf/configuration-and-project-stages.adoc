most configuration mistakes come from not knowing which of them wins.

[#sources]
== Where Faces Reads Its Configuration

Five mechanisms feed the configuration of a Faces application. They are independent and they overlap on purpose, so that a
library can configure itself, an application can override the library, and an operations team can change a setting without
rebuilding the WAR.

.The sources of Faces configuration
[cols="2,3,3",options="header"]
|===
| Source | What it configures | Who writes it

| Context parameters (`+<context-param>+` in `+web.xml+` or `+web-fragment.xml+`)
| Behaviour switches: project stage, Facelets, state saving, validation, mapping. Names start with `+jakarta.faces.+` for the
standard ones, `+com.sun.faces.+` for Mojarra and `+org.apache.myfaces.+` for MyFaces.
| The application, or a library through its `+web-fragment.xml+`

| JNDI environment entry `+java:comp/env/faces/ProjectStage+`
| The project stage only.
| The operations team, in the server or in the descriptor

| `+faces-config.xml+` documents
| Objects and registrations: locales, resource bundles, navigation rules, converters, validators, components, renderers,
phase listeners, factories, flows, protected views, ordering.
| The application and every library that ships a `+META-INF/faces-config.xml+`

| Annotations (`+@FacesConverter+`, `+@FacesValidator+`, `+@FacesComponent+`, `+@FacesRenderer+`, `+@FacesBehavior+`, ...)
| The same registrations as the XML, written next to the class.
| The application and libraries

| Code: `+ApplicationConfigurationPopulator+`, `+Application+` methods
| Registrations computed at startup.
| Frameworks and integrations
|===

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6201[Jakarta Faces 4.1 specification, 11.3.2 Application Startup Behavior] and https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_application_configuration_resource_file[Jakarta EE Tutorial: Application Configuration Resource File]

The sequence at startup is the same on both implementations. The container merges the descriptors, Faces decides whether it
has anything to do, collects the configuration resources, sorts them, combines the annotation metadata with them, and publishes
`+PostConstructApplicationEvent+` when it is finished. All of this happens before the first request is processed, which is why
configuration errors are deployment errors, not request errors.

Two details of the diagram deserve a sentence. The `+FacesServlet+` is mapped for you when you do not map it yourself and one of
these is true: `+WEB-INF/faces-config.xml+` exists, a `+META-INF/faces-config.xml+` or `+*.faces-config.xml+` file exists in a JAR,

even though none of the usual triggers is present.

[#startup-shutdown]
=== Startup and Shutdown

Startup ends with an event and shutdown starts with one. At startup the specification (11.3.2) has the runtime publish
`+PostConstructApplicationEvent+` immediately after all configuration resources have been processed, flows and resource library
contracts included; the events page lists it as an
xref:web/jsf/events-and-listeners.adoc#system-events[application system event]. A parsing error in a configuration resource is fatal to
startup and the container does not make the application available. At shutdown (11.3.4) the runtime must make sure that
`+FacesContext.getCurrentInstance()+` returns successfully while the application is going down (the API documentation of
`+FacesContext+` says that `+getApplication()+` is valid during startup and shutdown), then publish `+PreDestroyApplicationEvent+`,
and finally call `+FactoryFinder.releaseFactories()+`. So `+PreDestroyApplicationEvent+` is the hook for releasing what an
application-wide extension holds (a thread pool, a cache, a connection), and by the time the factories are released nothing of
Faces may be used any more.

.A listener that releases resources at shutdown, registered in faces-config.xml
[source,java]
----
package org.example.bookshelf.config;

import jakarta.faces.context.FacesContext;
import jakarta.faces.event.AbortProcessingException;
import jakarta.faces.event.SystemEvent;
import jakarta.faces.event.SystemEventListener;
import java.util.logging.Logger;

/** Runs when the web application stops: close what the application opened at startup. */
public class ShutdownHook implements SystemEventListener {

    private static final Logger LOG = Logger.getLogger(ShutdownHook.class.getName());

    @Override
    public void processEvent(SystemEvent event) throws AbortProcessingException {
        FacesContext ctx = FacesContext.getCurrentInstance();
        String line = "shutdown: FacesContext present = " + (ctx != null)
                + ", project stage = " + (ctx == null ? "?" : ctx.getApplication().getProjectStage());
        LOG.info(line);
        System.err.println(line);
        // close the catalogue cache, stop the import scheduler ...
    }

    @Override
    public boolean isListenerForSource(Object source) {
        return true;
    }
}
----

[source,xml]
----
<application>
    <system-event-listener>
        <system-event-listener-class>org.example.bookshelf.config.ShutdownHook</system-event-listener-class>
        <system-event-class>jakarta.faces.event.PreDestroyApplicationEvent</system-event-class>
        <source-class>jakarta.faces.application.Application</source-class>
    </system-event-listener>
</application>
----

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6248[Jakarta Faces 4.1 specification, 11.3.4 Application Shutdown Behavior] and https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/event/PreDestroyApplicationEvent.html[Jakarta Faces 4.1 API: PreDestroyApplicationEvent]

Run on Mojarra 4.1.17 and MyFaces 4.1.4 on Tomcat 11.0.26 (the embedded Tomcat was stopped with SIGTERM, with a hook that stops the
context): both implementations published the event, and in the listener `+FacesContext.getCurrentInstance()+` was not `+null+` and
`+getProjectStage()+` answered `+Production+`. In the first run the `+java.util.logging+` line of the listener did not appear in the log at all (the cause was not investigated), so the listener also writes to
`+System.err+`, which did appear; if a shutdown message is missing in your logs, check the logging configuration before suspecting the event. Treat the
`+FacesContext+` of such a listener as a way to reach the `+Application+`, not as a request: the specification only promises the context and the application object.

[#context-params]
== Context Parameters

A context parameter is a name and a string value that the servlet container exposes through the `+ServletContext+`. Faces
reads them once, at startup, so changing one needs a redeploy or restart. (The Facelets refresh period is no exception: it
sets how often the view files are checked, and is itself read at startup.)

=== Setting a Parameter

There are three places, and they combine under the rules of the Servlet specification, not of Faces.

.The Bookshelf web.xml with the three development parameters
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<web-app xmlns="https://jakarta.ee/xml/ns/jakartaee"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-app_6_1.xsd"
         version="6.1">

  <context-param>
    <param-name>jakarta.faces.PROJECT_STAGE</param-name>
    <param-value>Development</param-value>
  </context-param>
  <context-param>
    <param-name>jakarta.faces.FACELETS_REFRESH_PERIOD</param-name>
    <param-value>1</param-value>
  </context-param>
  <context-param>
    <param-name>jakarta.faces.FACELETS_SKIP_COMMENTS</param-name>
    <param-value>true</param-value>
  </context-param>

  <servlet>
    <servlet-name>facesServlet</servlet-name>
    <servlet-class>jakarta.faces.webapp.FacesServlet</servlet-class>
  </servlet>
  <servlet-mapping>
    <servlet-name>facesServlet</servlet-name>
    <url-pattern>*.xhtml</url-pattern>
  </servlet-mapping>
</web-app>
----

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_configuring_project_stage[Jakarta EE Tutorial: Configuring Project Stage] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6088[Jakarta Faces 4.1 specification, 11.1.3 Application Configuration Parameters]

A JAR can contribute parameters of its own through a `+META-INF/web-fragment.xml+`. A library that needs a Faces parameter to
work (a tag library registered through `+jakarta.faces.FACELETS_LIBRARIES+`, for example) ships it that way, so the
application does not have to copy it:

.A web-fragment.xml in a library JAR
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<web-fragment xmlns="https://jakarta.ee/xml/ns/jakartaee"
              xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
              xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-fragment_6_1.xsd"
              version="6.1">
  <name>bookshelfDefaults</name>
  <context-param>
    <param-name>jakarta.faces.FACELETS_SKIP_COMMENTS</param-name>
    <param-value>true</param-value>
  </context-param>
</web-fragment>
----

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/webapp/FacesServlet.html[Jakarta Faces 4.1 API: FacesServlet] (the API documentation of `+FacesServlet+` names `+web.xml+` and `+web-fragment.xml+` as the places where Faces looks)

In the scratch run a fragment that set `+jakarta.faces.PROJECT_STAGE+` to `+Development+` was honoured by both
implementations when `+web.xml+` set nothing, and lost to `+web.xml+` when `+web.xml+` set `+Production+`; a second parameter of the same fragment that
`+web.xml+` did not mention still applied. That is the Servlet rule (the main descriptor overrides a fragment), so a library's defaults
can be overridden by the application and never the other way round.

The third place is the container itself. Tomcat's `+context.xml+` can define an environment entry, and the project stage
(and only the project stage) is read from JNDI before the context parameter is consulted; the section on <<stage-resolution>> shows
it. Servers other than Tomcat have their own way to define the same JNDI name.

=== How Values Are Read

The values are strings and each parameter has its own rule. The specification states the rules of the boolean ones the same
way for most of them: the runtime calls `+toLowerCase().equals("true")+` on the string, so `+true+`, `+TRUE+` and `+True+` enable
the parameter, and anything else (`+yes+`, `+1+`, `+on+`) leaves it off. `+jakarta.faces.STATE_SAVING_METHOD+` is compared
ignoring case, `+jakarta.faces.PROJECT_STAGE+` is not: it has to be the exact name of a constant. The lists are separated by
different characters depending on the parameter (semicolon for the Facelets libraries, decorators and view mappings, comma for
`+CONFIG_FILES+` and `+FULL_STATE_SAVING_VIEW_IDS+`, a space for `+RESOURCE_EXCLUDES+` and `+FACELETS_SUFFIX+`); the tables below
say which. A mistyped parameter name is not an error: it is simply never read, and the application runs with the default. In the scratch run
`+jakarta.faces.PROJECT_STAG+`, a made-up `+com.sun.faces.numberOfLogicalViewz+` and the old `+javax.faces.PROJECT_STAGE+` were all
ignored on both implementations, without a log line, while the correct `+jakarta.faces.PROJECT_STAGE+` next to them set `+Development+`. Both
implementations can print what they read, which is the quickest way to find a typo (the sections on <<mojarra-params>> and
<<myfaces-params>> show how).

only in the API documentation. The next tables list all of them, grouped by purpose, with the default, the release that
introduced them and what they do. "Tested" in the last column means that the behaviour was run in the scratch application and is described
under the table or in the section named there.

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6088[Jakarta Faces 4.1 specification, 11.1.3 Application Configuration Parameters] and https://github.com/eclipse-ee4j/mojarra/blob/4.1/CONTEXT-PARAMS.md[Mojarra 4.1 context parameters]

Three rows need a comment on the source of the default. `+jakarta.faces.validator.DISABLE_DEFAULT_BEAN_VALIDATOR+` is
`+false+` in the Mojarra reference; the MyFaces reference table lists `+true+` in its default column, which contradicts the
specification wording (the validator is added unless the parameter is `+true+`) and was not checked at run time, so the table above
gives the Mojarra value. The defaults of `+RESOURCE_EXCLUDES+` and `+SEPARATOR_CHAR+` come from the specification text and
the Mojarra reference. And `+NUMBER_OF_CLIENT_WINDOWS+` is absent from the specification's list in chapter 11, yet both implementations
document it and the xref:web/jsf/scopes.adoc#window[Scopes page] observed it working on both.

[#facelets-params]
=== Facelets Parameters in Practice

The refresh period and the comment switch are demonstrated on the xref:web/jsf/project-setup.adoc[Project Setup] page, where the
combination with the project stage is tabulated. The other Facelets parameters change how a view id is mapped to a file or
what the compiler does, and they have traps.

[#facelets-suffix]
==== FACELETS_SUFFIX

A request for `+/books.xhtml+` becomes the view id `+/books.xhtml+`, and the Facelets compiler reads the physical file
`+books.xhtml+`. `+jakarta.faces.FACELETS_SUFFIX+` changes the file suffix that is looked for: it is a space-separated list of
extensions, each starting with a dot; the first physical file that matches one of them becomes the file behind the view id. A project that keeps its views in `+.facelet+` files while the URLs stay `+.xhtml+` configures it like this:

.Views stored as .facelet files
[source,xml]
----
<context-param>
  <param-name>jakarta.faces.FACELETS_SUFFIX</param-name>
  <param-value>.facelet .xhtml</param-value>
</context-param>
----

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/application/ViewHandler.html[Jakarta Faces 4.1 API: ViewHandler, FACELETS_SUFFIX_PARAM_NAME]

The _Bookshelf_ scratch application had `+suffix.facelet+` and `+index.xhtml+` in its web root, the `+FacesServlet+` mapped to
`+*.xhtml+` only, and the two implementations answered like this:

.FACELETS_SUFFIX observed on both implementations
[cols="3,3,2,2",options="header"]
|===
| Parameter value | Request | Mojarra 4.1.17 | MyFaces 4.1.4

| `+.facelet+`
| `+/suffix.xhtml+` (file `+suffix.facelet+`)
| 200
| 200

| `+.facelet+`
| `+/index.xhtml+` (file `+index.xhtml+`)
| 404
| 500

| `+.facelet .xhtml+`
| `+/suffix.xhtml+`
| 200
| 404

| `+.facelet .xhtml+`
| `+/index.xhtml+`
| 200
| 200
|===

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/application/ViewHandler.html[Jakarta Faces 4.1 API: ViewHandler, FACELETS_SUFFIX_PARAM_NAME]

Two lessons follow. First, a list of suffixes is not portable: with both `+.facelet+` and `+.xhtml+` in the list, Mojarra
found `+suffix.facelet+` for the request `+/suffix.xhtml+` and MyFaces answered 404 (it did not substitute the suffix
because the request already ended with one of the listed ones), while with the single value `+.facelet+` both implementations
served the page. The single value is the safe choice, and it means every view file must use it.

Second, and worse: the file `+suffix.facelet+` was answered with status 200 and its raw Facelets source on a direct request, in
every variant, because the container serves a file nobody maps as static content. The source of a page, with its EL
expressions, bean names and comments, was readable by anyone. A suffix other than `+.xhtml+` therefore needs a constraint that
blocks direct access:

.Blocking direct access to alternative view files
[source,xml]
----
<security-constraint>
  <web-resource-collection>
    <web-resource-name>Facelets sources</web-resource-name>
    <url-pattern>*.facelet</url-pattern>
  </web-resource-collection>
  <auth-constraint/>
</security-constraint>
----

With this constraint the direct request answered 403 on both implementations, and the view requested as `+/index.xhtml+`
still rendered. (The constraint has an empty `+auth-constraint+`, which in the Servlet specification means no role may access the
resource.) Views under `+WEB-INF+` need no constraint, because the container never serves that directory; that is the reason
templates are kept in `+WEB-INF/templates+` in the _Bookshelf_ layout.

Source: https://jakarta.ee/specifications/servlet/6.1/[Jakarta Servlet 6.1 specification, security constraints] and https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/webapp/FacesServlet.html[Jakarta Faces 4.1 API: FacesServlet, security considerations]

[#facelets-view-mappings]
==== FACELETS_VIEW_MAPPINGS

`+jakarta.faces.FACELETS_VIEW_MAPPINGS+` declares that some resources are Facelets views whatever their extension.
Each entry of the semicolon-separated list is a file extension written as `+*.xhtml+` or a prefix starting with a slash
and ending in `+*+`, as in `+/user/*+`. A legacy application with views called `+*.html+` that maps the `+FacesServlet+` to
`+*.html+` too would write:

.Treating .html files as Facelets views
[source,xml]
----
<context-param>
  <param-name>jakarta.faces.FACELETS_VIEW_MAPPINGS</param-name>
  <param-value>*.html</param-value>
</context-param>
<servlet-mapping>
  <servlet-name>facesServlet</servlet-name>
  <url-pattern>*.xhtml</url-pattern>
  <url-pattern>*.html</url-pattern>
</servlet-mapping>
----

In the scratch run a file `+legacy.html+` with Facelets content was served by MyFaces with this parameter alone (status 200,
the EL expression evaluated) and answered 404 on Mojarra. Adding `+jakarta.faces.FACELETS_SUFFIX+` with the value `+.html+` made both implementations serve it, with or without
the view mappings parameter. So `+FACELETS_SUFFIX+` is the parameter that decides which file is read; `+FACELETS_VIEW_MAPPINGS+`
decides which view ids count as Facelets, and Mojarra needs the first even when the second is set.

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/application/ViewHandler.html[Jakarta Faces 4.1 API: ViewHandler, FACELETS_VIEW_MAPPINGS_PARAM_NAME]

[#facelets-decorators]
==== FACELETS_DECORATORS

A `+TagDecorator+` sees each tag while a view is compiled and may replace it. The classes are named in the semicolon-separated
parameter, need a public no-argument constructor, and are created when the first request for a Facelets view reaches the
`+ViewHandler+`. A decorator that only observes returns `+null+`:

.A TagDecorator that logs every command button as the view is compiled
[source,java]
----
package org.example.bookshelf.config;

import jakarta.faces.view.facelets.Tag;
import jakarta.faces.view.facelets.TagDecorator;
import java.util.logging.Logger;

public class CompileLogDecorator implements TagDecorator {

    private static final Logger LOG = Logger.getLogger(CompileLogDecorator.class.getName());

    public CompileLogDecorator() {
        LOG.info("decorator created");
    }

    @Override
    public Tag decorate(Tag tag) {
        if ("commandButton".equals(tag.getLocalName())) {
            LOG.info("compiling " + tag.getQName() + " at " + tag.getLocation());
        }
        return null;
    }
}
----

[source,xml]
----
<context-param>
  <param-name>jakarta.faces.FACELETS_DECORATORS</param-name>
  <param-value>org.example.bookshelf.config.CompileLogDecorator</param-value>
</context-param>
----

On the first request for `+index.xhtml+` both implementations logged `+decorator created+` once and then
`+compiling h:commandButton at /index.xhtml @6,90+` (Mojarra) or `+... at /index.xhtml at line 6 and column 90+` (MyFaces). Because the compiled
view is cached, the decorator runs again only when the refresh period causes a recompilation. A decorator that returns a different
`+Tag+` rewrites the view before it is built; the tag libraries and templates documented elsewhere in this section are the usual
way to change markup, and a decorator is the tool for a rewrite that has to touch every view.

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/view/facelets/TagDecorator.html[Jakarta Faces 4.1 API: TagDecorator] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6088[Jakarta Faces 4.1 specification, FACELETS_DECORATORS in 11.1.3]

[#validation-params]
=== Conversion and Validation Parameters

Six parameters change what happens in the Process Validations phase (see
xref:web/jsf/request-processing-lifecycle.adoc[the lifecycle page]). Two are covered by earlier pages
(`+INTERPRET_EMPTY_STRING_SUBMITTED_VALUES_AS_NULL+` and `+VALIDATE_EMPTY_FIELDS+` on the xref:web/jsf/validators.adoc[Validators]
page, the Bean Validation parameters on the xref:web/jsf/bean-validation.adoc[Bean Validation] page); the other two have run-time
consequences worth demonstrating.

==== The time zone of f:convertDateTime

`+f:convertDateTime+` formats with GMT unless a `+timeZone+` attribute is given, a surprise for every application not running in
London. `+jakarta.faces.DATETIMECONVERTER_DEFAULT_TIMEZONE_IS_SYSTEM_TIMEZONE+` switches the default to the JVM's zone:

.Making the JVM time zone the default of every date converter
[source,xml]
----
<context-param>
  <param-name>jakarta.faces.DATETIMECONVERTER_DEFAULT_TIMEZONE_IS_SYSTEM_TIMEZONE</param-name>
  <param-value>true</param-value>
</context-param>
----

[source,xml]
----
<h:outputText value="#{dateBean.published}">
  <f:convertDateTime pattern="yyyy-MM-dd HH:mm z"/>
</h:outputText>
----

[source,java]
----
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Named;
import java.time.Instant;
import java.util.Date;

@Named
@RequestScoped
public class DateBean {
    public Date getPublished() { return Date.from(Instant.parse("2026-07-01T12:00:00Z")); }
}
----

For a date of 2026-07-01 at 12:00 UTC and a JVM started with `+-Duser.timezone=Europe/Madrid+`, the page printed
`+2026-07-01 12:00 GMT+` without the parameter and `+2026-07-01 14:00 CEST+` with it, on both implementations. The converter is
applied on output in the Render Response phase and on input in Process Validations, so a value typed in a form is parsed in the
same zone it was displayed in. Prefer an explicit `+timeZone+` attribute when the zone is part of the
business rule rather than of the server.

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6088[Jakarta Faces 4.1 specification, DATETIMECONVERTER_DEFAULT_TIMEZONE_IS_SYSTEM_TIMEZONE in 11.1.3] and https://jakarta.ee/specifications/faces/4.1/vdldoc/f/convertDateTime.html[Jakarta Faces 4.1 VDL: f:convertDateTime]

==== Required fields that are missing from the request

`+required="true"+` is checked when the input is decoded and validated, and only for the parameters that are present in the request.
A request that leaves the parameter out entirely is not an empty submission: the component has nothing submitted and, by default,
is not validated. A browser always sends the field of a text input, even empty, so the problem is invisible in the browser and
shows up in a scripted or malicious request.

.A form with a required field
[source,xml]
----
<h:form id="f">
  <h:inputText id="title" value="#{reqBean.title}" required="true"/>
  <h:message for="title"/>
  <h:inputText id="note" value="#{reqBean.note}"/>
  <h:commandButton id="b" value="save" action="#{reqBean.save}"/>
</h:form>
----

.The bean behind the form
[source,java]
----
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Named;

@Named
@RequestScoped
public class ReqBean {
    private String title;
    private String note;
    private String last = "none";
    public String getTitle() { return title; }
    public void setTitle(String t) { this.title = t; }
    public String getNote() { return note; }
    public void setNote(String n) { this.note = n; }
    public String save() { last = "saved title=[" + title + "] note=[" + note + "]"; return null; }
    public String getLast() { return last; }
}
----

A POST that carried `+f:b+` and `+f:note+` but not `+f:title+` called the action with `+title=null+` on both implementations, and no message
was added; a POST with `+f:title=+` (present but empty) produced "Validation Error: Value is required." With the parameter
`+jakarta.faces.ALWAYS_PERFORM_VALIDATION_WHEN_REQUIRED_IS_TRUE+` set to `+true+` the first request was rejected as well, with the same message,
and the action did not run.

.Validating required inputs even when their parameter is missing
[source,xml]
----
<context-param>
  <param-name>jakarta.faces.ALWAYS_PERFORM_VALIDATION_WHEN_REQUIRED_IS_TRUE</param-name>
  <param-value>true</param-value>
</context-param>
----

Treat the parameter as a hardening setting for any application where an action depends on a required value: the server must not
rely on the browser to send the fields. It costs one validation call per required input and changes no markup.

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/component/UIInput.html[Jakarta Faces 4.1 API: UIInput, ALWAYS_PERFORM_VALIDATION_WHEN_REQUIRED_IS_TRUE] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6088[Jakarta Faces 4.1 specification, 11.1.3]

[#separator-char]
=== The Client Id Separator

`+jakarta.faces.SEPARATOR_CHAR+` changes the character between the segments of a client id (`+f:title+` becomes `+f_title+`). Only
the first character of the value is used. It exists for style sheets and scripts that cannot cope with the colon, and it has
a price: every `+id+` with that character in it, every search expression and every piece of JavaScript written with the old
character stops working. In the scratch run a form `+f+` with the input `+in+` and the button `+b+` rendered the ids `+f_in+` and `+f_b+` on both
implementations, and the view state field `+j_id1_jakarta.faces.ViewState_0+` (Mojarra) and `+j_id__v_0_jakarta.faces.ViewState_1+` (MyFaces). The
xref:web/jsf/search-expressions.adoc[Search Expressions] page lists the places that must stay in step: the `+update+`
and `+render+` attributes, `+@form:id+` style absolute expressions, and CSS selectors that escape the colon.

.Underscore instead of colon in client ids
[source,xml]
----
<context-param>
  <param-name>jakarta.faces.SEPARATOR_CHAR</param-name>
  <param-value>_</param-value>
</context-param>
----

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/component/UINamingContainer.html[Jakarta Faces 4.1 API: UINamingContainer, SEPARATOR_CHAR_PARAM_NAME]

[#state-params]
=== State Saving Parameters

`+jakarta.faces.STATE_SAVING_METHOD+` decides where the view state lives, and it is the most visible parameter in the page source.
The xref:web/jsf/state-saving-and-stateless-views.adoc[state saving page] covers the mechanism, the limits of the server variant, the protection of the client
variant and the Mojarra and MyFaces parameters around it; here only the configuration is shown.

.Switching to client state saving
[source,xml]
----
<context-param>
  <param-name>jakarta.faces.STATE_SAVING_METHOD</param-name>
  <param-value>client</param-value>
</context-param>
----

The hidden field `+jakarta.faces.ViewState+` of a trivial page held 40 characters on Mojarra and 32 on MyFaces with the default
`+server+` method (an identifier of a state kept in the session), and 704 and 128 characters respectively with `+client+` (the state
itself, protected by the implementation). The size grows with the component tree on every response and every
postback, and the state leaves the server, so it must be protected: both implementations encrypt it and attach a message authentication code by default, and the
parameters that turn that off (`+com.sun.faces.disableClientStateEncryption+`, `+org.apache.myfaces.USE_ENCRYPTION+`) must never
be set in production.

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_to_specify_where_state_is_saved[Jakarta EE Tutorial: To Specify Where State Is Saved] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6088[Jakarta Faces 4.1 specification, STATE_SAVING_METHOD in 11.1.3]

[#phantom]
=== Parameters in the Specification Text That Do Nothing

Two parameters are listed in chapter 11 of the specification and in the MyFaces reference table, yet no trace of them was found in the
code that is delivered. `+jakarta.faces.HONOR_CURRENT_COMPONENT_ATTRIBUTES+` and `+jakarta.faces.FACELETS_RESOURCE_RESOLVER+` do not
appear as strings in the `+jakarta.faces-api+` 4.1.2 JAR, in `+jakarta.faces+` 4.1.17 (Mojarra) or in the `+myfaces-api+` and
`+myfaces-impl+` 4.1.4 JARs. The second also names a `+ResourceResolver+` class that is not part of the 4.1 API any more (it
was removed in Faces 4.0). Do not configure them; if a book or an old answer suggests it, the xref:web/jsf/resource-handling.adoc#custom-handler[resource handling] and xref:web/jsf/extending-faces.adoc[extending Faces]
pages describe the current extension points.

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6088[Jakarta Faces 4.1 specification, 11.1.3 Application Configuration Parameters]

[#project-stage]
== Project Stages

A *project stage* tells the runtime where the application is in its life: being written, being tested by machines, being
tested by people, or running for real. It is the Faces equivalent of the `+RAILS_ENV+` of Ruby on Rails, as the API
documentation puts it, and it is the one setting that both the specification and the implementations use to trade diagnostics against speed and
safety. The constants of `+jakarta.faces.application.ProjectStage+` are:

.The four stages
[cols="2,6",options="header"]
|===
| Constant | Meant for

| `+Development+`
| Programmers working on the application. Diagnostics are on, caches check for changes and error pages explain what went wrong.
| `+UnitTest+`
| Automated tests of single classes, run by the build.
| `+SystemTest+`
| Automated or manual tests of the deployed application as a whole.
| `+Production+`
| The default. Fast and quiet: nothing that explains the internals to the client.
|===

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/application/ProjectStage.html[Jakarta Faces 4.1 API: ProjectStage] and https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_configuring_project_stage[Jakarta EE Tutorial: Configuring Project Stage]

The specification gives the stages no behaviour beyond a handful of points listed in <<stage-effects>>. What each implementation does
with them is its own business, and the scratch measurements below show that `+UnitTest+` and `+SystemTest+` mean almost nothing in
practice: the practical choice is between `+Development+` and everything else.

[#stage-resolution]
=== How the Stage Is Determined

`+Application.getProjectStage()+` computes the stage the first time it is called and keeps it. The algorithm in the API documentation
looks for a JNDI environment entry first and for the context parameter second, and falls back to `+Production+` when the value cannot be used.

.How the project stage is chosen
[mermaid]
----
flowchart TD
    A["First call of Application.getProjectStage()"] --> B{"JNDI entry java:comp/env/faces/ProjectStage?"}
    B -- yes --> V["Use that value"]
    B -- no --> C{"Context parameter jakarta.faces.PROJECT_STAGE?"}
    C -- yes --> V
    C -- no --> P["Production"]
    V --> D{"Exactly the name of a ProjectStage constant?"}
    D -- yes --> S["That stage"]
    D -- no --> L["Log a message and use Production"]
----

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/application/Application.html[Jakarta Faces 4.1 API: Application.getProjectStage()]

The JNDI name is the constant `+ProjectStage.PROJECT_STAGE_JNDI_NAME+`, which holds `+java:comp/env/faces/ProjectStage+` (not
`+jakarta.faces.PROJECT_STAGE+`, which is the name of the context parameter). Two ways to define it were run on Tomcat with the
JNDI naming enabled, each time with the context parameter set to `+Production+`, and in each case both implementations
reported `+Development+`: the JNDI entry won. In `+web.xml+`:

.The stage as a JNDI environment entry in web.xml
[source,xml]
----
<env-entry>
  <env-entry-name>faces/ProjectStage</env-entry-name>
  <env-entry-type>java.lang.String</env-entry-type>
  <env-entry-value>Development</env-entry-value>
</env-entry>
----

and in the Tomcat `+META-INF/context.xml+` of the application, which is the variant an operations team controls without touching the WAR:

.The stage as a Tomcat environment entry
[source,xml]
----
<Context>
  <Environment name="faces/ProjectStage" value="Development" type="java.lang.String" override="false"/>
</Context>
----

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/application/ProjectStage.html[Jakarta Faces 4.1 API: ProjectStage, PROJECT_STAGE_JNDI_NAME] and https://tomcat.apache.org/tomcat-11.0-doc/config/context.html#Environment_Entries[Apache Tomcat 11: Environment Entries]

A value that is not exactly one of the four names is not an error. Mojarra logged `+INFO: Unable to discern ProjectStage for value Staging.+`
and MyFaces `+WARNING: Wrong value in context init parameter 'jakarta.faces.PROJECT_STAGE' (='Staging'), using default value 'Production'+`;
both then ran as `+Production+`. The lower-case `+development+` was refused in the same way, because the value goes through `+ProjectStage.valueOf()+`. The
Jakarta EE Tutorial says custom stages can be added; that cannot work with a Java enum, and in both implementations a custom
name means `+Production+` plus a log line. The mistake to avoid is a
typo in the one value that should enable diagnostics (or, worse, a typo that is meant to disable them): the application starts
without complaint and runs in `+Production+`.

=== Setting the Stage per Environment

The stage must follow the environment, not the source tree. Three arrangements work; the first is the simplest, the second is the
safest against a mistake in the build, the third is the one for containers that offer a JNDI configuration.

*A Maven property filtered into web.xml.* The default is `+Production+`, so that a build without a profile is a safe one, and a
`+dev+` profile selects `+Development+` and a one-second refresh period:

.web.xml with filtered values
[source,xml]
----
<context-param>
  <param-name>jakarta.faces.PROJECT_STAGE</param-name>
  <param-value>${faces.project.stage}</param-value>
</context-param>
<context-param>
  <param-name>jakarta.faces.FACELETS_REFRESH_PERIOD</param-name>
  <param-value>${faces.refresh.period}</param-value>
</context-param>
----

Source: https://maven.apache.org/plugins/maven-war-plugin/examples/adding-filtering-webresources.html[Apache Maven WAR Plugin: Adding and Filtering External Web Resources]

.pom.xml: Production by default, Development with -Pdev
[source,xml]
----
<properties>
  <faces.project.stage>Production</faces.project.stage>
  <faces.refresh.period>-1</faces.refresh.period>
</properties>

<build>
  <plugins>
    <plugin>
      <artifactId>maven-war-plugin</artifactId>
      <configuration>
        <webResources>
          <webResource>
            <directory>src/main/webapp</directory>
            <includes>
              <include>WEB-INF/web.xml</include>
            </includes>
            <filtering>true</filtering>
          </webResource>
        </webResources>
      </configuration>
    </plugin>
  </plugins>
</build>

<profiles>
  <profile>
    <id>dev</id>
    <properties>
      <faces.project.stage>Development</faces.project.stage>
      <faces.refresh.period>1</faces.refresh.period>
    </properties>
  </profile>
</profiles>
----

With these files `+mvn package+` wrote `+Production+` and `+-1+` into the packaged `+WEB-INF/web.xml+`, and `+mvn package -Pdev+` wrote
`+Development+` and `+1+`. The war plugin filters only the resources listed, which keeps stray `+${...}+` expressions in other files untouched.

*The JNDI entry in the server.* The `+context.xml+` and `+env-entry+` above move the decision out of the WAR: one artifact is
deployed to every environment and the stage comes from the server. Because the JNDI value wins over the context parameter, it can
override a `+Development+` left in `+web.xml+`, which makes it the safer of the two for a production server.

*A web-fragment.xml in a library.* A fragment can set the stage too (it applied in the scratch run), but a library that picks
`+Development+` for the application it is bundled in is a trap; keep the stage out of libraries.

Source: https://maven.apache.org/plugins/maven-war-plugin/examples/adding-filtering-webresources.html[Apache Maven WAR Plugin: Adding and Filtering External Web Resources]

[#stage-reading]
=== Reading the Stage

The stage can be read from three places, and a page may adapt to it, within the limits of <<ui-debug>>.

.A bean that exposes the stage to views
[source,java]
----
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.faces.application.ProjectStage;
import jakarta.faces.context.FacesContext;
import jakarta.inject.Inject;
import jakarta.inject.Named;

@Named
@RequestScoped
public class StageInfo {

    @Inject
    private FacesContext facesContext;

    public ProjectStage getStage() {
        return facesContext.getApplication().getProjectStage();
    }

    public boolean isDevelopment() {
        return getStage() == ProjectStage.Development;
    }

    public boolean isProduction() {
        return getStage() == ProjectStage.Production;
    }
}
----

.Using the stage in a view
[source,xml]
----
<ui:debug hotkey="d" rendered="#{stageInfo.development}"/>
<p>stage=#{stageInfo.stage}</p>
----

The page printed `+stage=Development dev=true prod=false+`, `+stage=UnitTest dev=false prod=false+` and
`+stage=Production dev=false prod=true+` under the three settings, on both implementations, and the debug script was
rendered only in the first. The same test can be written without a bean as
`+#{facesContext.application.projectStage eq 'Development'}+`: EL coerces the string to the enum, and the page behaved
identically. In JavaScript `+faces.getProjectStage()+` returns the stage as a string without a request (see the
xref:web/jsf/ajax.adoc[Ajax] page), which the Faces scripts themselves use to decide whether to show an alert.

=== What the Stage Changes

The specification names a short list of stage-dependent behaviour, and the implementations add their own. The first table is the
specification's; the second is what the two implementations did in the scratch run, with the same views and the same requests
under each stage.

.Stage-dependent behaviour required or allowed by the specification
[cols="3,5",options="header"]
|===
| Where | Rule

| `+FACELETS_REFRESH_PERIOD+` not set
| `+-1+` in `+Production+`, `+0+` in every other stage (run; see the xref:web/jsf/project-setup.adoc#development[Project Setup page]).

| Navigation case not found for a call node of a Faces Flow
| A message explaining that there was no match is rendered when the stage is not `+Production+`.

| Ajax errors
| In `+Development+` the client script signals errors with an `+alert+`. Mojarra did, MyFaces 4.1.4 did not (the xref:web/jsf/ajax.adoc#errors[Ajax page]).

| Composite component interface metadata
| `+displayName+`, `+shortDescription+`, `+expert+`, `+hidden+` and `+preferred+` are exposed only in `+Development+`.

| Invalid composite library name
| An informative message is placed in the page in `+Development+`, and it is only logged otherwise.

| Error information for Facelets error pages
| In `+Development+` the debug information (exception, tree, variables) is available to an error page through
`+<ui:include src="jakarta.faces.error.xhtml"/>+`.

| Resource metadata
| An implementation may cache the resolved resources when the stage is `+Production+`.
|===

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6088[Jakarta Faces 4.1 specification, FACELETS_REFRESH_PERIOD in 11.1.3] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html[Jakarta Faces 4.1 specification, faces.getProjectStage and the Ajax error handling in the JavaScript chapter]

Beyond that list each implementation decides. Every row of the next table was produced by one request to the same view under
`+Development+`, `+UnitTest+`, `+SystemTest+`, `+Production+`, no setting, `+Staging+` and `+development+` (the last three behaved as `+Production+`).

.Stage-dependent behaviour observed
[cols="3,4,4",options="header"]
|===
| Situation | Mojarra 4.1.17 | MyFaces 4.1.4

| `+h:link+` whose outcome matches no navigation case
| Text plus the sentence "This link is disabled because a navigation case could not be matched." in `+Development+`, `+UnitTest+` and
`+SystemTest+`; only the text in `+Production+`.
| Only the text, in every stage.

| An exception thrown while the view renders (a bean getter)
| `+Development+`: status 500 and a Faces error page of about 14 KB with the message, the stack trace, the component tree and the variables.
Other stages: status 500 and the container's own error report (about 3.5 KB with Tomcat's default).
| `+Development+`: status 500 and a Faces error page of about 11 KB. Other stages: status 500 with only the part of the page rendered before
the failure (73 bytes in the test).

| `+h:outputStylesheet+` / `+h:outputScript+` naming a resource that does not exist

| The same.

| `+LOG_WEB_CONTEXT_PARAMS+` defaults to `+dev-only+` (logged in `+Development+` only) and `+ERROR_HANDLING+` to `+true+` in `+Development+` and `+false+` otherwise.
|===

Source: https://github.com/eclipse-ee4j/mojarra/blob/4.1/CONTEXT-PARAMS.md[Mojarra 4.1 context parameters] and https://myfaces.apache.org/#/core41[Apache MyFaces Core 4.1 -- Configuration]

Three things stand out. Mojarra gives `+UnitTest+` and `+SystemTest+` the "not production" behaviour in the link row only, MyFaces never
distinguishes the three non-production stages, and a build that uses the two test stages to get development diagnostics will not
get them. Second, the error information of the `+Development+` page is exactly what an attacker wants (class names, source lines, bean
variables), so the stage is a security setting as much as a convenience; the same is true of MyFaces' `+ERROR_HANDLING+`, which switched the
error page on in `+Production+` when set to `+true+` in the scratch run (the page title was the exception message, status 500, 11 KB).
Third, a `+Production+` rendering failure is not pretty by default: Mojarra hands the exception to the container and MyFaces
sends what it has already rendered. The xref:web/jsf/exception-handling.adoc#error-pages[exception handling page] shows how to configure an `+<error-page>+`
and the `+ExceptionHandler+` so that a failure ends in a deliberate page.

[#ui-debug]
=== ui:debug and the Stage

The documentation of `+ui:debug+` says the tag works only when the stage is `+Development+`. In the scratch run that was not
the case. A page with `+<ui:debug hotkey="d"/>+` rendered the keyboard script in `+Development+` and in `+Production+` on both
implementations, and the URL that the script opens (`+/bookshelf/debug.xhtml?facelets.ui.DebugOutput=...+`, with the generated number
copied from the page) answered 200 with a page that listed the component tree, the request parameters and the scoped variables:
10 KB on Mojarra and 8 KB on MyFaces in `+Production+`. The request needs the session of the user who rendered the page, so it is
not an anonymous leak, but anyone who can use the page can read bean state with it. Guard the tag explicitly:

.Rendering ui:debug only in Development
[source,xml]
----
<ui:debug hotkey="d" rendered="#{stageInfo.development}"/>
----

With this guard the script was absent from the `+Production+` and `+UnitTest+` pages and present in `+Development+`, on both implementations. Put the tag in
the one template that all views use, as the tag documentation suggests, so that the guard exists once.

Source: https://jakarta.ee/specifications/faces/4.1/vdldoc/ui/debug.html[Jakarta Faces 4.1 VDL: ui:debug]

[#faces-config]
== faces-config.xml

`+faces-config.xml+` is the *application configuration resource*: an XML document in the Jakarta EE namespace that registers objects
with the `+Application+` and the factories, and that carries the settings that have no annotation. The same format is used by the
`+WEB-INF/faces-config.xml+` of the application, by the `+META-INF/faces-config.xml+` of every library and by the extra files
named in `+jakarta.faces.CONFIG_FILES+`.

=== The Document

A Faces 4.1 document starts with this declaration, which the specification requires:

.The faces-config.xml root element for Faces 4.1
[source,xml]
----
<?xml version="1.0" encoding="UTF-8"?>
<faces-config xmlns="https://jakarta.ee/xml/ns/jakartaee"
              xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
              xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/web-facesconfig_4_1.xsd"
              version="4.1">
  <!-- name, ordering, application, factory, lifecycle, ... in any order -->
</faces-config>
----

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6254[Jakarta Faces 4.1 specification, 11.3.5 Application Configuration Resource Format] and https://jakarta.ee/xml/ns/jakartaee/web-facesconfig_4_1.xsd[web-facesconfig_4_1.xsd]

The schema of 4.1 defines the root as a *choice* of its children, repeated, so the elements can appear in any order and the ordering of
the schema never causes a validation error. The root has three attributes: `+version+` (`+4.1+`), `+id+`, and
`+metadata-complete+`, which stops annotation scanning when it is `+true+` in `+WEB-INF/faces-config.xml+` (see <<annotations>>). The
xref:web/jsf/project-setup.adoc#faces-config[Project Setup] page shows the namespaces and version numbers of all the earlier
releases; a document that names an older schema is still read by 4.1 runtimes, but only a 4.1 document can use the elements added since.
A `+<managed-bean>+` element in a 4.1 document does not validate against the schema, and both runtimes ignored it silently in the
scratch run: the managed bean facility is gone, and CDI replaces it (the
xref:web/jsf/backing-beans-and-cdi.adoc[Backing Beans and CDI] page).

[source,java]
----
package org.example.bookshelf.config;

import jakarta.faces.event.PhaseEvent;
import jakarta.faces.event.PhaseId;
import jakarta.faces.event.PhaseListener;
import java.util.logging.Logger;

/** Registered from faces-config.xml: logs how long the Render Response phase took. */
public class RenderTimer implements PhaseListener {

    private static final Logger LOG = Logger.getLogger(RenderTimer.class.getName());
    private static final String START = RenderTimer.class.getName() + ".start";

    @Override
    public PhaseId getPhaseId() {
        return PhaseId.RENDER_RESPONSE;
    }

    @Override
    public void beforePhase(PhaseEvent event) {
        event.getFacesContext().getAttributes().put(START, System.nanoTime());
    }

    @Override
    public void afterPhase(PhaseEvent event) {
        Long start = (Long) event.getFacesContext().getAttributes().get(START);
        if (start != null) {
            LOG.info("render " + event.getFacesContext().getViewRoot().getViewId() + " took "
                    + (System.nanoTime() - start) / 1_000_000 + " ms");
        }
    }
}
----

=== Checking the File

Both implementations can validate configuration files against the schema, and by their references neither does by default (the
specification requires the check only of implementations that are part of a Jakarta EE server). With a bogus element added to a 4.1 document, MyFaces with
`+org.apache.myfaces.VALIDATE_XML+` set to `+true+` logged `+SEVERE: cvc-complex-type.2.4.a: Invalid content was found starting with
element '{"https://jakarta.ee/xml/ns/jakartaee":bogus-element}'+` and kept running; Mojarra with `+com.sun.faces.validateXml+` set to
`+true+` logged nothing and started. So the switch reported the error on MyFaces and not on Mojarra in this run, which makes it a poor safety net. An
editor that knows the `+xsi:schemaLocation+` (every IDE does) and a build step that runs `+xmllint --schema+` are better tools:

.Validating faces-config.xml in the build
[source,bash]
----
curl -sO https://jakarta.ee/xml/ns/jakartaee/web-facesconfig_4_1.xsd
xmllint --noout --schema web-facesconfig_4_1.xsd src/main/webapp/WEB-INF/faces-config.xml
----

Source: https://jakarta.ee/xml/ns/jakartaee/web-facesconfig_4_1.xsd[web-facesconfig_4_1.xsd] and https://myfaces.apache.org/#/core41[Apache MyFaces Core 4.1 -- Configuration]

[#annotations]
== Annotations or XML

Every registration that has an annotation can be written either way, and the specification fixes the winner when the two disagree:
an entry in an application configuration resource takes precedence over an annotation. The annotated classes are found by scanning,
and the scan can be restricted or switched off.

=== What Is Scanned

The specification (11.4.1) says that all classes in `+WEB-INF/classes+` are scanned, that the classes of a JAR in `+WEB-INF/lib+` are scanned
only if the JAR contains a `+META-INF/faces-config.xml+` (or a file ending in `+.faces-config.xml+`, even empty), and that a
`+metadata-complete="true"+` in `+WEB-INF/faces-config.xml+` turns the scan off for everything except the implementation's own classes. The
containers' initializer is told which annotations to look for (the list is in the API documentation of `+FacesServlet+`); that is also what
triggers the automatic mapping of the servlet. A library that wants its annotated classes found therefore ships a
`+META-INF/faces-config.xml+`, even an empty one. Mojarra scanned a library JAR without it in the scratch runs of earlier pages and MyFaces did not,
so the file is what makes the library portable.

Two parameters restrict the scan and shorten the startup of an application with a large class path:

.Restricting the annotation scan
[source,xml]
----
<!-- Mojarra: package names for WEB-INF/classes, or jar:name:packages -->
<context-param>
  <param-name>com.sun.faces.annotationScanPackages</param-name>
  <param-value>org.example.bookshelf.convert org.example.bookshelf.web</param-value>
</context-param>

<!-- MyFaces: comma separated packages -->
<context-param>
  <param-name>org.apache.myfaces.annotation.SCAN_PACKAGES</param-name>
  <param-value>org.example.bookshelf.convert,org.example.bookshelf.web</param-value>
</context-param>
----

In the scratch run, restricting the scan to `+org.example.bookshelf.config+` (a package without the `+@FacesConverter+` class) made the page
that uses the converter fail with status 500 on both implementations, and restricting it to the package that contains the converter
made the page work. The mistake it invites is silent: a class in a package that is not listed is never registered, and the first
error is at the first use of the id.

[cols="4,3",options="header"]

| Arrangement | Output

=== Replacing a Standard Converter

The same replacement works on the identifiers that Faces itself registers, as long as the new class is a subclass of the standard one.
The standard integer converter has the id `+jakarta.faces.Integer+`; a subclass that accepts an underscore as a digit separator and an XML entry that replaces it:

.A replacement for the standard integer converter
[source,java]
----
package org.example.bookshelf.convert;

import jakarta.faces.component.UIComponent;
import jakarta.faces.context.FacesContext;
import jakarta.faces.convert.IntegerConverter;

/** Replacement for the standard converter id jakarta.faces.Integer: accepts a thousands separator. */
public class UnderscoreIntegerConverter extends IntegerConverter {
    @Override
    public Object getAsObject(FacesContext c, UIComponent u, String v) {
        return super.getAsObject(c, u, v == null ? null : v.replace("_", ""));
    }
}
----

[source,xml]
----
<converter>
  <converter-id>jakarta.faces.Integer</converter-id>
  <converter-class>org.example.bookshelf.convert.UnderscoreIntegerConverter</converter-class>
</converter>
----

[source,java]
----
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Named;

@Named
@RequestScoped
public class NumBean {
    private Integer qty;
    public Integer getQty() { return qty; }
    public void setQty(Integer q) { this.qty = q; }
}
----

A form with `+<h:inputText value="#{numBean.qty}" converter="jakarta.faces.Integer"/>+` bound to this bean received `+1_000+`. Without the entry both runtimes
reported "must be a number consisting of one or more digits." and kept the form; with it the bean got `+1000+` and the page printed
`+qty=1000+`. The id has to be used explicitly: the replacement applies to the converter that is looked up by id, which is
what `+converter="jakarta.faces.Integer"+` does. Use this technique sparingly: it changes every use of the id in the application, in
every library, and a reader of the view sees nothing unusual.

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6297[Jakarta Faces 4.1 specification, 11.3.6 Configuration Impact on Jakarta Faces Runtime]

=== Which to Use

Prefer the annotation where one exists: the registration sits next to the class and cannot drift from it. Use XML when the registration must
be changeable without recompiling (a library default the application overrides), when the same class is registered under two ids,
when the item has no annotation (locales, bundles, navigation rules, phase listeners, factories, `+protected-views+`, ordering), or when
the annotation scan is too expensive and `+metadata-complete="true"+` is set so that everything is listed explicitly. A project can mix the
two freely; the rule above settles every conflict.

[#multiple-files]
== Several Configuration Files

An application is rarely a single file. Every JAR on the class path may bring its own `+faces-config.xml+`, the application has its
own, and a large application may split its configuration into parts. This section covers how the files are found, in which
order they are read, and what happens when they disagree.

=== Where the Files Are Found

The discovery rules are fixed by the specification (11.3.2) and were checked, one location at a time, with a phase listener registered
by each file and a page that printed the list of the registered phase listeners (`+Lifecycle.getPhaseListeners()+`).

.Where configuration files are found
[cols="4,2,4",options="header"]
|===
| Location | Found automatically? | Observed

| `+META-INF/faces-config.xml+` in a JAR in `+WEB-INF/lib+`
| yes
| read on Mojarra and MyFaces

| `+META-INF/<name>.faces-config.xml+` in a JAR (any file name ending in `+.faces-config.xml+` directly in `+META-INF+`)
| yes
| read on both

| `+WEB-INF/classes/META-INF/faces-config.xml+`
| yes
| read on both

| `+WEB-INF/faces-config.xml+`
| yes, and read last
| read on both, its listener last in the list

| `+WEB-INF/other.faces-config.xml+`, or any file outside `+META-INF+`
| no
| ignored by both until it is listed in `+jakarta.faces.CONFIG_FILES+`

| a service file `+META-INF/services/jakarta.faces.application.ApplicationConfigurationPopulator+`
| yes
| its class contributes a document on both; see <<populator>>
|===

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6201[Jakarta Faces 4.1 specification, 11.3.2 Application Startup Behavior] and https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_application_configuration_resource_file[Jakarta EE Tutorial: Application Configuration Resource File]

The tutorial adds a sentence on the class path: files are found in the JARs of `+WEB-INF/lib+` and in parent class loaders.
Beware that the tutorial names the parameter `+jakarta.faces.application.CONFIG_FILES+` in that section: the name defined by the
specification and the API (`+FacesServlet.CONFIG_FILES_ATTR+`) is `+jakarta.faces.CONFIG_FILES+`.

=== The CONFIG_FILES Parameter

`+jakarta.faces.CONFIG_FILES+` lists additional files, as comma-separated paths relative to the web application root. It is meant for

----

The specification says that when this parameter exists the search for `+META-INF+` files is skipped, and the API documentation of

|===
| Parameter | Mojarra 4.1.17 | MyFaces 4.1.4

[#populator]
=== Configuration from Code: ApplicationConfigurationPopulator

Before the documents are parsed, Faces asks every `+ApplicationConfigurationPopulator+` found with the `+ServiceLoader+` to fill an
empty `+faces-config+` document. The result is processed like a file, so a framework can compute its configuration (from a classpath scan, from
Spring properties, from annotations of its own) instead of shipping an XML file. The class below adds the render timer of the previous section with the same
elements the XML file would have contained:

.A populator that adds a phase listener
[source,java]
----
package org.example.bookshelf.config;

import jakarta.faces.application.ApplicationConfigurationPopulator;
import org.w3c.dom.Document;
import org.w3c.dom.Element;

/** Adds configuration in code: the same elements a faces-config.xml would contain. */
public class AuditConfigPopulator extends ApplicationConfigurationPopulator {

    private static final String NS = "https://jakarta.ee/xml/ns/jakartaee";

    @Override
    public void populateApplicationConfiguration(Document toPopulate) {
        Element root = toPopulate.getDocumentElement();
        Element lifecycle = toPopulate.createElementNS(NS, "lifecycle");
        Element listener = toPopulate.createElementNS(NS, "phase-listener");
        listener.setTextContent("org.example.bookshelf.config.RenderTimer");
        lifecycle.appendChild(listener);
        root.appendChild(lifecycle);
    }
}
----

.META-INF/services/jakarta.faces.application.ApplicationConfigurationPopulator
[source,text]
----
org.example.bookshelf.config.AuditConfigPopulator
----

With the service file in `+WEB-INF/classes/META-INF/services+` and no `+faces-config.xml+` listing the listener, both implementations registered
`+RenderTimer+` and logged the render times. The specification text of 11.3.2 calls the service
`+jakarta.faces.ApplicationConfigurationResourceDocumentPopulator+`; no such class exists in the 4.1 API, whose class is
`+jakarta.faces.application.ApplicationConfigurationPopulator+`, and the service file must carry that name. Mojarra's own runtime
configuration is contributed by a subclass of it (`+com.sun.faces.config.configpopulator.MojarraRuntimePopulator+`). Application code rarely needs
this, because a `+faces-config.xml+` does the same in a form the next programmer can read; the xref:web/jsf/extending-faces.adoc#map[extending Faces page]
lists the other extension points for integrations.

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/application/ApplicationConfigurationPopulator.html[Jakarta Faces 4.1 API: ApplicationConfigurationPopulator] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6201[Jakarta Faces 4.1 specification, 11.3.2 Application Startup Behavior]

[#ordering]
== Ordering of Configuration Files

When two files register something that can only have one value, or something that wraps what was registered before, the order in
which they are read decides the result. The classpath order is not a contract: it depends on the container and the build. The
specification therefore defines how files declare their order. The rules (11.3.8) are borrowed from the Servlet specification's ordering of web fragments.

=== The Rules

* A file may have a top-level `+<name>+`. Only named files take part in ordering.
* A library file may have an `+<ordering>+` with at most one `+<before>+` and one `+<after>+`; each contains the names of other files and may contain
`+<others/>+`, the set of all other files.
* `+<before><others/></before>+` moves the file to the beginning of the list, `+<after><others/></after>+` to the end; several files that
say so are in unspecified order among themselves.
* The application's own `+WEB-INF/faces-config.xml+` is always read last, and it alone may contain an `+<absolute-ordering>+`: a list of
`+<name>+` elements, optionally with one `+<others/>+`, that fixes the order of all the library files. A library file not named and
without `+<others/>+` in an absolute ordering is ignored (its configuration is not read at all).
* An `+<ordering>+` in `+WEB-INF/faces-config.xml+` or an `+<absolute-ordering>+` in a library is ignored, with a log message.
* A cycle is an error that must fail the deployment, and so must two files with the same name.

.The specification's example
[source,xml]
----
<!-- library A -->
<faces-config ...>
  <name>A</name>
  <ordering><after><name>B</name></after></ordering>
  <lifecycle><phase-listener>lib.PL_A</phase-listener></lifecycle>
</faces-config>

<!-- library B: no ordering -->
<faces-config ...>
  <name>B</name>
  <lifecycle><phase-listener>lib.PL_B</phase-listener></lifecycle>
</faces-config>

<!-- library C -->
<faces-config ...>
  <name>C</name>
  <ordering><before><others/></before></ordering>
  <lifecycle><phase-listener>lib.PL_C</phase-listener></lifecycle>
</faces-config>

<!-- WEB-INF/faces-config.xml: name "my", no ordering -->
----

The specification derives the order C, B, A, my. The scratch application built these four files plus an unnamed library `+D+`, and
printed the list of phase listeners:

.Order produced for the specification's example
[mermaid]
----
flowchart LR
    C["C: before others"] --> B["B"]
    B --> A["A: after B"]
    A --> M["my: WEB-INF/faces-config.xml, always last"]
    D["D: unnamed, no ordering, anywhere between C and my"] -.-> M
----

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6435[Jakarta Faces 4.1 specification, 11.3.8 Ordering of Artifacts] and https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html#_ordering_of_application_configuration_resource_files[Jakarta EE Tutorial: Ordering of Application Configuration Resource Files]

=== What the Two Implementations Do

Each case below was a separate deployment with the libraries named, the `+WEB-INF/faces-config.xml+` shown and one phase listener per file;
the cell is the order of the registered phase listeners.

.Ordering, observed
[cols="4,3,3",options="header"]
|===
| Case | Mojarra 4.1.17 | MyFaces 4.1.4

| The specification's example (A after B, C before others, D unnamed)
| `+C, B, D, A, my+`
| `+C, D, B, A, my+`

| `+<before><name>B</name></before>+` in A, `+<after><others/></after>+` in C, D unordered
| `+A, D, B, C, my+`
| `+D, A, B, C, my+`

| Absolute ordering `+C, <others/>, A+` in `+WEB-INF/faces-config.xml+`

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6435[Jakarta Faces 4.1 specification, 11.3.8 Ordering of Artifacts]

Four results deserve attention.

* *Where the specification leaves a choice, the implementations choose differently.* The unnamed library D landed between B and A
on Mojarra and before B on MyFaces, and with no ordering at all the unordered libraries were read in the alphabetical order of their file names in both runs;
that order came from the container's listing of `+WEB-INF/lib+` and must not be relied upon.
* *Mojarra 4.1.17 cannot start with an absolute ordering that leaves out `+<others/>+`* when there are library files, whether it names
all of them or not. The stack trace is an `+ArrayIndexOutOfBoundsException+` that ends in `+com.sun.faces.config.manager.Documents.sortDocuments(Documents.java:217)+`.
Until that is fixed, write `+<others/>+` in
every `+<absolute-ordering>+` (the case with `+<others/>+` worked), and use `+<before>+`/`+<after>+` rather than an absolute ordering when you can.
* *Duplicate names did not fail the deployment on either implementation*, although the specification requires it, so a clash is not
detected for you: two libraries must not use the same `+<name>+`.
* *A cycle fails differently*: Mojarra aborted the deployment (the application answered 404 afterwards), MyFaces logged a `+SEVERE+`
message and answered with status 500.

=== What Ordering Changes

Ordering decides two things. The first is the order of *decoratable artifacts*: a `+ViewHandler+`, `+NavigationHandler+`,
`+ActionListener+`, factory or other class named in `+<application>+` or `+<factory>+` wraps the one registered before it, so the file read
last is the outermost wrapper. The second is every registration that has an id: a later file replaces an earlier one, as the converter
table of <<annotations>> shows. For phase listeners, the order of the list is also the order of the calls: in both runs
`+beforePhase+` was called for the listeners in list order (`+C, B, D, A, my+` on Mojarra) and `+afterPhase+` in reverse order (`+my, A, D, B, C+`), so the first
listener registered is the outermost one. The xref:web/jsf/events-and-listeners.adoc[Events and Listeners] page describes how listeners registered in `+faces-config.xml+` relate to those of a view.

Source: https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6336[Jakarta Faces 4.1 specification, 11.3.7 Delegating Implementation Support] and https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a6435[11.3.8 Ordering of Artifacts]

The key parameters are the one place where a configuration file tempts a programmer into a security mistake. A key must be the same on
every node of a cluster and must not sit in the version control system of the project. Supply it at build or deploy time from the
environment, and build or deploy fails when it is missing:

.A secret filled in from the environment, never written in the file
[source,xml]
----
<context-param>
  <param-name>org.apache.myfaces.SECRET</param-name>
  <param-value>${env.BOOKSHELF_VIEWSTATE_SECRET}</param-value>
</context-param>
----

With the war plugin filtering of the earlier section, a build with `+BOOKSHELF_VIEWSTATE_SECRET=placeholder-from-ci+` in its environment wrote that
value into the packaged descriptor, and a build without the variable left the text `+${env.BOOKSHELF_VIEWSTATE_SECRET}+` in it unreplaced, which is why the
value must be checked after packaging (a deploy script that greps the descriptor for `+${+` is enough). The value shown is a placeholder; a real key is
generated with a secure random source and kept in the CI secret store or the server's configuration. The xref:web/jsf/state-saving-and-stateless-views.adoc#client-keys[state saving page] explains the
format of the key and the cluster implications.

[#extensionless]
== Extensionless Mapping and the FacesServlet Mappings

Which URLs reach the `+FacesServlet+` is configuration too. The xref:web/jsf/project-setup.adoc#servlet-mapping[Project Setup page] covers the three mapping styles of `+web.xml+`
(extension, prefix and exact); this section covers the parts that depend on parameters: the mapping Faces adds when you declare none, the
Faces 4.0 extensionless mapping, and what each setting does to the URLs the application generates.

=== The Automatic Mapping

When the servlet is not mapped in `+web.xml+` or `+web-fragment.xml+` and Faces detects that the application uses it (the triggers of the
diagram at the start of this page), the implementation maps it to four patterns: `+/faces/*+`, `+*.jsf+`, `+*.faces+` and `+*.xhtml+`.
`+jakarta.faces.DISABLE_FACESSERVLET_TO_XHTML+` removes the last of them. A mapping that you declare yourself replaces all four.

=== AUTOMATIC_EXTENSIONLESS_MAPPING

With `+jakarta.faces.AUTOMATIC_EXTENSIONLESS_MAPPING+` set to `+true+`, the implementation scans the web application at startup and
adds a mapping for the extensionless variant of every view it finds (`+/index+` for `+/index.xhtml+`). Mojarra's reference warns that
the scan walks the whole web root and registers a mapping per view, so the startup cost grows with the number of views.

.Automatic extensionless mapping
[source,xml]
----
<context-param>
  <param-name>jakarta.faces.AUTOMATIC_EXTENSIONLESS_MAPPING</param-name>
  <param-value>true</param-value>
</context-param>
----

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/webapp/FacesServlet.html[Jakarta Faces 4.1 API: FacesServlet, AUTOMATIC_EXTENSIONLESS_MAPPING_PARAM_NAME]

The exact alternative, which the Jakarta EE Tutorial describes, lists the views yourself and costs nothing at startup:

.Exact mappings for two views
[source,xml]
----
<servlet-mapping>
  <servlet-name>facesServlet</servlet-name>
  <url-pattern>*.xhtml</url-pattern>
  <url-pattern>/index</url-pattern>
  <url-pattern>/other</url-pattern>
</servlet-mapping>
----

The table has three consequences.

* *A declared mapping replaces the automatic ones.* With `+*.xhtml+` declared, `+/faces/index.xhtml+` and `+/index.jsf+` stop working,

* *The extensionless parameter adds, it does not replace.* The `+.xhtml+` URLs keep working, which is why a site migrating to clean URLs must
redirect or canonicalise the old ones itself.
* *`+DISABLE_FACESSERVLET_TO_XHTML+` without a mapping of your own serves the views as text.* `+/index.xhtml+` answered 200 with the
literal `+stage=#{configInfoBean.stage}+` of the source on both implementations, and `+/faces/index.xhtml+` still rendered: an attacker reads
every view's source, including the EL expressions and the structure of the application, by dropping the prefix. Use the parameter only
together with an explicit mapping for each URL pattern that must work, and a `+security-constraint+` for the rest, exactly as for prefix mapping.

=== URLs Generated by Faces

Faces builds the URLs of links, form actions and redirects from the mapping of the *current request*. With the extensionless
parameter on, a page requested with its extension linked to the other pages with their extension, and a page requested extensionless linked to extensionless URLs:

.URLs generated for h:link, h:form and a faces-redirect=true navigation
[cols="3,3,3,3",options="header"]
|===
| Request | h:link outcome="other" | Form action | Redirect from action="other?faces-redirect=true"

| `+/index.xhtml+`
| `+/bookshelf/other.xhtml+`
| `+/bookshelf/index.xhtml+`
| `+/bookshelf/other.xhtml+`

| `+/index+`
| `+/bookshelf/other+`
| `+/bookshelf/index+`
| `+/bookshelf/other+`

| `+/faces/index.xhtml+`
| `+/bookshelf/faces/other.xhtml+`
| `+/bookshelf/faces/index.xhtml+`
| not run

| `+/index.jsf+`
| `+/bookshelf/other.jsf+`
| not run
| not run
|===

The results are identical for Mojarra and MyFaces, and also hold for the configuration with exact mappings for `+/index+` and `+/other+`. The
rule has one consequence for links: the first URL of a visit decides the form of every later one, so a canonical form has to be
imposed on the first request (a redirect from the extension form to the clean form, or a link from outside that uses the clean
form). Another consequence is that the `+view id+` never changes: navigation outcomes, `+include-view-params+`, `+f:viewParam+` and the security
patterns are written with view ids, and the mapping is only a prefix or suffix applied when the URL is built. The
xref:web/jsf/navigation.adoc[Navigation] page and the xref:web/jsf/view-parameters-and-view-actions.adoc[View Parameters] page show that in use.

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/application/ViewHandler.html[Jakarta Faces 4.1 API: ViewHandler.getActionURL()]

[#implementations]
== Mojarra and MyFaces

The two implementations pass the same specification and agreed on most of what this page measured: the parameter semantics of the
standard names, the requirement that XML beats annotations, the discovery locations, the mapping matrix, the generated URLs, the JNDI
precedence of the stage and the silent handling of unknown names. They differ where the specification leaves a choice, and in a few places where it
does not.

.Configuration differences observed
[cols="3,4,4",options="header"]
|===
| Topic | Mojarra 4.1.17 | MyFaces 4.1.4

| Parameter namespace and printing
| `+com.sun.faces.*+`; `+displayConfiguration+` logs every parameter at `+INFO+`.
| `+org.apache.myfaces.*+`; `+LOG_WEB_CONTEXT_PARAMS+` logs the parameters, `+dev-only+` by default.

| `+UnitTest+` and `+SystemTest+`
| Behave as non-production for unresolved `+h:link+` outcomes only.
| Behave as `+Production+` in every measured respect.

| Failure while rendering
| `+Development+`: a Faces error page with tree and variables. Otherwise the container's error report.
| `+Development+`, or `+ERROR_HANDLING=true+`: a Faces error page. Otherwise status 500 with the part rendered so far.

| A resource that does not exist
| `+RES_NOT_FOUND+` in the markup; a message in `+Development+`.
| Nothing rendered, nothing logged.

| `+CONFIG_FILES+` and the `+META-INF+` search
| The scan is not skipped; the listed file is read after the `+META-INF+` files.
| The scan is not skipped; the listed file is read before them.

| Libraries with no ordering
| Alphabetical by file name. In the specification's example the unnamed library D landed between B and A.
| Alphabetical by file name. In the specification's example the unnamed library D landed before B.

| `+absolute-ordering+` without `+<others/>+`
| Startup fails with `+ArrayIndexOutOfBoundsException+` (`+Documents.sortDocuments+`).
| Works; unlisted files are ignored, as specified.

| `+<ordering>+` in `+WEB-INF/faces-config.xml+`
| Ignored with the warning `+JSF1081+`.
| Ignored without a message.

| Two files with the same name
| Both deployed (the specification asks for a failed deployment).
| Both deployed.

| Cycle in the ordering
| Deployment aborted.
| `+SEVERE+` at startup; status 500.

| XML validation switch
| `+validateXml+` logged nothing for an invalid file.
| `+VALIDATE_XML+` logged `+SEVERE: cvc-complex-type...+` and went on.

| `+FACELETS_SUFFIX+` with a list and `+FACELETS_VIEW_MAPPINGS+` alone
| A list works; the view mappings need the matching suffix.
| A list of `+.facelet .xhtml+` answered 404 for `+/suffix.xhtml+`; the view mappings alone serve the `+.html+` file.

| Ajax error in `+Development+`
| `+alert+`.
| No alert.
|===

Source: https://github.com/eclipse-ee4j/mojarra/blob/4.1/CONTEXT-PARAMS.md[Mojarra 4.1 context parameters] and https://myfaces.apache.org/#/core41[Apache MyFaces Core 4.1 -- Configuration]

The practical rule stays the one of the xref:web/jsf/project-setup.adoc#mojarra-vs-myfaces[Project Setup page]: keep the implementation parameters in a profile or a container-specific
descriptor, and test configuration-dependent behaviour on the implementation that production uses.

[#books]
== Where the Books Are Outdated

The books consulted for this section describe Faces 1.0 to 2.2. The `+faces-config.xml+` reference of Burns and Schalk and the
configuration chapter of Dudney and colleagues are the ones that touch this page, and the configuration they teach has changed in these ways:

* *`javax.faces.*` parameter names.* Every parameter of the books has a `+jakarta.faces.+` name since 3.0, and the old names are ignored without a
message (verified: `+javax.faces.PROJECT_STAGE+` had no effect on either implementation).
* *`<managed-bean>`, `<managed-property>` and `<referenced-bean>` in `+faces-config.xml+`.* The first two are gone from the schema and from the
runtime, and a `+<managed-bean>+` element is ignored; `+<referenced-bean>+` remains in the schema only as a note for tools. Beans are CDI beans.
* *The Pages-era configuration.* JSP views, `+DEFAULT_SUFFIX+` and a `+FacesServlet+` mapped to `+*.jsp+` or `+*.jsf+` for JSP pages belong to the past; the
default mapping and suffix are `+.xhtml+` and the Pages suffix is deprecated for removal.
* *DTD and old schemas.* The Faces 1.0 and 1.1 DOCTYPE with `+web-facesconfig_1_x.dtd+` and the schemas of 1.2 to 2.3 name namespaces that the 4.1 documents
do not use; the xref:web/jsf/project-setup.adoc#faces-config[Project Setup page] tabulates them.
* *The Facelets 1.x parameters.* The standalone Facelets book configures the library through its own `+facelets.*+` context
parameters and a `+com.sun.facelets+` view handler. Facelets is part of Faces since 2.0, and the `+jakarta.faces.FACELETS_*+` parameters of this page replace them.
* *Implementation parameters.* The Reference Implementation parameters of older books and articles come from Mojarra 1.x and 2.x. Check every name against `+CONTEXT-PARAMS.md+`:
a name that is not there (for example `+com.sun.faces.expressionFactory+`) is not a 4.1 parameter, and an unknown name is ignored without a
message.
* *Project stages and development mode.* Standalone Facelets had a development setting of its own. The `+ProjectStage+` of Faces 2.0 replaces it, and its effects
are the ones of <<project-stage>>, fewer than a reader may assume.
* *Secrets in configuration.* Nothing in Faces configuration needs a literal secret: take keys and passwords from the environment or the server, as shown for the
MyFaces key, and keep placeholders in the files under version control.

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html[Jakarta EE Tutorial: Configuring Jakarta Faces Applications] (the tutorial documents Jakarta EE 10; its managed-bean pages and the schema 3.0 shown in it are outdated for Faces 4.1)

[#pitfalls]
== Common Mistakes

* *Leaving `Development` in `web.xml` of a release.* The error page, the unhandled-message list and the refresh checks reach production. Make `Production` the default of the build and select
`+Development+` with a profile, or take the stage from JNDI.
* *Believing `UnitTest` and `SystemTest` do something.* On MyFaces they equal `+Production+`; on Mojarra they differ in one rendering detail.
* *Believing `ui:debug` is switched off in production.* It is not; guard it with the stage, once, in the master template.
* *Enabling `ERROR_HANDLING` (MyFaces) or the Development stage on a public server to find a problem.* Stack traces, bean state and the component tree go to the client.
* *Mistyping a parameter name.* Nothing complains; print the parameters at startup and look.
* *Trusting `required` for server-side rules.* A request that omits the field skips validation unless `+ALWAYS_PERFORM_VALIDATION_WHEN_REQUIRED_IS_TRUE+` is set; validate on the server whatever the browser sends.
* *A view suffix other than `.xhtml` without a constraint.* The raw Facelets source is served by the container.
* *`DISABLE_FACESSERVLET_TO_XHTML` without a mapping of your own.* The `.xhtml` views are then served as plain text.
* *Absolute ordering without `<others/>` on Mojarra 4.1.17.* The application does not start.
* *Relying on classpath order.* The order of unordered files is whatever the container lists; use `+<ordering>+`.
* *Relying on `CONFIG_FILES` to replace the `META-INF` search.* Neither implementation skipped it.
* *Duplicate `<name>` values.* The deployment is not refused, and one of the files may be shadowed.
* *Restricting the annotation scan too far.* A converter in a package that is not listed fails at first use, not at startup.
* *Real secrets in `web.xml` or `faces-config.xml`.* Keys, passwords and database URLs belong in the environment or the server; the files in version control carry placeholders.
* *Changing a descriptor and expecting a reload.* Only the view files are re-read; every parameter is read at startup.
