[#what-is-faces]
== What Jakarta Faces is

Jakarta Faces, called JavaServer Faces (JSF) in the Java EE era and Jakarta Server Faces in its first Jakarta EE
releases (2.3 and 3.0), is the component-based, server-side MVC web framework of
Jakarta EE. Instead of writing request handlers that return HTML, you declare a page as a tree of UI components, and the
framework keeps that tree on the server between requests:

* *Facelets* XHTML views declare the page. At run time they build a server-side *component tree* of inputs, outputs,
  tables and buttons, each with a renderer that writes its HTML.
* A six-phase *request processing lifecycle* restores the tree on a postback, decodes the submitted values, converts and
  validates them, copies them into *CDI backing beans* through the Expression Language, calls the action method and
  renders the response.
* On top of that the framework provides navigation, Ajax with partial rendering, view, flow and client-window scopes,
  state saving, resource handling, composite components, templating, internationalization and WebSocket push.
* A rich ecosystem sits on top of the standard: *PrimeFaces* (more than a hundred components and themes),
  *PrimeFaces Extensions*, *OmniFaces* (utilities that fill gaps in the standard) and smaller libraries.

Faces runs on any Jakarta EE Web Profile server (GlassFish, WildFly, Payara, Open Liberty, TomEE), on a plain servlet
container with a CDI implementation (Tomcat or Jetty with Weld), inside Spring Boot through JoinFaces and on Quarkus
through the MyFaces extension. Its closest relative outside Java is ASP.NET Web Forms, which shares the component tree,
the postback and the view state.

This section is for developers who:

* maintain or extend an existing JSF or Jakarta Faces application, often one written for JSF 2.x with `+javax.*+`, JSP
  or `@ManagedBean`, and need the current idioms and a migration path
* build component-rich internal or back-office applications on a Jakarta EE estate and want PrimeFaces or OmniFaces
  used well
* learned JSF from the classic books (2004 to 2015) and need to know what still holds and what has been removed
* are choosing between Faces, Vaadin, Thymeleaf with Spring MVC or a single-page application, and want the trade-offs

[#bookshelf]
== The Bookshelf scenario

Every example builds one small original application, _Bookshelf_, in the same domain as the
xref:web/django/index.adoc[Django], xref:backend/fastapi/index.adoc[Python FastAPI], xref:backend/nestjs/index.adoc[NestJS] and
xref:web/thymeleaf/index.adoc[Thymeleaf] sections, so the stacks can be compared page by page. Here it is a Maven WAR
with packages `org.example.bookshelf.model`, `service` and `web`, and it grows page by page into:

* a public catalogue of books and authors with Facelets templates, search, sorting and a lazy-loaded data table
* book details reached by bookmarkable URLs with `f:viewParam` and `f:viewAction`
* a review form with converters, validators and Bean Validation, submitted with Ajax
* a multi-step "borrow request" wizard implemented as a Faces Flow
* cover-image uploads with `h:inputFile`
* English and Spanish message bundles with a locale switcher
* a "new review" live feed with `f:websocket` and `@Push`
* a reusable "star rating" composite component and a small custom component
* form-based login with Jakarta Security and role-based views
* a PrimeFaces variant of the catalogue (data table, dialog framework, export) and OmniFaces utilities
* the same WAR running on WildFly or GlassFish, on Tomcat with Weld, on Spring Boot through JoinFaces and on Quarkus

.The Bookshelf application: browser, Jakarta Security, FacesServlet and lifecycle, Facelets views, component tree, CDI beans, services, persistence and WebSocket push

The browser sends initial GET requests, postbacks with the view state and Ajax partial requests from faces.js, and holds a WebSocket channel. Inside a Jakarta EE runtime or a servlet container with Weld, Jakarta Security checks the request and the FacesServlet runs the six lifecycle phases. Facelets views build or restore the component tree, whose components are bound by EL to CDI backing beans in request, view, flow or session scope. `contracts/`, `faces-config.xml`, `web.xml` and `beans.xml`) is assembled on
xref:web/jsf/project-setup.adoc[Project Setup].

== Reading path

The pages are ordered so that each one builds on the previous ones. Read them in this order the first time, then use
them as a reference. Before starting, be comfortable with the language underneath: the
xref:programming-languages/java/index.adoc[Java Reference] covers Java, Maven and JUnit, which these pages do not
re-explain.

. *Foundations*: what Faces is, versions, the architecture, the lifecycle, a project and a first application. Read
  xref:web/jsf/request-processing-lifecycle.adoc[Request Processing Lifecycle] carefully: almost every later page
  refers to its phases.
. *Facelets and views*: XHTML views, templating, the Expression Language, HTML5 markup, JSTL and views built in Java.
. *Standard components, conversion and validation*: the `h:` and `f:` tags, data tables, files, converters,
  validators, Bean Validation and messages.
. *Events, navigation, beans and scopes*: listeners, outcomes and redirects, bookmarkable pages, CDI beans, scopes,
  the flash and Faces Flows.
. *Ajax, push and components*: `f:ajax`, search expressions, WebSocket push, composite and custom components, tag
  files and client behaviours.
. *Resources, configuration, advanced topics and security*: resources and contracts, context parameters and project
  stages, state saving, exceptions, extension points, multiple windows, performance and security.
. *Component libraries*: PrimeFaces, PrimeFaces Extensions, OmniFaces and the other libraries.
. *Runtimes, testing and production*: application servers, Tomcat with Weld, Spring Boot, Quarkus, persistence,
  testing, deployment, migration from JSF 1.x and 2.x, and the best-practices checklist.

Readers coming from an existing JSF 2.x code base can start with
xref:web/jsf/migrating-to-jakarta-faces.adoc[Migrating to Jakarta Faces] and
xref:web/jsf/best-practices.adoc#avoid[the practices to avoid], then come back to the pages those link.
