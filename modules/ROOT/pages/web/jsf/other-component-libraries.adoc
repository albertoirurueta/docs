[#landscape]
== The Landscape in 2026

A component library is a set of tags, components and renderers on top of the standard ones. Jakarta Faces does not ship
tables with a pager, dialogs, menus or a grid layout; libraries fill that gap, and each makes a different bet about the
markup, the CSS and the JavaScript it brings. The table is the state of the libraries this page covers, from Maven
Central and the projects' own pages.

Two rules of thumb come out of the table. A library whose newest release is older than the Jakarta rename (Faces 3.0)
cannot be used with Faces 4.1 at all, because the `+jakarta.faces+` classes are not the `+javax.faces+` classes it
extends. A library that does use the
`+jakarta.faces.*+` packages can still break on 4.1, because 4.1 changed an interface (see <<action-trap>>); "supports
Jakarta EE 10" on the project page is a starting point, not a guarantee.

[#plugging-in]
== How a Library Plugs Into Faces

Everything on this page uses the same mechanisms, which are described in
xref:web/jsf/custom-components-and-renderers.adoc[Custom Components and Renderers] and
xref:web/jsf/extending-faces.adoc[Extending Faces]:

* *A tag library.* The jar contains a Facelets tag library (`+META-INF/*.taglib.xml+`) that maps tag names to component
  types and renderer types under a namespace URI. BootsFaces 2.0.1 declares 82 tags under `+http://bootsfaces.net/ui+`
  (not a `+jakarta.faces.*+` URN: the old-style URI is still how it is used), Tobago 6.12.2 declares its tags under
  `+http://myfaces.apache.org/tobago/component+`.
* *A `+faces-config.xml+` in `+META-INF+`.* It registers components, renderers, listeners and, in Tobago's case, a whole
  render kit. BootsFaces' file registers one system event listener, `+net.bootsfaces.listeners.AddResourcesListener+`,
  on `+PreRenderViewEvent+`; it adds the library's CSS and JavaScript to the page head. Tobago's file sets
  `+tobago+` as the default render kit id, adds a message bundle, and adds a phase listener
  (`+SecretPhaseListener+`, see <<tobago-security>>).
* *Resources* under `+META-INF/resources+`, served by the `+ResourceHandler+` (see
  xref:web/jsf/resource-handling.adoc[Resource Handling]).
* *Optionally a web fragment and CDI beans.* Tobago's `+web-fragment.xml+` registers a servlet context listener and a
  session listener; AdminFaces' registers error pages, a filter and the PrimeFaces theme.

What differs is how much of the page the library takes over. BootsFaces leaves the page to you: you write the HTML
skeleton with `+h:head+` and `+h:body+` and use `+b:*+` tags inside. Tobago owns the whole page: the root is `+tc:page+`
and the HTML skeleton is written by the library. AdminFaces gives you a Facelets template (`+/admin.xhtml+`) and fills it
with PrimeFaces components. Knowing that tells you where a bug is likely to be: in the library's renderer, not in your
markup.

Before a library goes into a project, six questions are worth asking; the sections that follow answer them for each
library:

* Which `+jakarta.*+` release does its newest jar target, and does it work on 4.1 (run a page and an Ajax request)?
* When was the last release, and who answers issues?
* What does it add to the page: bundled jQuery, Bootstrap or other frameworks, and do they clash with other libraries
  on the same page?
* What does it do to security: headers, inline scripts, escaping, its own state or tokens (see
  xref:web/jsf/security.adoc[Security])?
* How much of the server-side API does it override (render kit, exception handler, view handler)?
* What is the exit path: how many pages contain its tags?

[#bootsfaces]
== BootsFaces

BootsFaces puts Bootstrap into Faces: `+b:row+` and `+b:column+` are the grid, `+b:panel+`, `+b:navBar+`, `+b:modal+` and
`+b:growl+` are Bootstrap widgets, and `+b:inputText+`, `+b:selectOneMenu+` and `+b:dataTable+` are form controls and a
table that render with Bootstrap classes. The 2.0.1 tag library lists, by family:

* Layout: `+container+`, `+row+`, `+column+`, `+panel+`, `+panelGrid+`, `+tabView+`, `+tab+`, `+accordion+`,
  `+jumbotron+`, `+well+`, `+thumbnail+`, `+carousel+`.
* Navigation: `+navBar+`, `+navbarLinks+`, `+navLink+`, `+navCommandLink+`, `+breadcrumbs+`, `+dropMenu+`,
  `+flyOutMenu+`, `+pillLinks+`, `+tabLinks+`.
* Forms: `+form+`, `+inputText+`, `+inputTextarea+`, `+inputSecret+`, `+selectOneMenu+`, `+selectMultiMenu+`,
  `+selectBooleanCheckbox+`, `+radiobutton+`, `+switch+`, `+spinner+`, `+slider+`, `+datepicker+`, `+dateTimePicker+`,
  `+colorPicker+`, `+touchSpin+`, `+commandButton+`, `+commandLink+`, `+buttonGroup+`.
* Feedback: `+message+`, `+messages+`, `+growl+`, `+alert+`, `+modal+`, `+progressBar+`, `+label+`, `+badge+`.
* Data: `+dataTable+` and `+dataTableColumn+` (the DataTables jQuery plugin), `+tree+`, `+fullCalendar+`,
  `+openStreetMap+`.
* Ajax helpers: `+poll+`, `+remoteCommand+`, `+defaultCommand+`, `+focus+`, `+fetchBeanInfos+`.

Source: https://showcase.bootsfaces.net/[BootsFaces showcase] and the `+META-INF/bootsfaces-b.taglib.xml+` file inside `+bootsfaces-2.0.1.jar+`

package org.example.bookshelf.web;

import jakarta.annotation.PostConstruct;
import jakarta.faces.application.FacesMessage;
import jakarta.faces.context.FacesContext;
import jakarta.faces.view.ViewScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.ArrayList;
import java.util.List;
import org.example.bookshelf.model.Book;
import org.example.bookshelf.service.BookService;

@Named
@ViewScoped
public class CatalogueBean implements Serializable {

    @Inject
    private transient BookService service;

    @Inject
    private transient FacesContext facesContext;

    private String query;
    private List<Book> books;

    @PostConstruct
    void init() {
        books = new ArrayList<>(service.search(null));
    }

    public List<Book> getBooks() {
        return books;
    }

    public void search() {
        books = new ArrayList<>(service.search(query));
        facesContext.addMessage(null, new FacesMessage(FacesMessage.SEVERITY_INFO,
                books.size() + " book(s) found", null));
    }

    public String getQuery() { return query; }
    public void setQuery(String query) { this.query = query; }
}
----

Searching for `+ursula+` replaced the table with the single matching row and showed "1 book(s) found" on both
implementations. Four things in this page are specific to BootsFaces:

* *`+update+`, not `+f:ajax+`.* `+b:commandButton+` sends the request itself. Its `+update+` and `+process+` attributes take
  Faces search expressions such as `+@form+` and `+:bookTable+` (see
  xref:web/jsf/search-expressions.adoc[Search Expressions]); the rendered button carries an inline
  `+onclick="BsF.ajax.callAjax(...)"+` handler instead of a `+jakarta.faces.ajax+` behaviour.
* *`+actionListener+`, not `+action+`, on Faces 4.1.* That is the next section.
* *The table is client side.* `+b:dataTable+` renders every row into the HTML and attaches the DataTables plugin, which
  sorts, searches and pages in the browser (the rendered script calls `+.DataTable({...})+` with `+paging+`,
  `+searching+` and `+stateSave: true+`). With thousands of rows this sends all of them on every render; for large
  data use a server-side model, as in xref:web/jsf/data-tables-and-iteration.adoc[Data Tables and Iteration] and
  the lazy tables of the xref:web/jsf/primefaces-data-components.adoc#lazy[PrimeFaces data components page].
* *Input ids are prefixed.* The rendered `+b:inputText+` is a `+div+` with the client id `+searchForm:query+` around an
  `+input+` whose `+id+` and `+name+` are `+input_searchForm:query+` (both implementations). An `+f:ajax render+`
  target, a test selector or a hand-written `+POST+` must use the right one.

Table cells escape their values: with a fifth test book titled `+<b>Bold</b> & <script>alert(1)</script>+` added to
`+BookService+`, the cell contained `+&lt;b&gt;Bold&lt;/b&gt; &amp; &lt;script&gt;...+`, shown as text.

[#action-trap]
=== The ActionSource2 Trap on Faces 4.1

Faces 4.1 unified two interfaces. Until 4.0, `+UICommand+` implemented `+ActionSource2+`, which added the
`+action+` method expression to the listeners that `+ActionSource+` already had; in 4.1 `+ActionSource+` declares
`+getActionExpression()+` and `+setActionExpression()+` as default methods, `+UICommand+` implements only
`+ActionSource+`, and `+ActionSource2+` is deprecated for removal (the API says since 4.1). That is described in
xref:web/jsf/architecture-and-component-model.adoc[Architecture and the Component Model] and, for composite components,
in xref:web/jsf/composite-components.adoc#versions[Composite Components].

A library written against 4.0 that asks `+component instanceof ActionSource2+` now gets `+false+` for every `+UICommand+`.
BootsFaces 2.0.1 does exactly that: in `+AJAXRenderer.decode+` (read from the 2.0.1 bytecode, which matches the project's
source), a button gets an `+ActionEvent+` queued only if it has `+ActionListener+` instances _or_ is an `+ActionSource2+`
with a non-null action expression. On Faces 4.1 the second test is never true. The result, observed on Mojarra 4.1.17 and
MyFaces 4.1.4:

* `+<b:commandButton action="#{trapBean.run}"/>+`: the request arrives, the lifecycle runs, no `+ActionEvent+` is
  created, the method is not called, and nothing is logged or shown.
* `+<b:commandButton actionListener="#{trapBean.runListener}"/>+`: called.
* `+<h:commandButton action="#{trapBean.run}"/>+` in the same form: called.

The same page on Mojarra 4.0.26 (Faces 4.0) called `+action+` on the BootsFaces button. The check is in the renderer
the BootsFaces command components share; only `+b:commandButton+` was run here.

Source: https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/component/ActionSource.html[Jakarta Faces 4.1 API: ActionSource] and https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/component/ActionSource2.html[Jakarta Faces 4.1 API: ActionSource2]

Two remedies exist. Use `+actionListener+` on BootsFaces command components (a no-argument method worked, as in
`+CatalogueBean.search()+` above), or run on Faces 4.0 until the library is fixed. The project is not actively maintained,
so do not wait for a fix. And the general lesson is worth a tool: to find out whether an action reaches the default
action listener, decorate it. Faces lets a `+faces-config.xml+` replace the application's `+ActionListener+` with a class
whose constructor takes the original:

.ActionTraceListener.java and its registration -- a development aid
[source,java]
----
package org.example.bookshelf.web;

import jakarta.faces.event.AbortProcessingException;
import jakarta.faces.event.ActionEvent;
import jakarta.faces.event.ActionListener;
import java.util.logging.Logger;

/** Development aid: logs every ActionEvent the default ActionListener receives. */
public class ActionTraceListener implements ActionListener {

Observations:

* *Wrap the growl before updating it.* The first version updated the `+b:growl+` element by its own id. When the
  validation failed and the growl had nothing to show, Mojarra 4.1.17 left the literal text `+null+` in the page where the
  growl's `+<script>+` had been (MyFaces did not). Putting the growl inside an `+h:panelGroup layout="block"+` and
  updating that panel avoided it on both implementations, which is why the page does so.
* *`+b:growl+` does not escape by default: set `+escape="true"+`.* The tag's documentation says error messages encode
  HTML and script by default. They do not, for the growl: with the `+escape+` attribute left out, a reviewer name of
  `+Ana <img src=x onerror="window.__pwned=1">+` put a real `+img+` element into the notification and the handler ran
  (`+window.__pwned+` was `+1+`), on Mojarra 4.1.17 and MyFaces 4.1.4. The reviewer name reaches the message through
  `+ReviewBean.submit+`, so this is reflected user input rendered as HTML. With `+escape="true"+` (as in the
  page above) the same input was shown as text and nothing ran. `+b:messages+`, which the layout also updated in the same
  test, escaped the markup without being asked.
* *Escaping changes the text.* With `+escape="true"+` the growl displayed `+3/5+` as `+3-5+`: the slash is replaced by a
  dash, on both implementations. Avoid `+/+` in growl texts, or accept the dash.
* *`+f:validateLength+` works as a child.* The standard validators attach to BootsFaces inputs like to any `+EditableValueHolder+`
  (see xref:web/jsf/validators.adoc[Validators]).
* *Bean Validation is separate.* BootsFaces has `+b:fetchBeanInfos+` to copy Bean Validation constraints to the client; it
  was not run. The server side works as described in xref:web/jsf/bean-validation.adoc[Bean Validation].

[#bootsfaces-security]
=== Security and Production Notes

* *Bootstrap 3 is end of life.* The bundled `+core.css+` is Bootstrap 3.4.1. The Bootstrap project announced on
  2019-07-24 that Bootstrap 3 moved to end of life and no longer receives security updates; BootsFaces ships it
  unchanged, and the project is not maintained actively. The components still work, but the front end is frozen.
* *Inline scripts and handlers.* Command buttons render `+onclick="BsF.ajax.callAjax(...)"+` and several components emit
  inline `+<script>+` elements. A Content Security Policy without `+'unsafe-inline'+` (see
  xref:web/jsf/security.adoc#csp[Content Security Policy]) blocks those. Neither the Mojarra nonce setting nor PrimeFaces' CSP mode is documented to cover another library's
  markup. Plan for a policy that allows inline script, or do not use BootsFaces where a strict policy is required. This
  follows from the rendered markup and the CSP rules; the browser was not run against a strict policy.
* *Transitive dependencies.* Guava 32.0.1-jre and OWASP html-sanitizer 20220608.1 come with the jar. Run your dependency
  scanner over them: they stay at the versions the 2024 build used, and a fixed Guava or sanitizer will not arrive through a
  BootsFaces release. Overriding them in your own dependency management is the usual way out (not tried here).
* *Escaping.* The table cells and `+b:messages+` escape by default (both shown above); the growl does not, as observed in the
  last section, so set `+escape="true"+` on it and never set `+escape="false"+` on a component that shows user text; see
  xref:web/jsf/security.adoc#xss[Cross-Site Scripting and the escape Attribute].
* *Performance.* The page weight of `+b:dataTable+` (DataTables, pdfmake and a font file for the export buttons, all
  loaded when the table is present) is the thing to measure; see xref:web/jsf/performance.adoc[Performance].

[#tobago-sheet]
=== The Sheet: Sorting and Paging

`+tc:sheet+` is Tobago's data table. It has `+rows+`, a paginator, `+sortable+` columns, selection (`+selectable+`) and
`+lazy+` and `+lazyRows+` attributes for lazy loading (named in the tag library, not run). The page above sorts by title;
clicking the header sorted the five rows ascending and a second click descending on both implementations.

The first version of `+CatalogueBean+` returned the list that `+BookService+` built with `+List.of(...)+`, and clicking the
header changed nothing; the server log held the unhandled warning "Cant sort the column" (Tobago's own message text). Tobago's
`+SortingUtils+` calls `+Collections.sort+` on the bound `+List+` itself, so an immutable list fails. The bean above copies the list
(`+new ArrayList<>(...)+`) per view, which is also the right scope: sorting a list shared by users would reorder it for
everyone.

[#tobago-security]
=== Built-In Security

Tobago ships more security defaults than the other libraries on this page. All of it was observed:

* *Response headers.* Every page response fetched carried `+X-Frame-Options: DENY+`, `+X-Content-Type-Options: nosniff+`,
  `+Cache-Control: no-cache,no-store,max-age=0,must-revalidate+` and a
  `+Content-Security-Policy+` of `+style-src 'unsafe-inline' 'nonce-...' 'self';script-src 'self';frame-ancestors 'none';+`.
  Its `+script-src 'self'+` means the library renders no inline script. The `+tobago-config.xml+` schema documents
  `+prevent-frame-attacks+`, `+set-nosniff-header+` and `+content-security-policy+` (with mode `+on+`, `+off+` or
  `+report-only+` and `+directive+` elements) to adjust them.
* *A session secret.* Each rendered form contains a hidden field `+org.apache.myfaces.tobago.webapp.Secret+`. The schema
  documents `+create-session-secret+` and `+check-session-secret+`, both `+true+` by default, and the library's phase
  listener checks the field. A POST that carried a correct view state and the right button but no secret, or a wrong one,
  returned the page again with a new secret and did _not_ run the action (no message, `+search+` not called) on both
  implementations; the same POST with the secret ran it. This is a CSRF defence on top of the view state (see
  xref:web/jsf/security.adoc#csrf[Cross-Site Request Forgery]). The project's blank example turns both checks off in its
  `+tobago-config.xml+`; do not copy that into an application.
* *Escaping and sanitizing.* `+tc:out+` escapes by default. With `+escape="false"+` it sanitizes the HTML with jsoup
  (a `+relaxed+` safelist by default; the schema documents a `+sanitizer+` element to change it), and `+sanitize="never"+`
  turns that off. On a string containing `+<b>+`, `+<script>+`, an `+<img onerror>+` and a `+javascript:+` link:

    <tc:out id="escaped" label="Default" value="#{rawHtmlBean.hostile}"/>
    <tc:out id="sanitized" label="escape=false" value="#{rawHtmlBean.hostile}" escape="false"/>

.RawHtmlBean.java

----

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Named;

/** Stands for text a visitor typed: it contains markup that must never reach the page as markup. */
@Named
@RequestScoped
public class RawHtmlBean {

    public String getHostile() {
        return "<b>bold</b><script>alert(1)</script><img src=x onerror=alert(2)>"
                + "<a href=\"javascript:alert(3)\">link</a>";
    }
}
----

Source: https://github.com/apache/myfaces-tobago/blob/tobago-6.12.2/tobago-core/src/main/resources/org/apache/myfaces/tobago/config/tobago-config-5.1.xsd[Tobago 6.12.2: tobago-config-5.1.xsd] and the `+sanitize+` and `+escape+` entries of `+META-INF/tobago.taglib.xml+`

The three outputs, identical on Mojarra and MyFaces:

[cols="2,5",options="header"]
|===
|Attributes |Rendered inside the output element

|default
|`+&lt;b&gt;bold&lt;/b&gt;&lt;script&gt;...+`: everything as text

|`+escape="false"+`
|`+<b>bold</b><img><a>link</a>+`: the script element is gone, `+onerror+` and the `+javascript:+` `+href+` are removed

|`+escape="false" sanitize="never"+`
|the string exactly as given, including `+<script>+`, `+onerror+` and the `+javascript:+` link
|===

visitor typed, and treat `+sanitize="never"+` as a bug unless the string is trusted markup you wrote.

[#tobago-differences]
=== Mojarra, MyFaces and Tobago

* *Render kit.* Tobago's `+faces-config.xml+` sets `+tobago+` as the default render kit, and every form carries a hidden
  `+jakarta.faces.RenderKitId+` field with that value. A page that mixes `+h:*+` components into a Tobago page was not
  tried; stay with `+tc:*+` tags and the standard non-visual `+f:*+` ones. The same field is why a migration to or from
  Tobago touches every page, and why a half-removed Tobago jar changes how plain Faces pages render.
* *Both implementations ran.* The same two pages worked on Mojarra 4.1.17 and MyFaces 4.1.4. The only visible
  difference was in markup: Mojarra wrote the page's `+<?xml ... ?>+` declaration before the `+<!DOCTYPE html>+` of a
  page that begins with one, and MyFaces did not.
* *Ids.* Tobago uses `+::+` inside its generated ids (`+j_id_2::form+`, `+j_id_2:query::field+`), so selectors for tests must
  escape the colons, or find elements by their `+tobago-*+` custom element.
* *The exception handler.* `+enable-tobago-exception-handler+` is `+true+` by default; it replaced the error response with
  a generic "An unknown error has occurred!" page in a run where a tag attribute was wrong (the cause was only in the
  server log). Keep the log open while developing, or turn it off in `+tobago-config.xml+` in development.

== AdminFaces

AdminFaces is a family of projects on GitHub (`+adminfaces+`): `+admin-theme+`, a PrimeFaces theme styled after Bootstrap
and AdminLTE; `+admin-template+`, a Facelets admin layout (sidebar, top bar, breadcrumbs, error pages, session-expiry

Observed, on both Mojarra 4.1.17 and MyFaces 4.1.4:

* *With the template's own PrimeFaces 12.0.0 and OmniFaces 4.1* the page rendered with the admin theme
  (`+theme.css+` from the `+primefaces-admin+` library) and the Ajax search worked. The PrimeFaces 12 tag library only knows the
  `+http://primefaces.org/ui+` namespace: with `+xmlns:p="primefaces"+` the `+p:*+` tags were printed into the page as text.
* *With PrimeFaces 16.0.0 and OmniFaces 5.5.5 substituted* (the POM above) the template rendered, the sidebar was present,
  and the search updated the table. That was a smoke test of one page; the layout was not compared with a PrimeFaces 12
  render, and untested components may differ, since the theme was written for PrimeFaces 12.
* *The template needs two APIs that Tomcat does not have.* Its exception handler loads `+jakarta.ejb.EJBException+` and
  `+jakarta.persistence.OptimisticLockException+` by name, and its web fragment declares an error page for
  `+jakarta.ejb.AccessLocalException+`. On Tomcat 11 with Weld, the first request ended in
  `+ClassNotFoundException: jakarta.ejb.EJBException+` and the Ajax search failed (`+Request return with error+` in the
  browser console) until `+jakarta.ejb-api+` and `+jakarta.persistence-api+` were added, as in the POM. A Jakarta EE
  server that has both APIs needs neither entry.
* *Action methods and listeners* behaved normally: `+p:commandButton action=...+` ran (PrimeFaces is not affected by
  the ActionSource2 change).

Treat AdminFaces as a theme-and-template kit whose upstream moves slowly: pin its version, test the exact PrimeFaces version
you use, and look at the PrimeFaces components pages of this section for the components themselves.

[#discontinued]
== Libraries That Ended

The JSF books of the 2000s lean on libraries whose projects have ended. None of them can be used with Faces 4.1: their
newest jars extend `+javax.faces+` classes, and Faces 3.0 renamed the packages without a compatibility layer. This section records the
evidence, so that a project that still carries them knows what it is replacing.

[#rf]
=== RichFaces

RichFaces was the JBoss component framework, with two tag libraries: `+a4j+` (page-centric Ajax: `+a4j:ajax+`,
`+a4j:commandButton+`, `+a4j:poll+`, `+a4j:push+`, `+a4j:jsFunction+`, `+a4j:status+`) and `+rich+` (self-contained
components: `+rich:dataTable+`, `+rich:extendedDataTable+`, `+rich:popupPanel+`, `+rich:tabPanel+`, `+rich:calendar+`,
`+rich:fileUpload+`, `+rich:autocomplete+`, `+rich:select+`, `+rich:dataScroller+`). The 4.5 component reference documents
all of those. The project page states that RichFaces reached end-of-life in June 2016; the last 4.x release on Maven
Central is `+org.richfaces:richfaces:4.5.17.Final+` (2016-06-20), the GitHub repository is archived (last push
2018-03-26), and the RichFaces 5 alphas on Central stopped at `+5.0.0.Alpha3+`. The _JSF 2.0 Cookbook_ targets
RichFaces 3.3, one major version older still; a RichFaces 3 component such as `+rich:modalPanel+` is not in the 4.5 reference, which has
`+rich:popupPanel+` instead.

Source: https://richfaces.jboss.org/[RichFaces project page] and https://docs.jboss.org/richfaces/latest_4_5_X/Component_Reference/en-US/html_single/[RichFaces 4.5 Component Reference]

[#icefaces]
=== ICEfaces

ICEfaces (ICEsoft) added Ajax and the ICEpush Ajax-push engine to Faces, with a component set published as the
`+icefaces-ace+` artifact. Its open-source
line stopped on Maven Central at 4.3.0 (2018-08-27); that POM depends on `+javax.faces+` and `+javax.servlet-api+`, so the
published artifacts are pre-Jakarta. The vendor site still presents ICEfaces with a commercial Enterprise Edition; whether
that edition supports Faces 4.1 is something to ask the vendor, because nothing public on Central shows it.

Source: https://icesoft.com/icefaces/[ICEsoft: ICEfaces] and https://central.sonatype.com/artifact/org.icefaces/icefaces/4.3.0[Maven Central: org.icefaces:icefaces:4.3.0]

[#tomahawk]
=== MyFaces Tomahawk

Tomahawk (`+t:+`, namespace `+http://myfaces.apache.org/tomahawk+`) was the MyFaces extension set from the JSF 1.1 era:
`+t:saveState+`, `+t:inputFileUpload+`, `+t:inputDate+`, `+t:inputCalendar+`, `+t:dataTable+`, `+t:tree2+` and many more (all
present in the 1.1.14 tag library). The MyFaces site lists it under Inactive Projects (Maintenance Mode); the last
artifacts on Central (`+tomahawk21+` 1.1.14) are dated 2012-10-23.

Source: https://myfaces.apache.org/#/inactiveProjects[Apache MyFaces: Inactive Projects] and https://repo1.maven.org/maven2/org/apache/myfaces/tomahawk/tomahawk21/[Maven Central: tomahawk21]

[#trinidad]
=== MyFaces Trinidad

Trinidad (`+tr:+`, namespace `+http://myfaces.apache.org/trinidad+`) is the former Oracle ADF Faces: a large enterprise
component set with partial-page rendering, client-side validation, a dialog framework and `+pageFlowScope+`. It is also
under Inactive Projects (Maintenance Mode); `+trinidad-api+` 2.2.1 (2017-07-21) is the newest on Central.

Source: https://myfaces.apache.org/#/inactiveProjects[Apache MyFaces: Inactive Projects] and https://repo1.maven.org/maven2/org/apache/myfaces/trinidad/trinidad-api/[Maven Central: trinidad-api]

look), then replace components one family at a time while a page-level test (see xref:web/jsf/testing.adoc[the testing page] in the production

duplicate-request bugs of the old days came about. For the `+javax+` to `+jakarta+` step of an application as a whole, see
xref:web/jsf/migrating-to-jakarta-faces.adoc[the migration page] (see its xref:web/jsf/migrating-to-jakarta-faces.adoc#libraries[libraries section]).

== Choosing

Using what was observed:

.Choosing a component library for Faces 4.1
[cols="2,3,3",options="header"]
|===
|Need |Choice |Why

|Rich components, themes, large community
|PrimeFaces (its own pages)
|Active, ships its own CSP support, Faces 4.1 in the same release train

|Bootstrap grid and forms with a few widgets, small team, short life
|BootsFaces only after a test of every component you use
|Quick to start, but Bootstrap 3, no releases since 2024 and the ActionSource2 trap above

|Security-first business application, accepts a component model of its own
|Tobago
|Headers, session secret and sanitizing built in; active releases; the cost is a different page model (`+tc:page+`, its render kit)

|An admin UI with a ready sidebar and top bar
|AdminFaces' template, or build the layout on PrimeFaces' own layout components
|Fast; but pinned to the PrimeFaces 12 era in its POM and quiet upstream

|Plain Faces plus a few utilities
|Standard components with OmniFaces
|Nothing to migrate later
|===

A library page is only as good as the answers to the six questions in <<plugging-in>>. Three cheap tests are worth running before
adopting any library on Faces 4.1: one page with a command component using `+action+`, one Ajax update of a component
that renders a `+<script>+`, and one message or output component fed with `+<img src=x onerror=...>+`. The three surprises
in this page came from exactly those (the silent button, the growl that left `+null+`, and the growl that ran the
handler).

[#implementations]
== Mojarra and MyFaces

* *Tobago* ran on both with identical rendering; the one difference noted was the XML declaration Mojarra writes before
  the doctype. Tobago's project lists both implementations as supported.
* *BootsFaces* ran on both. The `+action+` problem is the same on both because it comes from the interface change, and the
  growl `+null+` text appeared only on Mojarra.
* *AdminFaces* ran on both, with PrimeFaces 12 and with 16.
* A library that decorates the `+ActionListener+`, `+ViewHandler+` or `+ExceptionHandler+` behaves differently when two of
  them are on the classpath; AdminFaces installs an exception handler of its own, which is the reason it needed the EJB
  and Persistence classes.

[#versions]
== What Changed in Which Version

* *Faces 3.0:* the `+javax.faces+` packages became `+jakarta.faces+`; every library that was not rebuilt stopped working. The
  libraries that ended (RichFaces, ICEfaces, Tomahawk, Trinidad) never were.
* *Faces 4.0:* JSP and several old APIs were removed. BootsFaces 2.0.0 and Tobago 6.0.0 are the releases for it (BootsFaces'
  README: Faces 4.0 and Jakarta EE required; Tobago's table: 6.x lists JSF 4.0).
* *Faces 4.1:* `+ActionSource+` and `+ActionSource2+` unified, the latter deprecated for removal. A library written for
  4.0 can compile and run on 4.1 and still misbehave (BootsFaces).
* *Faces 5.0 (upcoming):* only a milestone as of this writing (`+5.0.0-M9+`); the deprecated `+ActionSource2+` may be
  removed from it, and none of the libraries here was tried on it. Plan the library audit when 5.0 is released.
* *BootsFaces:* 0.x to 1.5 on `+javax+`; 2.0.0 and 2.0.1 on Jakarta, Java 11 (2.0.1 on 2024-09-02).
* *Tobago:* 4.x (JSF 2.x, Java 8), 5.x (JSF 2.3, Java 17), 6.x (JSF 4.0, Java 17, Bootstrap 5 based).
* *AdminFaces:* `+admin-template+` 1.6.1 targets Jakarta EE 9.1 with PrimeFaces 11 (`+jakarta+` classifier) and offers a
  `+legacy+` classifier for `+javax+`; 2.0 (2023-05-07) targets Jakarta EE 10 with PrimeFaces 12.

[#outdated]
== Where the Books Are Outdated

The _JSF 2.0 Cookbook_ (2010) is where the libraries of this page appear most: its recipes target JSF 2.0 with
RichFaces 3.3, PrimeFaces 2.0, Tomahawk, Trinidad, Seam 2 and Spring 2.5, and about half of them rely on an extension library. Today
RichFaces, Tomahawk and Trinidad are ended or in maintenance mode, Seam 2 and Spring 2.5 are long gone, and the standard
solutions replaced many of those recipes (file upload with `+h:inputFile+`, Ajax with `+f:ajax+`, scopes with CDI). Use the
tables above to map any recipe to its present counterpart. _JavaServer Faces 2.0: The Complete Reference_ covers the
standard component library and extension points but predates every library here, and the render-kit chapters of _Pro JSF
and Ajax_ (2006) are about rich-component frameworks of the JSF 1.x era (the skin and render kit mechanisms of ICEfaces,
Trinidad and RichFaces); the render-kit theory still holds, the libraries do not. The _PrimeFaces Cookbook_ and _Learning
PrimeFaces Extensions Development_ cover PrimeFaces and PrimeFaces Extensions, not these libraries, and are discussed on the
PrimeFaces pages. None of the books mentions BootsFaces, Tobago or AdminFaces, which appeared after or alongside them.

[#pitfalls]
== Pitfalls

* *Trusting "supports Jakarta EE 10" for Faces 4.1.* Test `+action+`, an Ajax update and a `+<script>+`-rendering component
  (<<action-trap>>).
* *`+b:commandButton action=+` on Faces 4.1.* Silently never called; use `+actionListener+`.
* *`+b:growl+` without `+escape="true"+`.* It renders user text in messages as HTML; set the attribute.
* *Updating `+b:growl+` by its own id.* Wrap it in a panel and update the panel.
* *`+b:dataTable+` with large lists.* The whole list is rendered and sorted in the browser.
* *Immutable lists in `+tc:sheet+`.* Sorting fails with an unhandled warning; copy the list per view.
* *Turning off Tobago's session secret or its sanitizer.* The blank example does the first; do not copy it. Never use
  `+sanitize="never"+` with user input.
* *Copying the `+xsi:schemaLocation+` of Tobago's examples.* The URL does not resolve.
* *AdminFaces on Tomcat.* Add the EJB and Persistence APIs, or errors turn into `+ClassNotFoundException+`.
* *Two jQuery versions.* BootsFaces skipped its copy when PrimeFaces' was present; other combinations were not tried.
* *Mixing component libraries on one page without testing.* Stylesheets collide even when scripts do not.
* *Keeping an ended library "for now".* Each year the gap to Jakarta Faces widens; plan the replacement before the next
  upgrade of the server, not during it.
