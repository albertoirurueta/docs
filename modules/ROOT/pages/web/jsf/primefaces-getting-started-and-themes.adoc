[#overview]
== What PrimeFaces Adds to Faces

PrimeFaces is a component library for Faces: tags in the `+p:+` namespace (176 tags in the 16.0.0 tag library, from
`+p:accordionPanel+` to `+p:wizard+`), a theme system, a JavaScript layer built on jQuery that every component talks to, and a
set of replacements for parts of the standard machinery. What the 16.0.0 jar registers on its own (read from its
`+META-INF/faces-config.xml+` and `+web-fragment.xml+`) is the reason a page with no explicit setup already behaves differently:

[cols="2,5"]
|===
|Registration |Effect

|Renderers for `+jakarta.faces.Head+` and `+jakarta.faces.Body+`
|`+h:head+` and `+h:body+` are rendered by PrimeFaces: they inject the theme, the icon font, the component styles and scripts, the
locale script and the client settings (<<head>>). A page without `+h:head+` receives none of it.

|`+PrimeResourceHandler+` (resource handler)
|Wraps resource handling: PrimeFaces resource URLs carry the parameter `+v=16.0.0+` (observed on the `+ln=primefaces+` URLs and absent on the
application's own `+ln=css+` URLs; <<params>>, `+HIDE_RESOURCE_VERSION+`), and the streamed content of components such as
`+p:graphicImage+` is served through it.

|`+PrimeFacesContextFactory+`, `+PrimePartialViewContextFactory+`
|PrimeFaces's own faces-context and partial-view-context factories, installed through the standard `+<factory>+` elements.

|Phase listeners `+AutoUpdatePhaseListener+`, `+CspPhaseListener+`, `+DialogKeepFlashPhaseListener+`
|Named after `+p:autoUpdate+`, the Content Security Policy support and the flash handling of the dialog framework.

|Validators for the ids `+jakarta.faces.Length+`, `+jakarta.faces.LongRange+`, `+jakarta.faces.DoubleRange+`,
`+jakarta.faces.RegularExpression+`, and twenty converters
|Classes in `+org.primefaces.validate+` and `+org.primefaces.convert+` registered under the standard ids, so once the jar is on the class path
every `+f:validateLength+` or standard converter of the application is served by a PrimeFaces class. Client-side validation is on the
xref:web/jsf/primefaces-ajax-forms-and-validation.adoc[the PrimeFaces Ajax, forms and validation page] of this section.

|`+PrimeServletContextListener+`, `+UploadedFileCleanerListener+`, `+<distributable/>+`, font MIME mappings (`+ttf+`, `+woff+`, `+woff2+`, `+eot+`, `+svg+`)
|Declared in the jar's `+web-fragment.xml+`, so a servlet container needs no `+web.xml+` entry for them.
|===

Source: https://primefaces.github.io/primefaces/16_0_0/#/gettingstarted/dependencies[PrimeFaces 16 documentation: Dependencies] and
https://github.com/primefaces/primefaces/blob/v16.0.0/primefaces/src/main/java/org/primefaces/renderkit/HeadRenderer.java[PrimeFaces 16.0.0 source: HeadRenderer]

The PrimeFaces jar also contains a `+beans.xml+` with `+bean-discovery-mode="all"+`, so a CDI container scans it. On a servlet
container that has no Bean Validation or Jakarta Persistence API on the class path, Weld 6.0.4 logged 36 `+WELD-000119+` lines at
`+INFO+` level ("Not generating any bean definitions from `+org.primefaces...+` because of underlying class loading error: Type
`+jakarta.validation...+` not found"). The application worked; the lines only mean that the optional PrimeFaces features
that need those APIs are off (<<dependencies>>).

== The Dependency and the Optional Libraries

PrimeFaces is one jar, `+org.primefaces:primefaces+`. Its published POM has no compile-scope dependency: `+mvn dependency:tree+` on
the project below lists the jar and nothing under it. The libraries PrimeFaces can use are declared `+provided+` or
`+optional+`, so each one reaches the WAR only if the application asks for it.

.pom.xml (excerpt) -- PrimeFaces, the extra themes and the libraries the Bookshelf pages use

[#head]
== The Head: What PrimeFaces Writes and in Which Order

The `+h:head+` of a PrimeFaces application is rendered by `+org.primefaces.renderkit.HeadRenderer+`, which replaces the standard
renderer of the type `+jakarta.faces.Head+`. Its class comment states the intended order: the `+first+` facet, the theme style
sheet, the PrimeIcons style sheet, the `+middle+` facet, the registered resources, the client validation scripts, the locale script,
the `+PrimeFaces.settings+` script, the initialisation scripts, the content of the `+h:head+` element and the `+last+` facet. The three
facets are PrimeFaces additions to `+h:head+`; the standard element knows no facets.

Reading the response shows how that works in practice, because it differs in one detail from the comment. In the output the theme
and the icon style sheet come with the registered resources and not before the `+middle+` facet, so markup in the `+middle+`
facet arrives before `+theme.css+`. The probe page puts one plain `+link+` and one
`+h:outputStylesheet+` into each facet and into the head:

.order-css.xhtml -- a probe for the order of style sheets
[source,xml]
----
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:f="jakarta.faces.core"
      xmlns:h="jakarta.faces.html"
      xmlns:p="primefaces">
<h:head>
  <f:facet name="first">
    <link rel="stylesheet" href="#{resource['css:link-first.css']}"/>
    <h:outputStylesheet library="css" name="res-first.css"/>
  </f:facet>
  <title>Resource order</title>
  <h:outputStylesheet library="css" name="res-body.css"/>
  <link rel="stylesheet" href="#{resource['css:link-body.css']}"/>
  <f:facet name="middle">
    <link rel="stylesheet" href="#{resource['css:link-middle.css']}"/>
    <h:outputStylesheet library="css" name="res-middle.css"/>
  </f:facet>
  <f:facet name="last">
    <link rel="stylesheet" href="#{resource['css:link-last.css']}"/>
    <h:outputStylesheet library="css" name="res-last.css"/>
  </f:facet>
</h:head>
<h:body>
  <h:form><p:inputText/></h:form>
</h:body>
</html>
----

Source: https://github.com/primefaces/primefaces/blob/v16.0.0/primefaces/src/main/java/org/primefaces/renderkit/HeadRenderer.java[PrimeFaces 16.0.0 source: HeadRenderer] and https://jakarta.ee/specifications/faces/4.1/vdldoc/h/outputStylesheet.html[Jakarta Faces 4.1 VDL: h:outputStylesheet]

The style sheets arrived in this order (observed; `+res-*+` are the `+h:outputStylesheet+` resources, `+link-*+` the plain links, all
in the library or directory `+css+`):

[cols="1,3,3",options="header"]
|===
|# |Mojarra 4.1.17 |MyFaces 4.1.4

|1 |`+link-first+` |`+link-first+`
|2 |`+link-middle+` |`+link-middle+`
|3 |`+theme.css+` (`+ln=primefaces-saga-blue+`) |`+theme.css+`
|4 |`+primeicons/primeicons.css+` |`+primeicons/primeicons.css+`
|5 |`+res-body+` |`+res-body+`
|6 |`+res-last+` |`+res-first+`
|7 |`+res-first+` |`+res-middle+`
|8 |`+res-middle+` |`+res-last+`
|9 |`+components.css+` (added by `+p:inputText+`) |`+components.css+`
|10 |`+link-body+` |`+link-body+`
|11 |`+link-last+` |`+link-last+`
|===

What follows from it:

* A plain element in the `+first+`, `+middle+` or `+last+` facet or directly in `+h:head+` is written where the order above puts it. An
`+h:outputStylesheet+` is a resource component: wherever it is written (in a facet too) it joins the list of registered
resources and is written there. A facet therefore does not move a resource component. On Mojarra the four resource components
arrived in the order body, last, first, middle; on MyFaces in the order they were declared. The probe page differs only by
that. Do not rely on the relative order of resources declared in different facets.
* The application's `+h:outputStylesheet+` resources arrived before `+components.css+` (the likely reason is that the PrimeFaces
component that pulls `+components.css+` in sits in the body and is processed after the head; the order itself was observed). At equal specificity `+components.css+` and the theme
therefore win over a style sheet declared with `+h:outputStylesheet+`.
* The plain `+link+` elements in `+h:head+` or in the `+last+` facet arrived after the PrimeFaces style sheets and the scripts, so
their rules win. The expression `+#{resource['css:link-last.css']}+` (library `+css+`, name `+link-last.css+`) produces the right
URL for a resource library; see xref:web/jsf/resource-handling.adoc#identifier[resource identifiers].
* `+h:outputScript+` is different. In a separate run (both implementations) a script written in the `+first+` facet was written in that
facet, ahead of `+theme.css+`, and scripts written in `+h:head+` and in the `+last+` facet came after the PrimeFaces scripts, in the places
of the plain elements.

[mermaid]
----
flowchart TB
    start["h:head encodeBegin: PrimeFaces HeadRenderer"]
    first["first facet: plain markup"]
    middle["middle facet: plain markup"]
    reg["registered resources: theme.css, primeicons.css, application style sheets, components.css, jquery.js, core.js, components.js, locale script"]
    settings["PrimeFaces.settings script and initialisation scripts"]
    children["children of h:head: plain markup, h:outputScript"]
    last["last facet: plain markup, then the closing head tag"]
    start --> first --> middle --> reg --> settings --> children --> last
----

Source: https://github.com/primefaces/primefaces/blob/v16.0.0/primefaces/src/main/java/org/primefaces/renderkit/HeadRenderer.java[PrimeFaces 16.0.0 source: HeadRenderer]

The consequence for styling is the layout the Bookshelf uses: the application's own rules go into a plain `+link+` in the `+last+`

.WEB-INF/templates/layout.xhtml (head excerpt) and resources/css/bookshelf.css (one rule)
[source,xml]
----
<h:head>
  <f:facet name="first">
    <meta charset="UTF-8"/>
    <meta name="viewport" content="width=device-width, initial-scale=1"/>
  </f:facet>
  <title>#{msg['app.name']}</title>
  <ui:insert name="head"/>
  <f:facet name="last">
    <link rel="stylesheet" href="#{resource['css:bookshelf.css']}"/>
  </f:facet>

----

[source,css]
----
.ui-button.bookshelf-accent { background: #6f42c1; border-color: #6f42c1; }
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/themes[PrimeFaces 16 documentation: Themes]

The selector has two classes, so it beats the theme's `+.ui-button+` rule whatever the order of the files. In headless Chrome the
button computed to `+rgb(111, 66, 193)+`, the accent colour, and not to the Saga Blue `+rgb(33, 150, 243)+`.

*A page without `+h:head+` gets nothing.* The renderers are attached to the standard tags. A page that uses the plain HTML elements
`+<head>+` and `+<body>+` rendered the PrimeFaces component markup but no `+link+` and no `+script+` of PrimeFaces on Mojarra and on
MyFaces: no theme, no icons, no widgets. Use `+h:head+` and `+h:body+` in every template and view that holds PrimeFaces
components. Faces keeps one renderer per type, so a second library that registers its own `+jakarta.faces.Head+` renderer would replace the
PrimeFaces one; that case was not tested, so check such a combination in a test.

*Moving the scripts to the end of the body.* `+primefaces.MOVE_SCRIPTS_TO_BOTTOM+` set to `+true+` removed every `+script+` element from
the head and wrote all of them, the PrimeFaces resources, the settings script and the initialisation scripts included, at the end
of the body (observed on the hello page: six script elements in the head and two inline widget scripts in the body without the parameter; none in
the head and six at the end of the body with it, five resource scripts and one inline script; both widgets of the page were
created in all three modes). The value `+defer+` additionally gave each resource script
a `+defer="defer"+` attribute and merged the initialisation scripts into one `+DOMContentLoaded+` handler that removes its own
element. The page paints before the scripts run, which is the performance advantage the PrimeFaces performance page names
(see xref:web/jsf/performance.adoc#primefaces[the PrimeFaces part of the performance page]). Test inline scripts of your own that call
`+PrimeFaces+` or jQuery, because they now run before the library is loaded.

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/performance[PrimeFaces 16 documentation: Performance]

[#lifecycle]
== Where the Setup Sits in the Request Processing Lifecycle

The setup features of this page touch the lifecycle (xref:web/jsf/request-processing-lifecycle.adoc#phases[the six phases]) in few
places, and knowing which ones explains the theme behaviour above:

[cols="3,6",options="header"]
|===
|Moment |What happens

|Application start
|The context parameters are read; `+PostConstructApplicationEvent+` and `+PreDestroyApplicationEvent+` listeners of the jar
(`+PostConstructApplicationEventListener+`, `+PreDestroyApplicationEventListener+`) are registered in its `+faces-config.xml+`. A changed parameter needs a restart: every test of this page restarted the application after changing one. Only the
expression in `+primefaces.THEME+` is evaluated again on each request.

|xref:web/jsf/request-processing-lifecycle.adoc#restore-view[Restore View] to xref:web/jsf/request-processing-lifecycle.adoc#process-validations[Process Validations]
|Nothing of this page. A theme chooser is an ordinary input: the value is converted and validated like any other (a posted theme
that is not in the menu stopped here with a validation error).

|xref:web/jsf/request-processing-lifecycle.adoc#update-model-values[Update Model Values]
|`+PrimeThemeBean.setName+` runs, so the new theme is already in the bean when the next phase starts.

|xref:web/jsf/request-processing-lifecycle.adoc#invoke-application[Invoke Application]
|`+PrimeThemeBean.apply+` runs and returns the outcome with `+faces-redirect=true+`; the lifecycle ends with a redirect and no Render Response.

|xref:web/jsf/request-processing-lifecycle.adoc#render-response[Render Response]
|Everything else. `+HeadRenderer.encodeBegin+` evaluates `+primefaces.THEME+` and writes the head resources, the locale script and the
settings (the settings gain `+projectStage:'Development'+` when the project stage is not `+Production+`, observed for `+Development+`); `+encodeEnd+` writes the
`+last+` facet. The three phase listeners that PrimeFaces registers
(`+AutoUpdatePhaseListener+`, `+CspPhaseListener+`, `+DialogKeepFlashPhaseListener+`) are all registered for the Render Response phase (source).
|===

Source: https://github.com/primefaces/primefaces/blob/v16.0.0/primefaces/src/main/java/org/primefaces/renderkit/HeadRenderer.java[PrimeFaces 16.0.0 source: HeadRenderer] and
https://jakarta.ee/specifications/faces/4.1/jakarta-faces-4.1.html#a401[Jakarta Faces 4.1 specification, 2.2 Standard Request Processing Lifecycle Phases]

[#params]
== The Context Parameters

PrimeFaces needs no configuration ("configuration by exception"). Everything that can be configured is a `+context-param+` in
`+web.xml+` named `+primefaces.NAME+`. The table lists every name the 16.0.0 jar reads (the 22 names of the documentation's
configuration table, plus `+CACHE_PROVIDER+`, `+PUBLIC_CAPTCHA_KEY+` and `+PRIVATE_CAPTCHA_KEY+` that belong to the cache and captcha
components, and the three standard parameters it also reads). Parameters are read once when the application starts, with two things
to know about expressions: `+HeadRenderer+` evaluates the value of `+THEME+` as a value expression on every request, and the
configuration evaluates the value of `+CSP+` as an expression once, while it is built (source). The last column says what was run.

[cols="3,2,6,3",options="header"]
|===
|Parameter |Default |Effect |Checked

|`+THEME+` |`+saga-blue+` |Theme library; `+none+` writes no theme link; `+saga+`, `+arya+` and `+vela+` are accepted as short names; a value expression is evaluated on every request (<<themes>>) |observed

buster, so after an upgrade a browser that cached `+components.js+` may keep the old file until its cache expires (the resource
handling page covers the cache headers: xref:web/jsf/resource-handling.adoc#caching[caching headers]).

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/misc[PrimeFaces 16 documentation: Misc]

[#themes]
== Themes

A PrimeFaces theme is a resource library named `+primefaces-<name>+` that holds one file, `+theme.css+`. `+HeadRenderer+` takes the value of
`+primefaces.THEME+` (default `+saga-blue+`), evaluates it as a value expression, and writes a link to `+theme.css+` in the library
`+primefaces-+` plus that value. The theme is a style sheet for the `+ui-*+` classes that `+components.css+` and the renderers use, and it
defines the colours, the fonts and the CSS custom properties (`+--surface-a+`, `+--primary-color+`, `+--text-color+` and others) of the page.

[#themes-available]
=== The themes that ship

Only `+saga-blue+` is inside `+primefaces-16.0.0.jar+`. Every other theme is in the separate `+primefaces-themes+` jar (since PrimeFaces
15.0.0, when the themes moved out of the main jar), which has the same version number as PrimeFaces. The 16.0.0 themes jar holds
the theme libraries below (listed from the jar), plus the shared libraries `+primefaces-aura-common+` (fonts) and
`+primefaces-material-light-common+`, which are not themes, and a directory `+primefaces-mytheme+` that looks like a sample (its primary colour is `+#2196F3+`, as in
Saga Blue).

[cols="2,5",options="header"]
|===
|Family |Theme names (value of `+primefaces.THEME+`)

|Saga |`+saga-blue+` (white surface, in the main jar; the default)
|Vela |`+vela-blue+` (dark surface)
|Arya |`+arya-blue+` (dark surface)
|Aura |`+aura-light-emerald+`, `+aura-dark-emerald+`
|Bootstrap 4 |`+bootstrap4-blue-light+`, `+bootstrap4-blue-dark+`, `+bootstrap4-purple-light+`, `+bootstrap4-purple-dark+`
|Material |`+material-indigo-light+`, `+material-indigo-dark+`, `+material-deeppurple-light+`, `+material-deeppurple-dark+`
|Material compact |`+material-compact-indigo-light+`, `+material-compact-indigo-dark+`, `+material-compact-deeppurple-light+`, `+material-compact-deeppurple-dark+`
|Luna |`+luna-blue+`, `+luna-green+`, `+luna-amber+`, `+luna-pink+`
|Nova |`+nova-light+`, `+nova-dark+`, `+nova-colored+`

Saga, Vela and Arya are the base light and dark themes. In the 16.0.0 jars their surface colour (`+--surface-a+`) was `+#ffffff+` (Saga Blue),
`+#1f2d40+` (Vela Blue) and `+#1e1e1e+` (Arya Blue), and their primary colour (`+--primary-color+`) `+#2196F3+`, `+#90CAF9+` and `+#90CAF9+`. Neither a
theme's name nor its CSS says reliably whether it is dark: `+vela-blue+`, `+nova-dark+` and `+aura-dark-emerald+` all declare `+color-scheme:light+`
in their CSS. Choose a theme by looking at it in the https://showcase.primefaces.org/[PrimeFaces showcase] (which refused scripted requests,
see the flags) and by testing the contrast of your own pages.

https://github.com/primefaces/primefaces/tree/v16.0.0/primefaces-themes[PrimeFaces 16.0.0 source: primefaces-themes]

The behaviour of the values, run on Tomcat 11.0.26 with the `+primefaces-themes+` jar on the class path:

[cols="3,6",options="header"]
|===
|Value |Result

|absent |`+theme.css.xhtml?ln=primefaces-saga-blue&v=16.0.0+`
|`+vela+`, `+saga+` (and `+arya+`) |Short names still work in 16.0.0: the link used `+ln=primefaces-vela-blue+` and `+ln=primefaces-saga-blue+`, and the file was served (HTTP 200, `+text/css+`); `+arya+` is mapped the same way in the source. [#themes-user]
=== A theme per user

Because `+HeadRenderer+` evaluates the parameter as an expression on every request, the theme can come from a bean. The Bookshelf
keeps the choice in a session-scoped bean (a user preference, not page state) and persists nothing else; a real application
would store it in the user's profile or in a preference cookie (xref:web/jsf/security.adoc#cookies[cookie attributes]).

.PrimeThemeBean.java
[source,java]
----
package org.example.bookshelf.web;

import jakarta.enterprise.context.SessionScoped;
import jakarta.faces.context.FacesContext;
import jakarta.inject.Named;
import java.io.Serializable;
import java.util.List;
import java.util.Set;

/** Holds the PrimeFaces theme chosen by the current user. */
@Named
@SessionScoped
public class PrimeThemeBean implements Serializable {

    private static final Set<String> ALLOWED = Set.of("saga-blue", "vela-blue", "arya-blue", "luna-green");

    private String name = "saga-blue";

    public List<String> getChoices() {
        return ALLOWED.stream().sorted().toList();
    }

    public String getName() {
        return name;
    }

    public void setName(String name) {
        if (ALLOWED.contains(name)) {
            this.name = name;
        }
    }

    /** Redirects to the current view so that the next response is built with the new theme only. */
    public String apply() {
        String viewId = FacesContext.getCurrentInstance().getViewRoot().getViewId();
        return viewId + "?faces-redirect=true";
    }
}
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/themes[PrimeFaces 16 documentation: Themes] and
https://jakarta.ee/specifications/faces/4.1/vdldoc/h/selectOneMenu.html[Jakarta Faces 4.1 VDL: h:selectOneMenu]

.web.xml (excerpt) and the form in the layout
[source,xml]
----
<context-param>
    <param-name>primefaces.THEME</param-name>
    <param-value>#{primeThemeBean.name}</param-value>
</context-param>
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/themes[PrimeFaces 16 documentation: Themes]

[source,xml]
----
<h:form id="themeForm" styleClass="bookshelf-theme">
  <p:outputLabel for="theme" value="#{msg['theme.label']}"/>
  <p:selectOneMenu id="theme" value="#{primeThemeBean.name}">
    <f:selectItems value="#{primeThemeBean.choices}"/>
  </p:selectOneMenu>
  <p:commandButton value="#{msg['theme.apply']}" icon="pi pi-palette"
                   action="#{primeThemeBean.apply}" ajax="false"/>
</h:form>
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/themes[PrimeFaces 16 documentation: Themes]

Three things in the bean are deliberate. The name goes into a resource library name, so it comes from a fixed list: the setter
ignores any other value, and the menu rejects it earlier (a posted `+evil+` produced a validation error, HTTP 200, and left the theme at
`+saga-blue+`). The action returns the current view id with `+faces-redirect=true+`, and the form uses `+ajax="false"+`. The reason is the
next table, which is the main pitfall of a per-user theme:

[cols="4,5",options="header"]
|===
|Response to the theme form |Theme links in the HTML (both implementations)

|`+302+` to the same view (`+faces-redirect=true+`), then `+GET+` |one: `+ln=primefaces-vela-blue+`
|`+200+`, the same view rendered again by the postback |two: `+ln=primefaces-vela-blue+`, then `+ln=primefaces-saga-blue+`
|===

After an ordinary postback that keeps the view the old theme link came back as well, after the new one, so the old theme wins the
cascade. The page showed the previous theme although the bean held the new one (the saved view is the likely source of the old
link; that was not verified). Redirecting to a fresh view, which is Post/Redirect/Get as on
xref:web/jsf/flash-and-post-redirect-get.adoc[the flash and Post/Redirect/Get page], gave one link.

[mermaid]
----
sequenceDiagram
    participant B as Browser
    participant F as FacesServlet
    participant T as primeThemeBean
    B->>F: POST themeForm with theme=vela-blue
    F->>T: setName vela-blue (Update Model Values)
    F->>T: apply (Invoke Application)
    T-->>F: outcome /catalogue.xhtml?faces-redirect=true
    F-->>B: 302 Location /bookshelf/catalogue.xhtml
    B->>F: GET /catalogue.xhtml
    F->>T: getName while h:head is rendered
    F-->>B: HTML with theme.css ln=primefaces-vela-blue
----

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-intro/faces-intro.html[Jakarta EE Tutorial: Introduction to Jakarta Faces]

*Changing the theme without leaving the page.* PrimeFaces has a client-side function for it, `+PrimeFaces.changeTheme(name)+`, which
replaces the library name in the `+href+` of the theme link. The 10.0.0 migration guide shows it as the replacement of the removed
ThemeSwitcher component, with an ordinary menu:

.themes-ajax.xhtml -- a menu that swaps the theme link in the browser
[source,xml]
----
<h:form id="frmTheme">
  <p:selectOneMenu id="themeSelectMenu" widgetVar="themeMenu" value="#{primeThemeBean.name}">
    <f:selectItems value="#{primeThemeBean.choices}"/>
    <p:ajax process="@this"
            oncomplete="PrimeFaces.changeTheme($('#frmTheme\\:themeSelectMenu_label').text());"/>
  </p:selectOneMenu>
</h:form>
----

Source: https://github.com/primefaces/primefaces/blob/v16.0.0/docs/migrationguide/10_0_0.md[PrimeFaces migration guide 10.0.0: ThemeSwitcher]

In headless Chrome, choosing `+vela-blue+` in the opened menu sent the value through `+p:ajax+` (a later request of the same session
rendered `+ln=primefaces-vela-blue+`) and changed the link in the open page; the button changed from `+rgb(33, 150, 243)+` to
`+rgb(144, 202, 249)+`. Calling `+PrimeFaces.changeTheme('vela-blue')+` from the console changes the page in the same way. The function changes only the browser; the next full page request uses whatever the
server-side expression returns, which is why the menu above also binds the value to the bean.

[#themes-custom]
=== A custom theme

There are two routes, and the first one can be run in minutes.

*Extend a ready-made theme.* A theme is just a style sheet in a library named `+primefaces-<name>+`, and Faces evaluates value
expressions inside style sheet resources (xref:web/jsf/resource-handling.adoc#el[expressions inside resource files]). A theme can
therefore import another theme and override rules after it:

.src/main/webapp/resources/primefaces-bookshelf/theme.css
[source,css]
----
@import url("#{resource['primefaces-saga-blue:theme.css']}");

/* Bookshelf brand colour on top of Saga Blue */
.ui-button:not(.ui-button-secondary) { background: #6f42c1; border-color: #6f42c1; }
.ui-button:not(.ui-button-secondary):enabled:hover { background: #5a32a3; border-color: #5a32a3; }
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/themes[PrimeFaces 16 documentation: Themes]

.web.xml (excerpt)
[source,xml]
----
<context-param>
    <param-name>primefaces.THEME</param-name>
    <param-value>bookshelf</param-value>
</context-param>
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/themes[PrimeFaces 16 documentation: Themes] and
https://jakarta.ee/specifications/faces/4.1/apidocs/jakarta.faces/jakarta/faces/application/ResourceHandler.html[Jakarta Faces 4.1 API: ResourceHandler]

On Mojarra and MyFaces the request for the theme returned the file with
`+@import url("/bookshelf/jakarta.faces.resource/theme.css.xhtml?ln=primefaces-saga-blue&v=16.0.0");+` in its first line, and in headless Chrome
a `+p:commandButton+` computed to `+rgb(111, 66, 193)+`, the brand colour. This costs a second request for the imported file and
it relies on the selectors of the imported theme (the `+:not(...)+` guard keeps the secondary buttons of the theme intact); it is
fine for small adjustments and for a prototype.

*Build a theme from the sources.* A production theme is compiled from SCSS. The `+primefaces-themes+` module of the PrimeFaces
repository holds `+theme-base+` (the layout and structure of all components) and `+themes+` (one folder per theme with
`+_variables.scss+`, `+_extensions.scss+` and a `+theme.scss+` that imports the variables, the base and the extensions). The 16.0.0 files of
Saga Blue start like this, and the build is `+mvn dart-sass:compile-sass+` (README of the module):

.primefaces-themes/themes/primefaces-saga-blue/theme.scss and the head of _variables.scss (PrimeFaces 16.0.0 source)
[source,scss]
----
@import './variables';
@import '../../theme-base/_components';
@import './_extensions';

/* _variables.scss */
$primaryColor: #2196F3 !default;
$primaryTextColor: #ffffff !default;
$shade000: #ffffff !default;    // surface
$shade700: #495057 !default;    // text color
----

Source: https://github.com/primefaces/primefaces/tree/v16.0.0/primefaces-themes[PrimeFaces 16.0.0 source: primefaces-themes]

A new theme is a new folder with its own variables, built by the same Maven plugin into `+META-INF/resources/primefaces-<name>/theme.css+`
in a jar or a `+resources/primefaces-<name>/theme.css+` folder in the WAR; the `+_extensions.scss+` file is the place for
customisations (its comment says "Customizations to the designer theme should be defined here"). The PrimeFaces documentation also
points to a community template repository that creates a theme without forking the whole module. The SCSS route was read from
the sources and not compiled for this page. The theme designer, the visual tool that produces such SCSS themes (the comment in
`+_extensions.scss+` speaks of "the designer theme"), could not be examined: the vendor's web site answers scripted requests with a
bot-protection page that this work does not bypass, so the tool is not described here; both points are listed in the flags.

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/themes[PrimeFaces 16 documentation: Themes] and
https://github.com/primefaces/primefaces/tree/v16.0.0/primefaces-themes[PrimeFaces 16.0.0 source: primefaces-themes]

[#themes-removed]
=== Themes and components that no longer exist

* *ThemeRoller themes.* Until PrimeFaces 14 the themes were jQuery UI ThemeRoller style sheets, distributed as the `+org.primefaces.themes+`
artifacts and picked from a gallery. The 15.0.0 migration guide states that "Legacy ThemeRoller themes are no longer supported and
will not render correctly". A theme name from a book such as `+bluesky+` or `+cupertino+` does not exist in 16.
* *`+p:themeSwitcher+`.* Deprecated in 10.0.0 and removed in 11.0.0; it is not among the 176 tags of the 16.0.0 tag library. Use a
menu and `+PrimeFaces.changeTheme+` or the per-user bean above.
* *The `+aristo+` and `+omega+` themes* were removed in 10.0.0 and `+saga+` became the default; the setting `+primefaces.THEME_FORMS+`
disappeared in 3.1.

Source: https://github.com/primefaces/primefaces/blob/v16.0.0/docs/migrationguide/15_0_0.md[PrimeFaces migration guide 15.0.0] and
https://github.com/primefaces/primefaces/blob/v16.0.0/docs/migrationguide/10_0_0.md[PrimeFaces migration guide 10.0.0]

[#icons]
== Icons: PrimeIcons and Font Awesome

*PrimeIcons* is the icon font of the PrimeTek libraries. It is part of the PrimeFaces jar (the font in five formats under
`+primefaces/vendor/primeicons/fonts+` and `+primeicons/primeicons.css+`), `+HeadRenderer+` includes it by default, and the parameter
`+primefaces.PRIME_ICONS+` set to `+false+` removes the style sheet (observed). Icons are CSS classes, `+pi+` plus `+pi-<name>+`, used on
any element or in the `+icon+` attribute of components such as `+p:commandButton+`:

.PrimeIcons on a heading and on buttons (and Font Awesome next to them)
[source,xml]
----
<h1><i class="pi pi-book"></i> PrimeIcons and <i class="fa-solid fa-book"></i> Font Awesome</h1>
<h:form id="actions">
  <p:commandButton id="pi" value="Search" icon="pi pi-search" type="button"/>
  <p:commandButton id="fa" value="Borrow" icon="fa-solid fa-book" type="button"/>
  <p:commandButton id="only" icon="pi pi-trash" type="button" title="Delete"/>
</h:form>
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/fonticons[PrimeFaces 16 documentation: Font Icons]

The button with `+icon="pi pi-search"+` rendered `+<span class="ui-button-icon-left ui-icon ui-c pi pi-search">+` before its label, and in headless
Chrome the `+::before+` content of the icon used the font family `+primeicons+`, which the browser reported as loaded. A button without a value
and with a `+title+` rendered the title as its text (`+ui-button-icon-only+`), which gives an icon-only button an accessible name; give every
icon-only control a `+title+` or an `+aria-label+`.

*Font Awesome* was removed from the PrimeFaces jar in 11.0.0. The documentation says PrimeFaces supports Font Awesome 4.x, 5.x and
6.x or later added by the application as a WebJar. The icons are used the same way (`+icon="fa-solid fa-book"+`, or a plain `+<i>+`) once the
style sheet is on the page. The style sheet is the part that needs care, and the check below was run on both implementations:

.The layout of a page that loads Font Awesome as a WebJar (icons.xhtml)
[source,xml]
----
<ui:composition template="/WEB-INF/templates/layout.xhtml">
  <ui:define name="head">
    <h:outputStylesheet library="webjars" name="font-awesome/6.7.2/css/all.min-jsf.css"/>
  </ui:define>
  ...
</ui:composition>
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/fonticons[PrimeFaces 16 documentation: Font Icons]

[cols="3,3,3",options="header"]
|===
|WebJar and style sheet |Files named `+*-jsf.css+` in the WebJar |Font in headless Chrome (Mojarra and MyFaces)

|`+font-awesome+` 6.7.2, `+css/all.min-jsf.css+` |yes |loaded
|`+font-awesome+` 7.2.0, `+css/all.min-jsf.css+` |yes |loaded
|`+font-awesome+` 7.2.0, `+css/all.min.css+` |yes |*error* (the font file was not found)
|`+font-awesome+` 7.3.0, `+css/all.min.css+` |*no* (the latest WebJar at the time of writing has none) |*error*
|===

The `+-jsf+` variants exist because the font URLs inside the standard style sheet are relative (`+../webfonts/...+`), and the URL of a
resource served by Faces carries the library as a query parameter (`+?ln=webjars+`), which a relative URL cannot express (that is the
likely reason; the failure itself, a font in the state `+error+`, was observed). The
`+-jsf+` style sheets replace those URLs with value expressions (the 6.7.2 file contains
`+url("#{resource['webjars:font-awesome/6.7.2/webfonts/fa-brands-400.woff2']}&#")+`) and Faces evaluates them. The practical rules: use the
`+*-jsf.css+` file, and before upgrading the WebJar check that it still contains the `+-jsf+` files (the 7.3.0 WebJar does not). Pin the
version in the library path, as `+font-awesome/6.7.2/...+` does; the version is part of the resource name.

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/fonticons[PrimeFaces 16 documentation: Font Icons] and
xref:web/jsf/resource-handling.adoc#el[expressions inside resource files]

[#responsive]
== Responsive Layout: ui-fluid, Grid CSS, PrimeFlex and panelGrid

The PrimeFaces documentation names three ingredients of a responsive page: the page layout (menu, header, content, footer, which
is plain HTML and CSS of the application), a grid framework that places the content, and components that adapt to their
container. PrimeFaces gives the last two a vocabulary.

[#responsive-fluid]
=== Fluid components

Form components have a fixed width by default. Putting them in a container with the class `+ui-fluid+` makes them take the full width
of the container, which is what a grid cell needs (`+p:selectOneMenu+` has `+autoWidth+`, whose default `+auto+` since 13.0.0 notices a
parent `+ui-fluid+` and skips its own width calculation). Complex components such as `+p:dialog+`, charts, the carousel and the pick
list have a `+responsive+` attribute that makes them react to the screen size (documentation, not run). Touch features (swipe on the
tab view, long press for the context menu) are on by default and `+primefaces.TOUCHABLE+` switches them off globally.

[#responsive-gridcss]
=== Grid CSS

Grid CSS is a 12-column fluid grid built into `+components.css+`. A container has the class `+ui-g+`; its columns have `+ui-g-1+` to
`+ui-g-12+`, `+ui-g-offset-N+` moves a column, `+ui-g-nopad+` removes the padding, and the prefixes `+ui-sm-N+`, `+ui-md-N+`, `+ui-lg-N+`
and `+ui-xl-N+` override the width above or below a breakpoint. The breakpoints are in the 16.0.0 `+components.css+`:

[cols="1,2,3",options="header"]
|===
|Prefix |Media query in `+components.css+` |Device named in the documentation

|`+ui-sm-*+` |`+max-width:40em+` |phones
|`+ui-md-*+` |`+min-width:40.063em+` |tablets
|`+ui-lg-*+` |`+min-width:64.063em+` |desktops
|`+ui-xl-*+` |`+min-width:90.063em+` |big screens
|===

.Four columns on large screens, two on tablets, one on phones
[source,xml]
----
<div class="ui-g">
    <div class="ui-g-12 ui-md-6 ui-lg-3">one</div>
    <div class="ui-g-12 ui-md-6 ui-lg-3">two</div>
    <div class="ui-g-12 ui-md-6 ui-lg-3">three</div>
    <div class="ui-g-12 ui-md-6 ui-lg-3">four</div>
</div>
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/components/gridcss[PrimeFaces 16 documentation: Grid CSS]

The older Grid CSS of the PrimeFaces 5 era, `+ui-grid+`, `+ui-grid-row+` and `+ui-grid-col-N+` (with `+ui-grid-responsive+`), is still in the
16.0.0 `+components.css+` and still used by some renderers (the default `+p:panelGrid+` wraps its rows in `+ui-grid ui-grid-responsive+`). The
10.0.0 migration guide deprecated Grid CSS in favour of PrimeFlex, and the 15.0.0 guide deleted the "grid" layouts of some
components, so new layouts should use PrimeFlex unless a component needs Grid CSS.

[#responsive-primeflex]
=== PrimeFlex (the flex grid)

The flex-based grid, "Flex Grid CSS" in the PrimeFaces documentation, is PrimeFlex, a library shared by PrimeFaces, PrimeNG and
PrimeReact. It is *not* in the PrimeFaces jar. The documentation adds it as a WebJar and includes the style sheet from the `+webjars+` library:

.pom.xml (excerpt) and the style sheet in the head of a page
[source,xml]
----
<dependency>
  <groupId>org.webjars.npm</groupId>
  <artifactId>primeflex</artifactId>
  <version>4.0.0</version>
</dependency>
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/responsive[PrimeFaces 16 documentation: Responsive Design]

[source,xml]
----
<h:head>
  <title>Grid</title>
  <h:outputStylesheet library="webjars" name="primeflex/4.0.0/primeflex.min.css"/>
</h:head>
<h:body>
  <div class="grid">
    <div class="col-12 md:col-6">one</div>
    <div class="col-12 md:col-6">two</div>
  </div>
</h:body>
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/responsive[PrimeFaces 16 documentation: Responsive Design]

With the WebJar of PrimeFlex 4.0.0 on the class path the stylesheet was served (the library name `+webjars+` is the directory
`+META-INF/resources/webjars+` of the jar) and the container computed to `+display:flex+` with `+flex-wrap:wrap+`. PrimeFaces 16 uses PrimeFlex
4.0.0, whose colour variables are `+--p-red-500+` instead of `+--red-500+` (16.0.0 migration guide); PrimeFlex 3 had changed the class names already (PrimeFaces 11 and 12 migration guides), and PrimeFaces ships a CLI tool to migrate pages from PrimeFlex 2 to 3.

The parameter `+primefaces.FLEX+` tells the components that have a responsive mode to emit PrimeFlex classes instead of Grid CSS
classes. Observed: `+p:selectOneRadio layout="responsive"+` rendered `+class="ui-grid ui-grid-responsive"+` over `+ui-g+` and
`+ui-g-12 ui-md-6+` cells without the parameter, and `+class="ui-grid-responsive"+` over `+grid+` and `+col-12 md:col-6+` cells with
`+FLEX=true+`. A `+p:panelGrid layout="grid"+` did not change (its layout is chosen by the attribute). The documentation says "not
implemented by all components yet"; the 16.0.0 attributes `+flex+` exist on `+p:dataGrid+`, `+p:dataView+`, `+p:datePicker+`,
`+p:orderList+`, `+p:selectManyCheckbox+` and `+p:selectOneRadio+`.

[#responsive-panelgrid]
=== p:panelGrid layouts

`+p:panelGrid+` is the layout component for forms. Its `+layout+` attribute selects the markup; the rendered output for the same
two cells in each mode was (class names from the run; the `+columns+` value must be a divisor of 12 for the grid layouts since 13.0.0):

[cols="2,5,4",options="header"]
|===
|`+layout+` |Rendered structure |Needs

|`+tabular+` |`+<table role="grid">+` with `+tr+` and `+td+` |nothing
|`+grid+` (the default since 13.0.0; without the attribute the output was this one) |`+div.ui-panelgrid-content.ui-grid.ui-grid-responsive+` containing `+div.ui-g+` rows and cells `+ui-g-12 ui-md-6+` |Grid CSS (in `+components.css+`)
|`+flex+` |`+div.ui-panelgrid-content.grid+` containing cells `+col-12 md:col-6+` |PrimeFlex
|`+tailwind+` |`+div.ui-panelgrid-content.grid.grid-cols-1.sm:grid-cols-2.gap-4+` containing cells `+ui-panelgrid-cell+` |Tailwind CSS (the application provides it)
|===

`+columnClasses+` sets the classes of the cells, and `+styleClass="ui-noborder"+` (or `+ui-panelgrid-blank+`) removes the borders. A form
with the labels at a quarter of the width on tablets and larger, and the fields at three quarters, is written once with Grid CSS
and once with PrimeFlex:

.panelGrid with Grid CSS classes (the Bookshelf search form)
[source,xml]
----
<div class="ui-fluid">
  <p:panelGrid columns="2" layout="grid" styleClass="ui-noborder"
               columnClasses="ui-g-12 ui-md-3, ui-g-12 ui-md-9">
    <p:outputLabel for="title" value="Title"/>
    <p:inputText id="title"/>
    <p:outputLabel for="author" value="Author"/>
    <p:inputText id="author"/>
  </p:panelGrid>
</div>
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/components/panelgrid[PrimeFaces 16 documentation: PanelGrid]

.panelGrid with PrimeFlex classes (the PrimeFlex style sheet is included in the head)
[source,xml]
----
<div class="ui-fluid">
  <p:panelGrid columns="2" layout="flex" styleClass="ui-noborder"
               columnClasses="col-12 md:col-3, col-12 md:col-9">
    <p:outputLabel for="title" value="Title"/>
    <p:inputText id="title"/>
    <p:outputLabel for="author" value="Author"/>
    <p:inputText id="author"/>
  </p:panelGrid>
</div>
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/components/panelgrid[PrimeFaces 16 documentation: PanelGrid]

In headless Chrome at a window width of 1280 pixels the two cells of a row measured 316 and 948 pixels (Grid CSS) and 320 and 960
pixels (PrimeFlex), a quarter and three quarters; at 756 pixels, below the tablet breakpoint, every cell was the full 756 pixels
wide in both. The documentation warns that labels may not line up with the fields in horizontal forms and suggests
`+align-items:center+` on `+.ui-panelgrid-content+` through a style class.

[#localisation]
== Localisation

PrimeFaces has two places for localised text, the server-side message bundles and the client-side locale scripts, and both are chosen
from the Faces locale of the view.

*The Faces locale.* Which locale PrimeFaces uses is the locale of the view. An application has to declare the locales it supports
in `+faces-config.xml+`: in the scratch application, without `+<supported-locale>es</supported-locale>+` a request with
`+Accept-Language: es+` was answered with `+locale:'en_US'+` in `+PrimeFaces.settings+`; with it, the settings carried `+locale:'es'+`
(see xref:web/jsf/messages-and-i18n.adoc#locale-selection[locale selection]).

.faces-config.xml (excerpt)
[source,xml]
----
<application>
  <locale-config>
    <default-locale>en</default-locale>
    <supported-locale>es</supported-locale>
  </locale-config>
  <resource-bundle>
    <base-name>org.example.bookshelf.messages</base-name>
    <var>msg</var>
  </resource-bundle>
</application>
----

Source: https://jakarta.ee/learn/docs/jakartaee-tutorial/current/web/faces-configure/faces-configure.html[Jakarta EE Tutorial: Configuring Jakarta Faces Applications]

*Server-side messages.* The messages of the components (validation, empty table, file limits) live in `+org/primefaces/Messages.properties+`
in the jar, with a translation per language: the 16.0.0 jar holds `+Messages_<language>.properties+` for Czech, German, Greek, Spanish,
Persian, French, Croatian, Hindi, Indonesian (`+in+`), Italian, Japanese, Georgian, Korean, Lithuanian, Latvian, Dutch, Norwegian, Polish,
Portuguese, Romanian, Russian, Slovak, Swedish, Turkish and Chinese, and an English file. A language that is missing is added, and a
shipped message is changed, by putting a file of the same name in `+WEB-INF/classes+` (or in an application jar earlier on the class path):

.src/main/resources/org/primefaces/Messages_es.properties -- the empty-table text of the Bookshelf
[source,properties]
----
primefaces.data.EMPTY_MESSAGE=Todav\u00eda no hay libros en el cat\u00e1logo.
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/localization[PrimeFaces 16 documentation: Localization]

.empty.xhtml -- an empty table
[source,xml]
----
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml" xmlns:h="jakarta.faces.html" xmlns:p="primefaces">
<h:head><title>empty</title></h:head>
<h:body>
  <p:dataTable id="t" value="#{emptyBean.books}" var="b">
    <p:column headerText="Title"><h:outputText value="#{b}"/></p:column>
  </p:dataTable>
</h:body>
</html>
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/localization[PrimeFaces 16 documentation: Localization]

.EmptyBean.java -- a bean that returns no rows
[source,java]
----
package org.example.bookshelf.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Named;
import java.util.List;

@Named
@RequestScoped
public class EmptyBean {
    public List<String> getBooks() {
        return List.of();
    }
}
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/localization[PrimeFaces 16 documentation: Localization]

Observed on Mojarra and on MyFaces: with the file, `+Accept-Language: en+` gave "No records found." and `+Accept-Language: es+` gave
"Todavía no hay libros en el catálogo."; without it the shipped Spanish text "No se encontraron registros." appeared. The `+\uXXXX+` escapes in
the file work with any file encoding.

*Client-side texts.* The widgets (date picker, filter menus, paginator tips, upload buttons) read their texts and the names of days
and months from a JavaScript object, `+PrimeFaces.locales['<language>']+`, defined by `+locales/locale-<language>.js+` of the
library `+primefaces+`. The 16.0.0 jar contains 48 of them, with English as the default. With `+primefaces.CLIENT_SIDE_LOCALISATION+` enabled,
which is the default (<<params>>), the head renderer adds the script of the current language, and nothing else is needed:

[source,xml]
----
<!-- observed for Accept-Language: es, no parameter in web.xml -->
<script src="/bookshelf/jakarta.faces.resource/locales/locale-es.js.xhtml?ln=primefaces&v=16.0.0"></script>
----

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/localization[PrimeFaces 16 documentation: Localization]

A page can also load one script by hand, `+<h:outputScript name="locales/locale-nl.js" library="primefaces"/>+`, for a language that the
Faces locale does not select. A language PrimeFaces does not ship is defined in your own script by assigning a complete object to
`+PrimeFaces.locales['xx']+`; the documentation lists the keys of the English object (day and month names, `+firstDayOfWeek+`, the filter
and paginator texts). The client scripts and the server bundles are independent: translate both.

== Security Settings of the Setup

The setup decisions of this page have security consequences that the later PrimeFaces pages build on:

* *Content Security Policy.* `+primefaces.CSP+` switches PrimeFaces to nonce-stamped scripts and registered handlers instead of
inline code. The xref:web/jsf/security.adoc#csp[security page] ran it (`+p:commandButton+` worked on Mojarra and MyFaces) and explains the
limitations (xref:web/jsf/security.adoc#csp[Content Security Policy]). Moving the scripts to the bottom (<<head>>) does not
replace it.
* *Rich text is untrusted markup.* `+p:textEditor+` refuses to render without the OWASP sanitizer unless `+secure="false"+` is set
(<<dependencies>>). Leave `+secure+` at its default for anything another user will read. The component documentation states the
sanitizer is there "to prevent XSS".
* *The theme name is a resource name.* A theme taken from a request parameter, a cookie or a profile reaches `+HeadRenderer+` as a
library name. Validate it against a fixed list as `+PrimeThemeBean+` does (<<themes-user>>) and store only the name.
* *Version disclosure.* `+v=16.0.0+` in every PrimeFaces URL tells an attacker the exact library version. `+HIDE_RESOURCE_VERSION+` removes
it (<<params>>); keep the library patched either way.
* *Cookies.* `+COOKIES_SAME_SITE+` (`+Strict+` by default) covers the cookies PrimeFaces' JavaScript writes. The session cookie and the
cookies of the Faces implementation have their own settings, described on xref:web/jsf/security.adoc#cookies[the security page].
* *Keys and credentials.* `+PUBLIC_CAPTCHA_KEY+` and `+PRIVATE_CAPTCHA_KEY+` are `+context-param+` values in the documentation's examples. The private
key is a secret: keep it out of the repository and of `+web.xml+` in version control, and give it to the server through its own
deployment configuration. This page has no example key on purpose.
* *Uploads.* `+p:fileUpload+` has limits and validators of its own; the xref:web/jsf/file-upload-and-download.adoc[upload and download page] sets the
posture (size limits, content sniffing, file name sanitising) that xref:web/jsf/primefaces-files-media-charts-and-drag-drop.adoc[the PrimeFaces files page] reuses
(xref:web/jsf/file-upload-and-download.adoc#limits[upload limits], xref:web/jsf/file-upload-and-download.adoc#validating[validating the content]).
* *View state.* Components are ordinary Faces components, so the rule of xref:web/jsf/security.adoc#csrf[the security page] applies: view state protects against
cross-site request forgery only with server-side state saving (xref:web/jsf/security.adoc#csrf[cross-site request forgery]).

Source: https://primefaces.github.io/primefaces/16_0_0/#/core/contentsecuritypolicy[PrimeFaces 16 documentation: Content Security Policy] and
https://primefaces.github.io/primefaces/16_0_0/#/components/texteditor[PrimeFaces 16 documentation: TextEditor]

== What Changed per Version

PrimeFaces versions move fast and change defaults in every release, so a page or a book is only as good as its PrimeFaces version.
The entries below are the ones that matter for this page, from the PrimeFaces migration guides and the 16.0.0 source:

[cols="2,7",options="header"]
|===
|Version |Change

|3.0 / 3.1 |Aristo is the built-in theme (3.0); ThemeSwitcher is reimplemented as a native widget (3.0); `+primefaces.THEME_FORMS+` is removed (3.1)
|5.0 / 6.0 |Widgets are referenced through `+PF('widgetVar')+` (5.0). `+primefaces.js+` is split into `+core.js+` and `+components.js+` (6.0), and the `+last+` facet is supported only in `+h:head+` (6.0)
|7.0 |`+RequestContext+` is replaced by `+PrimeFaces.current()+`; Push and Mobile are removed
|8.0 |Java 8 or later; `+p:textEditor+` requires the OWASP sanitizer by default; `+p:panelGrid layout="flex"+` is added
|10.0.0 |`+aristo+` and `+omega+` themes removed and `+saga+` becomes the default; Grid CSS, Font Awesome and ThemeSwitcher are deprecated in favour of PrimeFlex, PrimeIcons and a normal menu
|11.0.0 |Font Awesome and ThemeSwitcher removed from the jar; PrimeFlex 3 (a breaking release) arrives
|12.0.0 |PrimeFlex 3 is the version to use
|13.0.0 |`+p:panelGrid+` defaults to `+layout="grid"+`, the tabular layout is deprecated; Internet Explorer support is removed; Faces 2.0 and 2.1 support is deprecated
|14.0.0 |Java 11 is the minimum; Faces 2.0 to 2.2 support is removed; `+primefaces.CLIENT_SIDE_LOCALISATION+` is enabled by default
|15.0.0 |ThemeRoller themes are no longer supported; every theme except Saga Blue moves to `+primefaces-themes.jar+`; the themes are named `+saga-blue+`, `+arya-blue+` and `+vela-blue+` (the short names still work); Commons FileUpload support is removed
|16.0.0 |Java EE and `+javax.*+` support removed, so the baseline is Jakarta Faces 4.0 (Faces 5.0 is listed as supported by the download page); PrimeFlex 4.0.0 (its colour variables become `+--p-red-500+`); `+primefaces.HTML5_COMPLIANCE+` removed; `+PrimeClientWindowLifecycleFactory+` removed (use `+PrimeClientWindowFactory+`)
|===

[#books]
== Where the Books Are Outdated

_PrimeFaces Cookbook, Second Edition_ (Çalışkan and Varaksin, Packt, 2015; PrimeFaces 5.1 and 5.2 on JSF 2.2) is the book behind
this page: its first chapters cover setup, internationalisation and resource ordering, theming, icons, and panels and layouts. Its
approach to organising a PrimeFaces application is still sound; the details are not.

* *The platform.* The book is written for `+javax.faces+` on JSF 2.2; PrimeFaces 14.0.0 removed Faces 2.x support and 16.0.0 removed
`+javax.*+` altogether. Every namespace, import and server setup needs the Jakarta Faces 4.0 or later form. The `+p:+` namespace
`+http://primefaces.org/ui+` still works and `+primefaces+` is the short form.
* *Resource files.* The 5.x scripts were collected in `+primefaces.js+`; since 6.0 they are `+core.js+` and `+components.js+` (plus jQuery),
and in 16 the head renderer includes them, not an explicit tag or include. Nothing has to be added by hand; a custom
`+@ResourceDependency+` that names `+primefaces.js+` has to change.
* *Themes.* The book teaches ThemeRoller-style themes, the theme switcher component and Maven artifacts for extra themes. In
PrimeFaces 16 ThemeRoller themes do not render (15.0.0), `+p:themeSwitcher+` does not exist (11.0.0), and the extra themes are
Saga, Vela, Arya, Aura, Bootstrap, Material, Luna and Nova in the single `+primefaces-themes+` jar. The setting is still
`+primefaces.THEME+`, but the names are different. Custom themes are built from SCSS or extended with CSS, as in <<themes-custom>>.
* *Icons.* Font Awesome came with the jar in the book's era; it was removed in 11.0.0. PrimeIcons (`+pi pi-*+`) is the default and Font
Awesome is added as a WebJar with the `+-jsf+` style sheet (<<icons>>).
* *Grid CSS.* The book's layout recipes use the Grid CSS of its day (`+ui-grid+`, `+ui-grid-row+`, `+ui-grid-col-N+`). The classes still
ship in 16.0.0, but Grid CSS was deprecated in 10.0.0 in favour of PrimeFlex, which is a separate WebJar with its own class names
(`+grid+`, `+col-12 md:col-6+`), and `+p:panelGrid+` has the `+flex+` layout for it (<<responsive>>).
* *Resource ordering.* The book's advice on the order of style sheets and scripts rests on the head rendering of PrimeFaces 5. The
facets `+first+`, `+middle+` and `+last+` of `+h:head+` still exist, but they order plain markup, not `+h:outputStylesheet+` components, and
the order differs between Mojarra and MyFaces for the latter (<<head>>).
* *Internationalisation.* The mechanism (bundles for the components, client-side locale scripts) is the same idea, but client-side
localisation is on by default since 14.0.0 and the languages and keys are different (<<localisation>>).

Other books touch this page too. _Learning PrimeFaces Extensions Development_ (Jonna, 2014) sets up a PrimeFaces Extensions 1.2.1
project against PrimeFaces 4.0; the PrimeFaces Extensions page of this section covers the present setup. _JSF 2.0 Cookbook_
(Leonard, 2010) was written for PrimeFaces 2.0 alongside RichFaces and Tomahawk; nothing of its PrimeFaces setup applies. None
of the book content is reproduced here.

[#pitfalls]
== Common Mistakes

* *Plain `+<head>+` and `+<body>+` in a template.* No theme, no icons, no widgets; the components are rendered as bare markup
(<<head>>). Use `+h:head+` and `+h:body+`.
* *A typo in `+primefaces.THEME+`, or a theme name from `+primefaces-themes+` without the jar.* An unstyled page and, on Mojarra, a
`+RES_NOT_FOUND+` link; there is no error. Check the link in the page source after changing the theme (<<themes-select>>).
* *Re-rendering the view after the user changes the theme.* The old theme link is written as well, and it wins. Redirect to a fresh
view (<<themes-user>>).
* *Putting a user-chosen string into `+primefaces.THEME+`.* It becomes a library name. Allow a fixed list.
* *Overriding PrimeFaces CSS with an `+h:outputStylesheet+`.* It arrives before `+components.css+`. Use a plain `+link+` with
`+#{resource[...]}+` in the `+last+` facet and select with more specificity than the theme (<<head>>).
* *Depending on facets to order `+h:outputStylesheet+` components.* Facets order plain markup only, and the two implementations
disagree about resource components (<<head>>).
* *Hello world without the sanitizer.* The official `+p:textEditor+` page answers HTTP 500 until `+owasp-java-html-sanitizer+` is on the
class path; the cure is the dependency, not `+secure="false"+`.
* *Font Awesome with the plain style sheet, or with the WebJar 7.3.0.* The icons render as empty boxes because the font is not
found. Use the `+*-jsf.css+` file and check that the version you choose still has it (<<icons>>).
* *Trusting the documentation's configuration table for `+CLIENT_SIDE_LOCALISATION+`.* The table says `+false+`; the default is `+true+`
(<<params>>).
* *Relying on `+saga+`, `+arya+` and `+vela+` short names.* They still work in 16.0.0 but were announced for removal; use the `+-blue+` names.
* *Mixing PrimeFlex and Grid CSS in one form without meaning to.* `+p:panelGrid+` defaults to Grid CSS even when
`+primefaces.FLEX+` is `+true+`; the attribute `+layout="flex"+` and the PrimeFlex style sheet go together.
* *Reading `+PrimeFaces.settings+` as if it were configuration.* It is generated on every page from the context parameters; change
`+web.xml+`.
* *A `+WELD-000119+` flood taken for a failure.* The `+INFO+` lines on a servlet container without Bean Validation or Persistence
(<<overview>>) mean that optional features are off.
* *Different PrimeFaces and `+primefaces-themes+` versions.* They are released together; keep the same number in the POM.
* *Hard-coded keys.* No captcha key, API key or private value in `+web.xml+`, a bean or a page (<<security>>).
