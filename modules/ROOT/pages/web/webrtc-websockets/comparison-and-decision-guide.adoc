Every other page of this section goes deep on one concept. This page does the opposite: it puts the alternatives side by
side, tells you which question to ask first, and ends with a recommendation for each of the three scenarios of the
section -- *Chatterbox* (chat), *Huddle* (videoconference) and *Pixel Arena* (multiplayer game). The numbers and versions
are not repeated here in full; each table links to the page that explains and verifies them.

The comparison was checked on 2026-10-24 (the first survey was done on 2026-10-22) against the baseline of the
xref:web/webrtc-websockets/index.adoc[section home page]: RFC 6455, RFC 8441 and RFC 9220 for WebSockets; WebTransport as a
W3C Candidate Recommendation Snapshot; the W3C WebRTC 1.0 Recommendation with JSEP in RFC 9429; mediasoup 3.31.0, LiveKit
1.13.10, Janus 1.4.3, Pion 4.2.25 and aiortc 1.15.0; ejabberd 26.09, Prosody 13.0.7, Openfire 5.1.2 and MongooseIM 6.10.0;
ASP.NET Core 10.0.13, `socket.io` 4.8.4, python-socketio 5.17.0, uWebSockets.js v20.71.0, Channels 4.3.2, Spring Framework
7.0.10, Atmosphere 4.0.76, Swoole 6.2.3 and Laravel Reverb 1.12.0.

=== Transports compared

[cols="2,2,3,2,3",options="header"]
|===
|Transport |Direction |Reliability and ordering |Browser support |Choose it for

|Short polling
|Client pulls
|Reliable, per request
|Everywhere
|Dashboards and the last-resort fallback

|Long polling
|Server push through parked requests
|Reliable, gaps possible between requests
|Everywhere
|A fallback behind hostile proxies (Socket.IO and SignalR do it for you)

|Server-Sent Events
|Server to client
|Reliable, ordered, resumable with `Last-Event-ID`
|All current browsers
|Notifications, feeds, streamed text, light chat

|WebSocket
|Both ways
|Reliable, ordered (TCP)
|All current browsers
|Chat, presence, signalling, simple games

|WebRTC media
|Both ways, peer to peer or through an SFU
|Unreliable by design, adaptive bitrate
|All current browsers
|Calls and conferences

|WebRTC data channel
|Both ways, peer to peer or to a server peer
|Configurable per channel
|All current browsers
|Game state, chat inside a call, file transfer

|WebTransport
|Both ways, client to server
|Streams reliable, datagrams unreliable
|Chromium, Firefox and Safari 26.4 and later
|Games and live media where you control the server
|===

Details and measurements: xref:web/webrtc-websockets/real-time-web-overview.adoc[Real-Time Web Overview],
xref:web/webrtc-websockets/server-sent-events-and-long-polling.adoc[Server-Sent Events and Long Polling],
xref:web/webrtc-websockets/websocket-protocol.adoc[The WebSocket Protocol],
xref:web/webrtc-websockets/webrtc-data-channels.adoc[Data Channels] and
xref:web/webrtc-websockets/webtransport-and-media-over-quic.adoc[WebTransport and Media over QUIC].

The rule of thumb in the flow is the one the overview page argues for: use the simplest transport that fits, and move to
a more specialised one only when you can measure the problem. The decision can be written down as a function, which is
how Chatterbox's feature flags express it.

[source,javascript]
----
// transport-chooser.mjs -- an original helper; run with: node transport-chooser.mjs
export function chooseTransport({ media, clientSends, binary, gameState, serverAuthoritative, holBlocking }) {
  if (media) return "webrtc-media + websocket-signalling";
  if (gameState && holBlocking) return serverAuthoritative ? "webtransport + websocket-fallback" : "webrtc-datachannel";
  if (!clientSends && !binary) return "sse";
  return "websocket";
}

console.log(chooseTransport({ media: false, clientSends: true, binary: false })); // websocket
console.log(chooseTransport({ media: true })); // webrtc-media + websocket-signalling
console.log(chooseTransport({ gameState: true, holBlocking: true, serverAuthoritative: true })); // webtransport + websocket-fallback
----

Source: https://websockets.spec.whatwg.org/[WHATWG WebSockets Standard], https://html.spec.whatwg.org/multipage/server-sent-events.html[WHATWG HTML Standard: Server-sent events] and https://www.w3.org/TR/webtransport/[W3C: WebTransport]

Three facts hold for every stack and decide more incidents than the choice itself: allow-list the `Origin` header,
keep heartbeats shorter than the idle timeout of every proxy in the path, and send application close codes in the 4000
range so clients know why they were dropped. See
xref:web/webrtc-websockets/security.adoc[Security],
xref:web/webrtc-websockets/connection-lifecycle-heartbeats-and-reconnection.adoc[Connection Lifecycle, Heartbeats and Reconnection]
and xref:web/webrtc-websockets/scaling-websockets.adoc[Scaling WebSockets].

== XMPP servers and clients compared

Choose XMPP over a custom protocol when you need federation, an existing standards-based feature set (rooms, history,
receipts, push, OMEMO) or interoperability with other clients. Choose a custom protocol when the product is a closed
application whose message model does not map to stanzas. The pages are
xref:web/webrtc-websockets/xmpp-fundamentals.adoc[XMPP Fundamentals],
xref:web/webrtc-websockets/xmpp-servers.adoc[XMPP Servers] and
xref:web/webrtc-websockets/xmpp-chat-features.adoc[XMPP Chat Features].

[cols="2,3,3",options="header"]
|===
|Server |Strength |Pick it when

|ejabberd
|Scale, SQL and Redis backends, clustering, MQTT and SIP built in
|The chat must grow and you want clustering and large rooms
|Prosody
|Small, readable Lua configuration, low memory, the server inside Jitsi Meet
|A demo, a small team or a self-hosted community
|Openfire
|Admin console and Java plugins
|You want a GUI and run a Java stack
|MongooseIM
|Inbox, MUC Light, push and mobile focus
|A mobile product built on a messaging backend
|===

[cols="2,3,3",options="header"]
|===
|Client |Strength |Pick it when

|xref:web/webrtc-websockets/xmpp-in-the-browser.adoc[Strophe.js]
|Mature, plugin-based, works with WebSocket and BOSH
|Existing code bases and long-lived deployments
|xref:web/webrtc-websockets/xmpp-in-the-browser.adoc[`@xmpp/client`]

end-to-end encryption uses OMEMO (see xref:web/webrtc-websockets/omemo-encryption.adoc[OMEMO Encryption]).

== Recommendations by application

=== Chatterbox: a chat application

* *Transport:* a WebSocket. Use SSE only for read-mostly feeds, and long polling only as an automatic fallback.
* *Server:* the stack of the platform you already run. Starting fresh: Socket.IO if you control the clients and want
  rooms and acknowledgements immediately, a plain server (`ws`, uWebSockets.js, Channels, WebFlux) if third-party clients
  must connect.
* *Protocol:* the Chatterbox envelope with client-generated message ids for idempotency, server-assigned order per room,
  and history on demand, as in xref:web/webrtc-websockets/message-design-and-serialization.adoc[Message Design and Serialization].
* *Scaling:* a Redis backplane, with heartbeats and reconnect with backoff and jitter. See
  xref:web/webrtc-websockets/chat-architecture.adoc[Chat Architecture] and
  xref:web/webrtc-websockets/history-offline-delivery-and-moderation.adoc[History, Offline Delivery and Moderation].
* *Federated or standards-based instead:* XMPP on Prosody or ejabberd, with Converse.js or `@xmpp/client`.
* *Build it:* xref:web/webrtc-websockets/building-a-chat-app.adoc[Building a Chat App].

=== Huddle: a videoconference

* *Transport:* WebRTC media with a WebSocket signalling server using perfect negotiation
  (xref:web/webrtc-websockets/signaling-and-perfect-negotiation.adoc[Signaling and Perfect Negotiation]).
* *Topology:* mesh for up to four participants, an SFU above that. Add TURN with ephemeral credentials from day one,
  because some participants always sit behind networks that cannot connect directly.
* *Media server:* LiveKit for the shortest path, mediasoup when you need full control, Jitsi Meet when you want a
  finished product, Janus when you need SIP or plugins.
* *Extras:* simulcast for mixed networks, screen sharing, recording through the SFU or an egress service, SFrame when
  the server must not see media.
* *Build it:* xref:web/webrtc-websockets/videoconference-architecture.adoc[Videoconference Architecture] and
  xref:web/webrtc-websockets/building-a-videoconference-app.adoc[Building a Videoconference App].

=== Pixel Arena: a multiplayer game

* *Transport:* start with a WebSocket and a binary encoding. Move input and snapshots to WebTransport datagrams
  (server-authoritative) or an unordered, unreliable data channel (peer to peer) only after you measure head-of-line
  blocking, and keep the WebSocket fallback.
* *Server:* an authoritative server on a fixed tick, with the lowest per-message overhead you can afford (`ws`,
  uWebSockets.js, Axum, Swoole), or Colyseus for rooms and state synchronisation.
* *Client:* prediction, reconciliation, interpolation and server-side rewind for hit detection, in that order of
  importance.
* *Build it:* xref:web/webrtc-websockets/multiplayer-game-architecture.adoc[Multiplayer Game Architecture],
  xref:web/webrtc-websockets/latency-compensation.adoc[Latency Compensation],
  xref:web/webrtc-websockets/game-servers-and-colyseus.adoc[Game Servers and Colyseus] and
  xref:web/webrtc-websockets/building-a-multiplayer-game.adoc[Building a Multiplayer Game].

== Production checklist common to all three

* Authenticate before upgrading and authorise every message
  (xref:web/webrtc-websockets/authentication-and-authorization.adoc[Authentication and Authorization]).
* Validate `Origin`, set size and rate limits, use `wss` only
  (xref:web/webrtc-websockets/security.adoc[Security]).
* Configure proxies for `Upgrade`, `Connection` and long read timeouts
  (xref:web/webrtc-websockets/proxies-load-balancers-and-deployment.adoc[Proxies, Load Balancers and Deployment]).
* Expose connection counts, message rates, fan-out latency and ICE success
  (xref:web/webrtc-websockets/observability.adoc[Observability]).
* Test with real browsers and load tests
  (xref:web/webrtc-websockets/testing-real-time-apps.adoc[Testing Real-Time Apps] and
  xref:web/webrtc-websockets/load-testing-and-capacity-planning.adoc[Load Testing and Capacity Planning]).
* Plan the native clients (xref:web/webrtc-websockets/mobile-and-native-clients.adoc[Mobile and Native Clients]).
