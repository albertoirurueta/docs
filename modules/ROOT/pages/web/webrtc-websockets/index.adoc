= WebRTC & WebSockets
:description: Build real-time web applications -- chat, videoconference and multiplayer games -- with the WebSocket protocol, WebRTC and XMPP, and the SignalR, Socket.IO, uWebSockets.js, Django Channels, Spring WebFlux, Atmosphere, Swoole and Laravel Reverb servers, with end-to-end applications, production guidance and a downloadable cheat sheet.

This section teaches how to build three kinds of real-time web application: a *chat application*, a *videoconference
application* and a *multiplayer browser game*. It is written for web and backend developers who know HTTP and
JavaScript and now need persistent connections, peer-to-peer media or low-latency state synchronisation, and who want
to compare several server stacks on equal terms. Every concept has its own page with detailed explanations and runnable
examples, and every example is followed by a link to the official documentation it derives from.

Versions and standards were re-checked on 2026-10-24 (the first survey was done on 2026-10-22). The baseline is:
WHATWG WebSockets living standard with RFC 6455, RFC 7692, RFC 8441 and RFC 9220; `WebSocketStream` shipped only in
Chromium 124 and later and not on a standards track; WebTransport as a W3C Candidate Recommendation Snapshot of
2026-07-30, supported in Safari 26.4 and later; the W3C WebRTC 1.0 Recommendation (2025-03-13 edition) with JSEP in
RFC 9429 and WHIP in RFC 9725 (WHEP is still an Internet-Draft); mediasoup 3.31.0, LiveKit 1.13.10, Janus 1.4.3, Pion
4.2.25, aiortc 1.15.0, coturn 4.18.0 and eturnal 1.12.3; ejabberd 26.09, Prosody 13.0.7, Openfire 5.1.2 and MongooseIM
6.10.0; ASP.NET Core 10.0.13 (LTS) with .NET 11 still in release-candidate state; `socket.io` 4.8.4 and python-socketio
5.17.0; uWebSockets.js v20.71.0; channels 4.3.2; Spring Framework 7.0.10 and Spring Boot 4.1.2; Atmosphere 4.0.76;
Swoole 6.2.3 and OpenSwoole 26.2.0; and Laravel Reverb 1.12.0 on Laravel 13. Each page restates the versions it was
written against.

== The three scenarios

Every page uses one of three original scenarios, so that the stacks and techniques can be compared on the same problem.

* *Chatterbox* is a chat application with rooms (public, private and direct messages), presence, typing indicators,
  delivery and read receipts, paginated history, edits, reactions, attachments, moderation and offline catch-up. All
  server-stack pages implement the same JSON wire protocol (an envelope with `v`, `type`, `id`, `room`, `ts` and
  `payload`), so one browser client can talk to every server. An XMPP variant offers the same features on Prosody or
  ejabberd.
* *Huddle* is a videoconference application with 1:1 calls and rooms, a lobby, mute and camera toggles, device
  switching, screen sharing, active-speaker detection, chat over a data channel, recording and optional end-to-end
  encryption. It uses a WebSocket signalling server, a mesh mode for up to four participants, an SFU mode with
  mediasoup, a LiveKit variant and coturn with ephemeral credentials.
* *Pixel Arena* is a multiplayer browser game with an authoritative server, a fixed tick loop, snapshots,
  client-side prediction, reconciliation, interpolation, lag compensation and unreliable data channels, plus a Colyseus
  variant and a binary snapshot encoding compared with JSON.
