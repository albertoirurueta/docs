A URLconf is the table of contents of a Django site: a Python module whose `urlpatterns` list maps URL paths to views, and, because the
same table can be read backwards, it is also the only place that knows what a URL looks like. This page covers both directions. Going
forward it explains `path()` and `re_path()`, the converters that turn text from the URL into Python values, `include()` and the
application and instance namespaces that make URLs from different apps coexist, and the error handlers that answer when nothing matches.
Going backward it explains `reverse()`, `reverse_lazy()`, `get_absolute_url()` and the `{% url %}` template tag, so that no URL is ever
typed twice. It closes with the checks Django runs on your URLconf, per-request URLconfs, translated URLs and a step-by-step migration from
the long-removed `url()` function that most older tutorials still use. The views that the patterns point at are covered on the pages

request/response cycle page; the project layout that holds `config/urls.py` and `catalog/urls.py` is on

[#request-cycle]
== Where the URLconf sits in the request/response cycle

Routing is the step between the middleware chain and the view. When the handler (WSGI or ASGI) receives a request it builds an
`HttpRequest`, runs it down through the middleware listed in `MIDDLEWARE`, and only then, inside the innermost layer, resolves the path.
Django's documentation lists the algorithm exactly:

. Django picks the root URLconf module. Normally this is the `ROOT_URLCONF` setting, but if the `HttpRequest` has a `urlconf` attribute
(set by a middleware that ran earlier) its value is used instead.
. Django imports that module and reads its `urlpatterns` variable, a sequence of `path()` and/or `re_path()` instances (and `include()`
results).
. It runs through the patterns in order and stops at the first one that matches `request.path_info`, the path without the host, the query
string or any script prefix.
. It imports and calls the view with the `HttpRequest` as the first argument, plus the captured values as keyword arguments (or positional
arguments, if the pattern used unnamed regular-expression groups), overridden by the optional `kwargs` dictionary of the pattern.
. If no pattern matches, or any exception is raised on the way, Django calls an error-handling view.

Four consequences follow from this picture and come back in the sections below:

* *The URL is matched on the path alone.* The query string, the domain and the HTTP method play no part (`GET /books/` and
`POST /books/` reach the same view); the view or a decorator decides what to do with the method.
* *`request.resolver_match` exists only after resolution.* It is available in views, in `process_view()` and later hooks, and in
template contexts, but not in the "before the view" part of a middleware's `__call__`, which runs first.
* *The resolver is built once.* `get_resolver()` is cached per URLconf module, and the regular expressions of the patterns are compiled the
first time they are needed, so routing cost per request is a sequential scan of compiled patterns, not an import.
* *Resolution is synchronous and CPU-only.* The ASGI handler calls it directly in the event loop; it does no I/O, so an async view is
routed exactly like a sync one (see <<sync-async>>).

[#bookshelf-urls]
== The Bookshelf URL design used on this page

Every example belongs to the _Bookshelf_ catalogue, an app named `catalog` in a project named `config`. The model is small, because
what matters here is the URL design. `get_absolute_url()` is the canonical way to give a model instance an address and it already uses
`reverse()` (explained in <<reverse>>):

.catalog/models.py
[source,python]
----
from django.db import models
from django.urls import reverse


class Book(models.Model):
    title = models.CharField(max_length=200)
    slug = models.SlugField(unique=True)
    isbn = models.CharField(max_length=13, unique=True)

    def __str__(self):
        return self.title

    def get_absolute_url(self):
        return reverse("catalog:book-detail", kwargs={"slug": self.slug})
----

register_converter(converters.Isbn13Converter, "isbn13")

    path("books/new/", views.BookCreate.as_view(), name="book-create"),
    path("books/<slug:slug>/", views.book_detail, name="book-detail"),
    path("isbn/<isbn13:isbn>/", views.echo, name="by-isbn"),
    path("published/<yyyy:year>/", views.echo, name="by-year"),
    path("published/<yyyy:year>/<int:month>/", views.echo, name="by-month"),
    path("files/<path:file_path>", views.echo, name="file"),
    path("reviews/<uuid:review_id>/", views.echo, name="review"),
    path("about/", views.echo, {"template": "about"}, name="about"),
    path("page/", views.page, name="page-first"),
    path("page/<int:num>/", views.page, name="page"),
    path("search/", views.search_redirect, name="search"),

    # an old URL scheme keeps working: redirect permanently, rebuilding the target from the pattern name
    path("old-books/<slug:slug>/", RedirectView.as_view(pattern_name="catalog:book-detail", permanent=True)),
    path("ping/", views.ping, name="ping"),
    path("boom/", views.boom),
    path("forbidden/", views.forbidden),
    path("missing/", views.missing),
]

Most routes point at one deliberately simple view, `echo`, which returns what the dispatcher handed over (names, values and Python types)
as JSON. That makes the behaviour of every pattern observable with `curl`; real views are explained on the views pages:

.catalog/views.py
[source,python]
----
from django.core.exceptions import PermissionDenied
from django.http import Http404, HttpResponseRedirect, JsonResponse
from django.shortcuts import get_object_or_404, render
from django.urls import reverse, reverse_lazy
from django.views.generic import CreateView

from .models import Book


def book_list(request):
    return render(request, "catalog/book_list.html", {"books": Book.objects.order_by("title")})


def book_detail(request, slug):
    book = get_object_or_404(Book, slug=slug)
    return render(request, "catalog/book_detail.html", {"book": book})


def echo(request, *args, **kwargs):
    """Show what the URL dispatcher handed to the view: names, values and Python types."""
    match = request.resolver_match
    return JsonResponse(
        {
            "args": [[repr(a), type(a).__name__] for a in args],
            "kwargs": {k: [repr(v), type(v).__name__] for k, v in kwargs.items()},
            "view_name": match.view_name,
            "route": str(match.route),
            "app_names": match.app_names,
            "namespaces": match.namespaces,
        }
    )


def page(request, num=1):
    return JsonResponse({"page": num, "type": type(num).__name__})


def search_redirect(request):
    """Redirect to the list with a query string and a fragment (reverse(query=, fragment=), Django 5.2+)."""
    url = reverse("catalog:book-list", query={"q": request.GET.get("q", ""), "sort": "title"}, fragment="results")
    return HttpResponseRedirect(url)


class BookCreate(CreateView):
    model = Book
    fields = ["title", "slug", "isbn"]  # explicit fields, never "__all__"
    template_name = "catalog/book_form.html"
    # reverse() here would fail at import time: the URLconf imports this module. reverse_lazy waits.
    success_url = reverse_lazy("catalog:book-list")


def boom(request):
    raise RuntimeError("a bug in the view")


def forbidden(request):
    raise PermissionDenied("members only")


def missing(request):
    raise Http404("no such book")


async def ping(request):
    """Async views are routed exactly like sync ones; resolution itself is synchronous and CPU-only."""
    return JsonResponse({"pong": True, "resolved": request.resolver_match.view_name})
----

[#path]
== path(): routes, kwargs and name

`path(route, view, kwargs=None, name=None)` returns one element of `urlpatterns`.

* *`route`* is a string (or a `gettext_lazy()` string, see <<i18n-urls>>) containing the pattern. Angle brackets capture a part of the URL
and pass it to the view as a keyword argument (`<slug:slug>`); the part before the colon is the converter, which limits what matches and
what Python type the view receives. Without a converter the capture is `str` and matches any non-empty text except `/`.
* *`view`* is a function, the result of `View.as_view()` for class-based views, or an `include()`. Passing the class itself (a frequent
slip: `views.BookCreate` instead of `views.BookCreate.as_view()`) is caught by the system check `urls.E009`.
* *`kwargs`* is a dictionary of extra keyword arguments added to every call (<<extra-options>>).
* *`name`* makes the pattern reversible (<<naming>>).

Some rules are easy to miss and cause real bugs:

* *No leading slash.* Every URL has one, so you write `books/`, never `/books/` (system check `urls.W002`).
* *Order matters: the first match wins.* In `catalog/urls.py` `books/new/` comes before `books/<slug:slug>/`; swap them and the create
page becomes a book with the slug `new`, which `get_object_or_404` turns into a 404. Put specific literals before generic captures.
* *Trailing slashes are part of the pattern.* `books/` does not match `/books` (<<append-slash>>). Pick a convention (Django's is a
trailing slash on pages, none on file-like URLs such as `sitemap.xml` or `robots.txt`) and keep to it.
* *The method, the query string and the host are not matched.* `https://example.com/books/?page=3` is looked up as `books/`.
* *Patterns are matched against `path_info`.* Behind a proxy that mounts the project under a prefix, the prefix is the script prefix and
is not part of the route (<<script-prefix>>).

[#converters]
== Path converters

Converters make the common cases (numbers, slugs, UUIDs) readable and typed without a regular expression. Django ships five:

[cols="1,2,2,3",options="header"]
|===
| Converter | Regular expression | Python value | Notes

| `str` (default)
| `[^/]+`
| `str`
| Any non-empty text excluding `/`. Used when you write `<name>` with no converter.

| `int`
| `[0-9]+`
| `int`
| Zero or any positive integer. No sign, no limit on digits, leading zeros accepted (`007` becomes `7`).

| `slug`
| `[-a-zA-Z0-9_]+`
| `str`
| ASCII letters, digits, hyphen and underscore. Non-ASCII slugs from `allow_unicode=True` do not match.

| `uuid`
| `[0-9a-f]\{8}-[0-9a-f]\{4}-[0-9a-f]\{4}-[0-9a-f]\{4}-[0-9a-f]\{12}`
| `uuid.UUID`
| Dashes required and letters lowercase, so one UUID has exactly one URL.

| `path`
| `.+`
| `str`
| Any non-empty text *including* `/`: a whole sub-path such as `covers/2024/dune.png`. Put it last and give the route no trailing slash.
|===

The curl session below shows the values and Python types that reach the view (the `echo` view prints `repr(value)` and the type name).
Note that `year` and `month` arrive as `int`, not `str`:

[source,bash]
----
$ curl -si 'localhost:8822/published/2024/3/'

----

Converters have two jobs and one rule. They match (the `regex`), they convert (`to_python()` for the URL to the view, `to_url()` for
`reverse()`), and `ValueError` raised from either one means "this pattern does not apply": an incoming URL falls through to the next
pattern and finally to a 404, and a reverse lookup raises `NoReverseMatch` unless another pattern with the same name fits. Raising
`ValueError` from `to_url()` has been supported since Django 3.1.

[#custom-converters]
=== Custom converters

A converter is a plain class with a `regex` string attribute and the two methods. The Bookshelf registers two: a four-digit year, taken from
the official documentation's own example, and an ISBN-13 whose check digit is validated, so a mistyped ISBN is a 404 at routing time
instead of a failed lookup inside the view:

.catalog/converters.py
[source,python]
----
class FourDigitYearConverter:
    regex = "[0-9]{4}"

    def to_python(self, value):
        return int(value)

    def to_url(self, value):
        return "%04d" % value


class Isbn13Converter:
    """Matches 13 digits and rejects numbers whose check digit is wrong."""

    regex = "[0-9]{13}"

    @staticmethod
    def _valid(digits: str) -> bool:
        total = sum(int(d) * (1 if i % 2 == 0 else 3) for i, d in enumerate(digits[:12]))
        return (10 - total % 10) % 10 == int(digits[12])

    def to_python(self, value):
        if not self._valid(value):
            raise ValueError(value)  # no match: Django tries the next pattern, then 404
        return value

    def to_url(self, value):
        value = str(value)
        if len(value) != 13 or not value.isdigit() or not self._valid(value):
            raise ValueError(value)  # reverse() raises NoReverseMatch
        return value
----

`register_converter(converter, type_name)` takes the class (not an instance; Django instantiates it) and the name used inside angle
brackets. Call it at import time of a URLconf module, as `catalog/urls.py` does above, so the name exists before any pattern uses it. Two
details matter on Django 6.1:

* Registering a name twice, or a name that is a built-in (`int`, `str`, ...), raises `ValueError("Converter 'yyyy' is already
registered.")`. Overriding converters was deprecated in Django 5.1 and became an error in 6.0; a test below pins this behaviour.
* The `regex` is spliced into the pattern's regular expression, so it must not contain capturing groups. Use `(?:...)` if you need
grouping.

Pitfalls specific to converters:

* *`int` accepts leading zeros and has no upper bound.* `/page/007/` resolves to the same view as `/page/7/`, and `reverse()` always gives
`/page/7/`. Two URLs for one page is a duplicate-content problem for search engines; if it matters, use a stricter custom converter
(`[1-9][0-9]*`).
* *`slug` is ASCII only.* If your slugs contain accented characters, use `str` with a model lookup, or a custom converter with the regex
you need.
* *Converters match text, not existence.* `<int:pk>` matches `/books/999999/` even if there is no such book; the 404 comes from the view
(`get_object_or_404`), not the router.

[#re-path]
== re_path(): regular expressions

`re_path(route, view, kwargs=None, name=None)` is `path()` with a regular expression for the route, compatible with Python's `re` module. It
is the direct successor of the old `url()` (<<migrating>>). Use it when no combination of converters expresses what you need: optional
segments, several alternatives in one pattern, matching a fixed number of digits without writing a converter, or legacy URLs that must
keep working character for character.

* Write the route as a raw string (`r"..."`) so that sequences like `\d` need no doubled backslash.
* If the route ends in `$`, the whole of `path_info` must match (`re.fullmatch()` is used); otherwise the pattern matches a prefix, which
is how `include()` prefixes work with `re_path()`.
* Named groups `(?P<name>...)` become keyword arguments; unnamed groups `(...)` become positional arguments. Mixing both styles in one
pattern is a bug waiting to happen: when both appear, the unnamed groups are ignored.
* *All values arrive as strings.* There is no type conversion with `re_path()`. Switching a pattern between `path()` and `re_path()` changes
the type of the view's arguments, so adapt the view.
* Use non-capturing groups `(?:...)` for structure that the view does not need. Nested capturing groups pass the outer and the inner match
to the view and, worse, force you to reverse with a piece of URL.

The script below builds a throw-away URLconf and prints what `resolve()` and `reverse()` do with each style:

.ex/re_path_demo.py (run with `python manage.py shell -v0 < ex/re_path_demo.py`)
[source,python]
----
import types

from django.urls import NoReverseMatch, path, resolve, re_path, reverse

from catalog import views

urls = types.ModuleType("demo_urls")  # a throw-away URLconf, passed to resolve() and reverse()
urls.urlpatterns = [
    re_path(r"^legacy/([0-9]{4})/$", views.echo),                         # unnamed group -> positional
    re_path(r"^mixed/(\d+)/(?P<slug>[a-z]+)/$", views.echo),              # mixed -> unnamed ignored
    re_path(r"^blog/(page-([0-9]+)/)?$", views.echo, name="blog"),        # nested capture: bad
    re_path(r"^comments/(?:page-(?P<page_number>[0-9]+)/)?$", views.echo, name="comments"),  # good
    re_path(r"^kind/(?P<kind>books|authors)/$", views.echo, name="kind"),  # alternation inside a group
    re_path(r"^(?:books|authors)/$", views.echo, name="either"),          # top-level alternation
    path("n/<int:n>/", views.echo),
]

for url in ["/legacy/2024/", "/mixed/5/dune/", "/blog/page-2/", "/blog/", "/comments/page-2/", "/kind/books/", "/n/007/"]:
    match = resolve(url, urlconf=urls)
    print(f"{url:<20} args={match.args!r:<22} kwargs={match.kwargs}")

print(reverse("kind", kwargs={"kind": "authors"}, urlconf=urls))
print(reverse("blog", args=["page-2/"], urlconf=urls))      # you must pass the OUTER group
print(reverse("comments", kwargs={"page_number": 2}, urlconf=urls), reverse("comments", urlconf=urls))
try:
    reverse("either", urlconf=urls)
except NoReverseMatch:
    print("either: NoReverseMatch (a top-level | cannot be reversed)")
----

/blog/page-2/        args=('page-2/', '2')       kwargs={}
/blog/               args=(None, None)           kwargs={}
/comments/page-2/    args=()                     kwargs={'page_number': '2'}

Reading the output:

* `/legacy/2024/` arrives as the positional argument `'2024'`, a string.
* In the mixed pattern only `slug` is passed; the unnamed `(\d+)` group is silently dropped.
* The "bad" `blog` pattern passes `('page-2/', '2')` and `(None, None)` when the optional part is absent, and it can only be reversed by
passing the *outer* group (`page-2/`), a piece of URL rather than a page number.
* The "good" `comments` pattern with `(?:page-...)` passes only `page_number='2'`, and when the optional part is missing *the keyword
argument is omitted altogether*, not passed as `None`. A view behind an optional named group therefore needs a default value
(`def comments(request, page_number=1)`). The `echo` view above printed an empty `kwargs` for `/comments/` in the test suite for the same
reason.
* An alternation *inside a named group* (`(?P<kind>books|authors)`) reverses fine, because the group is replaced by the argument you
give. An alternation at the top level of the pattern (`^(?:books|authors)/$`) cannot be reversed: `reverse()` raises `NoReverseMatch`.
Django documents this restriction: patterns that you reverse must not contain choices with `|` outside a captured group.
* `/n/007/` matched `path("n/<int:n>/")` with `n=7`, the leading-zero duplicate URL mentioned above.

[#extra-options]
== Extra options and default arguments

There are three ways to give a view values that are not in the URL, and each is visible in `catalog/urls.py`:

* *The `kwargs` dictionary* (third positional argument of `path()`): `path("about/", views.echo, {"template": "about"}, name="about")`
calls `echo(request, template="about")`. If a captured name and a dictionary key collide, *the dictionary wins*. The syndication
framework uses this technique to hand options to its feed views.
* *Defaults on the view*: `page/` and `page/<int:num>/` both point at `views.page`, whose signature is `def page(request, num=1)`. The first
pattern captures nothing, so the view's default applies. Give the two patterns distinct names (`page-first`, `page`) or reverse them by
argument count; Django also matches names by the number and names of the arguments you pass.
* *`include()` with extra options*: `path("blog/", include("inner"), {"blog_id": 3})` passes `blog_id=3` to *every* pattern of the included
module, whether or not the view accepts it. Use it only when you control all the views in the module.

[#include]
== include(): composing URLconfs

`include()` mounts another set of patterns under a prefix. Django chops off the part of the URL matched so far and hands the rest to the
included patterns, so `catalog/urls.py` never needs to know whether it lives at `/`, `/shop/` or `/outlet/`. The signatures are:

* `include(module, namespace=None)`: a dotted path to a URLconf module (or the module object itself). The application namespace is
taken from the module's `app_name`.
* `include(pattern_list)`: any iterable of `path()`/`re_path()` instances, for small inline groups.
* `include((pattern_list, app_namespace), namespace=None)`: a 2-tuple that carries the application namespace with the list.

Typical uses, taken from the official guide and from `config/urls.py` above:

[source,python]
----
from django.urls import include, path

from credit import views as credit_views

extra_patterns = [
    path("reports/", credit_views.report),
    path("reports/<int:id>/", credit_views.report),
    path("charge/", credit_views.charge),
]

urlpatterns = [
    path("help/", include("apps.help.urls")),         # a module, by dotted path
    path("credit/", include(extra_patterns)),         # an inline list
    # one prefix, many suffixes: state the common part once
    path(
        "<page_slug>-<page_id>/",
        include([path("history/", views.history), path("edit/", views.edit)]),
    ),
]
----

Rules for `include()`:

* *Captured parameters flow down.* `path("<username>/blog/", include("foo.urls.blog"))` passes `username` to every view of
`foo/urls/blog.py`.
* *Never end the prefix route of an `include()` with `$`.* The rest of the URL must still be matched by the included patterns, so a `$`
makes everything below it unreachable; system check `urls.W001` warns about it (<<system-checks>>).
* *A trailing slash on the prefix is conventional.* `include("catalog.urls")` under `path("shop", ...)` would give `/shopbooks/`.
* *`include()` order is match order.* `path("", include("catalog.urls"))` in `config/urls.py` is last on purpose: an empty prefix matches
every URL, so anything placed after it that it can match is shadowed.
* *`i18n_patterns()` cannot be used inside an included URLconf*, only in the root one (<<i18n-urls>>).
* *Mount a project's URLs in one place.* Keep the include list in `config/urls.py` short and let each app own its patterns; this is the
same boundary as the app boundary described on xref:web/django/project-structure-and-apps.adoc[Project Structure & Apps].

`include()` also validates its arguments. Asking for an instance namespace without an application namespace is an error, which the
scratch project reproduced as:

[source,text]
----
ImproperlyConfigured: Specifying a namespace in include() without providing an app_name is not supported. Set the app_name attribute in the
included module, or pass a 2-tuple containing the list of patterns and app_name instead.
----

Source: https://docs.djangoproject.com/en/6.1/ref/urls/#include[django.urls.include()] and
https://docs.djangoproject.com/en/6.1/topics/http/urls/#including-other-urlconfs[Including other URLconfs]

[#naming]
== Naming URL patterns

Reversing needs names. Any string is allowed (it is not a Python identifier), but follow these rules:

* *Give every pattern that you link to a name*, and name patterns after what they are, not where they are: `book-detail`, `book-create`,
not `books-slug-view`.
* *Avoid names that other apps might use.* If two apps both call a pattern `comment`, `reverse("comment")` finds whichever is last in the
project's `urlpatterns`. Prefix with the app (`catalog-comment`) or, better, use a namespace (<<namespaces>>).
* *Do not put a colon in a name.* The colon is the namespace separator (system check `urls.W003`).
* *Reuse a name deliberately to override a view.* Django's own `LoginView` is found by `reverse("login")`; if you name your own login
route `login` and include it after `django.contrib.auth.urls`, `reverse()` finds yours.
* *The same name can serve several patterns* if they differ in their arguments. `reverse()` matches the name, the number of positional
arguments or the names of the keyword arguments, and any converter that raises `ValueError` in `to_url()`.

Source: https://docs.djangoproject.com/en/6.1/topics/http/urls/#naming-url-patterns[Naming URL patterns]

[#namespaces]
== Application and instance namespaces

Namespaces let different apps (or several copies of one app) use the same URL names without clashing. A namespace has two parts, and both
are strings:

* *Application namespace*: the name of the app being deployed. Every instance of an app shares it. It comes from `app_name` in the
included module or from the 2-tuple form of `include()`. Django's admin has the application namespace `admin`.
* *Instance namespace*: identifies one deployment of the app. It must be unique across the project. By default it equals the application
namespace, which makes that instance the *default instance*; pass `namespace="shop"` to `include()` to give it another name.

A namespaced name is written `app:name`, and namespaces nest: `api:v1:book-list` is the pattern `book-list` in the namespace `v1`, itself
inside `api`. The Bookshelf uses all of it. `catalog/urls.py` sets `app_name = "catalog"`; `config/urls.py` includes the module three times
(instances `shop`, `outlet`, and the default instance `catalog` at the root), and `api_urls.py` includes `api_v1_urls.py`, each with its own
`app_name`.

When Django reverses `catalog:book-list` it follows the documented strategy, which is worth knowing by heart because it explains most
"why did the link go to the wrong place" surprises:

[mermaid]
....
flowchart TD
  start(["reverse of app:name"]) --> appns{"app matches an<br/>application namespace?"}
  appns -->|"no"| inst["Look up app as an instance namespace directly"]
  appns -->|"yes: a list of instances"| cur{"current_app given<br/>or request.current_app set?"}
  cur -->|"yes"| use1["Use that instance, if it is one of the list"]
  cur -->|"no"| def{"An instance whose namespace<br/>equals the application namespace?"}
  def -->|"yes"| use2["Use the default instance"]
  def -->|"no"| use3["Use the last deployed instance"]
  inst --> done(["Resolve the name inside the instance"])
  use1 --> done
  use2 --> done
  use3 --> done
....

Applied to the Bookshelf's `config/urls.py`, the observed behaviour is:

* `reverse("shop:book-list")` and `reverse("outlet:book-list")` always go to that instance: `/shop/` and `/outlet/`.
* `reverse("catalog:book-list")` with no current instance goes to the *default instance* (instance namespace `catalog`): `/`. With only the
`shop` and `outlet` includes (no default instance), the same call returns `/outlet/`, the last deployed instance (checked with a throw-away
URLconf), which is the surprise that bites people who add a second instance later; `current_app="shop"` there returns `/shop/`.
* `reverse("catalog:book-list", current_app="outlet")` goes to `/outlet/`. The `current_app` hint is how a page rendered inside the
`outlet` instance keeps its links inside it.
* The `{% url %}` tag takes the namespace of the currently resolved view (`request.resolver_match.namespace`) as the current app, unless you
set `request.current_app` (<<url-tag>>). In a class-based view, pass `current_app=self.request.resolver_match.namespace` to `reverse()`
yourself.

.catalog/tests.py: instance namespaces, the default instance and the url tag following the current instance
[source,python]
----
class BookUrlsTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        cls.book = Book.objects.create(title="Dune", slug="dune", isbn="9780306406157")

    def test_get_absolute_url_and_template_url_tag(self):
        self.assertEqual(self.book.get_absolute_url(), "/books/dune/")
        html = self.client.get("/").content.decode()
        self.assertIn('href="/books/dune/"', html)
        self.assertIn('href="/isbn/9780306406157/"', html)
        self.assertIn('href="/books/new/"', html)
        self.assertIn("no optional page", html)  # {% url ... as var %} does not raise
        # {% url %} takes no query argument; {% querystring %} (Django 5.1+) appends one
        self.assertIn('href="/?page=2"', html)

    def test_url_tag_follows_the_current_instance(self):
        html = self.client.get("/shop/books/dune/").content.decode()
        self.assertIn("instance <code>shop</code>", html)
        self.assertIn('href="/shop/"', html)  # {% url 'catalog:book-list' %} stayed in "shop"
        html = self.client.get("/outlet/books/dune/").content.decode()
        self.assertIn('href="/outlet/"', html)

    def test_create_view_uses_reverse_lazy_success_url(self):
        response = self.client.post("/books/new/", {"title": "Emma", "slug": "emma", "isbn": "9780141439587"})

Pitfalls:

* *Duplicate instance namespaces.* Two `include()` calls with the same `namespace` make one of them unreachable by name; system check
`urls.W005` warns ("URL namespace ... isn't unique").
* *A namespace without an `app_name`* is an `ImproperlyConfigured` error since Django 2.0 (see above).
* *Reversing a namespaced view by its callable* does not work: `reverse(views.archive)` only reverses non-namespaced patterns. Always
reverse by name.
* *Do not hardcode instance names in reusable code.* A reusable app should reverse its own names through its application namespace and
let the project decide how many instances to deploy (that is what `AdminSite` instances do).

[#reverse]
== reverse() and reverse_lazy()

`reverse(viewname, urlconf=None, args=None, kwargs=None, current_app=None, *, query=None, fragment=None)` returns the absolute *path* (no
scheme or host) for a URL pattern name. It is the Python-code counterpart of the `{% url %}` tag, and the reason a URL is written exactly
once, in the URLconf.

* *`viewname`* is a pattern name (`"catalog:book-detail"`) or, discouraged, a callable view object from the URLconf. A view built with
`as_view()` can be reversed by object only if the same object is used in the URLconf, and namespaced views cannot be reversed by object.
* *`args` or `kwargs`*, never both: passing both raises `ValueError`.
* *`current_app`* is the hint described in <<namespaces>>.
* *`urlconf`* names a different URLconf module to reverse against (default: the root URLconf of the current thread, which is
`request.urlconf` if a middleware set one).
* *`query`* (Django 5.2 and later, keyword-only) is added to the returned URL after a `?`. It accepts a `QueryDict` (for example
`request.GET`) or anything `urllib.parse.urlencode()` accepts: a dict, or a list of pairs for repeated keys. Values are encoded for you.
* *`fragment`* (5.2 and later) is appended after `#`, *without* encoding.
* The result is already URL-quoted. Do not run it through `urllib.parse.quote()` again.
* If nothing matches, `NoReverseMatch` is raised. Its message lists every pattern that was tried.

The script below exercises all of it. On Django 5.1 or older, `query=` and `fragment=` raise `TypeError`; build the query string with
`urllib.parse.urlencode()` there.

.ex/reverse_demo.py (run with `python manage.py shell -v0 < ex/reverse_demo.py`)

=== reverse_lazy()

`reverse_lazy()` has the same signature but evaluates when the value is first used. It is needed whenever the URL is required before the
URLconf can be loaded, which is typically at import time of a module that the URLconf itself imports:

* the `success_url` attribute of a generic class-based view (a class body runs at import);
* the `login_url` argument of a decorator such as `permission_required`;
* a default value in a function signature.

`BookCreate` in `catalog/views.py` shows the first case, and the test `test_create_view_uses_reverse_lazy_success_url` above posts a form
and follows the redirect. Calling plain `reverse()` in that class body would try to import `config.urls` while `catalog.views` is still
being imported, a circular import. Inside a method, which runs per request, use `reverse()`; the lazy version only adds a proxy.

=== Redirecting after a POST

The idiomatic use of `reverse()` in a view is the Post/Redirect/Get redirect. `search_redirect` builds a URL with a query string and a
fragment, and the `redirect()` shortcut accepts a pattern name, a model instance (through `get_absolute_url()`), or a URL directly:

[source,python]
----
from django.shortcuts import redirect

def archive_book(request, slug):
    ...                                   # change state on POST only
    return redirect("catalog:book-list")  # a pattern name, resolved with reverse()

def after_create(request, book):
    return redirect(book)                 # calls book.get_absolute_url()
----

[#resolve]
== resolve() and ResolverMatch

`resolve(path, urlconf=None)` does what the dispatcher does: it turns a path into a `ResolverMatch`, or raises `Resolver404` (a subclass of
`Http404`) when nothing matches. Use it in tests, in middleware that needs to know which view will run, and in tools. A `ResolverMatch`
carries:

[cols="2,5",options="header"]
|===
| Attribute | Meaning

| `func`
| The view callable (for a class-based view, the function returned by `as_view()`, which has a `view_class` attribute).

| `args`, `kwargs`
| The positional and keyword arguments the view will receive. `kwargs` is `captured_kwargs` plus `extra_kwargs`.

| `captured_kwargs`, `extra_kwargs`
| The values captured from the URL, and the values added by the `kwargs` dictionary of `path()`/`include()`.

| `url_name`
| The `name` of the matched pattern.

| `route`
| The route of the matching pattern, for example `shop/published/<yyyy:year>/`.

| `app_name`, `app_names`
| The application namespace (and its components: `foo:bar` gives `['foo', 'bar']`).

| `namespace`, `namespaces`
| The instance namespace and its components.

| `view_name`
| The name including the namespace, e.g. `shop:by-year`, or the dotted path of the view if the pattern has no name.

| `tried`
| The patterns tried before the match; useful in debugging.
|===

A `ResolverMatch` unpacks as the triple `(func, args, kwargs)`; the session in the reverse demo above printed one:

[source,text]
----
ResolverMatch(func=catalog.views.echo, args=(), kwargs={'year': 2024}, url_name='by-year', app_names=['catalog'], namespaces=['shop'], route='shop/published/<yyyy:year>/', captured_kwargs={'year': 2024})
----

During a request the same object is `request.resolver_match`; the `echo` view uses it to print `view_name`, `route` and the namespaces
(see the curl output earlier on this page). It is how logging, analytics and CSS "active link" helpers know which route is running (`request.resolver_match.url_name`)
without parsing the path.

[#url-tag]
== The {% url %} template tag

In templates, `{% url %}` is `reverse()`: the first argument is the pattern name (a quoted literal or a context variable) and the rest are the
arguments, positional or keyword but never mixed. Special characters in the result are encoded with `iri_to_uri()`.

.catalog/templates/catalog/book_list.html
[source,html+django]
----
<h1>Books</h1>
<ul>
{% for book in books %}
  <li><a href="{{ book.get_absolute_url }}">{{ book.title }}</a>
      (<a href="{% url 'catalog:by-isbn' isbn=book.isbn %}">ISBN</a>)</li>
{% empty %}
  <li>No books yet.</li>
{% endfor %}
</ul>
<p><a href="{% url 'catalog:book-create' %}">Add a book</a></p>
<p>Archive: <a href="{% url 'catalog:by-year' 2024 %}">2024</a></p>
{% url 'catalog:missing-page' as optional_url %}
{% if optional_url %}<a href="{{ optional_url }}">never rendered</a>{% else %}no optional page{% endif %}
<p>Next: <a href="{% url 'catalog:book-list' %}{% querystring page=2 %}">page 2</a></p>
----

* `{% url 'catalog:by-isbn' isbn=book.isbn %}` uses keyword syntax; `{% url 'catalog:by-year' 2024 %}` uses positional syntax.
* `{% url 'catalog:missing-page' as optional_url %}` stores the URL in a variable instead of printing it and, unlike the plain form,
*does not raise* `NoReverseMatch` when the name does not exist; the variable is empty and `{% if %}` handles it. The variable is
scoped to the enclosing `{% block %}`. This is how a reusable template links to an optional page.
* A missing name *without* `as var` raises `NoReverseMatch` and the page becomes a 500 (a debug page with `DEBUG = True`). That is the
intended fail-fast behaviour for a link you expect to exist.
* The tag has no `query` or `fragment` argument. Append a query string with `{% querystring %}` (Django 5.1 and later), as in the last
line of the template, or write `?q={{ term|urlencode }}` by hand.
* *Always quote the name.* `{% url book-detail book.slug %}` without quotes looks up a context *variable* named `book-detail`, which is a
syntax or `NoReverseMatch` error at best and silently wrong at worst.
* The namespace of the current view is used as the current app, so a template served by the `shop` instance links to `/shop/`, as the
test `test_url_tag_follows_the_current_instance` verifies. It needs `django.template.context_processors.request` or a `RequestContext`
(`render()` provides one). To override the choice, set `request.current_app` in the view before rendering.
* For links to model instances prefer `{{ book.get_absolute_url }}`: the model, not each template, then decides what a book's address is.

The detail template shows the instance namespace of the resolved URL:

.catalog/templates/catalog/book_detail.html
[source,html+django]
----
<h1>{{ book.title }}</h1>
<p>You are in the instance <code>{{ request.resolver_match.namespace }}</code>.</p>
<p><a href="{% url 'catalog:book-list' %}">Back to the list</a></p>
----

https://docs.djangoproject.com/en/6.1/ref/templates/builtins/#querystring[The querystring template tag] and

[#error-handlers]
== Error handlers: handler400, handler403, handler404 and handler500

When no pattern matches, or a view raises, Django calls one of four error views. The defaults live in `django.views.defaults` and render
`400.html`, `403.html`, `404.html` and `500.html` from the top of your template tree if you provide them (they are used when `DEBUG` is
`False`; the 404 template receives `request_path` and `exception`, the 403 template receives `exception`, and the 400 and 500 templates
receive no exception text on purpose, so that nothing is disclosed). Override a handler by
assigning a callable or a dotted path to a *module-level variable of the root URLconf*; setting it in any other URLconf has no effect.

[cols="1,2,2",options="header"]
|===
| Variable | Raised by | Signature

| `handler400`
| `SuspiciousOperation` and its subclasses (bad host header, malformed multipart upload...)
| `view(request, exception)`, returns `HttpResponseBadRequest`

| `handler403`
| `PermissionDenied`
| `view(request, exception)`, returns `HttpResponseForbidden`

| `handler404`
| `Http404`, including the `Resolver404` of an unmatched URL
| `view(request, exception)`, returns `HttpResponseNotFound`

| `handler500`
| Any other exception raised by a view
| `view(request)`, *no* `exception` argument; returns `HttpResponseServerError`
|===

Since Django 2.0, custom 400, 403 and 404 views that do not accept the `exception` argument are no longer supported (and the default
handlers became callables instead of dotted paths); system checks `urls.E007` and `urls.E008` verify, at startup, that each custom handler can
be imported and takes the right number of arguments. The Bookshelf's handlers answer in JSON, which is what an API wants; an HTML site
would `render()` a template instead:

.catalog/error_views.py
[source,python]
----
from django.http import JsonResponse


def not_found(request, exception):
    # For an unmatched URL the exception is a Resolver404 whose first argument is a dict
    # ({"tried": [...], "path": ...}) describing your whole URLconf: never echo str(exception).
    message = exception.args[0] if exception.args and isinstance(exception.args[0], str) else ""
    return JsonResponse({"error": "not found", "path": request.path, "detail": message}, status=404)


def permission_denied(request, exception):
    return JsonResponse({"error": "forbidden"}, status=403)


def bad_request(request, exception):
    return JsonResponse({"error": "bad request"}, status=400)


def server_error(request):  # no `exception` argument: Django calls handler500(request)
    return JsonResponse({"error": "server error"}, status=500)
----

.catalog/tests.py: the handlers, DEBUG and request.urlconf
[source,python]
----
@override_settings(DEBUG=False, ALLOWED_HOSTS=["testserver", "api.localhost"])
class ErrorHandlerTests(SimpleTestCase):
    def setUp(self):
        self.client.raise_request_exception = False  # let the client return the 500 response

    def test_custom_handlers(self):
        r = self.client.get("/nope/")
        self.assertEqual((r.status_code, r.json()["error"]), (404, "not found"))
        self.assertEqual(r.json(), {"error": "not found", "path": "/nope/", "detail": ""})  # no URLconf leak
        r = self.client.get("/missing/")
        self.assertEqual(r.json()["detail"], "no such book")
        r = self.client.get("/forbidden/")
        self.assertEqual((r.status_code, r.json()), (403, {"error": "forbidden"}))
        r = self.client.get("/boom/")
        self.assertEqual((r.status_code, r.json()), (500, {"error": "server error"}))

    @override_settings(DEBUG=True)
    def test_with_debug_true_the_technical_404_page_wins(self):
        r = self.client.get("/nope/")
        self.assertEqual(r.status_code, 404)
        self.assertIn("Page not found", r.content.decode())  # Django's debug page, not handler404

    def test_request_urlconf_selects_another_urlconf(self):
        self.assertEqual(self.client.get("/", headers={"host": "api.localhost"}).json()["view_name"], "api-root")
        self.assertEqual(self.client.get("/about/", headers={"host": "testserver"}).json()["view_name"], "catalog:about")
----

The `curl` session below ran against `runserver` with `DEBUG = False`; `/boom/` raises `RuntimeError`, `/forbidden/` raises
`PermissionDenied`:

[source,bash]
----
$ curl -si 'localhost:8822/nope/'
HTTP/1.1 404 Not Found
{"error": "not found", "path": "/nope/", "detail": ""}
$ curl -si 'localhost:8822/forbidden/'
HTTP/1.1 403 Forbidden
{"error": "forbidden"}
$ curl -si 'localhost:8822/boom/'
HTTP/1.1 500 Internal Server Error
{"error": "server error"}
----

Four details from reading the implementation and from the run:

* *With `DEBUG = True`, `handler404` is not called.* Django shows its technical 404 page (with the list of patterns tried). That is why
the test above overrides `DEBUG=False`, and why "my custom 404 page never shows locally" is the most asked error-page question.
* *Never echo `str(exception)` for a URL that did not match.* The exception is a `Resolver404` whose first argument is a dictionary with
the whole list of patterns tried; printing it leaks your URLconf structure (an earlier draft of this handler did exactly that and the `curl`
output contained every route, including the admin prefix). The handler above only uses the message when it is a plain string (for example
`Http404("no such book")`).
* *Keep `handler500` trivial.* It runs when something already failed; if it touches the database, the cache or context processors that
caused the failure, it fails again. Render a static template or return a small response.
* *Test handlers by raising the exception in a test view*, with `@override_settings(ROOT_URLCONF=__name__)` for a module that defines
`handler403 = ...`, as the official documentation shows; `Client.raise_request_exception = False` lets the client return the 500 response
instead of re-raising it.

For CSRF failures there is a separate setting, `CSRF_FAILURE_VIEW`, not a `handler` variable. Views that return an error response
directly (`HttpResponseNotFound`, `HttpResponse(status=201)`) do not go through these handlers: the handlers are for exceptions.

[#per-request-urlconf]
== Choosing the URLconf per request

`request.urlconf`, when set by middleware, replaces `ROOT_URLCONF` for that request, and setting it to `None` returns to the default. This
is how a single Django process serves several hostnames with different routes (an `api.` subdomain, a "club" site, a staff site) without
running several projects. `HostUrlconfMiddleware` serves `config/urls_api_host.py` for hosts that start with `api.`:

.catalog/middleware.py
[source,python]
----
class HostUrlconfMiddleware:
    """Serve a different URLconf for api.* hosts by setting request.urlconf."""

    def __init__(self, get_response):
        self.get_response = get_response

    def __call__(self, request):
        host = request.get_host().split(":")[0]
        if host.startswith("api."):
            request.urlconf = "config.urls_api_host"
        return self.get_response(request)
----

.config/urls_api_host.py
[source,python]
----
from django.urls import path

from catalog import views

urlpatterns = [
    path("", views.echo, name="api-root"),
]
----

The test `test_request_urlconf_selects_another_urlconf` above sends two requests with different `Host` headers, and the real server
answered the same way:

[source,bash]
----
$ curl -s -H 'Host: api.localhost:8822' localhost:8822/
{"args": [], "kwargs": {}, "view_name": "api-root", "route": "", "app_names": [], "namespaces": []}
----

The middleware must be listed in `MIDDLEWARE` and must set `request.urlconf` *before* it calls `get_response`, because resolution happens
inside the innermost layer. `CommonMiddleware`'s `APPEND_SLASH` logic also consults `request.urlconf` when it decides whether a slash
redirect is possible, so a middleware that switches URLconfs belongs before `CommonMiddleware` if the redirect must follow the switch. (The
scratch project, whose host-specific URLconf has no slash-less routes, lists it right after `CommonMiddleware`.) Resolvers are cached per URLconf module, so
switching between a handful of modules is cheap, and `django.urls.set_urlconf()`/`get_urlconf()` exist for the rare place that has to switch
programmatically. `clear_url_caches()` is only needed in tests that modify a URLconf at runtime.

Source: https://docs.djangoproject.com/en/6.1/ref/request-response/#django.http.HttpRequest.urlconf[HttpRequest.urlconf] and
https://docs.djangoproject.com/en/6.1/topics/http/urls/#how-django-processes-a-request[How Django processes a request]

[#append-slash]
== Trailing slashes and APPEND_SLASH

`CommonMiddleware` implements the `APPEND_SLASH` setting (default `True`): if a request path does not end in `/`, does not match any pattern,
but would match once a slash is appended, the middleware answers with a permanent redirect (301) to the slash form. The test
`test_first_match_wins_and_trailing_slash` and the real server agree:

[source,bash]
----
$ curl -si 'localhost:8822/about'
HTTP/1.1 301 Moved Permanently
Location: /about/
----

Things to know:

* *A POST cannot be redirected without losing its body.* With `DEBUG = True`, an unslashed `POST`, `PUT`, `PATCH` or `DELETE` that would
need the redirect raises a `RuntimeError` explaining the problem, so that you notice in development. In production it silently becomes a
`301` and the data is lost; point forms at the slashed URL (generate it with `{% url %}`).
* *Opt a view out with `@no_append_slash`* from `django.views.decorators.common` (added in Django 3.2), for URLs that are intentionally
slash-less, such as file-like endpoints.
* *The redirect only fires when the slash form exists.* `/nope` stays a 404, not a redirect to `/nope/`.
* *Set `APPEND_SLASH = False`* for an API whose clients must get a clean 404 for the wrong spelling.
* *Case counts.* `/Books/` does not match `books/`. Django does not normalise case; add a redirect or lower-case at the proxy if you need
tolerance.

Source: https://docs.djangoproject.com/en/6.1/ref/middleware/#module-django.middleware.common[CommonMiddleware] and
https://docs.djangoproject.com/en/6.1/ref/settings/#append-slash[APPEND_SLASH]

[#redirectview]
== Redirecting old URLs with RedirectView

When you change a URL scheme, keep the old URLs alive with a permanent redirect. `RedirectView` builds the target from a pattern name, and
passes the captured arguments on:

[source,python]
----
from django.views.generic import RedirectView

path("old-books/<slug:slug>/", RedirectView.as_view(pattern_name="catalog:book-detail", permanent=True)),
----

That line is in `catalog/urls.py` above, and the real server answered with a 301 and `Location: /books/dune/`:

[source,bash]
----
$ curl -si 'localhost:8822/old-books/dune/'
HTTP/1.1 301 Moved Permanently
Location: /books/dune/
----

`permanent=True` answers 301 (browsers and search engines cache it), `False` answers 302. `RedirectView` also accepts `url=` and
`query_string=True`; Django 6.1 added `preserve_request`, which makes the redirect keep the HTTP method and body (status 307 or 308
instead of 302 or 301), useful when an endpoint moves and its POST clients must keep working. The class-based view page covers
`RedirectView` in full.

[#builtin-urlconfs]
== URLconfs that Django and other packages give you

Several pieces ship URLs that you `include()`; each has an `app_name` or a fixed set of names that other code expects:

* *The admin:* `path("admin/", admin.site.urls)` (namespace `admin`; `reverse("admin:index")`, `reverse("admin:app_list", kwargs={"app_label": "auth"})`).
Since Django 3.2 the admin installs a *catch-all view* that redirects unauthenticated visitors to the login page for any URL under its
prefix, so a pattern routed after `admin/` that also starts with `admin/` becomes unreachable. Reorder, or set
`AdminSite.final_catch_all_view = False`.
* *Authentication:* `path("accounts/", include("django.contrib.auth.urls"))` adds `login`, `logout`, `password_change` and the password
reset URLs under *unnamespaced* names (`login`, `logout`...), which is why `LOGIN_URL = "login"` works. `LogoutView` accepts only POST
since Django 5.0, so a logout link must be a small form.
* *Static and media files in development:* `static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)` from `django.conf.urls.static`
returns a pattern that serves files when `DEBUG` is true, and an *empty list otherwise* (and for prefixes that include a host). It is a
development convenience, never a production file server (see the static-files and file-upload pages). `STATIC_URL`/`MEDIA_URL` must end
with a slash (system check `urls.E006`).
* *Third-party and debug tools:* django-debug-toolbar adds `path("__debug__/", include("debug_toolbar.urls"))`; REST frameworks give you
routers that generate a URLconf from a viewset; admin sites for different audiences are separate `AdminSite` instances, which is the
instance-namespace feature at work.

[#i18n-urls]
== Translated and language-prefixed URLs

`i18n_patterns(*urls, prefix_default_language=True)` from `django.conf.urls.i18n` prepends the active language code to the patterns it
wraps (`/en/books/`, `/es/books/`), `reverse()` and `{% url %}` produce the URL in the active language, and routes may be marked
translatable with `gettext_lazy()` (`path(_("books/"), ...)`). It needs `LocaleMiddleware`, can only be used in the *root* URLconf (using it
in an included one raises `ImproperlyConfigured`), and `prefix_default_language=False` keeps existing URLs unprefixed for the default
language. Translating a segment needs a message catalogue, which is the subject of the internationalization page; the test below checks the
prefixing without one, and the unprefixed `/books/` is redirected by the middleware:

.config/urls_i18n.py
[source,python]
----
from django.conf.urls.i18n import i18n_patterns
from django.urls import path
from django.utils.translation import gettext_lazy as _

from catalog import views

urlpatterns = i18n_patterns(
    path(_("books/"), views.echo, name="books"),  # translated route: needs a catalogue to differ per language
    prefix_default_language=True,
)
----

.catalog/tests.py: language prefixes and an async view
[source,python]
----
class AsyncAndI18nTests(SimpleTestCase):
    async def test_async_view_is_routed_like_any_other(self):
        response = await AsyncClient().get("/ping/")
        self.assertEqual(response.json(), {"pong": True, "resolved": "catalog:ping"})

    @override_settings(
        ROOT_URLCONF="config.urls_i18n",

        MIDDLEWARE=["django.middleware.locale.LocaleMiddleware"],

[#script-prefix]
== The script prefix and mounting under a sub-path

If a proxy serves the project under a path such as `/bookshelf/`, the WSGI server passes that prefix as `SCRIPT_NAME`, Django stores it
with `set_script_prefix()`, and `reverse()`, `{% url %}` and redirects add it automatically, while patterns keep matching `path_info`
without it. `FORCE_SCRIPT_NAME` sets it explicitly. `get_script_prefix()` returns it (it is `"/"` when the project is at the root) and,
as the documentation warns, it cannot be used outside a request/response cycle because it relies on values initialised then. The test
`test_reverse_honours_the_script_prefix` above proves that `reverse()` adds `/bookshelf/` when the prefix is set. Never concatenate the
prefix by hand: use `reverse()` so that the same code works at `/` and under a sub-path.

Source: https://docs.djangoproject.com/en/6.1/ref/urlresolvers/#get-script-prefix[get_script_prefix()] and
https://docs.djangoproject.com/en/6.1/ref/settings/#force-script-name[FORCE_SCRIPT_NAME]

from django.core.management.base import BaseCommand
from django.urls import URLPattern, URLResolver, get_resolver


def walk(patterns, prefix="", namespace=""):
    for entry in patterns:
        route = prefix + str(entry.pattern)
        if isinstance(entry, URLResolver):
            ns = f"{namespace}{entry.namespace}:" if entry.namespace else namespace
            yield from walk(entry.url_patterns, route, ns)
        elif isinstance(entry, URLPattern):
            yield route, f"{namespace}{entry.name}" if entry.name else "-", entry.lookup_str


class Command(BaseCommand):
    help = "Print every route of the root URLconf as: route, namespaced name, view."

    def handle(self, *args, **options):
        for route, name, view in walk(get_resolver().url_patterns):
            self.stdout.write(f"{route:<42} {name:<22} {view}")
----

== Migrating from url() to path() and re_path()

Before Django 2.0 there was one routing function, `django.conf.urls.url()`, which took a regular expression. Django 2.0 added `path()`
(readable routes with converters) and `re_path()` (the same regular-expression behaviour as `url()`), made `include` importable from
`django.urls`, and Django 3.1 deprecated `url()`; it was *removed in Django 4.0*. On Django 6.1 the import fails:

[source,text]
----
ImportError: cannot import name 'url' from 'django.conf.urls'
----

(This is also asserted by the test `test_old_url_import_is_gone`.) The migration has two levels, and you can stop at the first one:

. *Mechanical:* rename `url(` to `re_path(` and import it from `django.urls`. The regular expressions stay, so the same URLs match and the
view still receives strings. This is safe and enough to run on a current Django.
. *Idiomatic:* convert the patterns that a converter expresses well to `path()`, and adapt the views for the new argument types.

Typical conversions:

[cols="3,3,3",options="header"]
|===
| Old | New | Notes

| `url(r"^$", v, name="home")`
| `path("", v, name="home")`
| No `^`, no `$`, no leading slash.

| `url(r"^books/(?P<pk>[0-9]+)/$", v)`
| `path("books/<int:pk>/", v)`
| `pk` is now an `int`; `/books/007/` still matches.

| `url(r"^tag/(?P<slug>[-\w]+)/$", v)`
| `path("tag/<slug:slug>/", v)`
| `slug` is ASCII only; `\w` also matches Unicode letters.

| `url(r"^archive/(?P<year>[0-9]\{4})/$", v)`
| `re_path(r"^archive/(?P<year>[0-9]\{4})/$", v)` or a `yyyy` converter
| `<int:year>` would accept any number of digits.

| `url(r"^blog/", include("blog.urls", namespace="blog", app_name="blog"))`
| `path("blog/", include("blog.urls", namespace="blog"))` plus `app_name = "blog"` in `blog/urls.py`
| The `app_name` argument of `include()` was removed in 2.0.

| `url(r"^admin/", include(admin.site.urls))`
| `path("admin/", admin.site.urls)`
| The 3-tuple form of `include()` was removed in 2.0.

| `url(r"^files/(?P<path>.*)$", v)`
| `path("files/<path:path>", v)`
| The `path` converter requires at least one character.
|===

The type change is the real risk: a view that did `int(year)` keeps working with an `int`, but one that did `year.zfill(4)` or compared with a
string breaks. The tests below show both syntaxes side by side in one URLconf and prove that they do not accept exactly the same URLs.

.config/urls_migration.py
[source,python]
----
from django.urls import include, path, re_path

from catalog import views

urlpatterns = [
    # Before (Django 1.x-3.x):  url(r"^archive/(?P<year>[0-9]{4})/$", views.echo)
    # Step 1, mechanical: same regex, same string arguments (works on Django 2.0+).
    re_path(r"^old/(?P<year>[0-9]{4})/$", views.echo),
    # Step 2, idiomatic: path() with a converter; the view now receives an int.
    path("new/<int:year>/", views.echo),
    # Before: url(r"^blog/", include("blog.urls", namespace="blog", app_name="blog"))
    # After: the application namespace lives in blog/urls.py as `app_name`; include() takes `namespace` only.
    path("blog/", include("catalog.urls", namespace="blog")),
]
----

.catalog/tests.py: the old and the new syntax
[source,python]
----
@override_settings(ROOT_URLCONF="config.urls_migration")
class UrlMigrationTests(SimpleTestCase):
    def test_re_path_keeps_strings_and_path_gives_ints(self):
        self.assertEqual(resolve("/old/2024/").kwargs, {"year": "2024"})
        self.assertEqual(resolve("/new/2024/").kwargs, {"year": 2024})

    def test_the_two_syntaxes_do_not_accept_exactly_the_same_urls(self):
        with self.assertRaises(Resolver404):
            resolve("/old/10000/")  # [0-9]{4} is exactly four digits
        self.assertEqual(resolve("/new/10000/").kwargs, {"year": 10000})  # <int:...> is any number of digits

    def test_old_url_import_is_gone(self):
        with self.assertRaises(ImportError):
            from django.conf.urls import url  # noqa: F401  (removed in Django 4.0)
----

*Automate the mechanical step.* The third-party django-upgrade tool rewrites `url()` calls when the target version is 2.0 or later. It
produces `path()` where the regular expression is a trivial route that a converter expresses and `re_path()` everywhere else. Run on this
file:

.legacy_demo/urls.py before
[source,python]
----
from django.conf.urls import include, url

from catalog import views

urlpatterns = [
    url(r"^$", views.book_list, name="book-list"),
    url(r"^books/(?P<pk>[0-9]+)/$", views.echo, name="book-detail"),
    url(r"^archive/(?P<year>[0-9]{4})/$", views.echo, name="archive"),
    url(r"^shop/", include("catalog.urls")),
]
----

[source,bash]
----
$ python -m django_upgrade --target-version 4.0 legacy_demo/urls.py
Rewriting legacy_demo/urls.py
----

.legacy_demo/urls.py after
[source,python]
----
from django.urls import include, path, re_path

from catalog import views

urlpatterns = [
    path("", views.book_list, name="book-list"),
    path("books/<int:pk>/", views.echo, name="book-detail"),
    re_path(r"^archive/(?P<year>[0-9]{4})/$", views.echo, name="archive"),
    path("shop/", include("catalog.urls")),
]
----

The tool (version 1.33.0 here; its fixer is named `django_urls`) exits with status 1 when it changed a file, so it fits a pre-commit hook.
It also rewrites existing `re_path()` calls to `path()` when the regular expression is eligible. Review its diff, because the `int` conversion
of `pk` is exactly the type change described above. Other old spellings you will meet in the same files:
`from django.core.urlresolvers import reverse` (module removed in 2.0, use `django.urls`), string view references such as
`url(r"^$", "app.views.home")` and `patterns("", ...)` (both removed in 1.10), `reverse("app.views.home")` with a dotted path (removed in 1.10).

[#sync-async]
== Sync and async notes

* *Routing is sync and trivial.* `resolve()` is a plain function that scans compiled regular expressions; the ASGI handler calls it directly
(`self.resolve_request(request)`) from the event loop without a thread hop, and converters, `reverse()`, `reverse_lazy()` and `resolve()` are
ordinary synchronous, I/O-free functions that are safe to call from async code.
* *The view's sync or async nature does not affect the pattern.* `path("ping/", views.ping)` works for `async def ping(request)` and the
test `test_async_view_is_routed_like_any_other` uses `AsyncClient` against it. A sync view reached through ASGI runs in a thread via
`sync_to_async`; an async view under WSGI is run to completion on a private event loop. The async page of this section explains when
each is worthwhile.
* *Keep converters and `to_python()` free of I/O.* A converter that queries the database would run inside the event loop on ASGI, blocking
it (and, in sync mode, would run for every non-matching pattern it is tried against). Validate formats in converters and look up rows in the
view.
* *`reverse()` in a coroutine is fine.* The only trap is `reverse_lazy()` proxies stored in module state: they evaluate on first use, in
whichever thread uses them first, which is harmless because the URLconf import is thread-safe.

Source: https://docs.djangoproject.com/en/6.1/topics/async/[Asynchronous support]

[#pitfalls]
== Pitfalls checklist

* *Hardcoded URLs.* `<a href="/books/{{ book.slug }}/">` and `redirect("/books/")` break when a prefix changes. Use `{% url %}`,
`get_absolute_url()` and `reverse()`.
* *`reverse()` at import time* (class attributes, default arguments, module constants) causes circular imports; use `reverse_lazy()`.
* *A missing `app_name`* is the cause of "`'catalog' is not a registered namespace`" (`NoReverseMatch`). Set `app_name` in the included module
or use the 2-tuple form.
* *Passing the class, not `as_view()`*, to `path()`; caught by `urls.E009`.
* *Specific routes after generic ones*, so `books/new/` becomes a slug lookup; put literals first.
* *`$` on an `include()` prefix* (`urls.W001`) and a leading `/` in a route (`urls.W002`).
* *Forgetting the trailing slash in a form action*, so a POST hits `APPEND_SLASH`; reverse the URL instead.
* *Mixing named and unnamed groups* in `re_path()`; the unnamed ones disappear.
* *Optional named groups pass nothing when absent*; give the view a default.
* *Reversing a top-level `|`*; restructure the pattern or add separate patterns for each alternative.
* *Same `include()` module mounted twice with the same instance namespace* (`urls.W005`); or relied on "last deployed instance" without
a default instance.
* *`handler404` seems ignored*, because `DEBUG = True` shows the technical 404 page; or because the handler was set in a URLconf other than
the root one.
* *Echoing `str(exception)` in a 404 handler* leaks the list of patterns tried.
* *Heavy work in `handler500`.* Return something static.
* *Registering a converter name twice* (for example by reloading a URLconf module in a test) raises `ValueError` since Django 6.0.
* *`int` leading zeros and unbounded size* give duplicate URLs; use a stricter custom converter.
* *Routing on the query string* is impossible; the URLconf never sees it. Branch in the view.
* *Different behaviour per HTTP method* belongs in the view (or `require_http_methods`), not in extra patterns: the URLconf ignores the method.

[#outdated]
== Where the books are outdated

The four reference books were written for Django 1.11 to 5; their URL chapters are right about the ideas (namespaces, named patterns,
`reverse()` instead of hardcoded URLs) and wrong about several spellings:

* *`url()`.* Older code and the Django 1.11 and 2 era books use `from django.conf.urls import url` with `^...$` regular expressions. `url()`
was deprecated in 3.1 and removed in 4.0. Use `path()` and `re_path()` (added in 2.0), see <<migrating>>.
* *`include()` arguments.* `include("app.urls", namespace="x", app_name="x")` and the 3-tuple `include(admin.site.urls)` were removed in 2.0;
the application namespace is `app_name` in the module (or the 2-tuple), and `admin.site.urls` goes straight into `path()`.
* *`django.core.urlresolvers`.* Removed in 2.0; import `reverse`, `reverse_lazy`, `resolve` and `NoReverseMatch` from `django.urls`.
* *Pre-1.10 idioms* such as `patterns("", ...)`, string view names and reversing by dotted path, still visible in old snippets, were removed in 1.10.
* *Everything is a string in the URL regexes of those books.* With `path()` and converters the view receives an `int`, `UUID` or custom type, so
code such as `int(pk)` is redundant (harmless) and `pk.isdigit()` raises `AttributeError`.
* *Logout links.* Books that link to `/accounts/logout/` with a GET produce a 405 on Django 5.0 and later, because `LogoutView` is POST-only.
* *Error handlers.* A custom `def handler404(request)` (or 400 or 403) without the `exception` argument fails: the argument has been required
since Django 2.0, and `urls.E007` reports the mismatch at startup. Only `handler500` takes just the request.
* *Query strings for redirects* are built by hand with `urlencode` in older code; `reverse(query=..., fragment=...)` does it since 5.2.

[#recent]
== What changed recently

[cols="1,4",options="header"]
|===
| Version | Change relevant to URLs and routing

| 6.1
| `RedirectView.preserve_request` keeps the HTTP method and body across the redirect. The URL dispatcher itself, `path()`, `include()`,
`reverse()` and the converters have no changes in the 6.1 release notes.

| 6.0
| Overriding an existing converter with `register_converter()` is no longer allowed (raises `ValueError`; deprecated in 5.1).

| 5.2 LTS
| `reverse()` and `reverse_lazy()` accept the keyword-only arguments `query` and `fragment`.

| 5.1
| The undocumented `django.urls.converters.get_converter()` was removed; overriding a registered converter was deprecated; the
`{% querystring %}` template tag arrived (for query strings in templates).

| 5.0
| `no_append_slash` is listed among the decorators that support async views; `LogoutView` accepts only POST.

| 4.0
| `django.conf.urls.url()` removed.

| 3.2
| The `@no_append_slash` decorator; the admin's final catch-all view (can disable with `AdminSite.final_catch_all_view = False`).

| 3.1
| Converters may raise `ValueError` from `to_url()` to mean "no match when reversing"; `url()` deprecated; async views.

| 2.0
| `path()`, `re_path()` and `from django.urls import include`; the `app_name` argument and 3-tuple form of `include()` removed;
`django.core.urlresolvers` removed; error handlers must accept `exception`; error-handler defaults became callables.
|===
