cached description of a query. This page shows how to build one, when it actually reaches the database, how to filter across
relationships, how to express "compare this column with that column" (`F`) and "this or that" (`Q`), how to create, update and
delete rows singly and in bulk, how to shape results (`values`, `alias`, `exists`, `contains`) and how to teach the ORM new lookups.

== QuerySets and laziness

A _manager_ (`Book.objects`) is the entry point; calling `all()`, `filter()` and the other query methods on it returns a
`QuerySet`. A QuerySet is a Python object that holds a query description, not rows. Three rules explain almost every ORM surprise:

. *Building is free.* `filter()`, `exclude()`, `order_by()`, `annotate()`, `values()`, slicing and the other "returns a new QuerySet" methods never touch the database.
. *Chaining never mutates.* Each of those methods returns a new QuerySet; the original is unchanged and can be reused as a base for other queries.
. *Evaluation runs the query once and caches the rows.* The first time you iterate, call `len()`, `list()`, `bool()` or `repr()`, index with a step, or pickle a QuerySet, Django executes the SQL and stores the instances in the QuerySet's result cache; reusing *that same object* costs no query.

.Laziness, caching and slicing (ex/e1_lazy.py)
[source,python]
----
from django.db import connection, reset_queries
from django.test.utils import CaptureQueriesContext
from catalog.models import Book

with CaptureQueriesContext(connection) as ctx:
    qs = Book.objects.filter(is_published=True)       # builds a query, runs nothing
    qs = qs.exclude(stock=0).order_by("-price")       # each call returns a NEW QuerySet
    print("queries after building:", len(ctx))
    print(qs.query)                                   # the SQL that would run
    titles = [b.title for b in qs]                    # iteration evaluates and fills the cache
    print("queries after iterating:", len(ctx))
    len(qs); bool(qs); list(qs)                       # served from the result cache
    print("queries after reusing cache:", len(ctx))
    qs.count()                                        # a fully loaded QuerySet answers from its cache
    print("queries after count() on a loaded QuerySet:", len(ctx))
    Book.objects.filter(is_published=True).count()    # a fresh QuerySet issues SELECT COUNT(*)
    print("queries after count() on a fresh QuerySet:", len(ctx))
print(titles)

# slicing an unevaluated QuerySet adds LIMIT/OFFSET and returns another QuerySet
page = Book.objects.order_by("title")[2:5]
print(type(page).__name__, "|", page.query)
# a step makes Django evaluate the slice immediately and return a list
print(type(Book.objects.order_by("title")[::2]).__name__)

# QuerySets are immutable: filter() never changes the original
base = Book.objects.all()
cheap = base.filter(price__lt=10)
print(base.count(), cheap.count())
----

The details that matter in practice:

* *Slicing.* `qs[2:5]` on an unevaluated QuerySet adds `LIMIT 3 OFFSET 2` and returns another QuerySet. A step (`qs[::2]`) forces evaluation and returns a list. Negative indices are not supported (`ValueError: Negative indexing is not supported.`), and a sliced QuerySet cannot be filtered further (`TypeError: Cannot filter a query once a slice has been taken.`) or deleted.
* *`str(qs.query)`* prints the SQL that would run (parameters inlined, for reading only). Do not execute it. For the SQL a block actually executed, wrap it in `CaptureQueriesContext`, as the listings here do, or use the Debug Toolbar.
* *The cache belongs to the object.* `Book.objects.filter(...)` called twice builds two QuerySets and runs two queries. Keep the QuerySet in a variable if you will iterate it twice, and pass it to the template rather than a list copy.
* *Which methods use the cache.* `len()`, iteration, `bool()` and `list()` evaluate and cache. `count()` on a QuerySet that is already loaded returns the length of the cache; on a fresh one it runs `SELECT COUNT(*)`. `exists()` and `contains()` use the cache when they can and otherwise ask the database for one row.
* *`if qs:` is a hidden `SELECT *`.* Truthiness evaluates the whole QuerySet. Use `qs.exists()` when you only need to know if there is a row, `qs.count()` when you only need the number, and `len(qs)` only when you will iterate afterwards.
* *`iterator()`* streams rows in chunks and bypasses the cache; it is the tool for very large results (see below).

[#request-cycle]
=== Where a query runs in the request/response cycle

A QuerySet is evaluated where it is first consumed, which is not always where it was written. A view that returns `Book.objects.all()` in the template context
queries when the template loop starts, after the view has returned; a QuerySet stored at module level is shared by every request and its result cache would be reused forever, so build
QuerySets inside the view (or call `.all()` on a stored one, which returns a fresh copy). The database connection is per thread and managed by Django: opened lazily on the first query of a request and
closed at the end of the request unless `CONN_MAX_AGE` keeps it open (`CONN_HEALTH_CHECKS` can validate a persistent connection before reuse). With `ATOMIC_REQUESTS = True` the whole view runs in one transaction, which is
covered on xref:web/django/transactions-raw-sql-and-multiple-databases.adoc[Transactions, Raw SQL & Multiple Databases]. The complete view and tests at the end of this page show the
cycle in action.

== Retrieving objects: all, filter, exclude and get

[cols="1,3",options="header"]
|===
|Method |Behaviour

|`all()`
|A QuerySet for every row (a copy; evaluation is still lazy).

|`filter(**lookups)`
|Rows matching all the keyword conditions (joined with `AND`). Arguments can also be `Q` objects (below).

|`exclude(**lookups)`
|Rows that do *not* match the combined conditions (`NOT (a AND b)`).

|`get(**lookups)`
|Exactly one object, as an instance, not a QuerySet. Raises `Model.DoesNotExist` for zero rows and `Model.MultipleObjectsReturned` for more than one (both subclass `ObjectDoesNotExist` / `MultipleObjectsReturned`).

|`first()` / `last()`
|The first or last object by ordering (falling back to the primary key when the QuerySet is unordered), or `None`. Since 6.1 they no longer add a primary-key ordering when you cleared the ordering with a bare `order_by()`.

|`earliest(field)` / `latest(field)`
|The object with the smallest or largest value of a field; raises `DoesNotExist` when there are no rows.

|`order_by(*fields)` / `reverse()`
|Ordering; a leading `-` is descending; `F("x").desc(nulls_last=True)` controls NULL placement.

|`distinct()`
|`SELECT DISTINCT`; needed when a join on a multi-valued relation repeats rows.

|`none()`
|An always-empty QuerySet that never queries; useful for permission filters.

|`in_bulk(id_list, field_name="pk")`
|A dict mapping the field value to the instance, in one query. 6.1 allows chaining it after `values()` / `values_list()`.
|===

.get(), DoesNotExist, MultipleObjectsReturned and friends (ex/e2_retrieve.py)

== Field lookups

A _lookup_ is the `__suffix` that says how to compare a field. `title="x"` is shorthand for `title__exact="x"`. The full form is `field__lookup=value`, optionally with
_transforms_ in between (`published__year__gte=1990` is the `year` transform followed by the `gte` lookup).

[cols="2,3",options="header"]
|===
|Lookup |Meaning

|`exact`, `iexact`
|Equality; `iexact` is case-insensitive. `exact=None` is `IS NULL`.

|`contains`, `icontains`
|Substring (`LIKE '%x%'`), case-sensitive or not. On SQLite `LIKE` is case-insensitive for ASCII text, so `contains` behaves like `icontains` there; PostgreSQL honours the difference.

|`startswith`, `istartswith`, `endswith`, `iendswith`
|Prefix and suffix matches.

|`in`
|Membership in a list, tuple or *another QuerySet* (which becomes a subquery).

|`gt`, `gte`, `lt`, `lte`
|Comparisons.

|`range`
|`BETWEEN low AND high` (inclusive); works for numbers, dates and datetimes.

|`isnull`
|`True` or `False` only; non-boolean right-hand values, which were never documented, stopped being accepted in Django 4.0.

|`regex`, `iregex`
|Regular-expression match, using the database's regex dialect.

|`date`, `year`, `iso_year`, `month`, `day`, `week`, `week_day`, `iso_week_day`, `quarter`, `time`, `hour`, `minute`, `second`
|Date and time component transforms that can be followed by another lookup (`published__year__lt=1965`). Datetime fields follow the current time zone when `USE_TZ` is true.
|===

.Common lookups, transforms and subqueries (ex/e3_lookups.py)
[source,python]
----
import datetime as dt
from django.db.models import F, Q
from catalog.models import Author, Book

def titles(qs):
    return sorted(b.title for b in qs)

print(titles(Book.objects.filter(title__exact="Solaris")))
print(titles(Book.objects.filter(title__iexact="solaris")))
print(titles(Book.objects.filter(title__contains="Earth")), titles(Book.objects.filter(title__icontains="the d")))
print(titles(Book.objects.filter(title__startswith="The "))[:5], titles(Book.objects.filter(title__endswith="Sower")))
wanted = list(Book.objects.filter(title__startswith="S").values_list("pk", flat=True))
print(titles(Book.objects.filter(pk__in=wanted)))
print(titles(Book.objects.filter(price__gte=11)), titles(Book.objects.filter(price__range=(9, 10))))
print(titles(Book.objects.filter(published__year=1969)), titles(Book.objects.filter(published__year__lt=1965)))
print(titles(Book.objects.filter(published__month=11)), titles(Book.objects.filter(published__gt=dt.date(1975, 1, 1))))
print(titles(Book.objects.filter(published__isnull=True)))
print(titles(Book.objects.filter(title__regex=r"^The (Left|Cyb)")))
print(titles(Book.objects.filter(published__year__gte=1990)))   # transform (year) then lookup (gte)
# a queryset as the right-hand side becomes a subquery
cheap_authors = Author.objects.filter(books__price__lt=9).values("pk")
print(titles(Book.objects.filter(author__in=cheap_authors)))
# lookups on annotations and in filters directly (Django 4.0+)
from django.db.models import Value
from django.db.models.lookups import GreaterThan
print(titles(Book.objects.filter(GreaterThan(F("pages"), Value(300)))))
print(Book.objects.filter(GreaterThan(F("pages"), 300)).query.where)

== Spanning relationships

Double underscores also walk relationships, forwards (`author__name`), backwards (`books__title`, using `related_name` or, by default, the model name in lowercase; set
`related_query_name` to change the query name independently) and through many-to-many tables (`genres__name`). Django adds the `JOIN`s itself. See
xref:web/django/relationships.adoc[Relationships] for how the relations are declared.

.Following relationships in filters (ex/e4_relations.py)
[source,python]
----
from django.db import connection
from django.test.utils import CaptureQueriesContext
from catalog.models import Author, Book, Genre, Review

def names(qs, attr="title"):
    return sorted(getattr(o, attr) for o in qs)

# forward: follow the ForeignKey with double underscores
print(names(Book.objects.filter(author__name__startswith="Stan")))
# backward: related_name="books" is also the default query name
print(names(Author.objects.filter(books__price__gt=12), "name"))
# many-to-many in both directions
print(names(Book.objects.filter(genres__name="Fantasy")), names(Genre.objects.filter(books__title="Kindred"), "name"))
# across two hops, and to a model without a reverse name (reviews -> reviewer)
print(names(Book.objects.filter(reviews__reviewer__username="ana")))
# isnull across a reverse relation = "has no rows"
print(names(Book.objects.filter(reviews__isnull=True)))
print(names(Author.objects.filter(books__isnull=True), "name"))

# multi-valued relations: one filter() call = one related row must satisfy ALL conditions
one_call = Book.objects.filter(reviews__rating=5, reviews__body="Dense but rewarding")
# chained filter() calls = conditions may be satisfied by DIFFERENT related rows
chained = Book.objects.filter(reviews__rating=5).filter(reviews__body="Dense but rewarding")
print("one call:", names(one_call), "| chained:", names(chained))
print(chained.query.__str__().count("JOIN"), "joins when chained;", one_call.query.__str__().count("JOIN"), "when in one call")

# exclude() on a multi-valued relation is a subquery, and does NOT behave like filter() negated
print(names(Book.objects.exclude(reviews__rating=5, reviews__body="Brilliant")))

# duplicates: a join on a multi-valued relation can repeat the parent row
print(Book.objects.filter(reviews__rating__gte=3).count(), Book.objects.filter(reviews__rating__gte=3).distinct().count())

# related managers are QuerySets scoped to one object
le_guin = Author.objects.get(name__startswith="Ursula")
print(le_guin.books.filter(price__lt=10).count(), le_guin.books.count())
solaris = Book.objects.get(title="Solaris")
print(solaris.reviews.all(), solaris.genres.all())
# traversing from an instance costs a query per access (see the optimisation page)
with CaptureQueriesContext(connection) as ctx:
    for book in Book.objects.all():
        book.author.name
print("queries for the loop:", len(ctx))

Three behaviours in this output decide whether a query is correct:

* *One `filter()` call versus a chain.* With a multi-valued relation (reverse foreign key, many-to-many), conditions in a *single* `filter()` call must be satisfied by the *same* related row, while
conditions in *chained* `filter()` calls may be satisfied by *different* related rows. Here no single review is both a 5 and "Dense but rewarding", but `The Dispossessed` has one review with
rating 5 and another with that text, so the chain matches it. The SQL differs accordingly (the chain adds a second `JOIN`).
* *`exclude()` does not mirror `filter()`.* On a multi-valued relation `exclude(reviews__rating=5, reviews__body="Brilliant")` removes books that have *a review matching both conditions*; Django builds it with a subquery, and the result
here removes only `The Dispossessed`, whereas `exclude(a).exclude(b)` would remove every book with a 5 or a "Brilliant" review.
* *Joins repeat rows.* Filtering on `reviews__rating__gte=3` joins `Book` to `Review`, so a book with two matching reviews appears twice (`4` rows versus `3` with `distinct()`). Use `distinct()`, or filter with a subquery (`pk__in=` or `Exists()`) when the duplicates matter.

The related manager (`author.books`, `book.reviews`, `book.genres`) is a manager scoped to one object: `le_guin.books.filter(price__lt=10)` is a normal QuerySet. Every
*attribute traversal* from an instance (`book.author`) is a separate query when the object was not loaded with the relation: the last loop above issues nine queries for eight books. That is the
N+1 problem; the cures (`select_related`, `prefetch_related` and the Django 6.1 fetch modes) are on xref:web/django/query-optimization-and-fetch-modes.adoc[Query Optimization & Fetch Modes].

== F expressions: referring to columns

An `F("field")` object refers to the value of a column *inside the database* instead of a Python value that was read earlier. It has three jobs: comparing two columns of one row, computing a new value from the current
one, and ordering or annotating by an expression. Because the arithmetic happens in SQL, an `F()` update is atomic with respect to other writers and avoids the lost-update race of "read, add one in Python, save".

.F expressions in filters, updates and annotations (ex/e5_fq.py)
[source,python]
----
from django.db import connection
from django.db.models import F, FloatField
from django.db.models.functions import Cast
from django.test.utils import CaptureQueriesContext
from catalog.models import Book

def titles(qs):
    return sorted(b.title for b in qs)

# F: compare two columns of the same row, inside the database
Book.objects.filter(title="Kindred").update(reserved=5)
Book.objects.filter(title="Solaris").update(reserved=1)
print(titles(Book.objects.filter(reserved__gte=F("stock"))))

# F in update(): one atomic UPDATE ... SET stock = stock - 1
with CaptureQueriesContext(connection) as ctx:

Points worth knowing:

* *After `save()` an F-assigned attribute holds the new value only on some databases.* Since Django 6.0, fields assigned expressions (and `GeneratedField`s) are refreshed from the database after `save()` on backends with a `RETURNING` clause (SQLite, PostgreSQL, Oracle) and marked deferred on MySQL/MariaDB; before 6.0 the attribute stayed an `F` object until `refresh_from_db()`. Calling `refresh_from_db(fields=[...])` works everywhere.
* *Do not save an instance again while it still holds an F-expression* (MySQL/MariaDB, or any backend before 6.0, until you call `refresh_from_db()`): the expression would be applied a second time.
* *Division and SQLite.* The per-page price uses `Cast("price", FloatField())`. Dividing the raw decimal column by an integer column is an integer division on SQLite when the stored price happens to be a whole number (a price of 5.00 divided by 80 pages gave 0 in the scratch project), so cast one operand explicitly; other databases return decimals.
* *`F()` can be negated for booleans* (`~F("is_published")`, Django 4.2), used with transforms and in `OuterRef()` since 3.2, and `F()` of a character field can be sliced since 5.1.
* *NULLs.* `F("a") + 1` is NULL when `a` is NULL; wrap nullable columns in `Coalesce(F("a"), 0)`.

== Q objects: AND, OR, NOT and XOR

Keyword arguments to `filter()` are always `AND`ed. A `Q()` object wraps the same keyword conditions so they can be combined with `&` (and), `|` (or), `~` (not) and, since Django 4.1, `^` (exclusive or: true when an *odd*
number of the operands is true). `Q` objects and keyword arguments can be mixed, but the `Q` objects must come first.

.Combining conditions with Q (ex/e6_q.py)
[source,python]
----
import operator
from functools import reduce
from django.db.models import Q
from catalog.models import Book

def titles(qs):
    return sorted(b.title for b in qs)

scifi_or_cheap = Q(genres__name="Fantasy") | Q(price__lt=9)
print(titles(Book.objects.filter(scifi_or_cheap).distinct()))
print(titles(Book.objects.filter(Q(is_published=True) & ~Q(stock=0))))
print(titles(Book.objects.filter(~Q(author__country="US"))))

# XOR (Django 4.1+): true when an odd number of the conditions are true
xor = Book.objects.filter(Q(pages__gt=300) ^ Q(price__gt=10))
print(titles(xor))
print(xor.query.where)
print(str(Book.objects.filter(Q(pages__gt=300) ^ Q(price__gt=10)).query).split("WHERE")[1][:210])

# Q objects first, keyword arguments afterwards
print(titles(Book.objects.filter(Q(title__startswith="The") | Q(title__startswith="A"), is_published=True)))

# building a filter from user input without a chain of ifs
def search(*, text="", author_country="", max_price=None, in_stock=False):
    q = Q()
    if text:
        q &= Q(title__icontains=text) | Q(author__name__icontains=text)
    if author_country:
        q &= Q(author__country=author_country)
    if max_price is not None:
        q &= Q(price__lte=max_price)
    if in_stock:
        q &= Q(stock__gt=0)
    return Book.objects.filter(q)

print(titles(search(text="le guin", in_stock=True)), titles(search(author_country="PL", max_price=11)))
print(search().count())                       # an empty Q() matches everything

# combining a list of terms
terms = ["earth", "sower", "kin"]
q = reduce(operator.or_, (Q(title__icontains=t) for t in terms))
print(titles(Book.objects.filter(q)))
# QuerySets combine with | & ^ as well
print(titles(Book.objects.filter(stock=0) | Book.objects.filter(pages__lt=100)))

* *XOR support.* MariaDB and MySQL have a native `XOR`; on PostgreSQL and SQLite Django rewrites it, as the printed SQL shows (for more than two operands the official page defines the result as "an odd number of operands match" and documents the conversion).

== get_or_create and update_or_create

`get_or_create(defaults=None, **kwargs)` looks the row up with `get(**kwargs)`; if it does not exist it creates it from `kwargs` plus `defaults` and returns `(object, created)`. `update_or_create()`
does the same but, when the row exists, applies `defaults` as updates (via `save()`), and returns `(object, created)`. Both are *not* single SQL statements: Django wraps them in a transaction (a savepoint when already inside one), and relies on
a unique constraint to resolve races.

.get_or_create and update_or_create (ex/e7_getorcreate.py)
[source,python]
----
from django.db import IntegrityError, connection
from django.test.utils import CaptureQueriesContext
from catalog.models import Author, Genre, Book

# get_or_create: lookups, plus defaults used only when creating
genre, created = Genre.objects.get_or_create(name="Poetry")
print(genre, created)
genre, created = Genre.objects.get_or_create(name="Poetry")
print(genre, created)

author, created = Author.objects.get_or_create(
    name="Italo Calvino", defaults={"country": "IT"},
)
print(author.country, created)
# existing row: defaults are ignored
author, created = Author.objects.get_or_create(name="Italo Calvino", defaults={"country": "XX"})
print(author.country, created)

# update_or_create: update the row if it exists, otherwise create it
book, created = Book.objects.update_or_create(
    isbn="9780156453806",
    defaults={"title": "Invisible Cities", "author": author, "price": "11.95", "pages": 165},
)
print(book, created)
book, created = Book.objects.update_or_create(isbn="9780156453806", defaults={"price": "12.95"})
print(book.price, created)

# create_defaults (Django 5.0): different values for the create branch than for the update branch
book, created = Book.objects.update_or_create(
    isbn="9780156453813",
    defaults={"stock": 5},                                                    # used on update
    create_defaults={"title": "If on a winter's night", "author": author,     # used on create
                     "price": "10.00", "pages": 260, "stock": 0},
)
print(book.title, book.stock, created)
book, created = Book.objects.update_or_create(
    isbn="9780156453813", defaults={"stock": 5},
    create_defaults={"title": "ignored", "author": author, "price": "1", "pages": 1},
)
print(book.title, book.stock, created)

# the lookup must be unique: get_or_create relies on get() and on a unique constraint for races
Author.objects.create(name="Twin"); Author.objects.create(name="Twin")
try:
    Author.objects.get_or_create(name="Twin")
except Author.MultipleObjectsReturned as exc:
    print("MultipleObjectsReturned:", exc)

    Genre.objects.get_or_create(name="Drama")
for q in ctx:
    print(q["sql"][:110])

* *`defaults` is applied only on creation* for `get_or_create`, and the keyword arguments are the lookup. Putting a non-lookup value (such as `price`) in the keyword arguments makes the lookup too narrow: the row exists with a different price and a duplicate is created or, with a unique column, an `IntegrityError` follows.
* *Concurrency needs a database-enforced unique constraint* on the lookup fields. Without it two concurrent calls can both create a row, and later calls fail with `MultipleObjectsReturned`, as the "Twin" authors show. With a unique constraint, the loser of the race gets an `IntegrityError` that Django catches and answers with a second `get()`.
* *`create_defaults` (Django 5.0)* gives `update_or_create()` (and `aupdate_or_create()`) different values for the insert than for the update, so a "created" row can be built with fields that an "update" must not overwrite (the `title` and `price` above are only used on creation).
* *Callable defaults* in `defaults` are called only when needed. `update_or_create()` uses `save()`, so signals and `auto_now` fields behave normally; on update it runs `select_for_update()` inside the transaction on databases that support it.
* *Do not use them in a loop for large imports.* That is one to three queries per row; use `bulk_create(update_conflicts=True)` below.
* *In views* build the lookup from validated input only; a `get_or_create` on `request.POST` data is a write triggered by user input and needs the same CSRF and validation care as any form handler.

== Creating, updating and deleting in bulk

[cols="2,3",options="header"]
|===
|Operation |What it does and what it skips

|`create(**kwargs)` / `save()`
|One `INSERT` or `UPDATE`; runs `save()` overrides, `pre_save`/`post_save` signals and field `auto_now` handling.

|`bulk_create(objs, batch_size=None, ignore_conflicts=False, update_conflicts=False, update_fields=None, unique_fields=None)`
|One `INSERT` (or several, per `batch_size`). Does not call `save()` or send signals, does not work with multi-table-inheritance children or many-to-many data, and casts `objs` to a list.

|`bulk_update(objs, fields, batch_size=None)`
|One `UPDATE ... CASE WHEN` per batch; returns the number of rows matched (Django 4.0). No `save()` and no signals; cannot update the primary key.

|`update(**kwargs)`
|A single `UPDATE ... WHERE` on the filtered rows; returns the number of rows matched. No `save()`, no signals, and `auto_now` fields are *not* refreshed unless you set them.

|`delete()`
|Deletes the matching rows (and, per `on_delete`, their dependants); returns the total and a per-model count dictionary. Cannot be called on a sliced QuerySet.
|===

.bulk_create, upserts, bulk_update, update and delete (ex/e8_bulk.py)

    created = Book.objects.bulk_create(
        [
            Book(title="His Master's Voice", isbn="9780156401739", author=author, price="10.00", pages=199),
            Book(title="Fiasco", isbn="9780156305471", author=author, price="10.50", pages=320),

    Book(title="Memoirs Found in a Bathtub", isbn="9780156586221", author=author, price="11.00", pages=216, stock=1),  # new row

The upsert is the headline: `bulk_create(..., update_conflicts=True, unique_fields=[...], update_fields=[...])` compiles to `INSERT ... ON CONFLICT (isbn) DO UPDATE SET ...`, so a nightly price import is one statement for any number of rows, instead of a
`get_or_create` per row. The facts to keep in mind:

* *Added in Django 4.1* (confirmed in the 4.1 release notes: "QuerySet.bulk_create() now supports updating fields when a row insertion fails uniqueness constraints"), supported on MariaDB, MySQL, PostgreSQL and SQLite 3.24+; the 6.1 baseline is SQLite 3.37, so it is available everywhere Django 6.1 runs, except Oracle.
* *`unique_fields` is required on PostgreSQL and SQLite* (the conflict target) and ignored on MySQL/MariaDB, which choose the target themselves; `update_fields` is the list of columns to overwrite. Give both on every backend so the code is portable.
* *Primary keys.* With `update_conflicts=True` Django 5.0 and later sets the primary key on every instance when the database supports it (the `[True, True]` line); `ignore_conflicts=True` never sets primary keys (the duplicate instance shows `None`). Before 5.0 the keys were missing for upserts, and on SQLite `bulk_create` only returned primary keys from 4.0 (SQLite 3.35+).
* *`ignore_conflicts` swallows more than duplicates* on MySQL and MariaDB (invalid values, non-nullable violations become warnings); the official page carries that warning.
* *Signals and validation are skipped.* No `save()`, no `pre_save`/`post_save`, no model `full_clean()`; validate before inserting.
* *Batching.* SQLite and Oracle limit the number of query parameters, so Django splits large inserts; set `batch_size` explicitly for very large lists (and to bound memory in `bulk_update`, which builds all `WHEN` clauses before running anything).
* *`update()` returns rows matched* (which can be more than the rows whose value actually changed). Use the return value to detect "nothing to update" for compare-and-set logic: `filter(pk=..., stock__gt=F("reserved")).update(reserved=F("reserved") + 1) == 1`, shown in `reserve_copy()` below.
* *`save(update_fields=[...])`* writes only the named columns (the last line prints the unchanged `pages`), which also narrows the window for lost updates between concurrent edits of different fields.
* *`delete()`* collects related objects in Python to honour `on_delete` and signals, unless the relation and the database allow a fast path; Django 6.1's `DB_CASCADE`, `DB_SET_NULL` and `DB_SET_DEFAULT` options move that work into the database (see xref:web/django/relationships.adoc[Relationships]). `PROTECT` raises `ProtectedError`, as the author with books shows.

== Shaping results: values, values_list, alias, exists and contains

`values()` returns dictionaries and `values_list()` tuples (or bare values with `flat=True`, or named tuples with `named=True`) containing only the requested columns or expressions: no model instances, no
`save()`, no methods, but also less to fetch and construct. `alias()` (Django 3.2) computes an expression for use in filters, ordering and later annotations *without selecting it*. `exists()` and `contains()` answer yes/no questions
cheaply.

* *`alias()` versus `annotate()`.* Both add the expression to the query; only `annotate()` adds it to the `SELECT` list (the `[] ['per_page']` line). Use `alias()` for filter-only or sort-only helper values and annotate only what the template or serializer reads.
* *Ordering and `values()`.* Since 5.2 the `SELECT` columns of `values()` / `values_list()` follow the order you list the expressions (previously a set of unintuitive rules applied), which matters when combining queries with `union()`.
* *`values()` before `annotate()` sets the `GROUP BY`* (`values("author__name").annotate(n=Count("pk"))` is "books per author name"); the other order annotates every row and then restricts the columns. The details are on xref:web/django/aggregation-expressions-and-functions.adoc[Aggregation, Expressions & Functions].
* *`values_list(flat=True)` needs one explicit field.* Calling it with `flat=True` and no field name is deprecated in 6.1; pass `"pk"` instead.
* *`dates()` and `datetimes()`* return the distinct dates or datetimes truncated to `year`, `month`, `week` or `day` (datetimes also `hour`, `minute`, `second`); there is no `decade` kind.
* *`only()` / `defer()`* select fewer columns but still return instances; touching a deferred field costs one query per instance (see the next page in the section on optimisation).

== Custom lookups and transforms

When no built-in lookup says what you mean, register your own. A `Lookup` subclass (`lookup_name`, `as_sql()`) adds a comparison such as `__ne`; a `Transform` subclass (`function`, an `output_field`) adds a step that can be
chained with further lookups, such as `pages__abs__lt`. Register them on a field class with `Field.register_lookup()` (a decorator form exists), import the module from `AppConfig.ready()` so registration happens at startup, and remember that the
lookup's `as_sql()` returns the SQL fragment and its parameters, never user data interpolated into the string.

.catalog/lookups.py
[source,python]
----
from django.db.models import CharField, Field, IntegerField, Lookup, Transform
from django.db.models.functions import Lower


@Field.register_lookup
class NotEqual(Lookup):
    """title__ne="x"  ->  title <> 'x'"""

    lookup_name = "ne"

    def as_sql(self, compiler, connection):
        lhs, lhs_params = self.process_lhs(compiler, connection)
        rhs, rhs_params = self.process_rhs(compiler, connection)
        return f"{lhs} <> {rhs}", (*lhs_params, *rhs_params)


@IntegerField.register_lookup
class AbsoluteValue(Transform):
    """pages__abs  ->  ABS(pages)"""

    lookup_name = "abs"
    function = "ABS"

    @property
    def output_field(self):
        return IntegerField()


# Lower is a Transform that Django ships but does not register on any field
CharField.register_lookup(Lower)

* *Register early.* A lookup is only known after its module is imported; importing it in `ready()` guarantees it exists before any query is built. Import errors there fail at startup, which is the point.
* *`Lookup` versus `Transform`.* A `Transform` takes one expression and returns a new one (`ABS(pages)`), so it can be followed by a lookup or another transform; a `Lookup` takes a left and right side and returns a boolean condition, so it ends the chain. * *`prepare_rhs`.* By default the right-hand value is converted with the left field's `get_prep_value()`: on a `CharField` the integer `7` would become the string `'7'` and SQLite would compare a number with text and match every row. * *`bilateral = True`* on a `Transform` applies it to both sides (a case-insensitive comparison via `UPPER` on both the column and the value).

== The Bookshelf search: queries, view, tests and curl

The pieces combine into a small search endpoint. The function builds one composable QuerySet from optional filters, `select_related("author")` loads the author in the same query, the view paginates
and returns JSON, and the tests pin both behaviour and query counts with `assertNumQueries`.

.catalog/queries.py
[source,python]
----
from decimal import Decimal

from django.db.models import F, Q

from .models import Book


def search_books(*, text: str = "", country: str = "", max_price: Decimal | None = None, in_stock: bool = False):
    """Build one composable QuerySet from optional filters; nothing runs until it is evaluated."""
    q = Q(is_published=True)
    if text:
        q &= Q(title__icontains=text) | Q(author__name__icontains=text)
    if country:
        q &= Q(author__country=country)
    if max_price is not None:
        q &= Q(price__lte=max_price)
    if in_stock:
        q &= Q(stock__gt=F("reserved"))
    return Book.objects.filter(q).select_related("author")


def reserve_copy(book_id: int) -> bool:
    """Atomic compare-and-set: succeeds only while an unreserved copy is left."""
    updated = Book.objects.filter(pk=book_id, stock__gt=F("reserved")).update(reserved=F("reserved") + 1)
    return updated == 1


def import_prices(rows: list[dict]) -> None:
    """Upsert (INSERT ... ON CONFLICT DO UPDATE) keyed on the unique ISBN."""
    Book.objects.bulk_create(
        [Book(**row) for row in rows],
        update_conflicts=True,
        unique_fields=["isbn"],
        update_fields=["price", "stock"],
    )
----

@require_GET
def book_search(request):

    except InvalidOperation:
        return JsonResponse({"error": "max_price must be a number"}, status=400)

        "results": [{"title": b.title, "author": b.author.name, "price": str(b.price)} for b in page],
    })

== Sync and async behaviour

Since Django 4.1 every QuerySet method that hits the database has an `a`-prefixed coroutine (`aget`, `acreate`, `acount`, `aexists`, `afirst`, `aupdate`, `adelete`, `abulk_create`, `aget_or_create`, `aiterator`, ...) and a QuerySet
can be consumed with `async for`. Django 4.2 added `Model.asave()`, `adelete()` and `arefresh_from_db()` and the async related-manager methods (`aadd`, `aclear`, `aremove`, `aset`); 5.0 added `aprefetch_related_objects()`, prefetching with `aiterator()`
and `create_defaults` for `aupdate_or_create()`. Methods that only build a QuerySet (`filter`, `exclude`, `order_by`, ...) are plain synchronous calls in both worlds.

.Async QuerySet usage (ex/e12_async.py)
[source,python]
----
import asyncio
from django.core.exceptions import SynchronousOnlyOperation
from catalog.models import Author, Book

async def main():
    book = await Book.objects.aget(isbn="9780156027601")                 # get()
    print(book.title, await Book.objects.filter(stock__gt=0).acount(), await Book.objects.filter(stock=0).aexists())
    print((await Book.objects.order_by("title").afirst()).title)
    print([b.title async for b in Book.objects.filter(pages__gt=340).order_by("title")])   # async for
    print([b.title async for b in Book.objects.order_by("title").aiterator(chunk_size=2)][:2])
    author, created = await Author.objects.aget_or_create(name="Async Author", defaults={"country": "ES"})
    print(created, await Author.objects.filter(name="Async Author").aupdate(country="PT"))
    print(await Author.objects.filter(name="Async Author").adelete())
    # QuerySet methods that need the database are blocked from async code unless awaited
    try:
        list(Book.objects.all())
    except SynchronousOnlyOperation as exc:
        print("SynchronousOnlyOperation:", exc)
    # related objects: await the relation, or fetch it in the query (select_related)
    book = await Book.objects.select_related("author").aget(isbn="9780156027601")
    print(book.author.name)
    rev = [r async for r in book.reviews.all()]
    print(len(rev))

asyncio.run(main())

* *Evaluating by accident.* `if qs:`, `len(qs)` and `list(qs)` load everything; use `exists()`, `count()` and slicing.
* *Querying in a loop.* `book.author.name` inside `for book in books` (nine queries for eight books above); load relations in the query.
* *Treating `filter().filter()` like one `filter()`* on multi-valued relations (and `exclude()` like a negated `filter()`).

* *`get()` for non-unique data*, and unhandled `DoesNotExist` in views (use `get_object_or_404`).
* *Read-modify-write without `F()`* (lost updates) or without a transaction and `select_for_update()` when the logic cannot be expressed as one `UPDATE`.
* *Assuming bulk operations call `save()`.* `bulk_create`, `bulk_update`, `update` and `delete` on a QuerySet skip custom `save()`, signals and `auto_now`.
* *Large `IN` lists.* A list of tens of thousands of ids can exceed SQLite's variable limit and slow other databases; use a subquery (`pk__in=other_queryset`) or a join.
* *NULL ordering and comparisons* differ by database; state `nulls_last` / `nulls_first` and use `isnull` explicitly.
* *Integer division and type affinity on SQLite* (see the F-expression notes): cast operands and test on the production database, because SQLite is more permissive than PostgreSQL.
* *Raw user-controlled lookups* (`filter(**request.GET.dict())`, `order_by(request.GET["sort"])`): whitelist field names. Raw SQL belongs with parameters (see xref:web/django/transactions-raw-sql-and-multiple-databases.adoc[Transactions, Raw SQL & Multiple Databases]).
* *Shared module-level QuerySets* keep their result cache for the process lifetime.
* *`select_related()` with no arguments is deprecated in 6.1;* name the relations.
* *Testing query counts.* Pin hot paths with `assertNumQueries` and use `setUpTestData` for read-only fixtures; see xref:web/django/testing.adoc[Testing].

== Where the books are outdated

Books written for Django 1.11 to 3.x describe the ORM correctly in outline (QuerySets, lookups, `F`/`Q`, `get_or_create`, `values`), but several parts have moved on:

* *Missing features.* They predate `QuerySet.alias()` (3.2), `QuerySet.contains()` (4.0), `Q` XOR (4.1), `bulk_create` upserts (4.1), `create_defaults` (5.0), per-field `register_lookup` (4.2), the async ORM (4.1/4.2), `QuerySet.totally_ordered` and fetch modes (6.1); pre-4.1 code typically reaches for raw SQL, `extra()` or a `get_or_create` loop where these now exist. The official documentation calls `extra()` a last resort that is expected to be deprecated.
* *Boolean checks.* Old advice to write `if qs.count() > 0` or `if len(qs)` is superseded by `exists()` (and `contains()` for a given instance).
* *`NullBooleanField`* was removed in 4.0 (use `BooleanField(null=True)`), and non-boolean values for `isnull` are no longer accepted (4.0); `django.utils.six` and Python 2 idioms (`iteritems`, `unicode`) are gone.
* *`bulk_update()`* returns the number of updated rows since 4.0; `bulk_create()` sets primary keys on SQLite since 4.0 and on upserts since 5.0.
* *Defaults.* Primary keys are `BigAutoField` by default since 6.0, so the ids printed in older listings (`AutoField`) differ in the migrations they generate.
* *`assertQuerysetEqual`* is `assertQuerySetEqual` (4.2; old name removed in 5.1) and no longer calls `repr()` on strings.
* *Shell and Python.* Interactive examples that import models by hand predate the shell auto-imports of 5.2; code based on `pytz` or timezone-naive datetimes predates `zoneinfo` (4.0) and the `USE_TZ = True` default (5.0).

== What changed recently

[cols="1,3",options="header"]
|===
|Version |Query-related change

|6.1
|`QuerySet.fetch_mode()` and fetch modes (`FETCH_ONE`, `FETCH_PEERS`, `FETCH_RAISE`); `totally_ordered`; `in_bulk()` after `values()`/`values_list()`; `first()`/`last()` stop forcing a primary-key ordering after a bare `order_by()`; default `Meta.ordering` applied to combined QuerySets; `JSONNull`; `UUID4`/`UUID7` functions; `BitAnd`/`BitOr`/`BitXor` aggregates; deprecations of `select_related()` without arguments and `values_list(flat=True)` without a field. SQLite 3.37 and PostgreSQL 15 are the minimums.

|6.0
|`StringAgg` and `AnyValue` aggregates, `order_by` for aggregates; expression-assigned fields and `GeneratedField`s refreshed after `save()` on SQLite, PostgreSQL and Oracle; `Model.NotUpdated`; `AsyncPaginator`.

|5.2 LTS
|Composite primary keys (see xref:web/django/constraints-indexes-and-composite-keys.adoc[Constraints, Indexes & Composite Keys]); `values()`/`values_list()` columns follow the requested order; `JSONArray`; `explain()` options; shell auto-imports.

|5.1
|`F()` and `OuterRef()` slicing of character fields; `Model.refresh_from_db(from_queryset=...)`; `explain(generic_plan=True)`.

|5.0
|`create_defaults` for `update_or_create()`; `bulk_create(update_conflicts=True)` sets primary keys; `aprefetch_related_objects()`; `aiterator()` honours `prefetch_related()`; `aget_object_or_404()`.

|4.2
|Per-field `register_lookup()`; `~F()` for boolean expressions; `Model.asave()`/`adelete()`/`arefresh_from_db()` and async related managers; `prefetch_related()` with sliced `Prefetch` querysets.

|4.1
|Async ORM (`aget`, `acount`, `async for`); `Q` and QuerySet XOR; `bulk_create(update_conflicts=True)`; `iterator()` with `prefetch_related()` when `chunk_size` is given.

|4.0
|`QuerySet.contains()`; non-boolean values for `isnull` rejected; lookup expressions usable in filters and annotations; `bulk_update()` returns a count; aggregates accept `default`.

|3.2
|`QuerySet.alias()`; transforms in `F()`, `OuterRef()` and aggregates; `When(condition=...)` with lookups.
|===
