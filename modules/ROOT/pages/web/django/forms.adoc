[#cycle]
== Where a form sits in the request cycle

A form is not part of the framework's request pipeline: nothing in the URL resolver or the middleware knows about
`Form`. Forms are ordinary Python objects that a view creates, feeds with the request's data and hands to a template. What
the framework does around them is the part that matters: the CSRF middleware inspects the submission before your view
starts, the request body is parsed lazily when first read, and the CSRF cookie is attached to the response when a template
asked for the token.

[mermaid]
....
sequenceDiagram
  participant B as Browser
  participant M as CsrfViewMiddleware
  participant V as View
  participant F as Form
  participant T as Template
  B->>M: POST /catalog/suggest/ with csrfmiddlewaretoken
  M->>M: compare cookie secret and posted token (reads request.POST)
  M->>V: request (view runs only if the token is valid)
  V->>F: BookSuggestionForm(request.POST)
  V->>F: is_valid() runs full_clean()
  alt valid
    V-->>B: 302 redirect to the success page
  else invalid
    V->>T: render with the bound form
    T-->>B: 200 with errors and submitted values
  end
....

In order, for one submission:

. The server (WSGI or ASGI) builds the `HttpRequest`. The body is not parsed yet.
. Middleware runs top-down. `CsrfViewMiddleware.process_view()` is the first code that reads `request.POST` for a POST
  without the `X-CSRFToken` header: it needs the `csrfmiddlewaretoken` field, so the whole form-encoded or multipart body
  (files included) is parsed here, before the view and before any form exists. A failed check ends the request with a 403
  and your view never runs.
. The URL resolver picks the view.
. The view decides bound or unbound from the HTTP method, builds the form, calls `is_valid()` (which triggers
  `full_clean()` once and caches the result) and chooses the response.
. If the template calls `{% csrf_token %}`, `get_token()` marks the request so that `process_response()` adds the
  `csrftoken` cookie and a `Vary: Cookie` header. That is also why a page containing a form is not safely cacheable by a
  shared cache.
. The browser follows the redirect with a fresh GET (or re-renders the page, for an invalid form).

Source: https://docs.djangoproject.com/en/6.1/topics/forms/#working-with-forms[Django: Working with forms] and https://docs.djangoproject.com/en/6.1/ref/csrf/#how-it-works[CSRF: how it works]

The middleware chain is explained in xref:web/django/middleware.adoc[Middleware] and the whole pipeline in
xref:web/django/request-response-cycle.adoc[The Request/Response Cycle].

[#html-forms]
== What the browser sends: HTML forms, GET and POST

An HTML `<form>` has an `action` (the URL, by default the current page), a `method` and fields with a `name`. The browser
sends the names and values of the controls it submits, encoded as one of three content types:

* `application/x-www-form-urlencoded` (the default) for text fields; Django exposes it as `request.POST` for POST requests
  and as `request.GET` for the query string.
* `multipart/form-data`, required when the form contains a file input (`enctype="multipart/form-data"`); text parts
  appear in `request.POST`, file parts in `request.FILES`.
* `text/plain`, which is for debugging and which Django does not parse.

A control that is not submitted is simply absent: an unchecked checkbox, an unselected radio group and a disabled control
send nothing. That one rule explains several details below (`BooleanField(required=False)`, `disabled=True`,
`value_omitted_from_data()`).

The choice of method is a design decision, not a style one. GET is for requests that can be repeated, bookmarked, cached
and prefetched without harm: a search, a filter, a pagination link. POST is for requests that change state on the server:
suggest a book, upload a file, log in. Django enforces that distinction in two places: the CSRF protection applies to every
method that is not GET, HEAD, OPTIONS or TRACE, and the `request.POST` dictionary is empty for a GET. Do not change state in
a GET handler; the books' habit of a "delete" or "add to basket" link that works through GET is wrong because a prefetching
browser, a crawler or an image tag on another site can trigger it.

Only form-encoded and multipart bodies fill `request.POST`. A JSON body, as sent by `fetch()` with
`Content-Type: application/json`, leaves `request.POST` empty and has to be parsed by hand (or by Django REST framework or
Django Ninja); a `Form` bound to it would report every field as missing.

Source: https://docs.djangoproject.com/en/6.1/topics/forms/#html-forms[Django: HTML forms] and https://docs.djangoproject.com/en/6.1/ref/request-response/#django.http.HttpRequest.POST[HttpRequest.POST]

[#form-class]
== The Form class

A form is a class whose class attributes that are `Field` instances become its fields, in declaration order. The metaclass
collects them into `base_fields`; every form _instance_ gets its own deep copy in `self.fields`, which is why changing
`form.fields["x"]` in a view or in `+__init__+` does not leak into the next request. The _Bookshelf_ suggestion form:

.A form with several field types (catalog/forms.py)
[source,python]
----
# catalog/forms.py
from django import forms
from django.db.models import TextChoices


class Genre(TextChoices):
    FICTION = "fiction", "Fiction"
    SCIENCE = "science", "Science"
    HISTORY = "history", "History"


class BookSuggestionForm(forms.Form):
    title = forms.CharField(max_length=200)
    author = forms.CharField(max_length=120)
    genre = forms.ChoiceField(choices=Genre, initial=Genre.FICTION)
    pages = forms.IntegerField(min_value=1, max_value=5000, required=False)
    published = forms.DateField(
        required=False,
        widget=forms.DateInput(attrs={"type": "date"}),
        help_text="Leave empty if unknown.",
    )
    website = forms.URLField(required=False)
    notes = forms.CharField(
        required=False,
        widget=forms.Textarea(attrs={"rows": 4}),
        max_length=1000,
    )
    notify_me = forms.BooleanField(required=False, label="Tell me when it is added")
----

Source: https://docs.djangoproject.com/en/6.1/ref/forms/api/[Django: The Forms API] and https://docs.djangoproject.com/en/6.1/ref/forms/fields/[Form fields]

Things the class gives you, all documented on the API page:

* *Constructor arguments.* `Form(data=None, files=None, auto_id="id_%s", prefix=None, initial=None, error_class=ErrorList,
  label_suffix=None, empty_permitted=False, field_order=None, use_required_attribute=None, renderer=None, bound_field_class=None)`
  (the last one since 5.2). Everything after `files` is conventionally passed by keyword.
* *Class attributes.* `field_order` (a list of names that moves those fields first), `use_required_attribute`,
  `default_renderer`, `template_name` and the `template_name_div`/`_p`/`_ul`/`_table`/`_label` family, `error_css_class`,
  `required_css_class`, `label_suffix`, and since 5.2 `bound_field_class`. The rendering attributes belong to
  xref:web/django/form-rendering-and-widgets.adoc[Form Rendering & Widgets].
* *Per-instance results.* `errors`, `cleaned_data` (only after validation), `changed_data`, `fields`, `initial`, `data`,
  `files`, `prefix`, `is_bound`.
* *Methods.* `is_valid()`, `full_clean()`, `clean()` and `clean_<fieldname>()` hooks, `add_error()`, `non_field_errors()`,
  `has_changed()`, `is_multipart()`, `order_fields()`, `visible_fields()`, `hidden_fields()`, `get_initial_for_field()`,
  iteration (`for field in form`) and indexing (`form["title"]`), both of which yield `BoundField` objects.

Validation (`clean_<field>()`, `clean()`, `add_error()`, validators) is the subject of
xref:web/django/form-validation-and-validators.adoc[Form Validation & Validators]; binding a form to a model is
xref:web/django/model-forms-and-formsets.adoc[Model Forms & Formsets].

A form does not have to match a model, a table or an HTTP request: it is a validation and rendering object. The
`BookSuggestionForm` has no model behind it, which is the right shape for input that is processed (a suggestion queued for
a librarian) rather than stored one to one.

[#bound]
== Bound and unbound forms

A form is _bound_ when it was constructed with data, _unbound_ otherwise. The distinction decides everything about how the
form behaves, and it is a plain test in the source: `is_bound = data is not None or files is not None`.

.Unbound, empty-bound, valid and invalid forms (run with manage.py shell)
[source,python]
----
from catalog.forms import BookSuggestionForm

unbound = BookSuggestionForm()
print(unbound.is_bound, unbound.is_valid(), unbound.errors)
# False False

empty = BookSuggestionForm({})          # an empty dict is still data
print(empty.is_bound, empty.is_valid())
# True False
print(empty.errors.as_json())
# {"title": [{"message": "This field is required.", "code": "required"}], "author": [...], "genre": [...]}

data = {"title": "Dune", "author": "Frank Herbert", "genre": "fiction", "pages": "412",
        "published": "1965-08-01", "notify_me": "on"}
form = BookSuggestionForm(data)
print(form.is_valid())
# True
print(form.cleaned_data)
# {'title': 'Dune', 'author': 'Frank Herbert', 'genre': 'fiction', 'pages': 412,
#  'published': datetime.date(1965, 8, 1), 'website': '', 'notes': '', 'notify_me': True}
print(form.changed_data)
# ['title', 'author', 'pages', 'published', 'notify_me']

bad = BookSuggestionForm({"title": "Dune", "author": "F", "genre": "poetry", "pages": "0", "website": "x"})
print(bad.is_valid())
# False
for name, errs in bad.errors.items():
    print(name, [e for e in errs])
# genre ['Select a valid choice. poetry is not one of the available choices.']
# pages ['Ensure this value is greater than or equal to 1.']
# website ['Enter a valid URL.']
print(bad.cleaned_data)
# {'title': 'Dune', 'author': 'F', 'published': None, 'notes': '', 'notify_me': False}
----

Source: https://docs.djangoproject.com/en/6.1/ref/forms/api/#bound-and-unbound-forms[Django: Bound and unbound forms] and https://docs.djangoproject.com/en/6.1/ref/forms/api/#using-forms-to-validate-data[Using forms to validate data]

What the run shows, and what to remember:

* *An unbound form is never valid and has no errors.* `is_valid()` is `is_bound and not errors`. Rendering an unbound form
  shows initial values and no error messages, which is what you want for the first GET.
* *An empty dict is bound.* `BookSuggestionForm({})` reports three "required" errors. The common mistake is to write
  `if request.POST:` to detect a submission: an empty POST (a form whose controls were all unchecked checkboxes) is falsy
  and would be treated as a GET. Test `request.method == "POST"` instead.
* *`cleaned_data` holds Python values, not strings.* `pages` is an `int`, `published` a `date`, `notify_me` a `bool`. This
  conversion is the reason to validate through a form rather than read `request.POST` yourself.
* *After a failed `is_valid()`, `cleaned_data` contains only the fields that passed.* Never read a key that may be
  missing; use it only after `is_valid()` returned `True` (or in `clean()` with `.get()`).
* *Initial values are for display only.* `genre` has `initial=Genre.FICTION` and is absent from `changed_data` when the
  submission equals it, but `initial` is not a fallback: submit `genre=""` and the field is "required", not "fiction".
  Initial data can also come from the constructor (`initial={"genre": "science"}`, which wins over the field's `initial`);
  callables are evaluated each time an unbound form is displayed.
* *`changed_data` and `has_changed()`* compare submitted data with the initial values. The model formset machinery uses
  them to skip untouched extra forms; `empty_permitted=True` lets a form whose data did not change validate as empty.
* *Every field is validated every time.* The validation cycle runs once, on the first access to `errors`, `cleaned_data` or
  `is_valid()`, and the result is cached on the instance; mutating `form.data` afterwards has no effect.

Two constructor arguments change how the same form object is used in one page. `prefix="shelf"` renames every control to
`shelf-name`, `shelf-capacity`, and so makes it possible to put two forms of the same class in one `<form>` tag or page;
the prefix must be passed when reading the data back. `auto_id` controls the `id` attributes (`"id_%s"` by default, `False`
to omit them), and the label suffix and ordering options (`label_suffix`, `field_order`, `order_fields()`) work as their
names say.

[#fields]
== Fields: validation and conversion

A `Field` converts and validates one submitted value. Its `clean(value)` runs `to_python()` (convert), `validate()` (field
rules, such as "required") and `run_validators()` (the field's own and any you pass in `validators`), and raises
`ValidationError` or returns the cleaned value. You can call it directly, which is the quickest way to learn what a field
does: `forms.EmailField().clean("not an address")` raises `ValidationError: ['Enter a valid email address.']`.

[#field-options]
=== The core arguments

Every field class accepts these arguments:

[cols="2,5",options="header"]
|===
| Argument | Effect

| `required`
| `True` by default: an empty value (`None` or `""`) fails with the `required` message. Required fields render the HTML `required` attribute unless the form sets `use_required_attribute = False`. `0`, `False` and `"0"` are not empty.
| `label`, `label_suffix`
| The text shown next to the control (default: the field name with underscores replaced and the first letter capitalised); the suffix (default `":"`) can be overridden per field or per form.
| `initial`
| Value (or callable) shown by an unbound form. Never a validation fallback.
| `widget`
| A widget class or instance replacing the field's default control. See <<widgets>>.
| `help_text`
| Descriptive text rendered with the field; since 5.0 inputs get an `aria-describedby` that points at it.
| `error_messages`
| A dictionary overriding messages by key (`required`, `invalid`, `max_length`, and field-specific keys such as `invalid_choice`).
| `validators`
| A list of callables run after the field's own validation; see xref:web/django/form-validation-and-validators.adoc[Form Validation & Validators].
| `localize`
| `True` enables localised input and output formats for the value (and forces a `TextInput` for numbers).
| `disabled`
| Renders the `disabled` attribute and, crucially, ignores whatever the client submits: the value always comes from the form's initial data. See <<disabled>>.
| `template_name`
| Template used by `as_field_group()` for this field (5.0).
| `bound_field_class`
| A per-field replacement for `Form.bound_field_class` (5.2).
|===

Three of these deserve a closer look because they are misused constantly.

*`ChoiceField` and its siblings.* The choices come from the model-field vocabulary since 5.0, so a `TextChoices` class can be
passed directly (`choices=Genre`) and no `.choices` property is needed. A `ChoiceField` always returns a string; for numbers
use `TypedChoiceField`. Both reject any submitted value that is not among the choices, which is a security property
(a tampered `<select>` cannot smuggle a value in) as well as a validation rule. The `ModelChoiceField` blank label changed
in 6.1: the default blank label of choice fields moved from `"---------"` to `"- Select an option -"`, defined as
`django.db.models.fields.BLANK_CHOICE_LABEL`, and the transitional setting `USE_BLANK_CHOICE_DASH` brings the old dash
back while it lasts (it is deprecated).

*`BooleanField`.* `forms.BooleanField()` is _required_ by default, so a form with an optional checkbox must say
`required=False`; otherwise every submission without the box ticked fails with "This field is required", which is correct
for an "accept the terms" box and wrong for a preference. The cleaned value is a real `bool`.

*`DecimalField` and `DateField`.* They parse according to the active locale only when `localize=True` (or the widget is
configured for it); by default they use the formats listed in `input_formats` and the ISO formats. A date typed into a
plain text input in a format Django does not know is rejected with `Enter a valid date.`; the cure is a `type="date"`
input (as in the example) or an explicit `input_formats` list, not a custom parser.

[#widgets]
== Widgets: rendering and extracting

A widget is the HTML control and the code that reads its value out of the submitted data. A field holds the logic
("is this a date?"), a widget the presentation ("is it a text box, a date picker or three selects?"). Each field class has a
default widget (see the table above) and the `widget` argument replaces it:

[source,python]
----
class CommentForm(forms.Form):
    name = forms.CharField()
    url = forms.URLField()
    comment = forms.CharField(widget=forms.Textarea)
----

Source: https://docs.djangoproject.com/en/6.1/ref/forms/widgets/#specifying-widgets[Django: Specifying widgets]

Source: https://docs.djangoproject.com/en/6.1/ref/forms/widgets/#built-in-widgets[Django: Built-in widgets]

Things that matter in practice:

* *`attrs` adds HTML attributes.* `forms.TextInput(attrs={"autofocus": True, "autocomplete": "off"})` renders the
  attributes verbatim; `True` renders a bare attribute (`autofocus`). This is how you add a CSS class, a `placeholder`,
  `inputmode` or `type="date"` without touching templates. To set attributes in bulk (every field gets a class), loop over
  `self.fields` in the form's `+__init__+` and update `widget.attrs`, or use `bound_field_class` or a template override
  (see the rendering page).
* *Field type and widget type are independent.* `DateField(widget=DateInput(attrs={"type": "date"}))` still validates a
  `date`; replacing the widget does not change what is accepted. Swapping `TextInput` for `HiddenInput` does not make the
  value trustworthy: a hidden field is client data like any other.
* *The widget extracts the value.* `value_from_datadict(data, files, name)` is what reads the raw value (for a
  `SelectDateWidget` it joins `name_year`, `name_month`, `name_day`). `value_omitted_from_data()` tells the form whether
  the control was submitted at all; `CheckboxInput` answers `False` always, because an unticked box is indistinguishable
  from an omitted one, which is why `BooleanField` can never be "left alone" in a partial update.
* *Required rendering.* A widget decides through `use_required_attribute(initial)` whether `required` is emitted; the
  built-in `ClearableFileInput` drops it when a file is already stored.
* *Accessibility attributes are automatic.* Since 5.0 a field with help text gets `aria-describedby`, an invalid field
  gets `aria-invalid="true"` (5.0), and (5.2) the error list is connected through `aria-describedby` too; `use_fieldset`
  controls whether multi-control widgets are wrapped in a `<fieldset>` with a `<legend>`.
* *Writing a widget* (a `template_name`, a `get_context()` override, a `Media` class for CSS and JavaScript) is covered in
  xref:web/django/form-rendering-and-widgets.adoc[Form Rendering & Widgets].

[#view]
== The GET/POST/redirect pattern

The standard way to handle a form in a view is the same few lines every time, and each line has a reason:

.The suggestion view (catalog/views.py)
[source,python]
----
# catalog/views.py
import logging

from django.contrib import messages
from django.shortcuts import redirect, render

from .forms import BookSuggestionForm

logger = logging.getLogger(__name__)


def suggest_book(request):
    if request.method == "POST":
        form = BookSuggestionForm(request.POST)
        if form.is_valid():
            logger.info("suggestion received: %s", form.cleaned_data["title"])
            messages.success(request, "Thanks, we will look into it.")
            return redirect("catalog:suggest-done")
    else:
        form = BookSuggestionForm()
    return render(request, "catalog/suggest.html", {"form": form})


def suggest_done(request):
    return render(request, "catalog/done.html")
----

[source,html+django]
----

{% include "catalog/messages.html" %}
<h1>Suggest a book</h1>
<form method="post" novalidate>
  {% csrf_token %}
  {{ form }}
  <button type="submit">Send suggestion</button>
</form>
----

----

The `curl` session against `runserver` (the cookie jar carries the CSRF cookie between requests; the token is read from the
form's hidden input) produced:

[source,bash]

$ curl -s -b jar.txt -X POST --data-urlencode "csrfmiddlewaretoken=$T" -d "title=&author=H&genre=poetry" .../catalog/suggest/

<ul class="errorlist" id="id_genre_error"><li>Select a valid choice. poetry is not one of the available choices.</li></ul>
200                                              # invalid: the page is shown again, with errors
$ curl -s -b jar.txt -D - -o /dev/null -X POST --data-urlencode "csrfmiddlewaretoken=$T" -d "title=Dune&author=Herbert&genre=fiction" .../catalog/suggest/

Location: /catalog/suggest/done/                 # valid: redirect

<p>Suggestion received.</p>
----

Why each part is the way it is:

* *Three outcomes, one view.* GET shows an empty form; an invalid POST shows the same template with the _bound_ form (the
  user's input and the errors); a valid POST does its work and redirects. The `else` branch builds the unbound form, so
  there is exactly one `render()` call for both display cases.
* *Redirect after a successful POST (Post/Redirect/Get).* If the success page were rendered by the POST itself, a browser
  refresh would resubmit the form (the "resend form data?" dialog) and create the suggestion twice. A `302` to a GET URL makes
  refresh harmless and the success page bookmarkable. Use `redirect()` or `HttpResponseRedirect` with a named URL through
  `reverse()`; never hard-code paths. A `303 See Other` is the status that says "fetch this with GET" most precisely;
  Django's default `302` is treated as a 303 by every browser for a POST.
* *An invalid form returns status 200.* Django's convention is to re-render with `200`, not `400` or `422`; browsers show
  it either way, but many tools treat a `4xx` page as a failure. JavaScript clients that need a machine-readable signal use
  a JSON response, as `suggest_api` below does with `422`.
* *The message survives the redirect.* `messages.success()` stores the text in the session or a cookie, and the next
  page's template shows and clears it; see xref:web/django/sessions-cookies-messages-and-signing.adoc[Sessions, Cookies,
  Messages & Signing].
* *`novalidate` is a choice.* It turns off the browser's own checks so you see Django's messages while developing; leave it
  off in production if you want the browser's early feedback. Browser checks are a convenience: the server always
  validates, because a client can send anything.
* *`{{ form }}` renders the whole form.* Since 5.0 it uses the `<div>`-based template; <<rendering>> shows the other ways.
* *Side effects go after `is_valid()`.* Do the work (save, enqueue, send) only with `cleaned_data`, never with
  `request.POST`. Work that must not run if a transaction rolls back belongs in `transaction.on_commit()`, see
  xref:web/django/transactions-raw-sql-and-multiple-databases.adoc[Transactions, Raw SQL & Multiple Databases].

The shortcuts and decorators around this pattern (`require_POST`, `require_http_methods`, `redirect()`) are covered in
xref:web/django/function-based-views-and-shortcuts.adoc[Function-Based Views & Shortcuts], in particular its section on
redirects.

[#get-forms]
== Forms that use GET

A form with `method="get"` puts its fields in the query string, which is exactly right for search and filtering: the result
page has a URL a person can bookmark, share and reload. There is no state change, so no CSRF token and no redirect.

.A search form bound to request.GET (catalog/forms.py and views.py)
[source,python]
----
# catalog/forms.py
class SearchForm(forms.Form):
    q = forms.CharField(required=False, label="Search")
    genre = forms.ChoiceField(
        required=False, choices=[("", "Any genre"), *Genre.choices]
    )


# catalog/views.py
BOOKS = [
    {"title": "Dune", "genre": "fiction"},
    {"title": "Cosmos", "genre": "science"},
    {"title": "SPQR", "genre": "history"},
]


def book_search(request):
    form = SearchForm(request.GET or None)
    results = BOOKS
    if form.is_valid():
        q = form.cleaned_data["q"].lower()
        genre = form.cleaned_data["genre"]
        results = [
            b
            for b in BOOKS
            if q in b["title"].lower() and (not genre or b["genre"] == genre)
        ]
    return render(request, "catalog/search.html", {"form": form, "results": results})
----

----
{# catalog/templates/catalog/search.html #}
<h1>Search</h1>
<form method="get" action="{% url 'catalog:search' %}">
  {{ form }}
  <button type="submit">Search</button>
</form>
<ul>
  {% for book in results %}<li>{{ book.title }} ({{ book.genre }})</li>{% empty %}<li>No books found.</li>{% endfor %}
</ul>

`request.GET or None` is the idiom for "unbound until the user submits something": an empty query string is an empty
`QueryDict`, which is falsy, so the form stays unbound and shows every book without errors. The pitfall is a form with
required fields on a page that other links reach with unrelated query parameters (`?page=2`): that non-empty query string
binds the form and reports "required" errors. In that case test for a field explicitly (`"q" in request.GET`) or give every
search field `required=False`, as here. A GET form is also the place where pagination links must carry the filter along; the
`{% querystring %}` tag (5.1) does it, see xref:web/django/pagination.adoc[Pagination].

[#csrf]
== CSRF protection and `{% csrf_token %}`

Cross-site request forgery makes a logged-in person's browser send a request they did not intend: a hidden form on another
site that POSTs to `/catalog/suggest/` rides on the session cookie the browser attaches automatically. Django's defence is
the _synchroniser token_ pattern implemented by `CsrfViewMiddleware`, which is in the default `MIDDLEWARE` list:

. A random secret is stored in the `csrftoken` cookie (changed at login).
. The `{% csrf_token %}` tag renders `<input type="hidden" name="csrfmiddlewaretoken" value="...">`. The value is the secret
  masked with a fresh random mask on every render (so the HTML differs each time, as a defence against BREACH-style
  compression attacks).
. For every request whose method is not GET, HEAD, OPTIONS or TRACE the middleware requires the cookie and a matching token,
  from the `csrfmiddlewaretoken` form field or from the `X-CSRFToken` header (`CSRF_HEADER_NAME`).
. It also checks the `Origin` header against the current host and `CSRF_TRUSTED_ORIGINS`, and, for HTTPS requests with no
  `Origin`, the `Referer` strictly. On failure the response is a 403, produced by the `CSRF_FAILURE_VIEW`
  (`django.views.csrf.csrf_failure` by default) and logged on the `django.security.csrf` logger.

An attacker's page can make the browser send the cookie but cannot read it (same-origin policy), so it cannot produce the
matching token. The protection assumes HTTPS with HSTS, validated `Host` headers and no XSS: an XSS hole already gives the
attacker everything CSRF would.

[#csrf-token]
=== Using the tag

[source,html+django]
----
<form method="post">
  {% csrf_token %}
  ...
</form>
----

Rules, from the how-to and the reference:

* Put `{% csrf_token %}` inside every `<form method="post">` that targets an internal URL.
* *Never* put it in a form whose `action` is an external site: the token would be leaked to that site.
* The template must be rendered with a `RequestContext`, which `render()`, the generic views and the contrib apps already
  do. If you build the response with `Template.render(Context(...))` and no request, the tag renders nothing and the POST
  fails with 403.
* GET forms need no token, and adding one only leaks it into URLs, logs and referrers.
* In the Jinja2 backend the equivalent is `{{ csrf_input }}`, which Django adds to the context.
* The token makes a page `Vary: Cookie` and sets a cookie, so it interacts with caching; the how-to explains the
  `cache_page`/`ensure_csrf_cookie` combinations (see xref:web/django/security.adoc[Security] for the whole security
  picture).

The `Client(enforce_csrf_checks=True)` tests below prove the rejection and the acceptance paths; the default test client
does _not_ enforce CSRF, so an ordinary test with `client.post()` passes even if the template forgot the tag, and only the
`curl` session (or a test that reads the token from the rendered page and posts it back) proves the template is right.

.CSRF behaviour under test (catalog/tests.py)
[source,python]
----

----

has no form.

=== CSRF settings and decorators

[cols="2,5",options="header"]
|===
| Item | Notes

| `CSRF_COOKIE_NAME`, `CSRF_COOKIE_AGE`, `CSRF_COOKIE_DOMAIN`, `CSRF_COOKIE_PATH`
| Cookie name (`csrftoken`), lifetime (one year), and scope. A domain such as `.example.com` allows cross-subdomain posts.
| `CSRF_COOKIE_SECURE`, `CSRF_COOKIE_HTTPONLY`, `CSRF_COOKIE_SAMESITE`
| `Secure` flag (set it with HTTPS), `HttpOnly` (breaks reading the cookie from JavaScript), `SameSite` (`"Lax"` by default).
| `CSRF_USE_SESSIONS`
| Store the secret in the session instead of a cookie.
| `CSRF_HEADER_NAME`
| The `request.META` key of the header, `"HTTP_X_CSRFTOKEN"` by default (the header is `X-CSRFToken`).
| `CSRF_TRUSTED_ORIGINS`
| Origins allowed to post cross-origin or behind a reverse proxy; each entry must include the scheme (`https://app.example.com`), required since 4.0.
| `CSRF_FAILURE_VIEW`
| A function `view(request, reason="")` that renders the 403 page; use it for a friendly message.
| `@csrf_protect`
| Enforces the check on one view; use it only if the middleware is removed, and then on both the view that renders the token and the one that receives the POST.
| `@csrf_exempt`
| Turns the check off for a view. Legitimate for a webhook that authenticates in some other way (a signature); never a fix for "my form gives 403".
| `@requires_csrf_token`
| Makes `{% csrf_token %}` work without enforcing the check.
| `@ensure_csrf_cookie`
| Forces the cookie to be sent by a view that has no `{% csrf_token %}`.
|===

Source: https://docs.djangoproject.com/en/6.1/ref/csrf/#settings[Django: CSRF settings] and https://docs.djangoproject.com/en/6.1/ref/csrf/#utilities[CSRF utilities]

The mass of "403 CSRF verification failed" reports reduce to a short list: the tag is missing (or is in a form that renders
without a request), the cookie is blocked or was never set (the page was served from a cache, or the form comes from a
different host), the site runs behind a TLS-terminating proxy and `CSRF_TRUSTED_ORIGINS` or `SECURE_PROXY_SSL_HEADER` is not
configured, or a `Referrer-Policy: no-referrer` header makes the strict HTTPS referer check fail. The reason string is in the
403 page and the `django.security.csrf` log record.

[#files]
== File fields

A file input needs three things on the HTML side and one on the Python side. The form must use `method="post"`, the form tag
must carry `enctype="multipart/form-data"`, and the view must pass `request.FILES` as the second argument. If any of the
three is missing the file is silently absent and the form reports "This field is required".

.A form with file fields (catalog/forms.py)
[source,python]
----
from django.core.exceptions import ValidationError
from django.core.validators import FileExtensionValidator


def validate_max_size(file, limit=1024 * 1024):
    if file.size > limit:
        raise ValidationError(
            "File too large (%(size)d bytes, limit %(limit)d).",
            code="too_large",
            params={"size": file.size, "limit": limit},
        )


class ExcerptUploadForm(forms.Form):
    title = forms.CharField(max_length=100)
    excerpt = forms.FileField(
        validators=[FileExtensionValidator(["pdf", "txt"]), validate_max_size],
        max_length=100,
    )
    cover = forms.ImageField(required=False)

                reverse("catalog:upload"),
                {"title": "x", "excerpt": SimpleUploadedFile("../../evil.txt", b"hello")},
                follow=True,
            )
        self.assertContains(response, "Stored as excerpts/evil")
----

Source: https://docs.djangoproject.com/en/6.1/ref/forms/fields/#imagefield[forms.ImageField] and https://docs.djangoproject.com/en/6.1/topics/http/file-uploads/[Django: File uploads]

What to know about file fields:

* *`FileField` cleans to an `UploadedFile`* (`InMemoryUploadedFile` below 2.5 MB, `TemporaryUploadedFile` above,
  controlled by `FILE_UPLOAD_MAX_MEMORY_SIZE`) with `name`, `size`, `content_type` and `read()`/`chunks()`. The name is the
  client's, reduced to a base name; it is still client data, which is why the view stores it through `default_storage` and
  not through `open(os.path.join(...))`. The test of the view posts `../../evil.txt` and checks that the stored name is
  `excerpts/evil...` inside `MEDIA_ROOT`.
* *The validators in the example run in order.* Extension and size are cheap and happen before any heavy work. They are
  not a security check: the extension and `content_type` are client claims, so serving uploaded files safely is a separate
  topic (xref:web/django/file-uploads-and-storage.adoc[File Uploads & Storage], including multiple files, upload handlers,
  storage backends and private files).
* *`ImageField` needs Pillow* and opens the image to verify it (`invalid_image` for a corrupt or fake file), attaching the
  Pillow object as `.image` on the cleaned file. Pillow closes the file descriptor after verifying, so non-pixel attributes
  (`width`, `height`, `format`) remain readable but pixel methods require re-opening the file. Passing validation proves that
  Pillow can parse the file, not that it is harmless.
* *`max_length` limits the file _name_*, not the size; `allow_empty_file=True` accepts a zero-byte file (the default rejects
  it with the `empty` code). There is no built-in size limit on the field: use a validator (as above),
  `DATA_UPLOAD_MAX_MEMORY_SIZE` (2.5 MB, counts everything in the body _except_ file parts), `DATA_UPLOAD_MAX_NUMBER_FILES`
  (100) and `DATA_UPLOAD_MAX_NUMBER_FIELDS` (1000), and a limit at the reverse proxy.
* *Widgets.* `ClearableFileInput` is the default; when the form has an `initial` file (an edit form) it shows the current
  file and a "Clear" checkbox for optional fields. `FileInput` is the plain control. Neither accepts `multiple` unless the
  widget class sets `allow_multiple_selected = True` (the fix for CVE-2023-31047 in 4.2.1, 4.1.9 and 3.2.19), and a field
  that validates every file needs a custom `FileField` subclass as well.
* *Request-cycle position.* Because `CsrfViewMiddleware` reads `request.POST` for the token, the multipart body (and so the
  upload) is parsed in the middleware, before the view. The consequence: upload handlers cannot be swapped inside the view
  on the same request unless the view is exempt from the middleware's parse and protected by `csrf_protect` inside, which
  is described in the file-uploads topic guide.

[#disabled]
== Pre-filling, read-only fields, extra arguments and field changes

[source,python]
----
# catalog/forms_extra.py
from django import forms


class ShelfForm(forms.Form):
    name = forms.CharField(max_length=60)
    capacity = forms.TypedChoiceField(
        choices=[("", "Not set"), (10, "Small"), (50, "Large")],
        coerce=int, empty_value=None, required=False,
    )
    owner = forms.CharField(disabled=True, initial="library")

    def __init__(self, *args, owner=None, **kwargs):
        super().__init__(*args, **kwargs)
        if owner is not None:
            self.fields["owner"].initial = owner
            self.initial["owner"] = owner
        self.fields["name"].widget.attrs.update({"autofocus": True, "autocomplete": "off"})
----

Source: https://docs.djangoproject.com/en/6.1/ref/forms/fields/#disabled[Django: Field.disabled] and https://docs.djangoproject.com/en/6.1/ref/forms/api/#dynamic-initial-values[Dynamic initial values]

[source,python]
----
f = ShelfForm(owner="ana")
print(f.as_p())     # the owner control renders as: <input type="text" name="owner" value="ana" required disabled id="id_owner">

g = ShelfForm({"name": "Poetry", "capacity": "50", "owner": "mallory"}, initial={"owner": "ana"})
print(g.is_valid(), g.cleaned_data, g.changed_data)
# True {'name': 'Poetry', 'capacity': 50, 'owner': 'ana'} ['name', 'capacity']

h = ShelfForm(prefix="shelf", owner="ana")
print(h["name"])
# <input type="text" name="shelf-name" maxlength="60" autofocus autocomplete="off" required id="id_shelf-name">
----

* *`disabled=True` ignores the client.* The attacker's `owner=mallory` is discarded and the initial value `ana` is what ends
  up in `cleaned_data`. This is the correct way to show a read-only value; a `readonly` HTML attribute alone is only a hint
  to the browser. Combine it with a `clean_<field>` hook if the value must be re-checked.
* *Extra constructor arguments go through `+__init__+`.* Take them as keyword-only parameters _before_ calling
  `super().__init__()` and never as a positional argument that shifts `data`. The common case is `request.user` or a
  queryset limited to the current user; a `FormView` supplies it through `get_form_kwargs()`.
* *Per-instance changes.* `self.fields` is a per-instance deep copy, so modifying a field's `choices`, `queryset`, `initial`
  or `widget.attrs` in `+__init__+` is safe. Changing the class-level field (`ShelfForm.base_fields`) at request time is not:
  it is shared by every request.
* *`TypedChoiceField` converts.* The blank option cleans to `None` through `empty_value`, and `"50"` cleans to `50`.

[#rendering]
== Rendering a form in a template

The form object renders itself when printed. `{{ form }}` (and `{{ form.as_div }}`) uses the `<div>` template since 5.0;
`as_p`, `as_ul` and `as_table` are the older layouts, and each field has `as_field_group` (5.0). All of them use the form
renderer and the templates shown in xref:web/django/form-rendering-and-widgets.adoc[Form Rendering & Widgets]; the quick
reference is:

[source,html+django]
----
{{ form }}                      {# every field, as <div> blocks (the default since 5.0) #}
{{ form.as_p }}                 {# <p> per field #}
{{ form.title.as_field_group }} {# label, help text, errors and widget for one field (5.0) #}

{{ form.non_field_errors }}     {# errors raised in clean() and add_error(None, ...) #}
{{ form.title.errors }}         {# the ErrorList of one field #}
{{ form.title.label_tag }}      {{ form.title }}   {{ form.title.help_text }}
{% for field in form.hidden_fields %}{{ field }}{% endfor %}
{% for field in form.visible_fields %}...{% endfor %}
----

A `BoundField` (what `form["title"]` and `{% for field in form %}` produce) exposes `name`, `html_name`, `id_for_label`,
`label`, `help_text`, `value()`, `errors`, `is_hidden`, `field`, `form`, `data`, `initial`, `css_classes()`, `label_tag()`,
`legend_tag()` (4.1), `aria_describedby` (5.2) and `as_field_group()` (5.0). A small run:

[source,python]
----
bf = SearchForm({"q": "dune"})["q"]
print(bf.name, bf.html_name, bf.id_for_label, bf.value(), bf.label, bf.is_hidden, bf.errors)
# q q id_q dune Search False
print(SearchForm()["q"].as_field_group())
# <label for="id_q">Search:</label>
# <input type="text" name="q" id="id_q">
print(SearchForm(use_required_attribute=False)["q"])
# <input type="text" name="q" id="id_q">
----

Source: https://docs.djangoproject.com/en/6.1/topics/forms/#rendering-fields-manually[Django: Rendering fields manually] and https://docs.djangoproject.com/en/6.1/ref/forms/api/#django.forms.BoundField[BoundField]

Two security notes belong here. Field and error text is escaped on output; `help_text` is _not_ escaped (it is meant to
carry markup), so never build it from user input without `format_html()`. And a manual loop that forgets
`{% csrf_token %}`, the hidden fields or `form.non_field_errors` produces a form that looks right and silently fails:
prefer `{{ form }}` or `as_field_group`, and test with a `POST` through the rendered HTML.

[#testing]
== Testing forms and views

Test the form on its own (cheap, no database, no URLs), then the view (status codes, redirect, context, messages), then
CSRF (with `enforce_csrf_checks`). `SimpleTestCase.assertFormError()` takes the _form instance_, the field name and the
expected message; the old `assertFormError(response, "form", "field", msg)` signature was deprecated in 4.1 and removed in 5.0.

[#async]
== Sync and async

Forms have no asynchronous API: `is_valid()`, `full_clean()`, `clean()` and every `clean_<field>()` hook are plain
synchronous methods, and there is no `ais_valid()`. That is harmless in an `async def` view as long as validation is pure
Python, and a bug when it touches the database:

* A form made of ordinary fields (`CharField`, `ChoiceField`, `FileField` with validators that read bytes) can be
  validated directly inside an async view; the work is CPU-bound and short. `request.POST` can also be read in an async
  view, because the ASGI handler has already buffered the body.
* `ModelChoiceField`, `ModelMultipleChoiceField`, `unique` checks in a `ModelForm`, and any `clean_<field>` hook that runs a
  query evaluate a queryset in the synchronous API. Called from the event loop, Django raises
  `SynchronousOnlyOperation`. Run the whole validation in a thread with `sync_to_async()` (or `asyncio.to_thread()`).

.A form without the database in an async view, and one with it (catalog/views.py)
[source,python]
----
from asgiref.sync import sync_to_async
from django.http import HttpResponse, JsonResponse


async def async_search(request):
    form = SearchForm(request.GET or None)
    ok = form.is_valid() if form.is_bound else False
    return JsonResponse({"bound": form.is_bound, "valid": ok})


async def pick_reviewer_wrong(request):
    form = ReviewerForm(request.POST)        # ReviewerForm has a ModelChoiceField
    return HttpResponse(str(form.is_valid()))  # raises SynchronousOnlyOperation


async def pick_reviewer(request):
    form = ReviewerForm(request.POST)
    valid = await sync_to_async(form.is_valid)()
    return HttpResponse(str(valid))
----

----
# catalog/forms.py
from django.contrib.auth import get_user_model

.Async tests (catalog/tests.py)
[source,python]
----
from django.contrib.auth import get_user_model
from django.core.exceptions import SynchronousOnlyOperation
from django.test import AsyncClient, TestCase


class AsyncTests(TestCase):
    async def test_form_without_database_access_works_in_async_view(self):
        response = await AsyncClient().get("/catalog/async/search/", {"q": "x"})
        self.assertEqual(response.json(), {"bound": True, "valid": True})

    async def test_model_choice_field_needs_sync_to_async(self):
        user = await get_user_model().objects.acreate_user("ana")
        client = AsyncClient()
        with self.assertRaises(SynchronousOnlyOperation):
            await client.post("/catalog/async/reviewer-wrong/", {"reviewer": user.pk})
        response = await client.post("/catalog/async/reviewer/", {"reviewer": user.pk})
        self.assertEqual(response.content, b"True")

Source: https://docs.djangoproject.com/en/6.1/topics/async/#asgiref.sync.sync_to_async[Django: Asynchronous support] and https://docs.djangoproject.com/en/6.1/ref/forms/fields/#modelchoicefield[ModelChoiceField]

Further notes: the CSRF middleware is sync and async capable, so it does not force a thread hop when the view is async (the
cost of adaptation is described on the middleware page); template rendering with `{{ form }}` is synchronous too, and a
`ModelChoiceField` evaluates its queryset when it renders, so a form with a model field needs the database in the render step
as well. The pragmatic rule is that views that process forms are usually better written as ordinary synchronous views: Django
runs them in a thread pool under ASGI, and nothing is gained by writing the form step as `async` while the validation has
to be wrapped anyway. See xref:web/django/async-support.adoc[Async Support].

[#pitfalls]
== Pitfalls

* *Detecting a submission with `if request.POST`.* An empty POST is falsy; use `request.method == "POST"`.
* *Forgetting `request.FILES` or `enctype`.* The file is silently absent; the field says "This field is required".
* *`@csrf_exempt` to cure a 403.* It removes the protection. Add `{% csrf_token %}`, render with a request, or fix
  `CSRF_TRUSTED_ORIGINS`.
* *`{% csrf_token %}` in a form with an external `action`.* It leaks the token to that site.
* *Rendering the success page from the POST.* Refresh resubmits; redirect (Post/Redirect/Get).
* *Changing state in a GET view.* CSRF does not protect GET; browsers prefetch and crawlers follow links.
* *Reading `request.POST[...]` instead of `cleaned_data`.* You skip validation, conversion and normalisation.
* *Reading `cleaned_data` after a failed `is_valid()`.* Keys of failed fields are missing.
* *`BooleanField` without `required=False`.* The checkbox becomes mandatory.
* *Believing `initial` is a default.* It is only for display; a missing value fails "required".
* *Treating `HiddenInput` or `readonly` as trusted.* Use `disabled=True` and validate on the server; a hidden control is
  user input.
* *Passing `request.POST` to a form behind a JSON API.* A JSON body leaves `request.POST` empty.
* *Mutating the class-level fields at request time.* Change `self.fields` in `+__init__+`.
* *Dynamic choices computed at import time.* `choices=[... for x in Model.objects.all()]` in the class body runs a query
  at import time and freezes the list; pass a callable, use a `ModelChoiceField`, or set the choices in `+__init__+`.
* *Mixing a validation concern into the template.* Show `form.errors`, `non_field_errors` and each field's errors, or users
  will not see why the page came back.
* *`fields = "__all__"` and `exclude` in model forms.* Mass assignment: always list the fields explicitly (see
  xref:web/django/model-forms-and-formsets.adoc[Model Forms & Formsets]).
* *Trusting the browser's `required` and `maxlength`.* They are hints; every rule must also exist on the server.
* *Validating a `ModelChoiceField` form in an async view without `sync_to_async()`.* `SynchronousOnlyOperation`.

[#outdated]
== Where the books are outdated

The four reference books target Django 1.11 to 2.1 (2017-2018); the concepts they teach for forms are still right (declare
fields, bind, validate, redirect), but a good deal of the surrounding code has moved on:

* *Manual field-by-field rendering loops.* Hand-written `{% for field in form %}` blocks printing the label, the errors and
  the widget, and `{{ form.as_table }}` wrapped in `<table>`, were the norm. Forms render through templates since 4.0,
  `as_div` arrived in 4.1 and became the default for `{{ form }}` in 5.0, and `as_field_group` (5.0) renders one field with
  its label, help text and errors in one call.
* *Hand-written CSRF exemption for AJAX.* Books that add a `CsrfExemptMixin` or `@csrf_exempt` to make a JavaScript POST
  work are wrong; the documented answer is the `X-CSRFToken` header (<<csrf-ajax>>).
* *`CSRF_TRUSTED_ORIGINS` without a scheme.* Entries must include `https://` since 4.0; the old bare host names make the
  system check fail.
* *`ugettext`/`ugettext_lazy` for labels and error messages.* Removed in 4.0; use `gettext_lazy`.
* *`url()` in `form action` reverse examples.* `django.conf.urls.url()` was removed in 4.0; use `path()`/`re_path()`.
* *`assertFormError(response, "form", "field", message)`.* The signature was deprecated in 4.1 and removed in 5.0; pass the
  form (`response.context["form"]`).
* *`attrs={"multiple": True}` on file inputs.* Raises `ValueError` since 4.2.1 (4.1.9, 3.2.19); see <<files>>.
* *`URLField` defaulting to `http`.* The default scheme for a value typed without one changed to `https` in 6.0 (the
  `assume_scheme` argument came in 5.0, and the `FORMS_URLFIELD_ASSUME_HTTPS` transitional setting is gone).
* *`ModelChoiceField` blank label `---------`.* It is `- Select an option -` in 6.1.
* *Choices as a hand-built list of tuples only.* `ChoiceField` also accepts an enumeration, a mapping or a callable (5.0),
  which is much tidier with `TextChoices` (3.0).
* *`render_to_response()`* (removed 3.0) and *`request.REQUEST`* (long gone) in form views; use `render()` and `request.POST`
  or `request.GET`.
* *`django.shortcuts.render_to_response` and `ModelForm` without `Meta.fields`.* The latter has raised `ImproperlyConfigured`
  since 1.8; the books' habit of `fields = "__all__"` still works and is a security flaw (mass assignment).
* *jQuery date pickers and Bootstrap 3/4 markup.* Today `<input type="date">` (via `DateInput(attrs={"type": "date"})`) and
  the framework of your choice (see the crispy-forms discussion in the rendering page) replace them.
