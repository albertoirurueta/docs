depth. The examples use the _Bookshelf_ application that grows across this section: a `catalog` app with a `Book` model
and an `accounts` app with the custom user model.

[#layout]
== Project layout

* *Keep three roots apart.* The repository root holds tooling (`pyproject.toml`, `README`, CI files), the project root
holds `manage.py` and the apps, and the configuration package holds `settings`, `urls`, `asgi` and `wsgi`; naming that
package `config` makes its role obvious. See xref:web/django/project-structure-and-apps.adoc[Project Structure & Apps].
* *One app, one job.* An app should be describable in one sentence without "and"; split it when it is not. Plural nouns
(`reviews`, `orders`) read well as app names. See xref:web/django/project-structure-and-apps.adoc[Project Structure & Apps].
* *Shared helpers live in a `core` app* (abstract models, template tags, utilities), not in a grab-bag `utils.py` at the
project root. See xref:web/django/project-structure-and-apps.adoc[Project Structure & Apps].
* *Use `AppConfig` and keep start-up work in `ready()`.* List apps by their `AppConfig` path when it does work at
start-up, and import signal handlers from `ready()` rather than from `models.py`. See
xref:web/django/project-structure-and-apps.adoc[Project Structure & Apps] and xref:web/django/signals.adoc[Signals].

Source: https://docs.djangoproject.com/en/6.1/ref/applications/#django.apps.AppConfig.ready[AppConfig.ready()]

* *Start from a template, not from memory.* `startproject` with a custom `--template`, or a community template such as
cookiecutter-django, gives every project the same layout. See xref:web/django/getting-started.adoc[Getting Started] and
xref:web/django/project-structure-and-apps.adoc[Project Structure & Apps].
* *Manage dependencies with `pyproject.toml` and a lock file.* Two Scoops recommended virtualenvwrapper and one
`requirements/*.txt` file per environment; that still works, but today `python -m venv` or uv with a locked
`pyproject.toml` is the norm, and Django 6.1 itself needs Python 3.12 or newer. See
xref:web/django/getting-started.adoc[Getting Started].

[#settings]
== Settings

* *Commit every setting, never a secret.* Settings files belong in version control; the secret key, database password
and API keys come from the environment or a secret manager. See
xref:web/django/settings-and-configuration.adoc[Settings & Configuration].
* *Fail fast when configuration is missing.* Raise `ImproperlyConfigured` with a clear message instead of falling back
to an insecure default, so a misconfigured server never starts. See
xref:web/django/settings-and-configuration.adoc[Settings & Configuration].

.config/settings.py (excerpt)
[source,python]
----
import os
from pathlib import Path

from django.core.exceptions import ImproperlyConfigured

BASE_DIR = Path(__file__).resolve().parent.parent


def env(name, default=None):
    value = os.environ.get(name, default)
    if value is None:
        raise ImproperlyConfigured(f"Set the {name} environment variable.")
    return value


SECRET_KEY = env("DJANGO_SECRET_KEY")  # no default: a missing key must stop start-up
DEBUG = env("DJANGO_DEBUG", "False") == "True"
ALLOWED_HOSTS = env("DJANGO_ALLOWED_HOSTS", "localhost").split(",")
----

Source: https://docs.djangoproject.com/en/6.1/topics/settings/[Django settings] and
https://docs.djangoproject.com/en/6.1/ref/exceptions/#improperlyconfigured[ImproperlyConfigured]

A suitable value for `DJANGO_SECRET_KEY` can be generated with
`python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"`.

* *Split per environment only as far as needed.* A `settings` package with `base.py` plus `local.py`, `test.py` and
`production.py`, selected with `DJANGO_SETTINGS_MODULE`, is still a good shape; libraries such as django-environ
(0.14.0) read typed values from the environment. Two Scoops' JSON secrets file remains possible but is now the exception.
See xref:web/django/settings-and-configuration.adoc[Settings & Configuration].
* *Build paths from `BASE_DIR`* (a `pathlib.Path` since Django 3.1) instead of hard-coding absolute paths. See
xref:web/django/settings-and-configuration.adoc[Settings & Configuration].
* *Keep environments alike.* Use the same database engine (PostgreSQL for most projects) in development, CI and
production, ideally in containers, so that a query that works locally works in production. See
xref:web/django/postgresql-and-database-backends.adoc[PostgreSQL & Database Backends].
* *Use the current settings names.* `MIDDLEWARE_CLASSES` was removed in Django 2.0 (use `MIDDLEWARE`);
`DEFAULT_FILE_STORAGE` and `STATICFILES_STORAGE` were replaced by `STORAGES` in 4.2 and removed in 5.1; `USE_L10N` was
removed in 5.0; `DEFAULT_AUTO_FIELD` (3.2) defaults to `BigAutoField` since 6.0, so new projects need not set it -- only
older projects that never set it pin `AutoField` to avoid unwanted migrations. See
xref:web/django/settings-and-configuration.adoc[Settings & Configuration] and
xref:web/django/file-uploads-and-storage.adoc[File Uploads & Storage].

[#models]
== Models

* *Share fields through abstract base classes.* A `TimeStampedModel` with `created` and `modified` fields is still a
sound pattern; Django 5.0 added `db_default` and `GeneratedField` for values the database should compute. See
xref:web/django/model-inheritance-and-meta-api.adoc[Model Inheritance & Meta API].
* *Avoid multi-table inheritance* for anything queried often: every access joins the parent table. Prefer an abstract
base, a proxy model or an explicit `OneToOneField`. See
xref:web/django/model-inheritance-and-meta-api.adoc[Model Inheritance & Meta API].
* *Decide `null` and `blank` deliberately.* Text fields use `blank=True` and store `""`, never `null=True` (two
"empty" values); other fields use `null=True` when "unknown" is a real state. See
xref:web/django/models-and-fields.adoc[Models & Fields].
* *Use enumeration types for choices.* `models.TextChoices` and `IntegerChoices` (Django 3.0) replaced the constants
and `Enum` recipes in Two Scoops; since 5.0 `choices` also accepts the enumeration class directly, a mapping or a
callable. See xref:web/django/models-and-fields.adoc[Models & Fields].
* *Put reusable queries on a custom `QuerySet`* and expose it with `as_manager()`, so that `Book.objects.published()`
chains like any other filter. See xref:web/django/managers-and-custom-querysets.adoc[Managers & Custom QuerySets].
* *Reference the user model through `settings.AUTH_USER_MODEL`* in relations (see <<user-model>>).

.catalog/models.py
[source,python]
----
from django.conf import settings
from django.db import models
from django.utils.translation import gettext_lazy as _


class TimeStampedModel(models.Model):
    created = models.DateTimeField(auto_now_add=True)
    modified = models.DateTimeField(auto_now=True)

    class Meta:
        abstract = True


class BookQuerySet(models.QuerySet):
    def published(self):
        return self.filter(status=Book.Status.PUBLISHED)


class Book(TimeStampedModel):
    class Status(models.TextChoices):
        DRAFT = "draft", _("Draft")
        PUBLISHED = "published", _("Published")

    title = models.CharField(_("title"), max_length=200)
    subtitle = models.CharField(max_length=200, blank=True)  # "" not NULL
    pages = models.PositiveIntegerField(null=True, blank=True)  # unknown is NULL
    status = models.CharField(max_length=10, choices=Status, default=Status.DRAFT)
    owner = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE)
    views = models.PositiveIntegerField(default=0)

    objects = BookQuerySet.as_manager()

    def __str__(self):
        return self.title
----

Source: https://docs.djangoproject.com/en/6.1/topics/db/models/#abstract-base-classes[Abstract base classes],
https://docs.djangoproject.com/en/6.1/ref/models/fields/#field-choices-enum-types[Enumeration types] and
https://docs.djangoproject.com/en/6.1/topics/db/managers/#creating-a-manager-with-queryset-methods[Creating a manager with QuerySet methods]

* *Keep "fat models" thin enough.* Behaviour that belongs to one row goes on the model; workflows that touch several
models or external services go into plain service functions (see <<views-urls>>), not a thousand-line model class. See
xref:web/django/models-and-fields.adoc[Models & Fields].
* *Avoid `GenericForeignKey` when a real foreign key will do.* Generic relations cannot be enforced by the database
and are harder to query; use them only for genuinely polymorphic links such as tags or comments. See
xref:web/django/contenttypes-and-generic-relations.adoc[ContentTypes & Generic Relations].
* *Let the database guard invariants.* Declare `Meta.constraints` (`UniqueConstraint`, `CheckConstraint`, Django 2.2)
and `Meta.indexes`; `index_together` was removed in 5.1, and composite primary keys arrived in 5.2. Add indexes when a
measured query needs them, not by reflex. See
xref:web/django/constraints-indexes-and-composite-keys.adoc[Constraints, Indexes & Composite Keys].
* *Use the cross-database `models.JSONField`* (Django 3.1) instead of the PostgreSQL-only field Two Scoops describes, and
`BooleanField(null=True)` instead of the removed `NullBooleanField` (4.0). See
xref:web/django/models-and-fields.adoc[Models & Fields].

[#migrations]
== Migrations

* *Commit migrations with the model change* and review the generated file; `makemigrations --check` in CI catches a
model change that forgot its migration. See xref:web/django/migrations.adoc[Migrations].
* *Data migrations use the historical model and stay reversible.* Inside `RunPython`, get models with
`apps.get_model()` (never import them) and always provide a reverse function, even if it is `RunPython.noop`.

.catalog/migrations/0002_title_case_titles.py
[source,python]

from django.db import migrations


def title_case(apps, schema_editor):
    Book = apps.get_model("catalog", "Book")  # historical model, not an import
    for book in Book.objects.filter(title__regex=r"^[a-z]"):
        book.title = book.title.capitalize()
        book.save(update_fields=["title"])


class Migration(migrations.Migration):
    dependencies = [("catalog", "0001_initial")]

    operations = [
        migrations.RunPython(title_case, migrations.RunPython.noop),
    ]
----

Source: https://docs.djangoproject.com/en/6.1/topics/migrations/#data-migrations[Data migrations] and
https://docs.djangoproject.com/en/6.1/ref/migration-operations/#runpython[RunPython]

* *Squash long histories* with `squashmigrations` once every environment has applied them, and give hand-written
migrations a descriptive `--name`. See xref:web/django/migrations.adoc[Migrations].
* *Back up and rehearse before migrating production.* `migrate --plan` shows what will run; a schema change on a large
table may need to be split into several deploys. See xref:web/django/migrations.adoc[Migrations].
* *Prefer data migrations or factories to fixtures for reference data* that must exist everywhere. See
xref:web/django/fixtures-serialization-and-initial-data.adoc[Fixtures, Serialization & Initial Data].

[#queries]
== Queries

* *Let the database do the arithmetic.* Use `F()` for updates that depend on the current value (no race between read
and write), `Q()` for complex conditions, and database functions and aggregates before reaching for raw SQL. See
xref:web/django/making-queries.adoc[Making Queries] and
xref:web/django/aggregation-expressions-and-functions.adoc[Aggregation, Expressions & Functions].
* *Kill N+1 queries* with `select_related()` for forward foreign keys and `prefetch_related()` for many-valued
relations, and assert the query count in tests. Django 6.1 adds fetch modes: `QuerySet.fetch_mode(models.FETCH_PEERS)`
loads a missing relation for the whole batch at once, and `FETCH_RAISE` turns an accidental lazy load into an error.
See xref:web/django/query-optimization-and-fetch-modes.adoc[Query Optimization & Fetch Modes].
* *Group related writes in `transaction.atomic()`*, and start side effects such as emails or tasks with
`transaction.on_commit()` so they never fire for a rolled-back change. Wrapping a single ORM call adds nothing.
`ATOMIC_REQUESTS` is simple but holds a transaction open for the whole view; explicit blocks are usually clearer. See
xref:web/django/transactions-raw-sql-and-multiple-databases.adoc[Transactions, Raw SQL & Multiple Databases].

.catalog/services.py
[source,python]
----
from django.db import transaction
from django.db.models import F

from .models import Book
from .tasks import notify_owner


def publish_book(book_id):
    with transaction.atomic():
        book = Book.objects.select_for_update().get(pk=book_id)
        book.status = Book.Status.PUBLISHED
        book.save(update_fields=["status", "modified"])
        transaction.on_commit(lambda: notify_owner.enqueue(book_id))
    return book


def record_view(book_id):
    Book.objects.filter(pk=book_id).update(views=F("views") + 1)
----

Source: https://docs.djangoproject.com/en/6.1/ref/models/expressions/#f-expressions[F() expressions] and
https://docs.djangoproject.com/en/6.1/topics/db/transactions/#performing-actions-after-commit[Performing actions after commit]

* *Use `get_object_or_404()` in views only.* In models, services and tasks a missing row is a normal case to handle, not
an HTTP response. See xref:web/django/function-based-views-and-shortcuts.adoc[Function-Based Views & Shortcuts].
* *Raw SQL is a last resort, and always parameterised.* Pass values as `params`, never with string formatting. See
xref:web/django/transactions-raw-sql-and-multiple-databases.adoc[Transactions, Raw SQL & Multiple Databases] and
xref:web/django/security.adoc[Security].

[#views-urls]
== Views and URLs

* *Keep business logic out of views and URLconfs.* A view parses the request, calls a model method or service function
and returns a response; that keeps the logic reusable from the admin, management commands, APIs and tasks. See
xref:web/django/function-based-views-and-shortcuts.adoc[Function-Based Views & Shortcuts].
* *Choose the simplest view that stays clear.* A generic class-based view for standard CRUD, a function for anything
unusual; Two Scoops' FBV-or-CBV decision guide is still a good one. See
xref:web/django/class-based-views.adoc[Class-Based Views] and xref:web/django/generic-views.adoc[Generic Views].
* *Keep CBV inheritance shallow and put mixins on the left*, so `LoginRequiredMixin` runs before the view. Since Django 5.1,
`LoginRequiredMiddleware` can make login the default for the whole site, with `login_not_required` for the
exceptions. See xref:web/django/class-based-views.adoc[Class-Based Views] and
xref:web/django/authentication.adoc[Authentication].
* *Name every URL and namespace every app.* Set `app_name` in the app's URLconf and use `reverse()` and the `{% url %}`
tag, never hard-coded paths. Use `path()` with converters; `django.conf.urls.url()` from the Two Scoops era was removed
in Django 4.0 (`re_path()` remains for genuine regular expressions), and since 2.0 a namespace needs `app_name`. See
xref:web/django/urls-and-routing.adoc[URLs & Routing].
* *Pass an explicit context*, never `locals()`. See
xref:web/django/function-based-views-and-shortcuts.adoc[Function-Based Views & Shortcuts].

from django.shortcuts import get_object_or_404, render
from django.urls import reverse_lazy
from django.views.generic import CreateView

from .forms import BookForm
from .models import Book

def book_detail(request, pk):
    book = get_object_or_404(Book.objects.published().select_related("owner"), pk=pk)

class BookCreateView(LoginRequiredMixin, CreateView):  # mixin first
    model = Book
    form_class = BookForm
    success_url = reverse_lazy("catalog:book-create")

    def get_form_kwargs(self):
        kwargs = super().get_form_kwargs()
        kwargs["user"] = self.request.user
        return kwargs

    def form_valid(self, form):
        form.instance.owner = self.request.user
        return super().form_valid(form)

[#forms]
== Forms

* *Validate all input through a form or serializer*, including query parameters and data from trusted partners. See
xref:web/django/forms.adoc[Forms] and xref:web/django/form-validation-and-validators.adoc[Form Validation & Validators].
* *List model form fields explicitly.* `fields = "__all__"` and `Meta.exclude` silently expose any field added later
(mass assignment); set server-side values such as the owner in the view. See
xref:web/django/model-forms-and-formsets.adoc[Model Forms & Formsets] and xref:web/django/security.adoc[Security].
* *Cross-field errors go through `clean()` and `add_error()`*, so each message is attached to the right field; pass
extra context such as `request.user` through `get_form_kwargs()` (shown in <<views-urls>>) rather than a global. See
xref:web/django/form-validation-and-validators.adoc[Form Validation & Validators].

.catalog/forms.py
[source,python]
----
from django import forms
from django.utils.translation import gettext_lazy as _

from .models import Book


class BookForm(forms.ModelForm):
    class Meta:
        model = Book
        fields = ["title", "subtitle", "pages"]  # never "__all__" or exclude

    def __init__(self, *args, user, **kwargs):
        self.user = user
        super().__init__(*args, **kwargs)

    def clean(self):
        cleaned = super().clean()
        title = cleaned.get("title")
        if title and Book.objects.filter(owner=self.user, title=title).exists():
            self.add_error("title", _("You already have a book with this title."))
        return cleaned
----

Source: https://docs.djangoproject.com/en/6.1/topics/forms/modelforms/#selecting-the-fields-to-use[Selecting the fields to use] and
https://docs.djangoproject.com/en/6.1/ref/forms/api/#django.forms.Form.add_error[Form.add_error()]

* *State changes use POST with `{% csrf_token %}`*; GET must be safe to repeat. Since Django 5.0 even logout requires
POST. See xref:web/django/security.adoc[Security] and xref:web/django/authentication.adoc[Authentication].
* *Customise rendering with templates, not Python string building.* Django 4.0 made widgets and forms template-based
(`FORM_RENDERER`), 5.0 made the `<div>` layout the default and added `as_field_group`; Two Scoops' widget subclassing
for markup is rarely needed now. See xref:web/django/form-rendering-and-widgets.adoc[Form Rendering & Widgets].

[#templates]
== Templates

* *Keep templates "stupid".* No queries, aggregation or API calls triggered from a template: prepare the data in the
view (with `select_related()` and friends) and let the template only display it. See
xref:web/django/templates.adoc[Templates] and xref:web/django/query-optimization-and-fetch-modes.adoc[Query Optimization & Fetch Modes].
* *Prefer a filter to a tag*, and write a custom tag only when a filter cannot express it. See
xref:web/django/custom-template-tags-and-filters.adoc[Custom Template Tags & Filters].
* *Keep inheritance shallow*: a base layout, a section layout, then pages. Django 6.0's template partials
(`{% partialdef %}`) cover the reusable fragments that used to need extra include files, and pair well with HTMX. See
xref:web/django/template-partials-and-htmx.adoc[Template Partials & HTMX].
* *Leave auto-escaping on* and build HTML in Python with `format_html()` (see <<security>>). See
xref:web/django/templates.adoc[Templates].
* *Make error templates static.* `404.html` and `500.html` must not depend on context processors or the database, which
may be what failed. See xref:web/django/templates.adoc[Templates].

[#apis]
== APIs

* *Keep API views thin* and reuse the same services as the HTML views; serializers (DRF 3.18) or schemas (Django Ninja 1.7)
validate input exactly as forms do. See xref:web/django/django-rest-framework.adoc[Django REST Framework] and
xref:web/django/django-ninja.adoc[Django Ninja].
* *Version the API from the first release*, and retire old versions with a published timeline and finally `410 Gone`.
See xref:web/django/django-rest-framework.adoc[Django REST Framework].
* *Throttle every public endpoint* and document the limits. See
xref:web/django/django-rest-framework.adoc[Django REST Framework].

* *Publish an OpenAPI schema.* DRF's Core API schemas, which Two Scoops shows, were removed in DRF 3.17; use
drf-spectacular (0.30) with DRF, while Django Ninja generates OpenAPI itself. See
xref:web/django/django-rest-framework.adoc[Django REST Framework] and xref:web/django/django-ninja.adoc[Django Ninja].
* *Test every endpoint*, including permission failures. JavaScript clients of session-authenticated APIs send the CSRF
token in the `X-CSRFToken` header. See xref:web/django/testing.adoc[Testing] and xref:web/django/security.adoc[Security].
* *Choose GraphQL only for a reason* (many clients with different data needs); it changes caching, permissions and
query-cost concerns. See xref:web/django/graphql-with-django.adoc[GraphQL with Django].

[#admin]
== Admin

* *The admin is for trusted staff*, not a front end for customers; build real views for end users. See
xref:web/django/admin-site.adoc[Admin Site].
* *Move it off `/admin/`, serve it only over HTTPS*, and consider restricting it by network or adding multi-factor
authentication (for example django-allauth's MFA). The admin-honeypot packages Two Scoops mentions are largely
unmaintained. See xref:web/django/admin-site.adoc[Admin Site] and xref:web/django/security.adoc[Security].

Source: https://docs.djangoproject.com/en/6.1/ref/contrib/admin/#hooking-adminsite-instances-into-your-urlconf[Hooking AdminSite instances into your URLconf]

* *Make list pages cheap*: `list_select_related`, `search_fields`, `list_filter` and `show_full_result_count = False` on
large tables; use `@admin.display` and `@admin.action` (Django 3.2) for computed columns and bulk actions. See
xref:web/django/admin-customization.adoc[Admin Customization].

[#user-model]
== The user model

* *Start every project with a custom user model*, even an empty subclass of `AbstractUser`; switching later, once
tables reference `auth.User`, is a painful migration. See
xref:web/django/custom-user-model-and-backends.adoc[Custom User Model & Backends].
* *Refer to it indirectly*: `settings.AUTH_USER_MODEL` in foreign keys and other definitions evaluated at import time,
`get_user_model()` at run time.

.accounts/models.py, settings and usage
[source,python]
----
# accounts/models.py
from django.contrib.auth.models import AbstractUser


class User(AbstractUser):
    pass


# config/settings.py
AUTH_USER_MODEL = "accounts.User"

# anywhere at run time (tests, services, commands)
from django.contrib.auth import get_user_model

user = get_user_model().objects.create_user("ana", "ana@example.com", "a-long-test-password")
----

Source: https://docs.djangoproject.com/en/6.1/topics/auth/customizing/#using-a-custom-user-model-when-starting-a-project[Using a custom user model when starting a project] and
https://docs.djangoproject.com/en/6.1/topics/auth/customizing/#referencing-the-user-model[Referencing the User model]

* *Use the built-in auth views and password machinery.* The function-based `login()`/`logout()` views were removed in
Django 2.1 in favour of `LoginView` and friends; keep `PASSWORD_HASHERS` current (Argon2 or the default PBKDF2) and
enable the password validators. See xref:web/django/authentication.adoc[Authentication] and
xref:web/django/passwords.adoc[Passwords].
* *Authorise with permissions and groups*, not ad-hoc `is_staff` checks scattered through views. See
xref:web/django/permissions-and-authorization.adoc[Permissions & Authorization].

[#testing]
== Testing

* *Test one behaviour per test, including the failure paths* (404, permission denied, invalid form), and name tests
after the behaviour. See xref:web/django/testing.adoc[Testing].
* *Build data with factories, not fixtures.* factory_boy (3.3) or model_bakery (1.24; the renamed model_mommy that Two
Scoops mentions) keep test data next to the test and survive schema changes; `setUpTestData()` creates shared rows once
per class. See xref:web/django/pytest-factories-and-browser-tests.adoc[pytest, Factories & Browser Tests].
* *Use the cheapest tool that proves the point*: `RequestFactory` for a view in isolation, the test client for the full
stack, `assertNumQueries()` to pin the query count, `captureOnCommitCallbacks()` for `on_commit` work, and mocks for
external services. See xref:web/django/testing.adoc[Testing].

.catalog/tests.py (excerpt)
[source,python]
----
from django.contrib.auth import get_user_model
from django.core import mail
from django.test import RequestFactory, TestCase
from django.urls import reverse

from .models import Book
from .services import publish_book
from .views import book_detail


class BookTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        cls.user = get_user_model().objects.create_user("ana", "ana@example.com", "pw-test-1")

    def test_draft_is_404(self):
        book = Book.objects.create(title="Draft", owner=self.user)
        response = self.client.get(reverse("catalog:book-detail", args=[book.pk]))
        self.assertEqual(response.status_code, 404)

    def test_published_counts_view(self):
        book = Book.objects.create(title="Dune", owner=self.user, status=Book.Status.PUBLISHED)
        request = RequestFactory().get("/")
        with self.assertNumQueries(2):  # one SELECT with the JOIN, one UPDATE
            response = book_detail(request, pk=book.pk)
        self.assertEqual(response.status_code, 200)

    def test_publish_sends_mail_after_commit(self):
        book = Book.objects.create(title="Dune", owner=self.user)
        with self.captureOnCommitCallbacks(execute=True):
            publish_book(book.pk)
        self.assertEqual(len(mail.outbox), 1)
----

https://docs.djangoproject.com/en/6.1/topics/testing/advanced/#the-request-factory[The request factory]

[#tasks]
== Background tasks

* *Move slow work out of the request* (emails, image processing, partner APIs). Two Scoops pointed to Celery or
serverless functions; Django 6.0 added the built-in Tasks framework (`django.tasks`, `@task`, `enqueue()`), which
defines the API while a backend such as django-tasks-db or django-tasks-rq runs the worker. Celery (5.6) remains the
choice for complex workflows, and the `django-tasks` package (0.12) backports the API to 5.2 LTS. See
xref:web/django/tasks-framework.adoc[Tasks Framework] and xref:web/django/celery-integration.adoc[Celery Integration].
* *Keep tasks thin and pass IDs, not model instances.* Arguments cross a process boundary as JSON; the task re-reads
the row, which may have changed or disappeared. See xref:web/django/tasks-framework.adoc[Tasks Framework].
* *Make tasks idempotent* so a retry or duplicate delivery does no harm, *enqueue on commit* (see <<queries>>), and log
failures with `logger.exception()` before re-raising so the backend records them. See
xref:web/django/celery-integration.adoc[Celery Integration].

.catalog/tasks.py
[source,python]
----
import logging

from django.core.mail import send_mail
from django.tasks import task

logger = logging.getLogger(__name__)


@task
def notify_owner(book_id):
    from .models import Book

    book = Book.objects.select_related("owner").filter(pk=book_id).first()
    if book is None or book.status != Book.Status.PUBLISHED:
        return  # nothing to do: safe to run twice
    try:
        send_mail("Published", f"{book.title} is live.", None, [book.owner.email])
    except OSError:
        logger.exception("Could not notify owner of book %s", book_id)
        raise
----

Source: https://docs.djangoproject.com/en/6.1/topics/tasks/[Django's Tasks framework]

* *Monitor the queue*: backlog, failure rate and age of the oldest job belong on a dashboard. See
xref:web/django/tasks-framework.adoc[Tasks Framework].

== Security

* *Run `manage.py check --deploy` against production settings* in CI; it flags `DEBUG`, a weak `SECRET_KEY`, missing
HTTPS settings and more. See xref:web/django/system-checks.adoc[System Checks] and xref:web/django/security.adoc[Security].

System check identified 4 issues (0 silenced).

* *HTTPS everywhere*: `SECURE_SSL_REDIRECT`, `SECURE_HSTS_SECONDS`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, and
`SECURE_PROXY_SSL_HEADER` only when a trusted proxy sets the header. Set `ALLOWED_HOSTS` explicitly. See
xref:web/django/security.adoc[Security].
* *Build HTML with `format_html()`, not `mark_safe()` plus string formatting*; `format_html()` escapes every argument.

[source,python]

* *Add a Content Security Policy with the built-in support.* Django 6.0 added `ContentSecurityPolicyMiddleware` and
the `SECURE_CSP` and `SECURE_CSP_REPORT_ONLY` settings, so the django-csp package recommended by Two Scoops is no longer
required; enable the `csp` context processor when the policy uses nonces. See
xref:web/django/content-security-policy.adoc[Content Security Policy].

.config/settings.py (CSP excerpt)
[source,python]
----

    # ...
    "django.middleware.csp.ContentSecurityPolicyMiddleware",

    "default-src": [CSP.SELF],

Source: https://docs.djangoproject.com/en/6.1/ref/csp/[Content Security Policy]

* *Treat uploads as hostile*: limit size, validate type by content, store them outside the code tree with generated
names, and never serve them from the application domain without care. See
xref:web/django/file-uploads-and-storage.adoc[File Uploads & Storage].
* *Do not expose sequential primary keys* in public URLs when enumeration matters; use a slug or a UUID field. Never
unpickle or `eval` untrusted data, and load YAML with a safe loader. See xref:web/django/security.adoc[Security].
* *Keep sessions and signed values server-trusted*: the default database-backed sessions and `django.core.signing`
cover most needs. See xref:web/django/sessions-cookies-messages-and-signing.adoc[Sessions, Cookies, Messages & Signing].
* *Stay on a supported release, update dependencies promptly, publish a security contact and keep an incident-response
plan.* See xref:web/django/security.adoc[Security].

[#logging]
== Logging

* *One logger per module*, created with `logging.getLogger(__name__)`, so configuration can target an app or a module.
See xref:web/django/logging-and-error-reporting.adoc[Logging & Error Reporting].
* *Pick levels deliberately* (`DEBUG` for development detail, `INFO` for business events, `WARNING` and above for
problems) and *use `logger.exception()` inside `except` blocks* to keep the traceback; pass values as arguments
(`logger.info("New user %s", pk)`) rather than pre-formatting the string. The task above shows the pattern; see
xref:web/django/logging-and-error-reporting.adoc[Logging & Error Reporting].
* *Centralise errors*: send `ERROR` records to an error tracker such as Sentry rather than relying on `ADMINS` emails
alone. See xref:web/django/logging-and-error-reporting.adoc[Logging & Error Reporting].

    "loggers": {"catalog": {"handlers": ["console"], "level": "INFO"}},
}

[#signals]
== Signals

* *Use signals as a last resort.* They hide control flow; when you own both sides, call a service function or override
`save()` instead. Signals fit when one app must react to another app's events without importing it, for example
reacting to a third-party model.
* *Register receivers in `AppConfig.ready()`* (shown in <<layout>>), pass `sender` to narrow them, and remember that
`QuerySet.update()` and `bulk_create()` do not send `pre_save`/`post_save`. See xref:web/django/signals.adoc[Signals].

.catalog/signals.py
[source,python]
----
import logging

from django.conf import settings
from django.db.models.signals import post_save
from django.dispatch import receiver

logger = logging.getLogger(__name__)


@receiver(post_save, sender=settings.AUTH_USER_MODEL)
def log_new_user(sender, instance, created, **kwargs):
    if created:
        logger.info("New user %s", instance.pk)
----

[#performance]
== Performance

* *Measure before optimising.* Profile with django-debug-toolbar (8.0) in development and with query counts in tests;
most slow Django pages are a query problem. See
xref:web/django/performance-and-optimization.adoc[Performance & Optimization] and
xref:web/django/query-optimization-and-fetch-modes.adoc[Query Optimization & Fetch Modes].
* *Cache in layers*: per-view with `cache_page`, template fragments with `{% cache %}`, expensive values with the
low-level cache API, and a shared backend in production (the built-in Redis backend arrived in Django 4.0; Memcached
via `PyMemcacheCache` since 3.2). Normalise first and cache before you denormalise.

.catalog/urls.py (cached list view)
[source,python]
----
from django.urls import path
from django.views.decorators.cache import cache_page

from . import views

app_name = "catalog"
urlpatterns = [
    # ...
    path("books/", cache_page(60 * 15)(views.book_list), name="book-list"),
]
----

Source: https://docs.djangoproject.com/en/6.1/topics/cache/#specifying-per-view-cache-in-the-urlconf[Specifying per-view cache in the URLconf]

See xref:web/django/caching.adoc[Caching].

* *Serve static files efficiently*: hashed names with long cache lifetimes, compression, and a CDN where traffic
justifies one. See xref:web/django/static-files-and-front-end-assets.adoc[Static Files & Front-End Assets].
* *Use async where it helps*: views that wait on several network calls benefit from `async def` under an ASGI server;
CPU-bound or ORM-heavy views do not. Native async views arrived in Django 3.1 and the async ORM interface in 4.1, so
Channels (4.3) is now needed only for WebSockets and similar long-lived connections. See
xref:web/django/async-support.adoc[Async Support] and xref:web/django/channels-and-websockets.adoc[Channels & WebSockets].
* *Reuse database connections* with `CONN_MAX_AGE` or, on PostgreSQL with psycopg 3, the connection pool option added
in Django 5.1. See xref:web/django/postgresql-and-database-backends.adoc[PostgreSQL & Database Backends].

[#operations]
== Operations

* *Automate deployments so they are repeatable*: build an image or artefact once, run `check --deploy`,
`migrate` and `collectstatic` as explicit steps, and keep a staging environment that mirrors production. Two Scoops'
Heroku free tier and Chef/Puppet recipes have given way to containers and platforms such as Fly.io, Render or Cloud
Run, with ASGI or WSGI servers such as Uvicorn (0.54), Gunicorn (26.2), Granian (2.8) or Daphne (4.2).
See xref:web/django/deployment.adoc[Deployment], xref:web/django/docker-and-kubernetes.adoc[Docker & Kubernetes] and
xref:web/django/settings-and-configuration.adoc[Settings & Configuration].

[source,bash]
----
$ python manage.py makemigrations --check --dry-run
No changes detected
$ python manage.py migrate --plan
Planned operations:
catalog.0002_title_case_titles
    Raw Python operation
----

Source: https://docs.djangoproject.com/en/6.1/ref/django-admin/#migrate[django-admin migrate] and
https://docs.djangoproject.com/en/6.1/ref/django-admin/#makemigrations[django-admin makemigrations]

* *Back up the database and test the restore*; a rollback plan is only real once it has been rehearsed. See
xref:web/django/postgresql-and-database-backends.adoc[PostgreSQL & Database Backends].
* *Put recurring maintenance in management commands*, not in ad-hoc shell sessions, so it is reviewed, tested and
schedulable. See xref:web/django/management-commands-and-shell.adoc[Management Commands & Shell].
* *Ship risky changes behind feature flags* and remove the flag once the change is settled; a flag is just a setting read
from the environment, see xref:web/django/settings-and-configuration.adoc[Settings & Configuration].
* *Upgrade one feature release at a time*, running the test suite with `python -Wd` to surface deprecation warnings
first; Django 6.1 introduced calendar versioning, so the release after 6.2 LTS is Django 2028. See
xref:web/django/whats-changed-and-upgrading.adoc[What's Changed & Upgrading].

[#i18n]
== Internationalisation

* *Never concatenate translated fragments.* Translate whole sentences with named placeholders, so translators can
reorder them. See xref:web/django/internationalization-and-translation.adoc[Internationalization & Translation].
* *Use lazy translation in definitions evaluated at import time* (model fields, form labels, `choices`) and eager
`gettext()` at run time. `ugettext()` and `ugettext_lazy()`, used throughout Two Scoops, were removed in Django 4.0.

.catalog/utils.py (excerpt)
[source,python]
----
from django.utils.translation import gettext as _


def welcome(name, count):
    return _("Welcome %(name)s, you have %(count)d books.") % {"name": name, "count": count}
----

Source: https://docs.djangoproject.com/en/6.1/topics/i18n/translation/#standard-translation[Standard translation]

* *Store times in UTC and convert at the edges.* `USE_TZ = True` is the default since Django 5.0, and `zoneinfo`
replaced `pytz` in 4.0. See xref:web/django/localization-and-time-zones.adoc[Localization & Time Zones].
