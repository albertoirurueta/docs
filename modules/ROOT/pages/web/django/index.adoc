This section is written against Django 6.1.1 (released 2026-09-02), checked on 2026-10-03; Django 6.1.2, a
security and bug-fix release, is scheduled for 2026-10-06. Django 6.1 supports Python 3.12, 3.13 and 3.14, and
PostgreSQL 15 or later, MySQL 8.4 or later, MariaDB 10.11 or later and SQLite 3.37 or later. Where the long-term
support release Django 5.2 LTS (supported until April 2028) behaves differently, the pages say so.

Django's support policy gives each feature release mainstream support (bug and security fixes) until the next
feature release ships, roughly eight months later, followed by security fixes for roughly eight more months; every
third release is a long-term support (LTS) release that receives security fixes for about three years. Django 6.1 receives mainstream support until April 2027 and security fixes until
December 2027, and Django 6.0 is supported until April 2027. Django 6.2, due in April 2027, is the next LTS release
and the last one under this scheme. Starting with the release planned for January 2028, named *Django 2028*, Django
moves to calendar versioning (DEP 20) with one release per year, each supported for three years. Django 6.1 already
renames its deprecation warnings accordingly: what used to be `RemovedInDjango70Warning` is now
`RemovedInDjango2028Warning`. The xref:web/django/whats-changed-and-upgrading.adoc[What's Changed & Upgrading] page
covers the timeline and how to keep a project current.

== What Django is

Django is a free, open-source, "batteries-included" Python web framework, maintained by the Django Software
Foundation since 2008 and in public development since 2005. A single installation provides everything a
database-backed web site needs:

* an object-relational mapper (ORM) with schema migrations
* URL routing, function-based and class-based views, middleware and the request/response objects
* a template language with inheritance, partials and automatic HTML escaping
* forms with validation and rendering, including forms generated from models
* an automatic, customisable admin interface
* authentication, permissions, sessions, and protection against CSRF, XSS, clickjacking and SQL injection, plus a
  built-in Content Security Policy since Django 6.0
* caching, email, a background tasks framework (`django.tasks`, Django 6.0), signals, logging, internationalisation,
  localisation and time zones, pagination and system checks
* contrib apps for content types, sites, sitemaps, syndication feeds, flat pages, redirects and GeoDjango
* WSGI and ASGI deployment, with async views, async ORM methods and async authentication helpers

Django follows a model-template-view (MTV) split: models describe data, views decide what to return, and templates
render it. Its design philosophies (loose coupling, less code, "don't repeat yourself", explicit over implicit)
are described on the xref:web/django/introduction-and-architecture.adoc[Introduction & Architecture] page.

This section is for developers who:

* know Python (or come from Flask, FastAPI, Spring Boot, ASP.NET Core, Laravel or Rails) and want to build and run
  server-rendered sites, admin-heavy back offices, content sites or JSON APIs with Django
* want one coherent path from a first project to testing, security, background work, real-time features,
  deployment and upgrades
* learned Django from older books and tutorials (the 1.11 to 2.1 era) and need the current idioms: `path()` instead
  of `url()`, the `STORAGES` setting, `zoneinfo`, psycopg 3, POST-only logout, async views, `django.tasks`, template
  partials and the built-in CSP

== The Bookshelf scenario

Every example builds one small original site, _Bookshelf_, in the same domain as the
xref:backend/fastapi/index.adoc[Python FastAPI] and xref:backend/nestjs/index.adoc[NestJS] sections, so that the
three stacks can be compared page by page:

* a public catalogue of `books`, `authors` and `reviews` with server-rendered pages, PostgreSQL full-text search and
  pagination
* a custom user model with email login, sign-up, password reset and per-object permissions for editing reviews
* staff curation in the admin
* cover-image uploads
* English and Spanish translations
* a "new review" live feed over Server-Sent Events from an async view, with a Channels WebSocket variant
* review-moderation emails sent through `django.tasks`, with a Celery variant
* Redis caching
* a versioned REST API built with Django REST framework, with a Django Ninja variant
* a sitemap and an RSS feed
* a Docker deployment with Gunicorn and Uvicorn

.The Bookshelf site: clients, servers, the Django project and its backing services
image::django-bookshelf-architecture.svg["Diagram of the Bookshelf site. Clients (browsers using HTML and htmx, staff using the admin, API clients and feed readers) reach a reverse proxy and application servers: Gunicorn for WSGI, Uvicorn for ASGI and Daphne for Channels, with WhiteNoise serving static files. Behind them the Django project runs its middleware stack and URLconf, which dispatch to four apps: catalog, accounts, reviews and api. The apps share models and the ORM, templates and the admin. The ORM reads and writes PostgreSQL, Redis holds the cache, the channel layer and the optional Celery broker, and cover images go to media storage. Views enqueue moderation emails through django.tasks, which a task worker or Celery worker sends through an email provider.",width=100%]

The final project layout (a `config/` settings package, `apps/catalog`, `apps/accounts`, `apps/reviews`,
`apps/api`, `templates/`, `static/` and `pyproject.toml`) is assembled on
xref:web/django/project-structure-and-apps.adoc[Project Structure & Apps].

== Reading path

The pages are ordered so that each one builds on the previous ones. Read them in this order the first time, then use
them as a reference:

. *Foundations*: what Django is made of, a first project, the project layout, settings, and `manage.py`.
. *Models and the ORM*: fields, relationships, inheritance, migrations, queries, aggregation, managers,
  constraints, transactions, query optimisation, database backends and fixtures.
. *HTTP*: the request/response cycle, URLs, function-based, class-based and generic views, middleware, sessions
  and cookies, file uploads and non-HTML responses.
. *Templates and the front end*: the template language, partials with htmx, custom tags and filters, static files.
. *Forms*: forms, validation, rendering and widgets, model forms and formsets.
. *The admin*: registering models, then customising the admin for staff curation.
. *Authentication, authorisation and security*: logins, the custom user model, permissions, passwords, the security
  middleware and settings, and Content Security Policy.
. *Application services*: caching, email, the tasks framework and Celery, signals, logging, internationalisation,
  localisation and time zones, pagination and system checks.
. *Contrib apps*: content types, sites, sitemaps and feeds, flat pages, redirects, humanize and GeoDjango.
. *Async and real-time*: async views and the async ORM, then Channels and WebSockets.
. *Web APIs*: Django REST framework, Django Ninja and GraphQL.
. *Testing*: Django's test framework, then pytest, factories and browser tests.
. *Production*: deployment, containers, and performance.
. *Beyond the basics*: what changed since older tutorials and how to upgrade, reusable apps and third-party
  packages, and best practices.

The cheat sheet at xref:web/django/cheat-sheet.adoc[Django Cheat Sheet] condenses the whole section onto one page
