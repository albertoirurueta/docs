[#support-today]
== Supported versions and the release policy

Django ships a *feature release* roughly every eight months and *patch releases* as needed; every third feature release
(x.2) is a *long-term support* (LTS) release that receives security and data-loss fixes for about three years. A feature
deprecated in one release keeps working, with a warning, for at least two feature releases and is then removed. The
mechanics of this policy, and why it gives you a predictable upgrade path, are explained in
xref:web/django/introduction-and-architecture.adoc#release-policy[Introduction & Architecture: release policy] and
xref:web/django/introduction-and-architecture.adoc#deprecation-policy[its deprecation policy]; this section only records the
state on 2026-10-03.

.Supported Django series on 2026-10-03 (download page)
[cols="1,1,2,2,2",options="header"]
|===
| Series | Latest patch | End of mainstream support | End of extended support | Python

| 5.2 LTS | 5.2.17 | 2025-12-03 | April 2028 | 3.10-3.14 (3.14 from 5.2.8)
| 6.0 | 6.0.8 | 2026-08-04 | April 2027 | 3.12-3.14
| 6.1 | 6.1.1 | April 2027 | December 2027 | 3.12-3.14
|===

Everything older, including 4.2 LTS (extended support ended in April 2026) and 3.2 LTS, receives no more security
fixes. The next three releases are already scheduled:

[#calendar-versioning]
=== Calendar versioning from Django 2028

Following DEP 20, adopted in Django 6.1, the releases previously planned as 7.0 and 7.1 are called *Django 2028* and
*Django 2029*. From 2028 a feature release ships every January and is named after its year; 6.2 is the last release under
the old numbering and support scheme, and from Django 2028 on every release is supported for three years. The
deprecation warning classes are renamed to the calendar version in which the feature disappears: what 6.0 and 6.1
deprecate is announced by `RemovedInDjango2028Warning` (formerly `RemovedInDjango70Warning`).

The rename has a timing detail worth knowing: Django 6.1.1 (2026-09-02) still defines only `RemovedInDjango70Warning`.
The rename was committed to the 6.1 stable branch on 2026-09-03 and keeps `RemovedInDjango70Warning` as an alias, so it
reaches users with the next 6.1 patch release. Code that filters warnings should therefore match on the parent class
(`PendingDeprecationWarning` or `DeprecationWarning`) rather than on either name, as the pytest configuration in
<<warnings>> does.

[source,bash]
----
$ python -c "from django.utils import deprecation as d; print([n for n in dir(d) if n.startswith('Removed')])"
['RemovedAfterNextVersionWarning', 'RemovedInDjango70Warning', 'RemovedInNextVersionWarning']
----
Source: https://docs.djangoproject.com/en/6.1/releases/6.1/#adopting-calendar-versioning[Django 6.1 release notes: Adopting calendar versioning] and https://github.com/django/django/blob/stable/6.1.x/django/utils/deprecation.py[django/utils/deprecation.py on the 6.1 branch]

== Release by release: 3.0 to 6.1

The books stop at Django 2.1. The table gives the eleven feature releases since then at a glance; each subsection below
lists what a project upgrading through that release has to know: the supported Python versions, the headline features,
the backwards-incompatible changes and what was removed. Patch releases (x.y.1, x.y.2, ...) never add features and are
backwards compatible except where a security or data-loss fix requires otherwise, so they are not listed.

* *Python:* 3.6, 3.7, 3.8 and, from 3.0.11, 3.9. *Databases:* PostgreSQL 9.5 or newer; MariaDB 10.1+ becomes officially

* *Deprecated:* `ugettext*()` and `ungettext*()`, `force_text()` and `smart_text()`, `urlquote()` and friends (all removed in 4.0).

[#one-model]
=== One model, ten releases

The quickest way to feel how much the model layer moved since the books is to write one _Bookshelf_ model with a feature
from almost every release. Each comment names the release that introduced the line; none of it existed in Django 2.1.

.catalog/models.py
[source,python]
----
from decimal import Decimal

from django.db import models
from django.db.models import F, Q
from django.db.models.functions import Lower, Now


class Book(models.Model):
    class Format(models.TextChoices):  # 3.0: enumeration types for choices
        HARDCOVER = "HC", "Hardcover"
        EBOOK = "EB", "E-book"

    title = models.CharField(max_length=200)
    format = models.CharField(max_length=2, choices=Format, default=Format.HARDCOVER)  # 5.0: no .choices
    metadata = models.JSONField(default=dict, blank=True)  # 3.1: JSONField on every backend
    pages = models.PositiveIntegerField()
    added = models.DateTimeField(db_default=Now())  # 5.0: database-computed default
    price = models.DecimalField(max_digits=8, decimal_places=2)
    price_with_vat = models.GeneratedField(  # 5.0: generated column
        expression=F("price") * Decimal("1.21"),
        output_field=models.DecimalField(max_digits=10, decimal_places=2),
        db_persist=True,
    )

    class Meta:
        indexes = [models.Index(Lower("title"), name="book_title_ci_idx")]  # 3.2: functional index
        constraints = [
            models.UniqueConstraint(Lower("title"), name="book_title_ci_unique"),  # 4.0: functional unique
            models.CheckConstraint(condition=Q(pages__gt=0), name="book_pages_positive"),  # 5.1: condition=
        ]

    def __str__(self):
        return self.title


class Review(models.Model):  # id is a BigAutoField: DEFAULT_AUTO_FIELD defaults to it since 6.0
    book = models.ForeignKey(Book, on_delete=models.DB_CASCADE)  # 6.1: database-level ON DELETE
    stars = models.PositiveSmallIntegerField()


class ShelfEntry(models.Model):  # 5.2: composite primary key
    pk = models.CompositePrimaryKey("shelf", "position")
    shelf = models.CharField(max_length=50)
    position = models.PositiveIntegerField()
    book = models.ForeignKey(Book, on_delete=models.DB_CASCADE)
----

Two details came out of running it. `GeneratedField` expressions are computed by the database with its own arithmetic:
on SQLite `F("price") * 121 / 100` returned `12.00` for a price of `10.00` because the division was done on integers, while
`F("price") * Decimal("1.21")` returns `12.10`. And `db_comment` (4.2) was left out on purpose: SQLite cannot store column
comments, so `manage.py check` reports `fields.W163` there; on PostgreSQL it is a one-word addition.

The test exercises every comment above and passes under `-W error`, which turns any deprecation warning into a failure:

.catalog/tests.py
[source,python]
----

from django.core.exceptions import ValidationError
from django.test import TestCase

from .models import Book, Review, ShelfEntry


class TimelineFeatureTests(TestCase):
    def test_features_from_3_0_to_6_1(self):
        book = Book.objects.create(title="Dune", pages=412, price=Decimal("10.00"))
        book.refresh_from_db()

[#timeline]
== The deprecation timeline

The official deprecation timeline is organised by the release in which things are *removed*, newest first, and each block
points to the release notes "of two versions prior" where the deprecation was announced. On 2026-10-03 its blocks are
2028, 6.1, 6.0, 5.1, 5.0, 4.1, 4.0, 3.1, 3.0 and older. There are no 4.2, 5.2 or 6.2 blocks: an LTS release removes nothing,
and every feature deprecated in the last two releases of a series is removed in the first release of the next one. That
is the rule that makes the LTS-to-LTS path predictable.

.How a deprecation travels through the releases
[cols="2,3,3",options="header"]
|===
| Deprecated in | Warning class while it still works | Removed in

| 5.0 or 5.1 | `RemovedInDjango60Warning` | 6.0
| 5.2 LTS | `RemovedInDjango61Warning` | 6.1
| 6.0 or 6.1 | `RemovedInDjango70Warning`, renamed `RemovedInDjango2028Warning` (<<calendar-versioning>>) | Django 2028
| 6.2 LTS | named after the release that removes it | Django 2029
|===

The warning raised one release before removal subclasses `DeprecationWarning`; earlier than that it subclasses
`PendingDeprecationWarning`: Django 5.2.17 defines `RemovedInDjango60Warning(DeprecationWarning)` and
`RemovedInDjango61Warning(PendingDeprecationWarning)`, Django 6.0.8 `RemovedInDjango61Warning(DeprecationWarning)` and
`RemovedInDjango70Warning(PendingDeprecationWarning)`. Python never shows `PendingDeprecationWarning` by default and shows
`DeprecationWarning` only for code run directly as `+__main__+`, so neither appears when `manage.py` imports your modules.
That is why a project can run for years on deprecated APIs without anyone noticing.

The *Django 2028* block is the next one you will meet. Grouped by area, it removes:

* *Email:* the `EMAIL_BACKEND`, `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS`,
`EMAIL_USE_SSL`, `EMAIL_SSL_CERTFILE`, `EMAIL_SSL_KEYFILE`, `EMAIL_TIMEOUT` and `EMAIL_FILE_PATH` settings; `get_connection()`;
the `connection`, `fail_silently`, `auth_user` and `auth_password` arguments of the mail functions; positional optional
arguments; `BadHeaderError`, `SafeMIMEText`/`SafeMIMEMultipart` and legacy `MIMEBase` attachments.
* *Settings:* `ADMINS`/`MANAGERS` as `(name, address)` tuples; the transitional `URLIZE_ASSUME_HTTPS`,
`USE_BLANK_CHOICE_DASH` and `SIGNED_COOKIE_LEGACY_SALT_FALLBACK` settings.
* *ORM:* `select_related()` with no arguments or with `True`; `values_list(flat=True)` without a field; `None` in a
`JSONField` top-level lookup will mean SQL `NULL` (use `JSONNull()` for JSON `null`); `BLANK_CHOICE_DASH`;
`transaction.savepoint()`; percent signs in column aliases; the PostgreSQL `StringAgg`, `OrderableAggMixin` and bit
aggregates.
* *Admin:* `list_select_related = True`; `get_actions()` and `get_action_choices()` overrides without the new
`action_location` parameter.
* *Templates and utilities:* double-dot variable lookups such as `+{{ book..title }}+`; `urlize` defaults to HTTPS; the
`salted_hmac()` default algorithm moves from SHA-1 to SHA-256; `Paginator(orphans=...)` greater than or equal to
`per_page` is rejected.

Source: https://docs.djangoproject.com/en/6.1/internals/deprecation/[Django Deprecation Timeline] and https://docs.djangoproject.com/en/6.1/internals/release-process/#deprecation-policy[Release process: deprecation policy]

[#warnings]
=== Turning deprecation warnings on

The upgrade guide asks you to make the warnings visible before changing anything. With the Django test runner, pass
`-Wa` (show every occurrence) to Python, as the 6.1 how-to does; the `-Wd` often quoted in older guides shows each
warning once per code location, which is enough for a first inventory. `-W error` turns each warning into an exception,
which is what you want in CI once the warnings are fixed:

[source,bash]
----
$ python -Wa manage.py test
$ python -W error manage.py test
$ PYTHONWARNINGS=always pytest --capture=no
----

With pytest the same policy is better kept in the configuration, so nobody has to remember the flag. Matching the parent
classes covers every Django warning class, whatever its name (and the 6.1 rename):

.pyproject.toml
[source,toml]
----
[project]
name = "bookshelf"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = ["django>=6.1,<6.2"]

[tool.pytest.ini_options]
DJANGO_SETTINGS_MODULE = "config.settings"
python_files = ["tests.py", "test_*.py"]
filterwarnings = [
    "error::DeprecationWarning",
    "error::PendingDeprecationWarning",
]
----

[source,bash]
----
$ pytest -q legacy catalog
....                                                                     [100%]
4 passed in 0.29s
----
Source: https://docs.djangoproject.com/en/6.1/howto/upgrade-version/#resolving-deprecation-warnings[How to upgrade Django: Resolving deprecation warnings] and https://docs.pytest.org/en/stable/how-to/capture-warnings.html[pytest: How to capture warnings]

Third-party packages sometimes call deprecated APIs on purpose so they can support several Django versions; a warning
raised from inside a package is a reason to check for a newer release or open an issue, not necessarily a bug. If one
blocks `error::` mode, add a narrow `ignore:` entry for that package's module rather than turning the policy off. The
xref:web/django/pytest-factories-and-browser-tests.adoc[pytest, Factories & Browser Tests] page covers the rest of the
pytest-django set-up.

[#upgrading]
== Upgrading Django

Upgrading regularly keeps the project on a version that still receives security fixes, brings new features and bug
fixes, and keeps each individual upgrade small. The official how-to describes the same loop for every hop; the diagram
condenses it.

[mermaid]
----
flowchart TD
    A[Read the release notes of every feature release up to the target] --> B[Read the deprecation timeline for those releases]
    B --> C[On the current version run the tests with python -Wa and fix every warning]
    C --> D[Check that each dependency supports the next feature release]
    D --> E[Install the latest patch of the next feature release in a fresh environment]
    E --> F[Run django-upgrade, the full test suite with warnings on, check and makemigrations --check]
    F --> G{All green?}
    G -- no --> C
    G -- yes --> H[Deploy, then clear the cache]
    H --> I{Target reached?}
    I -- no --> D
    I -- yes --> J[Turn warnings into errors in CI]
----

[#upgrade-steps]
=== The steps in detail

. *Read.* Read the release notes of every feature release after the one you run, up to and including the target, paying
most attention to the "Backwards incompatible changes" sections, and look the same releases up in the deprecation
timeline. The <<release-summary>> above is the short version.
. *Resolve warnings first.* On the version you run today, run the test suite with `python -Wa manage.py test` and fix every
`RemovedInDjango...Warning` that comes from your own code. A warning fixed now is a crash avoided after the upgrade.
. *Go one feature release at a time.* Upgrading 4.2 to 6.1 means 4.2 → 5.0 → 5.1 → 5.2 → 6.0 → 6.1, each on its latest
patch release, rather than all the changes at once. The same incremental approach is recommended between LTS releases:
LTS to LTS is a sequence of hops, not one jump. Python moves too: 6.0 needs Python 3.12, so a project on 3.10 or 3.11
upgrades Python while it is on 5.2.
. *Upgrade the dependencies.* Most Django-related packages publish a release for each new Django version; if one has not
yet, you may have to wait or contribute the fix. PyPI classifiers often lag behind: on 2026-10-03 Channels 4.3.2,
drf-spectacular, WhiteNoise and django-tasks still listed Django 6.0 as their newest classifier, while DRF 3.18.1, Django
Ninja 1.7.1, django-debug-toolbar 8.0.0 and django-allauth already listed 6.1. A missing classifier is a reason to run the
tests, not proof of incompatibility.
. *Install in a fresh environment.* For a major upgrade create a new virtual environment, then
`python -m pip install -U "Django>=6.1,<6.2"` (or bump the pin in `pyproject.toml` and `uv lock --upgrade-package django`).
. *Test.* Run the whole suite with warnings visible, plus `manage.py check` (and `check --deploy` with production settings)
and `manage.py makemigrations --check --dry-run`, which fails if the upgrade changed a model state, as the
`DEFAULT_AUTO_FIELD` change in 6.0 does for projects that never set it.
. *Deploy and clear the cache.* Objects pickled into the cache by one Django version are not guaranteed to unpickle in
another (cached `HttpResponse` objects from `cache_page()` were a past example), so clear the cache after deploying.

Source: https://docs.djangoproject.com/en/6.1/howto/upgrade-version/[How to upgrade Django to a newer version]

[#upgrade-hop]
=== A hop through 5.2 → 6.0 → 6.1, for real

A small app written against Django 5.2 shows what each step catches. It uses two APIs deprecated in 5.1 and never sets
`DEFAULT_AUTO_FIELD`:

.hop/models.py and hop/tests.py before the upgrade
[source,python]
----
from django.db import models
from django.db.models import Q


class Loan(models.Model):
    days = models.PositiveIntegerField()

    class Meta:
        constraints = [
            models.CheckConstraint(check=Q(days__lte=60), name="loan_days_max_60"),
        ]


# hop/tests.py
from django.test import TestCase

from .models import Loan


class LoanTests(TestCase):
    def test_create(self):
        loan = Loan(days=14)
        loan.save(False, False)  # positional force_insert, force_update
        self.assertEqual(Loan.objects.count(), 1)
----

[#django-upgrade]
== django-upgrade: rewriting old code automatically

https://django-upgrade.readthedocs.io/en/latest/[django-upgrade], by Django contributor Adam Johnson and listed under
"upgrade utilities" on the official community ecosystem page, is a command-line tool that rewrites Python files so they
stop using deprecated APIs, and in a few cases adopts the newer syntax. It enables every fixer up to and including the
`--target-version` you give it; without the option it reads the minimum Django version from `project.dependencies` in
`pyproject.toml` (falling back to 2.2). It does not recurse into directories, so you hand it the file list, and it exits
with status 1 when it changed something so a CI job or pre-commit run stops for review.

[source,bash]
----
$ python -m pip install django-upgrade
$ django-upgrade --version
1.33.0
$ git ls-files -z -- '*.py' | xargs -0r django-upgrade --target-version 6.1
$ django-upgrade --check legacy/*.py          # report only, exit 1 if something would change
$ django-upgrade --list-fixers                 # names for --only / --skip
----
Source: https://django-upgrade.readthedocs.io/en/latest/usage.html[django-upgrade: Usage] and https://django-upgrade.readthedocs.io/en/latest/options.html[django-upgrade: Options]

The usual way to keep it running is a pre-commit hook placed before formatters such as Black or Ruff, because
django-upgrade "focuses on upgrading your code and not on making it look nice":

.pre-commit-config.yaml (excerpt)
[source,yaml]
----
repos:
  - repo: https://github.com/adamchainz/django-upgrade
    rev: "1.33.0"
    hooks:
      - id: django-upgrade
        args: [--target-version, "6.1"]
----
Source: https://django-upgrade.readthedocs.io/en/latest/installation.html[django-upgrade: Installation]

[#django-upgrade-limits]
=== What it left for you

Reading the diff is part of the job; four things in it need a human:

* *`request.is_ajax()` is untouched.* There is no fixer, because the right replacement depends on intent. The 3.1 release
notes give the exact equivalent, `request.headers.get("x-requested-with") == "XMLHttpRequest"`, or
`request.accepts("application/json")` if the code really cares about the `Accept` header. Note that `accepts()` returns
`True` when the client sends no `Accept` header at all (the test client sends none), so a test that expected HTML got
JSON when the scratch run first tried it.
* *`[-\w]{plus}` stays a regex.* Only regexes that exactly match a path converter (`[0-9]{plus}`, `[-a-zA-Z0-9_]{plus}`, `[^/]{plus}`, `.{plus}`, the
UUID pattern) are converted, so the `slug` route became `re_path()`. `\w` matches non-Latin letters and Django's `slug`
converter does not, so changing it to `<slug:slug>` is a behaviour change you decide on. Where a route was converted, the
view now receives an `int` instead of a `str`; test those views.
* *Model changes need migrations.* The `null_boolean_field` and `index_together` fixers change model state. Run
`makemigrations`: for `index_together` it generates a `RenameIndex` operation that keeps the existing index. Keep
`makemigrations --check` in CI so a forgotten migration fails the build.
* *Formatting is not its job.* The admin rewrite left three blank lines at the end of the file; run your formatter after it.

[#books-outdated]
== Where the books are outdated: the consolidated table

The four reference books of this section (listed in the
xref:web/django/index.adoc#_bibliography[section bibliography]) remain good at explaining *why* Django works the way it
does, and most of their concepts are still current. What has aged is specific API usage, settings, tooling and
third-party advice. The tables below collect every such statement found while writing this section, paraphrased (no book
text is reproduced), with the chapter where it appears, the version in which it changed and the current form. The topic
pages repeat the relevant rows in their own "where the books are outdated" sections with more context.

Book abbreviations used in the tables:

* *M*: Antonio Melé, _Django 2 by Example_ (Packt, 2018; Django 2.0), chapters 1-13.
* *TS*: Daniel Roy Greenfeld and Audrey Roy Greenfeld, _Two Scoops of Django 1.11_ (Two Scoops Press, 2017; Django 1.11),
chapters and section numbers as printed; "App." is an appendix.
* *Ma*: Federico Marani, _Practical Django 2 and Channels 2_ (Apress, 2019; Django 2.0/2.1, Channels 2.1), chapters 1-10.
* *V*: William S. Vincent, _Django for Beginners_ (2018; Django 2.1), chapters 1-15.

[#pitfalls]
== Pitfalls

* *Jumping several releases at once.* Each removal is announced by a warning in the two releases before it; skipping
releases skips the warnings, and the first sign is an `ImportError` or `TypeError` at start-up, as in <<upgrade-hop>>.
* *Running the tests without warnings.* Django's warnings are invisible by default; a green suite under a plain
`manage.py test` says nothing about the next release. Use `-Wa` locally and warnings-as-errors in CI.
* *Letting 6.0 change your primary keys.* A project that never set `DEFAULT_AUTO_FIELD` gets migrations altering every
implicit `id` to `bigint`. Pin `AutoField` first, then migrate deliberately if you want big integers.
* *Trusting classifiers in either direction.* A package without a 6.1 classifier may work (Channels 4.3.2 did); one with
it may still emit deprecation warnings. The test suite decides.
* *Forgetting migrations after automatic fixes.* `null_boolean_field` and `index_together` change model state;
`makemigrations --check` in CI catches the forgotten migration.
* *Accepting every rewrite blindly.* django-upgrade turns `str` URL arguments into `int` when a regex becomes `<int:pk>`
and leaves intent-dependent code (`is_ajax()`) alone; review the diff and run the tests.
* *Matching warning classes by name.* `RemovedInDjango70Warning` becomes `RemovedInDjango2028Warning` during the 6.1
series; filter on `DeprecationWarning`/`PendingDeprecationWarning` instead.
* *Keeping the old cache.* Pickled objects are not guaranteed to survive a version change; clear the cache after the
deploy.
* *Copying a book's settings file.* Several of its settings no longer exist (`MIDDLEWARE_CLASSES`, `USE_L10N`, the storage
settings), others are insecure as printed (<<books-errata>>).
