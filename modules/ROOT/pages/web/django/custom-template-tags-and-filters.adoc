== In a hurry: which helper do I need?

[mermaid]
....
flowchart TD
  A[Need something in a template] --> B{Transform one value?}
  B -- yes --> F["Filter: @register.filter"]
  B -- no --> C{Wrap a block of template content?}
  C -- yes --> D{"Only needs the rendered text?"}
  D -- yes --> SB["@register.simple_block_tag (5.2)"]
  D -- no, needs the nodes --> N["@register.tag + Node + parser.parse"]
  C -- no --> E{Output is a fragment rendered by another template?}
  E -- yes --> I["@register.inclusion_tag"]
  E -- no --> G{Plain value or small HTML from arguments?}
  G -- yes --> S["@register.simple_tag"]
  G -- no, custom syntax --> N
....

[cols="2,3,3",options="header"]
|===
| Helper | Use it when | Auto-escaping of the result

| `@register.filter`
| One value in (plus an optional argument), one value out; chainable with the pipe character; usable in `{% if %}`.
| You decide with `is_safe`, `needs_autoescape` or by returning a safe string.

| `@register.simple_tag`
| Arguments in, string out; optional `takes_context` and `as var`.
| Output goes through `conditional_escape()` when auto-escaping is on (since 1.9).

| `@register.simple_block_tag`
| `{% name %}...{% endname %}`; the rendered body arrives as `content` (5.2).
| Same as `simple_tag`; the body is already rendered and escaped.

| `@register.inclusion_tag`
| Render a separate template with data computed in Python; it is the right tool for repeated fragments.
| The included template auto-escapes as usual.

| `@register.tag` with a `Node`
| Custom syntax, access to the parsed node list, several cooperating tags, stateful rendering.
| None: you escape and mark safe yourself.
|===

[#layout]
== Where the code lives: the templatetags package

A tag library is a Python module inside a `templatetags` package of an installed app. The module name, not the app name,
is what you pass to `{% load %}`.

.Layout of the catalog app
[source,text]
----
catalog/
    __init__.py
    models.py
    views.py
    templatetags/
        __init__.py          # required: makes the directory a package
        catalog_extras.py    # {% load catalog_extras %}
    templates/
        catalog/
            _book_card.html
----

The module must define a module-level variable called `register` that is a `django.template.Library`:

.catalog/templatetags/catalog_extras.py (top of the module)
[source,python]
----
from django import template

register = template.Library()
----

Four rules cause most of the first-hour problems:

* *The app must be in `INSTALLED_APPS`.* `{% load %}` only sees libraries of installed apps (plus those listed in the
  engine's `libraries` option, below). This is by design: a host can ship the code of many apps without enabling all of
  it for every project.
* *Restart the server after creating the package.* The autoreloader watches files it already knows about; a brand new
  `templatetags` module is not picked up by `runserver` until you restart it. Editing an existing module reloads
  normally.
* *Name modules to avoid clashes.* Two apps with a `templatetags/forms.py` fight over the label `forms`; prefix the
  module with the app name (`catalog_extras`).
* *Load per template.* `{% load %}` is not inherited: a child template using `{% extends %}` must load the library
  itself, even if the parent did.

Source: https://docs.djangoproject.com/en/6.1/howto/custom-template-tags/#code-layout[How to create custom template tags and filters: Code layout]

=== Loading selectively, and the libraries and builtins options

`{% load %}` accepts a whole library or only some of its members:

.Selective load
[source,html+django]
----
{% load catalog_extras %}
{% load shout money from catalog_extras %}
----

Asking for a name the library does not provide raises `TemplateSyntaxError: 'bold_nope' is not a valid tag or filter in
tag library 'catalog_extras'`, which is useful as a typo guard.

The `DjangoTemplates` backend has two options that change how libraries are found, both in `TEMPLATES[0]["OPTIONS"]`:

.config/settings.py (excerpt)
[source,python]
----
TEMPLATES = [
    {
        "BACKEND": "django.template.backends.django.DjangoTemplates",
        "APP_DIRS": True,
        "OPTIONS": {
            "context_processors": [
                "django.template.context_processors.request",
                "django.contrib.auth.context_processors.auth",
                "django.contrib.messages.context_processors.messages",
            ],
            # label -> dotted path: load under another name, or without an app
            "libraries": {"extras": "catalog.templatetags.catalog_extras"},
            # always available, no {% load %} needed (use sparingly)
            "builtins": ["catalog.templatetags.catalog_extras"],
        },
    },
]
----

`libraries` lets a template say `{% load extras %}` and registers modules that are not in a `templatetags` package or
not in an installed app. `builtins` adds a module to the built-ins so its tags and filters work in every template without
`{% load %}`; reserve it for a handful of project-wide helpers, because it hides where a tag comes from and a name clash
with another library silently changes behaviour. Both options exist since Django 1.9. A module without a `register`
variable is rejected when the engine is built: `InvalidTemplateLibrary: Module catalog.models does not have a variable
named 'register'`.

Source: https://docs.djangoproject.com/en/6.1/topics/templates/#module-django.template.backends.django[The Django template language: configuration]

[#filters]
== Filters

A filter is a Python function taking one or two arguments: the value to the left of the pipe (any type, not necessarily a
string) and an optional argument to the right of the colon. It returns the new value. Since the template language has no
exception handling, an exception in a filter becomes a server error, so a filter should return a sensible fallback
(usually an empty string) for input that merely looks odd, and raise only for something that is clearly a bug in the
template.

.Filters: plain function, optional argument, fail-silently rule
[source,python]
----
from decimal import Decimal, InvalidOperation

from django import template
from django.template.defaultfilters import stringfilter

register = template.Library()


@register.filter
def cut(value, arg):
    """Remove every occurrence of arg from the value."""
    return value.replace(arg, "")


@register.filter
@stringfilter
def initials(value):
    """'Ursula K. Le Guin' -> 'UKLG'. Plain text in, plain text out."""
    return "".join(word[0].upper() for word in value.split() if word)


@register.filter(name="money")
def format_money(value, currency="EUR"):
    """Decimal('12.5')|money:'USD' -> '12.50 USD'; fail silently on junk."""
    try:
        return f"{Decimal(value):.2f} {currency}"
    except (InvalidOperation, TypeError, ValueError):
        return ""


@register.filter
def get_item(mapping, key):
    """{{ prices|get_item:key }} -- dictionary lookup with a variable key."""
    try:
        return mapping.get(key, "")
    except AttributeError:
        return ""
----

.Using them
[source,html+django]
----
{% load catalog_extras %}
{{ "1020"|cut:"0" }}              {# 12 #}
{{ book.author.name|initials }}   {# UKLG #}
{{ book.price|money:"USD" }}      {# 12.50 USD #}
{{ prices|get_item:isbn }}        {# variable key: impossible with the built-in dot lookup #}
----

Registration notes:

* `@register.filter` without arguments uses the function name; `@register.filter(name="money")` (or
  `register.filter("money", format_money)`) chooses another name. The second argument of `register.filter()` is the
  function itself, not its name as a string.
* A filter takes at most one argument. To pass several values, pack them in one string and split it, or write a tag.
* `@stringfilter` converts the value to `str` before calling the function, so `{{ 42|initials }}` does not fail with an
  `AttributeError`. It does not mark anything safe.
* Filters can appear anywhere a variable can, including `{% if book.price|money %}` and `{% for x in items|dictsort:"name" %}`,
  which is why they are preferred over tags for pure transformations.
* A filter is a good place for formatting and a bad place for queries. See <<stupid-templates>>.

Source: https://docs.djangoproject.com/en/6.1/howto/custom-template-tags/#writing-custom-template-filters[Writing custom template filters]

[#filters-escaping]
=== Filters and auto-escaping: is_safe, needs_autoescape and safe strings

Two kinds of strings travel through a template: plain `str` values, escaped on output when auto-escaping is on, and
`SafeString` values (the result of `mark_safe()`, `format_html()` and `escape()`), which are output as they are because
someone has already escaped them. A filter sits between the two and must say what it does to safety. There are three
situations.

*1. The filter introduces no new HTML-significant character* (`<`, `>`, `&`, `"` or `'`) that was not already in the input.
Register it with `is_safe=True`: if a safe string comes in the result stays safe, and if a plain string comes in Django
escapes it as usual.

.is_safe=True
[source,python]
----
@register.filter(is_safe=True)
@stringfilter
def ensure_period(value):
    """Append a full stop if missing; adds no HTML-unsafe character."""
    return value if value.endswith(".") else value + "."
----

[source,html+django]
----
{{ "a < b"|ensure_period }}                   {# a &lt; b. #}
{{ "<b>x</b>"|safe|ensure_period }}           {# <b>x</b>. #}
----

The flag exists because ordinary string operations (`+`, `.replace()`, slicing) turn a `SafeString` back into a plain
`str`; rather than chasing every case, Django restores safeness after the filter returns. Be careful with filters that
remove characters: dropping a `>` can turn `<a>` into `<a`, and dropping a semicolon turns `&amp;` into the invalid `&amp`,
so a "truncate" filter is not automatically safe. Also remember that `is_safe=True` coerces the return value to a
string, so it is wrong for a filter that returns a boolean or a number.

*2. The filter introduces HTML markup* of its own. It must escape the data itself, and it must do so correctly whether or
not auto-escaping is in effect, so templates inside `{% autoescape off %}` behave. Register it with
`needs_autoescape=True`; Django then passes an extra keyword argument `autoescape` (true when escaping is active).
Give it a default of `True` so a call from plain Python code escapes too.

.needs_autoescape=True
[source,python]
----
from django.utils.html import conditional_escape, format_html
from django.utils.safestring import mark_safe


@register.filter(needs_autoescape=True)
def emphasize_first(text, autoescape=True):
    """Wrap the first character in <strong>, escaping the rest correctly."""
    text = str(text)
    if not text:
        return ""
    first, rest = text[0], text[1:]
    esc = conditional_escape if autoescape else (lambda x: x)
    return format_html("<strong>{}</strong>{}", mark_safe(esc(first)), mark_safe(esc(rest)))
----

.Result with the input `<b>`
[source,html+django]
----
{{ v|emphasize_first }}                                       {# <strong>&lt;</strong>b&gt; #}
{% autoescape off %}{{ v|emphasize_first }}{% endautoescape %} {# <strong><</strong>b> #}
----

`conditional_escape()` is like `escape()` except that it leaves `SafeData` alone, so already-escaped input is not escaped
twice. When a filter returns a safe string by hand, `is_safe` makes no difference either way.

*3. The filter reuses a built-in filter* such as `urlize` or `linebreaksbr`. The built-ins default to `autoescape=True`
today; in very old Django versions the default was `None` and had to be passed explicitly, which is a source of old
XSS bugs in copied snippets. Pass `autoescape=autoescape` through, as the official example does:

.Composing built-in filters
[source,python]
----
from django.template.defaultfilters import linebreaksbr, urlize


@register.filter(needs_autoescape=True)
def urlize_and_linebreaks(text, autoescape=True):
    return linebreaksbr(urlize(text, autoescape=autoescape), autoescape=autoescape)
----

Source: https://docs.djangoproject.com/en/6.1/howto/custom-template-tags/#filters-and-auto-escaping[Filters and auto-escaping]

[#filters-timezones]
=== Filters and time zones: expects_localtime

A filter that works on aware `datetime` objects almost always wants the _local_ time, not UTC. Register it with
`expects_localtime=True` and Django converts an aware first argument to the current time zone before calling it, following
the rules for time zone conversion in templates.

.expects_localtime=True
[source,python]
----
@register.filter(expects_localtime=True)
def business_hours(value):
    """True between 09:00 and 17:00 in the current time zone."""
    try:
        return 9 <= value.hour < 17
    except AttributeError:
        return ""
----

A test pins the behaviour: 07:30 UTC is "outside business hours" in UTC (`False`) but 09:30, so inside, under
`timezone.override(ZoneInfo("Europe/Madrid"))`; a non-datetime value returns the empty string. See
xref:web/django/localization-and-time-zones.adoc[Localization & Time Zones] for how the current time zone is chosen.

Source: https://docs.djangoproject.com/en/6.1/howto/custom-template-tags/#filters-and-time-zones[Filters and time zones]

[#simple-tag]
== simple_tag: arguments in, string out

Most tags only take some arguments (strings or template variables) and return a string. `simple_tag` wraps such a
function into a compile function and a `Node` for you. Before your function runs, Django has already validated the number
and names of the arguments, stripped the quotes of literals, and resolved variables to their current values (your
function receives the value of `book`, not the string `"book"`).

.catalog/templatetags/catalog_extras.py
[source,python]
----
from django.utils.html import format_html


@register.simple_tag
def site_title():
    return "Bookshelf & Co"


@register.simple_tag
def price_badge(book, currency="EUR", css="badge"):
    return format_html(
        '<span class="{}">{} {}</span>', css, book.title, format_money(book.price, currency)
    )


@register.simple_tag(name="shout")
def make_it_loud(text, times=1):
    return text.upper() + "!" * times
----

[source,html+django]
----
{% load catalog_extras %}
<title>{% site_title %}</title>
{% price_badge book currency="USD" %}
{% shout "hi" times=3 %}                {# HI!!! #}
{% shout "hi" as loud %}<p>{{ loud }}</p>   {# stores the result instead of printing #}
----

What to remember:

* *Arguments.* Positional and keyword arguments work as in Python (`def my_tag(a, b, *args, **kwargs)`); in the template
  they are separated by spaces, keyword arguments use `name=value` and must come after the positional ones, and values
  can use filters (`warning=message|lower`).
* *`as variable`.* `{% shout "hi" as loud %}` stores the result in the context instead of printing it, so you can use it
  several times or in an `{% if %}`. The variable lives until the end of the enclosing block; Django added `as` to
  `simple_tag` in 1.9, which made the old `assignment_tag` obsolete (removed in 2.0).
* *Errors at compile time.* Wrong arguments are reported when the template is compiled, not rendered:
  `'shout' did not receive value(s) for the argument(s): 'text'` and `'shout' received unexpected keyword argument
  'bogus'`.
* *`name=`.* Rename the tag when the function name is not what you want in the template.

Source: https://docs.djangoproject.com/en/6.1/howto/custom-template-tags/#simple-tags[Simple tags]

=== takes_context

Add `takes_context=True` and the function receives the template context as its first parameter, which must be called
`context`. This is how a tag reads the `request` (from the `request` context processor), the current user or a variable
the view put in the context without the template author passing it explicitly.

.A pagination helper that keeps the other query-string parameters
[source,python]
----
@register.simple_tag(takes_context=True)
def url_replace(context, **kwargs):
    """Current query string with some keys replaced."""
    query = context["request"].GET.copy()
    for key, value in kwargs.items():
        query[key] = value
    return query.urlencode()
----

[source,html+django]
----
<a href="?{% url_replace page=2 %}">next</a>   {# /catalog/shelf/?q=dune  ->  ?q=dune&amp;page=2 #}
----

`takes_context` depends on the `django.template.context_processors.request` context processor being enabled, which the
default `startproject` settings do. A tag that silently assumes `context["request"]` exists breaks when rendered from
`render_to_string()` without a request, so use `context.get("request")` if the tag may be used in emails. `url_replace`
is the classic example from older tutorials; since 5.1 the built-in `{% querystring %}` tag does exactly this (and in 6.0 it
accepts several positional mappings and prefixes its result consistently), so write your own only for variations on it.
In the output above the ampersand is `&amp;` because `simple_tag` escapes its result.

Source: https://docs.djangoproject.com/en/6.1/howto/custom-template-tags/#simple-tags[Simple tags] and https://docs.djangoproject.com/en/6.1/ref/templates/builtins/#querystring[querystring]

[#simple-tag-escaping]
=== simple_tag output is escaped

A `simple_tag` passes its return value through `conditional_escape()` when the context has auto-escaping on (the default).
So `site_title` above, which returns `Bookshelf & Co`, renders as `Bookshelf &amp; Co` in a page and as `Bookshelf & Co`
inside `{% autoescape off %}`. A string that is already safe, such as the result of `format_html()`, is not escaped a
second time, and that is exactly why you build HTML with `format_html()`: the data goes through escaping, the markup
stays. See <<escaping>> for the details and the mistake to avoid.

[#simple-block-tag]
== simple_block_tag (Django 5.2)

Sometimes a tag has to take a _section of the template_ as its input: a warning panel around a paragraph, a code
block to highlight, a chart description. Before 5.2 that needed a `Node` and `parser.parse()` (see <<from-scratch>>);
since Django 5.2 `Library.simple_block_tag()` does it with the same ergonomics as `simple_tag`. The function gets an extra
first argument called `content`, the already-rendered text between `{% name %}` and `{% endname %}`.

.A panel that knows the site name from the context
[source,python]
----
@register.simple_block_tag(takes_context=True)
def panel(context, content, level="info", title=None):
    """{% panel level="warning" title="Heads up" %}...{% endpanel %}"""
    return format_html(
        '<div class="panel panel-{}" data-site="{}">{}{}</div>',
        level,
        context.get("site", "Bookshelf"),
        format_html("<h3>{}</h3>", title) if title else "",
        content,
    )


@register.simple_block_tag(end_name="end_sidebar")
def sidebar(content, width=200):
    return format_html('<aside style="width: {}px">{}</aside>', width, content)
----

[source,html+django]
----
{% load catalog_extras %}
{% panel level="warning" title="Heads up" %}
  Prices include <em>VAT</em> for {{ books|length }} books.
{% endpanel %}

{% sidebar width=300 %}Links{% end_sidebar %}
----

which renders (whitespace aside) as `<div class="panel panel-warning" data-site="Bookshelf"><h3>Heads up</h3>Prices
include <em>VAT</em> for 3 books.</div>`.

The rules, all verified by tests:

* *Closing tag.* `{% name %}` is closed by `{% endname %}` unless you pass `end_name`: `sidebar` above is closed with
  `{% end_sidebar %}`, and `{% endsidebar %}` is rejected with `Invalid block tag on line 1: 'endsidebar', expected
  'end_sidebar'`.
* *`content` comes first (after `context`).* With `takes_context=True` the order is `(context, content, ...)`. The names
  `context` and `content` are mandatory.
* *The body is rendered before your function runs.* Variables and tags inside it are already resolved (so
  `request.user` inside the body is the user), and, because the body is rendered by Django, it is already escaped; `<em>VAT</em>`
  above is literal template text and passes through, while `{{ name }}` inside would arrive escaped.
* *Arguments are not in the body's scope.* Unlike `{% with %}`, the arguments you pass to the tag are not added to the
  rendering context of the body: in `{% sidebar width=5 %}{{ width }}|{% end_sidebar %}` the body renders `|` only.
* *Same helpers as `simple_tag`.* Argument validation, quote stripping, escaping of the result, `takes_context`, `name`,
  any number of positional and keyword arguments and the `as variable` form all work the same way.

Before 5.2 (including the 4.2 LTS that many books still target) the same tag needs the `Node` version in
<<from-scratch>>. On 5.2 and later prefer `simple_block_tag`.

Source: https://docs.djangoproject.com/en/6.1/howto/custom-template-tags/#simple-block-tags[Simple block tags] and https://docs.djangoproject.com/en/6.1/releases/5.2/#templates[Django 5.2 release notes: Templates]

[#inclusion-tag]
== inclusion_tag: render a fragment from Python data

An inclusion tag renders _another template_ with a dictionary your function returns. The template is fixed by the tag
author, not chosen by the template designer, which makes inclusion tags the right tool for fragments that are repeated
with different data (a book card, the buttons of a form, a pager, a breadcrumb). Django's admin uses them for the
`submit_row` buttons.

.Function, registration and fragment
[source,python]
----
@register.inclusion_tag("catalog/_book_card.html")
def book_card(book, show_price=True):
    return {"book": book, "show_price": show_price}
----

.catalog/templates/catalog/_book_card.html
[source,html+django]
----
<article class="card">
  <h2>{{ book.title }}</h2>
  <p>by {{ book.author }}</p>
  {% if show_price %}<p class="price">{{ book.price }}</p>{% endif %}
</article>
----

[source,html+django]
----
{% load catalog_extras %}
{% for book in books %}
  {% book_card book show_price=False %}
{% endfor %}
----

The returned dictionary is the _entire_ context of the fragment: it does not see the surrounding page's variables, which
is the point, because it makes the tag a self-contained component. Auto-escaping applies as in any template, so a title
like `Dune & co` renders as `Dune &amp; co`. Details worth knowing:

* *`takes_context`.* With `takes_context=True` the function takes only `context` and the tag takes no arguments; use it
  when the fragment is always rendered where certain variables exist.
+
[source,python]
----
@register.inclusion_tag("catalog/_user_badge.html", takes_context=True)
def user_badge(context):
    request = context["request"]
    return {"name": request.user.get_username() or "anonymous"}
----
* *Arguments.* Positional and keyword arguments work as for `simple_tag` (`{% book_card book show_price=False %}`).
* *Template argument.* Besides a template name, `inclusion_tag()` accepts a `Template` object (for example from
  `get_template()`), or an iterable of names from which the first existing template is selected.
* *CSRF.* Django copies `csrf_token` from the calling context into the inclusion template's context, so a fragment can
  contain a form with `{% csrf_token %}` and it works without extra plumbing. The test posts a search form through the tag
  and asserts that `csrfmiddlewaretoken` is in the page.
+
[source,python]
----
@register.inclusion_tag("catalog/_search_form.html")
def search_form(action):
    return {"action": action}
----
+
[source,html+django]
----
<form method="post" action="{{ action }}">{% csrf_token %}<input name="q"><button>Search</button></form>
----
* *The template is cached per render.* Django caches the compiled fragment in the `render_context`, so using a tag in a
  `{% for %}` loop does not reload and reparse the template for every item.
* *Everything else is lost.* The fragment does not see the context processors' variables (`request`, `user`, `perms`; verified: `{{ user }}` is empty inside)
  unless the function passes them in the dictionary.

Source: https://docs.djangoproject.com/en/6.1/howto/custom-template-tags/#inclusion-tags[Inclusion tags]

=== The cost of an inclusion tag that queries

An inclusion tag that runs a query is invoked once per use. The test below renders `{% latest_books 1 %}` five times in a
loop and counts exactly five queries, against one for a single use:

[source,python]
----
@register.inclusion_tag("catalog/_latest.html")
def latest_books(count=3):
    return {"books": Book.objects.select_related("author").order_by("-id")[:count]}
----

[source,python]
----
with self.assertNumQueries(1):
    render("{% latest_books 3 %}")
with self.assertNumQueries(5):  # one query per use: this is the cost
    render("{% for b in range4 %}{% latest_books 1 %}{% endfor %}", range4=range(5))
----

That is acceptable for a sidebar that appears once per page and a trap inside a loop. Pass the data from the view or use
`prefetch_related` there whenever the tag will be repeated; see xref:web/django/query-optimization-and-fetch-modes.adoc[Query Optimization & Fetch Modes].

Source: https://docs.djangoproject.com/en/6.1/howto/custom-template-tags/#inclusion-tags[Inclusion tags] and https://docs.djangoproject.com/en/6.1/topics/testing/tools/#django.test.TransactionTestCase.assertNumQueries[assertNumQueries]

[#escaping]
== Escaping: mark_safe versus format_html

Auto-escaping is the template language's main defence against cross-site scripting (XSS), and custom tags and filters are
where it is most often defeated by accident: you hand-build HTML in Python, mark it safe, and the data inside it is no
longer escaped. The rules are short.

* *Plain strings are escaped on output; safe strings are not.* `mark_safe()` _asserts_ that a string is safe, it does not
  make it safe. It is only correct for a literal you wrote or for content you have escaped yourself.
* *`format_html()` is `str.format()` with escaping.* The format string is trusted markup; every argument is passed through
  `conditional_escape()` first; the result is marked safe. Safe arguments pass through untouched, so nesting works.
* *Prefer `format_html()`, `format_html_join()` and templates* to string concatenation, f-strings or `%` formatting
  followed by `mark_safe()`.
* *Anything that removes characters from a safe string makes it unsafe again.* `.strip()`, slicing and `.replace()` return
  a plain `str`; `mark_safe()` can be applied again only if the result is genuinely safe.

The two filters below do the same job; only one is correct. The test feeds both `<script>alert(1)</script>`:

.The bug and the fix
[source,python]
----
@register.filter
def bold_unsafe(value):
    return mark_safe(f"<b>{value}</b>")  # BUG: value is not escaped


@register.filter
def bold(value):
    return format_html("<b>{}</b>", value)  # value escaped unless already safe


@register.simple_tag
def unsafe_greeting(name):
    return mark_safe(f"Hello <i>{name}</i>")  # BUG: do not do this
----

Rendered in a shell with the value `<script>alert(1)</script>`:

[source,text]
----
<b><script>alert(1)</script></b> | <b>&lt;script&gt;alert(1)&lt;/script&gt;</b> | Hello <i><script>alert(1)</script></i>
----

The first and third outputs execute the attacker's script; the second is inert text. `format_html("<b>{}</b>", mark_safe(x))`
still lets a genuinely safe `x` through, which is how you compose trusted fragments. Note that `format_html()` uses
`str.format()` placeholders (`+{}+` and `+{name}+`), but because every argument is converted with `force_str()`, format
specs such as number formatting do not work: format numbers before passing them in.

For lists of items use `format_html_join(sep, format_string, args_generator)`. The separator is escaped too, and since
Django 5.2 the generator may yield mappings that are passed to `format_html()` as keyword arguments:

[source,python]
----
from django.utils.html import format_html_join


@register.simple_tag
def author_list(authors):
    return format_html_join(
        ", ", '<a href="/authors/{}/">{}</a>', ((a.pk, a.name) for a in authors)
    )
----

With authors `A & B` and `<C>` the tag returns `<a href="/authors/1/">A &amp; B</a>, <a href="/authors/2/">&lt;C&gt;</a>`.

Other places where safeness is lost or granted, all worth a code-review question:

* *The `|safe` filter and `{% autoescape off %}`* in a template turn escaping off for a value or a region. If a filter's
  contract is "returns HTML", the template should not need `|safe` at all.
* *`simple_tag` and `simple_block_tag` escape* unsafe output, so returning a plain `"<b>x</b>"` shows the tags as text.
  Return `format_html(...)` (or `mark_safe` of a constant) when you do mean HTML.
* *Tags written with `Node.render()` are not escaped for you* (<<from-scratch-escaping>>).
* *Storing a result in a context variable* (`as var`) keeps its safeness; rendering the variable later applies the
  auto-escape setting in effect at that time. A custom `Node` that stores a value in the context must call `mark_safe()`
  itself when appropriate.
* *`json_script`.* To hand data to JavaScript do not build `<script>` text by hand; use the built-in `json_script`
  filter, which escapes `<`, `>` and `&` as Unicode escapes.

Source: https://docs.djangoproject.com/en/6.1/ref/utils/#module-django.utils.html[django.utils.html] and https://docs.djangoproject.com/en/6.1/ref/utils/#module-django.utils.safestring[django.utils.safestring]; background in https://docs.djangoproject.com/en/6.1/ref/templates/language/#automatic-html-escaping[Automatic HTML escaping]. The security angle (XSS, CSP) continues in xref:web/django/security.adoc[Security].

[#from-scratch]
== Tags from scratch: compile function and Node

The helpers above cover most needs. Write a tag from scratch when you need custom syntax (`{% alternate "a" "b" %}`), access
to the unrendered node list of a block (to render it zero, one or many times, or conditionally), or several cooperating
tags. Template processing has two steps. At _compile_ time the parser calls your compile function with the `parser` and the
`token` for the tag; it must return a `Node`. At _render_ time Django calls `node.render(context)` on every node and joins
the results. Compiling happens once per template (when it is loaded or cached); rendering happens on every request.

=== The compile function and the Node

.A hand-written, thread-safe cycle
[source,python]
----
import itertools

from django import template


class AlternateNode(template.Node):
    def __init__(self, values):
        self.values = values  # parsed once; never mutated at render time

    def render(self, context):
        if self not in context.render_context:
            context.render_context[self] = itertools.cycle(self.values)
        return next(context.render_context[self])


@register.tag
def alternate(parser, token):
    """{% alternate "odd" "even" %} -- a hand-rolled, thread-safe {% cycle %}."""
    bits = token.split_contents()[1:]
    if len(bits) < 2:
        raise template.TemplateSyntaxError(
            "%r tag requires at least two arguments" % token.contents.split()[0]
        )
    values = [bit[1:-1] for bit in bits if bit[0] == bit[-1] and bit[0] in "\"'"]
    if len(values) != len(bits):
        raise template.TemplateSyntaxError("%r arguments must be quoted" % bits[0])
    return AlternateNode(values)
----

[source,html+django]
----
{% for book in books %}<tr class="{% alternate "odd" "even" %}">...</tr>{% endfor %}
{# rows: odd, even, odd, ... and the first row is "odd" again on the next render #}
----

Points from the official guide that the example follows:

* *`token.split_contents()`, not `token.contents.split()`.* It keeps quoted strings together. The tag name is the first
  element.
* *Raise `TemplateSyntaxError` with a helpful message*, and use `token.contents.split()[0]` rather than a hard-coded name
  so the message survives renaming the tag.
* *Pass everything the node needs to `+__init__+`.* Parsing is done once, so keep parse-time data in attributes.
* *`render()` returns a string*, always (an empty string if the tag only sets a variable), and should normally fail
  silently in production: raise only when `context.template.engine.debug` is true or for a clear syntax problem.
* *Register* with `register.tag("name", func)` or as a decorator, `@register.tag` or `@register.tag(name="alternate")`;
  without a name the function name is used.

=== Thread safety: never store render state on the node

A compiled template is shared by every thread (and, under ASGI, every concurrent request) that renders it, so a `Node`
instance must be treated as read-only after `+__init__+`. State that changes while rendering, like the position of a
cycle, belongs in `context.render_context`, which behaves like a dictionary scoped to the template currently being rendered.
Use `self` as the key so two nodes of the same class in one template do not clobber each other. Storing the iterator on the
node (`self.cycle_iter = itertools.cycle(...)` in `+__init__+`) would make two simultaneous renderings share one cycle. The
tests render the same compiled template twice and assert that both runs start at `odd`.

=== Parsing until another tag: blocks with a node list

For a block tag use `parser.parse(("endname",))` to collect the nodes up to the closing tag, then
`parser.delete_first_token()` to consume the closing tag itself. The node list can then be rendered, with
`self.nodelist.render(context)`, as often (or never) as you like. Variable arguments are compiled with
`parser.compile_filter(bit)`, which returns a `FilterExpression` you resolve at render time with `.resolve(context)`
(this is how filters in the argument, `limit|add:1`, keep working).

.A block tag that clips its body, optionally storing the result
[source,python]
----
class ClipNode(template.Node):
    def __init__(self, nodelist, limit, var_name):
        self.nodelist = nodelist
        self.limit = limit  # a FilterExpression: literal or variable
        self.var_name = var_name

    def render(self, context):
        try:
            limit = int(self.limit.resolve(context))
        except (TypeError, ValueError, template.VariableDoesNotExist):
            return ""
        text = self.nodelist.render(context)  # already auto-escaped output
        clipped = text if len(text) <= limit else text[: limit - 1] + "…"
        if self.var_name:
            context[self.var_name] = clipped
            return ""
        return clipped


@register.tag
def clip(parser, token):
    """{% clip 20 %}...{% endclip %} or {% clip n as short %}...{% endclip %}"""
    bits = token.split_contents()
    tag_name = bits[0]
    var_name = None
    if len(bits) == 4 and bits[2] == "as":
        var_name = bits[3]
    elif len(bits) != 2:
        raise template.TemplateSyntaxError(
            "%r takes a limit and an optional 'as name'" % tag_name
        )
    limit = parser.compile_filter(bits[1])
    nodelist = parser.parse(("endclip",))
    parser.delete_first_token()
    return ClipNode(nodelist, limit, var_name)
----

[source,html+django]
----
{% clip 6 %}Hello, world{% endclip %}                          {# Hello… #}
{% clip n as short %}Hello, world{% endclip %}<{{ short }}>    {# <Hel…> with n=4 #}
----

Setting a variable in the context is plain assignment, `context[self.var_name] = value`, and the variable is visible only
in the template block where it was assigned (a scoping rule that prevents clashes between blocks). Let the template author
choose the name (`as name`) rather than hard-coding one, and return `""` from `render()`. Because the body is rendered
_before_ it is clipped, `{% clip 100 %}{{ v }}{% endclip %}` with `v="<b>"` yields `&lt;b&gt;`: clipping a rendered string
can cut an entity in half, which is a good reason to keep such tags for plain-text output or to clip the data in the
filter before it is escaped.

Source: https://docs.djangoproject.com/en/6.1/howto/custom-template-tags/#advanced-custom-template-tags[Advanced custom template tags]

[#from-scratch-escaping]
=== Auto-escaping inside a hand-written Node

A `Node` that returns a string from `render()` is _not_ auto-escaped, unlike `simple_tag`. Escape every piece of data you
put into the output (`format_html()`, `conditional_escape()`), and if the node renders a sub-template, create the new
`Context` with `autoescape=context.autoescape` so `{% autoescape off %}` regions are respected:

[source,python]
----
def render(self, context):
    t = context.template.engine.get_template("small_fragment.html")
    return t.render(Context({"var": obj}, autoescape=context.autoescape))
----

Source: https://docs.djangoproject.com/en/6.1/howto/custom-template-tags/#auto-escaping-considerations[Auto-escaping considerations]

[#stupid-templates]
== Design guidance: keep templates "stupid"

Custom tags are powerful enough to undo the reason the template language is restricted. A few rules, which agree with the
advice in books such as _Two Scoops of Django_ and with the Django design philosophy of keeping logic out of templates:

* *Prefer a filter to a tag* for a pure transformation of one value, and prefer a model method or property
  (`book.display_price`) when the logic belongs to the data.
* *Do not query in a filter or a tag that can run in a loop.* Compute in the view or the model layer (annotations,
  `select_related`, `prefetch_related`) and pass results in. A tag that queries once per page (a "latest books" sidebar)
  is fine; the same tag inside a loop is the N+1 problem hidden behind a pretty name.
* *Let the view decide, let the template present.* A tag that makes business decisions (permissions, pricing) is hard to
  test and easy to bypass; a tag that formats and arranges is not.
* *Prefer a template to Python HTML.* If a tag builds more than a line of markup, make it an inclusion tag (or a
  template partial, see xref:web/django/template-partials-and-htmx.adoc[Template Partials & htmx]) so designers can edit
  the markup.
* *Reach for a built-in first.* `{% querystring %}` (5.1), `{% partialdef %}` (6.0), `{% csp_nonce_attr %}` (6.1), `json_script`,
  `escapeseq` (5.0) and `{% include %}` with `only` cover many cases that older articles solve with custom tags.
* *Document the arguments* with a docstring and keep the library small: one library per concern, named for the app.

Jinja2 is different: the Jinja2 backend has no `Library`; you add _globals_, _filters_ and _extensions_ to the Jinja
environment instead. Custom tags and filters written for this page work only with the `DjangoTemplates` backend (see
xref:web/django/templates.adoc[Templates] for Jinja2 and custom backends).

[#async]
== Sync and async behaviour

Template rendering is synchronous and so are tag and filter functions: Django does not support `async def` tags or
filters. That matters in an async view because a tag that touches the ORM runs in the event-loop thread and Django
refuses a synchronous database call there. The two tests below hit the same `latest_books` inclusion tag from an async view:

[source,python]
----
from asgiref.sync import sync_to_async
from django.shortcuts import render


async def latest_async_bad(request):
    return render(request, "catalog/latest_page.html")  # tag queries inside the event loop


async def latest_async_ok(request):
    return await sync_to_async(render)(request, "catalog/latest_page.html")
----

The first raises `SynchronousOnlyOperation` (the test asserts it); the second, which runs the whole rendering in a worker
thread, returns 200. The better design is to load the data with the async ORM in the view and pass it in the context, so
no tag needs the database. See xref:web/django/async-support.adoc[Async Support] for the rules of async views and the
`sync_to_async` bridge.

Source: https://docs.djangoproject.com/en/6.1/topics/async/#async-safety[Asynchronous support: async-safety]

[#testing]
== Testing tags and filters

There are three levels, and each is cheap because none needs a running server.

*1. Call the function directly.* Filters and tag functions are ordinary Python functions. Most filters need only
`SimpleTestCase`, which does not touch the database:

[source,python]
----
from decimal import Decimal

from django.test import SimpleTestCase
from django.utils.safestring import SafeString

from catalog.templatetags import catalog_extras as tags


class FilterTests(SimpleTestCase):
    def test_cut_and_initials_are_plain_functions(self):
        self.assertEqual(tags.cut("a-b-c", "-"), "abc")
        self.assertEqual(tags.initials("Ursula K. Le Guin"), "UKLG")
        self.assertEqual(tags.initials(42), "4")  # stringfilter coerces

    def test_return_types(self):
        self.assertIsInstance(tags.bold("x"), SafeString)
        self.assertNotIsInstance(tags.cut("x", "y"), SafeString)
----

*2. Render a template string.* This exercises registration, argument parsing, escaping and `{% load %}`. A small helper
keeps tests short:

[source,python]
----
from django.template import Context, Template


def render(source, **context):
    return Template("{% load catalog_extras %}" + source).render(Context(context))


class EscapingTests(SimpleTestCase):
    attack = "<script>alert(1)</script>"

    def test_format_html_escapes(self):
        out = render("{{ v|bold }}", v=self.attack)
        self.assertNotIn("<script>", out)
        self.assertEqual(out, "<b>&lt;script&gt;alert(1)&lt;/script&gt;</b>")

    def test_simple_tag_escapes_plain_output(self):
        self.assertEqual(render("{% site_title %}"), "Bookshelf &amp; Co")
        self.assertEqual(
            render("{% autoescape off %}{% site_title %}{% endautoescape %}"), "Bookshelf & Co"
        )

    def test_wrong_arguments_raise_at_compile_time(self):
        with self.assertRaisesMessage(TemplateSyntaxError, "received unexpected keyword argument"):
            render("{% shout 'x' bogus=1 %}")

    def test_takes_context_url_replace(self):
        request = RequestFactory().get("/books/", {"q": "dune", "page": "1"})
        out = render("{% url_replace page=3 %}", request=request)
        self.assertEqual(sorted(out.split("&amp;")), ["page=3", "q=dune"])
----

Always include at least one test with hostile input (`<script>`, `&`, quotes) for every filter or tag that produces HTML,
one with `{% autoescape off %}` for filters that declare `needs_autoescape`, and one for the fail-silently path.

*3. Go through a view.* Use the test client with a real template to prove that the library is loaded, the app is
installed and the fragment appears in the page:

[source,python]
----
class ViewTests(TestCase):
    def test_shelf_page(self):
        r = self.client.get("/catalog/shelf/?q=x")
        self.assertContains(r, "<title>Bookshelf &amp; Co</title>")
        self.assertContains(r, 'class="odd"')
        self.assertContains(r, 'href="?q=x&amp;page=2"')
        self.assertContains(r, 'name="csrfmiddlewaretoken"')  # reached the inclusion template
----

Use `assertNumQueries()` for tags that touch the database (as in <<inclusion-tag>>), `assertInHTML()` when whitespace
and attribute order should not matter, and the `Engine(libraries=..., builtins=...)` constructor to test the registration
options in isolation. To test a library without installing its app, build an engine:

[source,python]
----
from django.template import Context, Engine

engine = Engine(libraries={"extras": "catalog.templatetags.catalog_extras"})
assert engine.from_string("{% load extras %}{% shout 'a' %}").render(Context()) == "A!"
----

See xref:web/django/testing.adoc[Testing] for the test runner, `RequestFactory` and the rest of the toolbox.

Source: https://docs.djangoproject.com/en/6.1/topics/testing/tools/#django.test.SimpleTestCase.assertInHTML[Testing tools] and https://docs.djangoproject.com/en/6.1/topics/testing/tools/#django.test.TransactionTestCase.assertNumQueries[assertNumQueries]

[#errors]
== Common errors and how to read them

[cols="3,4",options="header"]
|===
| Message | Cause

| `Invalid block tag on line 1: 'shout'. Did you forget to register or load this tag?`
| The template has no `{% load catalog_extras %}` (or `{% extends %}` child did not repeat it), or the tag is registered under another name.

| `'nope' is not a registered tag library. Must be one of: ...`
| The module name is wrong, the app is not in `INSTALLED_APPS`, the `templatetags` package has no `+__init__.py+`, or the server was not restarted after creating the package. The message lists every available library.

| `'shout' did not receive value(s) for the argument(s): 'text'`
| A required argument is missing from a `simple_tag`, `simple_block_tag` or `inclusion_tag` call; reported at compile time.

| `'shout' received unexpected keyword argument 'bogus'`
| A keyword the function does not accept.

| `Invalid block tag on line 1: 'endsidebar', expected 'end_sidebar'`
| A `simple_block_tag` registered with `end_name`; close it with that name.

| `InvalidTemplateLibrary: Module catalog.models does not have a variable named 'register'`
| A module listed in `libraries` or `builtins` does not define `register = template.Library()`.

| `'bold_nope' is not a valid tag or filter in tag library 'catalog_extras'`
| `{% load bold_nope from catalog_extras %}` names a member the library does not have.

| `SynchronousOnlyOperation`
| A tag or filter used the ORM while an async view was rendering the template. See <<async>>.
|===

[#where-books-outdated]
== Where the books are outdated

The four books consulted for this section predate Django 4 to 6 and, where they cover custom tags at all, do so briefly
(typically a `simple_tag` and an `inclusion_tag` for a blog sidebar, plus a Markdown filter). What to correct when you
meet the same material:

* *`assignment_tag`.* Old text uses `@register.assignment_tag` to store a result in a variable. It was deprecated in 1.9,
  when `simple_tag` gained `as variable`, and removed in 2.0. Use `simple_tag`.
* *`simple_tag` and escaping.* Before Django 1.9 `simple_tag` output was not escaped, so the snippets in older articles
  that return user data directly were XSS holes. Today the output is escaped unless safe; do not "fix" this by adding
  `mark_safe`.
* *`mark_safe` everywhere.* Tutorials often build HTML with `%` or f-strings plus `mark_safe()`. Use `format_html()` and
  `format_html_join()`; calling `format_html()` with no arguments was deprecated in 5.0 and raises `TypeError` since 6.0, so
  `format_html("<b>x</b>")` must become `mark_safe("<b>x</b>")` or a plain template.
* *`add_to_builtins()`.* The old private way to make tags available without `{% load %}` was formalised in 1.9 as the
  `builtins` option of the engine.
* *`{% load staticfiles %}` and `admin_static`.* Libraries removed in 3.0; use `{% load static %}`.
* *`ifequal`/`ifnotequal`* (removed in 4.0) and *`length_is`* (deprecated in 4.2, removed in 5.1) appear in examples that
  show custom filters replacing them; use `{% if a == b %}` and `{{ x|length }}`.
* *Python 2 idioms.* `from __future__`, `unicode`, `django.utils.encoding.force_text` (removed in 4.0) and
  `python_2_unicode_compatible` (removed in 3.0) are gone; strings are `str`.
* *No block tags without `Node`.* Before 5.2 a tag that wraps template content had to be written with `parser.parse()`;
  `simple_block_tag` is the modern shortcut.
* *Hand-rolled pagination links.* A `url_replace`-style tag to preserve query strings (found in many tutorials) can be
  replaced by `{% querystring %}` (5.1).
* *Markdown filters.* Django no longer ships a Markdown filter, so books that show one are showing a third-party package
  or a custom filter. A custom Markdown filter must return the converted HTML
  as a safe string only if the renderer sanitises raw HTML, so prefer a sanitising library over `mark_safe(markdown(text))`
  on user content.
* *Thread safety.* Books that cache an iterator or counter on the `Node` produce the cross-request bugs described above;
  use `render_context`.

[#checklist]
== Pitfalls checklist

* The `templatetags` directory has an `+__init__.py+`, its app is in `INSTALLED_APPS`, and the server was restarted.
* Every template that uses a tag has its own `{% load ... %}`, including children of `{% extends %}`.
* The module defines `register = template.Library()` at module level.
* Filters return a fallback instead of raising for odd input.
* `is_safe=True` only when no HTML-significant character can be introduced, and never for non-string results.
* `needs_autoescape=True` filters accept `autoescape=True` and escape with `conditional_escape()`.
* HTML is built with `format_html()` or `format_html_join()`; `mark_safe()` only on constants or already-escaped strings.
* No render-time state on a `Node`; use `context.render_context[self]`.
* Hand-written `Node.render()` escapes its output and passes `autoescape=context.autoescape` to new contexts.
* No queries in tags or filters that can run in a loop; no ORM in tags rendered inside async views.
* Tests cover hostile input, `{% autoescape off %}`, bad arguments and the full view.
