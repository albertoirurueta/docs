[#in-a-hurry]
== In a hurry: what goes where

[cols="2,4,3",options="header"]
|===
| Need | Rule of thumb | Section

| Pick a library
| Strawberry-Django for new projects (typed, async-capable, maintained); Graphene-Django only for existing schemas.
| <<choosing>>

| Expose a model
| `@strawberry_django.type(Model)` with `auto` annotations; list the fields you expose, never "all".
| <<types>>

| List, filter, sort, page
| `strawberry_django.field()` on the root type; `filter_type`, `order_type` and `pagination=True` on the type.
| <<queries>>

| Change data
| `mutations.create`/`update` for plain CRUD, `@strawberry_django.mutation(handle_django_errors=True)` for logic.
| <<mutations>>

| Restrict access
| Permission extensions (`IsAuthenticated`, `HasPerm`, ...) on fields and mutations; the user comes from the session.
| <<permissions>>

| Serve it
| `AsyncGraphQLView` under ASGI; GraphiQL only when `DEBUG`; keep CSRF on for cookie sessions.
| <<serving>>

| Stop N+1
| Always add `DjangoOptimizerExtension`; DataLoaders for computed fields; `FETCH_RAISE` as a guard.
| <<n-plus-1>>

| Test
| `strawberry_django.test.client.TestClient` plus `assertNumQueries` for every list query.
| <<testing>>
|===

[#request-cycle]
== Where GraphQL sits in the request cycle

A GraphQL endpoint is one ordinary Django URL. The request goes through the whole middleware stack first, so sessions,
authentication and CSRF protection have already run when the GraphQL view sees it; the view then parses the document,
validates it against the schema and executes it, calling one resolver per selected field. Strawberry-Django's resolvers
turn the root fields into QuerySets and the nested fields into attribute access on model instances -- which is exactly
where an unoptimized schema issues one SQL query per object.

.A GraphQL request through Django
[mermaid]
----
sequenceDiagram
    autonumber
    participant C as Client
    participant M as Middleware stack
    participant V as GraphQL view
    participant S as Schema and resolvers
    participant D as Database
    C->>M: POST /graphql/ with query and variables
    M->>M: sessions, CSRF check, request.user
    M->>V: HttpRequest
    V->>V: parse and validate the document
    V->>S: execute with context (request, response)
    S->>S: optimizer reads the selection set
    S->>D: one QuerySet per root field (JOINs and prefetches)
    D-->>S: rows
    S-->>V: data and errors
    V-->>C: 200 JSON {"data": ..., "errors": ...}
----

Two consequences follow. First, everything Django already gives a view -- `request.user`, the session, the CSRF check,
middleware such as `LoginRequiredMiddleware` -- applies to the GraphQL view as well, and nothing needs to be reinvented
in resolvers. Second, a GraphQL response is normally HTTP 200 even when a field failed: errors are reported in the
`errors` key or, with Strawberry-Django's error handling, as typed payloads (see <<mutations>>). Monitoring that only
looks at status codes will miss them.

Source: https://strawberry.rocks/docs/integrations/django[Strawberry: Django integration] and
https://docs.djangoproject.com/en/6.1/topics/http/middleware/[Django middleware]

[#choosing]
== Choosing a library

Three Python projects can serve GraphQL from Django. They all run on `graphql-core`, so the wire format and the GraphiQL
experience are the same; they differ in how you declare the schema and how much of the ORM they understand.

[cols="2,3,3,3",options="header"]
|===
| | Strawberry (plain) | Strawberry-Django | Graphene-Django

| Package
| `strawberry-graphql`
| `strawberry-graphql-django` (installs Strawberry)
| `graphene-django` (installs Graphene)

| Schema style
| Code-first, type annotations
| Code-first, type annotations plus model introspection (`auto`)
| Code-first, `DjangoObjectType` subclasses with an inner `Meta`

| Views
| `GraphQLView` and `AsyncGraphQLView`
| The same views
| `GraphQLView` (sync)

| ORM support
| None: you write every resolver
| Types, filters, ordering, pagination, CRUD mutations, permissions, query optimizer
| Types and filtering (via django-filter); no optimizer

| Latest release (2026-10-03)
| 0.329.0, 2026-10-02
| 0.92.0, 2026-10-01
| 3.2.3, 2025-03-13
|===

The rest of this page uses Strawberry-Django: it is the integration that Strawberry's own documentation recommends for
models, it declares support for Django 5.2 and 6.0 (6.0 since 0.68.0, 2025-12-03), and its optimizer solves the N+1 problem without hand-written prefetching.
<<graphene>> shows the same API in Graphene-Django for teams maintaining one.

Source: https://strawberry.rocks/docs/django[Strawberry-Django documentation],
https://pypi.org/project/strawberry-graphql-django/[strawberry-graphql-django on PyPI] and
https://pypi.org/project/graphene-django/[graphene-django on PyPI]

[#installing]
== Installing and wiring Strawberry-Django

Install the package into the project's virtual environment; it pulls in `strawberry-graphql` and `graphql-core`.

[source,bash]
----
$ python -m pip install strawberry-graphql-django
$ python -m pip list | grep -i -E "strawberry|graphql-core"
graphql-core              3.3.0
strawberry-graphql        0.329.0
strawberry-graphql-django 0.92.0
----

Add `strawberry_django` to `INSTALLED_APPS` -- it provides the GraphiQL template and the `export_schema` management
command -- and, optionally, tune the integration with the `STRAWBERRY_DJANGO` setting:

.config/settings.py (excerpt)
[source,python]
----
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",
    "strawberry_django",
    "catalog",
]

STRAWBERRY_DJANGO = {
    "FIELD_DESCRIPTION_FROM_HELP_TEXT": True,       # help_text -> field description
    "TYPE_DESCRIPTION_FROM_MODEL_DOCSTRING": True,  # model docstring -> type description
    "PAGINATION_DEFAULT_LIMIT": 20,                 # when the client sends no limit
    "PAGINATION_MAX_LIMIT": 100,                    # hard cap, also for limit: null
}
----

The two description switches are off by default because existing models often have docstrings written for developers,
not API consumers; turn them on only if your `help_text` and docstrings are fit to publish. Both pagination keys default
to `100`. Other keys set the default argument name of the CRUD mutations (`MUTATIONS_DEFAULT_ARGUMENT_NAME`, `"data"`),
whether mutations handle Django errors by default (`MUTATIONS_DEFAULT_HANDLE_ERRORS`, `False`) and the name of the
primary-key argument of single-object fields (`DEFAULT_PK_FIELD_NAME`, `"pk"`).

Source: https://strawberry.rocks/docs/django[Strawberry-Django: Quick Start] and
https://strawberry.rocks/docs/django/guide/settings[Strawberry-Django: Settings]

[#models]
== The Bookshelf models

The examples use three models in a `catalog` app: an author writes many books, and a reader (the user model) reviews a
book with a rating from 1 to 5, enforced by a check constraint.

.catalog/models.py
[source,python]
----
from django.conf import settings
from django.db import models


class Author(models.Model):
    """A person who wrote one or more books."""

    name = models.CharField(max_length=200, help_text="Full name as printed on the cover")

    def __str__(self):
        return self.name


class Book(models.Model):
    """A book in the shelf."""

    title = models.CharField(max_length=200)
    isbn = models.CharField(max_length=13, unique=True)
    published = models.DateField()
    author = models.ForeignKey(Author, on_delete=models.CASCADE, related_name="books")

    def __str__(self):
        return self.title


class Review(models.Model):
    """A reader's opinion of a book."""

    book = models.ForeignKey(Book, on_delete=models.CASCADE, related_name="reviews")
    reader = models.ForeignKey(
        settings.AUTH_USER_MODEL, on_delete=models.CASCADE, related_name="reviews"
    )
    rating = models.PositiveSmallIntegerField()
    body = models.TextField(blank=True)
    created = models.DateTimeField(auto_now_add=True)

    class Meta:
        constraints = [
            models.CheckConstraint(
                condition=models.Q(rating__gte=1, rating__lte=5),
                name="review_rating_1_to_5",
            ),
        ]
----

Source: https://docs.djangoproject.com/en/6.1/topics/db/models/[Models] and
https://docs.djangoproject.com/en/6.1/ref/models/constraints/#checkconstraint[CheckConstraint]

[#types]
== Types from models

`@strawberry_django.type(Model)` turns a class into a GraphQL object type backed by that model. Fields annotated with
`strawberry.auto` take their GraphQL type from the model field (`CharField` becomes `String!`, `DateField` becomes `Date!`,
a nullable column becomes a nullable type), and relations are annotated with the related GraphQL type: a `ForeignKey`
with the type itself, a reverse foreign key or many-to-many with a `list[...]`. Only the attributes you declare are
exposed -- there is no "all fields" switch, which keeps a new `password_hash` column from leaking into the API by accident.

.catalog/types.py (object types)
[source,python]
----
import strawberry
import strawberry_django
from strawberry import auto

from . import models


@strawberry_django.type(models.Author)
class AuthorType:
    id: auto
    name: auto
    books: list["BookType"]


@strawberry_django.type(
    models.Book, filters=BookFilter, ordering=BookOrder, pagination=True
)
class BookType:
    id: auto
    title: auto
    isbn: auto
    published: auto
    author: AuthorType
    reviews: list["ReviewType"]


@strawberry_django.type(models.Review)
class ReviewType:
    id: auto
    rating: auto
    body: auto
    created: auto
    book: BookType
----

`BookFilter` and `BookOrder` are defined just above these types (see <<queries>>). The `reader` foreign key is
deliberately left out of `ReviewType`: a public API has no business listing which user wrote what. The
`export_schema` command prints the SDL that these classes produce, which is worth committing and diffing in code review:

[source,bash]
----
$ python manage.py export_schema catalog.schema --path schema.graphql
$ grep -A6 '^type AuthorType' schema.graphql
"""A person who wrote one or more books."""
type AuthorType {
  id: ID!

  """Full name as printed on the cover"""
  name: String!
  books(filters: BookFilter, ordering: [BookOrder!]! = [], pagination: OffsetPaginationInput): [BookType!]!
}
----

The descriptions come from the model docstring and `help_text` because of the two settings above, and `AuthorType.books`
gained `filters`, `ordering` and `pagination` arguments because `BookType` declares them: a nested list is filterable
exactly like a root list. The model docstring is also copied onto input types built from the same model (`BookFilter`
is described as "A book in the shelf."), one more reason to keep docstrings user-facing when the switch is on.

`strawberry_django.input(Model)` and `strawberry_django.partial(Model)` build input types the same way: `input` keeps the
model's required fields required, `partial` makes every `auto` field optional, which is what an update needs.

.catalog/types.py (input types)
[source,python]
----
@strawberry_django.input(models.Author)
class AuthorInput:
    name: auto


@strawberry_django.partial(models.Author)
class AuthorPartial:
    id: auto
    name: auto
----

Source: https://strawberry.rocks/docs/django/guide/types[Strawberry-Django: Defining types],
https://strawberry.rocks/docs/django/guide/fields[Strawberry-Django: Fields] and
https://strawberry.rocks/docs/django/guide/export-schema[Strawberry-Django: Export schema]

[#queries]
== Queries: lists, single objects, filters, ordering and pagination

On the root `Query` type, `strawberry_django.field()` does the resolving for you: a `list[BookType]` field returns
`Book.objects.all()` (as a lazy QuerySet that the filters, ordering, pagination and optimizer then refine), and a
single `BookType` field gains a required `pk: ID!` argument and returns one row.

.catalog/schema.py (queries)
[source,python]
----
import strawberry
import strawberry_django

from .types import AuthorType, BookType


@strawberry.type
class Query:
    books: list[BookType] = strawberry_django.field()
    book: BookType = strawberry_django.field()
    authors: list[AuthorType] = strawberry_django.field()
----

A filter type is declared with `@strawberry_django.filter_type(Model)`; with `lookups=True` every field gets an input of
Django lookups (`exact`, `iContains`, `gte`, `inList`, `isNull` ...), and a relation can nest the related model's filter.
Each filter input also gets `AND`, `OR`, `NOT` and `DISTINCT` fields. An ordering type is declared with
`@strawberry_django.order_type(Model)`; clients pass a list of one-field objects, so the order of the criteria is
preserved. `pagination=True` adds an `OffsetPaginationInput` (`offset`, `limit`) argument, capped by
`PAGINATION_MAX_LIMIT`.

.catalog/types.py (filters and ordering)
[source,python]
----
@strawberry_django.filter_type(models.Author, lookups=True)
class AuthorFilter:
    name: auto


@strawberry_django.filter_type(models.Book, lookups=True)
class BookFilter:
    title: auto
    published: auto
    author: AuthorFilter | None


@strawberry_django.order_type(models.Book)
class BookOrder:
    title: auto
    published: auto
----

All three become ORM calls -- `filter(published__gte=..., author__name__icontains=...)`, `order_by("-published")` and a
slice -- so the database does the work, not Python:

[source,bash]
----
$ curl -s -b cookies.txt http://127.0.0.1:8000/graphql/ \
    -H "Content-Type: application/json" -H "X-CSRFToken: $CSRF" \
    -d '{"query": "query Recent($since: Date!) { books(filters: {published: {gte: $since}, author: {name: {iContains: \"le guin\"}}}, ordering: [{published: DESC}], pagination: {limit: 5}) { title published author { name } } }", "variables": {"since": "1970-01-01"}}'
----

[source,json]
----
{
  "data": {
    "books": [
      {
        "title": "The Dispossessed",
        "published": "1974-05-01",
        "author": {
          "name": "Ursula K. Le Guin"
        }
      }
    ]
  }
}
----

The cookie jar and `$CSRF` come from the GraphiQL page, see <<csrf>>. A single-object field with a non-existent primary
key raises `Book.DoesNotExist`, which surfaces as `"errors": [{"message": "Book matching query does not exist.", ...}]`
with `"data": null`, because the field is non-null.

Filters only narrow what the type's QuerySet already allows. To hide rows from everybody (unpublished books, other
users' drafts), override the `get_queryset` class method on the type: it receives the default QuerySet and `info` (and
so the current user) and returns a narrower QuerySet. <<fetch-raise>> shows one.

Source: https://strawberry.rocks/docs/django/guide/queries[Strawberry-Django: Queries],
https://strawberry.rocks/docs/django/guide/filters[Strawberry-Django: Filtering],
https://strawberry.rocks/docs/django/guide/ordering[Strawberry-Django: Ordering] and
https://strawberry.rocks/docs/django/guide/pagination[Strawberry-Django: Pagination]

[#mutations]
== Mutations

Strawberry-Django offers two ways to write a mutation. For plain create/update/delete of one model, the generated
`mutations.create`, `mutations.update` and `mutations.delete` take an input type and do the `save()` (running
`full_clean()` first) for you. For anything with business logic, decorate a method with `@strawberry_django.mutation`,
which differs from Strawberry's own `@strawberry.mutation` in three ways: a synchronous resolver is wrapped in
`sync_to_async` when the schema runs under ASGI, so ORM calls are safe; it integrates with the permission extensions; and
with `handle_django_errors=True` it catches `ValidationError`, `PermissionDenied` and `ObjectDoesNotExist` and returns
them as data instead of a top-level error.

.catalog/schema.py (mutations)
[source,python]
----
import strawberry
import strawberry_django
from strawberry_django import mutations
from strawberry_django.auth.utils import get_current_user
from strawberry_django.permissions import HasPerm, IsAuthenticated

from . import models
from .types import AuthorInput, AuthorPartial, AuthorType, ReviewType


@strawberry.type
class Mutation:
    create_author: AuthorType = mutations.create(
        AuthorInput,
        handle_django_errors=True,
        extensions=[HasPerm("catalog.add_author")],
    )
    update_author: AuthorType = mutations.update(
        AuthorPartial,
        handle_django_errors=True,
        extensions=[HasPerm("catalog.change_author")],
    )

    @strawberry_django.mutation(
        handle_django_errors=True, extensions=[IsAuthenticated()]
    )
    def add_review(
        self, info: strawberry.Info, book_id: strawberry.ID, rating: int, body: str = ""
    ) -> ReviewType:
        review = models.Review(
            book_id=book_id,
            reader=get_current_user(info),
            rating=rating,
            body=body,
        )
        review.full_clean()
        review.save()
        return review
----

With `handle_django_errors=True` the return type becomes a union of the declared type and `OperationInfo`, so the
exported schema reads `addReview(bookId: ID!, rating: Int!, body: String! = ""): AddReviewPayload!` with
`union AddReviewPayload = ReviewType | OperationInfo`. Clients select both members with inline fragments. The reader is
taken from the session (`get_current_user(info)` returns `info.context.request.user`), never from an argument, so a
client cannot post a review in somebody else's name. `full_clean()` runs the model's validators and, since Django 4.1,
its constraints, so the check constraint above comes back as a `VALIDATION` message instead of an `IntegrityError`:

[source,graphql]
----
mutation {
  addReview(bookId: "2", rating: 9) {
    ... on ReviewType { rating }
    ... on OperationInfo { messages { kind field message code } }
  }
}
----

[source,json]
----
{
  "data": {
    "addReview": {
      "messages": [
        {
          "kind": "VALIDATION",
          "field": null,
          "message": "Constraint “review_rating_1_to_5” is violated.",
          "code": null
        }
      ]
    }
  }
}
----

A field-level validation error (a `ValidationError` keyed by field name) fills `field`; give the constraint a
`violation_error_message` (and `violation_error_code`) if clients should show something friendlier. The generated CRUD
mutations take their input in an argument called `data` (`createAuthor(data: {name: "..."})`); `mutations.update`
looks the row up by the primary key in the partial input (`id` here), or by another unique field passed as
`key_attr`. Never expose a
generated mutation without a permission extension: it can write every field that the input type declares.

GraphQL mutations must not be sent with GET; Strawberry's views refuse them (`mutations are not allowed when using GET`,
HTTP 400), so the usual "state changes need POST and CSRF" rule holds without extra code.

Source: https://strawberry.rocks/docs/django/guide/mutations[Strawberry-Django: Mutations],
https://strawberry.rocks/docs/general/mutations[Strawberry: Mutations] and
https://docs.djangoproject.com/en/6.1/ref/models/instances/#validating-objects[Validating objects]

[#permissions]
== Permissions and the current user

Authorization belongs to the server, not to the client's choice of fields; the theory is in
xref:backend/graphql/authorization.adoc[Authorization]. Strawberry-Django maps it onto Django's own permission system with
field extensions from `strawberry_django.permissions`:

[cols="2,5",options="header"]
|===
| Extension | Passes when

| `IsAuthenticated()`
| `request.user` is authenticated and active.

| `IsStaff()` / `IsSuperuser()`
| `user.is_staff` / `user.is_superuser`.

| `HasPerm("app.codename")`
| The user has the model-level permission (`any_perm`, `with_superuser` and `with_anonymous` tune the check).

| `HasSourcePerm(...)`
| The user has the permission on the parent object of the field.

| `HasRetvalPerm(...)`
| The user has the permission on each returned object; with an object-permission backend such as django-guardian
this filters lists row by row.
|===

When a check fails, the extension does not simply raise. If the field can return `OperationInfo` (a mutation with
`handle_django_errors=True`), it returns a `PERMISSION` message; otherwise an optional field resolves to `null`, a list to
`[]` and a connection to an empty connection; only a non-null single value raises a `PermissionDenied` error. Pass
`fail_silently=False` to raise instead of returning an empty value, and `message="..."` to change the text. The exported
schema documents the checks as directives (`@isAuthenticated`, `@hasPerm(...)`), so clients can see them. For example,
an authenticated reader without `catalog.add_author` gets:

[source,json]
----
{
  "data": {
    "createAuthor": {
      "messages": [
        {
          "kind": "PERMISSION",
          "message": "You don't have permission to access this app."
        }
      ]
    }
  }
}
----

The same extensions work on query fields, e.g.
`drafts: list[BookType] = strawberry_django.field(extensions=[IsStaff()])`. Who the user is comes from Django's
`AuthenticationMiddleware`; for login and logout over GraphQL, `strawberry_django.auth.login()`, `logout()` and
`current_user()` provide ready-made fields that call `django.contrib.auth.login`/`logout` and therefore rotate the
session key and need the CSRF token like any other POST. Token-based clients (mobile apps, other services) typically
authenticate in middleware instead and never touch the session; see xref:web/django/authentication.adoc[Authentication]
and xref:web/django/permissions-and-authorization.adoc[Permissions & Authorization] for the Django side.

Source: https://strawberry.rocks/docs/django/guide/permissions[Strawberry-Django: Permissions],
https://strawberry.rocks/docs/django/guide/authentication[Strawberry-Django: Authentication] and
https://docs.djangoproject.com/en/6.1/topics/auth/default/#permissions-and-authorization[Django: Permissions and Authorization]

[#serving]
== Serving the schema: views, GraphiQL and CSRF

The schema object ties the root types and the schema extensions together; the view serves it on a URL.

.catalog/schema.py (schema)
[source,python]
----
from strawberry_django.optimizer import DjangoOptimizerExtension

schema = strawberry.Schema(
    query=Query,
    mutation=Mutation,
    extensions=[DjangoOptimizerExtension],
)
----

`strawberry.django.views` has two views. `AsyncGraphQLView` is an async Django view: under ASGI (Uvicorn, Daphne,
Granian, Hypercorn) it runs on the event loop, supports async resolvers and is the only one that can use DataLoaders.
`GraphQLView` is synchronous for WSGI deployments. Both accept the same main options:

[cols="2,2,5",options="header"]
|===
| Option | Default | Meaning

| `schema`
| required
| The `strawberry.Schema`.

| `graphql_ide`
| `"graphiql"`
| The in-browser IDE served to `GET` requests that accept HTML: `"graphiql"`, `"apollo-sandbox"`, `"pathfinder"`, or
`None` to disable it.

| `allow_queries_via_get`
| `True`
| Accept queries (never mutations) in the query string of a `GET`.

| `multipart_uploads_enabled`
| `False`

[#csrf]
=== CSRF with GraphQL

Neither view is exempt from CSRF protection, so with `CsrfViewMiddleware` enabled (the default) a cookie-session `POST`
without a token is rejected before the schema runs:

[source,bash]
----
$ curl -s -i -X POST http://127.0.0.1:8000/graphql/ \
    -H "Content-Type: application/json" -d '{"query": "{ books { title } }"}' | head -1
HTTP/1.1 403 Forbidden
----

That is the correct default: the API trusts the session cookie, so it must be protected from cross-site requests exactly
like a form view. The bundled GraphiQL page already reads the `csrftoken` cookie and sends it back as the `X-CSRFToken`
header -- but the GraphQL view never sets that cookie, so a browser that has not visited another Django page cannot run
mutations from GraphiQL. Wrapping the view in `ensure_csrf_cookie` fixes that, and turning the IDE off outside
development keeps the production endpoint from serving it:

.config/urls.py
[source,python]
----
from django.conf import settings
from django.contrib import admin
from django.urls import path
from django.views.decorators.csrf import ensure_csrf_cookie

from catalog.schema import schema
from catalog.views import BookshelfGraphQLView

graphql_view = BookshelfGraphQLView.as_view(
    schema=schema,
    graphql_ide="graphiql" if settings.DEBUG else None,  # no IDE in production
)

urlpatterns = [
    path("admin/", admin.site.urls),
    # ensure_csrf_cookie: GraphiQL reads the "csrftoken" cookie and sends it back
    # as X-CSRFToken, so session-authenticated POSTs pass CsrfViewMiddleware.
    path("graphql/", ensure_csrf_cookie(graphql_view)),
]
----

`BookshelfGraphQLView` is an `AsyncGraphQLView` subclass defined in <<dataloaders>>; Django's view decorators have
supported async views since Django 5.0. A JavaScript client does the same as GraphiQL: read the cookie, send the header.
With `curl`:

[source,bash]
----
$ curl -s -c cookies.txt -o /dev/null -H "Accept: text/html" http://127.0.0.1:8000/graphql/
$ CSRF=$(awk '/csrftoken/ {print $7}' cookies.txt)
$ curl -s -b cookies.txt http://127.0.0.1:8000/graphql/ \
    -H "Content-Type: application/json" -H "X-CSRFToken: $CSRF" \
    -d '{"query": "mutation { addReview(bookId: \"1\", rating: 5) { ... on OperationInfo { messages { kind message } } } }"}'
{"data":{"addReview":{"messages":[{"kind":"PERMISSION","message":"User is not authenticated."}]}}}
----

The token passed the CSRF check, and the anonymous request was then stopped by `IsAuthenticated`. Strawberry's own Django
page wraps the view in `csrf_exempt`; do that only when the API never authenticates with cookies (for example, it
accepts only `Authorization: Bearer` tokens), because otherwise any website can make a logged-in user's browser run
mutations. Cross-origin browser clients additionally need CORS, covered in xref:web/cors.adoc[CORS].

Source: https://strawberry.rocks/docs/django/guide/views[Strawberry-Django: Serving the API],
https://strawberry.rocks/docs/integrations/django[Strawberry: Django integration (options)],
https://docs.djangoproject.com/en/6.1/howto/csrf/#using-csrf-protection-with-ajax[Using CSRF protection with AJAX] and

[#n-plus-1]
== The N+1 problem with the ORM

Why nested resolvers multiply queries, and the general batch-and-cache cure, are explained in
xref:backend/graphql/performance-and-n-plus-1.adoc[Performance & the N+1 problem]; the Django side of the same problem
(lazy relations, `select_related`, `prefetch_related`) is in
xref:web/django/query-optimization-and-fetch-modes.adoc[Query Optimization & Fetch Modes]. In a Django schema the two
meet: each nested field is resolved by attribute access on a model instance, so `book.author` and `book.reviews.all()`
each run a query per book unless the root QuerySet loaded them in advance. Here is the query
`{ books { title author { name } reviews { rating } } }` against two books, run once on a schema built without the
optimizer and once on the real one:

[source,python]
----
import strawberry
from django.db import connection
from django.test.utils import CaptureQueriesContext

from catalog.schema import Mutation, Query, schema

QUERY = "{ books { title author { name } reviews { rating } } }"
naive = strawberry.Schema(query=Query, mutation=Mutation)  # no optimizer

for s in (naive, schema):
    with CaptureQueriesContext(connection) as ctx:
        s.execute_sync(QUERY)
    print(len(ctx.captured_queries))
    for q in ctx.captured_queries:
        print("  ", q["sql"])
----

[source,text]
----
5
   SELECT "catalog_book"."id", "catalog_book"."title", "catalog_book"."isbn", "catalog_book"."published", "catalog_book"."author_id" FROM "catalog_book" ORDER BY "catalog_book"."id" ASC
   SELECT "catalog_author"."id", "catalog_author"."name" FROM "catalog_author" WHERE "catalog_author"."id" = 1 LIMIT 21
   SELECT "catalog_review"."id", "catalog_review"."book_id", "catalog_review"."reader_id", "catalog_review"."rating", "catalog_review"."body", "catalog_review"."created" FROM "catalog_review" WHERE "catalog_review"."book_id" = 1 ORDER BY "catalog_review"."id" ASC
   SELECT "catalog_author"."id", "catalog_author"."name" FROM "catalog_author" WHERE "catalog_author"."id" = 1 LIMIT 21
   SELECT "catalog_review"."id", "catalog_review"."book_id", "catalog_review"."reader_id", "catalog_review"."rating", "catalog_review"."body", "catalog_review"."created" FROM "catalog_review" WHERE "catalog_review"."book_id" = 2 ORDER BY "catalog_review"."id" ASC

[#optimizer]
=== The query optimizer extension

`DjangoOptimizerExtension`, added to `strawberry.Schema(extensions=[...])` as in <<serving>>, reads the selection set of
each root field before the QuerySet is evaluated and rewrites it: `select_related()` for every selected foreign key and
one-to-one, `prefetch_related()` (with nested `Prefetch` objects, carrying the nested filters, ordering and pagination)
for every selected reverse or many-to-many relation, `only()` for the selected columns, and `annotate()` for fields
declared with `strawberry_django.field(annotate=...)`. Each step can be switched off with a constructor argument
(`enable_only_optimization`, `enable_select_related_optimization`, `enable_prefetch_related_optimization`,
`enable_annotate_optimization`, `enable_nested_relations_prefetch`, all `True` by default), which is mostly useful for
debugging. It is the one extension every Strawberry-Django schema should have; the library's own quick start adds it
from the first example.

The optimizer can only see what is declared. A custom resolver that touches other columns or relations defeats it --
`only()` defers the columns it did not see, and each access then costs a query. Tell it what the resolver needs with
optimization hints (`only`, `select_related`, `prefetch_related`, `annotate`) on the field:

[source,python]
----
@strawberry_django.type(models.Book)
class NoHint:
    @strawberry_django.field
    def byline(self) -> str:
        return f"{self.title} by {self.author.name}"


@strawberry_django.type(models.Book)
class WithHint:
    @strawberry_django.field(only=["title"], select_related=["author"])
    def byline(self) -> str:
        return f"{self.title} by {self.author.name}"
----

For two books, `{ byline }` on `NoHint` ran seven queries (the root query selected only `id`, then one query each for the
deferred `title`, the deferred `author_id` and the author, per book); on `WithHint` it ran one query with a JOIN. The
same hints can live on the model with `strawberry_django.model_property`, so the type can annotate the property with
`auto`. Hand-written `select_related()`/`prefetch_related()` calls are what you write when there is no optimizer at all,
as in the Graphene example in <<graphene>>.

Source: https://strawberry.rocks/docs/django/guide/optimizer#optimization-hints[Strawberry-Django: Optimization hints],
https://docs.djangoproject.com/en/6.1/ref/models/querysets/#select-related[select_related()] and
https://docs.djangoproject.com/en/6.1/ref/models/querysets/#prefetch-related[prefetch_related()]

[#dataloaders]
=== DataLoaders for computed fields

Some fields are not relations at all -- an aggregate, a value from another service, a row in another database -- so
there is nothing for the optimizer to join. That is the job of a DataLoader: every resolver asks the loader for one key,
the loader collects the keys requested in the same tick of the event loop and calls one batch function with all of
them. DataLoaders are async, so they need `AsyncGraphQLView` (the Strawberry-Django docs list them among the features a
WSGI deployment misses). The loader must be created per request -- its cache would otherwise serve one user's data to
another -- which is what a custom context is for:

.catalog/loaders.py
[source,python]
----
from dataclasses import dataclass, field

from django.db.models import Avg
from strawberry.dataloader import DataLoader
from strawberry.django.context import StrawberryDjangoContext

from .models import Review


async def load_average_ratings(book_ids: list[int]) -> list[float | None]:
    rows = (
        Review.objects.filter(book_id__in=book_ids)
        .values("book_id")
        .annotate(avg=Avg("rating"))
    )
    averages = {row["book_id"]: row["avg"] async for row in rows}
    return [averages.get(book_id) for book_id in book_ids]  # same order as keys


@dataclass
class BookshelfContext(StrawberryDjangoContext):
    average_rating: DataLoader[int, float | None] = field(
        default_factory=lambda: DataLoader(load_fn=load_average_ratings)
    )
----

.catalog/views.py
[source,python]
----
from strawberry.django.views import AsyncGraphQLView

from .loaders import BookshelfContext


class BookshelfGraphQLView(AsyncGraphQLView):
    async def get_context(self, request, response):
        # A fresh context -- and fresh DataLoader cache -- per HTTP request.
        return BookshelfContext(request=request, response=response)
----

Subclassing `StrawberryDjangoContext` keeps `info.context.request` working, which the permission extensions and
`get_current_user()` rely on. The field itself is an async resolver on the type; the `only=["pk"]` hint tells the
optimizer that it needs nothing but the primary key:

.catalog/types.py (BookType, continued)
[source,python]
----
    @strawberry_django.field(only=["pk"])
    async def average_rating(self, info: strawberry.Info) -> float | None:
        return await info.context.average_rating.load(self.pk)
----

The batch function must return one value per key, in the order of the keys, which is why it builds a dictionary and
maps the keys through it. It uses the async ORM (`async for` over a QuerySet), so it never blocks the event loop.
`{ books { title averageRating } }` now runs two queries for any number of books -- the books, and one
`SELECT book_id, AVG(rating) ... WHERE book_id IN (...) GROUP BY book_id` -- which the test in <<testing>> asserts.
For this particular field `strawberry_django.field(annotate=Avg("reviews__rating"))` would also do (the optimizer adds the
annotation to the root query); the DataLoader is the general tool for data the ORM cannot join.

Source: https://strawberry.rocks/docs/guides/dataloaders[Strawberry: DataLoaders],
https://strawberry.rocks/docs/integrations/django[Strawberry: Django integration (get_context)] and
https://docs.djangoproject.com/en/6.1/topics/db/queries/#asynchronous-queries[Asynchronous queries]

[#fetch-raise]
=== Guarding against regressions with FETCH_RAISE (Django 6.1)

Django 6.1's fetch modes make a lazy load an error instead of a silent query. Setting `FETCH_RAISE` in a type's
`get_queryset` turns any relation or deferred column that the optimizer did not load into `FieldFetchBlocked`, which is
a cheap way to fail tests the moment a schema change reintroduces N+1:

[source,python]
----
from django.db import models as m


@strawberry_django.type(models.Book)
class GuardedBook:
    title: auto
    author: AuthorType

    @classmethod
    def get_queryset(cls, queryset, info, **kwargs):
        return queryset.fetch_mode(m.FETCH_RAISE)
----

With the optimizer, `{ books { title author { name } } }` on this type returns data in one query; on a schema without
the optimizer the same query fails with `"errors": [{"message": "Fetching of Book.author blocked.", ...}]`. Use it in
tests or behind a setting rather than unconditionally in production, where a missed hint would turn a slow field into a
failing one. Django 5.2 has no fetch modes; there, `assertNumQueries` (next section) is the guard.

Source: https://docs.djangoproject.com/en/6.1/topics/db/fetch-modes/[Fetch modes],
https://docs.djangoproject.com/en/6.1/ref/models/querysets/#fetch-mode[QuerySet.fetch_mode()] and
https://strawberry.rocks/docs/django/guide/types[Strawberry-Django: Defining types (get_queryset)]

[#sync-async]
== Sync and async

Strawberry-Django is written so that the same schema runs under both views. Its own resolvers (`strawberry_django.field()`,
the CRUD mutations, `@strawberry_django.mutation`) detect an async context and run ORM work through `sync_to_async`, so
a plain `def` resolver that touches the ORM is safe under `AsyncGraphQLView`. Plain `@strawberry.field` resolvers get no
such wrapping: under the async view, a synchronous ORM call there raises `SynchronousOnlyOperation`, so either make the
resolver `async def` and use the async ORM (`aget`, `acount`, `async for`), or use `@strawberry_django.field` instead.
Since 0.92.0 (2026-10-01), list fields hand graphql-core an unevaluated QuerySet that it iterates with `async for` in
async execution.

Choosing between them follows the deployment, not the schema: run `AsyncGraphQLView` under an ASGI server if you want
DataLoaders, async resolvers or subscriptions (which additionally need Channels, see
xref:web/django/channels-and-websockets.adoc[Channels & WebSockets]); run `GraphQLView` under WSGI otherwise. Django's
async story in general -- what is truly async in the ORM and what still runs in a thread -- is on
xref:web/django/async-support.adoc[Async Support].

Source: https://strawberry.rocks/docs/integrations/django[Strawberry: Django integration],
https://github.com/strawberry-graphql/strawberry-django/releases/tag/0.92.0[strawberry-django 0.92.0 release notes] and
https://docs.djangoproject.com/en/6.1/topics/async/[Asynchronous support]

[#graphene]
== Graphene-Django in brief

Graphene-Django predates Strawberry and still runs many production schemas. Types subclass `DjangoObjectType` and name
their model and exposed fields in an inner `Meta`; resolvers are `resolve_<field>` methods; the view is a synchronous
`GraphQLView` that takes the schema from the `GRAPHENE` setting. Its 3.2.3 release (2025-03-13) is the latest on
2026-10-03 and its classifiers stop at Django 4.2; it installed and passed its test under Django 6.1.1 here, in a separate
virtual environment, because Graphene 3.4.3 requires `graphql-core` below 3.3 while current Strawberry requires 3.3.

.config/settings.py and config/urls.py (Graphene-Django)
[source,python]
----

GRAPHENE = {"SCHEMA": "catalog.schema_graphene.schema"}

# config/urls.py
from django.conf import settings
from django.urls import path
from graphene_django.views import GraphQLView

urlpatterns = [
    path("graphql/", GraphQLView.as_view(graphiql=settings.DEBUG)),
]

.catalog/schema_graphene.py
[source,python]
----
import graphene
from graphene_django import DjangoObjectType

from .models import Author, Book


class AuthorNode(DjangoObjectType):
    class Meta:
        model = Author
        fields = ("id", "name", "books")


class BookNode(DjangoObjectType):
    class Meta:
        model = Book
        fields = ("id", "title", "isbn", "published", "author")


class Query(graphene.ObjectType):
    books = graphene.List(BookNode)

    def resolve_books(root, info):
        # No optimizer: join the author by hand to avoid N+1.
        return Book.objects.select_related("author").order_by("title")


schema = graphene.Schema(query=Query)
----

Always set `fields` (or `exclude`): without either, `DjangoObjectType` exposes every model field and warns that this is
deprecated. Graphene-Django has no query optimizer, so the `select_related("author")` above is mandatory -- and it is
also wrong for a query that does not select `author`, which is the trade-off the optimizer removes. As with Strawberry,
the view is not CSRF-exempt; set `graphiql` from `DEBUG` in production.

[cols="2,3,3",options="header"]
|===
| | Strawberry-Django | Graphene-Django

| Type declaration
| Annotated class, `auto` from the model
| `DjangoObjectType` with `Meta.model` and `Meta.fields`

| Filtering, ordering, pagination
| Built in (`filter_type`, `order_type`, `pagination=True`)
| django-filter via `DjangoFilterConnectionField` (Relay connections)

| Mutations
| CRUD helpers and `@strawberry_django.mutation`, `OperationInfo` errors
| `graphene.Mutation` classes; `DjangoModelFormMutation` and DRF serializer mutations

| N+1
| `DjangoOptimizerExtension`, hints, DataLoaders
| Hand-written `select_related`/`prefetch_related` in resolvers; no optimizer

| Async
| `AsyncGraphQLView`, async resolvers
| Synchronous view

| Testing
| `strawberry_django.test.client.TestClient`/`AsyncTestClient`
| `graphene_django.utils.testing.GraphQLTestCase`

[#testing]
== Testing

Strawberry-Django ships two test clients built on Django's: `strawberry_django.test.client.TestClient` (wrapping
`django.test.Client`) and `AsyncTestClient` (wrapping `AsyncClient`). They take the endpoint path, post the document
and variables as JSON, assert by default that the response has no errors (`assert_no_errors=False` turns that off for
negative tests), return a `Response` with `data`, `errors` and `extensions`, and offer a `login(user)` context manager
that logs a user into the client's session. Because they go through the URL, the middleware and the view, they test the
real wiring -- including permissions and the custom context. Django's test client does not enforce CSRF checks unless
created with `enforce_csrf_checks=True`, so CSRF behaviour is better checked with `curl` as in <<csrf>>.

The most valuable GraphQL test is a query-count test: `assertNumQueries` around a list query with several rows fails as
soon as a schema change brings back N+1.

        self.assertEqual(response.data, {"books": [{"title": "Book 0", "averageRating": 4.0}]})
----

A few details are worth copying. `setUpTestData` creates the rows once per class; five books make the difference between
`2` and `1 + 5 + 5` queries unmistakable. The DataLoader test uses the synchronous client on purpose: the async view runs
through `async_to_sync`, and `assertNumQueries` itself cannot be entered inside an `async def` test (it raises
`SynchronousOnlyOperation`), so query counting stays in synchronous tests while `AsyncTestClient` covers the async path.
The permission test grants `catalog.add_author` between two requests inside the same `login()` block; each request loads
the user afresh, so the second request sees the new permission. For pure schema logic without HTTP,
`schema.execute_sync()` (or `await schema.execute()`) runs a document directly, as the optimizer tests do. With pytest,
the same clients work in tests that request pytest-django's `db` fixture.

[#production]
== Production checklist

* Serve GraphiQL only in development (`graphql_ide=None` unless `DEBUG`), and consider disabling introspection for
public APIs; see xref:backend/graphql/introspection.adoc[Introspection].
* Cap work per request: keep `PAGINATION_MAX_LIMIT` low, and add Strawberry's `QueryDepthLimiter` extension (and other
demand-control measures from xref:backend/graphql/security-and-demand-control.adoc[Security & demand control]) so that
a deeply nested query cannot fan out into thousands of prefetches.
* Keep CSRF protection for cookie-authenticated clients; exempt the view only for token-only APIs.
* Put a permission extension on every mutation and on every field that is not public, and narrow row visibility in
`get_queryset`.
* Keep `DjangoOptimizerExtension` in the schema and a query-count test per list field.
* Export the schema in CI (`manage.py export_schema catalog.schema --path schema.graphql`) and fail the build on an
unreviewed diff.

.Adding a depth limit to the schema
[source,python]
----
from strawberry.extensions import QueryDepthLimiter

schema = strawberry.Schema(
    query=Query,
    mutation=Mutation,
    extensions=[
        DjangoOptimizerExtension,
        lambda: QueryDepthLimiter(max_depth=6),  # a factory: one instance per request
    ],
)
----

A query nested deeper than six levels is rejected before execution with
`"'anonymous' exceeds maximum operation depth of 6"`. Pass extensions as classes or factories: since Strawberry 0.316.0
(2026-05-19) passing an instance such as `QueryDepthLimiter(max_depth=6)` directly is deprecated, because the one object
would be shared by concurrent requests (the extension's own documentation page still shows the instance form).

Source: https://strawberry.rocks/docs/extensions/query-depth-limiter[Strawberry: QueryDepthLimiter] and
https://strawberry.rocks/docs/django/guide/pagination[Strawberry-Django: Pagination (PAGINATION_MAX_LIMIT)]

[#pitfalls]
== Pitfalls

* **Forgetting the optimizer.** Everything works and every list query is 1 + N; nothing warns you. Add the extension and
the query-count test from day one.
* **Custom resolvers without hints.** A method field that reads `self.author` or a deferred column silently adds queries
per row, even with the optimizer; declare `only`/`select_related`/`prefetch_related`.
* **Plain `@strawberry.field` resolvers calling the sync ORM under the async view** raise `SynchronousOnlyOperation`;
use `@strawberry_django.field` or an `async def` resolver with the async ORM.
* **A module-level DataLoader.** Its cache outlives the request and leaks data between users; create loaders in
`get_context`.
* **`csrf_exempt` copied from a quick start** onto a cookie-authenticated API opens it to cross-site request forgery.
* **Taking the user from an argument** (`readerId: ID!`) instead of `get_current_user(info)` lets clients act as anybody.
* **Relying on HTTP status codes.** GraphQL errors arrive with HTTP 200; log and alert on the `errors` key and on
`OperationInfo` payloads.
* **Unbounded lists.** Before 0.85.0 (2026-05-23) `PAGINATION_MAX_LIMIT` defaulted to `None`, so `limit: null` returned
whole tables; projects pinned to older releases must set it explicitly.
* **Deprecated decorator names.** `strawberry_django.filter` (renamed `filter_type` in 0.59.0) and
`strawberry_django.order` (superseded by `order_type`, also 0.59.0) still work but emit deprecation warnings, which
`python -W error` turns into failures.

[#books]
== Where the books are outdated

None of the four books consulted for this section (see the xref:web/django/index.adoc#_bibliography[section
bibliography]) teaches GraphQL: they target Django 1.11 to 2.1, and _Practical Django 2 and Channels 2_ mentions GraphQL
only in passing, as the newer alternative to REST that single-page applications consume. What they do teach that
carries over is the ORM side -- lazy relations, `select_related()` and `prefetch_related()` -- and that advice is still
correct; in a GraphQL schema the optimizer applies it per request from the selection set instead of you writing it per
view. Material from the same years on GraphQL with Django is outdated in specific ways:

* Graphene 2 and graphql-core 2 (2018-2019) are superseded by Graphene 3 and graphql-core 3; Graphene 3 no longer
depends on the `promise` library, so promise-based DataLoaders from that era do not carry over.
* `DjangoObjectType` classes without `fields` or `exclude` exposed every column; that is now deprecated and warns.
* Wrapping the view in `csrf_exempt` "to make GraphiQL work" is unnecessary: keep CSRF protection and let the page send
the token (<<csrf>>).
* Synchronous-only examples predate async views (Django 3.1) and the async ORM (4.1); under ASGI, `AsyncGraphQLView` and
async resolvers are the default choice now.
* Strawberry did not exist in 2018 (its first release is from 2019), so there is no book-era coverage of the code-first,
type-annotation approach used here.
