= Event Handling
:description: Binding events with jQuery's .on()/.off()/.one(), the jQuery event object and its methods, event delegation for dynamic elements, programmatic triggering, and namespaced and window/document events.
:keywords: jQuery events, on, off, one, bind, delegate, live, click, hover, submit, keydown, event object, preventDefault, stopPropagation, event delegation, trigger, namespaced events

include::partial$ai-disclaimer.adoc[]

`.on()` is the single method for attaching event handlers in modern jQuery. It registers a normalised,
cross-browser event object and supports delegation. The older `.bind()`, `.live()`, and `.delegate()` are all
removed or deprecated -- everything they did, `.on()` does.

== Binding handlers

[source,javascript]
----
$('#btn').on('click', handler);                 // direct binding
$('#btn').on('click', { id: 42 }, handler);     // pass data -> event.data.id
$('#btn').on('mouseenter mouseleave', handler); // several event types at once
$('#btn').one('click', handler);                // auto-removes itself after the first call

$('#btn').off('click', handler);   // remove one specific handler
$('#btn').off('click');            // remove all click handlers
$('#btn').off();                   // remove every handler on the element
----

Shorthand methods exist for the common events -- `.click()`, `.dblclick()`, `.hover(inFn, outFn)`, `.focus()`,
`.blur()`, `.change()`, `.submit()`, `.keydown()`, `.keyup()`, `.keypress()`, and the mouse family
(`.mousedown()`, `.mouseup()`, `.mousemove()`, `.mouseenter()`, `.mouseleave()`). Since jQuery 3.3 the
**no-argument** signatures (`.click()` to *trigger* a click) are deprecated; call `+.trigger('click')+` instead.
The one-argument forms (`.click(handler)`) still work but `+.on('click', handler)+` is preferred for
consistency and because only `.on()` supports delegation.

== The jQuery event object

The handler receives one argument: a jQuery-normalised event. `this` and `event.currentTarget` are the element
the handler is bound to.

[source,javascript]
----
$('#form').on('submit', function (event) {
  event.type;              // "submit"
  event.target;            // the deepest element the event originated on
  event.currentTarget;     // === this: the element this handler is attached to
  event.which;             // normalised key/button code (legacy)
  event.key;               // "Enter", "a", ... (modern, from the native event)
  event.pageX;             // pointer X relative to the document
  event.data;              // the data object passed as .on('submit', data, fn)

  event.preventDefault();       // cancel the default action (no form submit)
  event.stopPropagation();      // stop the event bubbling to ancestors
  event.stopImmediatePropagation(); // also skip this element's remaining handlers
  return false;                 // shorthand for BOTH preventDefault + stopPropagation
});
----

NOTE: In a jQuery handler `return false` is `preventDefault()` **and** `stopPropagation()`. In a native
listener `return false` does nothing. This difference trips people up when porting code.

== Event delegation

Bind one handler to a stable ancestor and pass a selector as the second argument. jQuery checks, at event
time, whether `event.target` (or an ancestor of it, up to `currentTarget`) matches that selector:

[source,javascript]
----
// direct: only binds to the <li> that exist RIGHT NOW
$('#list li').on('click', handler);

// delegated: one handler on #list; works for <li> added later too
$('#list').on('click', 'li', function (event) {
  $(this).toggleClass('done');   // `this` is the matched <li>, not #list
});
----

Delegation matters for two reasons: dynamically added elements get the behaviour with no re-binding, and one
listener uses less memory than hundreds. It is the standard pattern for lists, tables, and any repeated markup.

== Triggering and custom events

[source,javascript]
----
$('#btn').trigger('click');                 // fire click: handlers run AND default action
$('#btn').trigger('click', [arg1, arg2]);   // pass extra args to the handlers
$('#btn').triggerHandler('click');          // run handlers only: no default, no bubbling

$(document).on('cart:add', (e, item) => updateBadge(item));  // custom event
$(document).trigger('cart:add', { sku: 'A1' });              // fire it with data

$('#btn').on('click.plugin', handler);      // namespaced
$('#btn').off('.plugin');                   // remove every handler in the .plugin namespace
----

Namespaces let a plugin (or a component) remove exactly its own handlers without disturbing others.

== Window and document events

[source,javascript]
----
$(window).on('resize', handler);
$(window).on('scroll', handler);       // consider throttling -- fires rapidly
$(window).on('load', handler);         // after all images/resources; rarely needed
----

== How an event travels: capture, target, bubble

A native event goes down the tree to its target (the capture phase), fires on the target, and then climbs back up
(the bubble phase). jQuery handlers always listen in the bubble phase, which is the phase delegation depends on.
The diagram follows one click on the delete button of the shopping list:

[mermaid]
....
sequenceDiagram
    participant D as document
    participant U as ul#list
    participant L as li
    participant B as button.del
    Note over D,B: capture phase, jQuery does not listen here
    D->>U: event travels down
    U->>L: event travels down
    L->>B: reaches the target
    Note over B: target phase, direct handlers on the button run
    B-->>L: bubble, direct handlers on the li run
    L-->>U: bubble, delegated handler for .del runs here
    U-->>D: bubble, stopPropagation in the handler halts the climb
....

The delegated handler on `ul#list` runs on the way *back up*, after handlers bound directly to the button or row.
This ordering is why a direct handler that calls `event.stopPropagation()` silently breaks every delegated handler
above it, a common cause of "the click works until I add that other script".

== The delegation event object

In a delegated handler three different elements are in play, and jQuery gives each its own property:

[source,javascript]
----
$('#list').on('click', 'li', function (event) {
  this;                     // the matched <li> -- the element the selector matched
  event.currentTarget;      // the same <li> (===  this)
  event.delegateTarget;     // the <ul id="list"> the handler was bound to
  event.target;             // the deepest element clicked, perhaps the <span> or the <button>
});
----

Because `event.target` can be a descendant of the element you care about, use `.closest()` rather than testing
`event.target` directly:

[source,javascript]
----
$('#list').on('click', function (event) {
  const $button = $(event.target).closest('button.del', this);   // the second argument bounds the search
  if ($button.length) { /* a delete button was clicked */ }
});
----

== Worked example: keyboard editing in the list

The running example edits a row in place: a double-click swaps the label for a text input, Enter commits the
change, and Escape cancels it. All three listeners are delegated, so they also work for rows added later:

[source,javascript]
----
$('#list').on('dblclick', 'span', function () {
  const $span = $(this);
  const $edit = $('<input type="text" class="edit">').val($span.text());
  $span.hide().after($edit);
  $edit.trigger('focus');
});

$('#list').on('keydown', 'input.edit', function (event) {
  const $edit = $(this);
  const $span = $edit.prev('span');
  if (event.key === 'Enter') {
    const text = $edit.val().trim();
    if (text) $span.text(text);               // ignore an empty edit
  } else if (event.key !== 'Escape') {
    return;                                   // any other key: keep typing
  }
  $edit.remove();                             // Enter and Escape both end the edit
  $span.show();
});
----

`event.key` is read from the native event and holds readable names such as `"Enter"` and `"Escape"`; the older
`event.which` numeric codes still work but are deprecated.

== One place for reactions: custom events

When several things must react to the same change (a counter, a save to storage, a "dirty" marker), have each
mutation announce itself with a custom event and let one listener do the reaction. The mutation code no longer
needs to know what depends on it:

[source,javascript]
----
const $list = $('#list');

$list.on('list:change.stats', function (event, info) {          // namespaced custom event
  $('#count').text(info.total + ' rows');
});
$list.on('list:change.save', function () {
  localStorage.setItem('shopping-list', JSON.stringify(readItems()));
});

$list.trigger('list:change', { total: 3 });     // extra data arrives as handler arguments
$list.off('.stats');                             // detach only the counter, the save handler stays
----

Custom event names may contain a colon, so `list:change` is a safe convention; the part after a dot is always the
namespace.

== Building and triggering a synthetic event

`jQuery.Event()` builds an event object so that you can set properties before `.trigger()` and inspect the result
afterwards. This is how code, and tests, exercise keyboard handlers without a real keypress:

[source,javascript]
----
const press = $.Event('keydown', { key: 'Enter' });
$('#add-input').trigger(press);
press.isDefaultPrevented();      // true if a handler called preventDefault()
----

`.triggerHandler()` runs only the handlers (no default action, no bubbling) and returns the value of the last
handler, which is useful for asking a component a question:

[source,javascript]
----
$('#add-input').on('ping', function () { return 'pong'; });
$('#add-input').triggerHandler('ping');      // 'pong'
----

== Handlers that ought to run once, and handlers that ought not to pile up

A frequent bug in long-lived pages is binding the same handler again each time a view is re-rendered. Two defences:
`.one()` for a handler that is only valid once, and `.off()` with a namespace before re-binding:

[source,javascript]
----
$('#add-input').one('focus', function () { $(this).attr('placeholder', 'Type and press Enter'); });

function bindToolbar($root) {
  $root.off('.toolbar')                      // remove the previous binding first
       .on('click.toolbar', '.up', moveUp)
       .on('click.toolbar', '.down', moveDown);
}
----

== Debugging a handler chain

Check what jQuery thinks it bound by looking at the native event, which jQuery keeps on every normalised event:

[source,javascript]
----
$('#list').on('click', 'span', function (event) {
  console.log(event.originalEvent instanceof MouseEvent);   // true for a real click
  console.log(event.isPropagationStopped());                // did something earlier stop it?
});
----

The `mouseenter` and `mouseleave` events do not bubble natively; jQuery simulates them so that
`+$('#list').on('mouseenter', 'li', fn)+` works with delegation, which the plain `addEventListener` does not
support (use `mouseover` and `relatedTarget` there).

== Modern equivalent

`el.addEventListener(type, handler, options)` and `removeEventListener`. There is no built-in delegation --
attach to a container and test inside: `+container.addEventListener('click', e => { const li = e.target.closest('li'); if (li) ... })+`. Dispatch custom events with `+new CustomEvent('cart:add', { detail })+`
and `+el.dispatchEvent(...)+`. For the full capture/target/bubble model see
xref:programming-languages/javascript/browser-events.adoc[Events].
