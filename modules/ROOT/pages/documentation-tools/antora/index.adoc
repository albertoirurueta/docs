== What Antora is

Antora is a static site generator for technical documentation. Authors write pages in AsciiDoc, keep them in a standard
directory layout inside one or more git repositories, and describe in a single YAML file, the _playbook_, where the
content and the user interface (UI) come from. Antora reads the content, converts it and writes a plain HTML site that
can be served from any web server or static host. The project positions itself around "docs as code": content under
version control, content separated from presentation, automation and reuse.

Three ideas distinguish Antora from generators that start from a single folder of Markdown files:

* *Multiple repositories, one site.* A playbook lists any number of content sources. Each source can be a local
  directory or a remote git repository, so product teams keep the documentation next to their code and the site
  aggregates it. This site pulls the documentation of a dozen other repositories this way.
* *Versions come from git.* Antora reads branches and tags, and every branch or tag that carries a component version
  descriptor becomes a version of a documentation component. Several versions can be published side by side.
* *The UI is separate.* The look of the site comes from a UI bundle, a ZIP of Handlebars templates, CSS, JavaScript and
  images, that is referenced from the playbook and can be replaced without touching the content.

== AsciiDoc and Asciidoctor.js

Antora does not invent a markup language. Pages are written in https://asciidoc.org/[AsciiDoc], a plain-text markup
with built-in support for includes, cross-references, attributes, tables, admonitions, callouts and extension points.
The https://asciidoctor.org/[Asciidoctor] project provides the processor that turns AsciiDoc into HTML; Antora uses
Asciidoctor.js, the JavaScript build of that processor, which is why Antora runs on Node.js and needs no Ruby. The
Antora site notes that Antora's core developers help lead the Asciidoctor organization.

Antora configures Asciidoctor.js for you and adds a few things on top of plain AsciiDoc:

* *Resource IDs.* Cross-references, includes and images use identifiers of the form
  `version@component:module:family$path`, so a page can link to another module, component or version, not just to a
  neighbouring file. They are covered on
  xref:documentation-tools/antora/resource-ids-and-xrefs.adoc[Resource IDs and Xrefs].
* *Families and modules.* Every file belongs to a module and a family such as `pages`, `partials`, `examples`, `images`
  or `attachments`; see xref:documentation-tools/antora/modules-and-families.adoc[Modules and Families].
* *Attributes.* Site, component and page attributes can be set in the playbook and in the component descriptor, see
  xref:documentation-tools/antora/asciidoc-attributes-and-extensions.adoc[AsciiDoc Attributes and Extensions].
* *Asciidoctor extensions.* The playbook key `asciidoc.extensions` registers Asciidoctor.js extensions. This site uses
  it for Mermaid diagrams and MathJax formulas, as described in the repository's `CLAUDE.md`.

A page in the Pocket Units component looks like any AsciiDoc document. The title, a description attribute and a
cross-reference to another page of the same module are enough to see the idea:

[source,asciidoc]
----
= Getting Started
:description: Install Pocket Units and run your first conversion.

Add the package, then read xref:guides:converting-lengths.adoc[Converting lengths].
----

Source: https://docs.antora.org/antora/latest/page/[Antora docs: Pages]

== How Antora works

Antora is a pipeline. Its build happens in one process: it reads the playbook, collects every file from the
repositories, builds an in-memory catalog and writes the result to disk. The official page "How Antora Works" splits
that run into steps; they group naturally into six stages.

[mermaid]
....
flowchart LR
    A["Playbook<br/>antora-playbook.yml"] --> B["Aggregate<br/>clone or read repositories,<br/>find antora.yml"]
    B --> C["Classify<br/>assign module, family<br/>and output paths"]
    C --> D["Convert<br/>Asciidoctor.js turns AsciiDoc<br/>into embeddable HTML"]
    D --> E["Navigation<br/>build the nav model<br/>from nav files"]
    E --> F["Compose<br/>wrap pages in UI<br/>templates"]
    G["UI bundle<br/>ui-bundle.zip"] --> F
    F --> H["Publish<br/>write site to output dir"]
    H --> I["build/site"]
....

. *Aggregate.* Antora builds the playbook from the file, the command line and the environment, then loads the content
  sources. Remote repositories are cloned or fetched into a cache; local ones are read in place. For every selected
  branch or tag it looks for an `antora.yml` file in the source root, which marks the start of a component version, and
  turns each file below it into a virtual file object assigned to that component version.
. *Classify.* Antora computes the module, the family and the relative path of each file, and from them the output path
  and the publish URL. The files are organized into a content catalog together with the component versions and their
  start pages.
. *Convert.* Asciidoctor.js converts every page to embeddable HTML (the page body without the surrounding template).
  Cross-references are resolved against the catalog at this point, so a link to a page that does not exist is reported
  here.
. *Navigation.* Navigation files registered in each `antora.yml` are converted into a navigation model that the UI
  shows as the menu of the component version.
. *Compose with the UI.* The UI bundle is fetched from the URL or path in the playbook, cached, unpacked and classified
  with the help of its `ui.yml` descriptor. Each page is then wrapped in a UI template and receives the page HTML, the
  site metadata and the navigation model. The UI is loaded concurrently with the content, so its exact position in the
  sequence can vary.
. *Publish.* Antora produces a sitemap when `site.url` is set and writes the pages, the UI files and the other
  resources to the output location, by default a directory but also an archive or other providers.

A run with extensions can hook into these stages through generator events such as `contentAggregated`,
`navigationBuilt` or `beforePublish`; that is the subject of
xref:documentation-tools/antora/antora-extensions.adoc[Antora Extensions].

=== Running the pipeline on Pocket Units

The scratch project used for this section has a playbook that aggregates two branches of the Pocket Units repository
(`v1.0` and `v2.0`) and a second repository, `shared`, that holds a style guide:

[source,yaml]
----
site:
  title: Pocket Units Docs
  url: http://localhost:5252
  start_page: pocket-units::index.adoc
content:
  sources:
  - url: ./src/pocket-units
    branches: [v1.0, v2.0]
  - url: ./src/shared
    branches: main
ui:
  bundle:
    url: ./ui-bundle.zip
    snapshot: true
output:
  dir: build/site
----

Source: https://docs.antora.org/antora/latest/playbook/

Each source root carries the component version descriptor. For the `v2.0` branch it is:

[source,yaml]
----
name: pocket-units
title: Pocket Units
version: '2.0'
nav:
- modules/ROOT/nav.adoc
- modules/guides/nav.adoc
asciidoc:
  attributes:
    product-name: Pocket Units
----

Source: https://docs.antora.org/antora/latest/component-version-descriptor/

Running the generator on the scratch project with Antora 3.2.1 printed the version and then produced the following
files, one version of the component per branch and one versionless component for the shared content:

[source,bash]
----
npx antora --version
npx antora --fetch antora-playbook.yml
----

[source,text]
----
@antora/cli: 3.2.1
@antora/site-generator: 3.2.1

build/site/index.html
build/site/404.html
build/site/shared/style-guide.html
build/site/pocket-units/1.0/index.html
build/site/pocket-units/1.0/getting-started.html
build/site/pocket-units/2.0/index.html
build/site/pocket-units/2.0/getting-started.html
----

Source: https://docs.antora.org/antora/latest/cli/

The listing of generated files is abridged: the real build also writes the changelog and guide pages of both versions,
the sitemaps and the UI files. The playbook shown above uses a placeholder UI path; the scratch build used a locally
built copy of the Antora Default UI.

== When to choose Antora

Antora fits best when documentation is spread over several repositories or must exist in several versions at once.

[cols="1,1",options=header]
|===
| Choose Antora when
| Look elsewhere when

| Several repositories or teams contribute to one site and each keeps its docs next to its code.
| You document a single project in one repository with no versions; a simpler generator needs less setup.

| You publish several released versions side by side and want them taken from git branches or tags.
| Your authors work in Markdown and cannot move to AsciiDoc.

| You need strong cross-references, includes and reusable partials across modules and components.
| You want a ready-made, single-command site with many bundled themes and plugins, without assembling a UI bundle.

| You want to own the look of the site through a UI bundle that can be shared by many sites.
| You need the generator to be built on React components or Python tooling; Antora's extension model is JavaScript on Node.js.
|===

Trade-offs to keep in mind: the learning curve is steeper than for a single-folder generator, because there are new
concepts (playbook, component version descriptor, modules, families, UI bundle), and a UI bundle must exist before the
first build. The Default UI is distributed as a CI job artifact rather than as tagged releases. The extensions for
search (`@antora/lunr-extension`, 1.0.0-alpha.13) and for cross-run references (`@antora/atlas-extension`,
1.0.0-alpha.6) are still alpha releases at the check date. The sibling pages of this section compare Antora with
Docusaurus, Zensical and DocFX.
