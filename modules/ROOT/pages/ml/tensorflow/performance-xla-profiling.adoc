= Performance, XLA & Profiling
:description: Measuring and improving TensorFlow 2.21 and Keras 3.15 training speed: the TensorFlow Profiler, the input pipeline analyzer, jit_compile and XLA, tf.function pitfalls, tf.data bottlenecks and a tuning checklist.
:keywords: TensorFlow, Keras, performance, XLA, jit_compile, profiler, tf.profiler.experimental, Trace, input pipeline analyzer, TF_XLA_FLAGS, tf.data, bottleneck

include::partial$ml-tensorflow-disclaimer.adoc[]

Training that feels slow is rarely slow for the reason you first suspect. The reliable method is to measure: find out whether the accelerator is waiting for input, executing many tiny kernels, or limited by arithmetic or memory, and only then change something. This page covers the TensorFlow Profiler (programmatic APIs, Keras callback, remote capture and the analysis tools), reading the input pipeline analyzer, XLA compilation through `jit_compile`, and a short checklist. The data-loading details are on xref:ml/tensorflow/tf-data-performance.adoc[tf.data Performance], graph behaviour on xref:ml/tensorflow/graphs-and-tf-function.adoc[Graphs, tf.function, AutoGraph and Retracing], reduced precision on xref:ml/tensorflow/mixed-precision.adoc[Mixed Precision], multi-device scaling on xref:ml/tensorflow/distributed-training.adoc[Distributed Training] and visualisation on xref:ml/tensorflow/tensorboard.adoc[TensorBoard]. The PyTorch equivalents are xref:ml/pytorch/profiling.adoc[Profiling with torch.profiler] and xref:ml/pytorch/torch-compile.adoc[torch.compile]; the general method is in xref:ml/deep-learning-tuning-playbook.adoc[Deep Learning Tuning Playbook].

It targets Python 3.13 and TensorFlow 2.21 with Keras 3.15 (TensorFlow 2.22 is "upcoming" and not covered), and was checked against the official documentation on 2026-10-30. TensorFlow was not installed while preparing this page, so the snippets follow the documented API and were not executed.

== A measure-first workflow

[mermaid]
----
flowchart TD
    A["Training is slow"] --> B["Capture a profile of about 10 steps after warm-up"]
    B --> C{"Input pipeline analyzer: device waiting for input?"}
    C -- yes --> D["Fix tf.data: prefetch, parallel map, cache, interleave"]
    C -- no --> E{"Many tiny ops or large host gaps?"}
    E -- yes --> F["tf.function, larger batch, jit_compile or XLA fusion"]
    E -- no --> G{"Compute or memory bound?"}
    G -- compute --> H["Mixed precision, Tensor Core friendly shapes"]
    G -- memory --> I["Smaller activations, mixed precision, checkpointing"]
    D --> B
    F --> B
    H --> B
    I --> B
----

Change one thing at a time and re-profile; warm-up steps (tracing, XLA compilation, autotuning) distort the first batches, so skip them.

== Capturing a profile

The TensorFlow Profiler writes trace data into a TensorBoard log directory and is viewed in the Profile tab of TensorBoard (install the `tensorboard-plugin-profile` package, see xref:ml/tensorflow/tensorboard.adoc[TensorBoard]). There are five ways to capture:

[source,python]
----
import tensorflow as tf
import keras

# 1. Keras callback: profile batches 10 to 15 of the first epoch
tb = keras.callbacks.TensorBoard(log_dir="logs/prof", profile_batch=(10, 15))
model.fit(train_ds, epochs=2, callbacks=[tb])

# 2. Programmatic start and stop
tf.profiler.experimental.start("logs/prof")
run_some_steps()
tf.profiler.experimental.stop()

# 3. Context manager
with tf.profiler.experimental.Profile("logs/prof"):
    run_some_steps()

# 4. Sampling mode: start a server in the training job, trigger from outside
tf.profiler.experimental.server.start(6009)
# elsewhere (or from the TensorBoard "Capture profile" button):
tf.profiler.experimental.client.trace("grpc://localhost:6009", "gs://my-bucket/logs", 2000)
----

Source: https://www.tensorflow.org/guide/profiler

Option 4 is the one that works for remote machines, multiple workers (pass a comma-separated list of `grpc://` addresses) and TPUs. Profile about 10 steps at a time and avoid the very first batches. When you start the profiler programmatically you can enable Python function tracing with `tf.profiler.experimental.ProfilerOptions`; the guide only mentions the option, so look up its fields in the API reference.

=== Marking steps in a custom loop

The profiler needs step boundaries to produce per-step statistics. Keras `fit` marks them automatically; in a custom loop wrap each step in `tf.profiler.experimental.Trace`.

[source,python]
----
import tensorflow as tf

iterator = iter(train_ds)
tf.profiler.experimental.start("logs/prof")
for step in range(20):
    with tf.profiler.experimental.Trace("train", step_num=step, _r=1):
        batch = next(iterator)        # fetch INSIDE the trace so input time is attributed
        train_step(batch)
tf.profiler.experimental.stop()
----

Source: https://www.tensorflow.org/guide/profiler

`name` is the step-name prefix, `step_num` is appended to it and `+_r=1+` marks the event as a step event. Writing `for step, batch in enumerate(dataset)` outside the `Trace` block is an anti-pattern: the time spent fetching the next element is then missing from the step and the input-pipeline analysis is inaccurate.

== The profiler tools

[cols="2,5"]
|===
| Tool | What it tells you

| Overview page | step time summary, device precision use, top device operations and recommendations
| Input pipeline analyzer | whether the program is input bound and where input time goes
| TensorFlow Stats | self and cumulative time per operation on host and device, with CSV export
| Trace viewer | a timeline of operations on host and device, limited to 1 million events per device
| GPU kernel stats | per-kernel statistics and the originating operation, including Tensor Core eligibility
| Memory profile | memory use over time, peak, fragmentation and allocations by operation, for out-of-memory debugging
| Pod viewer | per-step time breakdown across all workers
| tf.data bottleneck analysis | an experimental analysis of the slowest `tf.data` stage
|===

Source: https://www.tensorflow.org/guide/profiler

=== Reading the input pipeline analyzer

Open Profile, choose `input_pipeline_analyzer` in the Tools menu. It has three parts:

. Summary: the percentage of device time spent waiting for input from the host. A large figure means the program is input bound.
. Device-side analysis: a step-time graph in which red is device idle time waiting for input and green is active device work.
. Host-side analysis: input processing time split into reading files on demand (no caching, prefetching or interleaving), reading files in advance, preprocessing such as image decoding, and enqueuing data to the device. Expanding Input Op Statistics shows a per-operation table.

If most time is "reading data on demand", add `prefetch`, `interleave` and parallel reads; if it is preprocessing, add `num_parallel_calls=tf.data.AUTOTUNE` or move work offline; see xref:ml/tensorflow/tf-data-performance.adoc[tf.data Performance] and xref:ml/tensorflow/tf-data.adoc[Input Pipelines with tf.data].

Typical symptoms and the usual response:

* Device idle between steps, big host gaps in the trace: input bound, or Python overhead in an eager loop. Wrap the step in `tf.function` and increase prefetching.
* Thousands of very short kernels: fuse them with XLA (below) or restructure the model.
* Kernels not eligible for Tensor Cores: use float16 or bfloat16 and dimensions that are multiples of 8, see xref:ml/tensorflow/mixed-precision.adoc[Mixed Precision].
* Memory profile near the device limit: shrink the batch, use mixed precision, or recompute activations.

A quick wall-clock benchmark for a dataset alone separates the input pipeline from the model:

[source,python]
----
import time
import tensorflow as tf

def benchmark(dataset, steps=200):
    it = iter(dataset)
    next(it)                                  # warm-up
    start = time.perf_counter()
    for _ in range(steps):
        next(it)
    elapsed = time.perf_counter() - start
    print(f"{steps / elapsed:.1f} batches/s")

benchmark(train_ds)
----

Source: https://www.tensorflow.org/guide/data_performance

If the dataset alone cannot deliver more batches per second than the model consumes, the input pipeline is the bottleneck.

== XLA and jit_compile

XLA (Accelerated Linear Algebra) is a compiler that turns a TensorFlow graph into fused, device-specific code. Fusing element-wise operations avoids writing intermediate tensors to memory, which often helps memory-bound models and models with many small operations. There are three ways to turn it on.

[source,python]
----
import tensorflow as tf
import keras

# 1. Per function: compile this tf.function with XLA
@tf.function(jit_compile=True)
def dense_step(x, w, b):
    return tf.nn.relu(tf.matmul(x, w) + b)

# 2. Per Keras model: compile the train/test/predict steps with XLA
model.compile(optimizer="adam", loss="sparse_categorical_crossentropy", jit_compile=True)
# jit_compile="auto" is the Keras 3 default; False disables compilation

# 3. Whole-process auto-clustering (no code change)
#    TF_XLA_FLAGS=--tf_xla_auto_jit=2 python train.py
----

Source: https://www.tensorflow.org/xla and https://keras.io/api/models/model_training_apis/

Behavioural points:

* With `jit_compile=True` the function must be fully compilable by XLA. Shapes must be known when tracing; ragged tensors, data-dependent output shapes and unsupported operations make compilation fail with an error instead of silently falling back.
* XLA recompiles for each new input shape, so variable batch or sequence lengths cause repeated compilation. Pad to a few fixed sizes, or use `drop_remainder=True` when batching.
* Compilation adds start-up time; XLA pays off for long runs. Always compare against the non-XLA run with the same profiler capture.
* The auto-clustering flag `+--tf_xla_auto_jit=2+` and `+--xla_dump_to+` style debug options are environment-level switches described in the XLA documentation at openxla.org; their exact current spelling was not re-verified in this session.
* In Keras 3 the default for `+compile(jit_compile=...)+` is `"auto"`, which enables XLA when the active backend and model support it. On the JAX backend everything is compiled through XLA by default; see xref:ml/tensorflow/keras-multi-backend.adoc[Keras Multi-Backend].

XLA is complementary to xref:ml/tensorflow/graphs-and-tf-function.adoc[tf.function]: `tf.function` removes Python overhead, XLA optimises the graph itself. The PyTorch compiler plays a similar role, see xref:ml/pytorch/torch-compile.adoc[torch.compile].

== A tuning checklist

. Run on a representative number of steps after warm-up and capture a profile before changing anything.
. Make sure the input pipeline overlaps with training: `prefetch(tf.data.AUTOTUNE)`, parallel `map`, `interleave` for many files, and caching small datasets after decoding.
. Use `tf.function` (Keras `fit` already does) and avoid Python side effects and retracing in the step.
. Increase the batch size until memory or generalisation limits you, re-tuning the learning rate (xref:ml/gradient-descent-and-optimization.adoc[Gradient Descent and Optimization]).
. Enable mixed precision on Tensor Core or TPU hardware.
. Try `jit_compile=True` and keep it only if the profiled step time improves.
. Distribute only after one device is saturated, see xref:ml/tensorflow/distributed-training.adoc[Distributed Training].
. For deterministic runs use `tf.config.experimental.enable_op_determinism()`, which may slow some operations; see xref:ml/tensorflow/tensors.adoc[Tensors, Dtypes and Random Numbers] for seeding.

Also consider TensorFlow's GPU memory behaviour: by default it reserves most of the GPU memory at start-up; `tf.config.experimental.set_memory_growth(gpu, True)` makes it grow on demand (see xref:ml/tensorflow/devices-gpu-tpu.adoc[Devices]).
