= ExecuTorch for Mobile & Edge
:description: Running PyTorch models on phones, embedded boards and desktops with ExecuTorch: the export-lower-serialise workflow (torch.export, to_edge_transform_and_lower, partitioners, to_executorch, .pte), backends (XNNPACK, Core ML, Vulkan, Qualcomm and others), dynamic shapes, quantization with torchao PT2E, running from Python, C++, Android and iOS, and large language models.
:keywords: PyTorch, ExecuTorch, edge, mobile, on-device, .pte, to_edge_transform_and_lower, XnnpackPartitioner, to_executorch, delegate, backend, XNNPACK, Core ML, Vulkan, Qualcomm, Android, iOS, quantization, PT2E, export_llm

include::partial$ml-pytorch-disclaimer.adoc[]

*ExecuTorch* is the PyTorch runtime for inference on edge devices: phones and tablets, wearables, desktops and microcontrollers. A model is exported with `torch.export`, optionally *lowered* to a hardware backend (a *delegate*), and serialised into a compact `.pte` file that a small C{pp} runtime executes. The runtime has no Python dependency. A PyTorch blog post titled "ExecuTorch becomes part of PyTorch Core" is listed in the references (its content was not read for this page). The TorchScript-based mobile paths of older tutorials are not the way forward; see xref:ml/pytorch/legacy-and-deprecated.adoc[Legacy APIs & Migration]. The cross-framework picture, including LiteRT for TensorFlow and Keras models, is in xref:ml/onnx-and-interoperability.adoc[ONNX & Model Interoperability], and the decision of where to run a model is in xref:ml/deploying-and-serving-models.adoc[Deploying & Serving ML Models].

The facts below were checked on 2026-10-30 against the ExecuTorch stable documentation, which the pages describe for ExecuTorch 1.5.1 (PyPI release 1.5.1 at the check date), together with Python 3.13 and PyTorch 2.15. The documentation lists Python 3.10 to 3.14 and PyTorch 2.9 or later as prerequisites. `torch` and `executorch` were not installed in the environment used to write this page, so the snippets follow the documented API and were not executed. Mobile and desktop apps additionally need their own toolchains (Gradle, Xcode, CMake), which were not exercised.

== Workflow

[mermaid]
----
flowchart LR
    A["nn.Module + example inputs"] --> B["torch.export.export"]
    B --> C["to_edge_transform_and_lower(partitioner = backend)"]
    C --> D["to_executorch()"]
    D --> E["model.pte"]
    E --> F["ExecuTorch runtimeC++, Java/Kotlin, Objective-C, Python"]
----

. *Select a backend.* The backend decides what hardware accelerates the model and which operators are supported.
. *Prepare the model*: put it in `eval()` mode, choose example inputs, decide which dimensions are dynamic.
. *Export* with `torch.export.export` (see xref:ml/pytorch/torch-export.adoc[torch.export]).
. *Lower* with `to_edge_transform_and_lower`, passing the backend's partitioner. Parts of the graph the backend supports are delegated to it; the rest runs on the portable CPU kernels.
. *Serialise* with `to_executorch()` and write the `.pte` buffer to a file.

== Installing

[source,bash]
----
pip install executorch
# nightly builds
pip install executorch --pre --extra-index-url https://download.pytorch.org/whl/nightly/cpu
----

Source: https://docs.pytorch.org/executorch/stable/getting-started.html

The documentation supports Linux (x86_64, ARM64), macOS (ARM64) and Windows (x86_64) as export hosts; on Intel macOS PyTorch must be built from source. A C{pp}17 compiler is required for building the runtime, and Visual Studio 2022 or later on Windows (run from a Developer PowerShell).

== Exporting a model to .pte

[source,python]
----
import torch
import torchvision.models as models
from torchvision.models.mobilenetv2 import MobileNet_V2_Weights

from executorch.backends.xnnpack.partition.xnnpack_partitioner import XnnpackPartitioner
from executorch.exir import to_edge_transform_and_lower

model = models.mobilenetv2.mobilenet_v2(weights=MobileNet_V2_Weights.DEFAULT).eval()
sample_inputs = (torch.randn(1, 3, 224, 224),)

et_program = to_edge_transform_and_lower(
    torch.export.export(model, sample_inputs),
    partitioner=[XnnpackPartitioner()],
).to_executorch()

with open("model.pte", "wb") as f:
    f.write(et_program.buffer)
----

Source: https://docs.pytorch.org/executorch/stable/getting-started.html

The backend is chosen only by the `partitioner` argument. Several partitioners can be given in a list and are applied in priority order; operators that no backend takes fall back to the portable CPU kernels, which can be slow. For mobile the documentation recommends XNNPACK for Android and XNNPACK or Core ML for iOS.

=== Dynamic shapes

[source,python]
----
from torch.export import Dim, export

dynamic_shapes = {"x": {2: Dim("h", min=16, max=1024), 3: Dim("w", min=16, max=1024)}}
exported_program = export(model, inputs, dynamic_shapes=dynamic_shapes)
executorch_program = to_edge_transform_and_lower(
    exported_program, partitioner=[XnnpackPartitioner()]
).to_executorch()
----

Source: https://docs.pytorch.org/executorch/stable/using-executorch-export.html

Dimensions without a declaration stay at the example size. Keep upper bounds no larger than necessary, since the runtime plans memory from the bound. The same page documents that each method of a multi-method `.pte` is memory-planned separately, so activation memory is not shared between methods.

=== Pitfalls collected from the export guide

* Mutable buffers: use in-place operations (names ending in an underscore) or `copy_`, do not reassign the buffer variable, call `detach()` on tensors before storing them in a buffer, and expect `index_put_` to be a bottleneck. Buffers are not shared between methods, and not every backend supports buffer mutation; the page calls mutation support experimental.
* Dynamic control flow: use `torch.cond` for data-dependent branches. Dynamic loops are not supported; export the loop body as a method and drive the loop from application code.
* Only `forward` can be exported directly. Wrap other methods in their own `nn.Module` to export them as extra methods.
* Large weights can be kept out of the `.pte` in a separate `.ptd` data file (tagged with a pass from `executorch.exir.passes.external_constants_pass`) so that they can be shared or updated independently.

== Backends

The backend list in the documentation (all selected through a partitioner) includes:

[cols="2,3,2",options="header"]
|===
| Backend | Platforms | Hardware

| XNNPACK | All | CPU
| Core ML | iOS, macOS | Neural Engine, GPU, CPU
| Vulkan | Android (described as mature), Linux, Windows (experimental on desktops) | GPU
| Qualcomm (QNN) | Android | NPU
| MediaTek | Android | NPU
| Samsung Exynos | Android | CPU, GPU, NPU
| CUDA | Linux, Windows | GPU
| Arm Ethos-U, Arm Cortex-M | Embedded | NPU, CPU
| OpenVINO, NXP, Cadence | Embedded | CPU, GPU, NPU, DSP (varies)
| MLX, WebGPU | iOS and macOS (MLX, experimental on iOS), browser and desktop (WebGPU, experimental) | GPU
|===

Source: https://docs.pytorch.org/executorch/stable/backends-section.html

Each backend has its own page with installation steps, supported operators and options, for example https://docs.pytorch.org/executorch/stable/backends/xnnpack/xnnpack-overview.html[XNNPACK], https://docs.pytorch.org/executorch/stable/backends/coreml/coreml-overview.html[Core ML] and https://docs.pytorch.org/executorch/stable/backends/vulkan/vulkan-overview.html[Vulkan]. NPU backends from chip vendors usually require the vendor SDK and a model quantised in a specific way. The status labels above are those of the documentation index on the check date; recheck them before committing to a backend.

== Quantization

Quantization is normally applied after export and before lowering, because backends execute integer kernels. ExecuTorch uses the PT2E flow from torchao, with a quantizer provided by the target backend:

[source,python]
----
import torch
from torchao.quantization.pt2e.quantize_pt2e import convert_pt2e, prepare_pt2e

training_gm = torch.export.export(model, sample_inputs).module()

prepared = prepare_pt2e(training_gm, quantizer)   # backend-specific quantizer instance
for batch in calibration_data:                    # representative inputs
    prepared(batch)
quantized = convert_pt2e(prepared)

# Lower the quantized model as an unquantized one
et_program = to_edge_transform_and_lower(
    torch.export.export(quantized, sample_inputs),
    partitioner=[XnnpackPartitioner()],
).to_executorch()
----

Source: https://docs.pytorch.org/executorch/stable/quantization-overview.html

The overview names `XNNPACKQuantizer` and `CoreMLQuantizer` as examples of backend quantizers; their import paths are in the backend pages and are not repeated here. The overview shows prepare, calibrate and convert, and says lowering follows the backend-specific page; the final lowering call above is the standard lowering step from the export guide applied to the quantized module. The accuracy check with `compute_error` (SQNR) from `torchao.quantization.utils` is also shown there. Background on what quantization does and its accuracy costs is in xref:ml/model-compression.adoc[Model Compression]; the eager-mode torchao APIs are in xref:ml/pytorch/quantization-and-sparsity.adoc[Quantization, Sparsity & Pruning with torchao].

== Running a .pte

=== Python (for testing on the host)

[source,python]
----
import torch
from executorch.runtime import Runtime

runtime = Runtime.get()
program = runtime.load_program("model.pte")
method = program.load_method("forward")
output = method.execute([torch.randn(1, 3, 224, 224)])
print(output[0].shape)
----

Source: https://docs.pytorch.org/executorch/stable/getting-started.html

Compare the output with the eager model (`torch.allclose` with a tolerance such as `rtol=1e-3`, `atol=1e-5`) before shipping, particularly for quantized models.

=== C++

[source,cpp]
----
#include <executorch/extension/module/module.h>
#include <executorch/extension/tensor/tensor.h>

using namespace ::executorch::extension;

Module module("/path/to/model.pte");

float input[1 * 3 * 224 * 224];
auto tensor = from_blob(input, {1, 3, 224, 224});

const auto result = module.forward(tensor);
if (result.ok()) {
  const auto output = result->at(0).toTensor().const_data_ptr<float>();
}
----

[source,cmake]
----
set(CMAKE_CXX_STANDARD 17)
find_package(executorch REQUIRED COMPONENTS kernels_optimized)
target_link_libraries(my_target PRIVATE executorch::runtime executorch::kernels_optimized)
----

Source: https://docs.pytorch.org/executorch/stable/getting-started.html

The prebuilt C{pp} libraries come with the pip package (Linux and macOS); building from source with CMake uses a preset file (for example `llm.cmake`) and links `executorch`, `executorch::backends`, `executorch::extensions` and `executorch::kernels`.

=== Android

Module model = Module.load("/path/to/model.pte");

EValue[] output = model.forward(EValue.from(input));
float[] scores = output[0].toTensor().getDataAsFloatArray();

Source: https://docs.pytorch.org/executorch/stable/getting-started.html

=== iOS

ExecuTorch is distributed as a Swift Package Manager package with xcframework targets: in Xcode choose File, Add Package Dependencies, paste the repository URL and set the branch to `swiftpm-<version>` (for example `swiftpm-1.5.1`). The getting-started page provides no Swift sample; models are loaded and run through the C{pp} APIs from Objective-C. Prefer checking the current iOS guide on the edge-platforms page before relying on this.

Source: https://docs.pytorch.org/executorch/stable/getting-started.html

== Large language models

The documentation describes a two-step LLM workflow: export the model to a `.pte` with `export_llm` (ExecuTorch own export API with optimisations) or, for Hugging Face models with broader architecture coverage, the Optimum integration, then run the file with the C{pp} runner or the Swift and Java bindings. Exact commands, flags and the list of supported models change quickly and were not verified for this page; follow the LLM guides at https://docs.pytorch.org/executorch/stable/llm/working-with-llms.html. Related background on running language models locally is in xref:ai/local-llms/quantization-for-inference.adoc[Quantization for Inference] and xref:ai/hugging-face/model-formats.adoc[Model Formats].
