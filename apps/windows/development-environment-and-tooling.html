Development Environment & Tooling

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Before the first line of XAML is written, a Windows desktop developer needs an SDK, an IDE with the right workload, a way to run unsigned code during development, and tools that shorten the edit-run-inspect loop. This page covers that environment for the section’s running application, Bookshelf Desktop, and the tools used to inspect it while it runs.

The page was written against these versions, as verified on 2026-10-23:

  • .NET 10 LTS, latest patch 10.0.13, supported until 2028-11-14, and C# 14. .NET 8 and .NET 9 go out of support on 2026-11-10. .NET 11 is at release candidate 2 (go-live licence); general availability is expected at .NET Conf, 10-13 November 2026, and this page notes where it matters once it ships.

  • Visual Studio 2026, latest release 18.11.1. Feature updates ship monthly, so menu names can move between updates.

  • Windows App SDK 2.5.1 (stable channel) for WinUI 3, and CommunityToolkit.Mvvm 8.4.2 for the view models used in later examples.

  • Windows 10 and Windows 11. The tools below run on both. Windows 11 is the recommended development machine; consult the supported-OS list of each product before relying on an older Windows 10 build.

  • The winapp CLI (Microsoft.WinAppCli) is in public preview, v0.7.1 at the time of writing, so its commands and options can change between releases.

The C# language itself and the dotnet command line are covered on Getting Started with C# and Build and Tooling in the C# reference. This page adds what is specific to desktop UI development. The project files that these tools generate are explained on the section page Project Structure & Build, and the stack choice on Windows App Platforms: WPF, WinUI 3, WinForms, MAUI & More.

Developer Mode

Windows normally accepts only apps installed from the Microsoft Store or signed by a trusted certificate. Developer Mode relaxes this on a development machine. It enables the following behaviours:

  • installing packaged apps from loose files and from locally built packages, so that Visual Studio can deploy and debug a packaged WinUI 3 app (a layout deployment registers the files in the build output folder);

  • sideloading a package signed with a certificate that is not chained to a trusted root;

  • some developer-oriented settings of the Settings app, such as File Explorer and Terminal tweaks.

Developer Mode is a per-machine switch and requires administrative rights. Turn it on in Settings > System > For developers (Windows 11; on Windows 10 it is under Update & Security). It is not needed to run or debug a plain unpackaged WPF or Windows Forms executable, which is just a normal process.

Enabling and Checking It

The setting is stored in the registry under the AppModelUnlock key. The script below only reads that key, so it is safe to run without elevation and changes nothing. It reports whether Developer Mode and sideloading are on, which is the first thing to check when a packaged app refuses to deploy.

# Read-only: reports the Developer Mode and sideloading switches.
$path = 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\AppModelUnlock'

if (-not (Test-Path $path)) {
    Write-Output 'AppModelUnlock key not present: Developer Mode has never been configured.'
    return
}

$values = Get-ItemProperty -Path $path
[pscustomobject]@{
    DeveloperMode     = [bool]($values.AllowDevelopmentWithoutDevLicense -eq 1)
    SideloadTrustedApps = [bool]($values.AllowAllTrustedApps -eq 1)
}

A typical result on a configured machine:

DeveloperMode SideloadTrustedApps
------------- -------------------
         True                True

The two values map to the settings described in the official page: AllowDevelopmentWithoutDevLicense is the Developer Mode switch, and AllowAllTrustedApps allows installing apps from outside the Store. Group Policy or MDM can lock both, in which case the Settings toggle is disabled and an administrator must change the policy.

Source: Enable your device for development

Why It Is Not a Production Setting

Developer Mode weakens the platform’s install-time checks, so it belongs on development machines only. Customers install Bookshelf Desktop through signed packages, the Store or an installer; none of those paths requires Developer Mode. Publishing is covered on the section pages MSIX Packaging & Signing and Distribution Channels.

Repeatable Setup with winget configure

winget configure applies a WinGet configuration file: a YAML document that lists resources to bring the machine to a desired state. Resources are DSC (Desired State Configuration) resources, so the same file can install packages, turn on Developer Mode and run other settings modules. Running the file twice is safe because each resource first tests the current state.

The Windows apps documentation publishes a ready-made file for WinUI development at aka.ms/winui-config. The example below is a simplified file in the same format, adapted for Bookshelf Desktop. Save it as bookshelf.dev.winget.

# yaml-language-server: $schema=https://aka.ms/configuration-dsc-schema/0.2
properties:
  configurationVersion: 0.2.0
  resources:
    - resource: Microsoft.Windows.Developer/DeveloperMode
      directives:
        description: Enable Developer Mode
        allowPrerelease: true
      settings:
        Ensure: Present

    - resource: Microsoft.WinGet.DSC/WinGetPackage
      id: dotnet-sdk
      directives:
        description: Install the .NET 10 SDK
        allowPrerelease: true
      settings:
        id: Microsoft.DotNet.SDK.10
        source: winget

    - resource: Microsoft.WinGet.DSC/WinGetPackage
      id: git
      directives:
        description: Install Git
        allowPrerelease: true
      settings:
        id: Git.Git
        source: winget

    - resource: Microsoft.WinGet.DSC/WinGetPackage
      id: winapp-cli
      directives:
        description: Install the winapp CLI (public preview)
        allowPrerelease: true
      settings:
        id: Microsoft.WinAppCli
        source: winget

Apply it from an elevated terminal, because Developer Mode is a machine setting:

winget configure --file .\bookshelf.dev.winget --accept-configuration-agreements

The command prints the resources it is about to apply and then one result per resource. The output below is illustrative; the exact wording varies between winget versions.

Applying configuration...
  Enable Developer Mode ............ applied
  Install the .NET 10 SDK .......... applied
  Install Git ...................... already in the desired state
  Install the winapp CLI (public preview) ... applied
Configuration successfully applied.

Three practical points follow from how the feature works:

  • Configuration files are code that runs with your privileges. Read a file from the internet, including the aka.ms/winui-config one, before applying it, exactly as you would read an install script.

  • Package identifiers must be exact. Confirm them with winget search (for example, winget search "Microsoft.DotNet.SDK" or winget search "Visual Studio") because identifiers for new product versions are added over time. This page does not hard-code a Visual Studio 2026 identifier for that reason.

  • The Visual Studio workloads can also be requested from a configuration file, but the official page documents the package-level and settings-level resources; check the current resource list in the documentation before adding a workload resource.

Source: WinGet configuration

The winapp CLI

The winapp CLI (Microsoft.WinAppCli) is a command-line tool from Microsoft for the parts of Windows app development that traditionally needed Visual Studio dialogs or several separate SDK tools: working with the app manifest, giving an executable a debug package identity, building an MSIX package and signing it. It targets developers who use any framework (including WPF, Windows Forms, Electron or plain Win32), and CI pipelines.

It is in public preview, so treat the commands below as a starting point and run winapp --help to see what your installed version supports.

# Install (also done by the winget configuration file above)
winget install Microsoft.WinAppCli

# Confirm the installed version
winapp --version

# List the available commands and options of this version
winapp --help

The documented command groups include project initialisation, creating a debug identity for an unpackaged executable, packaging a build output folder as MSIX, generating a development certificate and signing a package. Their exact names and flags evolve with the preview. The distribution pages of this section show where each step fits in a release pipeline; they use the command names current at the time of writing and link back to the official reference.

What the official documentation does not provide is a stability guarantee for the preview: breaking changes between 0.x releases are possible, and the CLI should be pinned to a version in CI rather than installed as "latest".

Source: winapp CLI

XAML Hot Reload

XAML Hot Reload applies edits to XAML files to the running application without restarting it, while keeping the application state: the window stays open, the selected book stays selected, and the data stays loaded. It works for WPF and WinUI 3 projects debugged from Visual Studio (and for other XAML stacks listed in the official page). Managed code edits are handled by the separate .NET Hot Reload feature, with limits on what kinds of edits are applied.

A Hot Reload Workflow for Bookshelf Desktop

The following loop is the recommended way to build the main window. It uses the MainWindow below, with a binding to a BooksViewModel that is introduced properly on the MVVM pages of this section.

<Window x:Class="Bookshelf.Desktop.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        xmlns:d="http://schemas.microsoft.com/expression/blend/2008"
        xmlns:mc="http://schemas.openxmlformats.org/markup-compatibility/2006"
        xmlns:vm="clr-namespace:Bookshelf.Desktop.ViewModels"
        mc:Ignorable="d"
        d:DataContext="{d:DesignInstance Type=vm:BooksViewModel}"
        Title="Bookshelf Desktop" Height="480" Width="720">
    <Grid Margin="12">
        <Grid.RowDefinitions>
            <RowDefinition Height="Auto"/>
            <RowDefinition Height="*"/>
        </Grid.RowDefinitions>

        <TextBox Grid.Row="0" Margin="0,0,0,8"
                 Text="{Binding SearchText, UpdateSourceTrigger=PropertyChanged}"/>

        <ListView Grid.Row="1" ItemsSource="{Binding Books}"
                  SelectedItem="{Binding SelectedBook}">
            <ListView.View>
                <GridView>
                    <GridViewColumn Header="Title" DisplayMemberBinding="{Binding Title}" Width="320"/>
                    <GridViewColumn Header="Author" DisplayMemberBinding="{Binding Author}" Width="220"/>
                </GridView>
            </ListView.View>
        </ListView>
    </Grid>
</Window>

Follow these steps:

  1. Start debugging with F5. Visual Studio builds the app, launches it and attaches the debugger.

  2. Confirm that Hot Reload is enabled. In Tools > Options > Debugging > Hot Reload (the dialog is also reachable from the Hot Reload drop-down on the toolbar) the XAML Hot Reload option must be on, and "Enable Hot Reload on file save" controls whether reload happens when you save instead of when you click the toolbar button.

  3. Edit the XAML while the app runs, for example change the Width of the Title column from 320 to 360, or change Margin="12" to Margin="24".

  4. Save the file or choose Hot Reload in the debug toolbar. The running window updates in place, and the selection and scroll position are kept.

  5. Keep editing. If the change cannot be applied, the editor reports it and the app keeps running with the previous UI; stop and restart debugging only for such cases.

Edits that need a restart in practice are those that change what the compiler produces rather than what the XAML loader reads, for example changing x:Class, adding code-behind members or changing the project’s target framework. The official pages list the supported scenarios per stack; this page does not enumerate them, because the list changes with Visual Studio updates.

Source: Write and debug running XAML code with XAML Hot Reload

Design-Time Data with the d: Namespace

The mc:Ignorable="d" and d:DataContext lines in the example let the XAML designer, and the Live Preview window, render the window with sample data without running the application. The d: attributes are ignored by the runtime XAML loader. They are described on the XAML fundamentals page of this section.

Debugging a Binding Problem Step by Step

Suppose the book list is empty although the view model contains data. Use the tools in this order:

  1. Open XAML Binding Failures. A row such as "Cannot find source" or "Property 'Books' not found on object" tells you that either the DataContext or the path is wrong.

  2. In Live Visual Tree, select the ListView and open Live Property Explorer. Look at DataContext: if it is null, the window never received its view model. If it is a different type, the binding path points at the wrong object.

  3. Check ItemsSource in the explorer. If it shows a collection, the problem is in the item template; if it is empty, the problem is in the view model.

  4. Fix the source (for example assign the DataContext in the composition root), save, and let Hot Reload apply it.

A debugging setup for WPF data binding raises the trace level in code during development. This is a standard technique from the WPF data binding documentation; keep it out of release builds.

using System.Diagnostics;

namespace Bookshelf.Desktop;

public partial class App : System.Windows.Application
{
    protected override void OnStartup(System.Windows.StartupEventArgs e)
    {
#if DEBUG
        // Verbose binding diagnostics in the Visual Studio Output window.
        PresentationTraceSources.Refresh();
        PresentationTraceSources.DataBindingSource.Listeners.Add(new ConsoleTraceListener());
        PresentationTraceSources.DataBindingSource.Switch.Level = SourceLevels.Warning | SourceLevels.Error;
#endif
        base.OnStartup(e);
    }
}

Source: Windows Presentation Foundation overview

Debugging Packaged WinUI 3 Apps

A packaged app runs with a package identity and in the MSIX layout, and Visual Studio registers it before launching it (this is where Developer Mode is needed). An unpackaged WinUI 3 app runs as a normal executable. The two modes therefore differ when you debug features that require identity, such as notifications or some storage APIs. For a non-packaged executable, a debug identity can be added from the command line, which is one of the uses of the winapp CLI described above.

Pitfalls

  • Running the wrong Visual Studio. Opening a net10.0-windows solution in Visual Studio 2022 gives a missing-SDK error. Use Visual Studio 2026 or build with the .NET 10 SDK from the command line.

  • Applying a configuration file blindly. winget configure executes resources with your privileges. Review the YAML, including the official one, before applying it.

  • Leaving Developer Mode on in a shared or build image. Enable it where development happens and not on machines that run only production software.

  • Expecting Hot Reload to cover everything. Changes to the compiled shape of the app require a restart. If the running UI does not change, check the Hot Reload output and the Options setting before assuming a bug.

  • Ignoring the Output window. WPF swallows binding errors and shows blank UI. Binding failures are the first thing to check for an empty control.

  • Pinning nothing. The winapp CLI is in preview and the winget package may update. Record the version used by CI and by global.json for the SDK so builds are reproducible.

  • Mixing target frameworks. A test project that targets net10.0 cannot reference a net10.0-windows WPF project directly. Keep view models in a plain net10.0 library, as in the solution above, and test them there.

Historical Tools

Two tools appear in older tutorials and are described here only so that you recognise them.

  • Windows Template Studio was a Visual Studio extension that generated WinUI and UWP apps from a wizard. Its last release was in 2023 and there is no Microsoft Learn page for it, so this section does not use it.

  • Dev Home was a Windows dashboard that could run machine setup, including WinGet configuration files. It has been retired. The winget configure command described above works without it.

What the Official Documentation Does Not Provide

  • There is no single Microsoft Learn page that lists everything a WPF developer should install; the "start here" page is the closest, and it leads with WinUI. Treat the WPF overview and the .NET SDK documentation as complementary.

  • The aka.ms/winui-config file targets WinUI development. A WPF-only or Windows Forms-only configuration is a user composition of the same resources, as shown above, and is not an official file.

  • The winapp CLI documentation is a preview reference; there is no compatibility guarantee between 0.x versions.

  • WinUI 3 project creation from the dotnet CLI is not covered by the .NET SDK template documentation.

Third-party tools such as Avalonia’s templates, Uno Platform’s tooling, the FlaUI automation library and the XAML Styler formatting extension also exist. They are third-party products and are not covered here.
