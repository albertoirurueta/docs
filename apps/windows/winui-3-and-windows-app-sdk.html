WinUI 3 & the Windows App SDK

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

WinUI 3 is the UI framework that Microsoft recommends for new native Windows desktop apps, and the Windows App SDK is the set of libraries that ships it together with windowing, the app lifecycle, notifications, resource management and other platform APIs. Where WPF is a part of .NET and Windows Forms wraps the Win32 controls, WinUI 3 is an independent XAML framework that is delivered as a NuGet package and runs on Windows 10 and Windows 11 without depending on the operating system’s own version of the controls. This page explains what that means in practice: how an app is assembled, how {x:Bind} replaces {Binding} for most work, how a shell with NavigationView, a custom title bar and Mica is built, how single-instance and activation work, and how a packaged app differs from an unpackaged one. The running example is the main screen of Bookshelf Desktop, re-implemented in WinUI 3.

The page was written against these versions, current in October 2026:

  • .NET 10 LTS, latest patch 10.0.13, supported until 14 November 2028, with C# 14. .NET 11 is at release candidate 2 (11.0.0-rc.2); general availability is expected at .NET Conf, 10 to 13 November 2026. None of the APIs on this page is listed as changed for .NET 11.

  • Visual Studio 2026, latest 18.11.1, with the "WinUI application development" workload.

  • Windows App SDK 2.5.1 on the stable channel. Version 2.0 (29 April 2026) was the first release to follow semantic versioning, and the NuGet package version equals the SDK version.

  • CommunityToolkit.Mvvm 8.4.2 for the view models.

  • Windows 11 and Windows 10. The support page lists Windows 10 version 1809 (build 17763) as the oldest client release supported by Windows App SDK 2, and Microsoft supports the SDK only on Windows releases that are themselves still in support.

The XAML language is the subject of the XAML Language Fundamentals page and the differences between the three XAML dialects are in XAML Dialects: WPF, WinUI & MAUI. Choosing WinUI over WPF or Windows Forms is covered on Windows App Platforms: WPF, WinUI 3, WinForms, MAUI & More. This page goes deeper into what is specific to WinUI 3.

WinUI 3 and the Windows App SDK

WinUI 3 is the native UI framework of the Windows App SDK. Microsoft describes it as the recommended native UI framework for new Windows desktop applications, with the Fluent Design System, high-performance rendering and a XAML programming model for C# and C++. It is built in the open (the microsoft-ui-xaml repository on GitHub), parts of the Windows shell and built-in apps use it, and so do open-source tools such as PowerToys.

The Windows App SDK (formerly Project Reunion) is the wider package. WinUI is one of its components. The others are exposed to any desktop app, including WPF and Windows Forms apps.

Component What it provides

WinUI

The XAML framework: controls, styles, Window, input, text, animation and composition.

Windowing (AppWindow)

A high-level abstraction of the top-level window (HWND): size and position, title bar, icon, presenters such as overlapped, full screen and compact overlay.

App lifecycle

Instancing (AppInstance), rich activation (file, protocol, startup task) and power management notifications.

MRT Core

Resource management and localization with the .resw format and qualifiers.

Notifications

App notifications (toasts) and push notifications.

Deployment

The Deployment API and the bootstrapper for apps that are unpackaged or packaged with external location.

Text rendering and widgets

DWriteCore text rendering and Windows Widgets support.

Windows AI and ML

Windows AI APIs and Windows ML in separate packages.

Source: WinUI 3 and Windows App SDK release channels

WinUI 3 is not part of Windows or of .NET. An app carries (self-contained) or references (framework-dependent) the copy of the framework it was built with, so the controls look and behave the same on every supported Windows version. This is the biggest difference from WPF, where the controls ship with .NET, and from Windows Forms, whose controls are wrappers around the Win32 common controls of the operating system.

Versioning and release channels

Until 1.8 the Windows App SDK used its own version scheme and shipped a major or minor release every six months or so. Version 2.0 is the first release that follows semantic versioning 2.0.0, and the NuGet package version now matches the SDK version. The package family name aligns with the major version, so the next side-by-side major release will be 3.0.0 and breaking changes are allowed only across major versions.

The servicing policy distinguishes Current releases (the latest stable one, which receives fixes more often) from Maintenance releases (no longer the latest, critical fixes only). Version 2.0 is listed as Current with an end of servicing on 29 April 2027, version 1.8 moved to Maintenance and its end of servicing was 24 September 2026, and versions 1.7 and earlier are out of support. Support is conditional on using the latest patch of the release and a supported operating system. Plan to move a 1.x app to 2.x if it is still on the older line; the release notes list the behavior changes between them (see the version history table near the end of this page).

Project Anatomy

A WinUI 3 project is an SDK-style project like any other, with a handful of properties and files that identify it as a WinUI app. The full property list is on Project Structure & Build. The project of the Bookshelf WinUI front end, with everything this page uses, looks like this:

The three project references mirror the solution layout of the other Bookshelf pages: the model and repository interface in Bookshelf.Core, the EF Core and SQLite implementation in Bookshelf.Data, and the view models in a class library, so that the same BooksViewModel serves the WPF, WinUI 3 and Windows Forms front ends. The view models reference no UI types, which also makes them testable without a window (see the Testing View Models & UI page).

The files that a WinUI template creates, and what each is for:

File Purpose

App.xaml, App.xaml.cs

The Application subclass. Application resources (merge XamlControlsResources here) and the OnLaunched override, which creates the first window.

MainWindow.xaml, MainWindow.xaml.cs

The main Window. It derives from Microsoft.UI.Xaml.Window, which is not a FrameworkElement.

Package.appxmanifest

The package manifest of a packaged app: identity, publisher, capabilities, visual assets and extensions such as protocol and file-type associations.

The application manifest (DPI awareness, supported operating systems).

The XAML compiler turns each .xaml file into a binary .xbf file and generates a partial class in obj (MainWindow.g.cs) that connects the markup to your code, including the compiled {x:Bind} bindings. Opening these generated files and putting a breakpoint in them is a supported way to debug a binding.

The application class

The App class below registers the services with Microsoft.Extensions.DependencyInjection, creates the main window and hands the first activation to the same routine that later activations use. The generic host variant, with configuration, logging and hosted services, is on the Dependency Injection & the Generic Host page; here the container is plain so that the focus stays on WinUI.

using Bookshelf.Core;
using Bookshelf.Data;
using Bookshelf.Desktop;
using Bookshelf.Desktop.ViewModels;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Extensions.Hosting;
using Microsoft.UI.Xaml;
using Microsoft.Windows.AppLifecycle;

namespace Bookshelf.WinUI;

public partial class App : Application
{
    /// <summary>The running application, typed.</summary>
    public static new App Current => (App)Application.Current;

    public IServiceProvider Services { get; }

    public MainWindow? MainWindow { get; private set; }

    public App()
    {
        Services = ConfigureServices();
        InitializeComponent();
    }

    private static ServiceProvider ConfigureServices()
    {
        var services = new ServiceCollection();

        services.AddBookshelfData();                 // IBookRepository: EF Core + SQLite, from Bookshelf.Data
        services.AddSingleton<WinUiDialogService>();
        services.AddSingleton<IDialogService>(sp => sp.GetRequiredService<WinUiDialogService>());

        // One BooksViewModel for the whole shell, so that a protocol activation can select a book
        // in the same instance that the page is bound to.
        services.AddSingleton<BooksViewModel>();

        return services.BuildServiceProvider();
    }

    protected override async void OnLaunched(LaunchActivatedEventArgs args)
    {
        // A plain ServiceCollection never starts IHostedService registrations, so run the ones
        // AddBookshelfData adds (DatabaseInitializer migrates the database) before any page queries it.
        foreach (var hostedService in Services.GetServices<IHostedService>())
        {
            await hostedService.StartAsync(CancellationToken.None);
        }

        MainWindow = new MainWindow();
        MainWindow.Activate();

        // Launch, file and protocol activations all arrive through the same routine.
        ActivationRouter.Handle(AppInstance.GetCurrent().GetActivatedEventArgs());
    }
}

Source: Data Binding with WinUI and MVVM Toolkit, step 3: add dependency injection for the App.Current and Services shape. AddBookshelfData and ActivationRouter are Bookshelf helpers, shown in the activation section. Because the container is not a Generic Host, OnLaunched starts the registered hosted services itself; a Generic Host starts them in its own StartAsync.

The tutorial registers its view models as transient, so that each page gets a fresh one. BooksViewModel is a singleton here only because the shell has one books screen and an activation handler must reach it; a page that edits one book at a time would be transient.

The Bookshelf Main Screen in WinUI 3

The WPF version of the main screen is a Window with a DataGrid, a details pane and a toolbar. The WinUI 3 version has the same parts, arranged as a typical Windows 11 app: a custom title bar, a NavigationView as the shell, a Frame that hosts the pages, and Mica as the window backdrop. Three files carry it: MainWindow (the shell), BooksPage (the screen) and the view models that already exist on the MVVM Toolkit page.

using Bookshelf.WinUI.Views;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.UI.Xaml;
using Microsoft.UI.Xaml.Controls;
using Microsoft.UI.Xaml.Media.Animation;
using Windows.Graphics;

namespace Bookshelf.WinUI;

public sealed partial class MainWindow : Window
{
    private static readonly Dictionary<string, Type> Pages = new()
    {
        ["books"] = typeof(BooksPage),
        ["favorites"] = typeof(FavoritesPage),
    };

    public MainWindow()
    {
        InitializeComponent();

        // In code, in the constructor: setting it in XAML is an error, and setting it later can flash
        // the system title bar first.
        ExtendsContentIntoTitleBar = true;
        SetTitleBar(AppTitleBar);

        Title = "Bookshelf";
        AppWindow.Resize(new SizeInt32(1200, 800));

        App.Current.Services.GetRequiredService<WinUiDialogService>().Attach(Content.XamlRoot);

        NavView.SelectedItem = NavView.MenuItems[0];
    }

    private void OnNavSelectionChanged(NavigationView sender, NavigationViewSelectionChangedEventArgs args)
    {
        if (args.IsSettingsSelected)
        {
            Navigate(typeof(SettingsPage), args.RecommendedNavigationTransitionInfo);
        }
        else if (args.SelectedItemContainer?.Tag is string tag && Pages.TryGetValue(tag, out Type? pageType))
        {
            Navigate(pageType, args.RecommendedNavigationTransitionInfo);
        }
    }

    private void Navigate(Type pageType, NavigationTransitionInfo transition)
    {
        // Do not stack duplicate entries when the selected item is invoked again.
        if (ContentFrame.CurrentSourcePageType != pageType)
        {
            ContentFrame.Navigate(pageType, null, transition);
        }
    }

    private void OnTitleBarBackRequested(TitleBar sender, object args)
    {
        if (ContentFrame.CanGoBack)
        {
            ContentFrame.GoBack();
        }
    }

    private void OnTitleBarPaneToggleRequested(TitleBar sender, object args) =>
        NavView.IsPaneOpen = !NavView.IsPaneOpen;
}

Source: TitleBar, NavigationView and Manage app windows

What this shell uses, and where each piece is explained further down:

  • Window.SystemBackdrop with MicaBackdrop puts Mica behind everything. It shows through the title bar because the TitleBar control and the NavigationView content layer are transparent or low-opacity (see the backdrops section).

  • The TitleBar control replaces the system title bar. The back button and the pane toggle button live in the title bar, as the Fluent guidance recommends, so the NavigationView hides its own.

  • The NavigationView does not navigate by itself. It raises SelectionChanged (or ItemInvoked), and the code behind maps the Tag of the selected item to a page type and calls Frame.Navigate.

  • AppWindow.Resize takes physical pixels and sizes the whole window, including the border and title bar.

  • Content.XamlRoot is not available until the window has content, which is why the dialog service is attached after InitializeComponent. A ContentDialog needs it.

using Bookshelf.Desktop.ViewModels;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.UI.Xaml;

namespace Bookshelf.WinUI.Views;

public sealed partial class BooksPage : Page
{
    // x:Bind resolves "ViewModel.SearchText" against this class, so the view model is a property here.
    public BooksViewModel ViewModel { get; }

    public BooksPage()
    {
        // Frame.Navigate creates the page with its parameterless constructor, so the page asks the container.
        ViewModel = App.Current.Services.GetRequiredService<BooksViewModel>();
        InitializeComponent();
    }

    private async void OnLoaded(object sender, RoutedEventArgs e) =>
        await ViewModel.LoadCommand.ExecuteAsync(null);

    // A parameterless method can be the target of an event binding: Click="{x:Bind ClearSearch}".
    private void ClearSearch() => ViewModel.SearchText = string.Empty;

    // A function binding: re-evaluated when ViewModel.SelectedBook changes.
    public static bool IsNotNull(object? value) => value is not null;
}

public static class BookFormat
{
    public static string ByLine(string? author, int year) =>
        year > 0 ? $"{author}, {year}" : author ?? string.Empty;

    public static string Price(decimal price) => price.ToString("C");
}

Source: x:Bind markup extension, Functions in x:Bind with WinUI and x:Load attribute

A few details of the listing deserve a closer look:

  • The page sets x:DefaultBindMode="OneWay" on the root, so every {x:Bind} below it that does not name a mode is OneWay. The rows that really are static declare OneTime to avoid the change-tracking code.

  • Click="{x:Bind ClearSearch}" binds an event to a method with no parameters. Event binding does not track changes to the model: the path is evaluated when the event fires.

  • Command="{x:Bind ViewModel.AddBookCommand}" binds to the IAsyncRelayCommand that the MVVM Toolkit generates from AddBookAsync. The command-bar buttons enable and disable themselves through CanExecuteChanged.

  • x:Load on DetailsPane uses an x:Bind expression, so the pane exists only while a book is selected. The expression is a function, IsNotNull, whose argument is the bound SelectedBook.

  • Loaded="OnLoaded" starts the first load. The tutorial loads from OnNavigatedTo instead, which also refreshes the list each time the page is navigated to.

  • FavoritesPage and SettingsPage, used by the shell, are ordinary pages and are not shown.

The ListView replaces the DataGrid of the WPF version. WinUI 3 has no DataGrid in the box; the Windows App SDK 2.x release notes list a TableView control as experimental only. The lists page of this section covers the options.

x:Bind in Detail

{x:Bind} is the most important syntactic difference between WinUI and WPF. At XAML compile time it is converted into generated C# code that reads the value from the source, sets it on the target and, if requested, subscribes to change notifications. The generated files are in obj (for example BooksPage.g.cs), so a breakpoint can be placed in them. Compared with {Binding}, which uses general-purpose runtime object inspection, compiled bindings run in less time and memory, are validated at build time and can be debugged.

Where the path starts

{x:Bind} does not use the DataContext. Outside a DataTemplate it uses the page, user control or window class itself, looking for properties, fields and methods in the code-behind. That is why ViewModel is a property on BooksPage. Named elements (x:Name) are fields of that class, so there is no ElementName: write {x:Bind SearchBox.Text, Mode=OneWay}. Inside a DataTemplate it uses the type named by x:DataType. The x:DataType can be an interface or a base class, and casts can then be used to reach members of the real type. A path can use indexers (Teams[0].Players), dictionary keys (Players['John Smith']), attached properties (Button22.(Grid.Row)) and casts (((TextBox)obj).Text).

Binding modes

Mode Behavior Notes

OneTime

The value is read once, when the page or template loads. This is the default of {x:Bind}.

Cheapest: no listener code is generated. {Binding} defaults to OneWay, so porting markup changes behavior.

OneWay

The target is refreshed when the source raises PropertyChanged (or the dependency property changes).

Needs INotifyPropertyChanged on the source. More generated code per binding.

TwoWay

Also pushes target changes back to the source.

UpdateSourceTrigger decides when: PropertyChanged for every property except TextBox.Text, which uses LostFocus.

Source: x:Bind markup extension

x:DefaultBindMode changes the default for an element and its children, which is the cheapest way to make a whole page OneWay without repeating the mode, as BooksPage does. A TextBox that must filter while the user types needs UpdateSourceTrigger=PropertyChanged, because its default is LostFocus.

The properties of the extension

Property Meaning

Path

The property path, optional when written first. May end in a function call.

Mode

OneTime, OneWay or TwoWay.

Converter, ConverterParameter, ConverterLanguage

An IValueConverter instance referenced with {StaticResource}. Most conversions are better written as a function.

FallbackValue

Shown when the source or path cannot be resolved (for example a null link in the chain).

TargetNullValue

Shown when the path resolves to null. For a function binding it applies to the result of the call, not to the arguments.

BindBack

The function that writes a value back in a two-way function binding.

UpdateSourceTrigger

When a two-way binding writes to the source.

The expression cannot contain line breaks, and a single curly brace in a Path or ConverterParameter is written as \{ or enclosed in a second quotation set.

Functions in binding paths

A function can be the last step of a path. It can be static, written prefix:Class.Method(args), or an instance method found by the usual path rules. Arguments are bound paths, quoted string constants, numbers or booleans (x:True, x:False). With OneWay or TwoWay the binding is re-evaluated when any bound argument changes, and the binding engine also reacts to a PropertyChanged notification raised with the function name, which is how a view model can force an update. Functions replace both value converters and MultiBinding from WPF.

<!-- BookFormat.ByLine is defined on the page above; Describe, Currency and the sys: prefix
     (xmlns:sys="using:System") are illustrative helpers for this snippet -->
<!-- Static function with two bound arguments: re-evaluated if Author or Year change -->
<TextBlock Text="{x:Bind local:BookFormat.ByLine(Author, Year), Mode=OneWay}" />

<!-- A system function, with a string constant (single quotes) as the first argument -->
<TextBlock Text="{x:Bind sys:String.Concat('Price: ', local:BookFormat.Price(Price))}" />

<!-- Two-way function binding needs BindBack -->
<TextBox Text="{x:Bind local:Currency.Display(Price), BindBack=local:Currency.Parse, Mode=TwoWay}" />

<!-- Pathless cast: passes the item itself as an argument -->
<TextBlock Text="{x:Bind local:BookFormat.Describe((vm:BookViewModel))}" />

Source: Functions in x:Bind with WinUI

The function must be accessible to the generated code, must have a return type that matches the target property, and its argument types must match the data passed in: the binding engine does not perform narrowing conversions. Overloads are matched by number of arguments, and the first overload with that count is used.

Event binding

An event handler can be bound to a method of the page or of any object reachable from it: Click="{x:Bind ViewModel.Refresh}". The method must not be overloaded and must match the event signature, or have no parameters, or have parameters whose types are assignable from the event’s parameter types. This removes many one-line handlers from the code-behind. It is not a replacement for commands when CanExecute is needed.

Other facts about compiled bindings

  • Bindings.Update() refreshes all compiled bindings and hooks up listeners, Bindings.Initialize() does that only if not yet initialized, and Bindings.StopTracking() unhooks the listeners of OneWay and TwoWay bindings.

  • A resource dictionary that uses {x:Bind} needs a code-behind class, because the generated code has to live somewhere.

  • x:Phase renders the parts of a list item template progressively, to improve panning performance in long lists.

  • {x:Bind} is a markup extension only: there is no API to create or change these bindings from code.

  • The framework converts a bool to a Visibility in a property binding without a converter (Windows 10 version 1607 or later as the target SDK). That conversion is not applied inside function bindings.

  • {x:Bind} cannot bind to DataContext, because its type, object, is not known at compile time.

Deferred loading with x:Load

x:Load removes an element from memory until it is needed. While it is unloaded, a small placeholder (about 600 bytes per x:Load element) marks its place in the tree. It has a similar visual effect to Visibility, but the element’s memory is released. Put it on elements that are not visible in the first frame, such as a details pane, a rarely used panel, or UI that appears only after an interaction.

Way to realize or unload Notes

x:Load="{x:Bind Flag, Mode=OneWay}"

true loads, false unloads. Do not name the element with the same identifier as the binding path.

FindName("Name")

Realizes an element. In WinUI 3 it does not work when the XAML root is a Window: use an x:Bind expression instead.

GetTemplateChild, a VisualState setter or storyboard

Other ways to realize the element.

UnloadObject(element)

On a Page or UserControl; also XamlMarkupHelper.UnloadObject. Releases the references held by the generated code.

The restrictions: the element needs an x:Name, it must derive from UIElement or FlyoutBase, it cannot be the root element of a Window, Page, UserControl or DataTemplate, and it cannot be used in a ResourceDictionary or in XAML loaded with XamlReader.Load. Nested x:Load elements are realized from the outside in. When an element is unloaded all of its state is discarded, so state must come from bindings or be re-applied in Loaded. Overusing it can cost more than it saves, so measure.

Backdrops: Mica, Acrylic and SystemBackdropElement

Materials are the visual effects that give a window depth. Mica is an opaque material that samples the desktop wallpaper once and blends it with the theme, so it is cheap; it is for the base layer of long-lived windows. Mica Alt tints the wallpaper more strongly and suits apps with a tabbed or custom title bar where the commanding area needs contrast with the title. Desktop Acrylic is semi-transparent, like frosted glass, and is for transient, light-dismiss surfaces such as flyouts and context menus.

Window.SystemBackdrop

The recommended way (since Windows App SDK 1.3) is to set the SystemBackdrop property to a XAML SystemBackdrop. The property exists on Window, Popup, FlyoutBase, MenuFlyoutPresenter, CommandBarFlyoutCommandBar, DesktopWindowXamlSource and ContentIsland.

</Window.SystemBackdrop>

<!-- Mica Alt -->
<Window.SystemBackdrop>
  <MicaBackdrop Kind="BaseAlt" />
</Window.SystemBackdrop>

<!-- Acrylic on a flyout -->
<Flyout>
  <Flyout.SystemBackdrop>
    <DesktopAcrylicBackdrop />
  </Flyout.SystemBackdrop>
</Flyout>

Behavior and rules

  • Mica needs Windows 11 build 22000 or later. On older Windows, with transparency turned off, in Battery Saver, on low-end hardware, while the window is deactivated and in High Contrast mode, Mica falls back to a solid color (SolidBackgroundFillColorBase for Mica, SolidBackgroundFillColorBaseAlt for Mica Alt). No code is needed for the fallback.

  • Set the background of every layer between the window and the place where Mica should show to transparent. A backdrop is not applied to a UI element: it shows only if all layers between the element and the window are transparent. Do not apply a window backdrop material more than once.

  • Content layers use LayerFillColorDefaultBrush, a low-opacity solid color, as their background. With Mica Alt, the commanding layer uses LayerOnMicaBaseAltFillColorDefaultBrush.

  • For the advanced cases (a custom MicaController or DesktopAcrylicController, SystemBackdropConfiguration, overriding TintColor or FallbackColor), the page documents the controller model. It needs a dispatcher queue, disposing the controller in Closed, and keeping the configuration’s IsInputActive and Theme in sync. MicaController.IsSupported() and DesktopAcrylicController.IsSupported() report system support.

App Lifecycle: Activation and Single Instance

A WinUI app is multi-instanced by default: launching it twice starts two processes with two main windows. The Windows App SDK app lifecycle API lets an app decide, at launch, whether to carry on or hand its activation to an instance that is already running, and receives rich activations (files, protocols, startup) in the same way.

The activation flow

The decision has to be taken before any window exists, so a single-instance WinUI app replaces the generated Main.

flowchart TD A["User launches Bookshelf.exe"] --> B["Program.Main: InitializeComWrappers"] B --> C["AppInstance.GetCurrent().GetActivatedEventArgs()"] C --> D["AppInstance.FindOrRegisterForKey with the app key"] D --> E{"keyInstance.IsCurrent?"} E -->|"yes: first instance"| F["Subscribe to AppInstance.Activated"] F --> G["Application.Start: new App()"] G --> H["App.OnLaunched: create MainWindow, Activate"] H --> I["Route the launch args: normal, file or protocol"] E -->|"no: another instance owns the key"| J["RedirectActivationToAsync on a worker thread"] J --> K["Wait without blocking the STA: CoWaitForMultipleObjects"] K --> L["Bring the first window to the foreground"] L --> M["Second process exits"] J -.->|"args delivered"| N["First instance: Activated event"] N --> O["Marshal to the UI thread, route the args, Activate the window"]

The first instance registers the key and keeps running. Every later process finds the key already registered, receives that instance from FindOrRegisterForKey, redirects its own activation arguments to it and exits without ever creating a window.

Replacing Main for single-instancing

The DISABLE_XAML_GENERATED_MAIN symbol (set in the project file above) disables the generated Program. In Windows App SDK 2.3.1 and later the symbol renames the generated entry point (to XamlGeneratedProgram.XamlGeneratedMain() in C#) instead of removing it, and a hand-written Main still works.

using System.Diagnostics;
using System.Runtime.InteropServices;
using Microsoft.UI.Dispatching;
using Microsoft.UI.Xaml;
using Microsoft.Windows.AppLifecycle;

namespace Bookshelf.WinUI;

public static class Program
{
    private const string InstanceKey = "Bookshelf.Desktop.Main";

    [STAThread]
    private static int Main(string[] args)
    {
        WinRT.ComWrappersSupport.InitializeComWrappers();

        if (DecideRedirection())
        {
            return 0;
        }

        Application.Start(_ =>
        {
            var context = new DispatcherQueueSynchronizationContext(DispatcherQueue.GetForCurrentThread());
            SynchronizationContext.SetSynchronizationContext(context);
            _ = new App();
        });

        return 0;
    }

    private static bool DecideRedirection()
    {
        AppActivationArguments args = AppInstance.GetCurrent().GetActivatedEventArgs();
        AppInstance keyInstance = AppInstance.FindOrRegisterForKey(InstanceKey);

        if (keyInstance.IsCurrent)
        {
            keyInstance.Activated += OnActivated;
            return false;
        }

        RedirectActivationTo(args, keyInstance);
        return true;
    }

    // Raised in the first instance when a later process redirects its activation to it.
    private static void OnActivated(object? sender, AppActivationArguments args) =>
        ActivationRouter.HandleFromAnyThread(args);

    [DllImport("kernel32.dll", CharSet = CharSet.Unicode)]
    private static extern IntPtr CreateEvent(IntPtr lpEventAttributes, bool bManualReset, bool bInitialState, string? lpName);

    [DllImport("kernel32.dll")]
    private static extern bool SetEvent(IntPtr hEvent);

    [DllImport("ole32.dll")]
    private static extern uint CoWaitForMultipleObjects(uint dwFlags, uint dwMilliseconds, ulong nHandles, IntPtr[] pHandles, out uint dwIndex);

    [DllImport("user32.dll")]
    private static extern bool SetForegroundWindow(IntPtr hWnd);

    // Redirect on another thread and wait with a non-blocking COM wait, so the STA keeps pumping messages.
    private static void RedirectActivationTo(AppActivationArguments args, AppInstance keyInstance)
    {
        IntPtr redirectEventHandle = CreateEvent(IntPtr.Zero, true, false, null);

        Task.Run(() =>
        {
            keyInstance.RedirectActivationToAsync(args).AsTask().Wait();
            SetEvent(redirectEventHandle);
        });

        const uint CWMO_DEFAULT = 0;
        const uint INFINITE = 0xFFFFFFFF;
        _ = CoWaitForMultipleObjects(CWMO_DEFAULT, INFINITE, 1, [redirectEventHandle], out _);

        // Give the first instance's window the foreground.
        using Process process = Process.GetProcessById((int)keyInstance.ProcessId);
        SetForegroundWindow(process.MainWindowHandle);
    }
}

Source: Create a single-instanced WinUI app with C# and App instancing with the app lifecycle API

Facts to know about the instancing model:

Topic Behavior

Keys

FindOrRegisterForKey registers a key for the current instance. Keys have no meaning to the API; the app chooses them. An instance has one key at a time (a new one overwrites the previous). If the key is already registered by another instance, the call returns that instance, and IsCurrent is false.

Redirection targets

Any instance can be a target, whether or not it registered a key. Redirection is not terminal in the Windows App SDK, unlike UWP: the redirecting process must exit itself. A request can be redirected more than once, so guard against redirect loops.

GetInstances

Returns all running instances that use the AppInstance API, for this version and user.

Arguments

RedirectActivationToAsync requires the AppActivationArguments to be passed explicitly, so the redirecting app can modify or replace them. The call is asynchronous and the caller must wait for it to finish, or the redirect fails.

Unregistering

UnregisterKey lets an instance stop being a target before it exits, which avoids a race with a process that is already closing.

Testing

Debugging in Visual Studio cannot start the same project twice, so test single-instancing by deploying and launching from the Start menu.

The docs sample uses DllImport; the .NET analyzers (SYSLIB1054) suggest LibraryImport for new code, which needs AllowUnsafeBlocks in the project. Redirect and exit as early as possible in Main, before any window or host is created.

Routing activations

All entry points (the first launch, a redirected launch, a file, a protocol link) end in the same routine. The kinds that unpackaged apps support are Launch (command line, double click, ShellExecute), File, Protocol and StartupTask. Packaged apps support all 44 UWP activation kinds and always receive arguments in the Activated event and in GetActivatedEventArgs.

using Bookshelf.Desktop.ViewModels;
using Microsoft.Extensions.DependencyInjection;
using Microsoft.Windows.AppLifecycle;
using Windows.ApplicationModel.Activation;

namespace Bookshelf.WinUI;

public static class ActivationRouter
{
    /// <summary>Called from a thread that is not necessarily the UI thread.</summary>
    public static void HandleFromAnyThread(AppActivationArguments args)
    {
        // Marshal explicitly: the lifecycle documentation does not state which thread raises Activated.
        if (App.Current.MainWindow?.DispatcherQueue is { } queue)
        {
            queue.TryEnqueue(() => Handle(args));
        }
    }

    public static void Handle(AppActivationArguments args)
    {
        switch (args.Kind)
        {
            case ExtendedActivationKind.Protocol when args.Data is IProtocolActivatedEventArgs protocol:
                ShowBookFromUri(protocol.Uri);
                break;

            case ExtendedActivationKind.File when args.Data is IFileActivatedEventArgs file:
                // Import the first file: file.Files[0] is an IStorageItem.
                break;

            case ExtendedActivationKind.Launch when args.Data is ILaunchActivatedEventArgs launch:
                // launch.Arguments holds the raw command-line text.
                break;
        }

        // A reactivation should always bring the window forward.
        App.Current.MainWindow?.Activate();
    }

    // bookshelf://book/42 selects the book with Id 42.
    private static void ShowBookFromUri(Uri uri)
    {
        if (uri.Host == "book" && int.TryParse(uri.AbsolutePath.Trim('/'), out int id))
        {
            BooksViewModel viewModel = App.Current.Services.GetRequiredService<BooksViewModel>();
            viewModel.SelectedBook = viewModel.Books.FirstOrDefault(b => b.Id == id);
        }
    }
}

The MVVM Toolkit with WinUI

The MVVM Toolkit works the same on WinUI as on WPF, and it is the library that Microsoft’s own WinUI guidance points to: the Windows data binding and MVVM page recommends it for ObservableObject, [ObservableProperty] and [RelayCommand], and a complete tutorial refactors the WinUI Notes app to it. Details of the library are on the MVVM Toolkit page; this section covers what is specific to WinUI.

  • Use partial properties, not fields. A field with [ObservableProperty] generates code that is not AOT compatible in WinRT scenarios, UWP and WinUI 3 included, and the analyzer reports MVVMTK0045. A partial property ([ObservableProperty] public partial string? Name { get; set; }) lets the CsWinRT generators produce the WinRT marshalling code. The Bookshelf view models already use the partial property form.

  • Expose the view model as a property of the page and bind with {x:Bind ViewModel.Property, Mode=OneWay}. The INotifyPropertyChanged that ObservableObject implements is what OneWay and TwoWay listen to.

  • Commands bind directly: Command="{x:Bind ViewModel.AddBookCommand}". The generated command types are IRelayCommand and IAsyncRelayCommand, which implement ICommand.

  • Collections: an ObservableCollection<T> bound OneTime is enough when the property itself never changes, because the ListView tracks INotifyCollectionChanged independently of the binding mode.

  • Dialogs and navigation stay behind interfaces (IDialogService), implemented over ContentDialog and Frame in the WinUI project, so that BooksViewModel remains free of UI types.

  • Threading: UI objects belong to the thread of their DispatcherQueue. A view model that raises PropertyChanged from a background thread must marshal with DispatcherQueue.TryEnqueue, not WPF’s Dispatcher. The threading page of this section covers the details.

  • Unit tests of the view models need no WinUI types, and the toolkit tutorial adds a separate unit test project.

A command that must read the view model’s state before it runs, for the status line, looks like the one on the MVVM Toolkit page:

using System.Collections.ObjectModel;
using Bookshelf.Core;
using CommunityToolkit.Mvvm.ComponentModel;
using CommunityToolkit.Mvvm.Input;

namespace Bookshelf.Desktop.ViewModels;

public partial class BookViewModel(Book book) : ObservableObject
{
    public Book Model { get; } = book;
    public int Id => Model.Id;

Packaged and Unpackaged WinUI Apps

A WinUI 3 app can run in two ways. A packaged app is built into an MSIX package and installed with package identity. An unpackaged app is a plain executable (it can be installed by MSI, a zip or an installer, or run from a folder), and a third mode, packaged with external location, gives an otherwise unpackaged app a package identity. The Visual Studio template "WinUI Blank App (Packaged)" and the single-project MSIX feature produce a packaged app without a separate packaging project: the manifest and images live in the app project and EnableMsixTooling turns the tooling on.

An unpackaged project differs from the project above by one property:

<PropertyGroup>

Source: Deployment guide for apps packaged with external location or unpackaged (WindowsPackageType); WindowsAppSDKSelfContained is named in the Windows App SDK 2.0 release notes and is covered with the other deployment options on the .NET publishing page of this section.

The runtime installer is silent when asked: WindowsAppRuntimeInstall.exe --quiet, and --force replaces the MSIX packages and shuts down running Windows App SDK processes. Without administrator rights it installs for the current user only; with them it provisions the packages for all users. Its common return codes are 0x0 (success), 0x80073d06 (a package failed) and 0x80070005 (system-wide install without elevation). An Experimental or Preview runtime needs sideloading (Developer Mode) enabled.

The first MSIX build of a packaged app is made with MSBuild: the important switch for the single-project layout is /p:GenerateAppxPackageOnBuild=true, without which the build succeeds but no package is produced. The packaging, signing and distribution of the result are on the MSIX Packaging & Signing and Distribution Channels pages.

Trimming and Native AOT

The single-instancing page warns that apps compiled with trimming in release mode have known crashes in the Windows App SDK, and advises setting PublishTrimmed to false in the .pubxml files. Native AOT, by contrast, is supported: since Windows App SDK 1.6 the .NET PublishAot property works for WinUI 3 apps. Because AOT builds on trimming, the same trimming work applies, some libraries aren’t AOT-compatible, and the 1.6 notes list a known hang after page navigation under AOT. Test the published output carefully before turning either option on.

Pitfalls

  • Stale UI after a binding that never updates. The default of {x:Bind} is OneTime. A property that changes needs Mode=OneWay (or x:DefaultBindMode), and a source that implements INotifyPropertyChanged.

  • Looking for the DataContext. {x:Bind} does not use it. The view model must be a property or field of the page, or the template’s x:DataType must name its type. A DataTemplate cannot see the page; use a function, an event binding to a method of the item, or {Binding} with ElementName to reach it.

  • ExtendsContentIntoTitleBar in XAML. It produces an error. Set it in the constructor, in code.

  • ContentDialog throws. XamlRoot must be set, and only one ContentDialog can be open per window.

  • Treating the Window like a control. No DataContext, Resources, Loaded, FindName or RequestedTheme. Put those on the root content element. FindName cannot realize an x:Load element when the XAML root is a Window.

  • Duplicate navigation. Handling ItemInvoked and navigating unconditionally reloads the page and adds back-stack entries; compare CurrentSourcePageType first, or navigate from SelectionChanged.

  • Constructor injection into pages. Frame.Navigate uses the parameterless constructor. Resolve the view model from the container in the page, or navigate ViewModel-first.

  • Mica that does not show. An opaque background on any layer between the window and the element hides it. Set those layers to transparent and use the content-layer brush where a layer is wanted.

  • Redirecting too late. A single-instance check after the window or the host has started wastes time and can flash a second window. Keep Main minimal and finish the redirect before new App(). Test with a deployed app.

  • Field-based [ObservableProperty]. Reports MVVMTK0045 in WinUI because it is not AOT compatible; use partial properties.

  • Unpackaged app crashes at start. The runtime is missing or the bootstrapper was not initialized. Install the runtime or check that WindowsPackageType is None. Packaged-only APIs such as ApplicationData.Current throw without identity.

  • Window size in the wrong unit. AppWindow.Resize takes physical pixels, so a fixed number is a different size at 150% scale. Use the documented logical-size APIs only when they leave the experimental channel.

  • Blocking the UI thread in Activated. The handler may not run on the UI thread. Marshal with DispatcherQueue.TryEnqueue before touching the view model or any control.

What the Official Documentation Does Not Provide

  • There is no Microsoft Learn sample of the Generic Host in a WinUI 3 app; the WinUI MVVM tutorial uses a plain ServiceCollection, which is what this page shows. The host variant is a pattern described on the dependency injection page.
