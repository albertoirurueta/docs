In-App Purchases and Subscriptions with StoreKit 2

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production; see the section bibliography for the reference material consulted while preparing these pages.

FieldNotes is free, with an optional subscription, FieldNotes Pro, that unlocks unlimited notebooks, the augmented-reality map on Augmented Reality with ARKit and RealityKit and end-to-end encrypted note sharing from Security and Privacy. This page builds the store with StoreKit 2, the Swift-concurrency API that replaced the original SKPaymentQueue API, using the 27 releases (iOS, iPadOS, macOS, watchOS and visionOS 27), Xcode 27 and Swift 6.4, with the app’s deployment minimum of 26. The monthly-with-12-month-commitment billing plan needs 26.4 and the new offer-code redemption API needs 27, so both are guarded with if #available.

The page adds one type to FieldNotesServices: StoreManager, an @Observable @MainActor class that loads the two Pro products, runs purchases, listens for transactions from launch, and publishes whether the person is entitled to Pro. A StoreKit configuration file, Products.storekit, lets all of it run in Xcode without App Store Connect.

How a Purchase Flows

In StoreKit 2 the App Store signs every transaction as a JWS (JSON Web Signature, the same format as a JWT, see JWT and JOSE). StoreKit verifies the signature on the device before the app sees it and hands the app a VerificationResult<Transaction>: .verified or .unverified. There is no receipt to parse. A purchase can complete in the app, but it can also complete elsewhere: after Ask to Buy approval, on another device, as a renewal at 3 a.m., or as a refund. All of those arrive through Transaction.updates, which is why the listener has to run from launch.

StoreManager

StoreManager lives in FieldNotesServices so every target, including the widget, can ask whether Pro is unlocked. The FieldNotesApp scene owns one instance for the app’s lifetime.

// Packages/FieldNotesKit/Sources/FieldNotesServices/Store/StoreManager.swift
import Foundation
import Observation
import StoreKit

@Observable @MainActor
public final class StoreManager {
    public static let productIDs: [Product.ID] = [
        "com.example.fieldnotes.pro.monthly",
        "com.example.fieldnotes.pro.yearly",
    ]
    /// The "FieldNotes Pro" group ID from App Store Connect (and from Products.storekit).
    public static let proGroupID = "21500001"

    public private(set) var products: [Product] = []
    public private(set) var isPro = false
    public private(set) var proRenewalState: Product.SubscriptionInfo.RenewalState?

    @ObservationIgnored private var updatesTask: Task<Void, Never>?

    public init() {
        // Start listening before anything else, so no transaction is missed.
        updatesTask = Task { [weak self] in
            for await result in Transaction.updates {
                await self?.handle(result)
            }
        }
    }

    public func loadProducts() async {
        do {
            products = try await Product.products(for: Self.productIDs)
                .sorted { $0.price < $1.price }
        } catch {
            products = []          // offline or misconfigured: the store UI shows a retry button
        }
    }
}

See Apple Developer Documentation — products(for:) and Apple Developer Documentation — Implementing a store in your app using the StoreKit API.

Product.products(for:) returns only the IDs the App Store knows for the current storefront, localized, with displayName, description, displayPrice (already formatted in the person’s currency) and, for subscriptions, a subscription property with the period, group and offers. Never hard-code prices.

The Task created in init inherits the main actor, so handle(_:) runs on the main actor and can update isPro directly. The [weak self] capture keeps the loop from retaining the manager; in FieldNotes the manager lives as long as the app, so the task never ends. How tasks inherit isolation is covered on Async/Await and Tasks and Concurrency in Apps.

The app creates it at launch and injects it next to the note store:

// FieldNotes/FieldNotesApp.swift (excerpt)
import FieldNotesServices
import SwiftUI

@main
struct FieldNotesApp: App {
    @State private var store = AppServices.shared.store   // the single owner, see Background Execution
    @State private var storeManager = StoreManager()   // Transaction.updates starts here

    var body: some Scene {
        WindowGroup {
            ContentView()
                .environment(store)
                .environment(storeManager)
                .task {
                    await storeManager.loadProducts()
                    await storeManager.refreshEntitlements()
                }
        }
    }
}

See Apple Developer Documentation — updates.

Purchasing

A purchase needs a UI context to anchor the payment sheet. Product.purchase(options:) finds one on its own on iOS, macOS and watchOS but does not exist on visionOS, and the purchase(confirmIn:options:) variants take a UIKit scene or an AppKit window. The portable choice in SwiftUI is PurchaseAction, read from the environment as @Environment(\.purchase). StoreManager accepts it as a parameter, so the manager stays free of UI code:

// StoreManager.swift (continued)
extension StoreManager {
    public enum PurchaseOutcome { case unlocked, pending, cancelled }

    public func purchase(_ product: Product, using purchaseAction: PurchaseAction,
                         accountID: UUID? = nil) async throws -> PurchaseOutcome {
        var options: Set<Product.PurchaseOption> = []
        if let accountID { options.insert(.appAccountToken(accountID)) }   // ties it to the FieldNotes account

        switch try await purchaseAction(product, options: options) {
        case .success(let verification):
            await handle(verification)
            return isPro ? .unlocked : .pending
        case .pending:
            return .pending          // Ask to Buy or Strong Customer Authentication; arrives via updates
        case .userCancelled:
            return .cancelled
        @unknown default:
            return .cancelled
        }
    }
}

// FieldNotes/Views/ProUpgradeButton.swift
struct ProUpgradeButton: View {
    @Environment(StoreManager.self) private var storeManager
    @Environment(\.purchase) private var purchase
    let product: Product

    var body: some View {
        Button("Subscribe for \(product.displayPrice)") {
            Task { _ = try? await storeManager.purchase(product, using: purchase) }
        }
    }
}

See Apple Developer Documentation — PurchaseAction, Apple Developer Documentation — purchase(options:) and Apple Developer Documentation — Product.PurchaseResult.

.appAccountToken(_:) stores a UUID of the app’s choosing in the signed transaction. FieldNotes passes the account ID from AccountManager, so its server can match App Store Server Notifications to the right account. .pending is not a failure: the transaction may still succeed hours later and will arrive through Transaction.updates.

Verifying and Finishing Transactions

handle(_:) is the single place where a transaction changes what the person can do. It is called from the purchase result and from the updates listener.

// StoreManager.swift (continued)
extension StoreManager {
    func handle(_ result: VerificationResult<Transaction>) async {
        switch result {
        case .verified(let transaction):
            await refreshEntitlements()
            await transaction.finish()            // tell the App Store the content was delivered
        case .unverified(let transaction, let error):
            // Signed by someone else, or for another device: never unlock anything.
            print("Unverified transaction \(transaction.id): \(error)")
        }
    }
}

See Apple Developer Documentation — Transaction, Apple Developer Documentation — VerificationResult and Apple Developer Documentation — finish().

Only finish a transaction after the app has delivered what was bought. An unfinished transaction is delivered again through Transaction.updates at the next launch, which is the retry mechanism. For consumables, finishing is essential: until it happens the same product cannot be bought again.

On-device verification protects against a tampered app or a replayed transaction on another device, but a jailbroken device can still lie to its own app. When Pro unlocks a server feature, such as sharing through the FieldNotes server, the server must also check the purchase with the App Store Server API or App Store Server Notifications V2; the VerificationResult also exposes the raw jwsRepresentation for that purpose.

Entitlements and Subscription Status

Transaction.currentEntitlements yields the latest transaction for every product the person is currently entitled to: active subscriptions, owned non-consumables, including purchases made on other devices and through Family Sharing. It is the source of truth for isPro:

// StoreManager.swift (continued)
extension StoreManager {
    public func refreshEntitlements() async {
        var entitled = false
        for await result in Transaction.currentEntitlements {
            guard case .verified(let transaction) = result,
                  Self.productIDs.contains(transaction.productID),
                  transaction.revocationDate == nil,              // not refunded
                  !transaction.isUpgraded else { continue }      // superseded by another product
            if let expiry = transaction.expirationDate, expiry < .now { continue }
            entitled = true
        }
        isPro = entitled
    }
}

See Apple Developer Documentation — currentEntitlements, Apple Developer Documentation — revocationDate and Apple Developer Documentation — isUpgraded.

isPro is published through Observation, so every view that reads it re-renders when a renewal or refund arrives. To check a single product, Transaction.currentEntitlements(for:) (18.4 and later, so always available at FieldNotes’s minimum) filters by product ID.

Entitlement answers whether Pro is active. Subscription status answers how: subscribed, in a billing grace period, in billing retry, expired or revoked. FieldNotes uses it to show a "Payment problem, update your payment method" banner while a subscription is in grace period, instead of silently locking the person out:

// StoreManager.swift (continued)
extension StoreManager {
    public func refreshStatus() async {
        let statuses = (try? await Product.SubscriptionInfo.status(for: Self.proGroupID)) ?? []
        proRenewalState = statuses
            .filter { if case .verified = $0.transaction { true } else { false } }
            .map(\.state)
            .first
    }
}

// .subscriptionStatusTask(for: StoreManager.proGroupID) { taskState in

See Apple Developer Documentation — Product.SubscriptionInfo.Status, Apple Developer Documentation — Product.SubscriptionInfo.RenewalState and Apple Developer Documentation — subscriptionStatusTask(for:priority:action:).

A person with Family Sharing may have more than one status for the same group (their own and a family member’s); FieldNotes takes the first verified one, which is enough for a banner.

Restoring Purchases with AppStore.sync()

Because currentEntitlements already includes purchases made on other devices, most people never need to restore anything. Merchandising with StoreKit Views

StoreKit’s SwiftUI views load products, format prices, show the right legal text and buttons for each platform, and run the purchase. They are the fastest way to a store that passes review.

Monthly Subscriptions with a 12-Month Commitment

The 2026 billing option lets people pay for a yearly subscription monthly, in exchange for committing to twelve payments. It is not a new product: in App Store Connect you enable the monthly billing plan on an existing 1-year subscription, so com.example.fieldnotes.pro.yearly keeps its product ID and now offers two pricing terms: billed up front, or billed monthly with a 12-month commitment. Cancelling stops the commitment from renewing, but the remaining payments of the current commitment are still billed.

The APIs arrived in 26.4 and need an app built with the Xcode 26.5 SDK or later. The billing plan is offered worldwide except in the United States and Singapore; in those storefronts pricingTerms contains only the up-front entry. Because FieldNotes’s minimum is 26, every use is guarded:

// StoreManager.swift (continued)
extension StoreManager {
    /// The yearly product's monthly commitment plan, if this storefront offers it.
    @available(iOS 26.4, macOS 26.4, watchOS 26.4, visionOS 26.4, *)
    public func commitmentTerms(for product: Product) -> Product.SubscriptionInfo.PricingTerms? {
        product.subscription?.pricingTerms.first { $0.billingPlanType == .monthly }
    }

    @available(iOS 26.4, macOS 26.4, watchOS 26.4, visionOS 26.4, *)
    public func purchaseCommitment(_ product: Product, using purchaseAction: PurchaseAction) async throws {
        let result = try await purchaseAction(product, options: [.billingPlanType(.monthly)])
        if case .success(let verification) = result { await handle(verification) }
    }
}

// FieldNotes/Views/CommitmentOfferRow.swift
struct CommitmentOfferRow: View {
    @Environment(StoreManager.self) private var storeManager
    @Environment(\.purchase) private var purchase
    let yearly: Product

    var body: some View {
        if #available(iOS 26.4, macOS 26.4, watchOS 26.4, visionOS 26.4, *),
           let terms = storeManager.commitmentTerms(for: yearly) {
            VStack(alignment: .leading) {
                // Both amounts must be visible before the person subscribes.
                Text("\(terms.billingDisplayPrice) per month for 12 months")
                Text("Total commitment: \(terms.commitmentInfo.displayPrice)")
                    .font(.footnote).foregroundStyle(.secondary)

}

See Apple Developer Documentation — Supporting monthly subscriptions with a 12-month commitment Apple Developer Documentation — Product.SubscriptionInfo.PricingTerms and WWDC26 — What’s new in Apple In-App Purchase.

With SubscriptionStoreView, a single modifier makes the store feature the commitment plan instead:

SubscriptionStoreView(groupID: StoreManager.proGroupID)
    .preferredSubscriptionPricingTerms { _, subscriptionInfo in
        subscriptionInfo.pricingTerms.first { $0.billingPlanType == .monthly }
    }

See Apple Developer Documentation -- preferredSubscriptionPricingTerms(_:).

In the app, each monthly payment is an ordinary transaction that grants one month; the entitlement logic in refreshEntitlements() needs no change, because it already checks the transaction’s own expirationDate. The transaction’s commitmentInfo (billingPeriodNumber, totalBillingPeriods, price, expirationDate) is only for showing progress such as "payment 4 of 12". Never use commitmentInfo.expirationDate to decide access: a billing issue that recovers late moves it. Billing grace period does not apply to commitment plans, so revoke access while a monthly payment is in billing retry.

@available(iOS 26.4, macOS 26.4, watchOS 26.4, visionOS 26.4, *)
func commitmentProgress(of transaction: Transaction) -> String? {
    guard transaction.billingPlanType == .monthly, let info = transaction.commitmentInfo else { return nil }
    return "Payment \(info.billingPeriodNumber) of \(info.totalBillingPeriods)"
}

See Apple Developer Documentation — Transaction.CommitmentInfo and Apple Developer Documentation — Managing the life cycle of monthly subscriptions with a 12-month commitment.

The first time someone subscribes to a commitment plan, the system shows a one-time disclosure sheet with the number of payments and cancellation terms; the app does nothing for it. On the server, the plan adds billingPlanType and commitmentInfo fields to the decoded JWS transaction and renewal info, and the life-cycle article lists which App Store Server Notifications (DID_RENEW, DID_CHANGE_RENEWAL_STATUS, DID_FAIL_TO_RENEW, EXPIRED) to handle.

StoreKit Configuration Files and Testing in Xcode

A StoreKit configuration file describes products, subscription groups, prices and offers locally. When a scheme’s Run > Options > StoreKit Configuration points at it, StoreKit talks to Xcode’s local test environment instead of the App Store: no network, no sandbox account, instant renewals, and a Transaction Manager (Debug > StoreKit > Manage Transactions) to approve Ask to Buy, refund, expire or fail renewals. Create one with File > New > File from Template > StoreKit Configuration File, name it Products.storekit, and either add the products by hand or sync them from App Store Connect.

The file is JSON that Xcode’s editor maintains; edit it in the editor, not by hand. An abbreviated excerpt shows its shape:

App Review and Payment Rules

The App Review Guidelines' section 3.1 governs payments. The rules FieldNotes has to follow:

  • 3.1.1: digital content and features used in the app, such as FieldNotes Pro, must be sold through In-App Purchase. Physical goods and person-to-person services use other payment methods.

  • 3.1.2: auto-renewable subscriptions must provide ongoing value, work on all the app’s supported devices, and clearly state what the person gets, the price, the period and, for commitment plans, the total commitment before purchase. Terms of use and a privacy policy link must be reachable from the paywall.

  • Restore: a way to restore purchases must exist (AppStore.sync() or the .restorePurchases store button).

  • Regional exceptions: some storefronts allow links to, or alternative, external payment. StoreKit’s External Purchase APIs implement those programmes and require an entitlement per region; FieldNotes does not use them.

See Apple Developer — App Review Guidelines and Apple Developer Documentation — External Purchase.

In-App Purchases are submitted for review with the app. In 2026 App Store Connect groups products, in-app events and custom product pages into one review submission, and the App Store Connect API’s reviewSubmissions resources cover In-App Purchases too. Submission, metadata and TestFlight are covered on App Store Connect, TestFlight and App Review.
