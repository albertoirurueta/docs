App Store Connect, TestFlight and App Review

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production; see the section bibliography for the reference material consulted while preparing these pages.

A signed archive on a Mac is not yet an app anyone can install. This page follows FieldNotes from that archive to the App Store: creating the app record in App Store Connect, uploading and processing the build, testing it with TestFlight, filling in the product page’s privacy, accessibility and age-rating declarations, passing App Review and releasing in phases. It uses this section’s 2026 baseline: iOS, iPadOS, macOS, watchOS and visionOS 27, Xcode 27 and Swift 6.4, with a deployment minimum of 26. App Store rules change several times a year, so every requirement below gives the date it applies from and its official source, checked on 2026-09-24.

The signing that makes an upload possible (certificates, the App Store Connect provisioning profile, FieldNotes.entitlements, Info.plist) is covered on Membership, Signing, Capabilities and Info.plist, and automating this page’s steps on CI/CD with Xcode Cloud and the Command Line. The page adds ExportOptions.plist and two small Swift helpers to FieldNotes: FieldNotesInstallSource, which tells the app whether it came from the App Store, TestFlight or an alternative source, and ReviewPromptModifier, which asks for a rating at a sensible moment. The React Native view of the same pipeline is in the iOS Release Builds section of Building and Publishing.

From Archive to the App Store

Every FieldNotes release follows the same path. A build is archived and uploaded, Apple processes it, the team tests it internally, a wider group tests it after a light beta review, and the final build is submitted for App Review and released gradually:

Figure: The release sequence

The steps run in this order because each gate is cheaper than the next. Processing catches signing and packaging errors in minutes. Internal testers need no review. External testing needs a beta review, which is lighter than App Review and usually required only for the first build of each version. App Review is last, and phased release limits the damage of a bug that got past all of them.

The App Record

Before the first upload, an Account Holder, Admin or App Manager creates the app record in App Store Connect (Apps > + > New App). The record holds everything that is not in the binary: the platforms, the name, the primary language, the bundle ID it accepts builds for, an internal SKU, and which team members may access it. FieldNotes is one record with the iOS, macOS and visionOS platforms, so one purchase covers every device; watch-only apps count as part of the iOS platform. The Account Holder must have accepted the latest agreements, or the New App button does nothing useful.

The product page itself (subtitle, description, keywords, screenshots, the privacy policy and support URLs) is localized per language in the same record, separately from the app’s String Catalogs (see Localization with String Catalogs). New in 2026, product pages gain header and search-result asset placements and a preview tool; see WWDC26 — Enhance your presence on the App Store.

Everything in App Store Connect is also available through the App Store Connect API, a REST API that CI and scripts use instead of the website. Each request carries a JSON Web Token signed with ES256 by a private key downloaded from Users and Access > Integrations. The token’s header and payload look like this, with placeholders for the team’s own values; tokens must expire within 20 minutes:

{ "alg": "ES256", "kid": "<KEY_ID>", "typ": "JWT" }
{
  "iss": "<ISSUER_ID>",
  "iat": 1790200000,
  "exp": 1790201000,
  "aud": "appstoreconnect-v1",
  "scope": ["GET /v1/apps?filter[bundleId]=com.example.fieldnotes"]
}
# ASC_TOKEN holds a JWT signed with the .p8 key; the key file never enters the repository.
# -g (--globoff) stops curl from treating the brackets in filter[bundleId] as a URL glob.
curl -sS -g --fail-with-body -H "Authorization: Bearer $ASC_TOKEN" \
  "https://api.appstoreconnect.apple.com/v1/apps?filter[bundleId]=com.example.fieldnotes" \
  | jq '.data[0].id'
# "<APP_ID>"

See Apple Developer Documentation — Generating Tokens for API Requests and Apple Developer Documentation — List apps.

Needs a paid membership and an API key with a role that allows the call (App Manager or Admin for most of this page). The optional scope claim limits what a leaked token can do, which is worth setting for CI.

Uploading a Build

Archive, Organizer and Distribute App

An archive is a Release build plus its debug symbols, stored as an .xcarchive. In Xcode, choose the FieldNotes scheme and the Any iOS Device destination (or My Mac for the Mac build), then Product > Archive. The archive opens in the Organizer (Window > Organizer), where:

  • Validate App runs the automated upload checks without uploading: signature, bundle ID, entitlements against the profile, icons, the privacy manifest’s required-reason declarations.

  • Distribute App re-signs the archive for the chosen method and uploads it. App Store Connect makes the build available for TestFlight and App Store submission; TestFlight Internal Only marks it so it can never go further than the internal group, which is useful for experimental branches.

  • The custom path lets you choose whether to upload symbols (keep it on: crash reports are symbolicated with them) and whether Xcode may increment the build number when it collides with an earlier upload.

Every upload of the same version needs a new CFBundleVersion. FieldNotes keeps MARKETING_VERSION = 2.2.0 for the whole release and bumps CURRENT_PROJECT_VERSION (42, 43, …​) for each TestFlight build.

See Apple Developer Documentation — Distributing your app for beta testing and releases.

xcodebuild -exportArchive

The Organizer’s choices can be written down in an export options property list, so a script produces the same result. FieldNotes keeps its ExportOptions.plist next to the project:

Processing

After the upload, App Store Connect processes the build: it checks it again, prepares thinned variants for each device, and symbolicates. That takes minutes to an hour. The build then appears under TestFlight with status VALID, or an email explains why it is INVALID. Scripts can wait for it:

# The newest builds of FieldNotes and their processing state.
curl -sS -G -H "Authorization: Bearer $ASC_TOKEN" \
  "https://api.appstoreconnect.apple.com/v1/builds" \
  --data-urlencode "filter[app]=<APP_ID>" \
  --data-urlencode "sort=-uploadedDate" --data-urlencode "limit=3" \
  | jq -r '.data[] | "\(.attributes.version) \(.attributes.processingState)"'

# 42 VALID
# 41 VALID

Feedback. On iOS, iPadOS, macOS and visionOS, testers with TestFlight 2.3 or later send feedback from the TestFlight app or by taking a screenshot inside the beta app; crashes are sent with the tester’s comment. In-App Purchases always run in the sandbox environment, so testers are never charged (see In-App Purchases and Subscriptions with StoreKit 2), and requestReview does nothing. FieldNotes checks where it was installed from, both to show a "screenshot to send feedback" hint to testers and, in the EU, to adapt to alternative distribution:

// FieldNotes/Support/FieldNotesInstallSource.swift
import StoreKit
import os
#if os(iOS) && canImport(MarketplaceKit)
import MarketplaceKit
#endif

/// Where this copy of FieldNotes came from.
enum FieldNotesInstallSource: Sendable, Equatable {
    case appStore
    case testFlightOrDevelopment      // StoreKit's sandbox environment
    case xcodeStoreKitTesting         // a StoreKit configuration file in Xcode
    case alternativeMarketplace(String)
    case web
    case unknown

    private static let log = Logger(subsystem: "com.example.fieldnotes", category: "ui")

    static func current() async -> FieldNotesInstallSource {
        #if os(iOS) && canImport(MarketplaceKit)
        // iOS and iPadOS 17.4 and later: the distributor, including EU alternative sources.
        do {
            switch try await AppDistributor.current {
            case .appStore: return .appStore
            case .testFlight: return .testFlightOrDevelopment
            case .marketplace(let bundleID): return .alternativeMarketplace(bundleID)
            case .web: return .web
            case .other: break                // development builds and other sources: ask StoreKit
            @unknown default: break
            }
        } catch {
            log.error("AppDistributor unavailable: \(error.localizedDescription, privacy: .public)")
        }
        #endif
        do {
            let result = try await AppTransaction.shared
            let transaction: AppTransaction
            switch result {
            case .verified(let verified):
                transaction = verified
            case .unverified(let unverified, let error):
                log.error("Unverified app transaction: \(error.localizedDescription, privacy: .public)")
                transaction = unverified          // good enough to pick UI; never to unlock content
            }
            switch transaction.environment {
            case .production: return .appStore
            case .sandbox: return .testFlightOrDevelopment
            case .xcode: return .xcodeStoreKitTesting
            default: return .unknown
            }
        } catch {
            log.error("AppTransaction unavailable: \(error.localizedDescription, privacy: .public)")
            return .unknown
        }
    }
}

See Apple Developer Documentation — environment and Apple Developer Documentation — AppDistributor.

AppTransaction.shared may need the network and throws when the person isn’t signed in to the App Store, so the result is computed once in a .task and cached, and every failure path logs and falls back to .unknown rather than blocking the UI. The distinction is for presentation only: whether the person owns Pro is still decided by StoreManager's verified transactions.

Age rating

Every app answers the age-rating questionnaire under App Information: content descriptors with their frequency, in-app controls (parental controls, age assurance) and capabilities. App Store Connect turns the answers into Apple’s age rating and any regional ratings. An unrated app can’t be published on the App Store. Two dated changes apply in 2026:

  • Updated questions, required since January 31, 2026. Apple moved to a new age-rating system shown on devices running the 26 releases, and developers had to answer the updated questions by January 31, 2026 to avoid an interruption when submitting updates. Source: Apple Developer — Upcoming Requirements ("Age Rating Updates").

  • Social media questions, added July 9, 2026 and required from September 2026. To support Time Allowances in iOS 27, iPadOS 27 and macOS 27, the questionnaire asks whether the app redistributes, amplifies or lets people interact with user-generated content through a feed. Responses are required for new apps and updates, and for notarization for alternative distribution, starting in September 2026. Source: Apple Developer News — Age rating questionnaire now includes social media questions.

FieldNotes has no objectionable content, no feed and no public profiles. People share notebooks only with invited collaborators, so it answers No to the social media capability, declares no user-generated content that strangers can see, and gets the lowest rating.

See Apple Developer Documentation — Set an app age rating and Apple Developer Documentation — Age ratings values and definitions.

Submitting for review

To submit, create the App Store version (2.2.0) in the record, choose the build, fill in What’s New, and complete App Review Information: contact details, a demo account for anything behind sign-in, and notes that explain non-obvious features. For FieldNotes the notes explain how to create a shared notebook with the second demo account and where Pro features are. Asking for ratings

Ratings accumulate per version, and a release is a good moment to ask satisfied people for one. StoreKit decides whether the prompt actually appears (at most three times in 365 days) and it never appears in TestFlight builds, so the app only chooses the moment: never right after launch or on a button tap, but after a success. FieldNotes asks once per version, after the person has created ten notes in that version. It counts notes the person creates, not store.notes.count: loading the library at launch fills the list in one step, and a sync can add notes from other devices, and neither is a moment of success:

// FieldNotes/Support/ReviewPromptModifier.swift
import SwiftUI
import StoreKit
import FieldNotesModel
import FieldNotesServices

#if !os(watchOS)
enum ReviewPrompt {
    static let createdNotesKey = "notesCreatedSinceReviewPrompt"
    static let threshold = 10
}

extension NoteStore {
    /// The New Note button calls this instead of `add(_:)`; loading and syncing don't go through it.
    func addCreatedByPerson(_ note: Note) {
        add(note)
        let defaults = UserDefaults.standard
        defaults.set(defaults.integer(forKey: ReviewPrompt.createdNotesKey) + 1,
                     forKey: ReviewPrompt.createdNotesKey)
    }
}

struct ReviewPromptModifier: ViewModifier {
    @Environment(\.requestReview) private var requestReview
    @AppStorage(ReviewPrompt.createdNotesKey) private var createdNotes = 0
    @AppStorage("lastReviewPromptVersion") private var lastPromptedVersion = ""

    private var currentVersion: String { BuildIdentity().version }

    func body(content: Content) -> some View {
        content.onChange(of: createdNotes) { _, newCount in
            guard newCount >= ReviewPrompt.threshold,
                  lastPromptedVersion != currentVersion else { return }
            lastPromptedVersion = currentVersion
            createdNotes = 0                     // the next version counts from zero again
            requestReview()
        }
    }
}

extension View {
    func promptsForReviewAfterTenNotes() -> some View { modifier(ReviewPromptModifier()) }
}

#Preview {
    Text("Notes")
        .promptsForReviewAfterTenNotes()
}
#endif

See Apple Developer Documentation — RequestReviewAction and Apple Developer Documentation — requestReview.

FieldNotes applies .promptsForReviewAfterTenNotes() to the split view in ContentView. The counter lives in UserDefaults, so it survives relaunches, and @AppStorage observes the key, so the modifier sees each increment that addCreatedByPerson(_:) makes. BuildIdentity is the helper from Membership, Signing, Capabilities and Info.plist.

EU Alternative Distribution

In the European Union, under the Digital Markets Act, iOS and iPadOS apps can also be distributed outside the App Store, in brief:

  • Alternative app marketplaces. Apps that install other developers' apps. Operating one needs Apple’s Alternative App Marketplace Entitlement, an organization membership and financial qualifications; marketplaces use the MarketplaceKit framework, and users need iOS 17.4 or iPadOS 18 or later.

  • Web distribution. Eligible developers distribute their own apps from their website.

  • Notarization for iOS and iPadOS apps. Apps distributed either way are still checked by Apple against a subset of the App Review Guidelines (the guidelines page can highlight exactly which), mostly about security and functionality. In App Store Connect, the developer chooses the distribution methods, submits the build for notarization and gets an alternative distribution package.

  • Business terms. Apple’s August 18, 2026 announcement moves every developer distributing in the EU to one set of business terms from October 1, 2026, replacing the Core Technology Fee with a 5% Core Technology Commission on digital transactions in apps distributed outside the App Store.

See Apple Developer — Operating an alternative app marketplace in the EU, Apple Developer Documentation — Submit for Notarization and Apple Developer News — Changes for apps in the European Union.

FieldNotes ships only on the App Store. Its one concession to alternative distribution is FieldNotesInstallSource, which uses MarketplaceKit’s AppDistributor so that a future marketplace or web build would not point people to App Store–only features such as the review prompt. A marketplace developer uses much more of MarketplaceKit (installing apps, licenses, app search); that is out of scope here.
