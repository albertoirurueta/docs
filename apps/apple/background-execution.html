Background Execution

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production; see the section bibliography for the reference material consulted while preparing these pages.

A phone app spends most of its life not running. When a person switches away from FieldNotes, the system gives it a moment to tidy up and then suspends it: the process stays in memory, but none of its code runs. This keeps the battery healthy and the foreground app fast, and it means that "sync every hour" or "keep exporting after I lock the phone" is never automatic. The app has to ask for background time, and the system decides whether and when to grant it. This page covers the ways to ask, using the 2026 baseline of this section: iOS, iPadOS, macOS, watchOS and visionOS 27, Xcode 27 and Swift 6.4, with a deployment minimum of 26. It adds FieldNotes' three background tasks, whose identifiers are fixed for the whole section:

  • com.example.fieldnotes.refresh: an app refresh task that syncs notes a few times a day;

  • com.example.fieldnotes.reindex: a processing task that rebuilds the on-device search index while the device charges;

  • com.example.fieldnotes.export: a continued processing task that finishes a notebook export the person started, even after they leave the app.

Structured concurrency, cancellation and actors are not re-explained here. They are covered on Async/Await and Tasks and Actors, Isolation and Sendable, and their use inside the app on Swift Concurrency in Apps.

The Suspension Model

On iOS, iPadOS and visionOS an app process moves through a small set of states. The scene phases that SwiftUI reports (active, inactive, background) are described on App Structure and Life Cycle; underneath them are two process states the app never sees directly, suspended and terminated:

State What happens

Foreground (active or inactive)

The app is on screen and runs freely.

Background

The last scene has left the screen. Code still runs for a short grace period (a few seconds), or for as long as a granted background task, background mode or session lasts.

Suspended

The process is frozen in memory. No timers fire, no network callbacks arrive, and Tasks make no progress. Resuming is instant.

Terminated

The system reclaimed the memory. The next launch starts from scratch, possibly in the background because a task the app scheduled is now due.

Two things follow from this. First, work that is running when the app goes to the background simply stops at the next suspension point unless the app has asked for time. Second, a background task often starts with a cold launch: FieldNotesApp is created, its scenes are not shown, and only the task handler runs. Anything the handler needs, such as the NoteStore, must be reachable without a window.

macOS is different. Mac apps are not suspended when they lose focus; they keep running until they quit, and the system only throttles them through App Nap. That is why the BackgroundTasks framework is not on macOS at all. watchOS suspends even more aggressively than iOS and has its own session types, covered at the end of this page.

See Apple Developer Documentation — Background Tasks.

Finishing Work After Leaving the Foreground

The simplest request is "let me finish what I’m doing". beginBackgroundTask(withName:expirationHandler:) returns an identifier and gives the app extra time, usually well under a minute. The app must call endBackgroundTask(_:) when the work is done and from the expiration handler; an app that holds a background task past its time is terminated.

FieldNotes uses it when a scene moves to the background during a sync. The identifier is stored in a small main-actor object, so the expiration handler and the work can both end it without sharing a mutable local variable:

// FieldNotes/Background/SyncFinisher.swift
#if os(iOS) || os(visionOS)
import UIKit
import FieldNotesServices

@MainActor
final class SyncFinisher {
    private var taskID: UIBackgroundTaskIdentifier = .invalid

    /// Keeps the process alive until the current sync finishes or the system runs out of patience.
    func finishSync(of store: NoteStore) {
        guard taskID == .invalid else { return }
        taskID = UIApplication.shared.beginBackgroundTask(withName: "Finish FieldNotes sync") {
            self.end()   // time is up: stop cleanly rather than be terminated
        }
        Task {
            try? await store.refresh()
            end()
        }
    }

    private func end() {
        guard taskID != .invalid else { return }
        UIApplication.shared.endBackgroundTask(taskID)
        taskID = .invalid

Scheduled Tasks with BGTaskScheduler

BGTaskScheduler is the scheduler behind both scheduled task kinds, and it superseded the older setMinimumBackgroundFetchInterval(:)/application(:performFetchWithCompletionHandler:) background fetch API, which Apple deprecated in iOS 13 and which new code should not use. The pattern is always the same:

  1. Register a launch handler for the identifier. For refresh and processing tasks this must happen before the app finishes launching, because a background launch calls the handler straight away.

  2. Submit a request (BGAppRefreshTaskRequest or BGProcessingTaskRequest) with the same identifier. A request is a hint, not an appointment: earliestBeginDate is the earliest time, never a guaranteed one.

  3. When the system runs the task, do the work, then call setTaskCompleted(success:). Set an expirationHandler that cancels the work if time runs out.

  4. Submit the next request if the task should repeat. Tasks are one-shot.

An app refresh task gets about 30 seconds. A processing task can run for minutes, but only when the system decides the device is idle; setting requiresExternalPower makes it wait for a charger.

App refresh from SwiftUI

SwiftUI wraps registration in the backgroundTask(_:action:) scene modifier. The action is an async closure: the task counts as complete when the closure returns, and it is cancelled (in the Swift concurrency sense) when time runs out, so there is no expiration handler to write. FieldNotes schedules the next refresh at launch and at the start of every refresh:

// FieldNotes/Background/RefreshScheduler.swift (shared by the iOS, visionOS and watchOS app targets)
import Foundation
#if os(iOS) || os(visionOS)
import BackgroundTasks
#elseif os(watchOS)
import WatchKit
#endif

enum RefreshScheduler {
    static let identifier = "com.example.fieldnotes.refresh"

    /// Asks for the next refresh no earlier than `interval` from now. Submitting again replaces the pending request.
    @MainActor
    static func scheduleNext(after interval: TimeInterval = 2 * 60 * 60) {
        let earliest = Date.now.addingTimeInterval(interval)
        #if os(iOS) || os(visionOS)
        let request = BGAppRefreshTaskRequest(identifier: identifier)
        request.earliestBeginDate = earliest
        do {
            try BGTaskScheduler.shared.submit(request)
        } catch {
            print("Could not schedule refresh: \(error)")   // for example, Background App Refresh is off
        }
        #elseif os(watchOS)
        WKApplication.shared().scheduleBackgroundRefresh(withPreferredDate: earliest, userInfo: nil) { error in
            if let error { print("Could not schedule refresh: \(error)") }
        }
        #endif
    }
}

See Apple Developer Documentation — BGAppRefreshTaskRequest.

The scene hands the work to the store. The closure is @Sendable and runs off the main actor, so it captures the store explicitly and awaits its main-actor methods:

// FieldNotes/FieldNotesApp.swift (excerpt: background tasks; the other scenes are on App Structure and Life Cycle)
import SwiftUI
import FieldNotesServices

@main
struct FieldNotesApp: App {
    // The same instance that delegates and task handlers reach through AppServices.shared.
    @State private var store = AppServices.shared.store

    var body: some Scene {
        WindowGroup {
            ContentView()
                .environment(store)
                .task { RefreshScheduler.scheduleNext() }
        }
        #if os(iOS) || os(visionOS)
        .backgroundTask(.appRefresh(RefreshScheduler.identifier)) { [store] in
            await RefreshScheduler.scheduleNext()   // keep the chain going even if this run fails
            try? await store.refresh()
        }
        #endif
        .backgroundTask(.urlSession(AttachmentDownloader.sessionIdentifier)) {
            // The system relaunched FieldNotes because com.example.fieldnotes.attachments finished transfers.
            // Touching AttachmentDownloader.shared recreates the session (see Networking); returning after
            // its events are delivered lets the system suspend the app again.
            await AttachmentDownloader.shared.waitForBackgroundEvents()
        }
    }
}

See Apple Developer Documentation -- backgroundTask(_:action:).

Use either the SwiftUI modifier or BGTaskScheduler.register for a given identifier, never both. The background URL session itself is created on Networking: URLSession, Network Framework and ATS.

Processing tasks with BGTaskScheduler

The reindex task rebuilds FieldNotes' Core Spotlight entries. It is heavy, and nothing breaks if it waits until tonight, which makes it a textbook processing task. With a deployment minimum of 26, FieldNotes registers it the classic way, from the app delegate, before application(_:didFinishLaunchingWithOptions:) returns:

// FieldNotes/Background/ReindexTask.swift
#if os(iOS) || os(visionOS)
import BackgroundTasks
import CoreSpotlight
import FieldNotesModel

enum ReindexTask {
    static let identifier = "com.example.fieldnotes.reindex"

    /// Call from application(_:didFinishLaunchingWithOptions:).
    @MainActor
    static func register() {
        // `.main` runs the launch handler on the main queue, matching the main-actor isolation of this code.
        BGTaskScheduler.shared.register(forTaskWithIdentifier: identifier, using: .main) { task in
            guard let task = task as? BGProcessingTask else { return }
            let notes = AppServices.shared.store.notes
            let work = Task {
                do {
                    try await rebuildSearchIndex(for: notes)
                    task.setTaskCompleted(success: true)
                } catch {
                    task.setTaskCompleted(success: false)
                }
            }
            task.expirationHandler = { @Sendable in work.cancel() }
            schedule()
        }
    }

    static func schedule() {
        let request = BGProcessingTaskRequest(identifier: identifier)
        request.requiresExternalPower = true
        request.requiresNetworkConnectivity = false
        try? BGTaskScheduler.shared.submit(request)
    }

    static func rebuildSearchIndex(for notes: [Note]) async throws {
        let items = notes.map { note in
            let attributes = CSSearchableItemAttributeSet(contentType: .text)
            attributes.title = note.title
            attributes.contentDescription = note.body
            return CSSearchableItem(uniqueIdentifier: note.id.uuidString,
                                    domainIdentifier: "notes", attributeSet: attributes)
        }
        try Task.checkCancellation()
        let index = CSSearchableIndex.default()
        try await index.deleteAllSearchableItems()
        try await index.indexSearchableItems(items)
    }
}
#endif

See Apple Developer Documentation — BGProcessingTaskRequest.

The part 1 delegate gains one line in application(_:didFinishLaunchingWithOptions:): ReindexTask.register(), followed by ReindexTask.schedule(). The richer, App Intents-based index, where each note is an IndexedEntity, is on App Intents, Siri, Shortcuts, Spotlight, Deep Links and Extensions; the scheduling stays the same.

See Apple Developer Documentation — BGTaskScheduler.

New in iOS 27: processingTask(_:). SwiftUI now has a processing counterpart to appRefresh(_:), available on iOS, iPadOS, Mac Catalyst, tvOS and watchOS 27 (not visionOS). Continued Processing for Work the Person Starts (26)

Refresh and processing tasks run when the system chooses. BGContinuedProcessingTask, new in iOS and iPadOS 26, covers the opposite case: the person taps Export Notebook, then switches to Mail while the export runs. The task starts in the foreground, keeps running in the background, and the system shows its progress in a system Live Activity where the person can watch or cancel it. Requirements differ from the scheduled tasks:

  • It must start from an explicit user action, and its title and subtitle must describe that job.

  • The launch handler may be registered at any time before submitting, not only during launch.

  • It must report progress through its progress object. The system may end tasks that appear stuck.

  • strategy = .fail makes submission fail if the system cannot start it right away; the default, .queue, waits.

  • requiredResources = .gpu asks for background GPU access, when BGTaskScheduler.supportedResources contains .gpu. It needs the Background GPU Access capability.

FieldNotes' export controller registers on first use, submits the request, and writes each note as it goes:

// FieldNotes/Export/NotebookExportController.swift
#if os(iOS)
import BackgroundTasks
import FieldNotesModel
import FieldNotesServices

@MainActor
final class NotebookExportController {
    static let identifier = "com.example.fieldnotes.export"

    private var isRegistered = false
    private var pending: (notebook: Notebook, notes: [Note], destination: URL)?

    /// Called from the Export button: the person started this job, so continued processing fits.
    func export(_ notebook: Notebook, notes: [Note], to destination: URL) throws {
        if !isRegistered {
            isRegistered = BGTaskScheduler.shared.register(
                forTaskWithIdentifier: Self.identifier, using: .main
            ) { task in
                guard let task = task as? BGContinuedProcessingTask else { return }
                self.run(task)
            }
        }
        pending = (notebook, notes, destination)
        let request = BGContinuedProcessingTaskRequest(
            identifier: Self.identifier,
            title: "Exporting \(notebook.name)",
            subtitle: "Preparing \(notes.count) notes"
        )
        request.strategy = .queue
        try BGTaskScheduler.shared.submit(request)
    }

    private func run(_ task: BGContinuedProcessingTask) {
        guard let job = pending else {
            task.setTaskCompleted(success: false)
            return
        }
        pending = nil
        task.progress.totalUnitCount = Int64(job.notes.count)

        let work = Task {
            // Measured as a MetricKit interval; MetricsReporter is on Logging, MetricKit, Crash Reports and Organizer.
            MetricsReporter.shared.exportIntervalDidChange(started: true)
            defer { MetricsReporter.shared.exportIntervalDidChange(started: false) }
            do {
                let writer = try NotebookArchiveWriter(destination: job.destination)
                for (index, note) in job.notes.enumerated() {
                    try Task.checkCancellation()        // the person tapped Stop in the system UI
                    try await writer.append(note)
                    task.progress.completedUnitCount = Int64(index + 1)
                    task.updateTitle(task.title, subtitle: "\(index + 1) of \(job.notes.count) notes")
                }
                try await writer.close()
                task.setTaskCompleted(success: true)
            } catch {
                task.setTaskCompleted(success: false)
            }
        }
        task.expirationHandler = { @Sendable in work.cancel() }
    }
}
#endif

See Apple Developer Documentation — BGContinuedProcessingTask.

NotebookArchiveWriter is a small actor in FieldNotesServices that appends each note to a Markdown file. It is deliberately simple, so the example stays about the task; the document-based export (NotebookExportDocument) is on Preferences, Files and Document-Based Apps:

// Packages/FieldNotesKit/Sources/FieldNotesServices/Export/NotebookArchiveWriter.swift
import Foundation
import FieldNotesModel

public actor NotebookArchiveWriter {
    private let handle: FileHandle

    public init(destination: URL) throws {
        FileManager.default.createFile(atPath: destination.path(), contents: nil)
        handle = try FileHandle(forWritingTo: destination)
    }

    public func append(_ note: Note) throws {
        let markdown = "# \(note.title)\n\n\(note.body)\n\n"
        try handle.write(contentsOf: Data(markdown.utf8))
    }

    public func close() throws {
        try handle.close()
    }
}

See Apple Developer Documentation — Performing long-running tasks on iOS and iPadOS.

If the person closes FieldNotes from the app switcher, the system cancels the task without calling the expiration handler, so a half-written file can remain. The next export overwrites it.

Long-Running App Intents (27)

An App Intent that runs in the background from Shortcuts, Siri or a widget normally has about 30 seconds. New in the 27 releases, an intent that adopts LongRunningIntent can ask for more time by wrapping its work in performBackgroundTask(options:operation:). The protocol refines ProgressReportingIntent, and the system expects regular updates to progress; an intent that stops reporting can lose its extension. On macOS there is no 30-second limit in the first place.

FieldNotes offers an Export Notebook shortcut that reuses the same writer. The intent types and the dependency registration for NoteStore are covered on App Intents, Siri, Shortcuts, Spotlight, Deep Links and Extensions:

// FieldNotes/Intents/ExportNotebookIntent.swift
import AppIntents
import Foundation
import FieldNotesModel
import FieldNotesServices

@available(iOS 27, macOS 27, visionOS 27, watchOS 27, *)
struct ExportNotebookIntent: LongRunningIntent {
    static let title: LocalizedStringResource = "Export Notebook"

    @Parameter(title: "Notebook Name")
    var notebookName: String

    @Dependency private var store: NoteStore

    func perform() async throws -> some IntentResult & ProvidesDialog {
        let store = store
        let name = notebookName
        let notes = await MainActor.run { () -> [Note]? in
            guard let notebook = store.notebooks.first(where: { $0.name == name }) else { return nil }
            return store.notes.filter { $0.notebookID == notebook.id }
        }
        guard let notes else {
            // Never fall back to "notes without a notebook": an unknown name is an error the person can fix.
            throw $notebookName.needsValueError("There's no notebook named \(name). Which notebook?")
        }
        let destination = URL.documentsDirectory.appending(path: "\(notebookName).md")

        let written = try await performBackgroundTask {
            progress.totalUnitCount = Int64(notes.count)
            progress.localizedDescription = "Exporting \(notebookName)"
            let writer = try NotebookArchiveWriter(destination: destination)
            for (index, note) in notes.enumerated() {
                try Task.checkCancellation()
                try await writer.append(note)
                progress.completedUnitCount = Int64(index + 1)
            }
            try await writer.close()
            return notes.count
        }
        return .result(dialog: "Exported \(written) notes from \(notebookName).")
    }
}

See Apple Developer Documentation — LongRunningIntent and Apple Developer Documentation -- needsValueError(_:).

LongRunningTaskOptions currently has one option, .requiresGPU, for intents that run Core ML or Metal work in the background. An intent that also adopts CancellableIntent can use the onCancel: overload to learn why it was cancelled.

watchOS: Refresh Tasks and Extended Runtime Sessions

watchOS has no BackgroundTasks framework. Its scheduled work arrives through WKApplicationDelegate.handle(_:), as the WatchAppDelegate on App Structure and Life Cycle shows, or through the same SwiftUI .backgroundTask(.appRefresh(_:)) modifier. RefreshScheduler.scheduleNext() above already contains the watchOS branch. The watch gets a small refresh budget, which is best spent keeping a complication current.

A Mac app keeps running in the background, so it needs no permission to run. What it should do is let the system pick a good moment for maintenance. Debugging Background Tasks

The gap between submitting a task and the system running it can be hours, which makes waiting for it useless during development. BackgroundTasks has two private debugger entry points that start a task, or force it to expire, right away. They work only on a device, and only from the debugger; referencing them in shipping code is grounds for App Store rejection.

  1. Run FieldNotes from Xcode on a device.

  2. Pause after submit(_:) has run, for example with a breakpoint in RefreshScheduler.scheduleNext().

  3. In the LLDB console, launch the task, then continue:

(lldb) e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateLaunchForTaskWithIdentifier:@"com.example.fieldnotes.refresh"]
(lldb) continue

See Apple Developer Documentation — Starting and Terminating Tasks During Development.

To exercise the expiration path, pause inside the running task and simulate its expiration:

(lldb) e -l objc -- (void)[[BGTaskScheduler sharedScheduler] _simulateExpirationForTaskWithIdentifier:@"com.example.fieldnotes.reindex"]
(lldb) continue

See Apple Developer Documentation — Starting and Terminating Tasks During Development.

A few more habits help:

  • Check that the identifier is in BGTaskSchedulerPermittedIdentifiers whenever submit(_:) throws; BGTaskScheduler.Error.Code.notPermitted is the usual reason, and .unavailable means Background App Refresh is off or the app runs in the Simulator.

  • Filter the device log in Console.app by the dasd process to see the scheduler’s decisions about your tasks.

  • Test continued processing by starting an export and then pressing the Home button; the system progress UI should appear, and its Stop button should cancel the Swift Task.

  • Test with Low Power Mode on and with Background App Refresh off. The app must still sync when it is opened.

General LLDB and Xcode debugging techniques are on Debugging with Xcode and LLDB.
