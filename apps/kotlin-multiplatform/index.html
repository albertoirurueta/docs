Kotlin Multiplatform

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Welcome to the Kotlin Multiplatform reference. Kotlin Multiplatform (KMP) is JetBrains' technology for compiling one Kotlin codebase to several platforms — JVM and Android, native iOS and macOS binaries, JavaScript and WebAssembly — while still letting each platform keep its own code where it matters. You decide how much to share: only the business logic (networking, storage, domain rules and view models) behind fully native UIs written in Jetpack Compose and SwiftUI, or the user interface as well with Compose Multiplatform (CMP), JetBrains' port of Jetpack Compose to Android, iOS, desktop and the web. Both paths are documented in full here, on top of the same project.

This section targets Kotlin 2.4.20 and Compose Multiplatform 1.12.1 (based on Jetpack Compose 1.12.1), the Android Gradle Plugin 9.4 with its com.android.kotlin.multiplatform.library plugin, and Xcode 26.4, the version Kotlin 2.4.20 is tested against. Every page names the exact library versions it uses — Ktor 3.6.0, SQLDelight 2.4.0, Koin 4.2.2, Room 3 (androidx.room3) 3.0.3, SKIE 0.10.15, KMP-NativeCoroutines 1.0.6, Mokkery 3.5.0 and the rest — and states the stability level of every API that is not Stable. In particular, Swift export and SwiftPM import are Alpha, and Kotlin/Wasm and Compose Multiplatform for web are Beta, while Android, iOS, desktop and Kotlin/JS targets are Stable.

This section does not re-teach the Kotlin language, Jetpack Compose basics or SwiftUI basics — it links to them. The Kotlin language lives in the Kotlin Reference. The sibling sections are Android (native Android and Jetpack Compose), Apple Platforms (Swift, SwiftUI, Xcode and the App Store) and React Native (the TypeScript cross-platform alternative). The multi-platform projects page of the Apple section describes Apple’s own multi-platform targets and is unrelated to Kotlin Multiplatform.

How Kotlin Multiplatform got here

Year What changed

2017—​2018

Kotlin/Native entered preview and Kotlin gained multiplatform projects, sharing code between the JVM, JavaScript and native targets through expect/actual declarations.

2020

Kotlin Multiplatform Mobile (KMM) reached Alpha: Android and iOS apps sharing a Kotlin module, with a dedicated IDE plugin.

2021

Compose for Desktop and Compose for Web appeared as previews, the first steps toward sharing UI code beyond Android.

2022

The new Kotlin/Native memory manager (default since Kotlin 1.7.20) removed the object-freezing restrictions that had made concurrent iOS code awkward.

2023

Kotlin Multiplatform became Stable with Kotlin 1.9.20, together with the default hierarchy template.

2024

Google announced official support for Kotlin Multiplatform for shared business logic on Android, and Jetpack libraries (ViewModel, Room, DataStore, Paging) began to ship multiplatform artifacts. Kotlin 2.0 made the K2 compiler the default.

2025

Compose Multiplatform for iOS became Stable. Kotlin/Wasm and Compose Multiplatform for web reached Beta.

2026

The com.android.kotlin.multiplatform.library plugin became the Android target under AGP 9, which no longer allows com.android.application or com.android.library next to the KMP plugin. Swift export reached Alpha, as did SwiftPM import, steering iOS integration away from CocoaPods.

The TrailMate Everywhere project

Every code example is a slice of one project: the Android section’s TrailMate hiking-trail app (package com.example.trailmate) made multiplatform, so pages can link to the Android equivalents instead of repeating them.

  • Modules — sharedLogic (domain, data and view models), sharedUI (the Compose Multiplatform TrailListScreen, TrailDetailScreen, SettingsScreen, App() and TrailMateTheme), androidApp, iosApp (an Xcode project with a SwiftUI version and a Compose Multiplatform MainViewController version), desktopApp and webApp (wasmJs).

  • Domain and data — Trail(id, name, region, lengthKm, difficulty, photoUrl, isFavorite), enum class Difficulty, TrailPhoto; the remote API at https://api.example.com/v1/ through the Ktor TrailApiClient and TrailDto; a SQLDelight TrailMateDatabase with Room 3 as the alternative; a DataStore UserPreferencesRepository; the TrailRepository interface implemented by OfflineFirstTrailRepository; expect/actual platformName() and currentTimeZone(); and the LocationProvider interface with AndroidLocationProvider and IosLocationProvider.

  • Presentation — TrailListViewModel and TrailDetailViewModel exposing StateFlow<TrailListUiState>, wired through the Koin module trailMateModule.

  • Two UI paths — native UI (a SwiftUI TrailListView observing the shared view model through SKIE or KMP-NativeCoroutines, and Jetpack Compose on Android) and shared UI (Compose Multiplatform everywhere, with an MKMapView embedded on iOS).

  • Tests — OfflineFirstTrailRepositoryTest, FakeTrailApiClient (Ktor MockEngine), TrailListViewModelTest (Turbine) and TrailListScreenTest (runComposeUiTest).

  • Library example — the publishing and CI pages use a small library, com.example:trail-geo (geodesic distance and elevation-profile helpers), published to Maven Central and as an XCFramework through SwiftPM.
