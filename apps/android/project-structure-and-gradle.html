Project Structure, Gradle and Build Variants

This content was generated with the assistance of AI and should be verified against the official documentation of Android before being relied on in production.

See the section bibliography for the reference material consulted while preparing these pages.

Every Android app is a Gradle project, and Gradle’s job is to turn a tree of Kotlin/XML source files and declared dependencies into one or more signed .apk/.aab artifacts. This page walks through that project as it exists on disk, the files that configure it, and the build system that compiles it, targeting the section’s baseline: Android Gradle Plugin (AGP) 9.4.1 on Gradle 9.6 and JDK 17, with AGP’s built-in Kotlin compiler (Kotlin 2.4.20, no separate kotlin-android plugin), KSP 2.3.12 for annotation processing, and the Compose compiler as its own Gradle plugin. The running example, as introduced in Getting Started with Android, is TrailMate, a hiking-trail companion app. The Kotlin language itself — syntax, coroutines, the type system — is covered in the Kotlin Reference and is not repeated here; Kotlin: Build and Tooling covers the Kotlin compiler and Gradle plugin from the language side, while this page covers the Android-specific android {} DSL, build variants and packaging.

The app architecture page explains why TrailMate is split this way (separation of concerns, faster incremental builds, enforced api/implementation boundaries); this page covers how each module is configured to build at all. settings.gradle.kts

settings.gradle.kts is read before any other build script. It declares which modules exist and, in modern Gradle, centralizes two things that used to be scattered across every module: where plugins come from, and where dependencies come from.

// settings.gradle.kts
pluginManagement {
    repositories {
        google()
        mavenCentral()
        gradlePluginPortal()
    }
}

dependencyResolutionManagement {
    repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)
    repositories {
        google()
        mavenCentral()
    }
}

rootProject.name = "TrailMate"

include(":app")
include(":core:model", ":core:data", ":core:database", ":core:network")
include(":feature:trails", ":feature:settings")

See Gradle Documentation — Centralizing Repository Declarations.

pluginManagement.repositories controls where Gradle resolves plugins (AGP, the Kotlin plugin, KSP, Room, Hilt). dependencyResolutionManagement.repositories controls where it resolves ordinary dependencies (library artifacts), and FAIL_ON_PROJECT_REPOS forbids any module’s own build.gradle.kts from declaring a repositories {} block, so every module resolves from the same two repositories declared once, centrally. This is the standard shape Android Studio’s project wizard has generated since AGP 8. See Android Developers — Gradle Build Overview and Gradle — Centralizing Repository Declarations.

build-logic/settings.gradle.kts is a second, separate settings file: TrailMate treats build-logic as an included build (includeBuild("build-logic") in the root settings.gradle.kts) so its convention plugins can be applied by name from every module, as covered later on this page.

The Root build.gradle.kts

The root build script in a catalog-based, convention-plugin project is deliberately thin — it only declares which plugins are available to sub-projects, without applying them anywhere:

// build.gradle.kts (root)
plugins {
    alias(libs.plugins.android.application) apply false
    alias(libs.plugins.android.library) apply false
    alias(libs.plugins.kotlin.compose) apply false
    alias(libs.plugins.kotlin.serialization) apply false
    alias(libs.plugins.ksp) apply false
    alias(libs.plugins.hilt.android) apply false
}

See Android Developers — Gradle Build Overview.

apply false resolves and downloads the plugin’s classpath once, at the root, without activating it — each module then applies only the plugins it actually needs. This avoids every module re-declaring buildscript { dependencies { classpath(…​) } }, the pre-Gradle-7 way of doing the same thing. See Android Developers — Migrate your build to the Kotlin DSL.

The android {} DSL, Field by Field

Property Meaning

namespace

The package Kotlin/Java sources and generated R/BuildConfig classes live under (compile-time only).

applicationId

The identifier the Play Store and the device’s package manager use to identify the app; can differ from namespace and can vary per flavor/build type (applicationIdSuffix).

compileSdk / minSdk / targetSdk

Covered in Getting Started with Android; compileSdk picks the platform APIs available at compile time, minSdk/targetSdk go into the merged manifest.

buildTypes

Named build configurations (debug, release, and any custom ones) controlling minification, shrinking, signing and debuggability. Every module has debug and release by default.

productFlavors / flavorDimensions

Named variations along one or more dimensions (here, environment — staging vs production); each flavor can override applicationId, resources, buildConfigFields and its own source set.

buildFeatures

Opt-in switches for generated code paths: compose, buildConfig, viewBinding, dataBinding (legacy), aidl, renderScript (deprecated). Each one off by default to keep unused generators out of the build.

JVM toolchain

kotlin { jvmToolchain(17) } (or the equivalent compileOptions pair) pins the JDK used to compile Kotlin and Java sources, independent of whatever JDK launched Gradle itself.

Build Variants, Source Sets and Manifest Merging

A build variant is the cross product of every build type and every flavor dimension: TrailMate’s two build types (debug, release) times its one flavor dimension with two flavors (staging, production) yields four variants — stagingDebug, stagingRelease, productionDebug, productionRelease — each with its own Gradle tasks (assembleStagingDebug, bundleProductionRelease, …) and its own merged manifest, resources and BuildConfig.

Each variant assembles its sources by layering source sets from most specific to least specific:

src/
├── main/                    # shared by every variant
├── debug/                   # merged into every *Debug variant
├── release/                 # merged into every *Release variant
├── staging/                 # merged into every staging* variant
├── stagingDebug/            # merged only into the stagingDebug variant (highest priority)
├── test/                    # local JVM unit tests, all variants
└── androidTest/             # instrumented tests, all variants

See Android Developers — Configure Build Variants.

A resource or manifest entry in a more specific source set (stagingDebug) overrides the same entry from a less specific one (debug, then main). Manifest merging applies the same priority order to AndroidManifest.xml fragments — a flavor’s manifest can add a <meta-data> or override an android:label without touching main's manifest — and Android Studio’s Merged Manifest view shows exactly which source contributed each attribute. See Android Developers — Configure Build Variants and Android Developers — Manage the Manifest File.

BuildConfig is a generated class (one per variant, gated by buildFeatures.buildConfig = true) exposing buildConfigField entries and standard fields (BuildConfig.APPLICATION_ID, BuildConfig.VERSION_NAME, BuildConfig.DEBUG, BuildConfig.FLAVOR, BuildConfig.BUILD_TYPE) as compile-time constants, letting code branch on BuildConfig.BASE_URL without any runtime configuration lookup.

gradle.properties holds JVM and Gradle daemon settings plus AGP/Kotlin feature flags, and is committed (unlike local.properties, which holds machine-specific paths and is never committed):

Dependency Configurations and BOMs

Each dependencies {} entry names both a library and a configuration that controls its visibility and when it is needed:

Configuration Meaning

implementation

Available to compile and run this module, not re-exported to modules that depend on this one. The default choice; keeps a module’s dependency graph private and its own changes from forcing recompilation of consumers.

api

Like implementation, but re-exported to consumers' compile classpath. Only used on Gradle library modules whose public API genuinely needs a dependency’s types (for example :core:model exposing kotlinx.datetime types from its own public classes).

ksp

Registers an annotation processor that runs through KSP (Kotlin Symbol Processing) rather than kapt — ksp(libs.hilt.compiler), ksp(libs.androidx.room.compiler).

testImplementation

Only on the local-JVM test compile/runtime classpath (src/test/), run by ./gradlew test, executed on the host JVM against Robolectric or plain JVM code.

androidTestImplementation

Only on the instrumented-test classpath (src/androidTest/), run by ./gradlew connectedAndroidTest on a device or emulator.

debugImplementation

Only in debug builds — the standard way to add a debug-only tool (Compose’s ui-tooling, LeakCanary) without shipping it in release.

implementation(platform(libs.compose.bom)) declares a Bill of Materials: a single version (2026.09.00) that then governs every other androidx.compose.* artifact’s version implicitly, so compose-ui, compose-material3 and compose-ui-tooling-preview never drift out of sync with each other. Both Compose and OkHttp ship a BOM this way; declaring one BOM per ecosystem and letting individual artifact versions follow it is the recommended pattern over pinning each artifact’s version by hand. See Android Developers — Add Build Dependencies and Android Developers — Using the Compose BOM.

Convention Plugins: build-logic

Repeating the same android {} block, JVM toolchain and lint configuration in every one of TrailMate’s seven modules invites drift. A convention plugin — an ordinary Gradle plugin, written once in an included build named build-logic, applied by every module that needs its shape — centralizes that instead:

// build-logic/convention/src/main/kotlin/trailmate.android.library.compose.gradle.kts
plugins {
    id("trailmate.android.library")
    id("org.jetbrains.kotlin.plugin.compose")
}

android {
    buildFeatures {
        compose = true
    }
}

dependencies {
    val bom = project.dependencies.platform("androidx.compose:compose-bom:2026.09.00")
    add("implementation", bom)
    add("androidTestImplementation", bom)
}

See Gradle Documentation — Sharing Build Logic Between Subprojects.

A feature module then reduces its own build.gradle.kts to:

// feature/trails/build.gradle.kts
plugins {
    id("trailmate.android.library.compose")
    id("trailmate.hilt")
}

android {
    namespace = "com.example.trailmate.feature.trails"
}

dependencies {
    implementation(project(":core:model"))
    implementation(project(":core:data"))
}

See Gradle Documentation — Sharing Build Logic Between Subprojects.

build-logic is registered as an included build from the root settings.gradle.kts (includeBuild("build-logic")), which is what lets its plugins be applied to other modules by id, as if they had been published to a repository, without actually publishing anything. This is the pattern behind Now in Android and most production multi-module Android projects. See Android Developers — Extend the Android Gradle Plugin and Gradle — Sharing Build Logic Between Subprojects.

AGP 9 Migration: the New Variant API and newDsl

AGP 9.0 removed the legacy variant API (applicationVariants, libraryVariants, mutable BaseVariant/ApplicationVariant objects read inside android {}) that plugins and build scripts used to hook into per-variant configuration. In its place, the Variant API (androidComponents { onVariants { …​ } }) exposes each variant as an immutable, lazily-evaluated model built for configuration-cache compatibility:

// app/build.gradle.kts -- reading and customizing variants under the new API
androidComponents {
    onVariants { variant ->
        println("Configuring variant: ${variant.name}")

        if (variant.buildType == "release") {
            variant.outputs.forEach { output ->
                if (output is com.android.build.api.variant.impl.VariantOutputImpl) {
                    output.outputFileName.set("trailmate-${variant.name}-${variant.versionName.get()}.apk")
                }
            }
        }
    }
}

See Android Developers — Extend the Android Gradle Plugin.

Where old-API code read variant.buildType.buildConfigFields directly during configuration (breaking the configuration cache, since it captured live, mutable objects), onVariants receives a read-only snapshot and schedules any further work as a lazy Provider, so Gradle can safely cache and reuse the configuration between builds. AGP 9’s newDsl setting (on by default since 9.0) additionally changes how android {} itself is typed internally to support this; existing android {} blocks written the conventional way, as shown throughout this page, do not need to change. Projects still on the old variant API from AGP 8 or earlier should follow the official migration guide before upgrading further. See Android Developers — AGP 9.0.0 Release Notes, Android Developers — AGP 9.4.0 Release Notes and Android Developers — Extend the Android Gradle Plugin.

From kapt to KSP

kapt (Kotlin Annotation Processing Tool) ran a full, generated Java stub compilation of every Kotlin file just so Java-based annotation processors (like Room’s or Dagger’s original ones) could see them — slow, and a separate compilation pass per module. KSP (Kotlin Symbol Processing) gives compatible processors direct access to Kotlin’s own compiler symbols, without a Java-stub round trip, typically 2x or faster on processor-heavy modules. Room, Hilt, Moshi and most current-generation Android annotation processors ship a KSP-compatible artifact; the migration is usually just:

// before (kapt)
plugins {
    kotlin("kapt")
}
dependencies {
    kapt(libs.androidx.room.compiler)
}

// after (KSP)
plugins {
    alias(libs.plugins.ksp)
}
dependencies {
    ksp(libs.androidx.room.compiler)
}

See Android Developers — Migrate from kapt to KSP.

kapt is in maintenance mode — it still works, and some older third-party processors have not published a KSP variant, but new projects should default to KSP and existing ones should migrate opportunistically, one processor at a time (both can coexist in the same module during a migration). See Android Developers — Migrate from kapt to KSP and Kotlin — Kotlin Symbol Processing (KSP).

The Configuration Cache and the Build Cache

Two independent caches make repeated builds faster:

  • The configuration cache (org.gradle.configuration-cache=true) skips re-running the configuration phase — evaluating every build.gradle.kts, resolving plugins {} blocks, building the task graph — when nothing that would change it has changed, serializing that graph to disk instead. It is why the old variant API (which read live, mutable objects during configuration) had to be replaced: anything the configuration cache serializes must be a stable, cacheable snapshot, which is exactly what onVariants provides.

  • The build cache (org.gradle.caching=true, plus a buildCache {} block in settings.gradle.kts for a shared remote cache in CI) reuses individual task outputs — a Kotlin compile task, a KSP run, a lint report — keyed by a hash of their inputs, whether that hash was last produced locally or, with a remote cache, by a teammate’s or CI’s build.

Both are additive: the configuration cache speeds up the phase that decides what to run, the build cache speeds up the phase that actually runs it, by skipping tasks whose inputs have not changed. See Android Developers — Optimize Your Build Speed and Gradle — Configuration Cache.
