Views, Fragments and Activities vs. Compose: Architecture Comparison

This content was generated with the assistance of AI and should be verified against the official documentation of Android before being relied on in production.

See the section bibliography for the reference material consulted while preparing these pages.

By 2026, Jetpack Compose is Google’s recommended toolkit for new Android UI, and the Views/Fragments/Activities stack that preceded it is now consistently described as the classic, still-supported alternative rather than the default. Both toolkits remain fully maintained — Compose is built on top of the same Activity, Lifecycle and ViewModel foundations Views uses, not a replacement for them — and most non-trivial apps, including large existing codebases, run a mix of both for years. This page puts the two stacks side by side, feature by feature, so a team can reason concretely about where they differ, where a mixed codebase is a reasonable long-term state rather than a waypoint, and where Compose is a clear win. It targets Android 17 (API level 37), Compose BOM 2026.09.00, Fragment 1.9.1, Lifecycle 2.11.0 and Navigation 2.10.2 / Navigation 3 1.2.0, and uses the same TrailMate hiking-trail app used throughout this section, built once in each stack.

This page assumes the individual building blocks of each stack are already familiar from earlier pages: Activities and the Activity Lifecycle, Fragments and the Fragment Lifecycle, Views, XML Layouts, View Binding and Material Components and RecyclerView and Lists for the classic stack; Jetpack Compose Fundamentals, Compose Layouts, Modifiers and Lazy Lists and State, Recomposition and Side Effects in Compose for Compose; and Recommended App Architecture (UI, Domain and Data Layers) and ViewModel, Lifecycle-Aware Components, Coroutines and Flow for the shared architecture underneath both. Two closely related pages complete the trio this page belongs to: Saving UI State: Views vs. Compose gives the full, dedicated comparison of what survives a configuration change, process death or user dismissal in each stack — this page only summarizes that topic — and Migrating from Views to Compose gives the phased, before/after migration path for a codebase that wants to move from one stack to the other.

How to Read This Comparison

Each section below states what a concept means in each stack, gives a short table, and calls out the one or two things teams most often get wrong when moving between them. TrailMate names are consistent with the rest of the section: Trail, Difficulty, TrailListUiState, TrailListViewModel, TrailRepository, and the two parallel UI entry points, MainActivity : AppCompatActivity (Views, hosting NavHostFragment) and MainActivity : ComponentActivity (Compose, hosting TrailMateApp()). Both versions of TrailMate share the same TrailListViewModel, exposing StateFlow<TrailListUiState> and an onToggleFavorite(id: String) method — the architecture layer underneath the UI does not change based on which toolkit renders it, which is exactly why a mixed-stack app is viable: the UI layer is the only layer that differs.

UI Definition

Views / Fragments / Activities Compose

Where the UI lives

XML layout resource (res/layout/fragment_trail_list.xml) parsed and inflated at runtime into a tree of View objects, plus Kotlin code that looks the tree up and mutates it.

A tree of @Composable Kotlin functions. There is no separate markup file; the function is the UI description, and Kotlin’s type system checks it at compile time.

Composition unit

A View/ViewGroup subclass, one instance per screen element, retained for the screen’s lifetime.

A composable function invocation, which may or may not correspond to a retained object — the Compose runtime decides whether to keep, move or discard the underlying LayoutNode.

Reuse

Custom <include>, <merge>, and custom View subclasses; styles and themes for shared attributes.

Ordinary function composition and default parameters — a shared row is just a function called from several screens, with no XML inheritance model to reason about.

Tooling to author it

The Layout Editor’s WYSIWYG canvas and Blueprint view, or hand-written XML.

@Preview composables rendered by Android Studio’s Compose Preview, or the interactive/live-edit modes; there is no drag-and-drop canvas.

Update Model: Imperative Mutation vs. Recomposition

Views / Fragments / Activities Compose

How the screen changes

Code imperatively finds a View (findViewById, or a generated binding property) and mutates one of its properties: textView.text = newName, imageView.setImageDrawable(…​).

A composable re-reads the state it depends on and re-executes ("recomposes"); the runtime diffs what changed and only touches the underlying layout nodes that actually differ.

Who tracks "what changed"

The programmer, by hand, one property at a time. Forgetting to update a View after its backing state changes is a common, silent bug.

The Compose runtime’s snapshot system, via State<T> reads recorded during composition. A composable that never reads a piece of state simply never recomposes when it changes.

Granularity

Whatever the programmer chose to touch: a single property, or an entire subtree via notifyDataSetChanged().

Individual composables, addressed by position and, for lists, by key. TrailCard for one trail recomposes independently of the other rows in the list.

Failure mode when done carelessly

Stale UI (state changed, view was not touched) or excessive redraws (notifyDataSetChanged() blowing away `DiffUtil’s targeted updates).

Excessive recomposition from unstable parameter types, unnecessarily broad state reads, or lambdas that are recreated every recomposition; see State, Recomposition and Side Effects in Compose for the stability rules that prevent this.

Lifecycles

Views / Fragments / Activities Compose

Lifecycle owners in play

Three separate, nested lifecycles: the Activity’s, each hosted `Fragment’s, and each fragment’s view lifecycle (`viewLifecycleOwner), which is shorter-lived than the fragment itself.

Only the Activity (or NavBackStackEntry) lifecycle exists as a framework-level LifecycleOwner; composables do not have their own Lifecycle object. Compose has its own, additional notion of composition lifetime (entering/leaving composition) that is orthogonal to Lifecycle.

What "leaves the screen" means

A Fragment’s view can be destroyed and recreated (`onDestroyView/onCreateView) while the fragment instance and its ViewModel survive — the single most common source of Fragment memory leaks when a listener or binding reference outlives the view.

A composable "leaves composition" when its call site is no longer reached (e.g. because a condition became false, or a list item scrolled out of a lazy list without being kept alive), which triggers DisposableEffect cleanup. There is no separate "view" object to null out.

Common lifecycle bug

Setting binding = FragmentTrailListBinding.bind(…​) in onCreateView and forgetting to set it to null in onDestroyView, leaking the fragment view through the binding field.

Collecting a Flow with lifecycleScope.launch instead of repeatOnLifecycle/collectAsStateWithLifecycle, which keeps collecting (and doing work) while the screen is stopped.

Performance: Inflation, Recomposition and Baseline Profiles

Views Compose

Cost of creating a screen the first time

XML inflation: parsing and reflectively instantiating a View tree from a compiled binary XML resource. Deep or heavily nested ConstraintLayout/LinearLayout hierarchies inflate and measure/layout more slowly.

No inflation step; the first composition builds `LayoutNode`s directly from already-compiled Kotlin bytecode. Deep composable nesting is generally cheaper than the equivalent View nesting, but very large single composables can still be slow to skip if they are unstable.

Cost of updating the screen

Whatever the programmer chose to touch, which can be as cheap as one property write or as expensive as a full notifyDataSetChanged().

Recomposition of just the composables whose state inputs changed, provided those composables are skippable (stable parameter types) — see State, Recomposition and Side Effects in Compose for what breaks skippability.

Startup optimization

Baseline Profiles pre-compile hot XML-inflation and layout code paths ahead of time via Macrobenchmark-recorded profiles.

The same Baseline Profiles mechanism applies to Compose’s composition/layout/draw code paths; Compose benefits at least as much from a profile as Views does, since more of its work happens through generic runtime code paths that the JIT would otherwise need to warm up on every fresh install.

Common performance pitfall

Overdraw from deeply nested ViewGroup`s with overlapping backgrounds; unnecessary `requestLayout() calls.

Reading unstable state too high in the tree, causing large subtrees to recompose; unremembered lambdas recreated on every recomposition, defeating skipping in child composables.

How to measure

Layout Inspector, GPU rendering profile, Choreographer frame timing, Macrobenchmark.

Layout Inspector’s recomposition counts, the Compose compiler’s stability reports, Macrobenchmark — the same benchmarking tool works for both stacks.

See Android Developers — Compose performance and Android Developers — Baseline Profiles overview.

Startup Time and APK Size

Views Compose

App startup contribution

No extra runtime library beyond AppCompat/AndroidX; startup cost is dominated by Application/Activity initialization and the first layout’s inflation.

Adds the Compose runtime and UI libraries to the classpath and to cold-start class loading; in practice the difference is small next to app-specific initialization (DI graph construction, first network/DB calls) and is further reduced by R8/Baseline Profiles.

APK/AAB size contribution

Smaller Compose-related footprint (none), but XML layout resources and any Data Binding-generated classes add their own size.

The Compose runtime, UI, foundation and Material 3 artifacts add several megabytes before R8 shrinking; R8 with resource shrinking (default in AGP 9) removes the large majority of unused code from either stack.

Practical takeaway

Neither difference is normally the dominant factor in a real app’s startup time or install size; both are measured with Macrobenchmark and the Play Console’s app size report rather than assumed from first principles.

When Views Are Still the Right Choice

Compose being the recommended default for new UI does not make Views the wrong choice in every situation. Two cases come up repeatedly in practice:

Large existing codebases. A mature app with millions of lines of View-based UI, an established design system built on MDC, and a team fluent in that stack gains little from a wholesale rewrite, and a rewrite carries real risk: regressions in screens that already work, a long stretch where two UI systems must be kept visually consistent, and a large QA surface to re-cover. The pragmatic default for such a codebase is exactly what Migrating from Views to Compose describes: build new screens and new features in Compose, embed them into the existing View hierarchy with ComposeView, and migrate existing screens only when there is a concrete reason to touch them anyway (a redesign, a bug that is easier to fix after conversion, a screen that is about to gain complex animation). There is no deadline by which an app "must" finish migrating; Views remain a first-class, fully supported toolkit indefinitely.

Surface-based and SDK-provided View`s — check for a Compose wrapper first. Some Android APIs hand the caller an `android.view.Surface or a SurfaceHolder to draw into directly, rather than expecting onDraw(Canvas) calls, and some SDKs ship only a View. Several of the common cases now have first-party Compose APIs, so an AndroidView wrapper is only needed where none exists:

View type Compose option

com.google.android.gms.maps.MapView

Google’s maps-compose library (com.google.maps.android:maps-compose) provides a GoogleMap composable, with markers, polylines and camera state as composables and state holders. It wraps MapView internally, so a Compose screen no longer needs its own AndroidView for a map.

SurfaceView

AndroidExternalSurface (in androidx.compose.foundation) is a composable backed by a SurfaceView: it hands the app a Surface in an onSurface callback for low-latency, off-main-thread rendering (a custom renderer, or a video decoder’s output).

TextureView

AndroidEmbeddedExternalSurface is the TextureView-backed counterpart: the surface behaves like ordinary content for transforms, clipping, animation and blending, at a small composition cost.

GLTextureView and other custom surface `View`s

A custom View subclass that owns its own rendering machinery — such as the author’s real com.irurueta:irurueta-android-glutils library’s GLTextureView (an OpenGL ES-capable TextureView with its own EGL context and GL thread; see Graphics: Canvas, OpenGL ES and GLTextureView) — has no Compose wrapper, and stays a View embedded with AndroidView.

A View with no Compose wrapper is embedded with AndroidView, with lifecycle callbacks forwarded manually since Compose has no lifecycle hooks of its own that map onto Surface creation/destruction:

For a map or a plain SurfaceView/TextureView, prefer maps-compose and AndroidExternalSurface/ AndroidEmbeddedExternalSurface; for a View like GLTextureView that has no wrapper, AndroidView is the documented approach — not a workaround to be migrated away from later. See Google for Developers — Maps Compose library and Android Developers — androidx.compose.foundation (AndroidExternalSurface, AndroidEmbeddedExternalSurface).

Side-by-Side: The Same Feature in Both Stacks

To make every row of the tables above concrete at once, this section implements one complete feature — a trail list where tapping a heart icon toggles that trail’s favorite status — fully in both stacks. Both versions share the same TrailListViewModel and TrailRepository; only the UI layer differs, which is the point.

Shared: TrailListViewModel and the Repository Call

Neither UI layer talks to Room or the network directly; both call the same ViewModel method, which delegates to the same repository, exactly as Recommended App Architecture (UI, Domain and Data Layers) describes:

// feature/trails/src/main/kotlin/com/example/trailmate/feature/trails/TrailListViewModel.kt
@HiltViewModel
class TrailListViewModel @Inject constructor(
    private val repository: TrailRepository,
) : ViewModel() {

    // TrailListUiState is the sealed interface defined on the App Architecture page.
    val uiState: StateFlow<TrailListUiState> = repository.trails
        .map<List<Trail>, TrailListUiState> { TrailListUiState.Success(trails = it, onlyFavorites = false) }
        .catch { emit(TrailListUiState.Error(it.message.orEmpty())) }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), TrailListUiState.Loading)

    fun onToggleFavorite(trailId: String) {
        val trail = (uiState.value as? TrailListUiState.Success)?.trails?.firstOrNull { it.id == trailId } ?: return
        viewModelScope.launch { repository.setFavorite(trailId, isFavorite = !trail.isFavorite) }
    }
}

// feature/trails/src/main/kotlin/com/example/trailmate/feature/trails/TrailListFragment.kt
@AndroidEntryPoint
class TrailListFragment : Fragment(R.layout.fragment_trail_list) {
    private val viewModel: TrailListViewModel by viewModels()
    private var binding: FragmentTrailListBinding? = null
    private lateinit var adapter: TrailAdapter

    override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
        binding = FragmentTrailListBinding.bind(view)
        adapter = TrailAdapter(onToggleFavorite = viewModel::onToggleFavorite)
        binding?.trailRecyclerView?.apply {
            layoutManager = LinearLayoutManager(requireContext())
            adapter = this@TrailListFragment.adapter
        }

        viewLifecycleOwner.lifecycleScope.launch {
            viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
                viewModel.uiState.collect { state ->
                    if (state is TrailListUiState.Success) {
                        adapter.submitList(state.trails)
                    }
                }
            }
        }
    }

    override fun onDestroyView() {
        super.onDestroyView()
        binding = null
    }
}

    viewModel: TrailListViewModel = hiltViewModel(),

@Composable
fun TrailListScreen(
    uiState: TrailListUiState,
    onToggleFavorite: (String) -> Unit,
    modifier: Modifier = Modifier,
) {
    when (uiState) {
        is TrailListUiState.Loading -> CircularProgressIndicator(modifier = modifier)
        is TrailListUiState.Error -> Text(uiState.message, modifier = modifier)
        is TrailListUiState.Success -> {
            LazyColumn(modifier = modifier.fillMaxSize()) {
                items(items = uiState.trails, key = { it.id }) { trail ->
                    TrailCard(
                        trail = trail,
                        onToggleFavorite = onToggleFavorite,
                        modifier = Modifier.animateItem(),
                    )
                }
            }
        }
    }
}

The same feature is three collaborating pieces here: one ViewModel (shared with the Views version, unchanged), TrailCard (shown under UI Definition above), and TrailListScreen itself. There is no generated binding class, no separate item layout resource, no ViewHolder, no DiffUtil.ItemCallback to write by hand (structural equality of the Trail data class plus the key lambda does the equivalent job), and no fragment lifecycle to manage — collectAsStateWithLifecycle() already stops collecting when the screen is stopped, the Compose equivalent of the Views version’s explicit repeatOnLifecycle block.

What Stayed the Same, and What Did Not

Both versions: use the same Trail domain type, the same TrailListViewModel and TrailRepository, the same onToggleFavorite(id: String) call, the same Room-backed persistence underneath, and the same Hilt injection (@HiltViewModel/hiltViewModel() vs. @HiltViewModel/by viewModels()). Both versions differ in: how many files and classes exist (six across two resource files and four Kotlin files for Views, versus two Kotlin files for Compose, not counting the shared TrailCard), how updates propagate (imperative notifyItemChanged vs. automatic recomposition), and how much of the correctness burden falls on hand-written code (DiffUtil, nulling binding, wiring a LayoutManager) versus the framework (structural equality, automatic recycling, automatic lifecycle-aware collection). Neither version is "wrong" — an app already built the first way loses nothing by staying that way for existing screens, which is exactly the argument made under [When Views Are Still the Right Choice] above.
