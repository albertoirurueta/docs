Android

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Welcome to the Android reference. It documents how to build native Android apps with Google’s own tools and language of choice: Android Studio, Gradle and Kotlin, on top of the Android SDK and Jetpack. The result runs directly on the platform, with no cross-platform layer in between.

This section targets Android 17 (API 37), built with Android Studio Quail 4 and the Android Gradle Plugin (AGP) 9.4, written in Kotlin 2.4.20. TrailMate, the running example used across most pages, sets compileSdk = 37, targetSdk = 36 (Google Play requires targeting API 36 for new apps and updates since 2026-08-31) and minSdk = 26. Every page names the exact library versions it uses — Compose BOM 2026.09.00, Navigation 2.10.2 and Navigation 3 1.2.0, Room 2.8.5/3.0.3, Hilt 2.60.1 and the rest — so examples compile against a consistent, current baseline rather than mixed-era snippets.

Both classic View-based UI (Activities, Fragments and XML layouts) and Jetpack Compose are covered in full, because most real Android codebases still contain both, and knowing where one ends and the other begins is part of the job. This section does not re-teach the Kotlin language itself — for that, see the Kotlin Reference, which this section links to instead of repeating, including its dedicated Kotlin for Android page. For the cross-platform alternative that targets Android and iOS from one TypeScript codebase, see React Native; for the native counterpart on Apple’s platforms, see Apple Platforms.

How Android app development got here

Year What changed

2008

The Android SDK shipped alongside the first Android phone, apps written in Java against the platform’s own UI toolkit (Views, Activities).

2011

Fragments arrived (Honeycomb, API 11) to let a UI be composed and reused across screen sizes, particularly on tablets.

2014

Android Studio replaced Eclipse/ADT as the official IDE, Gradle became the build system, and the Android Runtime (ART) replaced Dalvik. Material Design was introduced the same year, defining the platform’s visual language.

2017—​2018

The Architecture Components (ViewModel, LiveData, Room) and Jetpack — Google’s umbrella for versioned, backward-compatible libraries — gave the platform an opinionated answer to app architecture. AndroidX replaced the original support libraries with semantically versioned packages.

2019

Google announced Kotlin as its preferred language for Android development, ahead of Java.

2021

Jetpack Compose 1.0 shipped: a declarative, Kotlin-first UI toolkit that replaces the View system’s imperative API with composable functions and state-driven recomposition. The Google Play Console also began requiring the Android App Bundle format for new apps.

2022

Material 3 (Material You) became Compose’s default design system, with dynamic color and expressive theming.

2025

OSSRH (Sonatype’s original Central staging service) shut down on 2025-06-30, moving library publishing to the Central Publisher Portal, and Navigation 3 reached 1.0.0 as a from-scratch, Compose-first navigation library.

2026

AGP 9 made Kotlin support built-in (no separate Kotlin Gradle plugin needed) and switched to a new DSL by default; Android 17 (API 37) shipped, and Google’s phased developer verification program began rolling out.

Much of what older books and tutorials describe predates this timeline: Eclipse/ADT, JCenter, AsyncTask and Loaders, Kotlin synthetics, startActivityForResult, and LiveData-first, Views-only architectures. These pages document the current approach and name the older one only where a reader is likely to meet it in an existing codebase — see Books and official sources compared below for the full list.

The TrailMate app

Every code example across pages 1—​36 is a slice of one running app, TrailMate: a hiking-trail companion, package com.example.trailmate, that lists trails, shows their detail and lets a hiker mark favorites and capture photos. Its domain is small on purpose: Trail(id, name, region, lengthKm, difficulty, photoUrl, isFavorite), enum class Difficulty { EASY, MODERATE, HARD } and TrailPhoto.

TrailMate is built twice across these pages, in the two UI styles this section covers: a modern version with a single ComponentActivity, TrailMateApp() and Compose screens (TrailListScreen/TrailDetailScreen/SettingsScreen/PhotoCaptureScreen), and a legacy version with an AppCompatActivity hosting a NavHostFragment and TrailListFragment/TrailDetailFragment built with RecyclerView, ViewBinding and Safe Args. Both versions share the same data layer: a Retrofit-backed TrailApi (with a Ktor TrailApiClient shown as an alternative) against https://api.example.com/v1/trails, a Room TrailMateDatabase and a DataStore-backed UserPreferencesRepository, unified behind a TrailRepository interface implemented by OfflineFirstTrailRepository. A TrailSyncWorker keeps data fresh in the background, and a RecordHikeService foreground service tracks an active hike. Dependency injection is shown with both Hilt (TrailMateApplication, NetworkModule, DatabaseModule, RepositoryModule) and a Koin alternative (trailMateModule); images load through Coil in Compose and Glide in the legacy code. The app is split into Gradle modules :app, :core:model, :core:data, :core:database, :core:network, :feature:trails and :feature:settings, and is exercised by tests such as TrailListViewModelTest, OfflineFirstTrailRepositoryTest, TrailDaoTest and TrailListScreenTest.

Pages 37—​40 (building, signing, publishing and CI/CD) step away from TrailMate and use a real, published library instead — com.irurueta:irurueta-android-glutils — so that the build, signing and Maven Central publishing steps are shown against an actual build.gradle.kts and GitHub Actions workflow rather than a fictional one.
