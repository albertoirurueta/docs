Theme App Extensions and Web Pixels

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page was written against Shopify CLI 5.0.0, the GraphQL Admin API version 2026-10 (the latest stable version, released on 2026-10-01), @shopify/web-pixels-extension 2.18.0 and the Customer Privacy API feature consent-tracking-api version 0.2, and checked on 2026-10-27. The Web Pixels API, the Customer Privacy API and Liquid are not versioned with the Admin API: Shopify lists all three among the surfaces that can change at any time, so the dates in the changelog entries quoted below matter more than a version number. None of the pages that describe theme app extensions or web pixels lists a Shopify plan requirement, so both are available to every app on every plan. Theme app extensions render only in Online Store themes; a headless storefront does not render theme blocks and has its own consent path, described at the end of the consent section.

An app that wants something to happen on the storefront has two jobs. It may need to show something, such as a rating next to the price or a floating chat bubble, and it may need to observe something, such as which variants customers add to the cart. For about a decade apps did both by editing the merchant’s theme through the Asset API or by registering a remote JavaScript file as a script tag. Those techniques left "ghost code" behind when the app was uninstalled, broke when the theme changed, and gave the merchant no way to see or switch off what the app was doing. Two extension types replace them. A theme app extension ships Liquid blocks, CSS and JavaScript that merchants add or activate in the theme editor. A web pixel extension ships a small JavaScript module that runs in a sandbox and subscribes to the customer events that Shopify publishes. This page explains both in full: the file layout, the block schema, every block target, how merchants activate the blocks and how an app detects that, the deprecation of script tags with the dates that now apply, the pixel sandbox and its APIs, how pixels are activated for a shop, and how consent decides whether any of this code runs.

The page sits after the pages on sections and theme blocks (which explain the @app block type from the theme side) and on apps and scaffolding (which explain shopify.app.toml and the CLI), and it uses the access scopes described in authentication and access scopes. The running example is the Pocket Coffee companion app. It ships an app block that shows the roast date of the beans on the product page (the "Roast date badge"), an app embed block with a small Coffee Club widget that used to be a script tag, and a web pixel that reports add-to-cart and purchase events to a first-party collector. All three respect the visitor’s consent choices.

This page was prepared without a Shopify account, so no extension was ever deployed, previewed in a theme editor or activated in a store. What did run locally is listed in What was run and what was not: the shopify app build command on a complete app with one theme app extension and one web pixel extension, Theme Check on the extension and on a theme that accepts app blocks, deliberately broken variants of both, the bundled pixel executed in a Node harness with fake events, the consent-gated storefront script executed with a stubbed Customer Privacy API, and every GraphQL document validated against the downloaded 2026-10 Admin schema. Everything that needs a store, such as shopify app dev, shopify app deploy, the theme editor and real consent banners, is documented from the official pages and was not executed.

Script tags, theme edits and the two replacements

Before the extension types existed, an app had three ways to reach the storefront, and the page needs the vocabulary of all three because most real apps still contain at least one.

Technique What it did Status on 2026-10-27

Asset API edits

The app wrote a snippet into the merchant’s published theme and edited layout, template or section files to render it.

The legacy path that the migration guide asks apps to leave. Uninstalling the app leaves the edited code (ghost code) behind, and the edits take the merchant’s theme off its automatic upgrade path.

Script tags

The app registered a remote JavaScript file with the ScriptTag resource. Shopify injected it into storefront pages (and, until 2025 and 2026, the Order status page).

Deprecated. scriptTagCreate and scriptTagUpdate fail from 2026-10-01 on every API version; Shopify stops injecting script tags into storefronts on 2027-03-01.

Theme app extensions

The app ships blocks (Liquid), assets and snippets in an extension. Shopify renders them and merchants control them in the theme editor.

Current, and required for any App Store app that integrates with a theme.

Web pixel extensions

The app ships a sandboxed JavaScript module that subscribes to customer events.

Current, and the replacement for script tags that only collect data.

The migration guide states the App Store rule plainly: an app that integrates with a Shopify theme and is submitted to the Shopify App Store must use theme app extensions. Built for Shopify (BFS), Shopify’s badge for apps that meet its quality criteria, adds that such an app must uninstall cleanly using theme app extensions; on 2025-09-25 Shopify extended the grace period for apps that stop meeting that criterion to 60 days before the badge is removed.

Script tag timeline

Script tags are being removed in two separate steps, one for each place they ran. The dates below come from the script tag deprecation pages and the developer changelog entry of 2026-08-24.

Date What happens

2025-02-01

Apps can no longer create script tags whose display_scope is order_status or all.

2025-08-28

Script tags stop running on the Order status page for Plus stores.

2026-08-26

Script tags stop running on the Order status page for all other stores.

2026-10-01

scriptTagCreate and scriptTagUpdate return a permission error on every API version, and POST and PUT requests to the REST ScriptTag resource fail the same way. Pinning an older API version does not defer it. Reads and deletes keep working so that an app can audit and clean up. Existing script tags keep running.

2027-03-01

Shopify stops injecting script tags into storefront pages. Leftover records have no effect after that date, so deleting them is optional.

Two details of the schema are worth knowing. The ScriptTagDisplayScope enum has three values in the 2026-10 schema: ONLINE_STORE, and the deprecated ALL and ORDER_STATUS (the latter "unavailable as a mutation input"). And the scriptTagCreate mutation is still present in the schema and not marked deprecated there, so a document that creates a script tag still validates against the schema; it is the runtime that refuses it. The deprecation page also records that an earlier plan to show a warning banner to merchants who install an app that uses script tags was dropped, so nothing in the admin will tell the merchant that an app is about to stop working.

Choosing the right extension

The deprecation page gives a two-row rule that is easy to remember: a script that loads JavaScript on storefront pages becomes an app embed block, and a script that tracks analytics, conversions or customer behaviour becomes a web pixel. A rule of thumb for the Pocket Coffee app: the roast date badge is an app block, because the merchant wants it next to the product price and the block must follow the product being displayed; the Coffee Club widget is an app embed block, because it floats over every page and has no place in the section layout; the add-to-cart reporting is a web pixel, because it only collects data.

Theme app extensions

A theme app extension is a bundle of app blocks, app embed blocks, assets and snippets that lives in the extensions folder of the app and is deployed with the rest of the app version. Its advantages over editing themes are the ones the documentation lists: the app is exposed in the theme editor automatically, every store gets the new version at the same time through app versions, assets are served from Shopify’s CDN, one set of integration logic works for all themes, and merchants never touch theme code. Extensions are generated with the CLI:

shopify app generate extension --template theme_app_extension --name pocket-coffee-theme

Source: Build theme app extensions

The command needs a logged-in Shopify identity and an app linked to the CLI, so it was not run for this page; in a non-interactive shell without credentials it stops with "To run this command, log in to Shopify". The template it uses is public (theme_app_extension in the Shopify/extensions-templates repository). It generates shopify.extension.toml with name and type, a blocks/star_rating.liquid app block that reads a demo.avg_rating product metafield, a snippets/stars.liquid snippet, a locale file and a thumbs-up image. The tutorial asks you to create that metafield definition (area Products, namespace demo, key avg_rating, type Integer) and give at least one product a value, so that the example block has something to show.

App blocks

An app block shows inline content that the merchant can place. You create one by setting "target": "content" in the schema. The older value section still works and behaves identically, but new blocks should use content. By default a theme has no app blocks after an app is installed: the merchant adds them from the Apps section of the theme editor, either inside a section that accepts app blocks or as a wrapped block of its own at section level.

Use app blocks for apps whose content should follow dynamic sources (reviews and star ratings), for content that merchants may want to reposition, and for content that should span the full page width. They are the right choice for the Pocket Coffee roast date badge:

{%- liquid
  assign product = block.settings.product
  assign roast_date = product.metafields['$app:roast'].roast_date.value
-%}

{%- if product != blank and roast_date != blank -%}
  <p class="pc-roast-badge" style="--pc-badge-color: {{ block.settings.badge_color }};" {{ block.shopify_attributes }}>
    {{- 'roast_badge.label' | t }}: {{ roast_date | date: '%d/%m/%Y' -}}
  </p>
{%- elsif request.design_mode -%}
  <p class="pc-roast-badge pc-roast-badge--empty" {{ block.shopify_attributes }}>
    {{- 'roast_badge.empty' | t -}}
  </p>
{%- endif -%}

The block does five things that are typical of app blocks. It reads the product through an autofill resource setting, so that on a product page it points at the product being shown without the merchant choosing it. It reads an app-owned metafield through the reserved prefix $app:roast (see App-owned data: metafields and metaobjects). It prints block.shopify_attributes so that the theme editor can select the block when it is clicked in the preview. It shows an explanatory placeholder only when request.design_mode is true, that is, inside the theme editor, so the merchant can see and position the block even before any product has a roast date. And it declares one stylesheet that Shopify loads once per page however many badges the page contains.

What a theme needs to host app blocks

App blocks only work in themes that contain JSON templates and sections that both support and render blocks of type @app. The theme side is described in the page on sections and theme blocks; the essentials for an app developer are these.

  • A section opts in by listing a generic block of type @app in its schema, and renders the blocks with the content_for 'blocks' tag (or with render block inside a for loop over section.blocks for section-defined blocks). A block of type @app does not accept the limit setting; Theme Check reports Property limit is not allowed if you add one.

  • A section that supports app blocks may contain at most one resource setting of each type as a section setting (one product, one collection), to keep autofill unambiguous.

  • App blocks are not supported in statically rendered sections.

  • When a merchant adds an app block as a top-level block of its own, Shopify wraps it in a wrapper section. The theme can supply sections/apps.liquid, or the more general sections/_blocks.liquid (which accepts both @theme and @app blocks), and both need an @app block type and a preset; without them the theme editor returns an error and merchants cannot use the section (for apps.liquid the messages are "Apps not supported" and "Apps section is invalid"). If neither exists, Shopify falls back to a platform-generated apps.liquid. The apps.liquid schema cannot use the templates attribute, because the wrapper must be available on all templates.

The following section and wrapper were added to the Skeleton reference theme and checked with Theme Check; they are the smallest theme that accepts the roast date badge on its product page.

When a merchant adds the badge to the Coffee Club product template, the theme editor saves a reference to the block in the template’s JSON. The reference has the form shopify://apps/<app handle>/blocks/<block handle>/<unique id>:

  "sections": {
    "main": {
      "type": "product",
      "blocks": {
        "roast-badge": {
          "type": "shopify://apps/pocket-coffee/blocks/roast_date_badge/00000000-0000-0000-0000-000000000000",
          "settings": {
            "badge_color": "#6f4e37"

The unique identifier shown here is a placeholder. The product setting is absent from the saved settings because an autofill setting resolves to a dynamic source and does not need a stored value.

Whether a store’s published theme supports app blocks decides which integration to ship, and the "Verify theme support" page shows how to find out. With the read_themes scope the app reads the main theme (themes(first: 1, roles: [MAIN])), fetches the JSON templates it wants to integrate with (templates/product.json, templates/collection.json, templates/index.json), finds the section whose id is main or whose type starts with main-, reads that section’s file, and looks for a block of type @app in its schema. If every template passes, use an app block and do not create a script tag; if not, use an app embed block, which works on vintage themes and in which your JavaScript places content wherever it needs to, as a script tag did. The onboarding differs accordingly: instructions for adding the block in the first case, and instructions for a manual step such as pasting a snippet or adding a custom Liquid block in the second. Only the main section of the default product template is required to support app blocks, although Shopify recommends that every section with blocks does.

Source: Verify theme support

App embed blocks

An app embed block holds code that has no UI slot of its own, or that floats or overlays the page: chat bubbles, product image badges, cookie banners, SEO meta tags, analytics and tracking snippets. Shopify renders it and injects it before the closing </head> or </body> tag, depending on the target:

target Where it is injected and what it is for

head

Inside the document head. For meta tags, structured data and scripts that must be early.

compliance_head

Inside the document head, first, ahead of the other head blocks. Reserved for cases where order matters for compliance, for example cookie consent banners and consent defaults that other scripts read.

body

Before the closing body tag. For floating components and scripts that can wait.

App embed blocks are off after installation. A merchant activates them in the theme editor under Theme settings and then App embeds, and an app cannot activate them on the merchant’s behalf; what the app can do is send the merchant to the theme editor with the embed already switched on (see Deep links). They work in vintage themes and in Online Store 2.0 themes alike, because they do not depend on sections or JSON templates, which is why one embed can replace a script tag for every merchant without maintaining a second installation path. The price of that independence is scope: an app embed block can only see the Global Liquid scope of the page it is rendered on, so it cannot use autofill or read a section’s settings. An embed can also limit itself to chosen templates with enabled_on, which a script tag could never do; loading a script only on the pages that need it is one of the performance arguments for the migration.

The Coffee Club widget is the Pocket Coffee example. It replaces a script tag that used to inject a floating "free shipping above 40 EUR for club members" message on every page.

  data-consent-purpose="{{ block.settings.consent_purpose }}"
  data-greeting="{{ 'club_widget.greeting' | t | escape }}"
  hidden
></div>

The same block could not read product on a product page unless the theme’s Global Liquid scope provides it there, and that is not guaranteed, which is the practical reason to prefer an app block whenever content must follow a resource.

A second embed uses the compliance_head target to set safe defaults before any other script runs:

<script>
  window.pocketCoffee = window.pocketCoffee || {};

</script>

The script that a block loads through the javascript attribute is added to the page head as <script async>, so its position relative to other scripts is not guaranteed; an inline script in a compliance_head block is the way to run something before them. If several blocks on the page reference the same JavaScript or stylesheet file, the file is included once.

Three notes on the table. First, the documentation asks for schemas to avoid cluttering the theme editor: all app embed blocks of all apps live in one panel, so limit settings to visual ones. Conditional blocks with available_if

A block can be shown only to some stores, for example only to a plan tier or a region. The condition is a boolean app-data metafield that the app writes, read through the Liquid app object:

{% schema %}
{
  "name": "Club members only",
  "target": "content",
  "stylesheet": "app.css",
  "javascript": "app.js",
  "available_if": "{{ app.metafields.conditional.block1 }}",
  "settings": []
}
{% endschema %}

Source: Configure theme app extensions: conditional app blocks

The example uses an app-data metafield of namespace conditional and key block1, which must be of type boolean. If the metafield value is true the block renders and is available in the theme editor; otherwise it is not. The app Liquid object has a single property, metafields, which exposes the metafields owned by the app. The snippet above was not included in the Pocket Coffee extension because the extension has no such metafield; the attribute is documented, not executed.

Autofill

autofill is a setting on resource settings (product, collection, article and similar) of app blocks. When the merchant adds the block to a section, Shopify fills the setting with a dynamic source: the parent section’s resource setting of the same type, or the template’s global resource. A featured product section has a product setting that selects the featured product, and an app block with an autofill product setting automatically uses it; on a product template it uses the product being displayed. That is why a reviews or ratings block never needs an extra step to find the product. The setting does not exist for app embed blocks, because they only have the Global Liquid scope.

Liquid scope and restrictions

App blocks and embeds are rendered in a restricted Liquid environment. The restrictions are not obvious from the theme side and cause most "it works in my theme but not in the extension" problems.

  • They cannot be rendered on checkout pages: contact information, shipping method, payment method and Order status. Checkout customisation uses checkout UI extensions and thank-you page extensions instead.

  • The content_for_header, content_for_index and content_for_layout objects are not available.

  • Of the parent section object only the id property is available. Use it with the Section Rendering API to re-render the section.

  • JSON files cannot contain comments or trailing commas.

  • Since 2026-01-13 Shopify enforces stricter Liquid parsing for all themes and requires new theme store and App Store submissions, including theme app extensions, to be strict-parsable. The changelog describes an automatic rewrite, with an explanatory comment, for non-conforming theme files; for an extension, write strict-parsable Liquid yourself and let Theme Check confirm it.

Detecting whether a block is active

There are two ways to learn whether the merchant added a block or enabled an embed, and the documentation recommends them in this order.

From inside the Shopify admin, call shopify.app.extensions() of the App Bridge App API. It needs no extra access scope and returns, for each extension of the app, the activation status of every block on the published theme. A status of active means the block is on the published theme; available means the app ships it but the merchant has not enabled it. Since 2026-01-23 the method covers theme app extensions as well as admin, checkout and customer account extensions.

const APP_EMBED_HANDLE = 'club_widget';

const extensions = await shopify.app.extensions();

const themeExtensions = extensions.filter(
  (extension) => extension.type === 'theme_app_extension',
);

const isActive = themeExtensions.some((extension) =>
  extension.activations.some(
    (block) => block.handle === APP_EMBED_HANDLE && block.status === 'active',
  ),
);

Source: Migrate to theme app extensions: check from your app in the Shopify admin

Because the method runs in the browser, the answer only exists when a merchant opens the app, so record it if you need it later. A block’s handle is its file name, which is why the deep link and the check use the same string.

An embed appears in settings_data.json only after it has been enabled once; if it is disabled afterwards it stays in the file with "disabled": true. Merchant experience and UX guidelines

Shopify’s UX guidance for theme app extensions is short, and following it is a condition for a good review.

  • App blocks should be responsive to the width of the section they are added to and inherit the theme’s typography and colours rather than hardcode their own.

  • App blocks in the header should have an icon and a text version so they fit inline, keep the interface the same on desktop, tablet and mobile, show icons no larger than 24 by 24 px, and give them a 44 by 44 px hit box.

  • Limit settings to visual ones, particularly for embeds, which all share one panel.

  • Merchants must be able to add, remove and reposition app blocks and edit their settings from the Apps section, and activate, deactivate and edit app embeds from the App embeds section, previewing before they save.

  • The App Store listing must say whether the app needs an Online Store 2.0 theme.

  • Give clear post-install instructions on the app’s onboarding page: ask which theme the merchant uses, because the instructions differ between Online Store 2.0 and vintage themes; explain how to add, remove and reorder app blocks, which templates they support and how to configure them; and for embeds provide a deep link and the list of templates on which the embed will appear.

  • When a merchant uninstalls the app, Shopify removes its blocks from online store themes automatically and entirely.

Migrating from script tags

The migration is mechanical once you know what the script does. The Pocket Coffee app had one script tag, registered years ago with scriptTagCreate, that loaded club-widget.js from the app’s own server and injected the floating Coffee Club message. The steps follow the deprecation page and the migration guide.

  1. Audit. List the script tags the app registered for each store with the scriptTags query. Custom apps maintained per client must be checked store by store, with a token the app already holds. Reads and deletes continue to work after 2026-10-01.

  2. Build the replacement. A theme app extension with an app embed block for a script that loads JavaScript, an app block if the content should be placed by the merchant (this works only on Online Store 2.0 themes), or a web pixel if the script only collects data. For themes that do not support app blocks, the migration guide says to keep a legacy onboarding flow.

  3. Stop writing. When a store’s published theme supports app blocks, the app must skip all POST requests to the Asset and ScriptTag resources.

  4. Release before 2026-10-01. After that date a store that installs the app has no script tag and no extension, so it gets nothing unless the replacement is already live.

  5. Send the merchant to the theme editor with the embed activated, using a deep link.

  6. Confirm that the embed is active on the published theme, with shopify.app.extensions() or the backend check.

  7. Delete the script tag with scriptTagDelete. Running both at once loads the script twice and can double-count analytics events or render the app’s interface twice.

Web pixels

A web pixel is a JavaScript module that runs on the store’s pages, subscribes to the customer events that Shopify publishes, and forwards them wherever the app needs: an analytics service, an advertising platform or the app’s own collector. Shopify’s design goal is to remove the need for merchants to paste tracking code, to give the developer only the data the pixel is entitled to, and to avoid the performance and privacy problems of arbitrary scripts that scrape or rewrite the page. The benefits listed in the documentation are the following: eliminating or minimising manual tracking code, secure access to all surfaces (storefront, checkout and post-purchase pages), control over what data the developer can access, no performance or privacy alerts, and smaller pixel libraries because the DOM-manipulation code is gone.

How a pixel receives events

Once the pixel has been created for a shop, it is loaded on that shop’s online store. As a customer browses, they trigger customer events, which Shopify publishes to a data layer, or event bus. A pixel subscribes to the events it cares about, transforms the payloads into the format of its endpoint, and sends them. The surfaces are not limited to the storefront: since 2025-07-21 web pixels also load automatically on customer account pages and on the Order status page, where the page_viewed event and the Advanced DOM API are supported and custom events can be published from a UI extension. Shops must use a custom domain for customer accounts (for example accounts.your-store.com) for the customer account pages to log events.

The sandbox

App pixels run in a strict sandbox: a web worker. It offers many of the globals of a browser worker, but only the following are guaranteed:

  • self, a reference to the global object.

  • console, the same console as the browser. Shopify asks that production pixels do not log anything.

  • setTimeout, clearTimeout, setInterval and clearInterval.

  • fetch, Headers, Request and Response. Requests to arbitrary endpoints are allowed, but each endpoint must explicitly support CORS, exactly as for fetch() in a normal worker. Use keepalive: true for requests that must survive page unload.

Other globals may be set to undefined or removed at any time, so a pixel must not rely on them. There is no document or window: anything that scrapes the DOM or writes to it is impossible, which is the point. The sandbox replaces the useful parts of those APIs with explicit, asynchronous ones:

Browser feature Pixel replacement

document.cookie

browser.cookie.get(name) and browser.cookie.set(cookieOrName, value), which run in the top frame and return promises.

localStorage, sessionStorage

browser.localStorage and browser.sessionStorage with clear, getItem, key, length, removeItem and setItem, all asynchronous.

navigator.sendBeacon

Deprecated in the pixel API; use fetch with keepalive: true.

document.location, document.title, document.referrer, navigator.userAgent, window.innerWidth

A read-only snapshot in init.context at page render, and in event.context at the moment of each event. document has characterSet, location, referrer and title; location has hash, host, hostname, href, origin, pathname, port, protocol and search; navigator has cookieEnabled, language, languages and userAgent; window has sizes, offsets and screen.

Besides standard events, the DOM Events API provides a subset of interaction events (clicked, form_submitted, input_blurred, input_changed, input_focused) across storefront, checkout and thank you pages (not on customer account pages or the Order status page), and an Advanced DOM Events API exists for finer interaction tracking.

Custom events and the visitor API

Storefront code, theme app extensions, checkout UI extensions and customer account UI extensions can publish their own events, which every app pixel and custom pixel can subscribe to. Partners and merchants cannot publish standard events. The online store exposes the method on the Shopify global:

Shopify.analytics.publish('pocket_coffee:club_widget_shown', { locale: 'en' });

Source: Emitting data

Prefix custom event names with the app name or another unique identifier (my_app:event_name) so they cannot collide with standard events. In a pixel the payload arrives in event.customData. Custom events can be published by users, other developers and even visitors from the browser console, so treat them as untrusted input. The Shopify.analytics.visitor method lets a storefront script pass an email address or phone number the visitor volunteered (for example to receive a discount code) so that Shopify and apps can use it; pass appId so that data quality does not degrade, and make sure the necessary notices and consent have been given. The Coffee Club widget publishes pocket_coffee:club_widget_shown after it has been displayed with consent (see the consent section), which is the link between the two extension types.

The Pocket Coffee pixel

The pixel reports two events to the app’s own collector: every add-to-cart, and the completed purchase. The endpoint is a setting, so each shop can point to a different collector, and the Spanish and English storefronts are told apart by the /en path prefix.

import {register} from '@shopify/web-pixels-extension';

register(({analytics, init, settings}) => {
  const endpoint = settings.endpoint;
  const locale = init.context.document.location.pathname.startsWith('/en') ? 'en' : 'es';

  const send = (name, payload) =>
    fetch(endpoint, {
      method: 'POST',
      headers: {'Content-Type': 'application/json'},
      body: JSON.stringify({name, locale, payload}),
      keepalive: true,
    });

  analytics.subscribe('product_added_to_cart', (event) => {
    const line = event.data.cartLine;
    if (!line) return;
    send('add_to_cart', {
      sku: line.merchandise.sku,
      quantity: line.quantity,
      amount: line.cost.totalAmount.amount,
      currency: line.cost.totalAmount.currencyCode,
    });
  });

  analytics.subscribe('checkout_completed', (event) => {
    const checkout = event.data.checkout;
    send('purchase', {
      orderId: checkout.order ? checkout.order.id : null,
      total: checkout.totalPrice.amount,
      currency: checkout.currencyCode,
      lines: checkout.lineItems.map((item) => ({
        sku: item.variant.sku,
        quantity: item.quantity,
      })),
    });
  });
});

Protected customer data in pixel events

Since 2025-12-10 Shopify enforces its protected customer data policy for all web pixel extensions on every surface (storefront, checkout and customer accounts). Personally identifiable fields (name, email, phone and address) are present in the payload only if the app has been approved for the corresponding protected scope; otherwise the field is null and the structure of the event does not change. The scopes are read_customer_name, read_customer_email, read_customer_phone, read_customer_address and read_customer_personal_data. Custom pixels are out of scope of this change. For the Pocket Coffee pixel, which sends SKUs, quantities and amounts, no PII is read, so no approval is needed; an app that forwards checkout.email must handle null without breaking its pipeline, and should request only the scopes it uses.

Consent and privacy

Every script that touches a visitor’s browser or sends data about them has a legal basis, and Shopify’s tools for it are the same for both extension types: the Customer Privacy API on the storefront and the [customer_privacy] declaration of a pixel. The material below describes what the tools do; what a particular merchant’s obligations are depends on their markets and is a question for counsel, as the Customer Privacy API documentation itself warns.

How Shopify models consent

Shopify distinguishes four processing purposes:

Purpose Meaning Check in the storefront API

Preferences

Remembering choices such as language, currency or size to personalise the visit.

preferencesProcessingAllowed()

Analytics

Understanding how customers use the site and the interactions they make.

analyticsProcessingAllowed()

Marketing

Marketing, attribution and targeted advertising from the merchant.

marketingAllowed()

Sale of data

Sharing data with third parties, usually for behavioural advertising.

saleOfDataAllowed()

Source: Customer Privacy API: call the API

Whether a purpose is allowed for a given visitor combines three things: the merchant’s current privacy settings (is consent required in this region?), the visitor’s location, and what the visitor has consented to. For regions that are configured to require consent, non-essential purposes are not allowed until the visitor consents. For other regions the default is to allow everything. The merchant configures regions and the cookie banner in the admin’s privacy settings; data sale opt-out regions, usually US states, are configured separately, and in them the Global Privacy Control signal is honoured automatically and sets sale_of_data to false.

Pixels and consent

For app pixels consent is enforced for you. The pixel declares its purposes in [customer_privacy], and Shopify’s pixel manager loads the pixel only if the visitor’s permission covers all the purposes the pixel declares as required. The behaviour at the callback level depends on the region:

  • Consent required. Callbacks run only after consent is given. Then all previously registered events are replayed, so the pixel catches up with what happened on the page before the visitor accepted.

  • Tracking on by default, visitor may opt out. Callbacks run as events are registered until the visitor opts out, and not afterwards.

A pixel cannot call the Customer Privacy API itself. If it needs to adapt to consent changes (for example to include the consent state in payloads), it reads init.customerPrivacy for the state at page load and subscribes to customerPrivacy.subscribe('visitorConsentCollected', ...) for later changes. The event payload carries the four flags analyticsProcessingAllowed, marketingAllowed, preferencesProcessingAllowed and saleOfDataAllowed.

import {register} from '@shopify/web-pixels-extension';

register(({analytics, init, customerPrivacy}) => {
  let consent = init.customerPrivacy;

  customerPrivacy.subscribe('visitorConsentCollected', (event) => {
    consent = event.customerPrivacy;
  });

  analytics.subscribe('product_added_to_cart', (event) => {
    const payload = {
      eventName: event.name,
      customerPrivacyStatus: consent,
    };
    fetch('https://collector.example.test/events', {
      method: 'POST',
      body: JSON.stringify(payload),
      keepalive: true,
    });
  });
});

Source: Pixel Privacy: Customer Privacy API

Custom pixels have the same API through api.customerPrivacy and init.customerPrivacy, and set their privacy requirements in the pixel’s settings in the admin instead of a toml file. The visitorConsentCollected event of the pixel sandbox and the document event of the storefront share a name but not an identical payload: the storefront documentation shows analyticsAllowed and preferencesAllowed in the detail, while the pixel API shows the ...ProcessingAllowed names. Read the exact keys from the documentation of the surface you are on, and log one event in a development store before relying on a key.

After the callback runs without an error, the API is on window.Shopify.customerPrivacy. The methods are:

Method Purpose

analyticsProcessingAllowed(), marketingAllowed(), preferencesProcessingAllowed(), saleOfDataAllowed()

Return true or false: may this purpose be processed now? They combine merchant settings, location and consent, and are the right calls to gate code.

currentVisitorConsent()

Returns the visitor’s decisions: {marketing, analytics, preferences, sale_of_data} with values 'yes', 'no' or the empty string (not yet decided). It does not include location or merchant configuration, so it must not be used to decide what is allowed.

setTrackingConsent(consent, callback)

Records the visitor’s decision. consent has analytics, marketing, preferences (booleans) and, separately, sale_of_data, plus optional metafields. Only call it as a result of a visitor interaction, never automatically on the visitor’s behalf.

shouldShowBanner()

true if consent is not yet set and the visitor is in a region that shows a cookie banner. It does not say whether consent was already given.

saleOfDataRegion()

true if the visitor is in a region configured for data sale opt-out.

getRegion()

The detected region as an ISO 3166-2 style string, such as USCA, CAON, IEL or GBENG; empty if unknown.

consentId()

The visitor’s consent ID, useful to look up their consent history in the merchant’s audit log.

getTrackingConsentMetafield(key)

Reads a custom value stored with setTrackingConsent.

The document event visitorConsentCollected is published when consent changes, with the new state in event.detail; updates are published only when consent changes, not when the listener is added. An app that renders its own banner calls setTrackingConsent with the visitor’s choice:

});

Four rules apply. Never read or modify Shopify cookies directly; the API is the only supported interface, and cookie names and formats change. Shopify stopped setting the _tracking_consent, _landing_page and _orig_referrer cookies on storefronts on 2025-09-15; the replacement for _tracking_consent is this API, and for the other two the browser’s window.location.href and document.referrer, or the Web Pixels API, or the customerJourneySummary of an order. Record a data sale opt-out only through a flow the visitor starts (a link or preference page), because the flag is true to allow and false to block and must not be applied on page load. And when the Shopify cookie banner is enabled it shows in the configured regions and passes consent to the API automatically; if the merchant uses an app for the banner, ask that app’s developer where the banner is rendered. The cookie banner has a small runtime API of its own: privacyBanner.showPreferences() opens the preferences modal.

Gating an app embed on consent

An app embed that loads for everyone must itself decide what it may do before consent. The Coffee Club widget does the following, and club-widget.js is the file the schema loads:

(function () {
  'use strict';

  var root = document.getElementById('pc-club-widget');
  if (!root) { return; }

  var purpose = root.dataset.consentPurpose || 'analytics';
  var allowedKey = { analytics: 'analyticsProcessingAllowed', marketing: 'marketingAllowed' }[purpose];

  function allowed() {
    if (purpose === 'none') { return true; }
    var api = window.Shopify && window.Shopify.customerPrivacy;
    return Boolean(api && typeof api[allowedKey] === 'function' && api[allowedKey]());
  }

  function render() {
    root.textContent = root.dataset.greeting;
    root.hidden = false;
  }

  var started = false;

  function maybeStart() {
    if (started || !allowed()) { return; }
    started = true;
    render();
    if (typeof window.Shopify.analytics !== 'undefined' && window.Shopify.analytics.publish) {
      window.Shopify.analytics.publish('pocket_coffee:club_widget_shown', { locale: root.dataset.locale });
    }
  }

  function boot() {
    maybeStart();
    document.addEventListener('visitorConsentCollected', maybeStart);
  }

  if (purpose === 'none') { boot(); return; }
  if (!window.Shopify || typeof window.Shopify.loadFeatures !== 'function') { return; }
  window.Shopify.loadFeatures([{ name: 'consent-tracking-api', version: '0.2' }], function (error) {
    if (error) { return; }
    boot();
  });
})();

Source: Customer Privacy API: use an event listener

The script follows the documented pattern: load the feature, test the purpose with the ...Allowed method that combines merchant settings, location and consent, subscribe to visitorConsentCollected for a later decision, and do nothing that needs consent until it is true. The merchant chooses the required purpose in the block settings; none is for a widget that is strictly necessary, and the default is analytics. The started flag matters: without it the script would render again and publish the custom event again every time a consent event arrived, including in the none mode.

The script was executed in a Node vm context with a stubbed window.Shopify (a loadFeatures that calls back at once, a customerPrivacy whose analyticsProcessingAllowed is switched by the test, an analytics.publish that records its calls) and a stubbed document. It printed:

Data sale opt-out, server-side consent and headless storefronts

Three further pieces complete the picture.

  • Server-side opt-out. The Admin API mutation dataSaleOptOut(email:) opts a customer out of data sale on the server side. It validated against the 2026-10 schema and returns the customerId and userErrors.

  • Headless storefronts. A storefront built outside the Online Store does not have the Shopify banner. For custom storefronts the Customer Privacy API documentation points to Hydrogen’s analytics and consent handling, which manages the session on the server so consent persists across page loads and is honoured by checkout, and is also the only way to integrate a cookie banner fully with Shopify Analytics. Direct callers pass headlessStorefront, checkoutRootDomain, storefrontRootDomain and storefrontAccessToken to setTrackingConsent. For the Storefront API itself, the @inContext directive accepts a visitorConsent argument (since 2025-09-02) with analytics, preferences, marketing and sale of data; the consent is encoded into the checkoutUrl that cart operations return as the _cs parameter, so Checkout Kit and other integrations carry the visitor’s choice into checkout.

  • Cookie-banner apps. If the merchant uses a consent app, the app is responsible for calling setTrackingConsent with the visitor’s choices; the pixel and embed code described above then see consent through the same API.
