Metafields and Metaobjects

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Shopify’s data model is fixed: a product has a title, a vendor and up to three options, and nothing more. Custom data is how a shop or an app adds the rest. A metafield is a typed value attached to an existing resource (a roast date on a product, a membership date on a customer, a gift message on an order). A metaobject is a new record type that you define yourself (a coffee origin with a name, a country, an altitude and a photo) and that products, pages or other metaobjects can point to. This page was written against the Admin GraphQL API and Storefront API version 2026-10, Shopify CLI 5.0.0 (Node.js 22.12 or later) and Theme Check 3.31.0, and every fact was checked on 2026-10-27. The guides state no plan restriction for custom data; the only plan-dependent number is the count of merchant-owned metaobject definitions, listed in Limits.

The page covers ownership and namespaces, how to create, read, update and delete definitions and values, the capabilities that switch on filtering, uniqueness and smart collections, the metaobject capabilities (draft and published entries, translations, web pages), declarative definitions in shopify.app.toml, and every surface that reads the data: Liquid, the Storefront API, Shopify Functions, checkout and customer account extensions, webhooks and analytics. It builds on the Admin GraphQL API page (versioning, cost, pagination), the Apps Overview and Scaffolding page (shopify.app.toml), the Authentication and Access Scopes page (the scopes that custom data needs) and the Liquid Language page. The running example is Pocket Coffee, a small specialty-coffee shop: a roast date, tasting notes and an origin on every product, a Coffee Club tier that a Discount Function reads, a gift message that travels from the cart to the order, and a member-since date on the customer.

Every GraphQL document on the page was validated against the public Admin and Storefront GraphQL schemas for 2026-10, downloaded by introspection. The Liquid was checked with Theme Check, the Function was built and run with the Shopify CLI, and the shopify.app.toml custom data was checked with a small offline script. Nothing was executed against a Shopify store: that needs a store and an access token, and no account or credential was created. The section What was run and what was not lists what each check covered.

What custom data is

Metafields and metaobjects are both custom data stored in Shopify, queryable through the Admin API, renderable in themes, readable by Functions and extensions, and editable by merchants in the Shopify admin when the definition allows it. They answer different questions.

Most data models use both: a metaobject defines the record and a reference metafield attaches it to the products it applies to. The figure shows the model that the rest of the page builds.

The model has two halves on purpose. The custom namespace and the origin metaobject are merchant-owned: store staff and every installed app can edit them, and a theme can rely on them. The $app data (the Coffee Club tier, the eligibility flag, the lot code, the gift message) is app-owned: only the Pocket Coffee app controls its structure. Choosing which half a piece of data belongs to is the central design decision, and the next section explains the rules.

Ownership and namespaces

A metafield’s namespace groups related keys and prevents collisions. It also decides who owns the data. A metaobject has no namespace; its definition type plays the same role. The prefix in the namespace or type is what encodes the owner.

Owner Namespace or type prefix Who can change the definition Who can change the values

Merchant-owned

Any name that does not start with $app and contains no --, such as custom, specs or origin

The merchant and every installed app that has the scope

The merchant and every installed app that has the scope

App-owned

$app or $app:name in the GraphQL API, app or a sub-namespace in shopify.app.toml; the stored form is app--<app id> or app--<app id>--name

Only the owning app

The owning app; merchants only if access.admin is merchant_read_write

Shopify-reserved

Shopify

Usually merchant-owned values

App-data (metafields only)

Any namespace, on the AppInstallation resource

The owning app

The owning app; hidden from the Shopify admin and invisible to other apps

Four rules follow from the table.

  • The $app shorthand is resolved for you in most places. Shopify replaces $app with the stored app--<app id> in Admin GraphQL input, in theme app extensions, in checkout and customer account extension configuration and in Function input queries. Code that is not running as your app (the merchant’s own theme, a headless storefront) uses the full stored namespace, for example app--123456--club. Look the definition up with metafieldDefinitions to see the namespace that Shopify stored.

  • -- is reserved. Since 2025-02-19 no new metafield namespace or metaobject type may contain two consecutive hyphens, because the form is used for shopify--standard and app--<app id>. Existing definitions were left alone.

  • App-owned data stopped being public in 2025. On 2025-05-19 Shopify converted every app-owned metafield and metaobject that had PUBLIC_READ to MERCHANT_READ and PUBLIC_READ_WRITE to MERCHANT_READ_WRITE, in all API versions. Data that another app must read has to move to a merchant-owned namespace such as custom.

  • App-owned does not mean secret. Liquid reads any metafield regardless of its storefront access, and the merchant can see app-owned metafields in the admin (read-only by default). Keep credentials in the app’s own database or in environment variables. Use an app-data metafield for per-installation configuration that the merchant must not see, never for secrets.

Namespace and key syntax

The MetafieldsSetInput documentation of 2026-10 states that a namespace is 3 to 255 characters and a key is 2 to 64 characters, both made of letters, digits, hyphens and underscores. If namespace is omitted in metafieldsSet, the app-reserved namespace is used. The Admin API and Liquid address a metafield as namespace.key; the search syntax adds a prefix, metafields.custom.roast_date.

Standard definitions

Shopify publishes standard metafield definitions for common data (subtitle, ISBN, care instructions, ingredients) and standard metaobject definitions (currently product_review, available to approved partners only). A standard definition has a reserved namespace and key, a known type and preset access, does not count against the definition limits, and is interoperable across themes and apps. List the templates with standardMetafieldDefinitionTemplates, enable one with standardMetafieldDefinitionEnable (or standardMetaobjectDefinitionEnable with the type), or declare it in shopify.app.toml with standard_metafields = ["descriptors.subtitle", "facts.isbn"] under [product.metafields]. A standard metafield definition is also enabled automatically the first time a value is written to its namespace and key. Once enabled, Shopify owns the schema while the values stay merchant-owned.

Metafield definitions

A definition is the schema of a metafield: namespace, key, name, owner type, type, validations, access and capabilities. Without one a metafield is an untyped string that merchants cannot edit with a typed editor, search or validate. Create the definition before you write values.

The MetafieldOwnerType enum of 2026-10 has 26 values: API_PERMISSION, ARTICLE, BLOG, CARTTRANSFORM, COLLECTION, COMPANY, COMPANY_LOCATION, CUSTOMER, DELIVERY_CUSTOMIZATION, DISCOUNT, DRAFTORDER, FULFILLMENT_CONSTRAINT_RULE, GIFT_CARD_TRANSACTION, LOCATION, MARKET, MEDIA_IMAGE, ORDER, ORDER_ROUTING_LOCATION_RULE, PAGE, PAYMENT_CUSTOMIZATION, PRODUCT, PRODUCTVARIANT, SELLING_PLAN, SHOP, TRANSFER (added for inventory transfers in 2026-07) and VALIDATION. There is no CART owner: cart metafields exist on the Storefront API and in checkout, and are copied to order metafields when the order is created. App-data metafields use the AppInstallation resource as owner and need no definition.

Create a merchant-owned definition

A definition in a namespace that is not reserved is merchant-owned. Pocket Coffee needs the roast date to be editable by staff, readable by the theme and by a headless storefront, and filterable in the admin. The mutation takes the input as a variable, which is how an app that lets merchants configure their own fields would call it.

mutation CreateRoastDateDefinition($definition: MetafieldDefinitionInput!) {
  metafieldDefinitionCreate(definition: $definition) {
    createdDefinition {
      id
      namespace
      key
      ownerType
      type {
        name
      }
      access {
        admin
        storefront
        customerAccount
      }
      capabilities {
        adminFilterable {
          enabled
        }
      }
    }
    userErrors {
      field
      message
      code
    }
  }
}

{"definition":{"namespace":"custom","key":"roast_date","name":"Roast date","description":"Date the batch on sale was roasted","type":"date","ownerType":"PRODUCT","access":{"storefront":"PUBLIC_READ"},"capabilities":{"adminFilterable":{"enabled":true}}}}

A merchant-owned definition cannot be declared in shopify.app.toml. The app needs the owner’s scope: write_products for product metafields, write_customers for customer metafields, write_orders for order metafields and so on. Metaobject-reference types need the metaobject scopes too.

Create an app-owned definition with GraphQL

The same mutation with a $app namespace creates an app-owned definition. This one declares a lot code that must match a pattern and be unique across products. Prefer shopify.app.toml for definitions that are the same in every shop (see Declarative definitions); use GraphQL when the structure depends on what the merchant configures in your app.

mutation CreateLotCodeDefinition {
  metafieldDefinitionCreate(
    definition: {
      namespace: "$app:roastery"
      key: "lot_code"
      name: "Lot code"
      description: "Internal lot identifier printed on the bag"
      type: "single_line_text_field"
      ownerType: PRODUCT
      access: { admin: MERCHANT_READ, storefront: NONE }
      validations: [{ name: "regex", value: "^LOT-[0-9]{6}$" }]
      capabilities: { uniqueValues: { enabled: true } }
    }
  ) {
    createdDefinition {
      id
      namespace
      key
    }
    userErrors {
      field
      message
      code
    }
  }
}

A definition that is declared in shopify.app.toml is read-only through the API: the mutation returns an error with the code APP_CONFIG_MANAGED. Change it in the file and deploy.

What happens on uninstall

When a merchant uninstalls the app, Shopify deletes its app-owned definitions, whether they came from TOML or from GraphQL, and keeps the values without a definition for an unspecified time while cleanup runs asynchronously. If the app is reinstalled before cleanup, the definitions are recreated and the values reattached. TOML definitions are deleted and recreated with new GIDs; GraphQL definitions can outlive the uninstall until cleanup removes them. Shopify does not guarantee the retention period, and a definition ID is not a stable identifier across an uninstall: look definitions up by owner type, namespace and key. The same applies to a definition you remove from the TOML file and deploy: the values are retained for a short period and are reattached, with a new GID, if you add the definition back before cleanup.

Data types

Metafields and metaobject fields share the same type system. A value is always stored and exchanged as a string, even for numbers and booleans; a structured value is a JSON string. The type decides how the value is validated, how the admin edits it and what object Liquid returns.

The guide lists 48 basic types in total, plus the reference and list types; metafieldDefinitionTypes returns the authoritative list for the API version you call. A file_reference defaults to a generic file and can be restricted to images or videos with the file_type_options validation. A metaobject_reference can be restricted to one definition, and a mixed_reference to a set of definitions. Deleting a product or variant removes it from every list metafield that references it. integer, json_string and string are older, deprecated types that Liquid still returns as plain values.

Size limits

Most types are limited to 64 KB (65,536 bytes). The exceptions are id and url (2 KB each) and json (128 KB). Since API version 2026-04, writes of JSON values are limited to 128 KB; apps that already used JSON metafields before 2026-04-01 keep the previous 2 MB limit, and new apps that need more can ask for an exception. Large values already stored stay readable in every version. A list holds at most 128 items (1,024 for metaobject references), and each item obeys the size limit of its single type. Shopify Functions input queries do not return metafield values larger than 10,000 bytes: the value is stored and the Admin API returns it, but the Function receives null.

The documentation pages disagree on the app-level definition counts (the limits pages and a changelog give larger numbers than the TOML reference). metafieldsSet has a dynamic cost since 2026-09-15: 10 + sum(distinct owners of a type * weight of that type), with weights of 10 for orders, 4 for products, 2 for variants and 1 for collections, customers and the shop. Setting two metafields on one product, one on another product and one on a variant costs 10 + 2*4 + 1*2 = 20. Cost is charged per mutation invocation, so aliases do not share the base cost, and putting all metafields of a resource in one call is the cheapest way to write them.

A value is written either on the resource’s own mutation, or on its own with metafieldsSet. Use metafieldsSet for anything that is not part of creating or editing the resource.

Metaobject definitions

A metaobject definition has a type (immutable, unique in its owner’s scope), optional name and description, a list of field definitions, an access block, a displayNameKey (the field whose value becomes the entry’s display name and handle), and capabilities. Field definitions have a key, a type from the same type system, a name, a description, required and validations. Since 2026-04 fieldDefinitions is optional in metaobjectDefinitionCreate, so a definition can start empty.

The admin access of a metaobject definition is MERCHANT_READ or MERCHANT_READ_WRITE (app-owned only; merchant-owned types are always fully editable) and the storefront access is NONE or PUBLIC_READ. A merchant-owned origin type needs the read_metaobject_definitions and write_metaobject_definitions scopes to create, and read_metaobjects and write_metaobjects to manage entries. Since API version 2026-04 an app needs no scope at all for its own $app: types.

Declarative definitions in shopify.app.toml

Definitions that are the same in every shop belong in the app’s configuration file. The CLI sends them with shopify app deploy, Shopify creates or updates them in every shop where the app is installed, and shopify app dev tests them on the development store first. The definitions are version-controlled with the app, roll out atomically with the app version and cannot be edited through the API.

Syntax

A metafield is declared as [<owner>.metafields.<namespace>.<key>] and a metaobject as [metaobjects.app.<name>] with [metaobjects.app.<name>.fields.<key>] tables for its fields. The owner is the snake-case form of the owner type: product, product_variant, customer and order in the guides; the other owner types follow the enum names in lower case. The namespace segment app means $app; any other segment creates a sub-namespace of the app, so [product.metafields.club.eligible] declares $app:club and eligible, which is stored as app--<app id>--club. Only app-owned definitions can be declared in TOML; the file cannot create custom or other merchant-owned ones.

access.admin, access.storefront, access.customer_account

merchant_read or merchant_read_write; none or public_read; none, read or read_write

Deploy with shopify app deploy. Remove a block and deploy again to delete the definition; the values are kept for a short period and reattached if the block comes back.

Constraints

  • Only app-owned definitions can be declared, so that Shopify can guarantee the same state in every shop.

  • At most 25 definition changes (create, update or delete) per deploy. The guide does not say whether each field of a metaobject counts as a change, so deploy large schemas in several versions.

  • Declared definitions are read-only through the Admin API (APP_CONFIG_MANAGED).

  • smartCollectionCondition, pin and the onlineStore metaobject capability cannot be declared in TOML.

  • The definitions are distributed to all installations, including shops that never use the feature; keep the count low.

Migrating existing definitions

shopify app import custom-data-definitions (announced on 2026-01-22 as import-custom-data-definitions for CLI 3.89; CLI 5.0.0 lists it with a space) reads the app-owned definitions of a development store, such as $app metafields and $app: metaobject types, and prints the equivalent TOML without writing a file. Review it, copy it into shopify.app.toml, run shopify app dev to test and shopify app deploy to distribute, then delete the code that created the definitions at runtime. Values keep working unchanged. The command needs a development store and a login, so it was not run here; its --help was read.

An offline check before deploy

shopify app build --no-input validates the app configuration, but it does not look inside the custom data tables: a misspelled access value, a reference to a metaobject that is not declared, a missing name, an unknown type and an unknown owner are all accepted, and Shopify rejects them only at deploy. A short script catches the common mistakes earlier. It parses the TOML (npm i smol-toml), resolves $app: references against the declared metaobjects, checks the access values, the owner of cart_to_order_copyable, the display field, the counts of the limits table, and prints the namespace that each declaration resolves to. It does not know the list of types or owner types, which Shopify validates on deploy.

const STOREFRONT = ['none', 'public_read'];

Reading custom data in Liquid

Liquid is the one surface that reads every metafield and every published metaobject entry regardless of the storefront access setting. A theme cannot create or change them: Liquid is read-only, and values are written by the admin or by an app. The Liquid reference describes the objects; this section collects the rules that cause most bugs.

Three details cause most of the confusion.

  • Lists have two ways to count. Reference lists expose .count; non-reference lists are plain arrays and use the size filter. A loop over a reference list returns only the first 50 items; wrap the loop in paginate (up to 250 per page) to reach more.

  • size, first and last are also filters. With dot notation, product.metafields.custom.size returns the number of metafields in the namespace when no metafield is called size. Use brackets, product.metafields.custom["size"], which always looks the key up.

  • Metafields without a type return "string" since 2024-10-28 (metafield.type == blank no longer matches), and the deprecated integer, json_string and string types return plain values without the value and type properties.

Filters that render a metafield

metafield_tag generates an element for the metafield: a <time> for dates, a <span> for numbers and text, an <a> for URLs and references, a <div> for rich text, a <script type="application/json"> for JSON, an <img> or <video> for files, and so on, each with a class such as metafield-date. metafield_text returns plain text (the title of a referenced product, the URL of a file, the number). Neither supports every list type: both handle list.single_line_text_field and list.metaobject_reference only. Dates are localized to the visitor.

Metaobjects in Liquid

The global metaobjects object gives access to published entries by type and handle: {{ metaobjects.origin.yirgacheffe.name.value }} or, with brackets, {{ metaobjects['origin']['yirgacheffe'].name.value }}. An entry is reached through the field keys of its definition, and each field is a metafield object (so .value, .type). The system property groups the built-in properties so that they do not collide with field keys: system.handle, system.id, system.type, system.template_suffix and system.url (the relative URL, set only when the definition has the online store capability). metaobjects.origin.values loops over every entry of a definition, and values_count returns their number. shop.metaobjects was the older path; it still works and has been deprecated since 2025-01-28.

When the publishable capability is on, a DRAFT entry is invisible: a direct lookup returns nil and loops skip it. A metaobject definition whose entries are web pages (renderable and onlineStore) adds a template templates/metaobject/<type>.json or .liquid; inside it the metaobject object is the entry being rendered, and metaobject.system.template_suffix returns the alternate template assigned to an entry, or nil.

Theme settings and dynamic sources

A section or block setting of type metaobject opens a picker for entries of one definition (metaobject_type is required); the value is a metaobject object, or blank when nothing is chosen or the entry is gone. metaobject_list is the multiple version (limit defaults to and cannot exceed 50) and its value can be paginated. Custom definitions are not allowed in themes that are listed in the Theme Store, which must use standard definitions; apps can use the settings with their own app-owned definitions.

Dynamic sources let a merchant connect a section or block setting to a metafield in the theme editor, so the setting follows the product (or collection, or page) being rendered. They are available for section and block settings only, not for general theme settings. Theme blocks reach the nearest resource of a type through closest, for example closest.product. Metaobjects with storefront visibility are available as dynamic sources in any setting, and market- specific values (metafields and metaobjects that are localized per market) follow the market.

Reading custom data with the Storefront API

The Storefront API is for headless storefronts, apps in the buyer’s browser and custom storefronts. It is read-only for metafields (apart from cart metafields) and reads only what the definition exposes.

Exposing and reading

A metafield or metaobject is returned only when its definition has access.storefront = PUBLIC_READ. The separate metafieldStorefrontVisibilityCreate mutation was removed in API version 2025-01; a metafield that was exposed with it must have its definition created or updated with the access setting. Reading metafields and metaobjects needs a Storefront access token: the tokenless access of 2026 covers products, collections, selling plans, search, pages, blogs, articles and the cart, but not metafields, metaobjects, product tags or menus. Use the public token from a browser or the private token from a server (with the buyer IP), as described on the Storefront API and Headless with Hydrogen page.

Resources that implement the HasMetafields interface have metafield(namespace:, key:) and metafields(identifiers: [{namespace:, key:}]). The list form returns one slot per identifier, null in the slot of an identifier that has no readable value, so the order of the response matches the order of the request. These types implement it in 2026-10: Article, Blog, Cart, Collection, Company, CompanyLocation, Customer, Location, Market, Order, Page, Product, ProductVariant, SellingPlan and Shop. A Metafield returns value, type, list, reference and references (for reference types) and parentResource. The reference union can be an Article, Collection, GenericFile, MediaImage, Metaobject, Model3d, Page, Product, ProductVariant or Video.

Metaobjects have two root fields: metaobject(handle: {type:, handle:}) or metaobject(id:), and metaobjects(type:, sortKey:, first:, after:, ...). The Storefront API has no field filter for metaobjects: filter in the Admin API or on the client. A Metaobject has handle, type, fields, field(key:), id, updatedAt, and, for definitions with the renderable and online store capabilities, seo and onlineStoreUrl. The seo title and description are fields themselves, so they need a selection of value. Only active entries are returned when the definition is publishable. The Storefront API accepts @inContext(country:, language:) to return the translation or the market-specific value of a field.

Shopify Functions

A Function’s input query can read the metafields of its function owner (a discount, a payment customization), of the cart, its lines' products and variants, the customer, the shop and the delivery options, and, since API 2026-04, app-owned metaobject entries by handle or ID through the shop field. The metaobject type must use the $app prefix; merchant-owned types are not available. The input query is limited to 3,000 bytes, to a calculated cost of 30 (a metafield costs 3, a metaobject root 1, a field(key:) 3, any other leaf 1) and to values of at most 10,000 bytes. Using a single json metafield for a complex configuration keeps both the query and the merchant interface simple, and changing the shape of a configuration is safest as an expand-and-contract migration: read the old and the new metafield, write both, migrate, then drop the old one.

The Coffee Club Discount Function reads a JSON configuration from the discount (created by the app with metafields on discountAutomaticAppCreate) and the $app:club.eligible flag of each product, and discounts only eligible lines.

The Function (JavaScript, @shopify/shopify_function; the type RunInput is generated by shopify app function typegen from the query and the schema of the target):

// @ts-check

/**
 * @typedef {import("../generated/api").RunInput} RunInput
 * @typedef {import("../generated/api").CartLinesDiscountsGenerateRunResult} CartLinesDiscountsGenerateRunResult
 */

/**
 * Applies the percentage stored in the discount's app-owned JSON metafield to
 * the cart lines whose product has the $app:club.eligible metafield set to true.
 * @param {RunInput} input
 * @returns {CartLinesDiscountsGenerateRunResult}
 */
export function run(input) {
  const config = input.discount.club?.jsonValue;
  if (!config || typeof config.percentage !== 'number') {
    return {operations: []};
  }

  const targets = input.cart.lines
    .filter((line) => 'product' in line.merchandise && line.merchandise.product.clubEligible?.value === 'true')
    .map((line) => ({cartLine: {id: line.id}}));

  if (targets.length === 0) {
    return {operations: []};
  }

  return {
    operations: [
      {
        productDiscountsAdd: {
          candidates: [
            {
              message: config.message ?? 'Coffee Club',
              targets,
              value: {percentage: {value: config.percentage}},
            },
          ],
          selectionStrategy: 'FIRST',
        },
      },
    ],
  };
}

Checkout and customer account UI extensions

An extension declares the metafields it needs in shopify.extension.toml: for the whole extension or for one target, each with namespace, key and, since 2026-10, owner_type (CART, COMPANY, COMPANY_LOCATION, CUSTOMER, PRODUCT, PRODUCTVARIANT or SHOP). owner_type is optional in 2026-10 and required in 2027-01, when a deployment that omits it is blocked. An app-owned metafield is requested with namespace = "$app" or "$app:sub"; the fully qualified app--<app id> form is not supported there, and an extension can read only the app-owned metafields of its own app. The values arrive through shopify.appMetafields. Checkout and customer account extensions can use cart metafields (checkout) and order metafields (customer accounts) in place of the removed checkout metafields.

Events, webhooks and analytics

  • Webhooks: metaobject topics need a type: filter, and metafield definition topics exist, as shown earlier.

  • Events: an Events subscription can name the metafields that trigger it, product.metafield(namespace: 'custom', key: 'roast_date').value, and query the resource that changed. Both $app and merchant-owned metafields are supported and the app must have access to the metafield.

  • Flow and admin extensions: merchant automations and admin UI built on the same definitions are covered on the Flow, POS and Admin Extensions page.

  • Analytics: a definition with the analyticsQueryable capability can be grouped and filtered in analytics reports and ShopifyQL.

  • Translations and markets: text types, rich_text_field, json, link, url and file_reference are translatable with translationsRegister, and money and reference types such as products and pages can be localized per market with marketLocalizationsRegister; Liquid and the Storefront API then return the value of the visitor’s market and language.

Pitfalls and documentation differences

Symptom Cause and fix

Unknown argument "input" on field "Mutation.productUpdate"

API 2026-10 takes product: (a ProductUpdateInput). The guides for app-owned and merchant-owned metafields still show productUpdate(input: {...}). The same applies to productCreate.

Enum "MetafieldStorefrontAccessInput" cannot represent non-enum value: "PUBLIC_READ"

Enum values are written without quotes. The Storefront guide shows access: { storefront: "PUBLIC_READ" }.

Unknown argument "id" on field "Mutation.metafieldDefinitionUpdate"

The update identifies a definition by ownerType, namespace and key inside definition. The Storefront guide shows an id argument.

Field "type" of type "MetafieldDefinitionType!" must have a selection of subfields

type and access of a definition are objects, so select type { name } and access { admin storefront }. One guide example selects them bare.

Field "key" is not defined by type "MetaobjectFieldDefinitionOperationInput"

Fields of a definition are updated with create, update and delete operations. The guide’s example passes the field directly.

Unknown type "MetaobjectDefinitionUpdate"

The input type is MetaobjectDefinitionUpdateInput. A capabilities example uses the shortened name.

Filter by metafield returns every product (before 2026-10) or an error (from 2026-10)

The definition has no adminFilterable capability, or the type or comparison is not supported. Enable the capability and use a documented comparison.

metafieldsSet rejects a value

The type is missing and there is no definition, the value does not match the type, a compareDigest is stale, or more than 25 metafields were sent.

Liquid prints nothing for an app-owned metafield in the merchant’s theme

The theme must use app--<app id>--sub; the $app: shorthand works only inside the app’s theme app extension.

A loop over a reference list stops at 50 items

Wrap the loop in paginate (250 per page).

product.metafields.custom.size returns a number

size is also a filter. Use product.metafields.custom["size"].

Draft metaobject missing on the storefront

The publishable capability is on and the entry is DRAFT. Publish it with metaobjectUpdate.

shopify app deploy is rejected for the 26th definition change

At most 25 definition changes per deploy; deploy in several versions.

Customer account extension gets null for an app metafield

Since 2026-06-16 the metafield needs a definition with access.customerAccount set.

The Function receives null for a metafield that exists

The value is larger than 10,000 bytes, or the metaobject type is not app-owned.
