Shipping, Taxes, Payments and Checkout Settings

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

This page was written against the Admin GraphQL API 2026-10 (the latest stable version, released 2026-10-01; 2027-01 is the release candidate), the Shopify Functions templates that Shopify CLI 5.0.0 generates (API version 2026-07) and the Shopify Help Center as it read on 2026-10-27, the day it was checked. It explains the four things a merchant configures after products exist and before the first real order: how shipping rates are built (delivery profiles today, shipping options by market as they roll out), how taxes are calculated and displayed, how payments are accepted and captured, and which checkout settings change what the buyer sees. For each area it lists the settings in the admin, the Admin and Storefront API operations that read or change them, the Shopify Functions that customize the result, the plan limits and the pitfalls. The running example is Pocket Coffee, the small Spanish specialty-coffee shop used across this section: two shipping zones (Spain at 4.90 EUR, free from 40 EUR, and the rest of the European Union at 9.90 EUR), a 5 kg parcel limit, a Coffee Club customer group, Spanish and English storefronts in EUR, and test customers ada@example.test and grace@example.test.

Everything that can run without a store was run: the GraphQL documents were validated against the introspected 2026-10 Admin and Storefront schemas (variables included), the two Shopify Functions were built with Shopify CLI 5.0.0 and run with the function runner, the Liquid snippets were checked with Theme Check, the shopify.app.toml and extension descriptors were validated by shopify app build, and the carrier-service callback was started locally and called with sample requests. Nothing that needs a Shopify store, an account or a login was executed: the admin steps come from the Help Center, the GraphQL mutations were not sent to a store, and the checkout behavior described for a live store is documented behavior, not observed behavior. The section "What was run and what was not" lists the details.

The money path of a checkout

A Shopify checkout builds the amount a buyer pays in stages. The cart holds the variants, quantities, weights and the delivery address. Delivery options are produced from the shipping configuration (delivery profiles, or shipping options attached to markets), from carrier services, local delivery and pickup, and are then optionally reshaped by a Delivery Customization Function. Taxes are calculated by the tax service selected for each region (Shopify Tax, Basic Tax, Manual Tax or a tax app) and displayed as included or added. Payment methods come from Shopify Payments, third-party gateways, wallets and manual methods, and are optionally reshaped by a Payment Customization Function. The order records the transactions and the capture setting decides when the money is taken.

Buyers never see these stages as separate steps; one-page checkout shows them on a single page. The stages matter to developers because each one has its own configuration owner, its own API and its own plan restrictions:

Delivery profiles in the admin

Shipping is configured in Settings, Shipping and delivery. Each store has a General profile that applies to all products; all existing and new products are added to it, and a product or variant that is not in a custom profile uses the General rates. A store can create up to 99 custom profiles when different products need different rates, for example fragile products that need a more expensive service. A product or variant belongs to exactly one profile at a time: adding it to a second profile removes it from the first, and removing a variant from a custom profile returns it to the General profile (the API field variantsToDissociate is documented the same way).

When a profile is created, every location that can fulfill online orders is added to it in one location group, so that all those locations share the same zones and rates. A location can be moved into its own location group to give it different zones and rates, removed from a group (shown under "Not fulfilling from"), or added to an existing group. If the last location of a group is removed, the group’s zones and rates are deleted. Locations that are deactivated are labeled Inactive: rates can be added to them, but they are not used at checkout until the location is activated. A location created after a profile is added to every profile as not fulfilling. Some apps that manage fulfillment, such as on-demand printing apps, are added to the profile as locations automatically and can change the setup.

A new store gets default rates created from the store location, domestic and international, and the Help Center warns that these frequently include a free shipping rate; they should be reviewed before the store accepts orders. Staff or collaborators need the Products and Manage settings permissions to work with shipping profiles.

Rate types

Within a zone, a rate has one of four types:

Rate type Behavior

Flat

One price for the zone. By default a flat rate applies once per order, not once per product; charging per product needs separate rates or an app.

Order amount

Price-based ranges, for example 24.99 USD from 0 to 100 USD, 9.99 USD from 100.01 to 200 USD and free above 200.01 USD. The maximum of the last range can be left empty.

Weight

Weight ranges evaluated on the combined weight of the items that ship from the same location with the same option. Every product needs a weight, or the rate does not calculate correctly; the store default package weight is added to each product.

Carrier or app calculated

The carrier or an app returns the price from weight, dimensions and destination. Built-in carrier integrations are available on all plans; connecting your own carrier accounts (UPS, FedEx, USPS, Canada Post, Australia Post) is third-party carrier-calculated shipping, which needs a plan or fee as described above.

Any rate can be made free by leaving the price empty or entering 0, and the "Offer free shipping" option adds a minimum order amount above which the rate costs nothing. Flat rates can show a transit time (a suggested value or a custom range such as 3-5 days) that feeds the delivery estimate at checkout. Flat rates in local currencies exist only for stores that use Shopify Payments: a rate set per market currency is shown as set, whereas automatic conversion of a EUR rate shows a converted amount (the Help Center gives roughly 120 SEK for a 10 EUR rate); separate zones per region give fixed prices instead of converted ones.

Source: Shopify Help Center: Setting up shipping zones and rates

How rates combine when a cart spans profiles and locations

Carts whose items sit in different profiles or ship from different locations get a single combined rate. The rules, as documented, are these:

  • Rates with the same name are added together and shown under that name, even if they are in different profiles. If the rate names differ, the cheapest options are added together and shown as "Shipping".

  • Price-based rates apply to the cart total; weight-based rates apply to each product’s weight plus the store default package weight, and the resulting rates are then combined.

  • If an order must ship from several locations of the same location group with a flat rate, one flat fee is charged: a 5 USD group charged once even when two locations are needed.

  • If several locations in the same group could fulfill all items, fulfillment priority picks the location, and the other location’s rate is free.

  • If an order needs different location groups, their rates are added.

The consequence is that the way profiles and rate names are organized changes what the buyer pays, and the Help Center states that a combined rate can lead to higher shipping costs. Two Pocket Coffee consequences: the Standard rate in the Spanish zone and the same-named Standard rate in a second profile for the Starter kit would be added together unless the profiles are deliberately named and priced as one rate, and the shop should keep every variant of the same parcel in one profile.

Source: Shopify Help Center: Calculating shipping rates from different shipping profiles

Backup rates

When all app or carrier calculated rates of a shipment fail and no other eligible rate exists, backup rates are shown so that checkout does not stall. They apply to the whole store by default and need no setup, only when at least one app or carrier-calculated rate exists. Shopify-supported carriers provide them where available (USPS, Canada Post, Evri, Chronopost, Poste Italiane and Correos in the listed countries), country-specific rates built from historical data cover the other zones, and legacy custom backup rates by order value or weight still work. Flat rates for the same destinations are always shown when eligible, so they can be chosen even while calculated rates work. A product without a weight is treated as weight 0 when backup rates are chosen, which can produce wrong prices. Since 2025-05-22 a 3xx or 4xx response from a carrier also triggers backup rates instead of a hard failure.

Source: Shopify Help Center: Backup shipping rates

The requirements and behaviors of the callback are:

  • The store must be on the Advanced plan or higher, on a lower plan with yearly billing or with the feature added for a monthly fee, or be a development store that is not on the Basic plan. If the store later stops meeting this, the association is deactivated.

  • Shopify sends a POST with a rate object (origin, destination, items with grams, price and requires_shipping, currency, locale). Since 2025-11-04 the payload also contains the order totals (subtotal_price, total_price, discount_amount) and the customer’s id and tags. For API-created services only the address fields address1, address2, city, zip, province and country are filled.

  • The response is {"rates": [...]} where every rate has service_name, description, service_code, currency and total_price (as a string in minor units, so 1290 for 12.90 EUR), and optionally phone_required, min_delivery_date and max_delivery_date.

  • An empty array with a 2xx status means that the service cannot handle the request; a 40x or 50x status forces backup rates; redirects are followed only on the same domain; there is no retry.

  • The read timeout depends on the requests per minute of the shop and app pair: 10 seconds under 1,500, 5 seconds from 1,500 to 3,000 and 3 seconds above 3,000.

  • Shopify caches identical requests (same variants, quantities, weights, origin and destination) for 15 minutes after a success and 30 seconds after an error.

  • From API version 2026-10, carrierServiceCreate only registers the service; it is no longer added automatically to the General shipping profile or its zones. The rates must be added to a profile by the merchant in the admin (the recommended path) or programmatically through the profile APIs, or merchants see no rates from the new service. Older supported API versions keep the automatic behavior until they are retired.

A minimal callback for Pocket Coffee that offers an Express rate (12.90 EUR) inside Spain for parcels up to 5 kg:

import { createServer } from "node:http";

const EXPRESS_PRICE_CENTS = 1290; // 12.90 EUR
const MAX_GRAMS = 5000; // parcel limit

export function ratesFor(rate) {
  const grams = rate.items
    .filter((item) => item.requires_shipping)
    .reduce((sum, item) => sum + item.grams * item.quantity, 0);

  // Express is offered inside Spain only, and only below the parcel limit.
  if (rate.destination.country !== "ES" || grams > MAX_GRAMS) {
    return []; // empty array with a 2xx status: "cannot handle this request"
  }

  // Delivery dates use the format shown in the carrier service documentation.
  const formatDate = (date) => date.toISOString().replace("T", " ").replace(/\.\d+Z$/, " +0000");
  const tomorrow = new Date(Date.now() + 24 * 3600 * 1000);
  const dayAfter = new Date(Date.now() + 48 * 3600 * 1000);
  return [
    {
      service_name: "Express",
      service_code: "pc_express",
      description: "Next working day",
      currency: "EUR",
      total_price: String(EXPRESS_PRICE_CENTS), // subunits, as a string
      min_delivery_date: formatDate(tomorrow),
      max_delivery_date: formatDate(dayAfter),
    },
  ];
}

const server = createServer((req, res) => {
  if (req.method !== "POST" || req.url !== "/carrier-rates") {
    res.writeHead(404).end();
    return;
  }
  let body = "";
  req.on("data", (chunk) => (body += chunk));
  req.on("end", () => {
    try {
      const { rate } = JSON.parse(body);
      res.writeHead(200, { "Content-Type": "application/json" });
      res.end(JSON.stringify({ rates: ratesFor(rate) }));
    } catch {
      res.writeHead(400).end(); // a 4xx makes Shopify fall back to backup rates
    }
  });
});

server.listen(Number(process.env.PORT ?? 8787), "127.0.0.1");

Local delivery, pickup in store, pickup points, split shipping

Besides shipping, a store can offer other delivery methods:

  • Local delivery is activated per location, within a radius or a list of postal codes. The maximum radius is 160 kilometers or 100 miles and does not cross borders. A location has up to 10 delivery zones, each with up to 3 extra price-based rules, and a postal-code list is at most 3,000 characters. The option name "Local delivery" cannot be changed. Eligibility requires that all physical items come from one location with enough stock, that Google can verify the address, and that the buyer has not chosen an accelerated checkout other than Shop Pay in the first step. B2B checkouts do not support it, but a B2B draft order with local delivery preselected does.

  • Pickup in store is activated per location with a processing time, optional store transfers (inventory moved from other locations when the pickup location lacks stock), transfer exclusions by collection and a "ready for pickup" notification. When a store transfer is needed, the checkout shows an estimated pickup time that includes the transfer.

  • Pickup points (post offices, relay points, lockers) are early access for eligible stores and carriers. Apps that generate pickup point options with Shopify Functions are available only to custom apps on development stores or Plus stores.

  • Ship and pickup in one order lets Plus and Enterprise merchants offer shipping or pickup per item in one checkout; it was in feature preview on 2026-10-27. Checkouts then have several delivery groups and orders can contain fulfillment orders with different delivery methods (SHIPPING and PICK_UP), so apps must not assume one method per order.

  • Split shipping happens when a cart cannot ship in one shipment: pre-orders, subscriptions, items from different locations, products from different profiles. The buyer sees the number of shipments and a method per shipment; by default the lowest total cost is selected. The setting is retired for stores upgraded to shipping options by market, where split shipping is always on.

Market-driven shipping (shipping options by market)

Shopify is replacing merchant-owned delivery profiles, location groups and zones with shipping options attached to each market. A market has options (flat, order-value, weight or carrier-calculated), and inside one option the rate can vary by product and location conditions. Product conditions are all products or collections (rates are no longer assigned to single variants, so a group of variants needs a collection), and location conditions pick the fulfillment locations. When several rates in the same option match a cart, only the highest matching rate is charged instead of the sum, and when several options match, the option prices are added. The upgrade combines rates with the same name into one option, turns the former product groupings into unpublished collections with the prefix [Shipping], can create sub-region markets to keep the former zone coverage, and keeps split shipping on. Staff need the Markets permission to manage it because existing roles do not receive it automatically.

The timeline (the dates are targets and may shift) is: feature preview from 2026-07-01 (selected when a development store is created), merchant rollout beginning on 2026-10-01 for stores whose apps are compatible, and all merchants on market-driven shipping by 2027-07-01. Until then the Help Center page for shipping options by market is labeled early access and only for certain stores, and a store keeps its profile-based setup until it is upgraded; a merchant can opt out during a window after the upgrade.

For apps the rule is simple. App-owned profiles keep working with deliveryProfileCreate and deliveryProfileUpdate and can now use coversAllItems. The merchant-owned profile fields and mutations (deliveryProfile, deliveryProfiles, deliveryProfilesCount, deliveryProfileLocationGroup, deliveryProfileLocationGroups, deliveryProfileCreate, deliveryProfileUpdate, deliveryProfileRemove) no longer represent the live merchant configuration on a shop that uses the new model: reads may return a stale snapshot and writes can succeed without changing anything. Readers should switch to Contextual Product Feeds (for sales channels) or read Market.delivery, writers should become app-profile integrations or write with marketCreate and marketUpdate, and the model of a shop is detected with ShopFeatures.marketDrivenShipping. Apps that ship from their own locations (fulfillment networks, print on demand) fit app-owned profiles; carrier-rate apps for the merchant’s own locations need the Markets API because, before the shop is upgraded, the merchant’s rates take precedence at a location that appears in both profiles.

A Delivery Customization Function changes the options that exist at checkout without changing the stored rates. export function cartDeliveryOptionsTransformRun(input) {
  const configuration = input?.deliveryCustomization?.metafield?.jsonValue ?? {};
  const expressCountries = configuration.expressCountries ?? ["ES"];
  const isClubMember = input.cart.buyerIdentity?.customer?.isClubMember ?? false;

  const operations = [];
  for (const group of input.cart.deliveryGroups) {
    const country = group.deliveryAddress?.countryCode;
    for (const option of group.deliveryOptions) {
      if (option.title === "Express" && !expressCountries.includes(country)) {

            deliveryOptionHandle: option.handle,
            title: "Standard (Coffee Club)",
          },
        });
      }
    }
  }
  return operations.length ? { operations } : NO_CHANGES;

Overrides, exemptions and product tax data

  • A single product can be taxed or not with "Charge tax on this product" (Admin API: ProductVariant.taxable). For a group, an override applies a tax rate to a collection of manually added products (not smart collections and not collections populated by an app) or to shipping charges, and the percentage entered is the amount to collect, not the amount exempted. Set 0 percent to exempt. An override beats the product category, and an unpublished collection works as an override carrier.

  • A customer’s tax exemption always wins over overrides. Customer exemptions can be set in the profile or with customerAddTaxExemptions (scope write_customers), whose enum covers rules such as EU_REVERSE_CHARGE_EXEMPTION_RULE; B2B company locations carry tax IDs and exemptions.

  • With Shopify Tax, product categories from the Standard Product Taxonomy decide exemptions and reduced rates, which reduces the need for overrides; with Manual Tax the overrides do the job.

  • "Company VAT number" in the checkout customer information triggers a reverse charge for a valid number on an eligible EU or UK cross-border order: VAT is removed and the customer reports it.

  • Charge tax on shipping rates is a global setting only for countries where tax on shipping is not automatic; in Australia, Canada, the European Union, New Zealand, Norway, Switzerland, the United Kingdom and the United States shipping is taxed where applicable regardless of it. When items in an order are not taxable the tax on shipping is proportional (by quantity, by price or exempt when everything is exempt, depending on the country), and in the EU and UK it follows the proportion of each VAT rate in the order.

  • Digital goods sold to EU consumers are charged VAT at the customer’s country rate; the Help Center lists OSS, Non-Union OSS and IOSS (physical goods only) and asks to collect two pieces of evidence of the buyer’s location.

  • Duties and import taxes can be charged at checkout when carriers support DDP labels, Shopify Fulfillment Network is not used and HS codes are set on products; the setting is managed in Taxes and duties and per market.

Payments

Choosing providers

Customers pay with the methods activated in Settings, Payments, Payment providers. A store can use Shopify Payments, a third-party provider or both, and add PayPal, Amazon Pay, Apple Pay, Google Pay, Shop Pay, manual methods and others. Three facts constrain the choice: Shopify Payments exists only in a list of countries (Spain is one of them), stores that sell subscription products need Shopify Payments as the primary gateway, and customers in Finland get no payment method preselected to comply with regulation.

Shopify Payments is the integrated processor. It needs two-step authentication on the account, accepts the major methods as soon as the store exists, and charges no third-party transaction fee on orders processed through Shopify Payments, Shop Pay and Shop Pay Installments or on manual methods such as cash on delivery and bank transfer; PayPal is exempt from the fee when Shopify Payments is the primary provider. It offers test mode, payouts with a schedule, a store currency setting for display and payout currencies, and "managed payment methods", which activate local methods by region (for example Bancontact for Belgium or BLIK for Poland) and personalize their order at checkout; that feature requires Shopify Network Intelligence to be activated in the customer privacy settings.

Source: Shopify Help Center: Shopify Payments

A third-party provider is either direct (the buyer pays on the store) or external (the buyer pays on a page hosted elsewhere). More than 100 card providers are available, and a provider can be the only card processor or can run alongside Shopify Payments. Third-party transaction fees apply to every transaction processed through third-party and alternate gateways, even when Shopify Payments is activated. Using Shopify Payments next to one direct third-party provider is available on request: the provider remains the primary processor for cards, Shopify Payments handles Shop Pay and local payment methods that the provider does not offer and can recover failed card payments. Wallets are routed to the provider that offers them, and the recovery applies only to credit and debit cards (not to wallets, local methods or recurring subscription charges). Fees there are the third-party fee for the provider, the standard Shopify Payments rate plus a 1.25 percent premium for Shopify Payments transactions and the same for recovered payments; Shopify Capital eligibility counts both providers, Shopify Protect covers only Shopify Payments transactions, and multi-entity stores can use only Shopify Payments as a direct provider. The feature is in early access for Plus stores with a contract.

Source: Shopify Help Center: Using Shopify Payments with a third-party provider

Manual payment methods (cash on delivery, bank deposit, money order, custom) create unpaid orders that the merchant marks as paid after receiving the money; there are no transaction fees. Custom manual methods have a name, additional details and payment instructions; the names Bank Deposit, Cash, Cash on Delivery (COD), custom, External Credit, External Debit, Gift Card, Money Order and Store Credit are reserved. In the API orderMarkAsPaid (scope write_orders and the mark_orders_as_paid permission) performs the same action.

Authorization and capture

A card payment is authorized (checked and held) and then captured (charged) within the provider’s authorization period. The store setting in Settings, Payments, Payment capture chooses when:

  • Automatically at checkout (the default): the payment is captured at the sale.

  • Automatically when the order is fulfilled: authorized at checkout and captured when the whole order is fulfilled, provided the authorization has not expired; a notification email can warn one day before expiry.

  • Automatically per fulfillment (Plus only): captured as line items are fulfilled.

  • Manually: the order stays Authorized until the merchant captures it, which suits fraud review, accounting rules that require capture on fulfillment, regulations that require cash on delivery to be offered, or multiple captures.

Capture settings apply to online store orders only, not to POS. Building a payment gateway with a payments extension

Third-party gateways that integrate with Shopify checkout are payments extensions built on the Payments Platform. They can be built only by approved Payments Partners (custom payments extensions are limited to eligible Plus merchants), and a public listing requires meeting the published criteria. The five types are:

  • Credit card payments, with 3D Secure and optional UI extensibility for extra fields such as installments.

  • Custom credit card payments, where the partner defines the hosted fields.

  • Alternative payment extensions (onsite), where partners collect extra fields and complete the payment with or without redirecting the buyer.

  • Offsite payments, which redirect buyers to an app-hosted page.

  • Redeemable payments for third-party gift cards.

The supported operations are charge, refund, authorize, capture and void, and the methods include cards, buy now pay later and installments, bank transfers, cryptocurrency, cash and ATM and wallets (with limitations). The lifecycle: a merchant installs the app, configures it, the app marks itself ready through the Payments Apps API, the merchant activates it and deactivates the legacy gateway to avoid duplicates. The Payments Apps API endpoint is https://{shop_domain}/payments_apps/api/2026-10/graphql.json, requires an approved partner and resolves, pends or rejects payment sessions and rejects or resolves captures, refunds and voids. The scopes write_payment_gateways and write_payment_sessions are granted automatically through the extension and are omitted from the first deployment of shopify.app.toml.

Customizing payment methods with a Shopify Function

A Payment Customization Function changes the methods shown in checkout: hide, rename, reorder, set payment terms and, for B2B, add a review requirement. The target is cart.payment-methods.transform.run. The documented limits are: at most 25 active payment customization functions per store; the function input always lists all payment methods, but operations on restricted methods have no effect; hiding by placement (the Express section versus the payment section) works only on Plus and elsewhere the whole method is hidden; wallets and the native gift card field cannot be renamed (names that are logos, such as Shop Pay, Apple Pay and Google Pay), wallets can be removed from the Express section but not reordered; Point of Sale does not run payment customizations; in Shop Pay they apply only to the native gift card field; payment terms apply to the single order, exist only on Plus, cannot be set on accelerated checkouts, and a D2C checkout with payment terms shows only deferred options. Testing payments without real money

There is no real-money test on a development store: dev stores are always password protected, cannot be transferred and do not support real transactions, so tests use one of three gateways.

  • The Test payment gateway: a payment provider any store can activate after choosing a paid plan, replacing the card provider while active (deactivate Shopify Payments by switching to a third-party provider first). It accepts the name on card "Test payment gateway", any future expiry, any 3-digit CVV and the card numbers 1 (approved), 2 (declined) and 3 (gateway failure). Real cards are rejected. It does not work with Shopify POS or subscription products; the test amount must exceed the equivalent of 1 USD.

  • Shopify Payments test mode (Settings, Payments, Manage, Enable test mode): real cards are not accepted for orders, but express wallets such as Apple Pay and Google Pay can still complete with real cards and no charge (check for the test banner on the order), local methods such as iDEAL are not available, and POS readers, Shop Pay Installments and PayPal Wallet are not covered. Published test card numbers include 4242424242424242 (Visa), 5555555555554444 (Mastercard) and 378282246310005 (American Express, 4-digit security code); failure cards include 4000000000000002 (declined), 4000000000009995 (insufficient funds), 4000000000000069 (expired) and 4000000000000259 (dispute). The expiry must be in the future and the name needs at least two words. A Shop Pay test card is added by starting the card nickname with test_card.

  • Test mode of a third-party provider, using that provider’s own test credentials.

Test orders and simulated transactions do not appear in payouts or reports. Customers cannot place live orders while a payment provider is in test mode, and shipping labels bought for test orders are charged, so test orders must not be fulfilled. Pitfalls

  • Treating a profile as a rate table: a variant is in exactly one profile, and rates from several profiles are summed unless the names match or the store uses shipping options by market.

  • Writing to merchant-owned delivery profiles on a shop that moved to market-driven shipping: calls may succeed and change nothing. Detect ShopFeatures.marketDrivenShipping first.

  • Creating a carrier service on API 2026-10 and expecting rates: it is registered but not placed in any profile.

  • Weight-based rates with products without weight, which also produces a weight of 0 for backup rates.

  • Computing a free-shipping threshold from the base currency in a theme: use the presentment amounts the cart returns.

  • Manual Tax together with Basic Tax or Shopify Tax in the EU and UK, which breaks duty collection.

  • Tax override percentages entered as the exempt part instead of the collected part, and overrides on smart collections, which are not supported.

  • Showing tax numbers from the Storefront cart: the tax and duty fields of CartCost are deprecated.

  • Combining automatic capture with an app that also captures payments.

  • Testing with Shopify Payments test mode in a production store, which blocks real card orders while it is on.

  • Fulfilling test orders, which buys real shipping labels.

  • Relying on payment customizations in POS or in Shop Pay (only the gift card field is customizable there) or hiding Express placements on non-Plus stores (the whole method is hidden instead).

  • Renaming a carrier-calculated option without its carrier name: the carrier name is always prepended.

  • Using the REST CarrierService page as an API reference for new code: it documents the callback wire format that both APIs share, but REST is legacy.
