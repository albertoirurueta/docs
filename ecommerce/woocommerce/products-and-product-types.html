Products and Product Types

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

A WooCommerce product is not one thing. It is a post with a type, and the type decides which class loads it, which fields the editor shows, how it is priced, whether it can go into a cart and what the storefront draws instead of the add-to-cart button. Four types ship with WooCommerce (simple, variable, grouped and external), two flags (virtual and downloadable) change what a simple product needs from the shop, a variation is a child of a variable product, and an extension can add a type of its own. This page covers all of them with the catalogue of the Pocket Coffee shop: the variable product "Single-origin beans" with 18 variations, the simple "Starter kit", a grouped "Brew at home", an external "Guest roaster box", a downloadable "Brewing guide" and a custom type, the "Tasting flight". It then goes into attributes, the fields of the classic product editor, the native variation galleries that WooCommerce 10.9.0 added, queries, the way each type behaves in the REST API, the Store API and WP-CLI, and what happened to the block product editor, which was deprecated in 10.9.0 and removed in 11.0.0.

The page was written against WooCommerce 11.2.1 (the stable release of 2026-10-09; 11.3.0-beta.1 followed on 2026-10-26) on WordPress 7.1.3, PHP 8.3.36 and MariaDB 11.8.9, and checked on 2026-10-27. Products work the same on every hosting plan and in the free plugin; subscription, bundle and booking products come from paid extensions that use the mechanism of the custom type section (see Subscriptions, Memberships and Bookings). Everything below was run on the lab store with the plugin pocket-coffee-products: the catalogue is created with CRUD objects and a WP-CLI command, the editor was driven in a headless Chromium, and the storefront, the REST API, the Store API and WP-CLI were called for each type. The CRUD classes themselves (getters, setters, data stores, meta) are the subject of CRUD Objects and Data Stores; the hooks used here follow Hooks: Actions and Filters; the storefront blocks that list products are in Product Collection and Blocks; the plugin skeleton is in Extension Development. PHP language details are in PHP classes and objects.

The product model

Types, classes and where a product is stored

WooCommerce stores a product as a row of wp_posts (post type product, or product_variation for a variation, with the parent in post_parent), its fields as rows of wp_postmeta, its type, categories, tags, global attributes and visibility flags as terms, and copies of some fields in lookup tables. HPOS changed that for orders only; products are still posts. The type is the term of the product_type taxonomy attached to the product, and wc_get_product() reads it to choose the class.

Type Class What it is How it is bought

simple

WC_Product_Simple

One purchasable item with its own price, stock, shipping data and SKU.

Add to cart; Store API add-item with the product id.

variable

WC_Product_Variable

A parent that holds attributes and a list of variations; the parent has no price of its own.

The shopper chooses attribute values; Store API add-item needs the variation attributes (woocommerce_rest_missing_attributes without them).

grouped

WC_Product_Grouped

A list of child products shown together, each with its own quantity.

Through the children; the group itself is not purchasable (woocommerce_rest_product_not_purchasable).

external

WC_Product_External

A product page whose button links to a URL on another site.

Never in the cart; the button submits to product_url.

variation

WC_Product_Variation (extends WC_Product_Simple)

One combination of attribute values of a variable product.

Through the parent; the cart line is the variation.

The slugs are the constants of Automattic\WooCommerce\Enums\ProductType (SIMPLE, VARIABLE, GROUPED, EXTERNAL, VARIATION); use them instead of string literals. ProductType::get_all() (added in 10.9.0) returns all five including the variation, which is not a type a merchant can choose; wc_get_product_types() returns the four selectable types as a slug and label map and is filterable, so it also contains the types that extensions registered (the filter is product_type_selector). Two flags change a simple product without changing its type: virtual (no shipping: the Shipping tab disappears and needs_shipping() is false) and downloadable (the product carries files). A product can be both, and the lab store has one.

These are properties of the classes (is_purchasable() returns false), which is why the Store API refuses them. === Where each piece of data lives

Two consequences matter for code. First, never read or write the meta keys directly: the CRUD classes keep the lookup tables, the caches and the hooks consistent, and a direct update_post_meta( $id, '_price', ... ) skips all of them. The lookup table wc_product_meta_lookup is rewritten on save and is what the shop queries for price and stock filters. The attributes lookup table wc_product_attributes_lookup is updated by Action Scheduler jobs unless the option woocommerce_attribute_lookup_direct_updates is yes (it was no on the lab store): right after the seed command it had no rows and many woocommerce_run_product_attribute_lookup_update_callback actions were pending. The tool Regenerate the product attributes lookup table in WooCommerce > Status > Tools rebuilds it. Second, the product object cache: the feature product_instance_caching ("Cache Product Objects") is on by default for stores installed from 11.0.0 and is off for older stores that upgrade; with it on, product objects are kept in the object cache, which is one more reason to go through the CRUD classes.

Simple products

The Starter kit, a hand grinder plus 250 g of beans for 24.00 EUR, is the smallest useful product. The function that creates it is part of the catalogue file used by the whole page; the file is listed in full in the variable product section, and this is the part that builds the simple product:

function pocket_coffee_create_kit( string $sku_suffix = '' ): int {
	$product = new WC_Product_Simple();

The details worth remembering are all in that output. wc_update_product_stock( $product, $quantity, $operation ) changes the stock in one database update (set, increase or decrease) and fires the stock hooks; setting stock_quantity and saving does not protect against two requests overlapping. A scheduled sale is stored with its dates but is_on_sale() stays false and get_price() keeps the regular price until the first day, which a recurring Action Scheduler action (woocommerce_scheduled_sales, registered with as_schedule_recurring_action() in the source of 11.2.1, since the cron jobs moved to Action Scheduler in 10.1) turns into the sale price. catalog_visibility and featured are not meta: they are terms of the product_visibility taxonomy (featured, exclude-from-catalog, exclude-from-search, outofstock and the rated-N terms), which is why a product with visibility search carries the term exclude-from-catalog. A SKU must be unique across products and variations; wc_get_product_id_by_sku() finds the owner, and the WC_Data_Exception has the code product_invalid_sku.

Attributes

An attribute describes a product (origin, grind, size). It can be a global attribute, a taxonomy shared by all products whose terms the shop can filter and archive, or a product-level attribute that exists only on one product. Both are objects of the class WC_Product_Attribute, put into the product with set_attributes():

Property Meaning

id

The attribute taxonomy id for a global attribute (wc_attribute_taxonomy_id_by_name( 'origin' )), 0 for a product-level one.

name

The taxonomy name (pa_origin) for a global attribute; the display label (Grind) for a product-level one.

options

Term ids for a global attribute, an array of strings for a product-level one.

position

Order in the editor and on the product page.

visible

Show the attribute on the Additional information tab.

variation

The attribute defines variations. Only variable products use it.

The slug limit is 29 bytes (WordPress limits taxonomy names to 32 and WooCommerce keeps three for pa_), some names are reserved because WordPress uses them as query variables (type is one; WooCommerce keeps a list), and an existing slug is refused. The only attribute type on the lab store is select. The type wc-visual (colour swatches, added behind the feature wc-visual-attribute) is off by default; 11.1.0 made WooCommerce create nine default colour terms when a visual attribute is created, and 11.0.0 refined the swatch editor.

The Pocket Coffee catalogue uses both kinds. Origin is global, so shoppers can filter the shop by origin; Roast level (pa_roast) is global and descriptive (it does not create variations); Grind and Size exist only on the beans. The keys differ in a way that can trip code: for a product-level attribute get_attributes() and the variation attribute meta use the sanitized name (grind), get_variation_attributes() uses the label (Grind), and the REST API returns the slug Grind for the product and grind for the variation:

attributes: [["Origin", "pa_origin", true], ["Grind", "Grind", true], ["Size", "Size", true], ["Roast level", "pa_roast", false]]
variation attributes in REST: [["Origin", "pa_origin", "Ethiopia Yirgacheffe"], ["Grind", "grind", "Whole bean"], ["Size", "size", "250 g"]]

Compare attributes by lower-cased sanitized names, not by label, when a product-level attribute is involved. The terms of global attributes are ordinary WordPress terms (wp_insert_term(), term_exists()); Products > Attributes in the admin manages the attributes and their terms.

Variable products and variations

A variable product is a parent with attributes flagged variation and one WC_Product_Variation per combination. The shopper chooses a value of each variation attribute; the matching variation supplies the price, stock, SKU, image and shipping data. Pocket Coffee sells one product with three variation attributes, 3 origins x 3 grinds x 2 sizes = 18 variations.

The catalogue file follows. pocket_coffee_create_beans() builds the attributes, the parent and the 18 variations; the other functions create the remaining products and are used in the next sections. SKUs get a suffix because they must be unique in the whole catalogue (the lab store appends -PRD).

<?php
/**
 * Pocket Coffee catalogue built with the CRUD classes: one function per product type.
 *
 * @package PocketCoffee\Products
 */

defined( 'ABSPATH' ) || exit;

/**
 * A global attribute (a taxonomy named pa_<slug>) with its terms.
 *
 * @param string   $label Attribute label, for example "Roast level".
 * @param string   $slug  Attribute slug without the pa_ prefix.
 * @param string[] $terms Term names.
 * @return array<string,string> Term slugs keyed by term name.
 * @throws RuntimeException When the attribute cannot be created.
 */
function pocket_coffee_global_attribute( string $label, string $slug, array $terms ): array {
	if ( ! wc_attribute_taxonomy_id_by_name( $slug ) ) {
		$result = wc_create_attribute(
			array(
				'name'         => $label,
				'slug'         => $slug,
				'type'         => 'select',
				'order_by'     => 'menu_order',
				'has_archives' => false,
			)
		);
		if ( is_wp_error( $result ) ) {
			throw new RuntimeException( esc_html( $result->get_error_message() ) );
		}
		// The taxonomy is registered on the next request; register it now so terms can be added.
		register_taxonomy( wc_attribute_taxonomy_name( $slug ), array( 'product' ) );
	}

	$taxonomy = wc_attribute_taxonomy_name( $slug );
	$slugs    = array();
	foreach ( $terms as $name ) {
		$existing       = term_exists( $name, $taxonomy );
		$term_id        = $existing ? (int) $existing['term_id'] : (int) wp_insert_term( $name, $taxonomy )['term_id'];
		$slugs[ $name ] = get_term( $term_id, $taxonomy )->slug;
	}
	return $slugs;
}

/**
 * Term ids of a taxonomy for a list of slugs.
 *
 * @param string   $taxonomy Taxonomy name, for example pa_origin.
 * @param string[] $slugs    Term slugs.
 * @return int[]
 */
function pocket_coffee_term_ids( string $taxonomy, array $slugs ): array {
	$terms = get_terms(
		array(
			'taxonomy'   => $taxonomy,
			'slug'       => array_values( $slugs ),
			'hide_empty' => false,
		)
	);
	return array_map( 'intval', wp_list_pluck( $terms, 'term_id' ) );
}

/**
 * A product attribute. An id above 0 is a global attribute; id 0 is a product-level (custom) attribute.
 *
 * @param int              $id        Attribute taxonomy id, or 0.
 * @param string           $name      Taxonomy name (pa_origin) or the label of a custom attribute.
 * @param array<int,mixed> $options   Term ids for a global attribute, values for a custom one.
 * @param int              $position  Position in the list.
 * @param bool             $variation Whether the attribute defines variations.
 * @return WC_Product_Attribute
 */
function pocket_coffee_attribute( int $id, string $name, array $options, int $position, bool $variation ): WC_Product_Attribute {
	$attribute = new WC_Product_Attribute();
	$attribute->set_id( $id );
	$attribute->set_name( $name );
	$attribute->set_options( $options );
	$attribute->set_position( $position );
	$attribute->set_visible( true );
	$attribute->set_variation( $variation );
	return $attribute;
}

/**
 * A product category by slug, created when missing.
 *
 * @param string $name Category name.
 * @param string $slug Category slug.
 * @return int Term id.
 */
function pocket_coffee_category( string $name, string $slug ): int {
	$term = get_term_by( 'slug', $slug, 'product_cat' );
	if ( $term ) {
		return (int) $term->term_id;
	}
	return (int) wp_insert_term( $name, 'product_cat', array( 'slug' => $slug ) )['term_id'];
}

/**
 * Variable product "Single-origin beans": 3 origins x 3 grinds x 2 sizes = 18 variations.

	$codes   = array(
		'ETH' => 'Ethiopia Yirgacheffe',

		'BRA' => 'Brazil Cerrado',
	);
	$grinds  = array(
		'WHL' => 'Whole bean',
		'ESP' => 'Espresso',
		'FIL' => 'Filter',
	);
	$sizes   = array(
		'250' => array(
			'label'  => '250 g',
			'price'  => 8.90,
			'weight' => '0.25',
			'units'  => 1,
		),
		'1KG' => array(
			'label'  => '1 kg',
			'price'  => 29.90,

Reading the output from the top: the parent reports a price range, because get_price_html() asks get_variation_price() for the minimum and maximum of its variations; the attribute list shows the two kinds of attribute side by side, with the description-only pa_roast not flagged for variations; the default attributes are what the product page preselects (the shopper lands on Ethiopia, whole bean, 250 g); and get_available_variation() is the array that WooCommerce prints into the data-product_variations attribute of the storefront form and that the front-end script reads when the shopper changes a choice. Extensions add their own keys to it with the filter woocommerce_available_variation, as the Pocket Coffee roast batch does later (the key pc_roast_batch in the output).

What a variation inherits matters when you write code against it:

  • Name and description. A variation has no title of its own; its name is the parent’s title plus the attribute values. variation_description is its own optional text.

  • Tax class. The stored meta is parent, and get_tax_class() in the view context resolves it to the parent’s class.

  • Stock. A variation can manage its own stock (the lab variations hold 20 units each) or leave it to the parent (get_manage_stock() then returns parent).

  • Weight, dimensions and shipping class. An empty field falls back to the parent’s value; the beans set the weight on every variation (0.25 and 1) and nothing on the parent.

  • Image. The variation’s own image, otherwise the parent’s. Galleries are the subject of a later section.

  • Price. Always its own. The parent keeps a derived price index: WC_Product_Variable::sync() runs when a variation is saved and recomputes the minimum and maximum, which the shop uses to filter and sort and which are cached in the transient wc_var_prices_<id>. A plugin that changes prices on the fly through the woocommerce_product_variation_get_price filters adds its own factor to the cache key with woocommerce_get_variation_prices_hash, or shoppers see a stale price.

An empty attribute value on a variation means "any": the variation matches every value of that attribute, and the editor writes it when a merchant chooses "Any Grind…​" in the variation’s drop-down.

Virtual and downloadable products

/**
 * Badge text for a product, or an empty string. The options come from the Pocket Coffee settings tab; the defaults apply
 * when that plugin is not active.
 *
 * @param WC_Product $product Product.
 * @return string
 */
function pocket_coffee_roast_badge( WC_Product $product ): string {
	$date = $product->get_meta( 'roast_date', true );
	if ( ! $date || 'no' === get_option( 'pocket_coffee_show_badge', 'yes' ) ) {
		return '';
	}

	$label = get_option( 'pocket_coffee_badge_label', __( 'Roasted on', 'pocket-coffee-products' ) );

	$days  = (int) $roast->diff( new DateTimeImmutable( 'today', wp_timezone() ) )->format( '%r%a' );

		/* translators: %d: days since the roast */

	if ( $days > (int) get_option( 'pocket_coffee_freshness_days', 30 ) ) {
		$text .= ' ' . __( '(past peak)', 'pocket-coffee-products' );
	}
	return esc_html( $text );

Custom product types

A new product type is a PHP class, a registration, a way to show the right fields and a way to sell it. The Pocket Coffee "Tasting flight" is three 50 g sample bags sold as one item. It behaves like a simple product (one price, one stock, shippable), keeps the origins it contains and is shown as its own type in the editor, the REST API and the shop.

The class

<?php
/**
 * The "tasting_flight" product type: three 50 g sample bags sold as one purchasable item.
 *
 * @package PocketCoffee\Products
 */

defined( 'ABSPATH' ) || exit;

/**
 * A tasting flight is purchasable like a simple product but keeps its own data: the origins it contains.
 */
class WC_Product_Tasting_Flight extends WC_Product {

	/**
	 * Meta key that stores the origins (term slugs of the pa_origin attribute).
	 */
	const META_ORIGINS = '_pc_flight_origins';

	/**
	 * Product type slug. Stored as the term of the product_type taxonomy.
	 *
	 * @return string
	 */
	public function get_type() {
		return 'tasting_flight';
	}

	/**
	 * A flight can always be added to the cart with quantity 1 from the loop.
	 *
	 * @return string
	 */
	public function add_to_cart_text() {
		return $this->is_purchasable() && $this->is_in_stock()
			? __( 'Add flight to cart', 'pocket-coffee-products' )
			: __( 'Read more', 'pocket-coffee-products' );
	}

	/**
	 * Origins in the flight.
	 *
	 * @return string[] Term slugs.
	 */
	public function get_origins() {
		$origins = $this->get_meta( self::META_ORIGINS, true );
		return is_array( $origins ) ? array_values( $origins ) : array();
	}

	/**
	 * Set the origins in the flight. Persisted by save().
	 *
	 * @param string[] $origins Term slugs.
	 * @return void
	 */
	public function set_origins( array $origins ) {
		$this->update_meta_data( self::META_ORIGINS, array_values( array_map( 'sanitize_title', $origins ) ) );
	}
}

What breaks when the plugin goes away

A custom type is data that outlives the code. With the plugin deactivated, wc_get_product() could not find the class and fell back to WC_Product_Simple, wc_get_product_types() no longer listed the type, and saving the product wrote the term simple: the type was lost, the origins stayed in the meta. Activating the plugin again did not bring the type back; saving through the custom class did.

A production extension checks for its own products in its deactivation and uninstall code, or keeps the class available in a must-use plugin (see Extension Development). WooCommerce 11.2.0 hardened the REST controller for the same reason: an update that names an unknown type keeps the stored type instead of converting the product to simple.

Variation galleries

Until 10.9.0 a variation had a single image. Since 10.9.0 (2026-06-23) it can also have an ordered gallery of its own: the changelog entry reads "Add native variation gallery support: each variation can now have its own ordered image set, replacing the retired Additional Variation Images extension", with a migrator for the data of that extension and a fallback that reads its meta key _wc_additional_variation_images until the variation is saved by core. The feature id is variation_gallery; it is enabled and, since 11.1.0, its flag is deprecated (Package::is_enabled() always returns true), so there is nothing to switch on. 11.1.2 and 11.2.0 fixed a recursive request for variation data while rendering the gallery, and 11.2.0 stopped the editor from storing the inherited parent image as the variation’s own image.

In code

WC_Product_Variation uses the same two properties as the parent: image_id (the primary image) and gallery_image_ids (the rest). They are stored in the variation’s _thumbnail_id and _product_image_gallery meta. The variable parent’s get_available_variation() adds image_id, gallery_image_ids and the rendered gallery_images_html to the data of the form. Three PNG files had been imported into the media library beforehand with wp media import; the snippet below sets the first variation’s images and roast batch and reads them back:

In the editor

Each variation row has a Variation gallery box: a hero image, thumbnails, the count ("3 images"), Manage and Replace buttons and the hint "First image is used as the primary. Drag to reorder." The browser keeps the order in a hidden input named variable_gallery_image_ids[<loop>], a comma-separated list of attachment ids where the first is the primary image; WooCommerce hooks woocommerce_variation_after_upload_image to print the box and woocommerce_admin_process_variation_object to save it (set_image_id() for the first id, set_gallery_image_ids() for the rest). The headless run above read the box of the first variation, "3 images" and 353,354,355, which is the primary image plus the two gallery images the snippet had set, and the save of the batch field kept the images.

On the storefront

The default variation carries three images. The classic gallery of the block template drew the primary image and the thumbnails for it, and the gallery was swapped to the placeholder when the shopper chose a variation without images (the output of the storefront section above shows both states). A plugin that wants a different behaviour filters woocommerce_available_variation or the woocommerce_product_variation_get_gallery_image_ids filter that core’s own legacy fallback uses.

Before 10.9.0 a variation gallery needed the paid Additional Variation Images extension or a plugin of your own with a meta field, a media-frame script and a woocommerce_available_variation filter; that pattern still works, but it duplicates what the core editor now does and should be migrated (the migrator reads the extension’s meta key; custom keys are not touched).

The block product editor was removed

For several years WooCommerce developed a second product editor made of blocks (the "new product editor", "Product Editor v2" or "block product editor"), with its own React package @woocommerce/product-editor, a set of PHP classes under Automattic\WooCommerce\Admin\Features\ProductBlockEditor, product templates and extension APIs for registering blocks and sections. It ran next to the classic editor and never replaced it, and it was retired in three steps:

"Deprecate Product Editor v2" and removal notices for the extension APIs and the public PHP classes; the product editor template flag removed; a first redesign of the classic Variations tab (a DataViews tab behind the flag product_variations_classic_redesign, off by default).

Querying products by type

wc_get_products() and WC_Product_Query are the supported way to list products; the arguments (status, type, SKU, category, price, stock, dates, dimensions, paging) are documented in CRUD Objects and Data Stores. These points are specific to types. type accepts one slug or an array and includes custom types; variations are excluded unless you pass type variation, so a parent argument alone returns nothing; sku is a partial match. A custom query variable is added by filtering woocommerce_product_data_store_cpt_get_products_query and reading the variable from the second argument.

<?php

	array(
		'type'   => 'variable',
		'sku'    => 'PC-BEANS-PRD',
		'return' => 'ids',
	)
);
echo 'variable by SKU: ', wp_json_encode( $ids ), "\n";

	array(
		'type'    => array( 'simple', 'tasting_flight' ),
		'sku'     => '-PRD',
		'return'  => 'ids',
		'orderby' => 'ID',
		'order'   => 'ASC',
	)
);
echo 'simple and tasting_flight: ', wp_json_encode( $ids ), "\n";

	array(

Older recipes, rechecked

Books and tutorials from 2015, such as the Rauland and Ravensbergen titles, explain products with get_post_meta( $post->ID, '_price' ), $post->ID, direct wp_insert_post() of a product post and classic template overrides. The editor hooks of that period (the meta box actions, woocommerce_process_product_meta, woocommerce_product_tabs, product_type_selector) are still present and were used on this page. What changed is how the data is read and written (CRUD objects instead of post meta), the class lookup of types (the filter and the naming rule instead of a product_type switch), the editor extension model (the block editor came and went) and the block themes, where woocommerce_single_product_summary still fires (through the compatibility layer) but the hooks of the classic loop templates, for example woocommerce_before_shop_loop_item_title, belong to templates that block themes replace with the Product Collection block; see Hooks: Actions and Filters for the recipes of the books rewritten for blocks.

Pitfalls

  • Reading or writing _price, _stock or _sku with get_post_meta() or SQL skips lookup tables, caches and hooks; use the CRUD classes.

  • SKUs are unique across products and variations; save() throws product_invalid_sku.

  • A global attribute slug is limited to 29 bytes and cannot be a WordPress reserved name; product-level attribute keys differ in case between get_attributes() and get_variation_attributes().

  • The attribute lookup table is filled by Action Scheduler; it can be empty right after products were created in bulk, until the queue runs.

  • A grouped or external product is not purchasable, and its Store API add-item fails with woocommerce_rest_product_not_purchasable.

  • A downloadable file outside an approved directory is refused with product_invalid_download, and the refusal leaves a disabled rule.

  • A custom type class that does not follow the WC_Product_<Type> naming rule works in the editor and loses its type in REST writes.

  • Deactivating an extension that owns a product type turns its products into simple products as soon as one is saved.

  • A product type or a field added only with block-editor APIs has nothing to attach to in 11.x.

  • A variation created by code has menu_order 0 and shows newest first in the editor; set set_menu_order() when the order matters.

  • Do not rely on the stored price of a grouped product or on the attribute lookup table to be current in the same request.

Run on the lab store (WordPress 7.1.3, WooCommerce 11.2.1, PHP 8.3.36, MariaDB 11.8.9, block theme ec-block-child): the catalogue with all six product types through the CRUD classes and a WP-CLI command; the snippets for stock, sales, SKUs, attributes, downloads and approved directories, queries and variation galleries; a completed order that granted a download; the classic editor driven in a headless Chromium (the type drop-down, field visibility per type, a flight saved through the form, the variations panel with the custom field, the gallery box and the AJAX save); the storefront of the beans (default selection, gallery swap, price, badge, tabs); the REST API v3 for types, variations and galleries; the Store API for each type; WP-CLI product and variation commands; the compatibility shim of the removed editor; deactivating the plugin; PHP_CodeSniffer (WooCommerce-Core and WordPress-Extra) on the plugin.
