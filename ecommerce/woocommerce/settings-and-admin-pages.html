Settings and Admin Pages

This content was generated with the assistance of AI and should be verified against the official documentation before being relied on in production.

Every WooCommerce extension that a merchant can configure needs a place to keep its options and a screen to edit them. WooCommerce offers four such places that are in daily use and one that is still experimental: a settings object (WC_Settings_API) for a payment gateway, a shipping method or an integration; a whole tab under WooCommerce > Settings; a section under a tab that already exists; a standalone admin page, written in PHP or in React; and, behind a feature flag, a React renderer for the tabs and sections themselves. This page walks through all of them with one running example, the settings of the Pocket Coffee roast date badge, and then goes further into the React side: how a page is registered, how the bundle is built and loaded, and what the @woocommerce/components, @woocommerce/data and @woocommerce/navigation packages offer. The WordPress menus and Settings API underneath are covered in Administration Menus and Settings API.

The page was written against WooCommerce 11.2.1 (the stable release of 2026-10-09; 11.3.0-beta.1 followed on 2026-10-26) on WordPress 7.1.3 and PHP 8.3.36, and checked on 2026-10-27. Settings screens and admin pages are part of the free WooCommerce plugin and behave the same on every hosting plan; nothing here needs a WooCommerce.com account. The extension used throughout is the plugin pocket-coffee-settings: it registers a Pocket Coffee tab with two sections, an integration page for the roaster’s system, a Roast badge section under Products (classic filters), a Roast parcels section under Shipping (section registry), a PHP-powered Roast log page and a React-powered Pocket Coffee page. It was installed on the lab store, driven through the admin forms, WP-CLI, the REST API and a headless browser; the PHP was checked with the WooCommerce coding standards and the JavaScript was built and run. The plugin skeleton itself (headers, compatibility declarations, uninstall) is the subject of Extension Development; the hooks used here follow the conventions of Hooks: Actions and Filters; the REST routes that expose the settings are covered in REST API and Webhooks. The React and JavaScript basics the bundle relies on are in React build and deployment and JavaScript modules; PHP basics are in PHP namespaces and autoloading.

Where settings belong

The first decision is placement, because it decides the class, the hooks, the URL the merchant sees and whether the values are reachable through the REST API.

Approach Use when Trade-off

WC_Settings_API (through WC_Payment_Gateway, WC_Shipping_Method or WC_Integration)

A configurable component such as a payment gateway, a shipping method or a connection to an external service.

The fields live in a single array option named after the component. The base class draws and saves the form; the code that registers the component must call the save method.

WC_Settings_Page subclass

The extension has several related options and deserves a tab with one or more sections.

One more tab for the merchant to scan. WooCommerce draws the fields, saves them as one option per field and exposes them to the REST API.

Section under an existing tab

A few options clearly belong to a core tab, for example a product display option under Products.

The URL needs both a tab and a section, so it is harder to link from documentation. Two ways exist: two filters (works on every release) or a SettingsSection object (10.9.0 and later).

Admin page (wc_admin_connect_page or wc_admin_register_page)

A tool, report or dashboard with its own layout that does not fit a settings form.

A PHP page is simple but static; a React page needs a JavaScript build step and the wc-admin data layer.

Settings UI (experimental)

A settings tab or section that should render with React and custom controls.

Behind the settings-ui feature flag, off by default, and the API may change in any release.

Source: WooCommerce docs: Settings APIs and admin pages

WooCommerce’s UX guidelines for extensions give the same advice from the merchant’s side: include only the options that are crucial, choose smart defaults, group related options and keep frequently used ones at the top, avoid long lists, use impersonal titles and add helper text where an option is not obvious. Those rules decide how many fields the Pocket Coffee tab has (four saved options and a preview on the General section, three options on Coffee Club) more than any technical constraint does.

The Settings API

WC_Settings_API is the base class of every configurable WooCommerce component. A payment gateway (WC_Payment_Gateway), a shipping method (WC_Shipping_Method), an integration (WC_Integration) and each transactional email extend it. It defines the fields in an array, draws the form, validates the posted values and stores everything in one WordPress option; it does not create a screen and does not hook its own save method, so the class that registers the component has to do both. Gateways and shipping methods registered with WooCommerce already get a save action named after their id, and integrations are saved on woocommerce_update_options_integration_{id}. Extend WC_Settings_API directly only when none of those fits, and then print the form and call process_admin_options() yourself.

Field definitions

The fields are the form_fields array, usually built in init_form_fields(). The array key is the field key; it becomes part of the HTML field name and the key of the stored array. The default values and the extra keys that WooCommerce understands are:

Key Meaning

title

Label in the left column.

type

One of the built-in types (below) or a custom one. A missing type is text.

description

Help text under the field; with desc_tip set to true it becomes a tooltip.

desc_tip

true to show description as a tooltip, or a string to use as the tooltip text.

default

Value used before anything is saved. An empty default is stored as an empty string.

class, css

CSS class and inline style of the input.

placeholder

Placeholder text.

disabled

Renders the input disabled.

custom_attributes

Array of extra HTML attributes (min, max, step, required, data-*).

label

Checkbox only: the text next to the box.

options

select and multiselect: an array of value and label pairs.

sanitize_callback

Callable that receives the posted value and returns what is stored; checked before the validate methods.

The built-in types are text, safe_text (added in 7.6.0, mostly used for gateway-related settings), price, decimal, password, color, textarea, checkbox, select, multiselect and title. Each has a generate_<type>_html() method that prints the table row and a validate_<type>_field() method that cleans the posted value. A title field prints a heading and stores nothing. A checkbox is stored as yes or no; price and decimal run the value through wc_format_decimal(); password is trimmed but otherwise untouched so that special characters survive.

Loading, saving and where the data goes

init_settings() reads the option woocommerce_<id>_settings (the base class joins plugin_id, which is woocommerce_, the object’s id and the suffix _settings; get_option_key() returns it) and falls back to the field defaults while the option does not exist. get_option( $key ) returns one value, with the default when the key is missing. Saving is process_admin_options(): for every field except titles it calls get_field_value(), which resolves the cleaner in this order, and then stores the whole array in one update_option() call:

  1. the field’s own sanitize_callback, when it is callable;

  2. a method named validate_<key>_field( $key, $value ) on the object;

  3. a method named validate_<type>_field( $key, $value );

  4. validate_text_field() as the fallback.

The whole array passes through the filter woocommerce_settings_api_sanitized_fields_{id} just before it is written, which is the place for a rule that involves several fields. An exception thrown by a validate method is caught by process_admin_options() and stored in the object’s errors list; the field keeps the value it had before.

The example is the roaster integration of the Pocket Coffee shop: a base URL, an API token and a debug switch. The class is registered with the woocommerce_integrations filter in the main plugin file (shown later) and appears under WooCommerce > Settings > Integration.

<?php
/**
 * Integration with the roaster's system.
 *
 * @package PocketCoffee\Settings
 */

defined( 'ABSPATH' ) || exit;

/**
 * Settings stored in one option: woocommerce_pocket-coffee-roaster_settings.
 */
class PC_Roaster_Integration extends WC_Integration {

	/**
	 * Roaster API token.
	 *
	 * @var string
	 */
	public $api_token = '';

	/**
	 * Constructor.
	 */
	public function __construct() {
		$this->id                 = 'pocket-coffee-roaster';
		$this->method_title       = __( 'Pocket Coffee Roaster', 'pocket-coffee-settings' );
		$this->method_description = __( 'Connects the shop to the roaster system that publishes roast batches.', 'pocket-coffee-settings' );

		$this->init_form_fields();
		$this->init_settings();

		$this->api_token = $this->get_option( 'api_token' );

		add_action( 'woocommerce_update_options_integration_' . $this->id, array( $this, 'process_admin_options' ) );
		add_filter( 'woocommerce_settings_api_sanitized_fields_' . $this->id, array( $this, 'sanitize_settings' ) );
	}

	/**
	 * Field definitions (keys become keys of the stored array).
	 *
	 * @return void
	 */
	public function init_form_fields() {
		$this->form_fields = array(
			'endpoint'  => array(
				'title'       => __( 'Endpoint', 'pocket-coffee-settings' ),
				'type'        => 'text',
				'description' => __( 'Base URL of the roaster API.', 'pocket-coffee-settings' ),
				'desc_tip'    => true,
				'default'     => 'https://roaster.example.test/api',
			),
			'api_token' => array(
				'title'       => __( 'API token', 'pocket-coffee-settings' ),
				'type'        => 'password',
				'description' => __( 'Read from the roaster dashboard. Use a constant in wp-config.php for production.', 'pocket-coffee-settings' ),
				'desc_tip'    => true,
				'default'     => '',
			),
			'debug'     => array(
				'title'   => __( 'Debug log', 'pocket-coffee-settings' ),
				'type'    => 'checkbox',
				'label'   => __( 'Log API requests', 'pocket-coffee-settings' ),
				'default' => 'no',
			),
		);
	}

	/**
	 * Called as validate_{key}_field() for the field "api_token" (WC_Settings_API::get_field_value()).
	 *
	 * @param string $key   Field key.
	 * @param string $value Posted value.
	 * @return string
	 */
	public function validate_api_token_field( $key, $value ) {
		$value = parent::validate_password_field( $key, $value );
		if ( strlen( $value ) > 64 ) {
			// Show a red notice and keep the stored token.
			WC_Admin_Settings::add_error( esc_html__( 'The API token is longer than 64 characters; it was not saved.', 'pocket-coffee-settings' ) );
			return $this->get_option( $key );
		}
		return $value;
	}

	/**
	 * Filter applied to the whole settings array before it is stored.
	 *
	 * @param array $settings Settings about to be saved.
	 * @return array
	 */
	public function sanitize_settings( $settings ) {
		if ( isset( $settings['endpoint'] ) ) {
			$settings['endpoint'] = untrailingslashit( esc_url_raw( $settings['endpoint'] ) );
		}
		return $settings;
	}
}

Saving the form with an endpoint that ends in a slash, a debug box ticked and first a 70-character token and then a short one gave this on 11.2.1. The long token was refused with a red notice and the stored token stayed as it was; the short one was stored in clear text, because a password field only hides the characters in the browser:

integration (70 chars) notices: ['The API token is longer than 64 characters; it was not saved.']
integration option: {"endpoint":"https:\/\/roaster.example.test\/api","api_token":"tok_test_abc","debug":"yes"}

Three details are worth knowing. First, the trailing slash of the endpoint was removed by the woocommerce_settings_api_sanitized_fields_{id} filter, after the field validators ran. Second, the first version of validate_api_token_field() threw an Exception instead of calling WC_Admin_Settings::add_error(): the field was left unchanged, the page still said Your settings have been saved and no error appeared, because the integration screen does not print the object’s errors list. WC_Admin_Settings::add_error() queues a notice that the settings screen does print. Third, an option stored in plain text is readable by every plugin and by anyone with a database dump; for a real secret keep the value in a constant in wp-config.php or an environment variable, and let the field only show whether it is set.

Custom field types

A field with an unknown type is drawn by a method called generate_<type>_html( $key, $data ) on the object, when one exists, or else by whatever is attached to the filter woocommerce_generate_{type}_html (added in 6.5.0), which receives an empty string, the key, the field array and the settings object and returns the markup of one table row. The posted value is cleaned by validate_<type>_field() or by the text fallback. WC_Settings_API also offers helpers for the markup (get_tooltip_html(), get_description_html(), get_custom_attribute_html()) that the built-in renderers use.

Settings pages

A settings page is an object of a class that extends WC_Settings_Page. WooCommerce collects the page objects in WC_Admin_Settings::get_settings_pages(): it includes the core pages in a fixed order (General, Products, Tax, Shipping, Payments, Accounts and Privacy, Emails, Integration, Site visibility, Point of Sale and Advanced), then applies the filter woocommerce_get_settings_pages to the array, so an extension adds its object there. Everything else follows from the page id.

How a page is wired

WC_Settings_Page registers its hooks in the constructor, and every hook name contains the page id, so the subclass must set $this->id and $this->label before it calls parent::__construct():

Hook What it does

woocommerce_settings_tabs_array (priority 20)

Adds the tab, keyed by the page id.

woocommerce_sections_{id}

Prints the section links (only when the page has more than one section).

woocommerce_settings_{id}

Prints the fields of the current section.

woocommerce_settings_save_{id}

Saves the fields of the current section.

The tab is available at wp-admin/admin.php?page=wc-settings&tab=<id>, and a named section at &section=<section id>. On the lab store the Pocket Coffee tab appeared between Point of Sale and Advanced: the settings screen moves the tab with the id advanced to the end of the tab bar, so an extension tab never comes after it. The page class of the lab is loaded lazily, from the filter callback, because WC_Settings_Page only exists once WooCommerce has included it.

Sections

A page has one section by default: the empty string. Override get_own_sections() to return an array of section id => label; the empty key is the default section and should always be there. The links are only drawn when there is more than one section. The id goes into the URL through sanitize_title(), so keep it lowercase. The fields of a section come from, in this order:

  1. a method named get_settings_for_<section>_section() (get_settings_for_default_section() for the empty id);

  2. otherwise get_settings_for_section_core( $section_id ), which an extension can override to serve many dynamic sections from one method (the default implementation looks the section up in the section registry, covered below).

The older get_settings() still exists and WooCommerce still calls it internally for the sake of legacy classes, but it is deprecated since 5.4.0: do not override it in new code. Whatever the method returns passes through the filter woocommerce_get_settings_{id}, which receives the settings array and the section id, so other plugins can add or remove fields. The section list passes through woocommerce_get_sections_{id}.

The field array

WC_Admin_Settings::output_fields() draws a settings array and WC_Admin_Settings::save_fields() saves it. The array is a list of field arrays, which are close to the WC_Settings_API ones but not identical:

Key Meaning

id

The option name and the HTML id. Required for every field that is saved.

type

See the list below.

title

Label; name is the older spelling and still works.

desc

Description next to the field (for checkboxes, the text after the box).

desc_tip

true to show desc as a tooltip, or a string to use as the tooltip.

default

Value shown and returned while the option does not exist.

options

select, multiselect and radio: an array of value and label pairs. A select only accepts the keys of this array when saved.

class, css

CSS class and inline style of the input; the class wc_input_price formats a price in the browser.

placeholder, suffix

Placeholder and text printed after the input (the suffix of the freshness window prints "days").

custom_attributes

Extra HTML attributes: min, max, step, required.

row_class

CSS class of the table row (WooCommerce prefixes it with wc-settings-row-).

autoload

Whether the option autoloads; true unless set to false. Use false for rarely needed options.

field_name

Input name when it differs from the id, including array-style names such as my_option[key].

is_option

false for a field that is drawn but not saved (the badge preview below).

fixed_value

Draws a fixed value instead of the saved one.

disabled, show_if_checked, hide_if_checked, checkboxgroup, legend, tooltip

Checkbox options: disabled state, show or hide the following rows (yes or option), group several boxes in one row (start and end), group legend, and a tooltip.

The types WooCommerce draws itself are title, sectionend, info (read-only text in text), notice (notice_type and text), text, password, number, email, url, tel, color, date, datetime, datetime-local, month, time, week, textarea, select, multiselect, radio, checkbox, single_select_page, single_select_page_with_search, single_select_country, multi_select_countries, relative_date_selector, image_width (kept for old code) and slotfill_placeholder. They are also available as constants (WC_Settings_Page::TYPE_TEXT, WC_Settings_Page::TYPE_SELECT and so on). Any other type is passed to do_action( 'woocommerce_admin_field_' . $type, $field ), which is where a custom renderer attaches. A title field also fires woocommerce_settings_{id} right after it opens the table, and a sectionend fires woocommerce_settings_{id}_end and woocommerce_settings_{id}_after, which makes them anchors for extra rows or notes. Group the fields of one section between a title and a matching sectionend with the same id.

The Pocket Coffee tab

The tab has two sections. General holds the badge options (show it, label, freshness window, display mode) and a read-only preview drawn by a custom field type; Coffee Club holds the discount, the free-shipping threshold and the member roles. The class overrides get_settings_for_default_section() and get_settings_for_club_section(), attaches two option-specific sanitizers and an action that runs after the club section is saved.

<?php
/**
 * Tab "Pocket Coffee" under WooCommerce > Settings.
 *
 * @package PocketCoffee\Settings
 */

defined( 'ABSPATH' ) || exit;

use Automattic\WooCommerce\Admin\Settings\LegacySettingsPageAdapter;
use Automattic\WooCommerce\Admin\Settings\SettingsUIPageInterface;

/**
 * Settings tab with a General and a Coffee Club section.
 */
final class PC_Settings_Page extends WC_Settings_Page {

	/**
	 * Set the tab id and label before calling the parent constructor.
	 */
	public function __construct() {
		$this->id    = 'pocket_coffee';
		$this->label = __( 'Pocket Coffee', 'pocket-coffee-settings' );

		parent::__construct();

		add_action( 'woocommerce_admin_field_pc_badge_preview', array( $this, 'output_badge_preview' ) );
		add_filter( 'woocommerce_admin_settings_sanitize_option_pocket_coffee_freshness_days', array( $this, 'sanitize_freshness_days' ), 10, 3 );
		add_filter( 'woocommerce_admin_settings_sanitize_option_pocket_coffee_club_free_shipping', array( $this, 'sanitize_price' ), 10, 3 );
		add_action( 'woocommerce_update_options_pocket_coffee_club', array( $this, 'after_club_saved' ) );
	}

	/**
	 * Opt in to the experimental React settings UI. Ignored while the "settings-ui" feature is off.
	 *
	 * @return SettingsUIPageInterface|null
	 */
	public function get_settings_ui_page(): ?SettingsUIPageInterface {
		return new LegacySettingsPageAdapter( $this );
	}

	/**
	 * Sections of the tab. The empty key is the default section.
	 *
	 * @return array
	 */
	protected function get_own_sections() {
		return array(
			''     => __( 'General', 'pocket-coffee-settings' ),
			'club' => __( 'Coffee Club', 'pocket-coffee-settings' ),
		);
	}

	/**
	 * Fields of the default section.
	 *
	 * @return array
	 */
	protected function get_settings_for_default_section() {
		return array(
			array(
				'title' => __( 'Roast date badge', 'pocket-coffee-settings' ),
				'type'  => 'title',
				'desc'  => __( 'Shows the roast date on the product page of single-origin beans.', 'pocket-coffee-settings' ),
				'id'    => 'pocket_coffee_badge_options',
			),
			array(
				'title'   => __( 'Show badge', 'pocket-coffee-settings' ),
				'desc'    => __( 'Show the roast date badge on product pages', 'pocket-coffee-settings' ),
				'id'      => 'pocket_coffee_show_badge',
				'type'    => 'checkbox',
				'default' => 'yes',
			),
			array(
				'title'    => __( 'Badge label', 'pocket-coffee-settings' ),
				'id'       => 'pocket_coffee_badge_label',
				'type'     => 'text',
				'default'  => __( 'Roasted on', 'pocket-coffee-settings' ),
				'desc'     => __( 'Text shown before the date.', 'pocket-coffee-settings' ),
				'desc_tip' => true,
			),
			array(
				'title'             => __( 'Freshness window', 'pocket-coffee-settings' ),
				'id'                => 'pocket_coffee_freshness_days',
				'type'              => 'number',
				'default'           => '30',
				'suffix'            => __( 'days', 'pocket-coffee-settings' ),
				'desc'              => __( 'Beans roasted longer ago than this are labelled "past peak".', 'pocket-coffee-settings' ),
				'desc_tip'          => true,
				'custom_attributes' => array(
					'min'  => '1',
					'max'  => '365',
					'step' => '1',
				),
			),
			array(
				'title'   => __( 'Display mode', 'pocket-coffee-settings' ),
				'id'      => 'pocket_coffee_display_mode',
				'type'    => 'select',
				'default' => 'date',
				'options' => array(
					'date'     => __( 'Roast date', 'pocket-coffee-settings' ),
					'relative' => __( 'Days since roast', 'pocket-coffee-settings' ),
				),
			),
			array(
				'title'     => __( 'Preview', 'pocket-coffee-settings' ),
				'id'        => 'pocket_coffee_badge_preview',
				'type'      => 'pc_badge_preview', // No built-in renderer: woocommerce_admin_field_pc_badge_preview prints it.
				'is_option' => false,              // Nothing to save.
			),
			array(
				'type' => 'sectionend',
				'id'   => 'pocket_coffee_badge_options',
			),
		);
	}

	/**
	 * Renderer of the custom field type "pc_badge_preview".
	 *
	 * @param array $field The field definition, after WC_Admin_Settings::output_fields() filled the defaults.
	 * @return void
	 */
	public function output_badge_preview( $field ) {
		$label = get_option( 'pocket_coffee_badge_label', __( 'Roasted on', 'pocket-coffee-settings' ) );
		?>
		<tr valign="top">
			<th scope="row" class="titledesc"><?php echo esc_html( $field['title'] ); ?></th>
			<td class="forminp">
				<span class="pc-roast-badge"><?php echo esc_html( $label . ' ' . wp_date( get_option( 'date_format' ) ) ); ?></span>
			</td>
		</tr>
		<?php
	}

	/**
	 * Fields of the "club" section (the method name comes from the section id).
	 *
	 * @return array
	 */
	protected function get_settings_for_club_section() {
		return array(
			array(
				'title' => __( 'Coffee Club', 'pocket-coffee-settings' ),
				'type'  => 'title',
				'id'    => 'pocket_coffee_club_options',

Saving, sanitizing and the order of the hooks

When the merchant presses Save changes, WC_Admin_Settings::save() checks that the user has the manage_woocommerce capability (otherwise it ends the request with a 403) and the nonce of the form (check_admin_referer( 'woocommerce-settings' )), fires the save hooks, queues the success notice and queues a rewrite-rule flush. For a WC_Settings_Page the page’s save() method calls WC_Admin_Settings::save_fields() on the fields of the current section. save_fields() handles each field by type: checkboxes become yes or no, textareas pass through wp_kses_post(), multiselects are cleaned item by item, a select is forced to one of the keys of its options (or the default), a password is only trimmed, and everything else goes through wc_clean(). Then two filters run, in this order, and the second can overrule the first:

  1. woocommerce_admin_settings_sanitize_option, with the cleaned value, the field array and the raw posted value;

  2. woocommerce_admin_settings_sanitize_option_{option name}, with the same arguments.

A filter that returns null skips the option: nothing is written and the stored value stays. The values are written with update_option(), with the autoload flag of the field. A trace of the save hooks on the lab store, recorded by a small development aid in the plugin that appends each hook name to an option, gave this order for the default section followed by the Coffee Club section:

woocommerce_update_options_pocket_coffee
woocommerce_update_options
woocommerce_settings_saved
woocommerce_settings_save_pocket_coffee
woocommerce_update_options_pocket_coffee_club
woocommerce_update_options_pocket_coffee
woocommerce_update_options
woocommerce_settings_saved

The default section does not fire a section-specific hook because its section id is empty, so code that must run on every save of the tab belongs on woocommerce_update_options_{id}; code for one section belongs on woocommerce_update_options_{id}_{section} (the class attaches after_club_saved() there). woocommerce_update_options fires for every settings tab and woocommerce_settings_saved is the last hook of the save.

The sanitizers did their work. Posting 900 as the freshness window stored 365; posting 45,50 as the free-shipping threshold stored 4550 and not 45.50, because wc_format_decimal() treats the comma as a thousands separator when the shop’s decimal separator is a dot. The first rule is a reason to add a sanitizer; the second is a reason to test with the locale of the shop:

option pocket_coffee_club_discount = "12.5"
option pocket_coffee_club_free_shipping = "4550"

A settings tab saves one option per field, so the values read back with get_option( 'pocket_coffee_freshness_days' ). Use WC_Admin_Settings::get_option( 'pocket_coffee_freshness_days', '30' ) when the field has a default and the option may not exist yet; it also understands array-style option names (my_option[key]). Compare with yes and no for checkboxes.

The experimental settings UI

WooCommerce 10.9.0 introduced a second renderer for settings: a React form built from DataViews' DataForm, mounted in place of the PHP table. The merchant-facing URLs, the permission check, the nonce and the save are unchanged, because PHP still owns the registration, the field schema and the persistence. The renderer is behind the feature flag settings-ui, which is false in the feature configuration shipped with 11.2.1, and WooCommerce’s own documentation marks the whole API (the PHP interfaces under Automattic\WooCommerce\Admin\Settings, the schema format and the @woocommerce/settings-ui package) as experimental and free to change in any release. PHP-powered pages

wc_admin_connect_page( $options ) tells the controller that a screen WordPress already renders belongs to WooCommerce Admin. The options are id (required: the name of the page in the controller), screen_id (required for a connected page: what PageController::get_current_screen_id() returns on that screen), title (a string, or an array of breadcrumb pieces of which only the first links to path), path (the page’s address), parent (the id of a parent page, for breadcrumbs), and the optional capability, icon, position and js_page. Connected pages get the WooCommerce Admin header; the page itself is drawn by the callback you passed to WordPress.

The screen id is built from the WordPress screen id, the action and, for the pages in a list of pages with tabs (wc-reports, wc-settings, wc-status, wc-addons), the current tab, and for a few tabs also the section. A submenu page under the WooCommerce menu with the slug pocket-coffee-roast-log therefore has the screen id woocommerce_page_pocket-coffee-roast-log, the value used above. Three filters adjust the computation. The names in the public documentation (wc_admin_pages_with_tabs, wc_admin_page_tab_sections, wc_admin_current_screen_id) are not the ones in the 11.2.1 source, which are woocommerce_navigation_pages_with_tabs, woocommerce_navigation_page_tab_sections and woocommerce_navigation_current_screen_id; use the latter, and check the version you target. woocommerce_navigation_connect_page_options filters the options of every connected or registered page, and woocommerce_navigation_get_breadcrumbs, woocommerce_navigation_is_connected_page and woocommerce_navigation_is_registered_page change the breadcrumbs and the detection.

When the lab opened the Roast log page, WordPress printed the callback’s output under the WooCommerce Admin header titled Roast log, and the submenu entry was highlighted under WooCommerce.

React-powered pages

wc_admin_register_page( $options ) takes the same options and adds the defaults parent null, capability view_woocommerce_reports, js_page true and path empty. The path is relative to the application: a value that does not start with wc-admin is turned into wc-admin&path=<path>, which WordPress shows as the menu link admin.php?page=wc-admin&path=<path>. With parent set to the id of an existing page (woocommerce is the top-level WooCommerce menu), the function calls add_submenu_page(); with parent null it calls add_menu_page() and the icon (a Dashicons class or a base64 SVG) and position options apply. The user needs the capability for the menu entry to show and the page to open. The public documentation says the default capability is manage_options; the source of 11.2.1 says view_woocommerce_reports, which shop managers have and administrators too. Pass capability explicitly, as the example does with manage_woocommerce.

const BadgeSettings = () => {
	const { settings, isRequesting } = useSelect( ( select ) => {
		const store = select( SETTINGS_STORE_NAME );
		return {
			settings: store.getSettings( GROUP )[ GROUP ],
			isRequesting: store.isUpdateSettingsRequesting( GROUP ),
		};
	}, [] );

		if ( settings ) {
			setDays( settings.pocket_coffee_freshness_days );

				onChange={ setDays }

				variant="primary"

				onClick={ () =>

							...settings,
							pocket_coffee_freshness_days: days,

			</Button>

 * Table of products read through the wc/admin/products store.
 */
const ProductsTable = () => {
	const query = getQuery();
	const page = parseInt( query.paged || '1', 10 );

	const { products, total, isLoading } = useSelect(
		( select ) => {
			const store = select( PRODUCTS_STORE_NAME );
			const args = { per_page: PER_PAGE, page, orderby: 'title', order: 'asc' };
			return {
				products: store.getProducts( args ),
				total: store.getProductsTotalCount( args ),
				isLoading: store.isResolving( 'getProducts', [ args ] ),
			};
		},
		[ page ]
	);

	const rows = ( products || [] ).map( ( product ) => [
		{ display: product.name, value: product.name },
		{ display: product.sku, value: product.sku },
		{ display: product.price ? Number( product.price ).toFixed( 2 ) : '-', value: Number( product.price || 0 ) },
		{ display: product.stock_quantity ?? '-', value: product.stock_quantity ?? 0 },
	] );

	return (
		<TableCard
			title={ __( 'Products', 'pocket-coffee-settings' ) }
			headers={ headers }
			rows={ rows }
			rowsPerPage={ PER_PAGE }
			totalRows={ total || 0 }
			isLoading={ isLoading }
			query={ { ...query, paged: page } }
			onQueryChange={ ( param ) => ( value ) => updateQueryString( { [ param ]: value } ) }
		/>
	);
};

The package also exports hooks (useSettings, useUser, useUserPreferences), hydration helpers (withSettingsHydration, withOptionsHydration, withCurrentUserHydration and so on, which fill a store from data that PHP printed into the page) and getFilterQuery, getReportTableData and friends for analytics pages. PHP can preload data: the filters woocommerce_admin_preload_options (a list of option names that appear in wcSettings.admin.preloadOptions) and woocommerce_admin_preload_settings (a list of settings groups, in preloadSettings) avoid a first request, and the filter woocommerce_admin_shared_settings adds keys to the wcSettings.admin object.

Two behaviours of the stores cost time on the lab store, and both are specific to extensions that keep their own options.

The options store is a closed list. /wc-admin/options only reads and writes the option names in a hard-coded array in Automattic\WooCommerce\Admin\API\Options (68 woocommerce_* options such as woocommerce_demo_store, woocommerce_default_country or woocommerce_manage_stock). An option of an extension is rejected with woocommerce_rest_cannot_view or woocommerce_rest_cannot_update. The filter that used to extend the list, woocommerce_rest_api_option_permissions, has been deprecated since 6.3.0. An extension’s options belong in a settings group (WC_Settings_Page or the woocommerce_settings_groups filter) and are read through SETTINGS_STORE_NAME, or are registered with register_setting() and show_in_rest and read through the WordPress core data store.

useSettings() needs a loaded group. The hook useSettings( group, [ ...keys ] ) returned an error on the first render of the lab page: the page showed WooCommerce’s Oops, something went wrong screen and the console printed Cannot read properties of undefined (reading 'dirty'). Its selector for the dirty flag reads the state of the group before the first request has created it. The hook works once the group is in the store: a test page that first selected getSettings( 'pocket_coffee' ) from the store, waited for the answer and only then rendered a child that called useSettings() printed the saved value without error. The example therefore selects from the store directly, which has no such assumption: getSettings( group ) triggers the request through its resolver and returns an empty object until the data arrives, and updateAndPersistSettingsForGroup( group, { [ group ]: values } ) marks the group dirty and posts the batch. If you use the hook, load the group first (for example with that selector in a parent component).

Pitfalls

  • The constructor of WC_Settings_Page builds its hook names from $this->id; an id set after parent::__construct() leaves the page registered under an empty id.

  • A WC_Settings_Page tab only shows for users with manage_woocommerce; the save is refused with a 403 for anyone else.

  • The woocommerce_get_settings_{tab} callback must return the received array for other sections, or the core fields vanish.

  • A sanitizer that returns an empty string writes an empty string; return null to keep the stored value.

  • wc_format_decimal() depends on the shop’s separators: test price fields with the shop’s real locale.

  • A password field is plain text in the database. A value that returns from get_option() is the secret itself.

  • A REST PUT response echoes the request; the stored value is what the sanitizers returned.

  • The names of the screen-id filters in the public documentation differ from the source of 11.2.1.

  • wc_admin_url() without a query array returns an address that does not exist.

  • The OPTIONS_STORE_NAME store cannot read an extension’s options; use a settings group.

  • useSettings() before the group is loaded fails the whole page; select from the store or hydrate first.

  • The experimental settings UI drops what it cannot describe in its schema (suffixes, custom rows): re-test each screen.

  • A bundle that needs a handle the page does not load runs nothing and reports nothing; read the dependency list in index.asset.php and the Network tab.
