Refresh token rotation and reuse detection

This documentation was generated with the assistance of AI. Please report any inaccuracies.

A client that holds a refresh token trades it at the token endpoint for a new access token. The default clients rotate refresh tokens (reuseRefreshTokens false), so every refresh also returns a new refresh token and the old one stops working. Spring Authorization Server does the rotation; this repository adds reuse detection on top: ReuseDetectingAuthorizationService, a decorator of the JDBC OAuth2AuthorizationService, records the SHA-256 hash of each rotated-out refresh token in consumed_refresh_tokens. If one of those tokens is ever presented again, the token was stolen or replayed, so the whole authorization is deleted: the attacker’s token and the legitimate client’s current refresh and access tokens all stop working.

At a glance

Item Value

Actors

A confidential client holding a refresh token (in this repository the bff, which refreshes on behalf of the browser session), auth-server; possibly an attacker holding a copied refresh token.

Client

bff: grant refresh_token, reuseRefreshTokens false, refresh token lifetime 8 hours, access token 10 minutes (DefaultClientDefinitions.bff). Any client created with the admin API and reuseRefreshTokens false behaves the same. A public client such as spa-public gets no refresh token in the authorization code grant (see Authorization code with PKCE for a public client).

Preconditions

The client was issued a refresh token by an earlier grant (for bff, the authorization code grant). Nothing to enable: the decorator is the OAuth2AuthorizationService bean built by JdbcAuthorizationServerConfiguration.

Endpoints

POST /oauth2/token with grant_type=refresh_token. The same detection applies to any lookup of a refresh token without a token type, as /oauth2/revoke and /oauth2/introspect make when no token_type_hint is sent.

Storage

oauth2_authorization (Spring Authorization Server schema, V100) and consumed_refresh_tokens (V230, foreign key to oauth2_authorization with ON DELETE CASCADE).

Steps

Normal refresh

  1. The client posts grant_type=refresh_token&refresh_token=RT1 to /oauth2/token, authenticating as usual (client_secret_basic for bff). In the bff this happens inside OAuth2AuthorizedClientManager, called by OAuth2ClientHttpRequestInterceptor when the access token of the session has expired.

  2. Spring Authorization Server calls findByToken(RT1, refresh_token). The delegate finds the authorization, so the decorator returns it unchanged.

  3. The framework checks that the refresh token belongs to this client and is active, then generates a new access token, a new refresh token RT2 (rotation) and, when openid was granted, a new ID token.

  4. It calls save(authorization). The decorator reads the stored version first (findById), saves the new one through the delegate and, because the refresh token value changed from RT1 to RT2, inserts the hash of RT1 with the authorization id into consumed_refresh_tokens (ON CONFLICT DO NOTHING).

  5. The client receives the new access token and RT2, and must drop RT1.

Reuse of a rotated token

  1. Someone presents RT1 again (an attacker with a copy, or a client that kept the old value).

  2. findByToken(RT1, refresh_token) finds nothing in oauth2_authorization, because the stored authorization now holds RT2.

  3. The decorator hashes RT1 and looks it up in consumed_refresh_tokens. It finds the authorization id, logs a warning (A rotated refresh token was presented again; revoking the authorization …​) and removes that authorization through the delegate. Its consumed_refresh_tokens rows go with it (cascade).

  4. The decorator returns null, so the token endpoint answers 400 invalid_grant.

  5. When the legitimate client next refreshes with RT2, the authorization no longer exists and it also gets 400 invalid_grant. In the bff, RestDocumentGateway reports the failed renewal as unauthorized, the SPA gets 401 and starts a new sign-in.

A token that was never issued, or whose authorization was already deleted (by a previous reuse or by ExpiredAuthorizationCleanupJob), is simply unknown: invalid_grant, nothing revoked.

The decorator and its table:

    @Override
    public void save(final OAuth2Authorization authorization) {
        final var previous = delegate.findById(authorization.getId());
        delegate.save(authorization);
        if (previous == null) {
            return;
        }
        final var oldToken = refreshTokenValue(previous);
        if (oldToken != null && !oldToken.equals(refreshTokenValue(authorization))) {
            jdbcClient.sql(INSERT_CONSUMED).params(hash(oldToken), authorization.getId()).update();
        }
    }

    @Override
    public void remove(final OAuth2Authorization authorization) {
        delegate.remove(authorization);
    }

    @Override
    public OAuth2Authorization findById(final String id) {
        return delegate.findById(id);
    }

    @Override
    public OAuth2Authorization findByToken(final String token, final OAuth2TokenType tokenType) {
        final var authorization = delegate.findByToken(token, tokenType);
        if (authorization != null || (tokenType != null && !OAuth2TokenType.REFRESH_TOKEN.equals(tokenType))) {
            return authorization;
        }
        jdbcClient.sql(FIND_CONSUMED).param(hash(token)).query(String.class).optional()
                .map(delegate::findById)
                .ifPresent(compromised -> {
                    log.warn("A rotated refresh token was presented again; revoking the authorization {}",
                            compromised.getId());
                    delegate.remove(compromised);
                });
        return null;
    }
-- Hashes of the refresh tokens that were rotated out of an authorization. Presenting one of them again means the
-- token was stolen or replayed, so the authorization is revoked.
CREATE TABLE consumed_refresh_tokens
(
    token_hash       varchar(64)              NOT NULL,
    authorization_id varchar(100)             NOT NULL REFERENCES oauth2_authorization (id) ON DELETE CASCADE,
    consumed_at      timestamp with time zone NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (token_hash)
);

CREATE INDEX ix_consumed_refresh_tokens_authorization ON consumed_refresh_tokens (authorization_id);

Tokens and claims

The refresh response has the same shape as the authorization code response: a new access_token (same claims as before, roles, tenant, aud, scope; amr, acr and auth_time keep describing the original sign-in), a new refresh_token, token_type, expires_in, scope and, with the openid scope, a new id_token.

Only hashes are stored in consumed_refresh_tokens, so the table cannot be used to obtain tokens. Lookups of other token types (access token, device and user codes) are forwarded unchanged.

How it is tested

  • auth-server/boot TokenFlowIT: refresh_whenTokenIsValid_rotatesTheRefreshToken (new access and refresh token, one authorization) and refresh_whenRotatedTokenIsReused_revokesTheAuthorization (the replay is refused, the authorization count drops to zero and the current refresh token is refused too); also revocation of a refresh token.

  • auth-server/infrastructure/persistence ReuseDetectingAuthorizationServiceIT: over the JDBC service and PostgreSQL, a replayed rotated token revokes the authorization, and a refresh token that is not rotated records nothing.

  • auth-server/infrastructure/persistence ReuseDetectingAuthorizationServiceTest: unit tests of each branch (new authorization, rotation, unchanged token, device and user codes forwarded unchanged, consumed and never-consumed tokens).
